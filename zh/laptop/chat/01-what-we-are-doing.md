## 1. 我们到底在做什么

**在敲下第一条命令之前，请先读完这段。之后的一切都会更好理解。**

### 你现在手上有什么

一个内部的「订单」服务。在 vSphere 里它占用了**三台虚拟机**——这正是这种情况通常的样子：

| 机器 | 上面跑着什么 | 地址 |
|---|---|---|
| `app` | 用 Java 写的 `orders-api` 应用，CentOS 7 | — |
| `db` | PostgreSQL，手工安装 | `192.168.10.30` |
| `mq` | Kafka，手工安装 | `192.168.10.40` |

这个应用用 Spring Boot 写成，作为一个普通的 systemd 服务运行，它的配置放在 `/etc/orders/application.properties` 里。有意思的地方就在这儿：

```properties
spring.datasource.url=jdbc:postgresql://192.168.10.30:5432/orders
spring.kafka.bootstrap-servers=192.168.10.40:9092
```

**这些地址是写死的。**不是名字——是数字。曾经有人立起了三台机器，把 IP 敲进配置里，从那以后这三个数字就撑起了整套部署。子网一变——应用就趴窝。数据库搬到另一台主机——你就得手工去改文件、重启服务。

如果你现在从中认出了自家的基础设施——是的，大家都是这样。

### 我们打算怎么处理它

我们**只搬 `app`**。另外两台机器哪儿也不去——取而代之，我们从 Cozystack 目录里取用现成的 Postgres 和 Kafka。

这个区别是根本性的。把三台虚拟机全部搬走，你不用我们也做得到——那样你只会得到同一座动物园，只不过换到了新硬件上。还是那个 2019 年装好的 Postgres，没人更新它，也没人给它做备份，因为「当时不是有个脚本嘛」。而一个托管服务到手时就带着复制、备份和监控，从此你再也不用为它操心。

**而且这个过程中数据一点都不能丢**——这么多年积攒的订单都得迁进新数据库。这是单独的一步，在真实的迁移里也是最让人提心吊胆的一步。

正是这个区别——「把动物园搬了过去」对上「把应用搬了过去，而把动物园扔掉」——才是这个工作坊的主题。

这条路分三个阶段。

**阶段 1 — 把镜像导出来。**需要把 vSphere 里那台虚拟机的磁盘转换成 Cozystack 能理解的格式，并放到集群能从中拉取的某个地方。这是第 1–3 步。

**阶段 2 — 在新家里把机器立起来。**从导出的镜像里立起一台虚拟机，这次是在 Cozystack 中，然后把它调回正常状态：它会没有网络，因为它周围的硬件已经变了。这是第 4 步和第 6 步。

**阶段 3 — 扔掉动物园。**我们从目录里立起 Postgres 和 Kafka，**把数据从旧数据库里迁出来**，再把应用从写死的 IP 重新配置到规规矩矩的名字上。这是第 5、7、8、9 步。

> **如果你从没用过 Kubernetes——没关系，这是刻意设计的。**所有术语都会边走边讲，而下一条消息就是一份小词典，其中这一切都被翻译成了 vSphere 的语言。
