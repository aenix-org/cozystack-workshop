# 实验 1 · 你的第一个应用

| | |
|---|---|
| **时长** | 25 分钟 |
| **它证明了什么** | 应用用文本描述，几秒钟内完成部署，而且你无需征得任何人的许可 |
| **你需要什么** | 实验 0 里的集群、`kubectl`、文件 `~/lab.kubeconfig` |

## 这为什么重要

在着手真正的任务之前，我们先拿一个无害的东西练练手。我们会部署一个极小的
应用，它什么都不做，只做一件事：显示**自己这份副本的名字**。

听起来毫无意义，但正是这个名字将成为接下来三个实验的主角。透过它，你会看到一份
副本死去又重生，看到它们增殖到六份，看到旧版本让位给新版本。

我们将用文本来部署：一个文件、一条命令。这个实验里没有鼠标，这是有原因的——我们
就从这里开始。

## 小词汇表

| 术语 | 它是什么 | 像……但是 |
|---|---|---|
| **Pod** | 应用的一份运行中的副本 | 像一台**虚拟机**，但 Pod 是一次性的。它不会被修复，也不会被备份——你删掉它，就会创建一个新的 |
| **镜像（Image）** | 应用连同运行所需的一切的快照 | 像一个 **VM 模板**，但不可变。你无法进去修改它——只能构建一个新的 |
| **Deployment** | 一份描述：用哪个镜像、保留多少份副本、如何更新它们 | 像一个 **vApp**，但它保存的是期望的副本数量，而不是对具体 VM 的引用 |
| **Service** | 副本背后的一个固定地址 | 像一个**负载均衡池**，但即使背后的每一份副本都被重建，这个名字也不会变 |
| **ConfigMap** | 存放在集群里的一个配置文件 | 像 **VM 磁盘上的一个文件**，但它独立于应用存在，在启动时被塞进去 |
| **清单（Manifest）** | 描述期望状态的文件 | 没有直接对应的东西，而这正是重点所在 |

## 步骤 1. 控制台在哪里结束，你的集群从哪里开始

📍 **位置：** 在笔记本电脑上。

Cozystack 控制台（dashboard）展示的是你**向平台订购的东西**：Kubernetes 集群、
数据库、队列、虚拟机——都是目录中的条目。实验集群 `lab` 在那里显示为单独一项：已订购、
正在运行。

控制台不会去看它的内部，也没法看。你的集群是一个独立的 API 服务器，有自己的地址
和自己的访问文件——就是那个 `~/lab.kubeconfig`；管理控制台并不和它通信。实验集群 `lab`
自己也没有图形化的控制台：在能挂给它的附加组件里，并没有列出这样一个。

由此划出责任边界，值得记住：**平台负责你所订购的东西，而订购之物内部的东西，由你
负责。** 在集群内部，工作通过 `kubectl` 进行——这条命令把对象的描述发送给它的
API 服务器，并向你展示此刻里面有什么。

我们来连接：

```bash
# KUBECONFIG —— kubectl 读取这个变量来得知该使用哪个访问文件。
# 这里指的是访问 lab 集群，而不是租户：文件不同，集群不同。
export KUBECONFIG=~/lab.kubeconfig
# get nodes =「显示节点」。回应确认 kubectl 连的是正确的地方。
kubectl get nodes
```

**你应该看到：** 一行，包含你的节点和状态 `Ready`。如果得到的却是连接错误——检查
`echo $KUBECONFIG`：这个变量需要在每个新的终端窗口里设置。

## 步骤 2. 部署应用

📍 **位置：** 在笔记本电脑上。

进入这个实验的文件夹——仓库你在实验 0 里已经拉取过了：

```bash
# 路径是相对于你克隆仓库进去的那个文件夹
cd labs/01-deploy
```

如果你还没有仓库：

```bash
# clone = 把整个仓库下载下来；旁边会出现一个同名的文件夹
git clone https://github.com/aenix-org/cozystack-migration-workshop.git
cd labs/01-deploy
```

文件夹里有 `rickroll.yaml`。在应用它之前——我们先弄清楚里面有什么。

<details>
<summary><b>细看：rickroll.yaml 里面有什么</b></summary>

文件里有四个对象，用 `---` 行隔开。我们按顺序过一遍。

### 第一个：Web 服务器的配置

```yaml
kind: ConfigMap
metadata:
  name: rickroll-conf
data:
  default.conf: |
    server {
      listen 8080;
      root /usr/share/nginx/html;
      location / {
        sub_filter '__POD__' '$hostname';
        sub_filter_once off;
      }
    }
```

`ConfigMap` 是把配置文件独立于应用放进集群的一种方式。里面是一份普通的 nginx 配置
（nginx 是一个 Web 服务器，就是它来提供我们这个页面），和虚拟机上放在
`/etc/nginx/conf.d/` 里的那份一样。

关键的一行是 `sub_filter '__POD__' '$hostname'`。它告诉 nginx：在你提供的页面里，把
文本 `__POD__` 替换成你所运行的那台机器的名字。在 Pod 内部，机器名就是 Pod 自身的
名字。页面就是这样知道是谁提供了它的。

为什么配置是一个单独的对象，而不是烤进镜像里：这样你就能改动它们而无需重新构建
镜像。我们会在关于滚动发布版本的实验里用到这一点。

### 第二个：页面本身

```yaml
kind: ConfigMap
metadata:
  name: rickroll-page-v1
data:
  index.html: |
    ...<div class="pod">为您服务的 Pod<b>__POD__</b></div>...
```

就是那个将被 nginx 替换的 `__POD__`。名字里的 `-v1` 并非偶然：在关于滚动发布版本的
实验里会出现 `-v2`，而在两者之间切换就是一次新版本的滚动发布。

### 第三个：应用

```yaml
kind: Deployment
spec:
  replicas: 1
```

`Deployment` 是对应用整体的描述。`replicas: 1` 是要保持运行多少份副本。注意措辞：
不是「运行一份」，而是**「保持一份」**。这个区别会在下一个实验里显现，当我们删掉
那份副本的时候。

```yaml
      image: nginxinc/nginx-unprivileged:1.27-alpine
```

镜像。我们选了 nginx 的非特权版本——它监听 8080 端口，并且不以 root 身份运行。
普通的 nginx 要求一些配置得当的集群不会授予的权限。这不是我们吹毛求疵——而是一项
安全要求，你在任何现代集群里都会遇到。

```yaml
      resources:
        requests: {cpu: 20m, memory: 32Mi}
        limits:   {cpu: 300m, memory: 128Mi}
```

两个不同的东西，人们却常常把它们搞混。

`requests` 是要**作为保证预留多少**。调度器用这个数字来决定 Pod 能放到哪个节点上。
最接近的类比是 vSphere 里的资源预留（reservation）。

`limits` 是它**不被允许超过**的上限。类比是 vSphere 里的 limit。

`20m` 读作「20 毫核」，也就是一个核的百分之二。我们故意只要一点点：应用极小，而在
关于扩缩容的实验里，一个较低的 request 能让你亲眼看到副本增长。

```yaml
      readinessProbe:
        httpGet: {path: /healthz, port: http}
```

就绪检查。集群会敲一敲这个地址，在得到回应之前不会把流量发给 Pod。正是它，将在
关于滚动发布版本的实验里提供零停机的更新：一份新副本只有在真正准备好处理请求
之后，才会开始接收请求。

### 配置是如何进到容器里的

两个 ConfigMap 我们已经描述过了，但它们本身只是待在集群里，永远到不了 nginx。有
两个块把它们联系起来——而这个实验全部的窍门就系于它们：

```yaml
          volumeMounts:
            - name: page
              mountPath: /usr/share/nginx/html
            - name: conf
              mountPath: /etc/nginx/conf.d
      volumes:
        - name: page
          configMap:
            name: rickroll-page-v1
        - name: conf
          configMap:
            name: rickroll-conf
```

从下往上读。`volumes` 声明：「拿这个 ConfigMap，把它变成一个装着文件的文件夹」。
`volumeMounts` 说：「把这个文件夹放到容器内部的这个路径上」。结果就是 `index.html`
落在 nginx 查找页面的地方，而 `default.conf` 落在它查找配置的地方。

从你熟悉的世界里最接近的类比，是把一个共享文件夹挂到虚拟机上。区别在于，其内容
作为一个独立的对象存在于集群里，你改动它们时无需触碰镜像，也无需触碰机器本身。

⚠️ **`volumes` 里的顺序很重要。** 关于滚动发布版本的实验会用一条命令来切换页面，这条
命令是**按编号**引用卷的——列表里的第一个。如果你把这两个块调换位置，命令就会不声
不响地把配置塞到页面的位置上，nginx 也就停止工作了。文件本身里对此有一条注释。安全
的做法——按卷的名字而不是编号做 patch-merge——在关于滚动发布版本的实验里讲解。

### 第四个：固定地址

```yaml
kind: Service
spec:
  selector:
    app: rickroll
  ports:
    - port: 80
      targetPort: http
```

`Service` 是一个固定的名字，应用的所有副本都站在它背后。你访问 `rickroll`，就会
到达其中的任意一份。

Service 和 Pod 之间的联系不是一份地址清单，而是一个**条件**：`selector: app: rickroll`
意思是「所有带标签 `app: rickroll` 的 Pod」。标签（label）是你贴到对象上的一对任意的
「键：值」，以便日后能凭它找到该对象；最接近它的是 vSphere 里的标签（tags），只不过
这里的标签不是用来用眼睛扫的，而是用来建立起作用的连接。一个带这个标签的新 Pod
出现了——它就自动加入负载均衡。它消失了——就退出。没有人用手去编辑那份清单。

这正是与负载均衡池的关键区别，在负载均衡池里你要把地址一个个写进去。

</details>

现在我们来应用它：

```bash
# apply =「把集群带到文件里所描述的样子」。四个对象用一条命令
# 一并创建；文件内部的顺序由集群自己搞定。
#   -f   从文件中取得描述
kubectl apply -f rickroll.yaml
```

**你应该看到** —— 四行关于对象被创建的信息：

```
configmap/rickroll-conf created
configmap/rickroll-page-v1 created
deployment.apps/rickroll created
service/rickroll created
```

等待副本启动：

```bash
# rollout status 会一直等到 Deployment 把事情办成：所需数量的副本
# 正在运行、并已就绪可以接收请求。到那时命令会自行结束。
kubectl rollout status deployment/rickroll
```

等待只是几秒钟的事。启动的不是一个操作系统，而是某个已在运行的操作系统里的一个
进程：节点上的内核早就起来了，为所有容器所共享。同样位置上的一台虚拟机则要花上
一两分钟才能启动——它得把自己的内核、各种服务和网络都拉起来。

## 步骤 3. 看看集群用这个文件做出了什么

📍 **位置：** 在笔记本电脑上。

集群存储的不是文件本身，而是它由文件创建出来的对象。我们来问问，我们所应用的东西
现在是什么样子：

```bash
# get deployment rickroll = 按类型和名字显示单个对象。
#   -o yaml   把它完整打印出来，形式和你可以手写出来的那种一样
kubectl get deployment rickroll -o yaml
```

输出很长：其中大部分是集群自己填进去的——默认值、内部字段、当前状态。用眼睛找到
这几行：

```yaml
spec:
  replicas: 1
  template:
    spec:
      containers:
      - image: nginxinc/nginx-unprivileged:1.27-alpine
```

这就是你写在文件里的东西。**在集群内部，一切都用文本来描述**——你所应用的，以及
集群交还给你的，都是如此。当你在实验 0 里通过 Cozystack 控制台订购集群时，它组装
出来的正是同样的文本，并发送给平台：按钮是文本之上的一层，而不是它的替代品。

区别在于事后留下了什么。文件你可以放进 Git、在应用前评审、查看是谁在何时改动过、
用一条命令回滚、在第二个集群里部署同样的东西而无需回想你在第一个里勾选了哪些框。
鼠标点一下不留任何痕迹：一个月后，没有人——包括你自己——会记得当时为什么设的正是
那个值。

## 步骤 4. 在浏览器里打开

📍 **位置：** 在笔记本电脑上。

**接下来会发生什么：** 应用生活在集群内部，从外面看不见。下面的命令会从你的
笔记本电脑往里开一条隧道。

```bash
# port-forward = 从笔记本电脑通往集群内部的一条隧道，只要命令在运行它就存活。
#   svc/rickroll   把隧道接到名为 rickroll 的 Service 上，而它再把
#                  请求转发到应用的一份存活副本
#   8080:80        左边的数字是笔记本电脑上的端口，右边是集群里 Service 的端口
kubectl port-forward svc/rickroll 8080:80
```

命令不会结束：它会一直把隧道开着，直到你停掉它。打开
<http://localhost:8080>。

**你应该看到：** 一个流光溢彩的标题、一句歌词，底部——是 Pod 的名字。把它和集群
显示的做个对照。

📍 **位置：** 在第二个终端窗口里。第一个正被隧道占着——命令运行期间，你在里面什么都
输入不了。打开一个新窗口，在里面重新设置访问文件：环境变量不会带进新窗口。

```bash
export KUBECONFIG=~/lab.kubeconfig
```

```bash
# get pods =「显示正在运行的副本」。
#   -l app=rickroll   不显示全部 Pod，只显示带标签 app=rickroll 的——
#                     正是 Service 用来找到它们的那个
kubectl get pods -l app=rickroll
```

名字对上了。正是这一份副本提供了那个页面。

关闭隧道——`Ctrl+C`。

## 检查

📍 **位置：** 在笔记本电脑上，在你之前操作 `kubectl` 的那同一个终端窗口里。

```bash
# 从实验文件夹里运行它：脚本会在自己旁边找它需要的文件。
# 名字前面的 ./ 意思是「就从这里运行这个文件」，而不是去系统文件夹里找它
./check.sh
```

⚠️ **在 Windows 上脚本从 WSL 运行**，而不是从 PowerShell——怎么装它，写在实验 0 的
开头。没有 WSL 你照样能完成这个实验，只是不会有产物报告。

脚本检查的不是清单被应用这个事实，而是实质上的工作：应用通过 HTTP 响应，响应里
含有一个 Pod 名字，而这个名字与一份实际运行中的副本相符。

## 清理

在实验 2、3 和 4 里你还会用到这个应用——现在别删。留着它很便宜：一份 nginx 副本只要
一个核的百分之二和 32 兆字节，而真到了要删它的时候——那是一条命令的事，资源在同一秒
就回到节点的共享池里。

## 我们现在会做什么了

- 分辨平台控制台在哪里结束、你自己的集群从哪里开始
- 用一个文件、一条命令部署一个应用
- 读懂一份清单，并解释其中每个块是做什么的
- 区分 `requests` 和 `limits`
- 理解 Service 是通过标签找到副本的，而不是通过一份地址清单
- 通过 `port-forward` 用浏览器进到集群内部

## 而在 vSphere 里这会是

一张申请 VM 的工单、一张向网络部门要地址的工单、一张向安全部门要证书的工单。快也
要好几天。而在这里——一个文件、一条命令。

**说实话，vSphere 更方便的地方。** 部署一台 VM 时，你得到的是一台完备的机器：你可以
进去、装任何东西、就地修改，并让它就那样运行下去。Pod 的构造不同——它是不可变的，
「进去修一修」在它身上毫无意义，因为下一次重启时改动就消失了。这会培养纪律，但一开始
让人恼火，假装不是这样就太傻了。
