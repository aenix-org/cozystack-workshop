# 实验 15 · 周一该做什么

| | |
|---|---|
| **时长** | 20 分钟，一条命令都不用敲 |
| **它证明了什么** | 你学到的东西可以从小处着手，应用到你自己的机器群上 |
| **你需要准备什么** | 只需要你自己，加上一份你的系统清单 |

这里没有命令，也没有 `check.sh`：只有周一才能检验这个实验。
这是一场关于接下来该做什么的对话——当测试环境关掉、工作里的一切都恢复原样之后。

## 我们最终得到了什么

在十四个实验里，你搭建起了一个能用的内部服务——「通行证」，员工通过它为访客申请通行证，安保在门岗看到名单，管理层每月看一次报表。每一部分都不是按顺序出现的，而是因为某个具体的痛点冒出来的：

| 出现了什么 | 是因为什么 |
|---|---|
| 自己的镜像仓库 | 安全团队禁止从互联网拉取镜像 |
| 一个缓存 | 遗留系统里的员工目录响应要 800 ms |
| 文档存储 | 通行证的字段各不相同：一次性、按周、车辆、团体 |
| 密钥存储 | 一次审计在清单（manifest）里发现了数据库密码 |
| 一个分析数据库 | 管理层想知道有多少访客、高峰在什么时候 |
| 一个 Bucket | 移动团队没地方放他们构建出来的 APK |
| 放进 Git 的基础设施 | 你们一共三个人，有人手动改了一下——然后全挂了 |
| 目录里属于你自己的一项 | 子公司也想给自己来一套同样的服务 |

这些服务你一个都没有安装或升级过：它们是目录里的条目，由平台负责。你唯一安装并修复过的，只有你自己的应用。

接下来——聊聊如何在测试环境之外把这件事重做一遍。

## 这为什么重要

这类培训最常见的结局是「挺有意思，但我们这儿行不通」。不是因为真的行不通，而是因为上完十四个实验之后，你还是搞不清在自己的基础设施里该从哪儿下手——那里有三百台虚拟机，一半是干什么的谁也想不起来了。

我们按顺序把它捋一遍：从哪里开始、哪些不要碰，以及怎么把意义讲给那些签预算的人听。

## 从哪里开始：第一步的三个候选

不要从最重要的应用开始，也不要从最荒废的那个开始。你要从「犯错代价小、成果又看得见」的那个开始。

### 候选一：反正你本来就打算重装的那个

每个人手上都有这么一套系统，早就决定「该把它迁到新的操作系统了」或者「该升个版本了」。这就是理想的第一步：反正你本来就要动它，风险已经算进计划里了，需要的审批数量也一分不多。

### 候选二：测试或演示环境

一份坏了也不心疼的生产应用副本。在这里你检验的是自己重现迁移的能力，而不是平台——平台你在工作坊里已经检验过了。区别在于，现在用的是你自己的镜像、你自己的网络、你自己的安全策略。

### 候选三：正在申请新资源的那个

一个来要几台虚拟机跑新服务的团队，是最省事的情况。什么都不用迁移，一切从零创建，你直接给他们看一个控制台（dashboard），而不是一张申请表。速度上的差别，两边都会看见。

## 一开始不要碰什么

**授权绑定到硬件的系统。** 在迁移任何东西之前先核对授权条款。有些产品按虚拟机监控程序（hypervisor）的物理核心数计算授权，迁移下来的花费可能比它省下的还多。

**你搞不懂的东西。** 如果这个应用是七年前某个承包商装的，从那以后没人进去看过，那迁移就会变成一场调查。这活儿能干，但不是第一个该干的。

**带有自身容错能力的集群系统。** 带复制的数据库、应用集群，一切自己盯着自己副本的东西。这里你得决定，现在由谁来负责容错——是应用还是平台——这是要和系统负责人另外谈的一件事。

## 一套行之有效的顺序

1. **搭起一个测试环境。** 不是为了迁移——而是为了让你能在同一个小时内验证任何一个想法，不用去走申请流程。一台服务器、一次安装、零承诺。
2. **把上面提到的系统迁一套过来。** 完整地、连数据一起，迁到「能跑、而且用户正在用着看着」的状态。
3. **跟它一起过一个月。** 在这里你会学到任何工作坊都给不了你的东西：它凌晨三点是什么表现、升级的时候什么会坏、监控里缺了什么。
4. **到现在才去为其余的部分做计划。** 用你在自己硬件上得到的数字，而不是演示文稿里的数字。

在第 2 步和第 3 步之间，你通常会想加快节奏。别这么做：让一套系统在生产里跑上一个月，比在同一周里迁十套系统教给你的更多。

## 如何把这件事讲给管理层

这场对话不会是关于技术的。通常有三样东西决定它。

**授权成本**——最常见的论据，但也是最滑不留手的。老老实实地算：省下来的不只是你划掉的那一行，还包括你花在迁移上的时间成本、团队的培训，以及两套平台同时运行的那段时期。

**发放资源的速度。** 这里你有第一手经验：你亲手在十分钟里拉起一个集群、五分钟里拉起一个数据库。拿它和同样一张申请在你公司里要走多久比一比。这是个业务方不用翻译就懂的数字。

**摆脱对单一供应商的依赖。** 一个这几年分量越来越重的论据。它单独用不太顶事，但和第一条搭在一起就行了：能够更换平台，正是让你在价格上有谈判筹码的东西。

最好别许下的承诺：它会更简单。不会的——至少第一年不会。它会更便宜、发放资源更快、不被单一供应商锁定，但它不会更简单。承诺简单，是让你半年后失去信任的最快办法。

## 有问题去哪里问

- **Telegram 上的社区**——就是工作坊所在的那个群。「这件事怎么做才对」这样的问题，任何时候都合适。
- **文档**——[cozystack.io/docs](https://cozystack.io/docs/)。
- **源代码**——[github.com/cozystack/cozystack](https://github.com/cozystack/cozystack)。
  如果某样东西的行为和文档写的不一样，通常直接去看 chart 比瞎猜要快。你在讲自己镜像仓库的那个实验里已经这么做过了。

## 我们现在会做什么了

- 按「犯错代价小」而不是「最重要」的标准，挑出第一套要迁的系统
- 把值得往后放的情况和现在就该接手的情况区分开
- 不向管理层承诺一个根本不会有的简单
- 知道在身边没人知道答案时该去哪里问

## 而在 vSphere 里，这会是

这场对话会更短：你已经知道周一该做什么了，因为你干这行已经十年了。差别就在这儿——不在技术上，而在于你在这里得从头把自己的习惯重新养一遍。

好消息是，这些习惯可以一点一点地攒起来，一次一套系统。坏消息是，头几个月你会比自己习惯的节奏慢。随着新习惯越攒越多，速度会回来——但你得提前把这段落差算进你的时间表里。
