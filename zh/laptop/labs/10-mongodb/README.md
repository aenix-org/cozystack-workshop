## 为什么这很重要

「通行证」服务上线时只有一种通行证——针对某个具体日期的一次性通行证。一个月后，
来自客户的一些细化需求到了，而且它们都很合理：

| 通行证类型 | 还需要什么 |
|---|---|
| 一次性 | 日期、入口 |
| 周卡 | 起止时段、入口列表、是否归还工牌的标记 |
| 车辆 | 车牌号、车型、是否带挂车、重量、车位号 |
| 团体 | 单位、联系人、陪同人、带年龄的参加者名单 |

在一张列固定的表里，这个任务有两种解法，而且两种都不好。

**方案一：一张包含所有列的表。** 你加上 `car_plate`、`car_model`、`trailer`、
`weight_kg`、`parking`、`valid_from`、`valid_to`、`badge_returned`、`organization`、
`contact`、`escort`——于是一张一次性通行证在十五个字段里有十一个是空的。半年后就会有
三十列，没人记得清哪些列对哪种类型是必填的，而第一个 `NOT NULL` 字段就会让一半的
场景失效。

**方案二：每种类型一张表。** 四张表而不是一张，外加第五张把它们串起来，好让保安能在
门口出示一份合并的名单。每一种新的通行证类型都意味着一次模式迁移、一次发布和一次
签核。而「给我看今天所有通行证」这个查询，会变成四段拼起来的 `UNION`，添加第五种时
还得改它。

**团体通行证上的参加者名单两种方案都装不下。** 它是变长的，所以还需要再来一张表，
带一个指回通行证的引用。

有第三条路：一种不要求所有记录都是同一形态的存储。在这个实验里，我们会立起 MongoDB，
往里放四张四种不同形态的通行证，并跨它们搜索。然后我们会老实看看为此付出了什么代价
——因为确实要付，而且不少。

Kubernetes 和 MongoDB 的术语在本实验中首次出现时会加以解释，其中一部分收进了下面的
小词汇表。

## 小词汇表

| 术语 | 是什么 | 类似……但 |
|---|---|---|
| **文档** | 一条记录。一组字段、嵌套对象和列表 | **表中的一行**，但相邻记录的字段集合可能不同，而这并不是错误 |
| **集合** | 一组文档 | **一张表**，但默认没有模式。你可以添加模式，但那是另一个决定 |
| **BSON** | 文档存储所用的二进制格式 | 类似 JSON，但带类型：日期就是日期，而不是字符串 |
| **副本集** | 若干副本，一个主节点，其余接替 | **一个 HA 集群**，但副本之间相互投票，所以数量得是奇数 |
| **`mongosh`** | MongoDB 的命令行 shell | **PowerCLI**，但它是完整的 JavaScript，而不是查询语言 |

本实验中剩下的词——_id、分片、点号字段表示法、稀疏索引、模式校验器、$lookup——都会
随进度引入，在首次需要它们的那一步讲解。现在无需死记：脱离了具体动作，它们记不住。

<details>
<summary><b>如果你想一次看到完整列表</b></summary>

| 术语 | 是什么 | 类似……但 |
|---|---|---|
| **`_id`** | 文档的唯一键 | **主键**，但如果你不设置，它会自动为你创建 |
| **分片** | 把数据拆分到多个副本集 | 关乎数据量，而非可靠性 |
| **点号字段表示法** | 用点号访问嵌套字段：`car.plate` | **文件夹中的文件路径**，但它也能深入列表：`members.age` |
| **稀疏索引** | 只收录存在该字段的文档的索引 | 当字段只存在于少数记录时，这是一种纯粹的必需 |
| **模式校验器** | 文档必须满足的规则 | **保存前的表单校验**，但它是手动、事后开启的——默认没有模式 |
| **`$lookup`** | 从另一个集合拉取数据的方式 | **JOIN**，但是单向的，而且明显更贵：连接不是由优化器选择的，而是靠暴力执行的 |

</details>

## 第 1 步。订购 MongoDB

📍 **位置：** 在浏览器里，在 Cozystack 控制台中，在你的租户里。

租户 → **创建应用** → `MongoDB`。

| 字段 | 值 | 为什么 |
|---|---|---|
| Name | `passes` | 短——之后你得在地址里键入它 |
| Version | `v8` | 当前分支 |
| Replicas | **1** | 教学测试环境。生产环境为什么是三个，紧接着下面说 |
| Size | `5Gi` | 四个文档只占几个字节，其余是余量 |
| Storage class | `replicated` | 数据会以三份副本落在不同节点上 |
| Resources preset | `s1.small` | 1 个处理器，2 GB |
| Sharding | 关闭 | 当数据在单台服务器上放不下时才分片 |
| Users | `passapp` 用户，**显式**设置密码 | 我们就用它来工作 |
| Databases | `passes` 数据库，`passapp` 担任 admin 角色 | 没有角色的用户不会被接受 |
| External | 关闭 | 我们不对外暴露它 |

⚠️ **务必手动设置密码并记下来。** 如果你把该字段留空，chart 会自己生成一个密码——
并把它放进一个在控制台里看不到的 Secret 里。你会得到一个能用却连不上的数据库。

从这里开始，有两个词后面会多次遇到。**Chart** 是平台用来部署服务的蓝图：一组模板
加上你在表单里填的值。最接近的类比是带设置向导的虚拟机模板。**Secret** 是集群里保存
密码和密钥的对象；在控制台里它作为应用卡片上的一个单独标签页显示。

⚠️ **没有角色的用户会导致部署失败。** 如果你在 Users 区块里创建了 `passapp`，却没有在
Databases 区块的任何数据库里给它授予角色，chart 就会停下并报错 "user is not assigned
to any database role"。这不是故障，而是对无用用户的一道防线，只是这条消息不容易一下子
找到。

⚠️ **单副本不是正常形态的 MongoDB，值得弄明白为什么。** MongoDB 是为三副本的集合设计的：
它们通过投票选出主节点，失去一个也不会停止工作。投票需要多数，所以副本数取奇数。只有
一个副本时没人可投票，为此 chart 会开启一个特殊的 `unsafeFlags` 模式。在实验里这能节省
测试环境的资源；在生产里绝不能这么做。

### 细看：mongodb.yaml 里面是什么

实验目录里有 `mongodb.yaml`：

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: MongoDB
metadata:
  name: passes
  namespace: tenant-workshopXX
spec:
  replicas: 1
  size: 5Gi
  storageClass: replicated
  resourcesPreset: s1.small
  version: v8
  external: false
  sharding: false
  users:
    passapp:
      password: 你的密码
  databases:
    passes:
      roles:
        admin:
          - passapp
  backup:
    enabled: false
```

`namespace: tenant-workshopXX` —— **托管服务运行在管理集群上你的租户里，而不是实验 0 的
实验集群里。** 这是两个不同的集群。

`users` 和 `databases` 是两张相互关联的映射表，它们之间的关联是必需的。`users` 列出账户，
`databases` 列出数据库以及谁在其中能做什么。`roles.admin` 授予在单个数据库内读、写和
修改结构的权限；`roles.readonly` —— 只读。

⚠️ 用户是在服务数据库 `admin` 里创建的，但权限是在你的数据库里授予的。因此连接字符串
会需要 `authSource=admin` —— 这一点下一步单独讲。

`sharding: false` —— 一个普通的副本集。开启分片会增加配置服务器和路由器：为了我们并不
需要的数据拆分，多出三四个 Pod。

这个文件应用的**不是实验集群**，而是租户——这意味着访问文件也得是租户的那个。kubeconfig
（含集群地址和登录数据的文件）从控制台获取：**Info → Secrets 标签页 →
`kubeconfig-tenant-workshopXX`**。把它保存到 `~/.kube/workshop`——每个实验里都用这个路径。

现在我们用文本来订购数据库。这条命令本身不安装任何东西：它把订单交给平台，平台在
自己那边把需要的一切拉起来。

```bash
# apply = 「把集群变成文件里所描述的样子」。
#   --kubeconfig ~/.kube/workshop  用哪个访问文件。不加它，kubectl
#                                  会使用默认访问，跑到错误的集群上去
#   -f mongodb.yaml                要应用哪个文件（-f = file）
kubectl --kubeconfig ~/.kube/workshop apply -f mongodb.yaml
```

**你应该看到** —— `mongodb.apps.cozystack.io/passes created`。`created` 这个词的意思是
订单已被接受，而不是数据库已就绪。

就绪需要三到五分钟：服务器启动、副本集初始化、用户被创建。你可以这样观察进展：

```bash
# get = 「告诉我现在有什么」。READY 列会告诉你订单是否已进入可用状态。
#   -n tenant-workshopXX  在哪个 namespace 里查找（namespace 是集群内部的一块隔断；
#                         你的租户正是这样一个独立的 namespace）
kubectl --kubeconfig ~/.kube/workshop get mongodb passes -n tenant-workshopXX
```

⚠️ **控制台里的 `mongodb-passes-credentials` Secret 在最初几分钟里密码会是空的。** 它保存
的是服务账户 `databaseAdmin` 的凭据，而 chart 只有在 operator（平台里那个把订单推进到
可用状态、之后持续照看它的程序）创建好用户之后才会填入它们——也就是在下一轮状态调谐时。
等几分钟再刷新页面。这个账户我们用不上：我们以 `passapp` 工作，它的密码是你自己设的。

## 第 2 步。创建一个工作 Pod

📍 **位置：** 在笔记本电脑上，在实验集群里。

布局和其他关于托管服务的实验一样。

**MongoDB 运行在管理集群上你的租户里。** 你在租户里的角色允许你订购和删除服务，但不
允许在那里运行自己的 Pod，也不允许转发端口。

**你的工作场地是实验 0 的实验集群。** 我们就从那里出发，走内部地址：

```
mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017
```

| 部分 | 含义 |
|---|---|
| `mongodb-` | Cozystack 目录给应用名加的前缀 |
| `passes` | 你在控制台里设的名字 |
| `-rs0` | 副本集名称。operator 就这样命名第一个集合的服务 |
| `tenant-workshopXX` | 你的租户。替换成你自己的编号 |
| `svc.cozy.local` | 管理集群的内部名称域 |
| `27017` | MongoDB 的标准端口 |

**Pod** 是 Kubernetes 中最小的执行单元：一个或多个容器，它们始终位于同一个节点上，并
共享同一个地址。最接近的类比是为单一任务而拉起的虚拟机，只不过它在几秒内创建、毫不
可惜地关掉。我们会用 `mongo:8.0` 镜像拉起这样一个 Pod：它里面装着 `mongosh` ——
MongoDB 的命令行 shell，你不必在笔记本电脑上安装它。

数据库地址连同用户名和密码写成一行——它叫连接字符串。在键入命令之前，我们先把它逐段
过一遍。

<details>
<summary><b>逐段解析连接字符串</b></summary>

```
mongodb://passapp:密码@主机:27017/passes?authSource=admin&directConnection=true
```

`mongodb://` —— 协议方案。接着是用户名、密码、地址、端口。

端口后面的 `/passes` —— **默认数据库**。连上就直接在它里面，无需单独的命令。

`authSource=admin` —— **到哪个数据库里去找账户本身。** `passapp` 用户是在服务数据库
`admin` 里创建的，而它的权限是在 `passes` 里授予的。没有这个参数，驱动会跑到 `passes`
里找账户，找不到，然后返回 "Authentication failed" —— 这条消息看起来像「密码错误」，会把
排查引向错误的方向。这是第一次连接托管 MongoDB 时最常见的错误。

`directConnection=true` —— 「直接连到这台服务器，别试图弄清副本集的组成」。没有这个参数，
驱动会向服务器询问集合里还有谁，得到的是成员的内部名称，而这些名称并不总能从外部解析。
只有一个副本时没什么可弄清的，所以直说更简单。生产环境里三副本则相反：不设这个参数，
因为那里想要的正是在旧主节点失效时自动切换到新的主节点。

**为什么地址和密码放进 Pod 变量，而不是直接写进命令。** 你在 `kubectl exec` 里写的一切
都会进入你 shell 的历史记录，以及节点上的进程列表。Pod 变量只设置一次，之后密码就不再
出现在命令里。

这并不能完全解决问题，坦白说更诚实：通过 `--env` 传入的值会留在 Pod 的 spec 里——任何有
权读取你 namespace 中 Pod 的人都能看到它，它存在集群数据库里，还会落进审计日志。对教学
测试环境这可以接受，对生产环境则不行：那里要把密码放进 Secret，通过 `envFrom` 接入。
关于 Secret 的那个实验讲的正是这件事。

</details>

拉起这个 Pod。把 `workshopXX` 替换成你的租户编号，把 `你的密码` 替换成你自己的密码：

```bash
# KUBECONFIG —— kubectl 使用哪个访问文件。这里是实验 0 的
# 实验集群：你只在它里面启动自己的 Pod，用这个访问不进租户。
export KUBECONFIG=~/lab.kubeconfig

# run = 「创建一个 Pod 并在其中运行这个镜像」。要紧的标志：
#   --image=mongo:8.0        运行什么。镜像里带有 mongosh shell
#   --restart=Never          只创建一个单独的 Pod，而不是 Deployment。否则
#                            每次它结束，集群都会把它重新拉起
#   --env=MONGO_URI=...      Pod 内部的环境变量。密码留在它里面，
#                            而不是在后续每条命令里重复
#   --command -- sleep 86400 用什么让容器保持忙碌。mongo 镜像默认会启动
#                            数据库服务器——我们不需要它，我们要的是一个可以进去的
#                            活着的容器。86400 秒就是一天
kubectl run mongo-workbench \
  --image=mongo:8.0 \
  --restart=Never \
  --env=MONGO_URI="mongodb://passapp:你的密码@mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017/passes?authSource=admin&directConnection=true" \
  --command -- sleep 86400

# wait = 「在条件满足之前不要交还控制权」
#   --for=condition=Ready  我们一直等到 Pod 自己报告就绪
#   --timeout=180s         等多久后返回错误，而不是永远挂着
kubectl wait --for=condition=Ready pod/mongo-workbench --timeout=180s
```

**你应该看到** —— `pod/mongo-workbench created`，随后是 `pod/mongo-workbench condition met`。

现在我们设置一条简短的命令，免得每次都要把这一大串都敲一遍，并检查与数据库的连接：

```bash
# mo —— 一个存活到你关闭终端窗口为止的快捷方式：在 shell 里
# 就是这样声明你自己的命令的。
#   exec        在一个已经运行的 Pod 内部执行某些东西
#   -i          把标准输入转发进去：没有它就没法喂入一段程序
#   sh -c '...' 我们在 Pod 里运行一个 shell，好让它自己替换 $MONGO_URI。
#               引号故意用单引号：替换变量的应该是 Pod，而不是
#               你的终端——否则密码会进入命令历史
#   --quiet     不打印 mongosh 的问候语，只留下答案
mo() { kubectl exec -i mongo-workbench -- sh -c 'mongosh --quiet "$MONGO_URI"'; }

# ping —— 一个服务请求，「你还活着吗？」。它不读也不写，只检查连接
# 以及凭据是否被接受。| 号把这一行送到 mongosh 的输入
echo 'db.runCommand({ ping: 1 })' | mo
```

**你应该看到** —— `{ ok: 1 }`。

`mongosh` 从标准输入读取程序，所以同一条命令能够吞下整个文件：`mo < passes.js`。

⚠️ **如果回答是 `Authentication failed`** —— 连接是通的，但凭据不对。按顺序检查：连接
字符串里的 `authSource=admin`；密码和你在控制台里设的一致；用户名是 `passapp`。要用改正后
的字符串重建 Pod：`kubectl delete pod mongo-workbench` 然后重来。

⚠️ **如果回答是 `getaddrinfo ENOTFOUND` 或者连接卡住** —— 名称无法解析。最可能是你没有
把 `workshopXX` 换成自己的编号，或者控制台里的应用还没就绪。

查看数据时，与其一条命令一条命令地来，不如在一个活着的 shell 里更方便——它一直开着，你在
里面一条接一条地敲查询：

```bash
# -it 而不是 -i：多了个 t ——「给我一个终端」。于是有了输入提示符、
# 上箭头的命令历史，以及高亮。没有 t，shell 会默默等待输入。
kubectl exec -it mongo-workbench -- sh -c 'mongosh "$MONGO_URI"'
```

**你应该看到** —— 一个形如 `passes>` 的提示符：你所进入的数据库的名字。

从这里开始，正文里的命令都按你在这个 shell 里键入的样子给出。退出——`exit`。

## 第 3 步。放入四张四种不同形态的通行证

📍 **位置：** 在笔记本电脑上，在实验集群里。

`passes.js` 文件是给 `mongosh` 的一段程序：它往数据库里添加四张通行证，并打印出一共有
多少个文档。事先一张表都不需要创建，紧接着下面会解释为什么。

```bash
cd labs/10-mongodb
# < 号把文件内容喂到命令的输入——就跟你在 mongosh shell 里
# 手动把文件的全部文本敲一遍是一回事。
mo < passes.js
```

**你应该看到** —— `документов в коллекции: 4`。

<details>
<summary><b>逐一解析我们放进去的内容</b></summary>

首先值得注意的一点：**并没有 `CREATE TABLE`**。`passes` 集合是在第一次插入的那一刻诞生
的。它没有模式——也就是说，默认情况下 MongoDB 对文档可以有哪些字段没有意见。

现在说文档。

**一次性通行证** —— 最短的形态：

```js
  {
    type: "разовый",
    guest: "Иванов Иван Иванович",
    host: "petrov@corp.ru",
    entrance: "Северная",
    valid_on: ISODate("2026-09-01T09:00:00Z"),
    purpose: "собеседование"
  }
```

六个字段，全是标量。在表里这就是普通的一行。

`ISODate(...)` 不是字符串，而恰恰是一个日期。MongoDB 以二进制 BSON 格式存储文档，其中
值是有类型的：日期、整数、浮点数、布尔值、二进制数据。这是与普通 JSON 的一个重要区别：
你可以按日期比较和排序，而按字符串 `"2026-09-01"` 就只有在书写格式碰巧走运时才行。

**周卡** —— 现在不是 `valid_on`，而是 `valid_from` 和 `valid_to`，而且不再是单个入口，
`entrances` 现在是**一个列表**：

```js
    entrances: ["Северная", "Южная"],
    badge_returned: false
```

列表就在字段里。在表里，这要么需要一张单独的「通行证—入口」表，要么需要一个用逗号分隔的
字符串，而那种字符串之后谁也没法好好搜索。

一次性通行证根本没有 `badge_returned` 字段。不是 `NULL`，也不是空——**这个文档里没有这个
字段。** 这是不同的事情，搜索方式也不同。

**车辆通行证** —— 出现了一个**嵌套对象**：

```js
    car: {
      plate: "А123ВС174",
      model: "ГАЗель Next",
      trailer: false,
      weight_kg: 3500
    },
```

所有和车辆相关的东西都放在单个 `car` 字段里。这不是内部塞了 JSON 的字符串，而是一个
完备的结构：你可以按 `car.plate` 搜索，并在它上面建索引。

**团体通行证** —— **一个对象列表**：

```js
    members: [
      { name: "Орлов Пётр", age: 16 },
      { name: "Волкова Мария", age: 15 },
      { name: "Зайцев Илья", age: 17 }
    ]
```

一个变长的参加者列表，每个人都有自己的字段。而且——注意——这个文档**没有 `guest` 字段**：
占据来宾位置的是一个单位和一个联系人。这个文档的形态与其他文档的不同，不在于某一个字段，
而在于本质。

文档模型存在的意义正在于此。没有空列，没有四张表，也没有把它们串起来的第五张表。

</details>

## 第 4 步。跨不同形态的文档进行搜索

📍 **位置：** 在工作 Pod 内部的 `mongosh` shell 里。

保安和管理层需要的一切都是普通的查询。它们的读法都一样：`db` 是你连接到的数据库，
`passes` 是其中的集合，接着点号之后是动作，括号里是筛选条件。条件总是写成一个对象：
「字段——它应该有什么值」。

**某个具体日期的所有通行证：**

```js
// find = 「显示符合条件的文档」
// { valid_on: ISODate(...) } —— 文档的 valid_on 字段必须恰好等于这个
// 日期。ISODate 是日期，不是字符串：比较按时间进行，而不是按写法
db.passes.find({ valid_on: ISODate("2026-09-02T07:30:00Z") })
```

**你应该看到** —— 一个文档，库兹涅佐夫的车辆通行证。

**只看车辆通行证：**

```js
// 针对普通字符串字段的条件：整体匹配，这里没有不区分大小写这回事
db.passes.find({ type: "автомобильный" })
```

**按车牌号搜索——通过点号深入嵌套对象内部：**

```js
// "car.plate" —— 通往文档内部的路径：car 对象里的 plate 字段。
// 路径两边的引号是必需的，否则 JavaScript 会按自己的方式理解这个点号
db.passes.find({ "car.plate": "А123ВС174" })
```

<details>
<summary><b>为什么这样能行，以及它与「内部塞了 JSON 的字符串」有何不同</b></summary>

`"car.plate"` 是通往某个字段的路径的点号表示法。MongoDB 理解文档的结构，能够深入其内部，
而不是把嵌套对象当作一段文本来存。

这个区别很实际。如果 `car` 作为一个内部塞了 JSON 的 `TEXT` 列放在关系表里，按车牌搜索就
意味着 `LIKE '%А123ВС174%'` —— 没有索引的全表扫描，还带误报。这里它是一个可以在其上建索引
的普通条件，而我们也会这么做。

⚠️ `"car.plate"` 两边的引号是必需的：没有它们，JavaScript 会把点号理解成访问对象属性，
从而搞不懂在问它什么。

</details>

**在多个入口处有效的通行证：**

```js
// entrances 不是字符串，而是一个列表：["Северная", "Южная"]。条件仍然像对
// 普通字段那样书写，MongoDB 会自己对列表的每个元素逐一检查
db.passes.find({ entrances: "Южная" })
```

注意：条件写得就好像 `entrances` 是一个值为 `"Южная"` 的普通字段，而实际上它是一个列表。
**MongoDB 自己就明白，如果一个字段是列表，条件就要对每个元素逐一检查。** 不需要单独的
「包含」语法。

**含有未成年人的团体通行证：**

```js
// 路径 members.age 深入一个对象列表——到达每个参加者的 age 字段。
// $lt = less than，「小于」。带 $ 的条件不是值，而是一种比较方式：
// 「字段必须小于 16」，而不是「字段必须等于 16」
db.passes.find({ "members.age": { $lt: 16 } })
```

点号路径也能深入对象列表：条件会对每个参加者逐一检查。`$lt` ——「小于」。这类条件大约有
二十个：`$gt`、`$gte`、`$in`、`$ne`、`$exists`、`$regex` 等等。

**所有指定了车辆的通行证：**

```js
// $exists 问的不是值，而是字段在文档中是否存在这件事本身：
// 「这个文档到底有没有 car 字段？」
db.passes.find({ car: { $exists: true } })
```

`$exists` 正是「字段不存在」与「字段为空」之间的那个区别。在表里这个问题不会出现：列总是在
那儿，唯一的问题是 `NULL`。

**给管理层的汇总——每种类型有多少张通行证。** 这里查询不是筛选文档，而是对它们求出一个
合计，所以命令也不同——`aggregate`。在键入之前我们先把它过一遍。

<details>
<summary><b>逐段解析聚合管道</b></summary>

MongoDB 里的聚合是一条**管道**：一列阶段，每个阶段都以上一个阶段的结果作为输入。就像
shell 里的命令管道，一个命令的输出进入下一个命令的输入。

`$group` —— 分组。`_id: "$type"` 的意思是「分组键是 `type` 字段的值」；名字前面的美元符号
表示「这是对字段的引用，而不是字符串」。`$sum: 1` —— 每个文档加一，也就是对它们计数。

`$sort: { count: -1 }` —— 按降序排列；`-1` 是「降序」，`1` 是「升序」。

在 SQL 里同样的结果 —— `SELECT type, count(*) FROM passes GROUP BY type ORDER BY 2 DESC`。
更短、更熟悉，而在这里诚实的比较对 MongoDB 不利：它的查询语言更啰嗦，也要花更长时间才能
掌握。

</details>

```js
// aggregate = 「让文档穿过一串阶段」。阶段按顺序执行，
// 每个阶段都接收上一个阶段产出的东西：
//   $group —— 按 type 字段的值把文档分到各组，并对每组计数
//   $sort  —— 按数量给各组排序，-1 表示「降序」
db.passes.aggregate([
  { $group: { _id: "$type", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
])
```

**你应该看到** —— 四行，形如 `{ _id: 'разовый', count: 1 }`。

## 第 5 步。为一个大多数文档都没有的字段建索引

📍 **位置：** 在工作 Pod 内部的 `mongosh` shell 里。

保安每天都按车牌号搜索。我们来看看现在这次搜索代价如何：查询和之前一样，只是我们要的
不是文档，而是一份关于数据库如何查找它们的报告。

```js
// explain = 「别给我文档，告诉我你是怎么查找它们的」
//   "executionStats"     报告模式：不只有计划，还有实际发生了什么
//   .executionStats      我们从回答里只取这一节，免得把全部都读一遍
// 报告里我们看 totalDocsExamined —— 为了返回一个文档，数据库读了
// 多少个文档
db.passes.find({ "car.plate": "А123ВС174" }).explain("executionStats").executionStats
```

**你应该看到** —— `totalDocsExamined` 等于集合中的文档数。数据库把它们全都过了一遍，才
找到一个。四个文档时这察觉不到，四十万个文档时就不然了。

我们来建一个索引——一个数据库用来找到所需文档、而不必挨个读完的独立结构：

```js
// createIndex = 「在这个字段上建一个索引，从此自己持续维护它」
//   { "car.plate": 1 }   在哪个字段上。1 是「升序」
//   name: "car_plate"    给索引起什么名字，以便日后认出并删除它
//   sparse: true         只有拥有该字段的文档才进入索引
db.passes.createIndex({ "car.plate": 1 }, { name: "car_plate", sparse: true })

// 我们重复同一份报告，并和上一份比较
db.passes.find({ "car.plate": "А123ВС174" }).explain("executionStats").executionStats
```

**你应该看到** —— `totalDocsExamined` 等于一，而计划里出现了 `IXSCAN` 而不是 `COLLSCAN`。
这些是查找方式的名称：`COLLSCAN` 是对整个集合的扫描，`IXSCAN` 是按索引查找。

<details>
<summary><b>什么是稀疏索引，以及它为什么出现在这里</b></summary>

`{ "car.plate": 1 }` —— 在哪个字段上建；`1` 表示「升序」，`-1` —— 降序。对于精确匹配搜索
方向无所谓；对于排序则有所谓。

`sparse: true` —— **只有拥有该字段的那些文档才进入索引。**

没有这个标志，MongoDB 也会给那三个没有车辆的文档创建索引条目，值为「字段不存在」。索引会
变大将近一倍，而那些条目毫无用处：没人会按「未指定车辆」这个条件去搜通行证。

在真实的通行证记录里，车辆通行证大约占百分之十。稀疏索引会比普通索引小十倍，维护起来也
便宜十倍。

⚠️ **稀疏索引是有代价的，你得知道。** 通过这样的索引按此字段排序时会丢掉没有该字段的
文档——它们不在索引里。这种情况下 MongoDB 会自己放弃索引、退回到扫描；不痛快的地方在于，
这件事是悄无声息发生的。

**现在说这一步的要点。** 在一个用单张表装下所有通行证类型的关系数据库里，`car_plate`
上的索引不得不建在一个九成行都是 `NULL` 的列上。有些数据库管理系统照样会把这样的行放进
索引，于是它膨胀。人们用部分索引来绕开这一点——一种和 `sparse` 同类的机制，只是并非到处
都有，也不是一眼就能想到。

所以问题是同一个问题。区别在于，这里它不是作为「把所有类型都放进一张表」的副作用而产生的：
我们没有那种为了少数记录而不得不创建的列。

</details>

## 一次可预见的失败 · 不在名单上的通行证

我们继续。门口的值班人员又开了一张一次性通行证——通过一段匆忙写就的脚本：

```js
// insertOne = 「添加一个文档」。里面有哪些字段，数据库不过问
db.passes.insertOne({
  tipe: "разовый",
  guest: "Николаев Сергей Игоревич",
  host: "petrov@corp.ru",
  data: ISODate("2026-09-04T09:00:00Z")
})
```

插入成功了：返回了 `acknowledged: true`（「已接受」）和一个新的 `_id` —— 文档的唯一键，
是数据库自己想出来的。我们来检查一下现在是不是有五个文档：

```js
// countDocuments = 「对符合条件的文档计数」。
// 空的花括号是没有任何限制的条件，也就是「全部」
db.passes.countDocuments({})
```

五个。现在做保安每天早上做的事——打开一次性通行证的列表：

```js
// 和搜索那一步一样的按类型筛选：显示 type 字段等于
// "разовый" 的通行证
db.passes.find({ type: "разовый" })
```

> **在继续读下去之前，停下来想一想。**
>
> 返回了多少张通行证？第五张在哪儿？同样的错误在关系数据库里会发生什么——为什么那样更好？

<details>
<summary><b>答案，以及一个比这个错误更宽泛的教训</b></summary>

返回了一张通行证，而不是两张。来宾尼古拉耶夫会到，保安找不到他，弄清楚要花一阵子——因为
文档**存在**，它**插入成功了**，而且哪里都没有记录任何错误。

原因是两个拼写错误：本应是 `type` 却写成了 `tipe`，本应是 `valid_on` 却写成了 `data`。
MongoDB 没有察觉，因为**集合没有模式，因此也没有关于哪些字段是正确的意见。** 对它来说，
`tipe` 和其他任何字段一样合法。

我们来找出受害者——那些根本没有 `type` 字段的文档：

```js
// $exists: false —— 与上一步相反：「字段不在文档里」。
// 这样的查询值得随手备着：它能显示出绕过模式积累了什么
db.passes.find({ type: { $exists: false } })
```

在关系数据库里，带 `tipe` 列的 `INSERT` 会立刻失败：`column "tipe" does not exist`。错误
会在测试时暴露，而不是一周后在门口。**这就是模式灵活性的主要代价：以前由数据库做的检查，
现在得由别人来做。**

**一个比这个错误更宽泛的教训。** 在这里重要的是别得出错误的结论。正确的结论不是「文档数据库
不好」，而是「默认没有模式并不意味着完全没有模式」。你的数据总是有一个模式：它要么被显式
描述，要么活在人们的脑子里和代码里，而在那里没人检查它。

我们来删掉这个损坏的文档，并开启校验。

</details>

我们删除没有类型的文档：

```js
// deleteMany = 「删除所有符合条件的文档」。条件和上面搜索时
// 一样——也就是说，你刚才看到的正是会被删掉的东西
db.passes.deleteMany({ type: { $exists: false } })
```

**你应该看到** —— `deletedCount: 1`。

现在我们开启校验——一条每个文档都必须满足的规则。它在 `validator.js` 文件里；在应用它
之前我们先把它过一遍。

<details>
<summary><b>逐段解析这条规则</b></summary>

```js
db.runCommand({
  collMod: "passes",
  validator: { $jsonSchema: { … } },
  validationLevel: "strict",
  validationAction: "error"
});
```

`collMod` —— 修改一个已有集合的设置。校验器是事后挂到活着的集合上的，什么都不需要停。

```js
      required: ["type", "host"],
```

必填字段。**注意列表里没有什么：`guest`。** 团体通行证没有来宾，取而代之的是一个单位。
规则必须足够宽泛，好让合法的文档形态能通过它——而这个约束会立刻被感受到：你的文档越是
多样，你能对它们所有人共同提出的要求就越少。

```js
        type: {
          enum: ["разовый", "недельный", "автомобильный", "групповой"],
        },
```

只能是列表里的值。第五种通行证类型会需要修改规则——而这是好事：这个改动会变成有意为之。

```js
        car: {
          bsonType: "object",
          required: ["plate"],
          …
        },
```

规则在嵌套对象上也起作用。如果 `car` 字段存在，它就必须有一个 `plate`。如果字段不存在——
没有任何要求，文档是合法的。

```js
  validationLevel: "strict",
  validationAction: "error"
```

`strict` —— 校验所有插入和所有更新。还有更温和的 `moderate`：它校验新文档，以及对那些
已经满足规则的文档的更新，而放过旧的不合规文档。正是用 `moderate`，你才能给一个已经积累
了不一致的集合开启校验：先停止把情况弄得更糟，再修复旧的，然后切到 `strict`。

`error` —— 拒绝。还有 `warn`：记进日志，但照样接受。适合在开启拒绝之前，先花一周看看
到底会进来多少。

</details>

我们应用这条规则：

```bash
# 和 passes.js 一样的手法：文件内容被喂到 mongosh 的输入。
# 规则挂到活着的集合上——不需要停数据库
mo < validator.js
```

**你应该看到** —— `правило установлено`。

我们试着重复同样的拼写错误——现在有规则盯着：

```js
// tipe 字段规则并不认识，而文档里没有必填的 type。
// 以前，这样的文档会悄无声息地落进集合
db.passes.insertOne({ tipe: "разовый", guest: "Проверка", host: "x@corp.ru" })
```

**你应该看到** —— `MongoServerError: Document failed validation`。现在拼写错误过不去了。

⚠️ **校验并不能捕获一切，这一点必须说明白。** 规则要求 `type` 字段存在并且来自列表。
**可选**字段里的拼写错误——本应是 `guest` 却写成 `guestt`——它会放过去：文档依然合法，
只是多了一个字段。你可以禁止任何未知字段（`additionalProperties: false`），但那样每个新
字段都会需要修改规则，你就又回到了当初想摆脱的东西——事事都要做一次模式迁移。界线画在
哪里，是由你来做的决定，而它永远是一种折中。

## 第 6 步。老实说：文档模型在哪里落于下风

📍 **位置：** 在工作 Pod 内部的 `mongosh` shell 里。

模式灵活性不是唯一的区别，而其余的区别都不利于 MongoDB。

<details>
<summary><b>没有常见形式的连接（JOIN）</b></summary>

任务：为每张通行证拉取订购它的那名员工的电话和职位。员工在一个单独的集合 `staff` 里，
以邮箱为键。

在 SQL 里这是一行：`JOIN staff ON staff.email = passes.host`。

这里——是一个管道阶段：

```js
db.passes.aggregate([
  // $lookup = 「对每张通行证，去另一个集合把一条记录取回来」
  { $lookup: {
      from: "staff",          // 去哪儿 —— 员工集合
      localField: "host",     // 比较通行证的哪个字段
      foreignField: "email",  // 与员工的哪个字段
      as: "host_info"         // 用什么名字把找到的放进文档
  } },
  // 找到的东西总是以列表放入，哪怕只有一个匹配。
  // $unwind 把列表展开回单个值
  { $unwind: "$host_info" }
])
```

我们没有 `staff` 集合——查询会返回空。它在这里是作为语法的样例，而不是实验的一步。

它能用。但是：

- `$lookup` 是**单向的**：对左边的每个文档，都在右边执行一次查找。这不是一个会选择连接
  方式的优化器，而恰恰是带查找的暴力遍历
- 结果**以列表**返回，哪怕只有一个匹配。因此有 `$unwind`，用来把它展开
- 连接超过两个集合会变得笨重而缓慢
- 在分片部署里，直到不久前 `$lookup` 都还带着限制

这就是为什么在 MongoDB 的世界里，这个任务是用另一种方式解决的：**需要在一起的数据就存在
一起。** 订购人的电话和职位被直接写进通行证文档。

而这是一个真正的取舍，不是小小的不便：

| | 指向 `staff` 的引用 | 数据在文档里的一份副本 |
|---|---|---|
| 读取 | 需要 `$lookup` | 一次查找 |
| 某员工换了电话号码 | 在一处改好 | 你得把所有通行证都过一遍 |
| 完整性 | 由数据库看守 | 由应用看守，也就是你 |

在关系数据库里没有选择——那里是范式化和外键。这里有选择，而随之而来的是责任。

</details>

<details>
<summary><b>根本没有外键</b></summary>

试试看：

```js
// host 字段按含义指向一名员工。这样的员工并不存在——
// 数据库会检查这件事吗？文档满足上一步的规则：type 在
// 且来自列表，host 是字符串
db.passes.insertOne({ type: "разовый", host: "не-существует@corp.ru", guest: "Тест" })
```

文档会被插入。没有哪个员工用这个邮箱，而数据库不会去管这个。

在关系数据库里，外键会拒绝这样的行。这里根本不存在外键这个概念：**数据的连贯性完全落在
应用身上。** 上一步的校验器检查文档的形态，但无法检查某个字段的值在另一个集合里是否存在。

实际上这意味着：「有没有这样一名员工」的每一次检查都由开发者来写，而如果他忘了——你会在
保安试图给订购人打电话时发现。

别忘了删掉测试文档：

```js
// deleteOne = 「删除一个符合条件的文档」，而不是一次删掉全部
db.passes.deleteOne({ host: "не-существует@corp.ru" })
```

</details>

<details>
<summary><b>有事务，但不是默认开启</b></summary>

这里重要的是要精确，因为人们常常在两个方向上都对 MongoDB 说不实之词。

**真的：** 多文档事务在 MongoDB 里确实存在，从 4.0 版起为副本集提供。你可以修改两个文档，
使得要么两个都生效，要么一个都不生效。

**也是真的：** 默认它们不在。对**单个文档**的操作是原子的。想要更多——就开一个会话并显式
开启一个事务：

```js
// 会话是与数据库的一次单独「对话」，在它内部你可以声明一个事务
const s = db.getMongo().startSession();
s.startTransaction();          // 从这一刻起改动开始累积，但谁也看不见
// … 通过 s.getDatabase("passes") 进行的操作 …
s.commitTransaction();         // 一次性全部应用。要一次性全部取消 —— abortTransaction()
```

**还有第三条真相，最实用的：** MongoDB 里的事务比关系数据库里更贵，它们有时间限制，而整个
数据模型都建立在你几乎不需要它们这个假设之上。如果你的场景经常需要它们，那就是一个信号：
数据本该以另一种方式来组织——或者这里根本不需要文档数据库。

对通行证服务来说这不是问题：一张通行证就是一个文档，对它的所有操作本身就是原子的。对算
工资来说这是问题，而且是个大问题。

</details>

<details>
<summary><b>模式不一致会自行滋生</b></summary>

我们已经在拼写错误上见过这个。但还有一种更阴险的变体：不是因为错误、而是因为疏忽而滋生的
不一致。

一年后你在集合里发现，日期以三种方式存储：作为 `ISODate`、作为字符串 `"2026-09-01"`，
以及作为带时间戳的数字——因为三个不同的团队在不同的时间写入了它们。按日期做范围搜索只找到
三分之一的记录，而没人明白为什么。

你可以这样看看集合里实际有什么：

```js
db.passes.aggregate([
  // $$ROOT —— 整个完整的文档。$objectToArray 把它拆成
  // 「字段名 —— 值」的对，好让你之后把字段当作数据来处理
  { $project: { fields: { $objectToArray: "$$ROOT" } } },
  // 我们展开这些对的列表：一个对 —— 下一个阶段输入端的一行
  { $unwind: "$fields" },
  // 我们同时按两个属性分组：字段名（k）和它的值类型（t），
  // 并统计这样的组合出现了多少次
  { $group: { _id: { k: "$fields.k", t: { $type: "$fields.v" } }, n: { $sum: 1 } } },
  { $sort: { "_id.k": 1 } }   // 按字母顺序，好让一个字段和它自己的各种类型挨在一起
])
```

这个查询把每个文档拆成「字段——值」的对，判定值的类型，并统计每个字段以每种类型出现了多少
次。在我们的四个文档上，它会显示一幅整齐的图景。在一个用了一年的真实集合上，它会显示出谁
也没料到的东西，而它是理清一个继承来的数据库时最有用的查询之一。

**值得带走的结论：** 模式校验器不是装饰，也不是「走过场的形式」。在文档数据库里，它是站在
你和不一致之间的唯一一样东西。它应该马上就开启，而不是等到火烧眉毛。

</details>

**诚实比较的底线：**

| 任务 | 关系型 | 文档型 |
|---|---|---|
| 相同形态的记录 | 自然 | 也可以，但何必 |
| 不同形态的记录 | 空列，或每种类型一张表 | 自然 |
| 列表与嵌套 | 单独的表 | 文档里的一个字段 |
| 与其他数据连接 | JOIN，有优化器 | `$lookup` 或数据的一份副本 |
| 引用完整性 | 由数据库看守 | 由应用看守 |
| 事务 | 默认开启 | 显式、更贵、更少用 |
| 防拼写错误 | 总是有模式 | 校验器，如果你开了的话 |
| 修改模式 | 一次迁移加一次发布 | 新字段自己就冒出来了 |

## 清理

工作 Pod 不再需要了——这一整段时间里它都用 `sleep` 命令让容器保持忙碌：

```bash
# delete = 「从集群里移除」。Pod 连同它的 MONGO_URI 变量一起消失，
# 所以密码不会留在集群里
kubectl delete pod mongo-workbench
```

MongoDB 本身在控制台里删除：`passes` 应用 → 删除。

为什么这很便宜。经典基础设施里的 MongoDB 副本集是三台虚拟机、安装、投票配置、复制延迟
监控，外加一个懂得如何修好这一切的人。这里你借用一个服务一小时，十秒就归还了，它占用的
空间回到集群的空闲容量里——别人马上就能来认领。

⚠️ **数据会随删除一起消失。** 那四张通行证一条命令就能恢复，所以在实验里这不算损失。如果
你往里放了真实的东西——先开启备份；它们在订购表单上是一个单独的区块。

## 我们现在会做什么

- 说清楚文档模型什么时候合适，什么时候是给自己招麻烦的方式
- 从目录订购 MongoDB，而不在 `authSource`、角色和单副本上栽跟头
- 存储不同形态的文档，并按嵌套字段、深入列表进行搜索
- 建立稀疏索引，并理解它为自己的节省付出了什么
- 开启模式校验器，并看清它能防住什么、防不住什么
- 把文档数据库缺什么直说出来：外键、常见的连接、默认的事务

## 而在 vSphere 里，这会是

三台机器用于副本集，而其中最费工的部分不是安装，而是配置副本之间的投票：谁是主节点，失去
连接时怎么办，如何把落后的那个拉回来。外加和信息安全团队单独谈一次：一年后由谁来更新这个
数据库。

这里——目录里的一个条目，加五分钟。

**老实说，vSphere 在哪里更方便。** 装着 MongoDB 的虚拟机是一台你能走到跟前的机器：通过
SSH 登录，看看 `mongotop`，改改配置，在危险操作前打个快照。托管服务**有意**不给你这些：
租户不会让你 `exec` 进 Pod，也进不了数据库的日志。只要一切正常，这就是优势——把它弄坏的
途径更少。当数据库表现古怪时，管理员惯常的那套动作用不上，剩下的只有去找运营平台的人。

还有第二件事，特别针对 MongoDB。托管服务把版本和一整套参数钉死。升级 MongoDB 的大版本是
一项操作，在你自己的安装里由你自己规划，带着应用兼容性检查，以及回滚到快照的选项。这里换
版本是表单上的一个字段，加上底层里别人的升级流程。通常这正是你想要的。但在升级出岔子的那
一天，收拾局面的不会是你自己的手，而你需要事先就明白这一点，而不是走到半路才发现。
