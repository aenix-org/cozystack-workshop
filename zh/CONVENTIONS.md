# 如何编写实验

在你动手修改任何一个实验之前，请先读这份文档。它只有一个目标：让这十五个实验读起来像一份完整的作品，而不是十五份互不相干的东西。

## 读者是谁

一位 VMware 系统管理员。这是他第一次、或者说几乎第一次接触 Kubernetes，而**这没问题**——这份材料正是为这样的人准备的。他很聪明，有二十年的经验，对虚拟化、网络和存储了如指掌。他不知道的，只是我们的术语。

其余的一切，都由这一点推导而来。

## 语言规则

**每个术语在本实验中第一次出现时，都要给出解释。**不能说「另一个实验里讲过」——实验是不分先后顺序做的。解释要借助读者已经从 vSphere 里熟悉的东西。

**禁用词：**「只需」、「显然」、「照例」、「仅仅」、「轻而易举」。如果某件事真的显而易见，那就不必写出来。如果它并不显而易见，「只需」就是在轻视读者。

**直接称呼读者为「你」。**不要含糊其辞，不要假装亲昵，不要用感叹号。

**不要推销。**不要「强大」、「灵活」、「开箱即解决一切问题」。好处要靠事实和对比来展示，而不是靠一个形容词。与其写「Cozystack 提供高可用」，不如写「删掉一个 Pod，然后盯着表看」。

**对缺点要诚实。**如果某样东西做得比 vSphere 差，就直说。读者反正都会发现，而如果我们闭口不提，他就不会再信任其余的内容。

## 一个实验必需的结构

实验文件夹里的一个 `README.md` 文件。各节的顺序是固定的。

1. **标题**——`# Lab NN · 名称`
2. **头部**——所需时间、它能证明什么、你会用到什么
3. **为什么做这个**——一个来自真实工作的任务，而不是「现在我们来学 X」。它是贯穿场景的延续（见下文）
4. **小词表**——只列本实验中新出现的术语，用三列表格：术语、它是什么、「像……但」。第三列点出那个来自 vSphere 的东西，并在同一句话里说清这个术语与它有何不同——用一句话，而不是拆成两个片段放进两个单元格。不能有单独的「类比在哪里失灵」一列：脱离上下文，它的表头什么也说明不了
5. **实验文件夹里有什么**——一张列出本实验每个文件的表格：文件、它是什么、什么时候用得上。读者不应该去猜 `apply` 命令里的 `name.yaml` 是从哪来的，也不该去猜要不要自己创建它。实验要应用的每个文件，都必须放在它自己的文件夹里（或放在相邻的文件夹里，那样就把路径写明：`../03-scale/hpa.yaml`）
6. **步骤**——每个步骤只做一个动作
7. **验证**——结果应该是什么样，以及如何看到它
8. **清理**——必须有，并解释清楚为什么它的代价很低
9. **我们现在会做什么了**——三四个要点
10. **而在 vSphere 里这会是**——一次诚实的对比，包括 vSphere 更方便的地方

## 贯穿场景

所有实验都是同一项工作任务的组成部分，而不是一组练习。

**背景设定：**你在平台团队。业务方请你上线一个内部服务，叫「门禁通行证」（Passes）——员工通过手机应用为访客申请通行证，安保在门岗看到名单，管理层每月看一次报表。

每个服务的出现都是**因为一个具体的痛点**，而不是因为轮到它了：

| 出现了什么 | 因为什么 |
|---|---|
| Harbor | 安全部门禁止从互联网拉取镜像 |
| Redis | 遗留系统里的员工通讯录响应要 800 毫秒 |
| MongoDB | 通行证有不同的字段：一次性的、按周的、给车用的 |
| OpenBao | 一次审计在清单里发现了数据库密码 |
| ClickHouse | 管理层想知道「来了多少访客，以及高峰在什么时候」 |
| Bucket | 移动团队没地方放 APK |
| GitOps | 我们一共三个人，有人手动改了点东西，然后整个都挂了 |
| 目录 | 子公司也想给自己弄一套一样的服务 |

实验 0–4 是在一个无害的应用上练手，在真正的工作任务开始之前。这一点要直说：先「拿它练手」。

## 逐行讲解代码和清单

**任何地方都不会出现没有讲解的 YAML。**读者要应用的文件，没有一个是没弄懂就照搬的。

讲解放进一个折叠块里，这样主线不会臃肿：

```markdown
<details>
<summary><b>逐行讲解这份清单</b></summary>

……逐行地，用散文……

</details>
```

在讲解里我们解释**这个块为什么需要**，而不是里面写了什么。反面例子：「`replicas: 1` 是副本数量。」正面例子：「`replicas: 1`——要保持运行多少个副本。如果一个副本消失了，集群会不声不响地新建一个。下一个实验里的自愈就是从这儿来的。」

## 可预料的失败

**每个实验，只要合适，都要包含一次通不过的检查。**读者撞上墙，去诊断，然后自己领悟到下一步的必要性。

形式始终是同一个，其中的顺序绝不调换：

1. 我们建议去检查，仿佛一切都已就绪
2. **我们把错误亮出来**——先是输出，再是问题。不能反过来
3. 我们让读者停下
4. 一个带答案的折叠块——以及一个比这个具体错误更宽泛的教训

有三处措辞是逐字固定的，好让各个实验不至于各走各的。

叫停始终是一个块引用式的提示框，不带 ⚠️（那个标记留给陷阱用）：

```markdown
> **在继续读下去之前，停下来想一想。**
>
> 一个问题。第二个问题，如果有的话。
```

折叠块的标题始终是 `答案，以及一个比这个错误更宽泛的教训`。

折叠块内那段讲教训本身的文字，开头始终是：`**这个教训比这个错误更宽泛。**`

失败必须是真实的，而不是摆拍出来的。如果某个步骤能跑通，就不必人为地把它弄坏。

## 两条路径：用鼠标和用文本

凡是一个动作既能在控制台（dashboard）里做、也能通过 `kubectl` 做的，我们**两条都**展示，并说清各自在什么时候合适。

**两条路径都不藏进折叠块里。**用文本干活不是控制台挂了时的后备方案：它恰恰是我们要把读者引向的方向，因为写在文件里的描述可以被评审、放进 Git、再回滚。折叠块是用来讲字段的，而不是用来讲干活方式本身的。

托管服务（Harbor、Redis、MongoDB、ClickHouse、OpenBao、bucket、虚拟机）——我们通过控制台来操作：自助服务的那种感觉正是在这里体会到的。

你自己的应用——通过 `kubectl` 和 Git：基础设施就是文本这件事正是在这里体会到的，而文本可以被评审、可以回滚。

## 一以贯之的命名

同一样东西，在每个实验里、在每一条聊天消息里，都叫同一个名字。读者不分先后顺序地过材料，不该还要去猜 `lab` 和「实验集群」是同一个东西。

| 东西 | 我们怎么称呼它 |
|---|---|
| 材料的单位 | 「实验」（lab）。不叫「实验练习」，不叫「模块」，不叫「课」 |
| 实验 0 里的实验集群 | `lab` 应用 |
| 实验 0–4 的练手应用 | `rickroll` |
| 实验 5–14 的生产服务 | 正文里叫「门禁通行证」，清单里叫 `passes` |
| 租户编号 | 占位符里用 `workshopXX`，讲解示例里用 `workshop03` |

另外说一点：**访问文件的路径和环境变量的名字，处处都一样。**如果在一个实验里租户的 kubeconfig 放在一个路径，在相邻的实验里放在另一个路径，读者就会认定这是两个不同的文件，于是给自己留了两份。

实验标题里的名称，和根 `README.md` 表格里的简称，两者要能相互认出来。表格里的「缓存」和文件里的「在慢后端前面加一层缓存」，明显是同一个实验。如果表格里是一个词、标题里是另一个词，读者就会瞎点文件。

实验头部里的时间，和根 `README.md` 表格里的时间，是同一个数字。头部里我们给出完整的时间，包括等待，并单独说明其中有多少花在等待上。

## 排版

- 各节和各步骤都用 `##` 级。步骤的标题：`## Step N. 我们做什么`。我们不用「部分」、「阶段」、「练习」这些词——处处都是「步骤」。步骤内的子标题用 `###`，但更多时候折叠块更合适
- 命令放进标注了语言的代码块：` ```bash `、` ```yaml `、` ```sql `
- 每条命令之前，写清接下来会发生什么。之后，写清你应该看到什么
- 每行不超过 100 个字符
- Emoji 只作为功能性标记使用：📍 在哪里运行，⚠️ 一个陷阱。实验里再没有别的了。在聊天消息里，还会加上 🖱 鼠标路径、📄 仓库里的一个文件、⏳ 一次长时间的等待——到此列表就封口了
- 只要有多列，就用表格代替列表

## 验证

每个文件夹里都有一个 `check.sh`。参与者自己运行它，得到一份报告：检查了什么、什么通过了、什么没通过，并附上证据。对脚本的要求在 `check/README.md` 里。

在实验正文里，我们在「验证」一节引用它。

## 不要做什么

- 不要引用其他实验里的步骤编号——它们是不分先后顺序做的
- 即使在自己的实验里也不要引用步骤编号（「第 7 步的那次可预料的失败」）：一编辑步骤就会移位，引用便悄悄变得不实。写「再往实验里走一点」
- 不要假设上一个实验已经做过，除非在「你会用到什么」里写明了
- 不要在已发布的正文里留下 `TODO`、`TBD` 或占位符
- 不要凭空捏造清单的字段和 Secret 的名字。要对照 cozystack 仓库里的 `packages/apps/<app>/values.schema.json` 来核对
