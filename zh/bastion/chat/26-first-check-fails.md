## 26. 第一次检查：先尝试启动它，然后抓住报错

**别跳过这一步。它是所有步骤里最有用的一步。**

📍 **位置：** 在你自己的虚拟机内部——就是你在第三阶段启动的那台（app-VM）。不是在 bastion 上。

虚拟机已经迁移过来、启动完成，网络也通了。按理说它就该直接跑起来——应用一直好端端地待在这台虚拟机上，位置和原来一模一样，我们从没动过它。来验证一下：

```bash
systemctl status orders-api
curl -s -o /dev/null -w 'HTTP %{http_code}\n' localhost:8080/actuator/health
```

**它跑不起来。** 服务要么没能启动，要么返回 `503`。我们来看看它在抱怨什么：

```bash
journalctl -u orders-api --no-pager | tail -20
```

日志里会出现类似 `Connection to 192.168.10.30:5432 refused` 的内容，或者是对同一个地址的连接超时。

> **先停下来想一想，再往下读。**
>
> 应用我们没动过，虚拟机已经启动，网络也是通的。它为什么起不来？

<details>
<summary><b>答案，以及一个比这个报错更宽泛的教训</b></summary>

因为配置里把地址 `192.168.10.30` 和 `192.168.10.40` 写死了——那是数据库和消息队列，它们原本跑在 **vSphere 里另外两台虚拟机上**。我们没有把它们迁过来，本来也没打算迁。在这里，这两个地址上什么都没有。

应用是好的，虚拟机是好的，网络也是好的。唯一坏掉的，是那个「周围的世界还和原来一样」的假设。

**这才是一次真正的迁移。** 搬动一块磁盘是其中最简单的部分，而人们的注意力往往全都集中在这上面。真正会出问题的，永远是外部的东西：地址、DNS 名称、凭据、证书、相邻的系统。所以在真实项目里，搬迁虚拟机你只安排一天，而「把它弄到能正常工作」要安排几周。

现在你亲身、以吃苦头的方式在两分钟里看清了这一点，而不是在别人的幻灯片里看到的。

</details>

**接下来我们做什么。** 我们要修的不是应用，而是它对世界的认知：把写死的 IP 换成我们在第 5 步启动的那些托管服务的名称。
