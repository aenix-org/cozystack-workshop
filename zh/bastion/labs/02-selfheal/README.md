# 实验 2 · 自愈：杀掉一个副本，看看会发生什么

| | |
|---|---|
| **时长** | 25 分钟 |
| **能证明什么** | 副本会在几秒内自己回来，但仅凭这一点还算不上容错 |
| **需要什么** | 实验 0 中的集群、实验 1 中的 `rickroll`、`kubectl`、两个终端窗口 |

## 为什么这很重要

很快你就要为「门禁通行」服务负责了：安保在早上七点核对来宾名单，「我们正在重启，请稍等」这种话在那儿是行不通的。在你把这样的承诺揽到身上之前，值得先在没有任何风险的情况下弄清楚——集群到底有哪些是自己会做的，哪些是你必须亲自动手的。

我们来拿 Kubernetes 最响亮的承诺开刀——自愈。我们会删掉一个正在运行的应用副本，并掐着表计时它缺席了多久。然后再删掉别的东西——然后你会看到那个副本没有回来。这两种情况之间的区别，就是本实验的主题。

## 小词表

| 术语 | 是什么 | 像……但 |
|---|---|---|
| **期望状态** | 集群里的一条记录，写着「应该长这样」 | **vCenter 里的集群设置**，但集群不是应用它一次就完事——它会无休止地把现实拉齐到它 |
| **控制器** | 集群控制平面里的一个进程，负责把「下达的命令」和「实际情况」对照核实 | **vSphere HA**，但它持续运行、覆盖所有对象，而不是等某台主机故障时才醒来 |
| **ReplicaSet** | 一个对象，确保副本数恰好等于下达的数量 | **一条「保持 N 个实例」的规则**，但它不修复坏掉的东西——它创建一个新的来顶替消失的那个 |
| **ownerReferences** | 对象内部的一个标记：「创建我的是这个」 | 正是靠它，删除父对象会自动连带它所有的子对象一起删掉 |
| **终止（Termination）** | 「删除」和「进程被杀」之间的那段停顿 | **Guest Shutdown 而不是 Power Off**，但默认是 30 秒，之后就会被强行杀掉 |
| **EndpointSlice** | Service 背后一组存活地址的清单 | **负载均衡器上一个池的成员清单**，但它是根据标签和就绪状态自动构建的——你不用手工往里写 |

## 步骤 1. 看看我们手上有什么

📍 **在哪里：** 在 bastion 上（在 bastion 的终端里）。

`rickroll` 应用已经在运行了。在动手破坏任何东西之前，先看看它由哪些对象组成：用一条命令一次性向集群询问三种实体。

```bash
# KUBECONFIG — 指向那个文件的路径，文件里有集群的地址和你的登录凭据。
# 在这个变量设置好之前，kubectl 会在 bastion 本机上找集群，然后找不到。
export KUBECONFIG=~/lab.kubeconfig

# get = 「把有什么给我看看」。用逗号一次列出三种对象。
#   -l app=rickroll   只显示带 app=rickroll 标签的那些——也就是我们的
#                     应用，而不是集群的全部内容
kubectl get deployment,replicaset,pods -l app=rickroll
```

**你应该看到** —— 三个对象各一行：

```
NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/rickroll   1/1     1            1           14m

NAME                                  DESIRED   CURRENT   READY   AGE
replicaset.apps/rickroll-6f4b9c8d57   1         1         1       14m

NAME                             READY   STATUS    AGE
pod/rickroll-6f4b9c8d57-xk2mp    1/1     Running   14m
```

⚠️ **`replicaset` 那行可能不止一行。** 每次滚动发布一个新版本，都会把上一个集合留在历史里——各列都是零。存活的那个是数字为一的那行；其余的留着，是为了有个地方可以回滚。

对象有三个，尽管在实验 1 的清单里你只描述了一个 Deployment。另外两个是集群自己创建的，这不是装点门面的细节——后面所有的一切都依赖这条链。

<details>
<summary><b>拆解这条链：谁创建了谁，为什么</b></summary>

看看这些名字。一个 Pod 的名字是 ReplicaSet 的名字加上五个随机字符，而 ReplicaSet 的名字是 Deployment 的名字加上一个哈希。这条链就是这么搭起来的。

**Deployment** 完整保存着你的意图：用哪个镜像、多少个副本、怎么更新。它不直接盯着 Pod——它盯着 ReplicaSet。

**ReplicaSet** 只保存一个念头：「带 `app=rickroll` 标签的 Pod 应该恰好有这么多个」。就这些。它对镜像和版本一无所知。

**Pod** 就是一个正在运行的副本。

要确认这不是瞎猜，可以这样：

```bash
# kubectl 默认的表格不显示 ownerReferences 字段——你得显式地把它要出来。
#   -o jsonpath=...   「从服务器的响应里把这几个字段抽出来，按这样打印」
# 表达式内部：range .items[*] — 遍历找到的每一个 Pod，.metadata.name —
# Pod 的名字，ownerReferences[0].kind 和 .name — 创建它的那个东西的类型和名字。
kubectl get pods -l app=rickroll -o jsonpath='{range .items[*]}{.metadata.name}{"  <- "}{.metadata.ownerReferences[0].kind}{"/"}{.metadata.ownerReferences[0].name}{"\n"}{end}'
```

输出：

```
rickroll-6f4b9c8d57-xk2mp  <- ReplicaSet/rickroll-6f4b9c8d57
```

`ownerReferences` 字段就是「创建我的是这个对象」这条记录。ReplicaSet 也有同样的记录，只是那里指向的是 Deployment。

为什么要三层而不是一个对象：各层负责不同的事。当实验 4 里我们滚动发布新版本时，Deployment 会为新版本创建**第二个** ReplicaSet，并开始把副本从旧集合一个一个地挪到新集合。旧的 ReplicaSet 在此期间哪儿也不会去——正是它让你能用一条命令回滚。

一个值得记住的附带事实：删除父对象会连带它的子对象。手动删掉 ReplicaSet——Deployment 会在一秒内创建一个新的。删掉 Deployment——一切都消失。第二种情况我们会在实验结尾验证。

</details>

## 步骤 2. 杀掉一个副本并计时

现在我们要删掉一个 Pod。不是关机，不是重启——是彻底删掉，就好像有人对着一台虚拟机点了 Delete from Disk。

**接下来会发生什么：** 下面这条命令会记住当前副本的名字，删掉它，然后每秒一次地询问集群，是否出现了一个**不同**名字、处于 Running 状态的副本。一旦出现，它就打印出这花了多长时间。

```bash
# items[0].metadata.name — 列表里第一个 Pod 的名字。我们把它存进 POD 变量：
# 没有它，后面就没法把旧副本和新副本区分开。
POD=$(kubectl get pods -l app=rickroll -o jsonpath='{.items[0].metadata.name}')
echo "正在杀掉 $POD"

# date +%s — 当前时间，以秒计。这是我们的秒表：删除前记下它，
# 最后再从新的读数里减去它。
START=$(date +%s)

# delete pod — 把副本彻底删掉。
#   --wait=false   不等 Pod 完全消失，立刻交还控制权：
#                  我们要从这一刻开始数秒，而不是从之后
kubectl delete pod "$POD" --wait=false

# 每秒一次重新读取 Pod 列表，找出一行同时满足以下所有条件的：
#   $1!=old        名字和旧的不一样——所以这是另一个副本
#   $2=="1/1"      一个容器里有一个就绪
#   $3=="Running"  pod 正在运行
#   --no-headers   不打印表头，好让 awk 只看到数据
#   2>/dev/null    在完全没有 Pod 的那几秒里，隐藏错误消息
while true; do
  NEW=$(kubectl get pods -l app=rickroll --no-headers 2>/dev/null \
        | awk -v old="$POD" '$1!=old && $2=="1/1" && $3=="Running" {print $1; exit}')
  [ -n "$NEW" ] && break
  sleep 1
done
echo "新副本 $NEW 已就绪，用时 $(( $(date +%s) - START ))s"
```

**你应该看到：**

```
正在杀掉 rickroll-6f4b9c8d57-xk2mp
pod "rickroll-6f4b9c8d57-xk2mp" deleted
新副本 rickroll-6f4b9c8d57-p9wqt 已就绪，用时 4s
```

四秒。在测试环境上，波动范围是二到十五秒，取决于节点有多忙。镜像已经在节点上了，没什么要下载的，所以一切都归结于启动进程和就绪检查。

**注意名字。** 尾巴变了：`xk2mp` 变成了 `p9wqt`。这不是同一个 Pod 重启了——这是另一个 Pod。旧的那个哪儿都不在了；你没法修复它、从回收站里恢复它，也没法看它磁盘上曾有过什么。

没有人「恢复」了任何东西。ReplicaSet 每秒好几次地把「下达：1」和「实有：0」对照，一旦不一致就创建缺少的那个。副本消失了——不一致出现了——一个副本被创建了。同样的机制在这些情况下也会触发：Pod 因为更重要的工作负载被从节点上驱逐、节点本身宕掉、或者 Pod 内部的应用因为内存耗尽而死掉。

## 步骤 3. 检查这期间有没有容错

副本在四秒内回来了。这是否意味着服务没有中断？

我们来查一下。需要**两个终端窗口**。

📍 **窗口 1** —— 我们在集群内部启动一个极小的 Pod，它每秒一次通过 Service 戳一下我们的应用，成功就画一个点，出错就画一个 `X`：

```bash
export KUBECONFIG=~/lab.kubeconfig

# run = 直接从命令行创建一个单独的 Pod，不用清单。
#   --rm             一旦你中断命令，就删掉这个 Pod
#   -it              Pod 的输出直接送到你的屏幕，Ctrl+C 停止它
#   --restart=Never  只有一个副本，也不需要重建它：这是个工具，不是服务
#   --image          busybox — 一个几兆大小、自带 wget 的镜像
# -- 之后的一切都在 Pod 内部执行。地址 http://rickroll 是 Service 的名字；
# 在集群内部它会自己变成应用的地址。
#   -q               不打印下载统计
#   -T 2             等待应答不超过两秒，否则就算作一次失败
#   -O /dev/null     把响应体扔掉，我们只在乎有没有应答这个事实
kubectl run pinger --rm -it --restart=Never --image=busybox:1.36 -- \
  sh -c 'while true; do wget -q -T 2 -O /dev/null http://rickroll/healthz \
         && echo "$(date +%T) ." || echo "$(date +%T) X"; sleep 1; done'
```

每一行都带一个时间戳：这样你不仅能看到故障本身，还能看到它持续了**多少秒**——而这正是整个实验想要的那个数字。

⚠️ **你需要第二个终端，而不是后台运行。** 这个练习的意义在于，要在你于另一个窗口删掉副本的**那一刻**看到故障：带叉的那行应该在你眼前出现。事后在 `kubectl logs` 里读它也可以，但那样最重要的东西就丢了——你的动作和它后果之间的联系。

为什么从集群内部而不是从 bastion：`port-forward` 会锁定到某个具体的 Pod，并随它一起死掉，所以它无论如何都会显示一次故障——哪怕根本没有故障。而从邻近 Pod 发出的 `wget` 走的是 Service，也就是真实客户端会走的那条路。

等到点开始跑起来。

📍 **窗口 2** —— 杀掉副本：

```bash
export KUBECONFIG=~/lab.kubeconfig

# 没有给 pod 名字，而是给了一个标签：删除所有带 app=rickroll 标签的副本。
# 现在只有一个，所以离开的正是 pinger 正在轮询的那一个。
kubectl delete pod -l app=rickroll
```

📍 **看窗口 1。** 你会看到大致这样：

```
.........XXXXX.........
```

有几秒钟服务在用错误应答——我们这里出了五个，在繁忙的节点上可能是十五个。副本很快就回来了，但在它缺席的那段时间，没有谁来应答。

**下面是对我们所观察到的东西的诚实表述。** 自愈不是容错。自愈让系统在没有人的情况下恢复正常。容错意味着客户端根本什么都没察觉。一个副本给你前者，给不了后者。

别停下 pinger，马上还要用它。

## 步骤 4. 做同样的事，但用三个副本

📍 **窗口 2。** 我们下达三个副本而不是一个，并等到三个全部就绪。

```bash
# scale 只改应用记录里的一个字段——副本数。
kubectl scale deployment rickroll --replicas=3

# rollout status 会占住终端并打印进度，直到你要求的所有副本
# 都就绪。命令会自己结束——不用手动去轮询 get pods。
kubectl rollout status deployment/rickroll
```

我们在期望状态里只改了一个数字。接下来一切都由那个同一个 ReplicaSet 完成：它看到「下达 3，实有 1」，就创建缺少的那两个副本。这花的时间和之前一样是几秒。

确认现在有三个副本，而且它们全都落到了 Service 后面：

```bash
# EndpointSlice — 就是 Service 替你维护的那份存活地址清单。
#   -l kubernetes.io/service-name=rickroll   取属于 Service rickroll 的那份清单
#   -o jsonpath=...                          从每条记录里只打印地址本身，
#                                            一行一个
kubectl get endpointslices -l kubernetes.io/service-name=rickroll \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{"\n"}{end}'
```

三个地址。没有人把它们填进去——Service 自己组装了这份清单，依据的是标签 `app=rickroll` 和每个副本的就绪状态。这正是实验 1 讲过的、与负载均衡器上的池的区别：那里你把地址填进去，这里你描述一个条件。

现在我们杀掉三个副本中的一个：

```bash
# 取三个副本里第一个的名字——具体是哪一个无所谓。
POD=$(kubectl get pods -l app=rickroll -o jsonpath='{.items[0].metadata.name}')

# 然后删掉它。这里不用 --wait=false：命令会在 Pod 已经消失后才返回。
kubectl delete pod "$POD"
```

📍 **看窗口 1：**

```
...........................
```

一个 `X` 都没有。副本被杀了，它被重建了，客户端没察觉。

单副本测试和三副本测试之间的区别，是清单里的一个数字。**这里的容错不是一项你打开的功能——而是副本多于一个所带来的结果。** 这正是为什么 Kubernetes 里没有「启用 HA」这个勾选框：没什么可启用的，只有 `replicas`。

在窗口 1 里按 `Ctrl+C` 停掉 pinger。如果 Pod 还挂在那儿，把它删掉：`kubectl delete pod pinger`。

## 步骤 5. 一个不会通过的测试

机制很清楚：删掉一个副本，它就回来。我们再测一次，但这次删的不是副本，而是应用本身：

```bash
# 我们删的不是副本，而是应用记录本身。不会有确认提示，
# 对象不会进任何回收站——除了那个文件，没别的地方能恢复它。
kubectl delete deployment rickroll
```

我们等几秒，看看副本有没有回来：

```bash
# 我们按应用的标签找 pod。这里的空应答本身也是一种回答。
kubectl get pods -l app=rickroll
```

**你会看到：**

```
No resources found in default namespace.
```

副本没有回来。五秒后没有，一分钟后也没有。

> **在往下读之前，停下来想一想。**
>
> 为什么之前你杀掉副本时它会重新出现，而现在不会？我们可什么都没关掉。

<details>
<summary><b>答案，以及一个比这个错误更宽泛的教训</b></summary>

之前你删的是一个**副本**——也就是一个事实。「应该有三个副本」这条记录还留在原地，现实和它出现了分歧，控制器把分歧消除了。

这次你删的是**记录本身**。已经没有什么可分歧的了：期望状态是「这个应用不存在」，实际状态是「这个应用不存在」。它们一致，控制器无事可做。顺带着，沿着 `ownerReferences` 链，ReplicaSet 和三个 Pod 都跟着 Deployment 一起离开了。

**一个比这个错误更宽泛的教训。** 值得从这个实验里整个带走的规则：

> Kubernetes 保护你不丢失一个**事实**，但对于丢失**意图**它什么也不做。

整个自愈机制的运作，恰好只在「事情应该如何」这条记录完好无损的期间内成立。如果这条记录被改动或删除——集群会尽职尽责且非常迅速地把现实拉齐到新的期望状态，不管那是什么样的状态。它不会问「你确定吗？」，也不会留下回收站。

有两个实际后果，而且都只会让人不快恰好一次。

**第一：这里的删除比 vSphere 里更悄无声息。** 拆掉一个 Deployment 就是一行——没有确认，没有带红色图标的「Delete from Disk?」。你没法从集群里恢复它：被删除的对象哪里都不保存。

**第二：唯一真正的保护是把意图存在集群之外。** 如果清单存在 Git 里，由自动化把它送进集群，那么误删就能被治好——自动化会在一分钟后把对象从仓库里送回来。这就是 GitOps，我们会在实验 5 里把它打开。目前，你的 `rickroll.yaml` 是意图的唯一副本。好在它存在一个文件里：你可以审阅它、把它放进 Git、再次应用它。

顺便说一句，中间那个环节值得单独测一测，它的表现有所不同。恢复应用（下一步），然后试着删掉 ReplicaSet 而不是 Deployment：

```bash
# rs — replicaset 的简写；kubectl 两种写法都认。
# 我们删掉中间环节，把 Deployment 留在原地。
kubectl delete rs -l app=rickroll

# 然后立刻看看剩下什么：把这个集合的名字和删除前的名字比一比。
kubectl get rs -l app=rickroll
```

集合会在一秒内重新出现——而且**名字一模一样**。名字里的哈希是根据 Pod 模板算出来的，而我们没动模板：同样的名字意味着集群恢复的正是同一个东西，而不是创建了什么新东西。「应该有这个应用」这条记录仍然完好——负责它的是 Deployment，而它挺过了集合的删除。

</details>

## 步骤 6. 把应用找回来

你有意图，它就在一个文件里。恢复就是一条命令：

```bash
# apply = 「把集群拉齐到文件里描述的样子」。对象不存在——它会被创建。
#   -f ../01-deploy/rickroll.yaml   文件在实验 1 的目录里，所以路径要经过 ../
kubectl apply -f ../01-deploy/rickroll.yaml

# 我们等副本起来并准备好接收请求。
kubectl rollout status deployment/rickroll
```

注意这里**没有**什么：没有备份，没有快照，没有从 vCenter 的导出。你从一个十千字节的文本文件里恢复了应用，得到的东西和之前的字面上一模一样。换成虚拟机，这一招行不通：它的描述和它的内容是分不开的。

## 校验

📍 **在哪里：** 在 bastion 上，就在你用 `kubectl` 干活的那个终端窗口里。

脚本检查的不是你有没有运行那些命令，而是集群里还剩什么：应用再次通过 Service 提供请求服务，它把自己副本的名字插进页面里，而这个名字属于一个真正在运行的 Pod。它还单独查找副本被重建的痕迹——从 Pod 的年龄，以及从集群的事件里。

## 清理

`rickroll` 应用在实验 3 和实验 4 里还要用——我们不删它。

这里没什么可清理的，而这件事本身就值得注意。你从文件里恢复了应用，而文件下达的是一个副本——多出来的两个，集群早在上一步就自己关掉了，没问也没等你的命令。要确认：

```bash
# READY 那一列应该是 1/1。
kubectl get deployment rickroll
```

节点的资源在容器结束的那一刻就释放了。这里没有「碎片整理」，也没有按计划回收空间：一个容器结束了——它的内存和 CPU 时间立刻就供邻居们使用。

## 而在 vSphere 里，这会是

vSphere HA 在主机故障后重启一台 VM：集群先得确认这台主机确实丢了（那是几十秒），然后机器从零开始引导——内核、服务、应用。是分钟级。基于心跳丢失的 VM Monitoring 也是同样的方式、同样的时间量级。

这里是秒级，而且不只是主机故障时：同样的机制在副本被驱逐、被 OOM 杀掉、被你自己删掉时都会触发。

**说句公道话，哪些地方 vSphere 更方便。** 三件事。

第一，vSphere HA 找回的是**同一台机器**，连同它磁盘上原有的一切。而 Pod 回来时是空的：任何没放在持久卷上的东西都永久丢失了。对于无状态应用这是优点；而对于一个多年来一直往自己 `/var` 里写东西的遗留服务，这是一个非常讨厌的意外的来源。

第二，vSphere 有 Fault Tolerance：两台机器锁步运行，主机故障时零停机，完全不用改造应用。Kubernetes 里没有直接的对应物，也不可能有——这里的零停机是靠有多个副本来实现的，这意味着应用必须能以多个副本运行。如果它做不到，Kubernetes 不会替你解决这个问题，而是会把它暴露出来。

第三，事后复盘。在 vCenter 里，一台机器重启的原因作为集群事件里的一条记录清晰可见，而且它会一直留在那里。在 Kubernetes 里，事件只活大约一个小时，然后就消失了，你得从好几个组件的日志里把整幅图景拼回来。在你搭好日志和事件采集（实验 14）之前，「它为什么半夜重启了」是一个没有答案的问题。
