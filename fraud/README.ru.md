# Воркшоп: антифрод для карточных платежей в реальном времени на собственном облаке

За два часа вы соберёте работающую систему, которая в реальном времени ловит
мошенничество с картами, а затем проведёте её через то, что банк переживает в
продакшене: всплеск трафика, отказ ноды базы данных и переезд сервера прямо посреди
потока платежей.

Всё работает на [Cozystack](https://cozystack.io) — открытой платформе из CNCF,
которая превращает обычные серверы в частное облако. Вы работаете через общую ВМ,
бастион, так что вам нужен только ноутбук с терминалом и браузером.

[English version](README.md)

## Легенда

Каждый раз, когда картой расплачиваются, терминал магазина задаёт банку-эмитенту
один вопрос: одобрить или отклонить? Программа, которая принимает эти запросы,
называется **свитч** (card authorization switch, процессинговый коммутатор). В
большинстве банков он старый, работает на виртуальной машине, и трогать его никто
не хочет. Наш ничем не лучше: он живёт на ВМ в вашем тенанте и одобряет всё, что
меньше $5 000. Для мошеннической группировки — подарок.

Переписывать свитч вы не будете. Вы построите антифрод вокруг него:

```
  card terminals ──► switch (VM, legacy) ──► Kafka: auth.requests ──► scorer (your Kubernetes)
                        ▲   │                                           │  card history in Redis
                        │   │                Kafka: auth.decisions ◄────┘
                        └───┘ approve / decline in milliseconds;
                            │ no answer in 400 ms → the switch decides alone ("stand-in")
                            ▼
                     Kafka: auth.journal ──► cases ──► PostgreSQL ──► dashboard
                                               │
                                               └──► explainer: a small language model
                                                    in your cluster, "why was this blocked?"
```

| Компонент | Где работает | Что делает |
|---|---|---|
| switch | ВМ в вашем тенанте | отвечает терминалам; спрашивает scorer или решает сам — режим стенд-ин (stand-in) |
| Kafka | сервис из каталога | переносит каждый запрос авторизации, каждое решение и каждую запись журнала |
| Redis | сервис из каталога | помнит недавнюю активность каждой карты: как часто, где и на какие суммы |
| PostgreSQL | сервис из каталога, две реплики | база кейсов: каждая транзакция и каждое срабатывание |
| scorer, cases, dashboard | ваш собственный кластер Kubernetes | принимают решения, записывают, показывают |
| explainer | ваш собственный кластер Kubernetes | Qwen2.5 0.5B на CPU пишет понятное объяснение для каждой блокировки |
| terminals | ваш собственный кластер Kubernetes | магазины по всем США, присылающие обычные платежи |

Исходный код всех компонентов лежит в [`app/`](app/). Правила скоринга и их веса
собраны в одном коротком файле, [`app/internal/scoring/rules.go`](app/internal/scoring/rules.go).

## Шаг 1. Kafka, Redis и PostgreSQL из каталога

📍 На бастионе, не в консоли ВМ.

Все три сервиса берутся из каталога Cozystack — так же, как в публичном облаке
заказывают управляемую базу данных. Один файл заказывает все три:

```bash
cat manifests/01-data-services.yaml
kubectl --context platform apply -f manifests/01-data-services.yaml
kubectl --context platform get kafka,redis,postgres -w
```

**Должно получиться:** `features` (Redis) и `cases` (PostgreSQL) переходят в
`READY True` за минуту-две, а `kafka` — за три–десять минут: когда заказывает весь
зал разом, платформа ставит их по очереди. Остановите наблюдение через `Ctrl-C`.
К шагу 2 можно переходить, как только готовы Redis и PostgreSQL: сервисы сами
дождутся Kafka.

Пока они запускаются, посмотрите на заказанное в дашборде Cozystack
(https://dashboard.workshop.aenix.io, ваш тенант `tenant-dallasNN`): там те же три
приложения с их сервисами и секретами. За ними стоят операторы — Strimzi для Kafka,
CloudNativePG для PostgreSQL и оператор Redis, — и ни один из них вам не пришлось
устанавливать.

Зачем нужен каждый сервис:

* **Kafka** переносит три топика. В `auth.requests` свитч спрашивает «одобрить или
  отклонить?», в `auth.decisions` отвечает scorer, а в `auth.journal` свитч
  записывает каждый данный им ответ, кто бы ни принял решение.
* **Redis** — кратковременная память каждой карты: сколько платежей было за
  последнюю минуту, где её видели в последний раз, сколько крошечных «пробных»
  платежей она сделала.
* **PostgreSQL** — база кейсов. Две реплики, primary и горячий standby: в шаге 6
  primary у вас отнимут.

⚠️ Если `apply` падает с `SchemaError … unknown model in reference`, ошибку даёт
проверка на стороне клиента, а не кластер. Добавьте `--validate=false`.

## Шаг 2. Scorer и подключение свитча

📍 На бастионе.

Разверните сервисы антифрода в своём кластере:

```bash
kubectl --context fraud apply -f manifests/02-scoring.yaml
kubectl --context fraud -n fraud get pods -w
```

**Должно получиться:** `scorer`, `cases` и `dashboard` в состоянии `Running`.
Остановите через `Ctrl-C`.

Сервисы обращаются к Kafka, Redis и PostgreSQL по их именам в платформе, например
`kafka-kafka-kafka-bootstrap.tenant-dallasNN.svc.cozy.local`. Ваш кластер — тенант
платформы, и сервисы платформы находятся с ним в одной сети.

Scorer запущен, но его пока никто ни о чём не спрашивает: свитч по-прежнему решает
сам. Вернитесь на свитч:

```bash
virtctl console vm-instance-switch
```

Внутри ВМ направьте свитч на Kafka и перезапустите его:

```bash
sudo sed -i 's#^KAFKA_BOOTSTRAP=.*#KAFKA_BOOTSTRAP=kafka-kafka-kafka-bootstrap:9092#' /etc/auth-switch/env
cat /etc/auth-switch/env
sudo systemctl restart auth-switch
journalctl -u auth-switch -f
```

Короткого имени `kafka-kafka-kafka-bootstrap` достаточно: домен вашего тенанта уже
прописан в списке поиска DNS на ВМ.

**Должно получиться:** `switch started in SCORING mode`, затем
`100 authorizations, 0 declined, stand-in 0.0%`. В первые пять секунд, пока
прогреваются соединения, может мелькнуть немного stand-in.

Теперь каждый платёж совершает путь через Kafka к scorer в вашем кластере и обратно,
а терминал всё так же получает ответ примерно за десять миллисекунд. Если scorer не
ответил за 400 мс, свитч возвращается к своему старому статическому правилу, так
что медленный scorer никогда не останавливает платёж. В банках это называют
**stand-in processing**.

Выйдите из консоли (`Ctrl-]`) и откройте свой дашборд:
`https://fraud.dallasNN.workshop.aenix.io`

**Должно получиться:** около 20 авторизаций в секунду, почти никаких отказов,
задержка принятия решения и лаг Kafka около нуля.

## Шаг 3. Языковая модель объясняет каждый заблокированный платёж

📍 На бастионе.

Отказу нужна причина, которую сотрудник поддержки сможет зачитать клиенту. Её пишет
небольшая языковая модель — Qwen2.5 0.5B Instruct, которую llama.cpp запускает
прямо в вашем кластере на CPU. Веса модели приходят в кластер, а данные карт из него
не уходят, и никакие внешние ИИ-сервисы не участвуют.

```bash
cat manifests/03-explainer.yaml
kubectl --context fraud apply -f manifests/03-explainer.yaml
kubectl --context fraud -n fraud rollout status deploy/explainer --timeout=5m
```

**Должно получиться:** `successfully rolled out` через минуту-другую — под скачивает
модель на 400 МБ и загружает её. Если команда не дождалась, запустите её ещё раз.

В `cases` адрес explainer уже прописан, и сервис его ждал. Но пока ничего не
блокируется, объяснять нечего. Шаг 4 это исправит.

## Шаг 4. Атака мошенников

📍 На бастионе, с открытым дашбордом.

Мошенническая группировка атакует ваших держателей карт сразу тремя способами:

* **card testing**: с трёх украденных карт делают десятки крошечных онлайн-платежей,
  чтобы проверить, что карты рабочие, а затем пытаются купить дорогую электронику;
* **невозможное перемещение**: картой, которой только что платили в Далласе, через
  две минуты расплачиваются в Лагосе;
* **BIN-атака**: шестьдесят номеров карт подряд из одного банковского диапазона, по
  доллару каждый.

```bash
kubectl --context fraud apply -f manifests/04-attack.yaml
kubectl --context fraud -n fraud logs job/attack -f
```

**Должно получиться:** в логе атаки большинство платежей `declined`. Первые
несколько проб по каждой украденной карте проходят: один крошечный платёж ничем не
отличается от обычного, картина складывается через несколько штук. На дашборде растёт число отказов и появляются заблокированные транзакции с
кодами причин. В течение минуты-двух модель снабжает каждую из них понятным
объяснением. Модель совсем маленькая и работает на одном ядре: объяснения приходят
по одному, и иногда какое-нибудь выходит корявым.

Прочитайте правила, которые поймали атаку:
[`app/internal/scoring/rules.go`](app/internal/scoring/rules.go). Серию card testing
останавливают примерно на шестой пробе, BIN-атаку — примерно на восьмой карте.

## Шаг 5. Чёрная пятница

📍 На бастионе, с открытым дашбордом.

Трафик вырастает в двадцать раз. Терминалы берут частоту платежей из ConfigMap,
поэтому её можно поменять без перезапуска (Kubernetes доставит новое значение в под
в течение минуты):

```bash
kubectl --context fraud -n fraud patch configmap traffic -p '{"data":{"rate":"400"}}'
```

Понаблюдайте за дашбордом минуту. **Должно получиться:** лаг Kafka у scorer растёт,
задержка решения переваливает за 400 мс, а **доля stand-in** ползёт вверх. Stand-in
означает, что свитч решил сам, по статическому правилу. В настоящем банке именно в
этот момент мошенничество и проходит: платёж никто не проверил.

Одного scorer мало. Добавьте ещё:

```bash
kubectl --context fraud -n fraud scale deploy/scorer --replicas=6
kubectl --context fraud -n fraud get pods -l app=scorer -o wide
```

**Должно получиться:** новые scorer запускаются, и за две-три минуты лаг
перестаёт расти и держится низким, а stand-in падает до нескольких процентов. Если часть подов застряла в `Pending`, в кластере кончилось
место: cluster autoscaler добавит вторую ноду, это занимает несколько минут
(`kubectl --context fraud get nodes -w`).

Теперь попробуйте двенадцать:

```bash
kubectl --context fraud -n fraud scale deploy/scorer --replicas=12
```

Пропускная способность перестаёт расти на восьми. В `auth.requests` восемь
партиций, а в consumer group Kafka одну партицию в каждый момент читает только один
потребитель. Горизонтальное масштабирование потоковой системы закладывается при
создании топика, а не при добавлении подов.

Возвращаемся к обычному дню:

```bash
kubectl --context fraud -n fraud patch configmap traffic -p '{"data":{"rate":"20"}}'
kubectl --context fraud -n fraud scale deploy/scorer --replicas=2
```

## Шаг 6. Падает primary-нода базы данных

📍 На бастионе, с открытым дашбордом.

Найдите primary своего кластера PostgreSQL:

```bash
kubectl --context platform get pods -l cnpg.io/cluster=postgres-cases -L role
```

Под с `role=primary` — тот, куда идут все записи. Уберите его, как будто его сервер
вышел из строя (`--grace-period=5` пропускает обычное аккуратное завершение):

```bash
kubectl --context platform delete pod <the primary pod> --grace-period=5
kubectl --context platform get pods -l cnpg.io/cluster=postgres-cases -L role -w
```

**Должно получиться:** за считаные секунды второй под становится `primary`, а
удалённый возвращается уже как новая реплика.

Тем временем на дашборде панель базы данных несколько секунд показывает
`database unavailable`, а лаг `cases` растёт. Платежей это не касается: свитч с
базой вообще не общается. Его журнал ждёт в Kafka. В логе `cases`:

```bash
kubectl --context fraud -n fraud logs deploy/cases --tail=20
```

вы увидите `database unavailable, holding … messages, retrying`, а затем запись
накопившегося хвоста. Строка сверки на дашборде сравнивает то, что свитч записал в
журнал, с тем, что сохранилось в базе; когда хвост записан, она показывает
`missing: 0`. Ни один кейс не пропал.

## Шаг 7. Свитч переезжает на другой сервер посреди потока платежей

📍 На бастионе, дашборд открыт.

Серверу под вашим свитчем нужно обслуживание. В банке это обычно окно изменений в
три часа ночи. Здесь ВМ переезжает на другой сервер и продолжает отвечать терминалам:

```bash
kubectl --context platform get vmi vm-instance-switch -o wide
virtctl migrate vm-instance-switch
kubectl --context platform get vmim -w
```

**Должно получиться:** за минуту миграция проходит `Pending`, `Scheduling`,
`TargetReady` и `Succeeded`, после чего `get vmi` показывает другую ноду. Память работающей ВМ
копируется на новый сервер на ходу, а диск переносить не нужно: он лежит на
реплицируемом хранилище, доступном обоим серверам.

На дашборде **ошибок терминалов остаётся ноль**. Секунду-другую сеть ВМ
устанавливается на новом сервере, и несколько авторизаций остаются без ответа; терминалы
поступают как настоящие и повторяют их с тем же номером транзакции. Дашборд считает
их как **повторённые терминалом**.

```bash
kubectl --context fraud -n fraud logs deploy/terminals --tail=20
```

## Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| `virtctl console` ничего не показывает | Нажмите Enter. Приглашение для входа выводится только один раз. |
| В логе свитча `stand-in 100%` после шага 2 | Kafka ещё не готова или в адресе в `/etc/auth-switch/env` опечатка. `kubectl --context platform get kafka` должен показывать `READY True`. |
| Дашборд отвечает 502 или 503 | Под дашборда ещё не запустился: `kubectl --context fraud -n fraud get pods`. |
| После шага 4 нет объяснений | Explainer ещё загружает модель: `kubectl --context fraud -n fraud logs deploy/explainer`. |
| `forbidden` на какой-то команде | Проверьте контекст: сервисы из каталога, ВМ и поды PostgreSQL живут в `platform`, сервисы антифрода — в `fraud`. |
