# ラボの書き方

どのラボであれ、最初の編集に取りかかる前にこれを読んでください。この文書の目的はただ一つ
——15個のラボが、15個の別々のものではなく、一つの作品として読めるようにすることです。

## 読者は誰か

VMwareのシステム管理者です。Kubernetesを見るのは初めて、あるいはほぼ初めてで、**それで
問題ありません**——教材はまさにこの人に向けて作られています。彼らは優秀で、20年の経験が
あり、仮想化・ネットワーク・ストレージを知り尽くしています。知らないのは、私たちの用語
だけです。

ほかのすべては、ここから導かれます。

## 言葉のルール

**このラボで初めて出てくる用語は、必ず説明を添える。**「別のラボで説明した」は通用しません
——ラボは順不同で進められます。読者がvSphereですでに知っているものを通して説明してください。

**禁止語:**「〜だけ」「当然」「いつものように」「ほんの」「自明に」。本当に自明なら、書く
必要はありません。自明でないなら、「〜だけ」は読者を見下すことになります。

**読者には「あなた」と直接呼びかける。** もったいぶらず、なれなれしくせず、感嘆符も
使いません。

**売り込まない。**「強力」「柔軟」「あらゆる課題をそのまま解決」は禁物です。利点は、形容詞
ではなく事実と比較で示します。「Cozystackは高可用性を実現します」ではなく——「Podを削除
して、時計を見てください」。

**欠点には正直に。** vSphereより劣る点があるなら、そう書きます。どのみち読者は気づきますし、
黙っていれば、ほかの記述も信じてもらえなくなります。

## ラボの必須構成

ラボのフォルダにある `README.md` ファイルです。セクションの順序は厳格に守ります。

1. **タイトル** — `# ラボNN · 名前`
2. **ヘッダー** — 所要時間、何を証明するか、何が必要か
3. **なぜこれを** — 「これからXを学びます」ではなく、実際の業務課題。連続シナリオの続き
   （後述）
4. **ミニ用語集** — このラボで新しく出てくる用語だけを、3列の表で: 用語、それが何か、
   「〜に似ているが」。3列目はvSphereのものの名を挙げ、同じ一息で、その用語がそれとどう
   違うかを述べます——2つの断片を別々のセルに分けるのではなく、一つのフレーズで。
   「アナロジーが崩れるところ」という別列を設けてはいけません: 文脈がなければ、その見出しは
   何の意味も持ちません
5. **ラボのフォルダにあるもの** — ラボのすべてのファイルの表: ファイル、それが何か、いつ
   役立つか。読者は、`apply` コマンドの `name.yaml` がどこから来たのか、自分で作る必要が
   あるのかを、推測させられてはいけません。ラボが適用するファイルはすべて、そのフォルダに
   置く必要があります（または隣のフォルダに置き、その場合はパスを明示する:
   `../03-scale/hpa.yaml`）
6. **ステップ** — 1ステップにつき1つの動作
7. **確認** — 結果はどうあるべきか、どうやって見るか
8. **後片付け** — 必須、そしてそれがなぜ安上がりかの説明を添えて
9. **これでできるようになること** — 3〜4項目
10. **vSphereならこれは** — 正直な比較。vSphereのほうが便利な点も含めて

## 連続シナリオ

すべてのラボは、練習問題の寄せ集めではなく、一つの業務課題の一部です。

**前提:** あなたはプラットフォームチームの一員です。事業部門から、「入館証」という社内
サービスを展開してほしいと依頼されます——社員がモバイルアプリでゲスト用の入館証を申請し、
警備が受付でその一覧を見て、経営層は月に一度レポートを見ます。

各サービスは、順番が来たからではなく、**具体的な痛みがあるから**登場します:

| 登場するもの | 理由 |
|---|---|
| Harbor | 情報セキュリティ部門がインターネットからのイメージ取得を禁じた |
| Redis | レガシーシステムの社員名簿が応答に800msかかる |
| MongoDB | 入館証によってフィールドが違う: 一回限り、1週間、車両用 |
| OpenBao | 監査がマニフェスト内にデータベースのパスワードを見つけた |
| ClickHouse | 経営層が「ゲストは何人で、ピークはいつか」を知りたがっている |
| バケット | モバイルチームにAPKを置く場所がない |
| GitOps | 3人でやっていて、誰かが手作業で変更し、すべてが落ちた |
| カタログ | 子会社が同じサービスを自分たちにも欲しがっている |

ラボ0〜4は、本番の課題が始まる前の、無害なアプリケーションでの練習です。これははっきりと
断ります:「まずは補助輪から」。

## コードとマニフェストの読み解き

**読み解きのないYAMLは、どこにも登場しません。** 読者が理解しないまま適用するファイルは、
一つもあってはなりません。

読み解きはスポイラーに入れ、本文の流れが膨らまないようにします:

```markdown
<details>
<summary><b>マニフェストを1行ずつ読み解く</b></summary>

...1行ずつ、散文で...

</details>
```

読み解きでは、そのブロックに何が書いてあるかではなく、**なぜそのブロックが必要か**を
説明します。悪い例:「`replicas: 1` はレプリカ数です」。良い例:「`replicas: 1` — 起動した
まま保つコピーの数。コピーが消えると、クラスターは何も聞かずに新しいものを作ります。次の
ラボの自己修復は、ここから来ています」。

## 予測される失敗

**どのラボにも、ふさわしい箇所には、通らない確認を必ず入れます。** 読者は壁にぶつかり、
原因を切り分け、次のステップの必要性を自分で理解します。

形は常に同じで、その順序は決して入れ替えません:

1. すべてがすでに整っているかのように、確認を促す
2. **エラーを見せる** — まず出力、それから質問。逆にしない
3. 読者を止める
4. 答えを収めたスポイラー——そして、この個別のエラーより広い教訓とともに

ラボが互いにばらけないよう、言い回しを一字一句固定する箇所が3つあります。

「止め」は常に引用ブロックのコールアウトで、⚠️ は付けません（このマーカーは落とし穴用に
取ってあります）:

```markdown
> **読み進める前に、立ち止まって考えてください。**
>
> 質問。あれば、2つ目の質問。
```

スポイラーの見出しは常に `答えと、このエラーより広い教訓` です。

スポイラー内の、教訓そのものを述べる段落は、次のように始めます:
`**教訓は、このエラーより広い。**`

失敗は、演出ではなく本物でなければなりません。ステップが動くなら、わざと壊す必要は
ありません。

## 2つの道: マウスとテキスト

ある操作がダッシュボードと `kubectl` の両方で可能な場合は、**両方**を示し、それぞれがいつ
ふさわしいかを述べます。

**どちらの道もスポイラーには隠しません。** テキストでの作業は、ダッシュボードが落ちたときの
予備手段ではありません: まさにそれこそ、私たちが読者を導いていく先です。なぜなら、ファイルに
書かれた記述はレビューでき、Gitに入れられ、ロールバックできるからです。スポイラーは、
フィールドを読み解くためのものであって、作業のやり方そのもののためではありません。

マネージドサービス（Harbor、Redis、MongoDB、ClickHouse、OpenBao、バケット、仮想マシン）は、
ダッシュボードで進めます: セルフサービスの感覚が伝わるのはそこだからです。

自作のアプリケーションは、`kubectl` とGitで進めます: インフラがテキストであり、レビュー
でき、ロールバックできるということが伝わるのはそこだからです。

## 一貫した名づけ

一つのものは、すべてのラボ、すべてのチャットメッセージで、同じ名で呼びます。読者は順不同で
教材を進めるので、`lab` と「学習用クラスター」が同じものだと推測させてはいけません。

| もの | 呼び方 |
|---|---|
| 教材の単位 | 「ラボ」。「実習」でも「モジュール」でも「レッスン」でもない |
| ラボ0の学習用クラスター | `lab` アプリケーション |
| ラボ0〜4の練習用アプリケーション | `rickroll` |
| ラボ5〜14の本番サービス | 本文では「入館証」、マニフェストでは `passes` |
| テナント番号 | プレースホルダーでは `workshopXX`、読み解き例では `workshop03` |

別途: **アクセスファイルへのパスと環境変数の名前は、どこでも同じにします。** あるラボでは
テナントの kubeconfig が一つのパスにあり、隣のラボでは別のパスにあると、読者はこれらを2つの
別ファイルだと判断し、結局2つ持つことになります。

ラボのタイトルにある名前と、ルートの `README.md` の表にある短い名前は、互いにそれと分かる
必要があります。表の「キャッシュ」と、ファイルの「遅いバックエンドの前段のキャッシュ」は、
明らかに同じラボです。表が一つの語を掲げ、タイトルが別の語を掲げていると、読者はファイルを
手当たり次第に開くことになります。

ラボのヘッダーにある所要時間と、ルートの `README.md` の表にある所要時間は、同じ数字です。
ヘッダーでは、待ち時間も含めた全体の時間を示し、そのうちどれだけが待ち時間かを別途
明記します。

## 体裁

- セクションもステップも、どちらも `##` レベルです。ステップの見出しは `## ステップN. 何をするか`。
  「パート」「段階」「演習」という語は使いません——どこでも「ステップ」です。ステップ内の
  小見出しは `###` ですが、多くの場合はスポイラーのほうが適しています
- コマンドは、言語を明記したブロックに入れます: ` ```bash `、` ```yaml `、` ```sql `
- 各コマンドの前に、これから何が起きるか。あとに、何が見えるはずか
- 行は100文字を超えない
- 絵文字は機能マーカーだけ: 📍 どこで実行するか、⚠️ 落とし穴。ラボではこれ以外は使いません。
  チャットメッセージでは、これらに 🖱 マウスでの操作、📄 リポジトリ内のファイル、
  ⏳ 長い待ち時間が加わり——リストはそこで打ち止めです
- 列があるところでは、リストではなく表を使います

## 確認

どのフォルダにも `check.sh` があります。参加者は自分でそれを実行し、レポートを受け取ります:
何が確認され、何が通り、何が通らなかったか、そして添付された証跡。スクリプトの要件は
`check/README.md` にあります。

ラボの本文では、「確認」セクションでそれに言及します。

## してはいけないこと

- 他のラボのステップ番号を参照しない——ラボは順不同で進められます
- 自分のラボの中でさえ、ステップ番号を参照しない（「ステップ7の予測される失敗」）: 編集する
  とステップはずれ、参照は静かに誤ったものになります。「ラボのもう少し先で」と書きます
- 「何が必要か」に書かれていない限り、前のラボが済んでいると想定しない
- 公開するテキストに `TODO`、`TBD`、プレースホルダーを残さない
- マニフェストのフィールドや Secret の名前を創作しない。cozystack リポジトリの
  `packages/apps/<app>/values.schema.json` で確認します
