## 1. 私たちが実際に行うこと

**最初のコマンドを実行する前に、これを読んでください。この先がずっと分かりやすくなります。**

### 現在あなたが持っているもの

社内の「Orders」サービスです。vSphere では、これに**3台の仮想マシン**が割り当てられています。よくある構成そのままです。

| マシン | 搭載されているもの | アドレス |
|---|---|---|
| `app` | Java で書かれた `orders-api` アプリケーション、CentOS 7 | — |
| `db` | 手作業でインストールされた PostgreSQL | `192.168.10.30` |
| `mq` | 手作業でインストールされた Kafka | `192.168.10.40` |

このアプリケーションは Spring Boot で書かれており、通常の systemd サービスとして動作し、設定は `/etc/orders/application.properties` に置かれています。そして、まさにそこが面白いところです。

```properties
spring.datasource.url=jdbc:postgresql://192.168.10.30:5432/orders
spring.kafka.bootstrap-servers=192.168.10.40:9092
```

**アドレスがべた書きされています。** 名前ではなく、数字です。かつて誰かが3台のマシンを立ち上げ、IP を設定ファイルに書き込み、それ以来この3つの数字がインストール全体を支えてきました。サブネットが変われば、アプリケーションは動かなくなります。データベースを別のホストに移せば、ファイルを手作業で開いてサービスを再起動しなければなりません。

今これが自分のインフラのことだと思い当たったなら——そう、どこでも同じです。

### これに対して私たちが行うこと

移すのは **`app` だけ**です。他の2台はどこにも移しません。その代わりに、Cozystack のカタログからすぐに使える Postgres と Kafka を利用します。

この違いは本質的です。3台の仮想マシンをすべて移すだけなら、私たちなしでもできます。しかしそれでは、同じ動物園を新しいハードウェアの上に再現するだけです。2019年にインストールしたきりの、誰も更新せず、誰もバックアップも取らない——「あれ用のスクリプトがあったはずだよね」という——あの同じ Postgres です。マネージドサービスは、レプリケーション、バックアップ、モニタリングを備えて届き、あなたはそれについて一切考えなくてよくなります。

**その過程でデータが1件も失われてはいけません**——これまでの全期間の注文を、新しいデータベースへ移さなければなりません。これは独立したステップであり、実際のマイグレーションでは最も緊張する作業です。

この違い——「動物園を移した」のか、それとも「アプリケーションを移して動物園を捨てた」のか——こそが、このワークショップの主題です。

その道のりは3つのフェーズに分かれます。

**フェーズ1 — イメージを取り出す。** vSphere の仮想マシンのディスクを、Cozystack が理解できる形式に変換し、クラスターが取得できる場所に置く必要があります。これがステップ1〜3です。

**フェーズ2 — 新しい環境でマシンを立ち上げる。** 取り出したイメージから、今度は Cozystack 上で仮想マシンを立ち上げ、正気に戻します。周囲のハードウェアが変わったため、ネットワークがない状態になっているからです。これがステップ4と6です。

**フェーズ3 — 動物園を捨てる。** カタログから Postgres と Kafka を立ち上げ、**古いデータベースからデータを移し**、アプリケーションをべた書きの IP から適切な名前へと設定し直します。これがステップ5、7、8、9です。

> **Kubernetes を扱ったことがなくても——大丈夫です、そういう設計になっています。** すべての用語は進めながら説明され、次のメッセージは、それらすべてを vSphere の言葉に翻訳した小さな用語集です。
