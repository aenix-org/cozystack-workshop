## 26. 最初のチェック：起動を試してエラーを捕まえる

**このステップは飛ばさないでください。すべての中でいちばん役に立ちます。**

📍 **場所：** あなたのVMの中 — フェーズ3で立ち上げたVM（app-VM）です。bastionの上ではありません。

VMは移動し、起動し、ネットワークも動いています。理屈で言えばそのまま動くはずです — アプリケーションはこのVMの上に前と同じ場所に載っていて、私たちは何も触っていません。確認してみましょう：

```bash
systemctl status orders-api
curl -s -o /dev/null -w 'HTTP %{http_code}\n' localhost:8080/actuator/health
```

**動きません。** サービスは起動に失敗しているか、`503` を返しています。何に文句を言っているのか見てみましょう：

```bash
journalctl -u orders-api --no-pager | tail -20
```

ログには `Connection to 192.168.10.30:5432 refused` のようなもの、あるいは同じアドレスに対するタイムアウトが出るはずです。

> **読み進める前に、立ち止まって考えてください。**
>
> アプリケーションには触れていない、VMは起動した、ネットワークも動いている。なのに、なぜ起動しないのでしょうか？

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

なぜなら、設定にはアドレス `192.168.10.30` と `192.168.10.40` がべた書きされているからです — データベースとキューで、これらは **vSphere上の別の2台のVM** に載っていました。私たちはそれらを運んでこなかったし、運ぶつもりもありませんでした。ここではそのアドレスには何もありません。

アプリケーションは正常、VMも正常、ネットワークも正常。壊れている唯一のものは、周りの世界が前のままだという思い込みです。

**これこそが本物のマイグレーションです。** ディスクを移すのはその中でいちばん簡単な部分で、たいてい注目がすべてそこに集まります。壊れるのはいつも外側にあるもの — アドレス、DNS名、認証情報、証明書、隣接するシステムです。だからこそ実際のプロジェクトでは、VMを移すのに1日、「動くようにする」のに数週間を見込むのです。

あなたはたった今、それを2分で、しかも自分の身をもって体感しました — 誰かのスライド資料の中で、ではなく。

</details>

**次にやること。** 直すのはアプリケーションではなく、その世界観です：べた書きされたIPの代わりに、ステップ5で立ち上げたマネージドサービスの名前を入れます。
