## 24. ステップ5: カタログからデータベースとキューを

**マネージドの Postgres と Kafka を立ち上げる**

📍 **場所:** bastion 上。

元のシステムでは、データベースとキューは別々の CentOS 7 の VM 上で動いていました。設定ファイルにあった、まさにあの
`192.168.10.30` と `192.168.10.40` です。これらは **持ち込みません**。代わりにプラットフォームのサービスを使います。時代遅れの OS にパッチを当てるのは、もうあなたの仕事ではありません。

<details>
<summary><b>なぜアプリケーションにキューが必要なのか、そもそもキューは何をするのか</b></summary>

もっともな疑問です。データベースが必要なのは明らかですが、キューはここで何をしているのでしょう。

**アプリケーションの動き方。** ユーザーが注文を作成します。もしアプリケーションがすべての作業を一度にやってしまうと——注文を記録し、計算を実行し、メールを送り、隣接システムを呼び出す——ユーザーはそれが全部終わるまで待たされます。そして隣接システムがダウンしていれば、タイムアウトになるまで待たされたあげく、注文はすでに作成済みなのにエラーを受け取ることになります。

そこで作業を二つに引き裂きます。アプリケーションは注文をステータス `NEW` でデータベースに書き込み、「注文 #123 が現れた」というメッセージをキューに載せて、**すぐさまユーザーに返答します**。その先は、ハンドラーが自分のペースでキューからメッセージを取り出し、重い部分を処理して、注文のステータスを `PROCESSED` にセットします。

まさにこのために、テーブルには `processed_by` フィールドがあります。ステップ9でそこに `kafka` という値が入っているのを見ることになります——それが、「アプリケーション → キュー → ハンドラー」という連鎖が新天地で再びつながったことの証拠になります。

**vSphere ではどうだったか。** 別建ての VM があり、その上に手作業で入れられた Kafka と ZooKeeper が載っていました。誰が入れたのかは不明、バージョンはその当時のありもの、更新は一度もなし、監視もなし。誰もが再起動を怖がる、あの古典的なマシンです。

**なぜキューは移す必要がなく、データベースは必要なのか。** 違いは、それぞれが何を保持しているかにあります。データベースには全歴史にわたるすべての注文が入っています——失えば、会社はデータを失います。キューにはいままさに輸送中のメッセージだけが入っています——寿命は数秒です。キューの正しい移行とは、ハンドラーに残りを食べきらせて、新しいほうへ切り替えることです。コピーするものは何もありません。

これはワークショップから持ち帰る価値のある一般則です。**移行で苦労するのは、状態を保持しているもの相手です。** それ以外はすべて一から作り直されます。

</details>

```bash
kubectl apply -f manifests/04-managed.yaml
kubectl get postgreses.apps.cozystack.io,kafkas.apps.cozystack.io -n tenant-workshopXX
```

これらは一瞬では立ち上がりません——待っているあいだに、ダッシュボードで何が作成されたのかを見てみましょう。

**何が作成されたか:** `db` という名前の **Postgres** オブジェクト——その中にデータベース `orders` とユーザー `orders` があります——と、トピック `orders` を持つ `kafka` という名前の **Kafka** オブジェクトです。名前は変えないでください。以下のアドレスや次のステップのコマンドは、これらの名前を当てにしています。

🖱 **ダッシュボード経由:** これはマウスにとって一番わかりやすいステップです。プラットフォームのカタログで
**Postgres → Deploy new**: 名前 `db`、レプリカ1つ、users セクションにユーザー `orders`、databases セクションにデータベース `orders`。続いて **Kafka → Deploy new**: 名前 `kafka`、レプリカ1つ、トピック `orders`。

**書き留めておく必要はありませんが、アドレスを挙げておきます——ステップ7で役に立ちます。** クラスター内部からは、データベースとキューは名前でアクセスできます:

• Postgres — `postgres-db-rw.tenant-workshopXX.svc.cozy.local:5432`
• Kafka — `kafka-kafka-kafka-bootstrap.tenant-workshopXX.svc.cozy.local:9092`

この2行こそが、2ステップ先で、アプリケーションの設定ファイルにベタ書きされたアドレス `192.168.10.30` と `192.168.10.40` を置き換えることになります。これらは出来合いのコマンドとしてお送りしますので、`XX` の代わりに自分の番号を当てはめてください。

違いそのものを覚えておいてください。以前はアプリケーションはベタ書きのアドレスを頼りに動いていましたが、いまは名前で動きます。アドレスは変わりうるが、名前は残ります。
