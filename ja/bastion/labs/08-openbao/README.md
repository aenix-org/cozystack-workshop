## なぜこれが重要か

「入館証」サービスは動いています。従業員がゲストのために入館証を申請し、警備がそのリストを見ます。
警備チームが定例監査でやって来て、あなたのリポジトリから一行を持ち込みました。

```yaml
- name: DB_PASSWORD
  value: "Propusk2019!"
```

入館証データベースのパスワードがマニフェストの中にあります。マニフェストは Git の中にあります。Git は
3 つのチームにまたがる 12 人が見られ、さらに 4 人はすでに退社しており、去年インテグレーションを担当した
業者の VM には、リポジトリの完全なコピーが残っています。

監査担当の問いは、いかにも定例らしく聞こえます。**「このパスワードを変更し、過去 1 か月で誰がそれを
読んだか見せてください」**。答えようがありません。パスワードを変えるとは、ハードコードされている場所を
すべて見つけ出すこと。誰が読んだかは不明です。なぜなら Git からファイルを読んだ記録は、どこにも残らない
からです。

このラボでは、パスワードを OpenBao へ移し、アプリケーションにそこから取得させることを教え、パスワードを
1 つのコマンドで変更し、そしてそれについてシステムが何を知っているかを見ます。

その道中で、ほとんどの人がつまずく問いに決着をつけます。**Kubernetes の Secret は本物のシークレットストアと
どう違うのか。**

このラボのすべての用語は、初めて登場したときに説明されます。そして次の節は、すでに導入した用語の
用語集です。

## 用語集

| 用語 | それは何か | ～に似ているが |
|---|---|---|
| **Secret（Kubernetes）** | base64 で書かれたデータを保持するクラスターオブジェクト | **VM のディスク上のパスワードファイル**。ただし保護されているように見えて、実は保護されていない——これは下で分解します |
| **base64** | 任意のバイト列を印字可能な文字で書き表す方法 | **uuencode、MIME 添付**。ただし暗号化ではない。鍵は存在せず、誰でも元に戻せる |
| **シークレットストア** | 独立したサービス。シークレットを暗号化して保持し、ルールに従って渡す | **直接の対応物はない**。ただし「パスワードだらけのネットワークフォルダ」ではなく、ポリシー・有効期限・ログを備えたサービスである |
| **OpenBao** | そうしたストアの一つ。HashiCorp Vault のフォークで、MPL ライセンスの下でリリースされている | コマンドと API は Vault と一致する。ユーティリティの名前が `bao` である点だけが違う |
| **Root トークン** | すべてにフルアクセスできるアカウント | **root**。ただしセットアップ時に一度だけ使い、その後は権限を絞ったトークンを発行する |

このラボの残りの語彙——`sealed`、開封鍵（unseal key）、ポリシー、トークン、KV v2、ローテーション、監査ログ、
init コンテナ——は、それぞれが初めて必要になるステップで、進みながら導入します。今それらを暗記する必要は
ありません。動作から切り離せば、どのみち頭に残らないからです。

<details>
<summary><b>最初に一覧をまとめて見たい方へ</b></summary>

| 用語 | それは何か | ～に似ているが |
|---|---|---|
| **Sealed（封印済み）** | サービスは動いているが、マスターキーがメモリにない状態。データは暗号化されたまま置かれ、API はリクエストを拒否する | **「サービスは起動したが、ボリュームがマウントされていない」**。ただし再起動のたびに、また手作業で開封しなければならない |
| **開封鍵（unseal key）** | ストアを開封するのに使う、マスターキーの分割片 | **金庫の鍵**。ただし分割片は複数あり、既定では複数を提示しなければならない |
| **ポリシー** | パスと、そのパスで何が許可されているかの一覧 | **フォルダの ACL**。ただしパスはディスク上のファイルではなく、API 内のアドレスである |
| **トークン** | ストアへの一時的な通行証 | **セッション**。ただしトークンには有効期間があり、自分で失効し、取り消すこともできる |
| **KV v2** | バージョン履歴を持つ「キー・バリュー」エンジン | **変更履歴付きのファイルフォルダ**。ただし全バージョンと各書き込みのタイムスタンプを保持する。古い値は決して消えない |
| **ローテーション** | 予定に沿ったシークレットの新しいものへの入れ替え | **スケジュールに従ったパスワード変更**。ただしここでは 1 つのコマンドで済み、アプリケーションは次回起動時に拾い上げる |
| **監査ログ** | 「誰が、いつ、何を要求したか」の記録 | **ファイル共有のアクセスログ**。ただし失敗や拒否も含め、API リクエストごとに一行が書かれる |
| **シークレットゼロ** | アプリケーションが他のすべてへの権利を証明するために使う、たった一つのシークレット | 完全になくすことはできない。短命・狭い権限・使い捨てにはできる |
| **Init コンテナ** | メインのコンテナが起動する前に実行され、終了するコンテナ | **サービス起動前に走るスタートアップスクリプト**。ただし失敗するとメインのコンテナはそもそも起動しない——それこそが望ましい挙動である |

</details>

## ラボのフォルダに何があるか

ファイルはすべてもう手元にあります——リポジトリと一緒に受け取っています。作ったり打ち直したりするものは
何もありません。下の本文で `kubectl apply -f name.yaml` と書かれている箇所では、そのファイルはここから来ます。

```bash
cd labs/08-openbao
```

| ファイル | それは何か | いつ使うか |
|---|---|---|
| `openbao.yaml` | シークレットストアの注文——ダッシュボードのボタンと同じもの | `lab` クラスターではなく、**テナント内で** 適用します |
| `secrets-demo-naive.yaml` | サービスが今どう見えるか——パスワードがファイルの中にそのまま。これが監査で見つかったもの | 自分の `lab` クラスターで適用します |
| `secrets-demo-secret.yaml` | 「素朴な修正」——パスワードを Secret に移した、そしてなぜそれでは不十分なのか | 同じ場所に適用します |
| `secrets-demo.yaml` | 最終版——パスワードはどこにもない。平文でもなく、base64 でもなく | 同じ場所に適用します |
| `check.sh` | アプリケーションがストアからパスワードを取得していることのチェック | ラボの最後に実行します |

## ステップ 1. 問題を自分の目で見る

📍 **場所:** bastion 上、lab クラスターで。

監査の見つけたものを自分の場で再現しましょう。lab クラスターに小さな `secrets-demo` サービスを立て、
その記述からパスワードをそのまま渡します。まずファイルを読み解き、それから適用します。

<details>
<summary><b>詳しく見る: secrets-demo-naive.yaml の中身</b></summary>

これはごく普通の `Deployment`——アプリケーションの記述です。どのイメージを取り、いくつのコピーを動かし
続けるか。**イメージ** とは、プログラムを内側に含んだファイルシステムの出来上がったスナップショットです。
vSphere で最も近い対応物は VM テンプレートで、ただしオペレーティングシステムがない状態のものです。
**コンテナ** はイメージの実行中のインスタンスです。**Pod** は Kubernetes における最小の実行単位で、
常に一緒に生き、一緒に死ぬ 1 つ以上のコンテナです。
Deployment は、動いている Pod の数が注文された数と一致するよう見張ります。

```yaml
      containers:
        - name: app
          image: busybox:1.36
```

自前レジストリのラボで Go で組み上げた本物の「入館証」アプリには、ここでは手を触れません。それは動いて
おり、演習のために壊す理由はありません。そこで、その傍らに別の小さな `secrets-demo` サービスを立てます——
関心の対象はアプリケーションではなく、パスワードがそこへ届く経路だからです。だからその代わりに置くのは、
唯一の意味ある仕事をする小さなコンテナ——10 秒に一度、どのパスワードで動いているかをログに書く、それだけです。

```yaml
          env:
            - name: DB_PASSWORD
              value: "Propusk2019!"
```

この一行こそが話の眼目です。環境変数は、アプリケーションに設定を渡すごく普通のやり方です。マニフェスト内の
`env` がコンテナ内の変数になります。仕組みは良い。悪いのは、**値がファイルの中にそのまま置かれている** ことです。

```yaml
                  "$(printf %s "$DB_PASSWORD" | sha256sum | cut -c1-12)"
```

アプリケーションはパスワードそのものではなく、その **フィンガープリント**——sha256 の最初の 12 文字——を
出力します。フィンガープリントを見ればパスワードが変わったことは分かりますが、そこからパスワード自体は
復元できません。ログはこう書くべきで、このラボの残りでもこれを使います。

`resources.requests` は、保証として確保しておくリソース量（vSphere の reservation の対応物）、
`resources.limits` はそれを超えて上がることを許さない上限（limit の対応物）です。値がわざと極小なのは、
アプリケーションが何もしないからです。

</details>

**適用します。**

```bash
# KUBECONFIG は、kubectl がどのクラスターと話すかを指定する。ここではラボ 0 の
# lab クラスター。テナントは後で、ストアを注文するステップで必要になる。
export KUBECONFIG=~/lab.kubeconfig
cd labs/08-openbao
# apply = 「クラスターをファイルに記述された状態に合わせよ」。-f = ファイルから記述を取る。
# この名前のオブジェクトはまだ存在しないので、作成される。
kubectl apply -f secrets-demo-naive.yaml
```

**見えるはず** — `created` という語で終わる行。

得られたものを見てみましょう。

```bash
# logs = アプリケーションが出力に何を書いたかを表示する。別途のログファイルはない。
#   deploy/secrets-demo  この記述によって立ち上がった Pod から出力を取る
#   --tail=2             起動以来すべてではなく、最後の 2 行だけ
kubectl logs deploy/secrets-demo --tail=2
```

**見えるはず** — こんなもの。

```
08:14:31 connecting to passes-db.internal as passes_app, password fingerprint sha256:a609df223d57
```

アプリケーションは動いています。パスワードはファイルの中、ファイルは Git の中。これがまさに、監査が
見つけた状況です。

## ステップ 2. 素朴な修正: パスワードを Secret へ移す

📍 **場所:** bastion 上、lab クラスターで。

インターネット検索がまず勧めてくること——「それなら Kubernetes に Secret がある」。勧めどおりにやって
みましょう——そしてまず、ファイルで何が変わるかを見ます。

<details>
<summary><b>マニフェストで何が変わったか</b></summary>

独立したオブジェクトが現れました。

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: passes-db
type: Opaque
data:
  password: UHJvcHVzazIwMTkh
```

`Secret` は、機微なデータのためのクラスターオブジェクトです。`data` フィールドの値は base64 で書かれるので、
ファイルの中では `Propusk2019!` の代わりに `UHJvcHVzazIwMTkh` が立っています。

そして Deployment では、値の代わりに参照が現れました。

```yaml
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: passes-db
                  key: password
```

`value` の代わりの `valueFrom` は、「値をここからではなく、あちらのあのオブジェクトから取れ」を意味します。
Kubernetes は、コンテナ起動時に `passes-db` シークレットの `password` キーの中身を `DB_PASSWORD` 変数に
差し込みます。

これ自体は正しい技法です——値を書き込むのではなく、シークレットを参照する。問題は、参照の先に何があるか
です。

</details>

**適用します。**

```bash
# 同じ apply。ファイルには 2 つのオブジェクト——Secret と変更後の Deployment がある。クラスターは
# 記述されたものと既にあるものを比べ、両者を一致させる。
kubectl apply -f secrets-demo-secret.yaml
```

アプリケーションが依然として動くことを確かめましょう。

```bash
# rollout status は、アプリケーションの新バージョンが旧バージョンを完全に置き換えるまで待ち、その後で
# 初めて制御を返す。これがないと、古い Pod のログを読んでしまうことがある。
kubectl rollout status deploy/secrets-demo
kubectl logs deploy/secrets-demo --tail=2
```

フィンガープリントは同じ——`sha256:a609df223d57`。アプリケーションは、別の経路で同じパスワードを受け
取りました。

**問題は解決したでしょうか。** パスワードはもう Deployment に書かれていません。ファイルには読めない文字列が
立っています。確かめてみましょう。

## 予測できる失敗 · 「Secret」は「暗号化」を意味しない

もうすべて大丈夫だと自分を納得させてみてください。クラスターに、シークレットの中身が何かを尋ねます。

```bash
# get … -o yaml = 「オブジェクトを丸ごと、クラスターが保存しているそのままの形で見せよ」。
# 見るべきは data フィールド——それがシークレットの中身。
kubectl get secret passes-db -o yaml
```

同じ文字列 `UHJvcHVzazIwMTkh` が見えます。読めなさそうで、だから安全に見えます。

さて、コマンドを一つ。

```bash
#   -o jsonpath='{.data.password}'  ラッパーなしで、オブジェクトからちょうど 1 フィールドを取り出す
#   | base64 -d                     それを渡してデコードする: d = decode
#   ; echo                          末尾の改行を打つ。さもないと結果が次のターミナルの
#                                   プロンプトに続いてしまう
kubectl get secret passes-db -o jsonpath='{.data.password}' | base64 -d; echo
```

> **読み進める前に、立ち止まって考えてください。**
>
> パスワードを得るために、あなたはたった今、正確には何をしましたか。どんな鍵が必要でしたか。ほかに誰が
> このコマンドを実行できますか。

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

出力は `Propusk2019!` です。平文で。

**base64 は暗号化ではなく、エンコーディングです。** これはテキスト向けに作られたチャネルを通じて任意の
バイト列を運ぶために考案されました——メールの添付、JSON 内のデータ、設定ファイル内のバイナリ。鍵はありません。
なぜなら保護もないからです。誰でも元に戻せます——どんな人でも、どんなブラウザでも、どんなデコーダーの
ウェブサイトでも。

Kubernetes が Secret で base64 を使うのは、まさにこの理由からです。任意のバイト列（たとえば証明書や鍵）を
YAML に入れることはできませんが、base64 になら入れられます。オブジェクト名の中の「Secret」という語は、
「ここには機微なものを入れる」を意味するのであって、「ここでは保護されている」ではありません。

これが実際に何を意味するか。

| 主張 | 本当か |
|---|---|
| Secret はクラスター内で暗号化されている | いいえ。管理者が保存時暗号化を別途オンにしていない限り、クラスターのデータストアではほぼ平文で置かれている |
| Secret は Git にコミットできる | いいえ。それはパスワードをそこに置くのと同じ |
| 誰が Secret を読んだか分かる | いいえ。オブジェクトの通常の読み取りはどこにも記録されない |
| Secret は権限なしには読めない | 本当。そしてこれが唯一の本物の保護。クラスター内の権限はアクセスを実際に制限する |
| Secret はスケジュールに従って自ら変わる | いいえ。あなたが手作業で、すべての場所を一度に変える |

**このエラーより広い教訓。** そして肝心な点。仮にこれらすべてが解決されても、監査担当の問いは残ります。
**過去 1 か月で誰がパスワードを読んだか見せてください。** Kubernetes はこれに一切答えられません——作りが
悪いからではなく、それが Kubernetes の仕事ではないからです。シークレットの保管は別の仕事であり、そのための
別のサービスが存在します。

ちなみに、Cozystack テナントでのあなたのロールは、`kubectl` 経由でシークレットを読むことを **許しません**——
試せば拒否されます。しかしラボ 0 の lab クラスターは丸ごとあなたのもので、そこではあなたが管理者です。
上のコマンドが動いたのは、まさにそのためです。

</details>

## ステップ 3. OpenBao を注文する

📍 **場所:** ブラウザ内、Cozystack ダッシュボード内、自分のテナントで。

テナント → **アプリケーションを作成** → `OpenBAO`。

| フィールド | 値 | なぜ |
|---|---|---|
| Name | `secrets` | 短く、後でアドレスに打ち込むことになる |
| Replicas | **1** | 訓練用のテスト環境。2 以上ではチャートが Raft レプリケーションを有効にし、それはもう別のストレージモードになる |
| Size | `2Gi` | シークレットはキロバイト単位。この容量は内部データ用 |
| Storage class | `replicated` | データは異なるノードにまたがって 3 つのコピーで置かれる |
| Resources preset | `t1.small` | 1 CPU、512 MB |
| UI | 有効 | クラスター内部のウェブインターフェース |
| External | 無効 | 外へは公開しない |

⚠️ **1 コピーと複数コピーの切り替えは、チェックボックスではありません。** 1 コピーはデータをファイルに、
複数は Raft に保存します。モードの変更はデータの移行を要するので、本番ではこの判断はインストールの前に
下すのであって、後ではありません。

### 同じことをテキストで——そしてフィールドの読み解き

ラボのフォルダには `openbao.yaml` があります。

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: OpenBAO
metadata:
  name: secrets
  namespace: tenant-workshopXX
spec:
  replicas: 1
  size: 2Gi
  storageClass: replicated
  resourcesPreset: t1.small
  ui: true
  external: false
```

`apiVersion: apps.cozystack.io/v1alpha1` は Cozystack のカタログそのものを、API のように見える側から見たもの
です。ボタンを押すと、ダッシュボードはまさにこのオブジェクトを組み立ててクラスターへ送ります。ボタンは
テキストの上に載った層であって、テキストの代替ではありません。

`kind: OpenBAO` はカタログ内の項目です。大文字小文字に注意してください。`OpenBao` ではなく `OpenBAO`。
クラスターは大文字小文字にうるさいのです。

`namespace: tenant-workshopXX` — **マネージドサービスは、ラボ 0 の lab クラスターではなく、管理クラスター上の
あなたのテナントに住みます。** これは 2 つの異なるクラスターであり、このラボの残りを通じて心に留めておくことが
重要です。アプリケーションは一方に、ストアはもう一方にあります。

`replicas`、`size`、`storageClass`、`resourcesPreset` — マウスで埋めたのと同じものです。

`ui: true` — ウェブインターフェースを立てる。`external: false` — サービスに外部アドレスを与えない。クラスター
内部からはどのみち到達できます。

このファイルは **lab クラスターにではなく**、テナントに適用します。

```bash
# --kubeconfig はアクセスファイルを明示的に指定し、KUBECONFIG 変数を上書きする。
# よって注文は lab クラスターではなく、管理クラスター上のテナントへ向かう。
kubectl --kubeconfig ~/.kube/config apply -f openbao.yaml
```

テナントへの管理アクセスは、この bastion 上で既に設定済みです——ファイル `~/.kube/config`（トークンベースで、
ブラウザは開きません）。取り出したり保存したりするものは何もありません。

以降の本文では、このファイルはほとんど使いません。サービスはマウスで注文し、OpenBao 自体との作業は、その
固有の API を通じて行います。

アプリケーションが準備完了の状態に達するまで待ってください。1、2 分です。

## ステップ 4. 作業用 Pod を用意し、接続を確認する

📍 **場所:** bastion 上、lab クラスターで。

ここで立ち止まって、配置を理解する必要があります。

**OpenBao は管理クラスター上のあなたのテナントに住んでいます。** テナントでのあなたのロールは、サービスの
注文と削除は許しますが、そこで自前の Pod を動かしたり、ポートフォワーディングでサービスに接続したりは
できません。これは欠陥ではなく、境界です。テナントはマネージドサービスのための場所であって、作業台では
ありません。

**あなたの作業台は、ラボ 0 の lab クラスターです。** そこではあなたが管理者です。そこから OpenBao へ
到達します——どのサービスにもある内部アドレス経由で。

```
openbao-secrets.tenant-workshopXX.svc.cozy.local:8200
```

名前を部分に分けてみましょう。

| 部分 | 何を意味するか |
|---|---|
| `openbao-` | カタログが名前に付ける接頭辞。あなたはアプリケーションを `secrets` と名付けたが、オブジェクトは `openbao-secrets…` のような名前を得た |
| `secrets` | ダッシュボードであなたが与えた名前 |
| `tenant-workshopXX` | あなたのテナント。自分の番号に置き換える |
| `svc.cozy.local` | 管理クラスターの内部名前ゾーン |
| `8200` | OpenBao の API ポート |

作業用 Pod を立てましょう。その内側に `bao` ユーティリティが入っています——これでストアに命令し、bastion に
インストールする必要もありません。自分のテナント番号に置き換えてください。

```bash
# run は指定したイメージから 1 つの Pod を作る——クラスター内の使い捨ての小さなマシン。
#   --image          中身をどこから取るか: bao ユーティリティ入りの公式 OpenBao イメージ
#   --restart=Never  内部のコマンドが終わったら、もう一度立ち上げ直さない
#   --env            Pod の環境変数: その内部のどんなコマンドもこれを見る
#   --command --     2 つのダッシュ以降はすべて、Pod が実行するコマンド
# sleep 86400 = 「1 日何もしない」: Pod は作業場所としてのみ必要。
kubectl run bao-workbench \
  --image=openbao/openbao:2.5.1 \
  --restart=Never \
  --env=BAO_ADDR=http://openbao-secrets.tenant-workshopXX.svc.cozy.local:8200 \
  --command -- sleep 86400
# wait は条件が満たされるまでターミナルを保持する。
#   --for=condition=Ready  Pod が起動し、コマンドを受け付ける準備ができた
#   --timeout=120s         2 分後に諦めてエラーを返す
kubectl wait --for=condition=Ready pod/bao-workbench --timeout=120s
```

`BAO_ADDR` は、`bao` ユーティリティがストアのアドレスを取る変数です。Pod の作成時に一度設定しておけば、
毎回のコマンドで `-address=…` を書かずに済みます。

Pod は使い捨ての作業台で、惜しむものではありません。ラボの最後に、1 つのコマンドで削除します。

lab クラスターからテナントが見えることを確認しましょう。

```bash
# exec = 既に動いている Pod の内部でコマンドを実行する。コマンド自体は -- の後に来る。
# bao status はストアにその状態を尋ねる: 封印されているか、初期化されているか。
# ここではこれが接続チェックも兼ねる: 返事が来たこと自体が——テナントが見えている証。
kubectl exec bao-workbench -- bao status
```

**見えるはず** — 状態のテーブル。ここでは `Initialized false` と `Sealed true` の値が正しいものです。
ストアは動いているが、まだセットアップされておらず、閉じています。

```
Key                Value
---                -----
Seal Type          shamir
Initialized        false
Sealed             true
Total Shares       0
Threshold          0
Version            2.5.0
Storage Type       file
```

⚠️ **コマンドはゼロでない終了コードを返します——2 で、これはエラーではありません。** `bao status` では
終了コードはコマンドの成否ではなく、ストアの状態を意味します。0 は開封済み、2 は封印済みです。あなたの
シェルがゼロでないコードを強調表示したり、`command terminated with exit code 2` という注記が見えたりしても——
慌てないでください。すべて想定どおりに進んでいます。

⚠️ **コマンドが `connection refused`、`no such host`、または `i/o timeout` で失敗する場合は——**
先へ進んでも意味がありません。まず接続です。よくある原因を、可能性の高い順に。`workshopXX` を自分の番号に
置き換えていない。ダッシュボードのアプリケーションがまだ準備できていない。名前のタイプミス。名前は
`openbao-<アプリケーション名>` の規則で組み立てられます。あなたはアプリケーションを `secrets` と名付けたので、
アドレスに含まれるのは `secrets` ではなく `openbao-secrets` です。

## 予測できる失敗 · ストアがサービスを拒む

接続はあるので、パスワードを保存できます。試してみましょう。

```bash
# bao kv put = ストアにレコードを置く。
#   secret/passes/db  それが住むことになるパス
#   password=…        レコードの中身: 「フィールド名 = 値」のペア
kubectl exec bao-workbench -- bao kv put secret/passes/db password=Propusk2026
```

**見えるはず** — 書き込みの確認ではなく、拒否。

```
Error making API request.
Code: 503. Errors:
* Vault is sealed
```

> **読み進める前に、立ち止まって考えてください。**
>
> サービスは動き、ポートは応答するのに、ストアは働くことを拒みます。なぜ動いているサービスが、意図的に
> リクエストを提供しないことがあるのでしょう。そしてなぜ、それがおそらく正しいことなのでしょう。

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

前のステップの `bao status` の出力を、もっとよく見てください。

```
Sealed             true
Initialized        false
```

**封印されたストアは、インストールしたての OpenBao の正常な状態です。** ディスク上のデータはマスターキーで
暗号化されており、そのマスターキーはプロセスのメモリにありません。それがそこに置かれるまで、サービスは
何も読むことも書くこともできず、正直にすべてを拒否します。

このラボの残りを通じて、「開封する（unseal）」はちょうど一つのことを意味します——マスターキーの分割片を
ストアに提示し、鍵をそのメモリに置かせること。この語は紙への印刷とは何の関係もありません。

なぜこう作られているか。もしマスターキーが暗号化されたデータの隣に置かれていたら、暗号化は何も意味しません。
ディスクを盗んだ者が両方を手に入れてしまうからです。だから鍵は **RAM の中だけ** に住み、人や外部システムが
それを提示したときにそこへたどり着きます。

ここから、すぐに受け入れておく価値のある帰結が導かれます。**Pod が再起動するたびに、OpenBao は再び封印されます。**
ノードが再起動した、バージョンをアップグレードした、クラスターが Pod を移動させた——すると、開封されるまで
ストアはまた応答をやめます。本番ではこれを外部モジュール（クラウド KMS、ハードウェア HSM）による自動開封で
処理しますが、それはそれ自体で一つのプロジェクトです。ラボでは手作業で開封し、その仕組みを生で見ます。

**このエラーより広い教訓。** **マネージドサービスは、インストール・アップグレード・レプリケーション・
バックアップをあなたの肩から下ろしましたが、運用上の判断は下ろしませんでした。** Cozystack は OpenBao の
プロセスを 2 分で立ち上げてくれました。開封鍵をどこに保管するか、誰が開封してよいか、ノードが再起動した
午前 3 時に何をするか——これらは依然としてあなたの問いであり、プラットフォームがそれらを黙って肩代わり
しなかったのは良いことです。

</details>

## ステップ 5. 初期化して開封する

📍 **場所:** bastion 上、lab クラスターで。

**これから何が起こるか:** OpenBao はマスターキーを生成し、それを分割片に切り、root トークンと一緒に私たちに
渡します。これは二度と起こりません——鍵はちょうど一度だけ表示されます。

```bash
# operator init はストアの一生で一度だけ実行される: マスターキーを作り、その分割片を
# root トークンと一緒に出力する。この値を再び見せる者はいない。
#   -key-shares=1     マスターキーをいくつの分割片に切るか
#   -key-threshold=1  それを組み直すのにいくつの分割片を提示しなければならないか
kubectl exec bao-workbench -- bao operator init -key-shares=1 -key-threshold=1
```

**見えるはず:**

```
Unseal Key 1: 8kJq…=
Initial Root Token: s.7Yx…
```

⚠️ **両方の値を、今すぐ bastion 上のファイルにコピーしてください** — たとえば `~/openbao-lab.txt` に、
クリップボードだけにではなく。再びこれを見せる者はいません。開封鍵を失えば、ストア内のすべての
シークレットを失います——それらの復旧は設計上（by design）不可能です。

両方とも一度ならず必要になります。それがいつかというと。

- **開封鍵** — ストアの Pod が再起動するたびに。再起動時に再び封印され、あらゆるコマンドが
  `Code: 503 ... * Vault is sealed` と答え始めます。
  対処は、中断した同じ場所から、同じコマンドでもう一度開封すること。
- **root トークン** — ラボの最後、チェックスクリプトのために。この 2 つの時点の間にラボのほぼ全体が
  過ぎ去り、その頃にはおそらくターミナルを閉じているでしょう。

<details>
<summary><b>`-key-shares` と `-key-threshold` の意味、そしてなぜ本番は違うのか</b></summary>

マスターキーは丸ごとは渡されません。`key-shares` 個の分割片に切られ、それを組み直すには `key-threshold` 個を
提示しなければなりません。この方式はシャミアの秘密分散（Shamir's Secret Sharing）と呼ばれます。

肝心なのは、**開封を一人の人間が行えないようにすること** です。古典的な本番構成は 5 分割・しきい値 3 です。
分割片は異なる部門の 5 人の保持者に渡され、再起動後にストアを立ち上げるには、そのうち任意の 3 つを集める
必要があります。退社する管理者が一人いてもアクセスを持ち去りませんし、不正な管理者が一人いても単独では
手に入れられません。

私たちが 1 分割・しきい値 1 に設定するのは、ラボではあなた一人で、手順ではなく仕組みが欲しいからです。
**本番でこうしてはいけません**。そしてそれは形式論ではありません。単一の分割片は、そこからすべてが漏れうる
単一の点を意味します。

</details>

開封します。自分の開封鍵に置き換えてください。

```bash
# unseal はストアにマスターキーの分割片を 1 つ渡す。分割片がしきい値に達すると、
# 鍵はプロセスのメモリに入り、ストアはリクエストの提供を始める。
kubectl exec bao-workbench -- bao operator unseal <your-unseal-key>
# 変わった状態を見るために status を繰り返す。
kubectl exec bao-workbench -- bao status
```

**見えるはず** — `Sealed  false` と `Initialized  true`。

さて root トークンでログインします。それは作業用 Pod の内側に記憶され、以降のコマンドはトークンを尋ねません。

```bash
# login は入力したトークンを Pod 内のファイルへの記録に交換する——以降ユーティリティは
# そこからトークンを自分で取り、毎回のコマンドに打ち込まずに済む。
# -it は Pod にターミナルを与える: なければユーティリティはプロンプトを出す先も、入力を受ける先もない。
kubectl exec -it bao-workbench -- bao login
```

ユーティリティはトークンを尋ね、**入力中はそれを表示しません**——これは設計どおりです。`init` の出力から
Initial Root Token を貼り付けてください。

⚠️ **`bao login` がトークンファイルを書けないと文句を言う場合**、トークンを毎回のコマンドで環境変数として
渡してください。
`kubectl exec bao-workbench -- env BAO_TOKEN='your-token' bao status`。
これは動きますが、トークンがコマンド履歴に残ります——ラボでは許容範囲、本番では違います。

## ステップ 6. エンジンを有効にしてパスワードを保存する

📍 **場所:** bastion 上、lab クラスターで。

新しい OpenBao は空です。中には何かを置ける場所が一つもありません。シークレットエンジンは明示的に有効化します。

```bash
# secrets enable はエンジンを有効にする——一種類の仕事を知っているストアの一部分。
#   -path=secret  それをどのパスに掛けるか: 以降すべては secret/… として書かれる
#   kv-v2         正確にはどのエンジンか: バージョン履歴付きの「キー・バリュー」
kubectl exec bao-workbench -- bao secrets enable -path=secret kv-v2
```

<details>
<summary><b>シークレットエンジンとは何か、なぜ複数あるのか</b></summary>

OpenBao は単一のストアではなく、エンジンの集合です。それぞれが自分の仕事を知り、自分のパスにマウントされます。

| エンジン | 何をするか |
|---|---|
| `kv-v2` | あなたが入れたものを、バージョン履歴付きで保存する。普通の「キー・バリュー」 |
| データベースエンジン群 | PostgreSQL や MongoDB に一時ユーザーを 2 時間だけ **自分で** 作り、自分で削除する |
| PKI | 年に一度の警備部門への申請の代わりに、要求に応じて証明書を発行する |
| transit | 保存せずに、要求に応じてデータを暗号化する: 鍵はストアを離れない |

`-path=secret` — それをどのパスにマウントするか。以降このエンジンへのアクセスはすべて `secret/…` を通じて
行われます。

私たちは `kv-v2` を取ります——最も単純なケースです。保存すべき出来合いのパスワードがあります。データベース
エンジン群のほうがはるかに面白いです。それらは各実行ごとにアプリケーションに一時アカウントを発行し、
恒久的なパスワードという現象そのものをなくします。それは次のレベルで、それに成長して追いつく必要があります。
ここから始めるのが理にかなっています。

</details>

パスワードを保存します。

```bash
# kv put は新しいバージョンを丸ごと書く: 列挙されたフィールドがその中身になる。
# フィールドはいくつでもよい。ここでは 2 つ——パスワードとデータベースのユーザー名。
kubectl exec bao-workbench -- \
  bao kv put secret/passes/db password=Propusk2026 username=passes_app
```

**見えるはず** — `version  1` と作成時刻を持つ小さなテーブル。

読み戻せることを確認しましょう。

```bash
# kv get はレコードを読み、そのフィールドをテーブルで出力する。まだ root トークンで読んでいる——つまり、
# レコードが収まったことを確認しているのであって、アプリケーションに権限が足りるかは確認していない。
kubectl exec bao-workbench -- bao kv get secret/passes/db
```

## ステップ 7. アプリケーションにアクセスを与える——ちょうど一行だけ

📍 **場所:** bastion 上、lab クラスターで。

アプリケーションに root トークンを与えてはいけません。それでは何でもできてしまい、他人のシークレットの
読み取りやストアの削除まで含まれます。アプリケーションに必要なのは、たった一つのパスへの読み取りアクセスです。

ポリシーを書きましょう。

```bash
# policy write は名前付きの権限リストをストアに保存する。
#   passes-read  ポリシーの名前; 後でこの名前でトークンに付与される
#   -            ポリシーのテキストをファイルからではなく、標準入力から取る
#   -i           kubectl exec で: その入力を Pod の内側へ転送する
# <<'HCL' … HCL は複数行のテキストを、ファイルなしでコマンドに直接渡す方法。
kubectl exec -i bao-workbench -- bao policy write passes-read - <<'HCL'
path "secret/data/passes/db" {
  capabilities = ["read"]
}
path "secret/metadata/passes/db" {
  capabilities = ["read"]
}
HCL
```

<details>
<summary><b>ポリシーの読み解き</b></summary>

ポリシーは、パスと、そのパスで何が許可されているかの一覧です。明示的に許可されていないものはすべて拒否
されます。別途「拒否」を書く必要はありません。

```hcl
path "secret/data/passes/db" {
  capabilities = ["read"]
}
```

`secret/data/passes/db` は、ファイルシステム内ではなく **API 内** のパスです。`kv-v2` エンジンでは、
こう構成されています。`secret` はエンジンがマウントされている場所、`data` はエンジン固有の内部接頭辞、
`passes/db` は `kv put` コマンドで指定したものです。

⚠️ **この `data` 接頭辞は、腑に落ちない拒否の半分の源です。** コマンドラインでは `secret/passes/db` と
書きますが、ポリシーでは `secret/data/passes/db` です。`bao kv` ユーティリティは `data` をあなたの代わりに
差し込みますが、ポリシーは差し込みません。

`capabilities = ["read"]` — 読み取りのみ。書き込みでも、削除でも、隣接パスの一覧表示でもありません。

2 つ目のブロック、`secret/metadata/passes/db` は、バージョン情報へのアクセスです。いつ書かれたか、
バージョンがいくつあるか、どれが現在か。これも読み取りのみです。

`bao policy write passes-read -` — 末尾のダッシュは「中身を標準入力から読め」を意味します。だからこの
コマンドは `kubectl exec -i` で実行します。`-i` フラグが入力を Pod の内側へ転送します。

</details>

このポリシーでトークンを発行します。

```bash
# token create は新しいトークンを発行し、権限のセットをそれに結びつける。
#   -policy=passes-read  どの権限か: 上で書いたポリシー
#   -ttl=24h             有効期間; 1 日後にトークンは自分で働かなくなる
#   -field=token         周りのテーブルなしで、トークンの値だけを出力する——
#                        そのほうがコピーして渡すのに楽
kubectl exec bao-workbench -- \
  bao token create -policy=passes-read -ttl=24h -field=token
```

**見えるはず** — トークンの入った 1 行。

トークンをコピーしてください——すぐに必要になります。

ここでの有効期間は形式論ではありません。トークンがログに紛れ込んだ、バックアップに入った、bastion ごと
漏れた——明後日にはそれは役に立ちません。マニフェスト内のパスワードには、そうした性質はありません。

## ステップ 8. トークンをクラスターに置き、パスワードをマニフェストから取り除く

📍 **場所:** bastion 上、lab クラスターで。

アプリケーションには、自分が名乗るとおりの者だと OpenBao に証明する何かが必要です。トークンがその何かです。

```bash
# create secret generic は、ディスク上のファイルを介さず、クラスターに直接 Secret オブジェクトを作る。
#   passes-bao-token      オブジェクトの名前; アプリケーションの記述はこの名前でシークレットを参照する
#   --from-literal=name=…  値をコマンドラインから文字列として設定する
#                          （値がファイルにある場合の --from-file もある）
kubectl create secret generic passes-bao-token \
  --from-literal=token='paste-the-token-from-the-previous-step'
```

**注目: ファイルではなくコマンドです。** トークンはクラスターに直接作られ、Git には決してたどり着きません——
たどり着くべきファイルが存在しないからです。

<details>
<summary><b>シークレットゼロ: 私たちが打ち負かせなかったものについての正直な言葉</b></summary>

もっともな反論です。データベースのパスワードは取り除いたが、トークンをクラスターに置いた。一つの問題を
もう一つに取り替えただけではないか、と。

そうではありません。トークンがパスワードとどう違うかを示します。

| | マニフェスト内のパスワード | クラスター内のトークン |
|---|---|---|
| Git にある | はい、永遠に、コミット履歴の全体を通じて | いいえ、コマンドで作られた |
| 有効期間 | 永遠 | 1 日、その後は自分で死ぬ |
| 何を与えるか | 入館証データベースへのフルアクセス | ストア内の一行の読み取り |
| 取り消し | 書かれているあらゆる場所でパスワードを変更 | 1 つのコマンドで、即座に |
| 誰が使ったか分かる | いいえ | はい、監査ログに |

しかしこれで問題が完全に片づくわけではなく、片づいたふりをするのは不正直です。**アプリケーションが残りへの
権利を証明する、たった一つのシークレットは常に残ります。** それには名前さえあります——シークレットゼロ。
それを取り除くことは不可能です。何かで身元を示さなければならないからです。

一人前のシステムがそれをどう扱うか。

- **Kubernetes 認証。** OpenBao は Pod のサービストークンを Kubernetes 自身に対して検証し、引き換えに自分の
  トークンを発行します。すると「シークレットゼロ」は、人間が置いた文字列ではなく、クラスターが付与する
  Pod のアイデンティティになります
- **使い捨てトークン（response wrapping）。** オペレーターが、一度だけ使えるトークンを発行します。もし
  アプリケーションが「すでに使用済み」の拒否を受け取ったら、トークンが傍受されたということ——そしてそれは
  即座に分かります

どちらのアプローチも存在し、機能しますが、このラボでは私たちを遠回りさせてしまいます。道は存在すること、
そして目標は「シークレットゼロ個」ではなく「十数個の永遠のシークレットの代わりに、一つの短命で狭く、
取り消し可能なシークレット」であることを、心に留めておいてください。

</details>

さてクリーンなマニフェストを適用します。まず、自分のテナント番号に置き換えてください。

```bash
# sed は s/置き換えるもの/置き換え先/g のパターンでテキストを編集する; g = 行の最初だけでなく、
# すべての場所で。-i は結果を画面に出力するのではなく「ファイル自体を編集する」を意味する。
# 例の workshop03 の代わりに、自分の番号を置く。

# macOS: -i の後の空の引用符は必須——さもないと sed は次の単語を
# バックアップファイルの拡張子と受け取り、何も置き換えない
sed -i '' 's/tenant-workshopXX/tenant-workshop03/g' secrets-demo.yaml
# Linux
sed -i 's/tenant-workshopXX/tenant-workshop03/g' secrets-demo.yaml
```

<details>
<summary><b>詳しく見る: secrets-demo.yaml の中身</b></summary>

肝心なことから始めましょう。**このファイルの中でパスワードを探してください。** それはありません——
平文でも、base64 でも、それが収まっているであろうオブジェクトへの参照としても。

```yaml
      volumes:
        - name: secrets
          emptyDir:
            medium: Memory
            sizeLimit: 1Mi
```

`emptyDir` は、Pod と同じだけ生き、それとともに消える一時フォルダです。`medium: Memory` は、それが
ディスク上のファイルではなく、RAM の領域であることを意味します。パスワードはノードのディスクにも、
ボリュームのスナップショットにも、バックアップにも届きません。

```yaml
      initContainers:
        - name: fetch-secret
          image: openbao/openbao:2.5.1
```

init コンテナは、メインのコンテナ **より前に** 実行され、成功して終了しなければならないコンテナです。
それが失敗すれば、メインはそもそも起動しません。シークレットの取得にとって、これはまさに望ましい挙動です。
アプリケーションは空のパスワードで起動して、その後データベースへの最初のリクエストで失敗するべきでは
ありません。

```yaml
              bao kv get -field=password secret/passes/db \
                | tr -d '\n' > /secrets/db_password
              chmod 0400 /secrets/db_password
```

1 つのフィールドを取り、ファイルに書きます。`tr -d '\n'` は、万一改行が現れた場合にそれを取り除きます。
末尾に余分な文字が付いたパスワードはデータベースに通らず、それを突き止めるのは不愉快です。`chmod 0400` — 
所有者だけが読めます。

```yaml
          env:
            - name: BAO_ADDR
              value: http://openbao-secrets.tenant-workshopXX.svc.cozy.local:8200
            - name: BAO_TOKEN
              valueFrom:
                secretKeyRef:
                  name: passes-bao-token
                  key: token
```

ストアのアドレスとトークン。トークンは、あなたがコマンドで作ったオブジェクトへの参照で来ます。ファイルには
オブジェクトの名前だけがあり、名前はシークレットではありません。

```yaml
      securityContext:
        runAsNonRoot: true
        runAsUser: 100
        runAsGroup: 1000
        fsGroup: 1000
```

すべて non-root で動きます。`fsGroup` は、2 つのコンテナ——ファイルを書くほうと読むほう——の両方が
フォルダへのアクセスを持つために必要です。これがないと init コンテナは、メインが開けないファイルを書き、
あなたはどこで間違えたのか 30 分考え込むことになります。

```yaml
          volumeMounts:
            - name: secrets
              mountPath: /secrets
              readOnly: true
```

フォルダはメインのコンテナに読み取り専用で与えられます。アプリケーションはパスワードを壊すことも、
すり替えることもできません。

</details>

**適用します。** Deployment は新しいバージョンにロールオーバーします。init コンテナがストアへ行き、
パスワードを Pod のメモリに置き、それから初めてアプリケーション自体が起動します。

```bash
kubectl apply -f secrets-demo.yaml
# 新しいバージョンが旧バージョンを完全に置き換えるまで待つ。init コンテナがパスワードを
# 取得できなければ、待機は終わらない——そしてそれこそが、私たちの望む挙動。
kubectl rollout status deploy/secrets-demo
```

## ステップ 9. アプリケーションがストアからパスワードを取得したことを検証する

📍 **場所:** bastion 上、lab クラスターで。

まず init コンテナが何と言ったかを見ましょう。

```bash
# -c は Pod 内のコンテナを選ぶ。ここには 2 つあり、-c なしでは kubectl はどちらを
# 指すか当てられない。fetch-secret は、アプリケーション起動前に走ったほう。
kubectl logs deploy/secrets-demo -c fetch-secret
```

**見えるはず:**

```

```

さてサービス自体。

```bash
# メインのコンテナ: init コンテナが置いたファイルを読む。
kubectl logs deploy/secrets-demo -c app --tail=2
```

フィンガープリントが **変わりました**——以前は `sha256:a609df223d57` でしたが、今は別のものです。
アプリケーションは、リポジトリのどのファイルにもない新しいパスワードで動いています。

素朴なシークレットを取り除きましょう。もう不要で、邪魔になるだけです。

# delete はオブジェクトをクラスターから取り除く。アプリケーションはもうそれを参照していないので、

## ステップ 10. ローテーション: ファイルを一つも触らずにパスワードを変更する

📍 **場所:** bastion 上、lab クラスターで。

監査担当の最初の要求に戻りましょう。「パスワードを変更してください」。以前これは、書かれているあらゆる
場所を見つけ、直し、コミットし、ロールアウトし、何も見落としていないことを祈る、を意味しました。

今は。

```bash
# 同じ kv put。レコードの前のバージョンは消されない——その隣に 2 つ目が現れる。
kubectl exec bao-workbench -- \
  bao kv put secret/passes/db password=Propusk2026-осень username=passes_app
# rollout restart は、記述の一行も変えずにアプリケーションの Pod を作り直す。
# これがすべての目的だった: 新しいパスワードは次回起動時に拾い上げられる。
kubectl rollout restart deploy/secrets-demo
kubectl rollout status deploy/secrets-demo
# ログのフィンガープリントは、パスワードそのものを見せずに、パスワードが変わったことを示す。
kubectl logs deploy/secrets-demo -c app --tail=2
```

**見えるはず** — フィンガープリントがまた変わりました。2 つのコマンド、変更されたファイル 0、コミット 0。

⚠️ **アプリケーションは新しい値を、即座にではなく再起動時に拾い上げます。** 私たちは起動時に init コンテナで
シークレットを取得します——単純で信頼できるアプローチですが、更新には再起動が必要です。サービスがシークレットを
その場で拾い上げる必要がある場合は、タイマーで値を読み直してファイルを更新するサイドカーコンテナを追加します。
それはより複雑で、そこから始めるべきではありません。

履歴を見てみましょう。

```bash
# kv metadata get は値ではなく、レコードのバージョンについての情報を表示する: いくつあるか、
# それぞれいつ作成されたか、そして今どれが現在か。
kubectl exec bao-workbench -- bao kv metadata get secret/passes/db
```

**見えるはず** — 両方のバージョンと、その作成時刻。古い値は消えていません。もし新しいパスワードが
データベースに合わないと分かっても、戻る先があります。

前の値を丸ごと読むこともできます。

```bash
# -version=1 は現在のものではなく、最初に書かれたバージョンを読む。
kubectl exec bao-workbench -- bao kv get -version=1 secret/passes/db
```

これこそが **ローテーション** です。漏洩が起きた後ではなく、計画に沿ってシークレットを新しいものに
入れ替えること。「サービスアカウントのパスワードは四半期に一度変える」といった規則が、実行不能から
スケジュール上の一行へと変わります。

## ステップ 11. 監査ログ: 誰が何を求めたか

📍 **場所:** bastion 上、lab クラスターで。

監査担当の 2 つ目の要求——「誰がパスワードを読んだか見せてください」。ログを有効にしましょう。

```bash
# audit enable は監査デバイスを有効にする。
#   file              デバイスの種類: レコードをテキストで書く
#   file_path=stdout  ディスク上のファイルの代わりに——Pod の標準出力へ、そこから
#                     プラットフォームがログを集める
kubectl exec bao-workbench -- bao audit enable file file_path=stdout
# audit list は有効なデバイスを一覧表示する——上のコマンドが通ったかのチェック。
kubectl exec bao-workbench -- bao audit list
```

**見えるはず** — `file` タイプの有効なデバイスが 1 つ入ったテーブル。

<details>
<summary><b>監査ログに何が入るか、そしてそれが普通のログとどう違うか</b></summary>

この時点から OpenBao は、**API リクエストごとに** レコードを書きます。誰が求めたか（どのトークン、どの
ポリシー）、正確には何を、いつ、どのアドレスから、そして何と答えたか。リクエストごとにレコードは 2 つ——
リクエスト自体と、それへのレスポンスです。

見慣れたアプリケーションログとの 3 つの違い。

**拒否も書かれます。** 他人のパスを読もうとした試みは、成功した読み取りとまったく同じように痕跡を残します。
警備チームの関心を引くのは、まさにその拒否です。成功した読み取りは業務ですが、一連の拒否は偵察です。

**シークレットの値はログに入りません。** パス、名前、トークンはハッシュ化され、シークレットそのものは
書かれません。ログは、その中身も一緒に渡すことなく、外へ渡せます。

**ログを書く先がなければ、OpenBao は動作を止めます。** これは意図的な決定です。記録できないままリクエストを
提供するストアは、停止しているストアより悪いのです。ここから実務上の帰結が導かれます——唯一の監査デバイスを、
いっぱいになりうるディスク上のファイルに向けないこと。

⚠️ **このログをラボで読むことは許されません。これははっきり言っておかねばなりません。** 私たちはそれを
OpenBao の Pod の標準出力に向けましたが、あなたのロールはテナント内の Pod のログを読めません——テナントは
サービスの管理をあなたに渡しますが、その内部へのアクセスは渡しません。実際のインストールでは、プラットフォームの
ログ収集器がログを拾い上げ、あなたが `kubectl` 経由でではなく、警備チームが見る場所に置きます。

それでもあなた自身に見えるのは、前のステップのバージョン履歴（`bao kv metadata get`）です。誰が、いつ
**書いた** か、秒単位で。これは完全な監査ではありませんが、「最後にパスワードを変えたのはいつか」という
問いには答えます。

</details>

## vSphere ならこれは

直接の対応物はなく、それが正直な答えです。古典的なインフラでは、サービスアカウントのパスワードは 3 か所に
同時に住んでいます。VM 上の設定ファイル、部門のパスワードマネージャー、そしてそれを設定した人の頭の中。
ローテーションはこの 3 か所すべてを巡ることを意味し、だからこそ行われません。「誰が読んだか」という問いには
答えがありません。誰もファイルの読み取りを記録しないからです。

vSphere Credential Store があり、Windows Credential Manager があり、企業のパスワードマネージャーがあります——
それらはすべて「人がパスワードを保管するのに便利」という問題を解きます。「アプリケーションがパスワードを
自分で、ポリシーに従い、期限付きで、記録に残る形で取得する」という問題は、それらは解きません。

**vSphere のほうが便利なところを、正直に。** 上に挙げたどれでもありません——しかし便利さには代償が伴い、
それが何かを示します。

VM 上のファイル内のパスワードは **常に利用可能** です。ホストが再起動し、マシンが立ち上がり、サービスが
ファイルを読んで動き出す。午前 3 時に誰も起こす必要はありません。OpenBao は再起動後は封印されており、
開封されるまでアプリケーションは起動しません。これはあなたのインフラに新しい障害点と新しい手順を加えます——
当番、鍵の保持者、文書化されたプロセスとともに。外部 KMS による自動開封はこの問題を取り除きますが、
その外部 KMS への依存を加えます。

そして 2 つ目。ディスク上のファイルは、どんな管理者も一目で理解します。パス、ポリシー、トークン、TTL、
パスの途中の `data` 接頭辞——これはチームが学ばねばならない別のモデルであり、最初の数か月は腑に落ちない
拒否の源になります。

利得はそれでも上回りますが、それは無料ではなく、この代償を念頭に置いて移行を計画すべきです。
