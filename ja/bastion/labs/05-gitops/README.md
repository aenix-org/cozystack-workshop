## なぜこれが大切か

練習は終わりです。ここから先は本物の課題です。

ビジネス側は **「Passes(入館証)」** という社内サービスを求めています。従業員はモバイルアプリで来訪者パスを申請し、警備は受付でその一覧を見て、経営陣は月に一度レポートを見ます。あなたはプラットフォームチームの一員で、これを世に出すのがあなたの仕事です。

このサービスの背後にはいくつものチームがつき、プラットフォームチームはあなたを含めて三人です。そして、このラボが実務パートの一番最初に来る理由が、ここから始まります。

**管理者が三人いると何が起きるか。** 誰かはダッシュボードからアプリを立ち上げた。誰かは真夜中に火が出ていたから `kubectl edit` で上限をいじった。誰かは金曜にコピー数を変えて、月曜には忘れていた。一か月後、二つの問いに誰も答えられません。**なぜこの設定はこうなっているのか**、そして **本来どうあるべきか**。そしてすべてが崩れたとき、そこから復元できるものは何もないと分かります。状態はクラスターの頭の中だけにあり、クラスターと一緒に消えてしまったのです。

これに対する治療法は方針でもなければ、「みんなで手作業で触らないと約束しよう」でもありません。治療法は、手作業で触ることを **無意味にする** ことです。クラスターが元どおりに戻してしまうのです。今日オンにするのは、まさにこれです。

## 小さな用語集

| 用語 | それは何か | ～に似ているが |
|---|---|---|
| **リポジトリ(Repository)** | ファイル一式と、その編集の全履歴をまとめたもの。何が、誰によって、なぜ変わったか | **共有ドライブ上のテンプレートのフォルダ** に似ているが、一つを全員で共有するのではなく、各自が自分の完全なコピーを持つ |
| **GitOps** | 一つのアプローチ。望ましい状態は Git にあり、クラスター内で動くエージェントがそれを向こう側へ運んでいく | **ブループリントを使った vRealize Automation** に似ているが、一回きりの適用ではなく、継続的な突き合わせである |
| **Flux** | まさにそのエージェント。クラスターの中で動く | **スケジュール実行のエージェント/スクリプト** に似ているが、「適用したら忘れる」ではない。毎分チェックし、ずれがあれば直す |
| **Kustomization** | クラスター内のオブジェクト。リポジトリから何を適用するかを正確に定める | **デプロイのジョブ** に似ているが、`kustomize` ユーティリティと混同しないこと。名前は同じでも意味は別 |

このラボに残る言葉 — Git、Commit、Branch、Pull request、リコンサイル、ドリフト、GitRepository、Prune — は、進めながら、それが初めて必要になるステップで紹介します。今すぐ暗記する必要はありません。実際の操作と切り離すと、どのみち頭に残らないからです。

<details>
<summary><b>一覧をまとめて見ておきたい場合</b></summary>

| 用語 | それは何か | ～に似ているが |
|---|---|---|
| **Git** | テキストファイルを編集の全履歴つきで保管する仕組み | **設定ファイルのアーカイブ + 変更ログ** に似ているが、ファイルのコピーではなく一つ一つの変更を個別に、その著者と理由とともに保存する |
| **Commit** | 保存された一つの変更。何を、誰が、なぜ | **変更ログの一項目** に似ているが、編集が起きたという記述だけでなく、変わったテキストそのものを保存する |
| **Branch** | 変更の並行した一本の流れ | 直接の対応物はない。作業中のバージョンに触れずに変更を準備するために必要 |
| **Pull request** | ブランチをマージする提案。適用される前に誰かがそれをレビューする | **申請の承認** に似ているが、話し合うのは申請の大意ではなく、設定の具体的な行についてである |
| **リコンサイル(Reconciliation)** | ループ。望ましい状態を読む → 実際の状態と比べる → 直す | **クラスターを目標状態へ引き寄せる DRS のロジック** に似ているが、突き合わせるのはマシンの配置ではなく、記述されたすべてである |
| **ドリフト(Drift)** | 事実と記述との食い違い | **テンプレートの外で加えられた変更** に似ているが、ここでのドリフトは「コンプライアンスレポートに記録される」のではなく、黙って取り除かれる |
| **GitRepository** | クラスター内のオブジェクト。状態をどこから取るか | **テンプレートのソースの設定** に似ているが、そのソースは誰かが「デプロイ」を押した瞬間ではなく、スケジュールに従って自ら取得される |
| **Prune** | 「Git から消えたものはクラスターからも削除する」というモード | 直接の対応物はない。これがないと、リポジトリからファイルを消してもクラスターでは何も消えない |

</details>

## ラボのフォルダには何があるか

ファイルはすべて、もうあなたのものです。リポジトリと一緒に手に入れました。作ったり打ち直したりするものは何もありません。以下で `kubectl apply -f name.yaml` と書かれていれば、そのファイルはここにあります。

```bash
# ここから先、すべてのコマンドはこのフォルダから実行します。`kubectl apply -f` のパスはここからの相対です。
cd labs/05-gitops
```

| ファイル | それは何か | いつ役立つか |
|---|---|---|
| `app/` | クラスターに最終的に入るべきもの。namespace と「Passes」サービスそのもの | 自分の Git リポジトリに入れる |
| `flux/` | Flux 向けの二つの記述。リポジトリをどこから取るか、そこから何を適用するか | 自分の `lab` クラスターに適用する |
| `check.sh` | クラスターが自力で Git から変更を取り込んだかどうかのチェック | ラボの最後に実行する |

## ステップ 1. リポジトリを用意する

📍 **どこで:** ブラウザ、GitHub 上。

新しいリポジトリを作成します。

| 項目 | 値 | なぜ |
|---|---|---|
| 名前 | `passes-gitops` | これがソースコードではなくサービスの状態だと分かる |
| 公開範囲 | **Public** | Flux が鍵なしで到達でき、アクセス権に時間を取られないように |
| README ファイルを追加 | チェックを入れる | さもないとリポジトリは空でブランチもなく、Flux は読むものを見つけられない |

⚠️ **ここで公開リポジトリにするのは、学習用テスト環境のための意図的な簡略化です。** 本番ではリポジトリは非公開で、Flux はデプロイキー経由で到達します。それは SSH 鍵をいじる二十分がまた別に増えるということで、今日の主題はそこではありません。中に何が住むことになるか — パスワードを一つも含まないマニフェスト — は自分の目で確かめられます。パスワードは Git に入れません。それには別のラボがあります。

📍 **どこで:** bastion 上(bastion のターミナルで)。

リポジトリを自分のマシンに取り込みます。

```bash
# clone = リポジトリを、その編集の全履歴もろとも丸ごとダウンロードすること。共有フォルダへの
# アクセスではなく、ディスク上の自分だけの完全なコピーが手に入ります。オフラインでも作業できます。
# `YOUR-LOGIN` を自分の GitHub ログインに置き換えてください。さもないと他人のリポジトリに行ってしまいます。
git clone https://github.com/YOUR-LOGIN/passes-gitops.git
# clone はリポジトリと同じ名前のフォルダを作ります。ここから先はその中で作業します。
cd passes-gitops
```

## ステップ 2. 「Passes」サービスをリポジトリに入れる

📍 **どこで:** bastion 上(bastion のターミナルで)。

このラボのフォルダには二つのファイルがあります。`app/namespace.yaml` と `app/passes.yaml` です。これらを自分のリポジトリの `apps` フォルダにコピーします。

```bash
# apps — Flux が記述を取り込むフォルダ。名前は私たちが選んだもので、Flux の設定で名指しされている
# のとまったく同じ名前です。だから理由なく変える必要はありません。
#   -p  フォルダがすでに存在してもエラー扱いにしない
mkdir -p apps
# ワークショップ教材(~/workshop にあります)から両方のファイルを自分のリポジトリにコピーします。
# `*.yaml` で二つのファイルを一度に取ります。
cp ~/workshop/labs/05-gitops/app/*.yaml apps/
```

送り出す前に、何を入れるのかをおさらいしておきましょう。

<details>
<summary><b>もっと詳しく: namespace.yaml と passes.yaml の中身</b></summary>

### `namespace.yaml` — 自分専用の namespace

```yaml
kind: Namespace
metadata:
  name: passes
```

namespace は一つのクラスター内部の論理的な仕切りです。vSphere で最も近いのは vCenter ツリーのフォルダ、あるいはリソースプールです。リソースは同じでも、スコープが別、権限が別、クォータが別です。

これをアプリと一緒に Git に入れ、手作業で作らない理由は、いずれサービスがリポジトリから去るとき、Flux が namespace も一緒に取り除いてくれるからです。半年後に誰も何のために作ったか覚えていない空の仕切りが、後に残ることはありません。

### `passes.yaml` — サービスそのもの

`---` の行で区切られた四つのオブジェクトです。

**一つ目 — nginx 設定を持つ `ConfigMap`。** `ConfigMap` はテキストファイルをアプリケーションとは別にクラスターへ入れ、そのファイルがコンテナ内部にマウントされます。狙いは、イメージを作り直さずに設定を変えられることです。

中身はごく普通の nginx の設定です。一行だけ注目に値します。

```
sub_filter '__POD__' '$hostname';
```

これは nginx にこう指示します。配信するページの中で、テキスト `__POD__` を、それが動いているマシンの名前に置き換えなさい、と。Pod の内部では、マシンの名前は Pod 自身の名前です。こうしてページは、どのコピーが自分を配信したかを報告します。あとでその名前によって、いまやコピーが二つあることが分かります。

**二つ目 — ページを持つ `ConfigMap`。** 今のところこれは仮置きです。本物のアプリケーションは次のラボで登場し、今日大切なのはサービスが何を表示するかではなく、クラスターの中でそれが **どこから来たか** です。

**三つ目 — `Deployment`。** アプリケーションの記述です。どのイメージを、いくつのコピーで、レディネスをどうチェックするか。

```yaml
spec:
  replicas: 1
```

いくつのコピーを稼働させ続けるか。言い回しに注意してください。「一つ起動せよ」ではなく「一つを保て」です。これが、Git を通して変え、何が起きるかを見る、その数です。

```yaml
          readinessProbe:
            httpGet:
              path: /healthz
              port: http
```

レディネスチェック。クラスターはこのアドレスをノックし、応答が返るまでそのコピーにトラフィックを送りません。Flux にもこれが必要です。適用した直後に成功を報告するのではなく、レディになるのを待つよう頼むからです。

**四つ目 — `Service`。** すべてのコピーの前に立つ、変わらない名前です。`Service` と Pod の結びつきはアドレスの一覧ではなく、`selector: app: passes` という条件、つまり「このラベルを持つすべての Pod」です。ラベルを持つ新しいコピーが現れれば、自動的に負荷分散の対象に入ります。

四つのオブジェクトのどれ一つとして、パスワードも鍵もトークンも含みません。それは偶然ではありません。Git に入ったものは永遠にそこに入ります。履歴は書き換えられますが、クローンできた人はみな古いコピーを持ち続けます。シークレットはここに置き場所がありません。それには別の仕組みと別のラボがあります。

</details>

GitHub に送ります。Git は手当たり次第に何でも覚えるのではなく、明示的に示されたものを覚えます。だからこそコマンドが三つあり、それぞれが自分の役目を果たします。

```bash
# add = 次の履歴の一項目に入るファイルに印をつける。
git add apps
# commit = 印のついたものを一つの項目として保存する。中身、著者、時刻、理由。
#   -m "..."  まさにその理由。履歴に永遠に残り、人が読みます。
# commit はまだあなたの bastion の上だけにあります。GitHub にはまだありません。
git commit -m "add passes service v1"
# push = 溜まった commit を GitHub へ送る。このコマンドまで、向こうでは何も変わりません。
git push
```

**見えるはず** のもの — ブラウザのリポジトリのページに、二つのファイルが入った `apps` フォルダ。一方でクラスターではまだ何も変わっていません。Git はクラスターのことを何も知らないのです。

## ステップ 3. Flux を自分のクラスターにインストールする

📍 **どこで:** bastion 上(bastion のターミナルで)。

Flux はあなたのクラスター内のいくつかのサービスです。一つは Git に手を伸ばして中身をダウンロードし、もう一つはダウンロードしたものをクラスターに適用してずれを見張ります。

クラスターはあなたのもので、あなたはその完全な管理者です。自分でインストールします。プラットフォームチームに頼む必要はありません。

まず `flux` コマンドラインツール。これはクラスターの中ではなくあなたの bastion に住みます。これを使ってサービスをインストールし、その後は状態を尋ねます。

macOS:

```bash
# Homebrew は Flux プロジェクトのリポジトリから formula を取り、実行ファイルを一つ置きます。
brew install fluxcd/tap/flux
```

Linux:

```bash
# Flux サイトのスクリプトはアーキテクチャを判別し、ファイルを /usr/local/bin に置きます。
#   -s          curl はダウンロード表示なしで静かに動く
#   | sudo bash ダウンロードしたテキストを管理者権限でそのまま実行する。システムフォルダへの
#               書き込みのために必要
curl -s https://fluxcd.io/install.sh | sudo bash
```

Windows(PowerShell、Chocolatey が入っている場合):

```powershell
# choco — Windows 向けのサードパーティ製パッケージマネージャー。同じ単一の flux.exe を入れます。
choco install flux
```

さて、サービス本体をクラスターにインストールします。

```bash
# アクセスファイルを設定します。下のコマンドはクラスターにオブジェクトを作るので、どのクラスターか
# が重要です。
export KUBECONFIG=~/lab.kubeconfig
# flux install はクラスターに `flux-system` namespace を用意し、そこにサービスをデプロイします。
#   --components=...  具体的にどれをインストールするか:
#     source-controller     Git に手を伸ばし、リポジトリの新鮮なコピーを保つ
#     kustomize-controller  ダウンロードしたものをクラスターに適用し、ずれを見張る
flux install --components=source-controller,kustomize-controller
```

⚠️ **Enter を押す前に `KUBECONFIG` がどこを指しているか確認してください。** Flux をインストールするのはあなた自身の `lab` クラスターであって、それが手渡された元のクラスターではありません。迷ったら — `kubectl get nodes` で、`kubernetes-lab-md0-...` のような名前のノードが一つ表示されるはずです。

**見えるはず** のもの — 何が作られているかのリストと、最後に成功したインストールについての一行。

```
✔ install finished
```

四つのサービスのうち二つだけをインストールします。Flux のフルセットは Helm チャートのデプロイやメッセンジャーへの通知送信もできますが、今日それは必要なく、こちらにはメモリの少ないノードが一つあるだけです。

サービスが立ち上がったことを確認します。

```bash
# -n flux-system — Flux が落ち着いた namespace。このフラグがないと kubectl は default namespace を
# 見て何も表示しません。
kubectl get pods -n flux-system
```

**見えるはず** のもの — `Running` 状態の二行。

<details>
<summary><b><code>flux</code> CLI のインストールがうまくいかなかった場合</b></summary>

まったく同じものが、ツールなしで、普通のマニフェストでインストールできます。

```bash
# 同じサービス一式を、ただし出来合いの記述として。-f はディスク上のパスだけでなくリンクも受け付けます。
# kubectl はファイルをダウンロードして中身を適用します。
kubectl apply -f https://github.com/fluxcd/flux2/releases/latest/download/install.yaml
```

違いは、こうすると二つではなく四つのサービスがすべて立ち上がることです。それはメモリに響きますが、ラボ自体は通ります。この先、`flux ...` のコマンドは状態を見るためだけに必要で、`kubectl get gitrepository` と `kubectl get kustomization` で置き換えられます。同じものを、ただ少し不格好に見せるだけです。

</details>

## ステップ 4. Flux をリポジトリに向ける

📍 **どこで:** bastion 上(bastion のターミナルで)。

Flux はインストールされましたが、まだどこへ行けばよいか知りません。二つのオブジェクトで教えてやります。

このラボのフォルダから `flux/gitrepository.yaml` を開き、`REPLACE-ME` の仮置きの代わりに **あなたの** リポジトリのアドレスを入れます。

```yaml
  url: https://github.com/REPLACE-ME/passes-gitops
```

<details>
<summary><b>もっと詳しく: gitrepository.yaml と kustomization.yaml の中身</b></summary>

### `GitRepository` — どこから取るか

```yaml
kind: GitRepository
spec:
  interval: 1m
  url: https://github.com/REPLACE-ME/passes-gitops
  ref:
    branch: main
```

このオブジェクトの唯一の役目は、リポジトリの新鮮なコピーを保つことです。クラスターには何も適用せず、ダウンロードするだけです。

`interval: 1m` — どのくらいの頻度で更新を取りに行くか。一分はラボ向けの選択で、待たなくて済むようにしてあります。本番では通常一分から五分の間に設定し、push への即時反応はインターバルを縮めるのではなく webhook で行います。何かが変わると GitHub の側からクラスターをノックするのです。

`ref: branch: main` — どのブランチを真実の源として扱うか。`main` にマージされたものはすべてクラスターへ渡っていきます。他のブランチにあるものは渡りません。レビューはここから生まれます。変更はまず自分専用のブランチに住み、そこで見てもらえて、`main` にマージして初めて効き始めます。

### `Kustomization` — 何を適用するか

```yaml
kind: Kustomization
spec:
  interval: 1m
  path: ./apps
  prune: true
  sourceRef:
    kind: GitRepository
    name: passes
  wait: true
```

`path: ./apps` — リポジトリ内部のフォルダ。この中にあるものはすべてクラスターへ渡ります。その隣にあるファイル — たとえばルートの `README.md` — には手をつけません。

`interval: 1m` はここでは `GitRepository` のときと同じ意味ではありません。あちらでは「どのくらいの頻度でダウンロードするか」でした。ここでは **クラスターの実際の状態を記述された状態と、どのくらいの頻度で突き合わせるか** です。Git で何も変わっていなくても、一分に一度 Flux はクラスターが記述に合っているかを確かめ、合わせます。まさにこれに、このラボの少し先で引っかかります。

`prune: true` — Git から消えたオブジェクトをクラスターから削除する。これがないと Git は完全な記述ではなくなります。リポジトリからファイルを消しても、オブジェクトはクラスターで動き続け、半年後に誰もそれがどこから来たのか分かりません。`prune` があれば、記述と現実は双方向で一致します。

`wait: true` — 適用した直後に成功を報告するのではなく、適用したものがレディになるまで待つ。違いは「申請を出した」と「申請が済んだ」の違いとまったく同じです。

</details>

両方を適用します。

```bash
# -f はファイルではなくフォルダを指します。その中のすべてのマニフェストが適用されます —
# GitRepository も Kustomization も。どちらも flux-system namespace に作られます。
kubectl apply -f flux/
```

どうなったか見てみましょう。

```bash
# Flux にリコンサイルの状態を尋ねます。
#   --watch  ウィンドウを占有し続け、変化に応じて行を更新する
# READY: True はリポジトリの中身がクラスターに届き、適用されたことを意味します。
# REVISION — ブランチと、いま適用されている commit の短い識別子。
flux get kustomizations --watch
```

**見えるはず** のもの — 数十秒後に `Ready: True` の状態と、適用されている commit のハッシュ。

```
NAME     REVISION            SUSPENDED  READY  MESSAGE
passes   main@sha1:a1b2c3d   False      True   Applied revision: main@sha1:a1b2c3d
```

`Ctrl+C` で watch を止め、クラスターに何が現れたか見ます。

```bash
# all — Pod、Deployment、Service など主要なオブジェクト種別をまとめて指す略記です。
# `passes` namespace はあなたが手で作ったのではありません。アプリケーションと一緒にリポジトリから届いたのです。
kubectl get all -n passes
```

**あなたは手作業で何も適用していません。** テキストを GitHub に入れただけで、クラスターが自力で取り込みました。これと `kubectl apply -f` の違いは便利さではありません。いまや、どうあるべきかが書かれた唯一の場所がある、ということです。

## ステップ 5. `git push` による最初の変更

📍 **どこで:** bastion 上、リポジトリのフォルダで。

「Passes」サービスにコピーが一つでは足りません。警備は一覧を四六時中見ており、アプリケーションの更新で受付を止めるわけにはいきません。二つにしましょう。

以前なら `kubectl scale` を実行したでしょう。いまは — ファイルの編集です。

`apps/passes.yaml` を開き、こう変えます。

```yaml
spec:
  replicas: 2
```

送り出します。

```bash
# 最初の送信と同じ三ステップ: ファイルに印をつけ、理由とともに保存し、送る。
git add apps/passes.yaml
git commit -m "passes: two replicas so the gate does not go dark during rollout"
git push
```

さあクラスターを見て待ちます。

```bash
# -w = 「見張って追記し続ける」: ウィンドウは占有され続け、コピーの状態が変わるたびに新しい行が
# 現れます。Ctrl+C で抜けます。
kubectl get pods -n passes -w
```

**見えるはず** のもの — 一分以内に二つ目のコピーが現れます。あなたはそれを作っていません。

一分待ちたくなければ、Flux に今すぐリコンサイルするよう頼めます。

```bash
# reconcile = 「次の一分を待たず、今すぐリコンサイルする」。
#   kustomization passes  どのオブジェクトをリコンサイルするか
#   --with-source         まず Git へ新鮮な commit を取りに行き、それから適用する。
#                         このフラグがないと、以前ダウンロードしたコピーを元にリコンサイルする
flux reconcile kustomization passes --with-source
```

commit のメッセージに注目してください。`two replicas so the gate does not go dark during rollout` — これが理由です。半年後に誰かが「なぜここは一つでなく二つなのか」と尋ねたとき、答えは五秒で見つかります。

```bash
# log = commit の履歴。新しいものが上。
#   --oneline         commit ごとに一行: 短い識別子と理由のテキスト
#   apps/passes.yaml  このファイルに触れた commit だけを表示する
git log --oneline apps/passes.yaml
```

ダッシュボードも `kubectl` も、こんな痕跡を残しません。

## ステップ 6. すべてが管理下にあることを確かめる

📍 **どこで:** bastion 上(bastion のターミナルで)。

夜、インシデント、サービスはコピーが足りない。あなたはいつもどおりのことをします。

```bash
# コピー数を Git を迂回してクラスターの中で直接変える — 今日までそうしていたように。
#   -n passes  アプリケーションはこの namespace に住む。フラグがないとコマンドは見つけられない
kubectl scale deployment passes -n passes --replicas=5
```

```
deployment.apps/passes scaled
```

うまくいきました。確認しましょう。

```bash
# READY 列は「レディ/注文数」と読みます: 何個のコピーが応答し、何個あるべきか。
kubectl get deployment passes -n passes
```

コピーは五つ。一分待ってもう一度見ます。

```bash
# 同じコマンド。違うのは、二回の実行の間に一分が経ったことだけ。
kubectl get deployment passes -n passes
```

**見えるもの:**

```
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
passes   2/2     2            2           8m
```

またコピーは二つ。あなたのコマンドは実行され、そして取り消されました。

> **読み進める前に、立ち止まって考えてください。**
>
> 誰が取り消したのか。なぜあなたのコマンドに対してエラー一つ返さず、黙って起きたのか。
> そして何より、これは直すべき故障なのか、それとも意図どおりに働いているのか。

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

Flux が取り消しました。それこそが、これがインストールされた目的です。

一分に一度、`Kustomization` は Git にあるものを取り、クラスターにあるものと比べます。Git は `replicas: 2` と言っています。クラスターは `5` になっていました。ずれ — つまりクラスターの側が間違いです。クラスターは真実の源ではないからです。

**なぜ `kubectl scale` はエラーを返さなかったか。** 返せるはずがありません。それは頼まれたことを正直にそのとおり実行しました。Kubernetes は変更を受け入れ、コピーは実際に立ち上がりました。一分後にリコンサイルが来て、記述された状態を復元しました。誰も誰とも争っていません。異なる仕組みが、それぞれ自分のルールで働いただけです。

**なぜこれがバグではなく機能なのか。** ラボの冒頭の痛みに戻ってください。あなた方は三人で、誰かが手で何かを変え、どこに何が設定されているか誰も知らない。いま、それは起きません。Git の外で加えられた変更は次のリコンサイルまで生き — つまり生きません。ここから三つのことが導かれます。

1. **クラスターをこっそり誤設定することはできない。** 「良しとされない」ではなく、物理的に不可能です。
2. **Git は常に現実を記述している。** 「記述すべき」ではなく、実際に記述している。ずれは自ら取り除かれるからです。
3. **クラスターの復元が退屈な手順になる。** Flux をインストールし、リポジトリを与え、待つ。そこにあったものはすべて戻ってきます。全部が書き留められているからです。

**教訓はこのエラーより広いものです。** あなたはいま「適用して忘れる」と「絶えずリコンサイルする」の違いを見ました。普通の `kubectl apply` は一発の射撃です。状態が変わり、あとは独りでに生き、誰でもそれをつつけます。リコンサイルは射撃ではなく牽引です。記述が現実を絶えず自分の側へ引き寄せます。

ちなみにまったく同じ仕組みが、あなた以外の間違いも直します。ノードの障害が Pod を消したり、誰かがうっかり `Service` を消したりしても — それも戻ってきます。

**それが邪魔になるとき。** 邪魔になるのはインシデントのときです。本当に今すぐ何かを変えなければならず、話し合っている時間がない。そういう場合のために、Flux は一時停止できます。

```bash
# suspend = このオブジェクトのリコンサイルを一時停止する。Flux はクラスターを記述へ合わせるのを
# やめ、手作業の変更が生き始めます。その間、Git の中身は変わりません。
flux suspend kustomization passes
```

これ以降リコンサイルは走らず、手で何でもできます。元に戻すには:

```bash
# resume = リコンサイルを再びオンにする。次のリコンサイルが、手で行ったすべてを取り除きます。
flux resume kustomization passes
```

⚠️ 一時停止は先送りにした負債です。`Kustomization` が停止している間、Git はまた現実を記述しなくなり、あなたは出発点にちょうど戻ります。ルールは一つ — 停止したら、また戻すためのリマインダーを自分にセットすること。

</details>

## ステップ 7. `git revert` による切り戻し

📍 **どこで:** bastion 上(bastion のターミナルで)。

さて本物の状況です。変更を出したところ、それがまずいと分かる。

編集をします。たとえば誰かが何も考えずにメモリを動かない値まで絞ったとしましょう。`apps/passes.yaml` でメモリ上限を変えます。

```yaml
          resources:
            requests:
              cpu: 20m
              memory: 4Mi
            limits:
              cpu: 300m
              memory: 4Mi
```

送ります。承知のうえでのまずい変更も、良い変更とまったく同じ道を通ります。いまは `push` とクラスターの間にチェックがありません — そしてそれがこのステップの狙いです。

```bash
# 同じ add、commit、push。commit の理由は正直に書きます。五分後、この変更を取り消さなければ
# ならなくなったとき、役に立ちます。
git add apps/passes.yaml
git commit -m "passes: trim memory limit"
git push
```

待って見張ります。

```bash
# リコンサイルが新しい記述を持ってくるまで、コピーを見張ります。
kubectl get pods -n passes -w
```

**見えるはず** のもの — 新しいコピーが立ち上がりません。`OOMKilled` 状態はメモリ上限を超えたためにプロセスが killされたことを意味し、`CrashLoopBackOff` はクラスターがすでにコピーを何度も続けて再起動し、いまや次の試行まで待ち時間をどんどん長くしていることを意味します。nginx は四メガバイトに収まらず、起動直後に死にます。

```bash
# 同じ一覧を、ただし watch なしの一枚のスナップショットとして。
kubectl get pods -n passes
```

```
NAME                      READY   STATUS             RESTARTS   AGE
passes-6c9d4f7b8-2xk4n    1/1     Running            0          12m
passes-7f8a1b2c3-qq7lp    0/1     CrashLoopBackOff   3          90s
```

古いコピーはまだ動いています — サービスは生きていますが、更新は行き詰まりました。切り戻しの時です。

**以前ならどう切り戻したか:**

```bash
# undo は Deployment を前のリビジョンへ — 編集前の設定へ戻します。
kubectl rollout undo deployment/passes -n passes
```

このコマンドは効きます。コピーは前のイメージと前の設定に戻り、二十秒ですべてが元どおりになります — Flux が Git とリコンサイルする瞬間までは。そして Git には相変わらず `memory: 4Mi` と書いてあります。一分以内に壊れた状態が戻ってきます。

**`rollout undo` をしてはいけません。真実の住む場所で切り戻す** — Git で:

```bash
# revert = 指定した commit の変更を打ち消す新しい commit を追加する。
#   HEAD       「現在のブランチの最後の commit」 — まさにあのまずい上限の commit
#   --no-edit  commit メッセージ用のエディタを開かない。ヘッダは Git が自分で書く
git revert --no-edit HEAD
# 打ち消しの commit が GitHub に送られるまで、Flux はそれを何も知りません。
git push
```

**見えるはず** のもの — `Revert "passes: trim memory limit"` というヘッダの新しい commit と、一分以内にクラスターで再び二つの動くコピー。

```bash
# コピーが再び立ち上がります: 動作するメモリ上限が戻りました。
kubectl get pods -n passes
# そしてここで、いまどの commit が適用されているか見られます — 打ち消しの commit と一致するはずです。
flux get kustomizations
```

<details>
<summary><b><code>git revert</code> と「元どおりに戻す」はどう違うか</b></summary>

`git revert` はまずい commit を消しません。まずい commit の変更を打ち消す **新しい** commit を追加します。すべてが履歴に残ります。何が壊れ、いつ気づかれ、何が切り戻されたか。

```bash
# -4 — 直近の四つの commit を表示する。一番上が一番新しい。
git log --oneline -4
```

```
9f3c1ab Revert "passes: trim memory limit"
5d2b8e0 passes: trim memory limit
c71a4f9 passes: two replicas so the gate does not go dark during rollout
0e5f2d3 add passes service v1
```

これを Git がない場合の見え方と比べてください。一か月後、「あれ、この地雷はもう踏んだんだっけ?」という問いに答えはありません。`kubectl rollout undo` は痕跡を残さず、`Deployment` のリビジョン履歴は最後の十件を保つだけで、オブジェクトとともに死にます。

ここには四行あり、そこから見て取れます。はい踏みました、これがいつ、これが誰、これが正確に何をしたか、これが切り戻すまでどれだけ生きていたか。

**もう一つ `git reset` というコマンドがあり、これは本当に履歴を消します。** 共有リポジトリでは使いません。自分のマシンで消した commit も、同僚二人のマシンにはまだあり、彼らの次の `push` がそれを連れ戻します。共有ブランチでの取り消しは常に `revert` です。

</details>

## ステップ 8. pull request によるレビュー

📍 **どこで:** ブラウザ、GitHub 上。

私たちが治している痛みの最後の部分です。変更がクラスターへ即座に渡り、誰もそれを見なかった。前のステップのまずいメモリ上限は、レビューなら十秒で落とされたでしょう — しかしレビューがありませんでした。

変更のためのブランチを立てます。

```bash
# checkout -b = 新しいブランチを立て、すぐそれに切り替える。ブランチは変更の別の一本の流れ:
# そこで行われた commit は `main` に届かず、したがってクラスターにも届きません。
#   passes/version-line  ブランチ名。名前のスラッシュは許され、グループ分けの役に立つ
git checkout -b passes/version-line
```

`apps/passes.yaml` で、ページの行 — たとえばテキスト中のバージョン — を `v1` から `v1.1` に変えます。ブランチを送ります。

```bash
git add apps/passes.yaml
git commit -m "passes: bump the version shown on the page"
# origin — リポジトリをクローンした元のアドレスを Git が覚えている名前。
#   -u origin passes/version-line  GitHub に同名のブランチを作り、それとの結びつきを覚えて、
#                                  以降は素の `git push` で足りるようにする
git push -u origin passes/version-line
```

応答として GitHub は pull request を作るためのリンクを表示します。それを開きます。

**「Files changed」タブを見てください。** これがインフラのレビューです。「Pete が上限を直したと言っている」ではなく、具体的な行 — 前と後 — がハイライトされています。あなたの同僚はクラスターへ渡っていくものをそのまま見て、特定の行にコメントを残せます。

その間クラスターは変わっておらず、変わりません。`GitRepository` は `main` ブランチを見ており、変更は別のブランチに住んでいます。

**Merge pull request** をクリックすると — 変更は `main` に着地し、次のリコンサイルがそれをクラスターへ持っていきます。一分後、トンネルを開いてサービスが何を配信するか見ます。

```bash
# port-forward = bastion からクラスターへの一時的なトンネル。
#   -n passes     サービスが住む namespace
#   svc/passes    どこへ導くか: 特定のコピーではなく Service へ
#   8080:80       左が bastion のポート、右がクラスター内部のサービスのポート
kubectl port-forward -n passes svc/passes 8080:80
```

📍 **ブラウザで** <http://localhost:8080> — ページは `v1.1` と表示します。`Ctrl+C` でトンネルを閉じます。

いまや変更の全経路はこうです。**ブランチ → pull request → レビュー → マージ → クラスター**。どのステップでも、誰も手作業でクラスターに入りませんでした。

<details>
<summary><b>このうち、本番で行うのに私たちがやらなかったこと</b></summary>

実務のリポジトリが上乗せする三つのこと。

**ブランチ保護。** GitHub の設定で `main` ブランチは直接 push を閉じられ、入る唯一の道は承認つきの pull request です。さもないと規律は善意に頼ることになり、善意は午前三時に崩れます。

**マージ前のチェック。** 自動化がマニフェストを、クラスターへ渡る前に、構文とポリシー適合の観点でチェックし、壊れたものをマージさせません。

**複数の環境。** 通常リポジトリはフォルダ一つではなく `apps/staging` と `apps/production` を持ち、それぞれが自分のクラスターに自分の `Kustomization` を持ちます。変更はまず staging へ渡り、落ち着いてから production へ。

これをやらなかったのは、どれもそれぞれ別に一時間かかり、これらがあってもメカニクスは変わらないからです。真実の源は相変わらず Git で、Flux は相変わらずクラスターをそこへ引き寄せます。

</details>

## 検証

📍 **どこで:** bastion 上、`kubectl` で作業したのと同じターミナルウィンドウで。

```bash
# ラボのフォルダに戻ります: スクリプトはそこにあり、あなたは自分のリポジトリのフォルダで作業していました。
cd labs/05-gitops
export KUBECONFIG=~/lab.kubeconfig
# スクリプトはクラスターの何も変えません: 状態を読んでレポートを表示するだけです。
./check.sh
```

⚠️ **Windows ではスクリプトは WSL から実行します**。PowerShell からではありません — インストール方法はラボ 0 の冒頭に書いてあります。WSL がなくてもラボはこなせますが、レポートの成果物は残りません。

スクリプトがチェックするのは Flux がインストールされているという事実ではなく、仕組みが働いていることです。Flux のサービスが生きていること、ソースがあなたのリポジトリを指してそこから正常に読んでいること、クラスター内のオブジェクトが本当に Flux のもの(手作業で適用されたのではなく)であること、サービスが HTTP で応答すること、そしてリコンサイルが一時停止されていないこと。

スクリプトにあなたのリポジトリの履歴も見てほしければ — クローンがどこにあるかを教えます。

```bash
# LAB_REPO — スクリプトがあなたのリポジトリのクローンの場所を知るための変数。
# ホームフォルダ以外にクローンしたなら、自分のパスを入れてください。
export LAB_REPO=~/passes-gitops
./check.sh
```

すると、クラスターで適用された commit があなたのブランチの最新のものと一致すること、そして切り戻しが `revert` で行われたことも、追加で検証します。

## 後片付け

私たちは何も削除しません。リポジトリと Flux はあとで必要になります — 次のサービスも同じ道でクラスターに届きます。

すべてのラボを終えたら、一度にまとめてこう取り除けます。

```bash
# delete kustomization = リコンサイルのオブジェクトをクラスターから取り除く。
#   --silent  もう一度確認を尋ねない
flux delete kustomization passes --silent
```

`prune: true` のおかげで、`Kustomization` が持ってきたものはすべて、それと一緒に去ります。アプリケーション、設定、そして `passes` namespace 自体も。手作業で列挙する必要はなく、誰も残り物を忘れません。Flux が何を作ったかのリストを自分のために保っているからです。

これはちなみに、すぐには気づかれない GitOps の別の利点です。サービスを完全に削除するのは、フォルダの `git rm` と `push` です。

## いま私たちにできること

- クラスターの状態を Git に保ち、それが `kubectl apply` とどう違うか理解する
- Flux を自分のクラスターにインストールし、リポジトリに向ける
- リコンサイルとは何か、そしてなぜ Git の外で加えた変更が生き残らないかを説明する
- `kubectl rollout undo` ではなく `git revert` で切り戻す
- インフラの変更を pull request とレビューを通して進める

## これが vSphere ならば

最も近いのは vRealize Automation のブループリントです。望ましい構成が別に記述され、その記述からデプロイされます。しかしそこから先、道は分かれます。ブループリントはデプロイして手を離します。その後誰かが vCenter に入ってマシンのメモリを変えても、ブループリントはそれを知りません。コンプライアンスツールはずれをレポートに表示します — そしてそれだけ、人が解消しに行きます。

ここではずれが自ら解消します。毎分、レポートもなく、人もなく。

二つ目の違いは履歴についてです。vCenter にはタスクログがあります。誰が何をいつ、と。それは「何が起きたか」には答えますが、「なぜ」と「どうあるべきか」には答えません。Git には両方があります。変更のテキスト、著者、commit メッセージの中の理由、そして pull request の中の議論。

**正直に言って vSphere のほうが便利なところ。** 三つあります。

**参入の障壁。** vCenter で仮想マシンのメモリを変えるには、vCenter の使い方を知る必要があります。ここで変えるには、Git の使い方 — ブランチ、commit、マージ、コンフリクト — を知る必要があります。Git を知らない人にとって、これは「より便利」ではなく新しい職能であり、最初の二週間はこれまでより仕事が遅くなります。

**反応の速さ。** 緊急時には、ブランチとレビューと一分のリコンサイルを通してではなく、今すぐ状態を変えたいものです。一時停止の仕組みはありますが、使うのを覚えておき、戻すのを覚えておかねばなりません。

**失敗の明快さ。** vCenter で何かがデプロイされないとき、エラーつきのタスクが示されます。ここでデプロイされないときは、`GitRepository` の状態、次に `Kustomization`、次にイベント、次に二つのサービスのログを見なければなりません。診断がレイヤーにまたがっていて、慣れるまでは正直これが不便です。
