# ラボ14 · オブザーバビリティ: グラフの中から自分の作った急増を見つける

| | |
|---|---|
| **所要時間** | 30分 |
| **何を証明するか** | メトリクスは継続的に、しかも後追いで、自動的に集まります。監視システムを別途購入する必要はありません |
| **必要なもの** | ラボ0で作ったクラスター、ラボ1のアプリ、完了済みのラボ3（負荷とHPA）、テナントのダッシュボードへのアクセス |

## なぜこれが大切か

昨日の16:40、「Propusk」は15分ほど応答が遅くなりました。苦情が届いたのは今日の11:00、
いつものことです。経営陣からの質問はこうです。あれは何だったのか、そしてまた起きるのか。

「では今その状況を再現して見てみよう」というやり方は通用しません。昨日の誰かの負荷を
今から再現することはできないのです。答える唯一の方法は、誰かが尋ねてくる前に取られていた
**昨日の記録**を持っていることです。

このラボでは、ラボ3で自分がかけた負荷の痕跡をグラフの中から見つけます。トラフィックが
始まったときのCPUの急増と、オートスケーリングがコピーを増やしたときの段差です。そのために
特別な準備は何もしていません。記録はすでにそこにあります。

## ミニ用語集

| 用語 | それは何か | 似ているのは… ただし |
|---|---|---|
| **メトリクス** | 定期的に取られる数値: CPUがどれだけ、メモリがどれだけ、リクエストが何件 | **vCenterのグラフのカウンター**。ただし最後の値ではなく履歴として保存される |
| **ラベル（label）** | メトリクスに付く「名前=値」のペア: pod、namespace、cluster | **カウンターが結び付いている対象**。ただしラベルは多数あり、そのどれでも切り分けたりグループ化したりできる |
| **時系列** | 1組のラベルを持つ1つのメトリクスの時間変化 | **vCenterの1つのグラフ**。ただしラベルの組み合わせごとに別々の系列になり、その数は数千に及ぶ |
| **スクレイプ（scrape）** | 収集: エージェントがN秒ごとにソースを問い合わせる | **vCenterのカウンター収集**。ただしアプリがプッシュするのではなく、エージェントがデータを引き取る |
| **PromQL** | メトリクスへのクエリ言語 | 直接の対応物はない: vCenterではカウンターを選ぶが、ここでは式を書く |
| **VictoriaMetrics** | 収集したメトリクスを溜めておくストア | **vCenterの統計データベース**。ただしPrometheusのクエリ言語を理解する。Prometheus本体ではないのに |
| **Grafana** | メトリクスとログへのインターフェース | **Performanceタブ**。ただし別製品で、ダッシュボードは手で書くか出来合いのものを使う |
| **保持期間（retention）** | 履歴をどれだけ保つか | **vCenterの統計レベル**。ただしパラメータで指定する。デフォルトでは3日と14日、2つの別々のストアに分かれる |
| **ログ** | アプリが書き出す行 | **ゲストOSのログ**。ただし中央で集められ、独自のクエリ言語を持ち、PromQLではない |
| **Pod** | 実行の最小単位: 1つまたは複数のコンテナ、常に単一のノード上にある | **仮想マシン**。ただし使い捨て: 再起動する代わりに、新しい名前で作り直される |
| **Namespace** | クラスター内部の仕切り: 別々のnamespaceにある同じ名前どうしは衝突しない | **vCenterインベントリのフォルダ**。ただし権限、クォータ、ネットワークポリシーまで区切る |
| **テナント** | プラットフォームのうちあなたの取り分: Grafanaはそこにあり、クラスターのメトリクスもそこへ流れ込む | **独自の権限を持つResource Pool**。ただしリソースだけでなく出来合いのサービスまで払い出す |

### メトリクスとログ ── なぜ別物なのか

この2つは絶えず一緒くたにされ、そのせいでメトリクスにしか存在しないものをログの中に探す羽目になります。

| | メトリクス | ログ |
|---|---|---|
| それは何か | 一定間隔ごとの数値 | イベントが起きた瞬間の行 |
| 例 | 「16:41:30にPodは240ミリコアを使った」 | 「16:41:31 ERROR connection refused」 |
| 容量はどれだけ | 少ない、しかも量が予測できる | 多い、しかも量はアプリのおしゃべりさに左右される |
| どれだけ保つか | 数週間から数か月 | 数日 |
| 答えられる問い | 「どれだけ、いつ」 | 「正確に何が起きたか」 |
| クエリ言語 | PromQL | LogsQL（Grafanaではこれは別のデータソース） |

この2つはペアで働きます。**メトリクスは瞬間を、ログは原因を見つけてくれます。** グラフが
16:41に急増を示したら、その分のログを見に行く。逆方向はうまくいきません。ログをたどって
「いつ調子が悪くなったか」を探すのは、いつまでかかるか分かりません。

### なぜメトリクスは要求時ではなく継続的に取られるのか

これが監視を診断から分ける肝心な点であり、はっきり言葉にしておく価値があります。

要求されてから集めるのは**物理的に**不可能です。問いが立った時点で、そのイベントはもう終わって
います。昨夜の負荷を昨夜のうちに誰も記録していなければ、どんなシステムもそれを見せてはくれません。

だからエージェントは、見境なく、30秒ごとにすべてを問い合わせ、ストレージに溜めます。そう、
これらの数値の99%は誰にも見られないでしょう。その99%の代価はディスク数ギガバイト。
欠けている1%の代価は「何が起きたのか分からず、これからも分からない」です。

⚠️ **あらかじめ知っておくべき裏面。** 継続的な収集は継続的なコストを意味します。エージェントは
CPUとメモリを消費し、ストレージは増え続けます。大きなクラスターではメトリクスが消費の中で
目立つ項目になり、間引かなければならなくなります。保持期間を短くし、不要なラベルを捨て、
ほとんど使われないメトリクスの収集を止める。これは日常的な運用作業で、最初の1か月には
現れませんが、いずれ現れます。

## ステップ1. そもそもメトリクスが集まっているかを確かめる

📍 **どこで:** bastion 上（bastion のターミナルで）。

`lab` クラスターは自力ではメトリクスを外に出さず、`Monitoring agents` アドオンを通じて出します。
これが有効かどうかを確認します。

```bash
# KUBECONFIG — クラスターのアドレスと、誰としてログインするかを kubectl が読み取る変数。
# ファイル ~/lab.kubeconfig は `lab` クラスターを作ったときに保存したものです。
# 新しいターミナルウィンドウごとに、改めて設定する必要があります。
export KUBECONFIG=~/lab.kubeconfig

# get pods = 「どんな pod があるか見せて」。
#   -n cozy-monitoring   クラスター全体ではなく、この namespace だけを見る: アドオンが
#                        収集器を置くのは、まさにここです。
kubectl get pods -n cozy-monitoring
```

**リストに `vmagent` と `fluent-bit` が見えれば** ── すべて揃っています、先へ進んでください。

⚠️ **リストが空かどうかではなく、名前を見てください。** `cozy-monitoring` namespace は
常に存在します。プラットフォームはそこに `metrics-server` も置きますが、これは独自の etcd を持つ
どのクラスターにもインストールされ、アドオンには依存しません。つまり `metrics-server` の行を
見て、メトリクス収集が有効だと結論づけるのは典型的な間違いで、それはすべてが空っぽの Grafana で
初めて露見します。

**リストに `metrics-server` はあるが、`vmagent` も `fluent-bit` もない場合:**

```
NAME                              READY   STATUS    RESTARTS   AGE
metrics-server-7d4b8c9f5-x2klm    1/1     Running   0          3d
```

これはアドオンが無効で、過去の記録が手元にないということです。ちなみにこれは前の節の
まさに正確な実例です。収集を後追いで有効にすることはできません。

有効にするのはダッシュボードで行います。`Kubernetes` → `lab` → 編集 → Addons のセクションで
`Monitoring agents` にチェックを入れます。アドオンは数分で立ち上がりますが、**メトリクスが
溜まり始めるのはその瞬間から**です ── ラボ3の急増はもう見つかりません。

ですから、急増を作り直さなければなりません。ラボ3の後片付けでオートスケーリングが、
ラボ4の後片付けで負荷生成器が消えていますので、両方を戻す必要があることに注意してください。

```bash
export KUBECONFIG=~/lab.kubeconfig          # 上と同じアクセスファイル

# apply = 「ファイルに書かれた状態にクラスターを合わせて」。どちらのファイルも隣の
# ラボのフォルダにあるので、パスは `../` で始まります ── 改めて打ち込む必要はありません。
kubectl apply -f ../03-scale/hpa.yaml       # rickroll 向けのオートスケーリング規則
kubectl apply -f ../03-scale/fortio.yaml    # 負荷生成器

# rollout status = 「ターミナルを掴んだまま、ロールアウトが終わったら教えて」。
# deployment/fortio — オブジェクトの種類とその名前。生成器が立ち上がると、コマンドは
# `successfully rolled out` の行とともにプロンプトを返します。
kubectl rollout status deployment/fortio
```

`kubectl get hpa rickroll` が `<unknown>` の代わりにパーセンテージを表示するまで待ってください。
`hpa` は `HorizontalPodAutoscaler`（オートスケーリングのオブジェクト）の略です。これには数分
かかります。それから生成器のポートをフォワードし、ラボ3と同じ負荷をかけてください。そうしないと
オートスケーリングの段差が現れません。

```bash
# port-forward = bastion からクラスター内部へトンネルを掘る。コマンドが動いている間、
# localhost:8081 へのリクエストは負荷生成器に届きます。
#   svc/fortio    ターゲット: fortio という名前のサービス（pod ではない）
#   8081:8080     左が bastion 側のポート、右がサービス内部のポート
# ウィンドウは閉じないこと: トンネルはコマンドが動いている間だけ生きています。
kubectl port-forward svc/fortio 8081:8080
```

<http://localhost:8081/fortio/> で: **URL** `http://rickroll/`、**QPS** `1200`、
**Duration** `90s`、**Connections** `80`。終了して数分後にここに戻ってください ── データが
そこにあります。

⚠️ この状況に陥らないために、`Monitoring agents` はクラスターを作るときにすぐ有効にしてください
── ラボ0ではパラメータ表の中の独立した1行になっています。

<details>
<summary><b>そこで正確に何が動いていて、集められたデータはどこへ行くのか</b></summary>

あなたのクラスターの `cozy-monitoring` namespace では、次のものが動いています。

| 誰が | 何をするか |
|---|---|
| `vmagent` | 30秒ごとにメトリクスのソースを問い合わせ、集めたものをテナントへ送る |
| `kube-state-metrics` | クラスターのオブジェクトの状態をメトリクスに変える: レプリカが何個か、Pod がどんな状態か |
| `node-exporter` | ノード自体のメトリクス: CPU、メモリ、ディスク、ネットワーク |
| `fluent-bit` | コンテナのログを集めてテナントへ送る |
| `metrics-server` | **監視の一部ではない**: クラスターと一緒にインストールされ、`kubectl top` とオートスケーリングのために現在の数値を供給する。何も保存せず、メトリクス収集には一切関与しない |

注意: **ここにはストレージがありません**。集められたものはすべて即座にネットワーク越しに
テナントへ、Grafana の隣にある共有のメトリクスストアへ送られます。これは意図的です。`lab`
クラスターは使い捨てのもので ── あなたはそれを削除しますが、それがどう振る舞ったかの記録は、
その削除を生き延びなければならないのです。

収集器がデータをどのアドレスへ送っているかを見るには:

```bash
# get vmagent = 「収集器オブジェクトを見せて」。いつものテーブルの代わりに、その記述から
# 1つのフィールドだけを求めます ── -o jsonpath の構文はどんなクラスターオブジェクトにも使えます:
#   .items[0]                  見つかった最初の（そしてここでは唯一の）収集器
#   .spec.remoteWrite[0].url   メトリクスを渡す先のアドレス
#   {"\n"}                     改行、そうしないと出力がプロンプトにくっついてしまう
kubectl get vmagent -n cozy-monitoring \
  -o jsonpath='{.items[0].spec.remoteWrite[0].url}{"\n"}'
```

```
http://vminsert-shortterm.tenant-workshopXX.svc.cozy.local:8480/insert/0/prometheus
```

アドレスはあなたのテナントを指しています。これはラボ12の仮想マシンがアプリと会話するのに
使ったのと同じ仕組みです。ふつうのアドレスどうしをつなぐ、ふつうのネットワークです。

</details>

## ステップ2. テナントの Grafana を開く

📍 **どこで:** ブラウザで。

アドレスはあなたのテナントホストの `grafana` サブドメインです。

```
https://grafana.<あなたのテナントホスト>
```

正確なアドレスはダッシュボードに記されています。あなたのテナント → `Monitoring` アプリ →
`Ingress` タブ。Ingress とは、サービスをドメイン名の下で外部に公開する規則です。最も近い
対応物はロードバランサー上のエントリで、ただしそれが同じクラスターの中で記述されているものです。
そこにはホスト名まで含めてアドレスが丸ごと載っています。

もう1つの場所は、この同じラボの `check.sh` の出力です。「Grafana for your metrics」の行です。
スクリプトはこの同じ ingress からアドレスを取り出すので、手で打ち込む必要はありません。

⚠️ **あなたのテナントに `Monitoring` アプリがない場合** ── 自分の Grafana もなく、メトリクスは
親テナントの監視へ流れます。確実な道は、カタログから `Monitoring` をデプロイすることです
（`Administration` セクション）。アドレスは今度こそあなた自身のアプリの `Ingress` タブに現れ、
以下のクエリはすべて動きます。`check.sh` は他人の監視も見つけ、それが動いている namespace の
名前を教えてくれますが、それを開けるのはその namespace へのアクセスがある場合だけです。

**何でログインするか。** ログインは `admin` です。パスワードは `grafana-admin-password` Secret に
あります。ダッシュボード → `Monitoring` アプリ → `Secrets` タブ → `password` キー → `Reveal`。

テナントとしては `kubectl` はこの Secret へのアクセスを与えません（core Secret はあなたには
見えません）ので、ダッシュボード経由で進んでください。

監視が親テナントのものである場合、この Secret には手が届きません ── そのときは上で述べたように
自分の `Monitoring` アプリをデプロイするか、テスト環境を運用している人にアクセスを求めてください。

入ったら **Explore** を開いてください ── これはダッシュボードを保存せずに単発のクエリを行う
セクションです。データソースのドロップダウンで **`vm-shortterm`** を選びます（デフォルトでも
これが選ばれています）。

⚠️ **クエリ欄を `Code` モードに切り替えてください。** Grafana は Explore をビルダー（`Builder`）で
開きます ── クエリのテキストを打ち込む場所がない、ドロップダウン付きのフォームです。
`Builder | Code` の切り替えは入力欄の上、右側にあります。以下のクエリはすべて `Code` で入力します。

<details>
<summary><b>リストにあるデータソースとは何か</b></summary>

| ソース | 中身 | 保持 |
|---|---|---|
| `vm-shortterm` | 高解像度のメトリクス | 3日 |
| `vm-longterm` | 同じメトリクスを間引いたもの | 14日 |
| `vlogs-generic` | コンテナのログ | 1日 |

メトリクスストアが1つではなく2つあるのは、解像度と容量の折り合いです。
インシデントの調査は `shortterm` で行い、そこでは30秒ごとに見えます。「2週間前にはどう
振る舞っていたか」という問いには `longterm` で答え、そこでは解像度は粗いものの、遡れる
深さは大きくなります。

vCenter の統計レベルとまったく同じ論理です。20秒間隔のデータは1日、時間単位のデータは1年
生きています。

⚠️ **`vlogs-generic` はログであり、そこでのクエリ言語は別物です。** PromQL はそこでは動きません。
これはバグではありません: ログには独自の文法があります。ソースを切り替えて同じクエリを
貼り付けても時間の無駄です。

</details>

⚠️ **テナントの Grafana には Pod 向けの出来合いのダッシュボードはありません。** リストには
データベース、ingress、キューのダッシュボードがあります ── これらはマネージドサービスに
属するものです。「Pod とノード」レベルのダッシュボードはテナントのセットには含まれません。
ですから以降は Explore で作業し、クエリを手で書きます。これは vCenter の出来合いの Performance
タブより不便で、そうでないふりをする意味はありません。

## ステップ3. 自分の Pod を見つける

📍 **どこで:** Grafana、Explore、`vm-shortterm` ソースで。

いちばん粗い問いから始めましょう。そもそもクラスターにはどんな Pod が見えているのか。
クエリは短いですが、見慣れない部分が3つあります ── 入力する前に解説を開いてください。

<details>
<summary><b>クエリを部分ごとに分解する</b></summary>

```promql
container_cpu_usage_seconds_total
```

メトリクスの名前です。これはカウンターで、コンテナが起動以来消費したCPU時間の秒数です。
コンテナが再起動するまで増える一方で、再起動後はゼロから始まります。

これ単体では役に立ちません。「Pod は4718秒のCPUを使った」は何も語りません。
このメトリクスが役立つようになるのは `rate()` を通した後で、それは次のステップで扱います。

```promql
{cluster="kubernetes-lab", namespace="default"}
```

ラベルによるフィルタです。ここでは両方のラベルが重要です。

`cluster` ── プラットフォームが把握しているあなたのクラスターの名前です。これは `lab` と
**等しくありません**: アプリの名前は `lab` ですが、それがデプロイされているリリースは
`kubernetes-lab` であり、ラベルに入るのはリリース名の方です。これは誰もがつまずく最初の
落とし穴です。あなたのが何という名前かを確認するには: 値を消して、Grafana のオートコンプリートが
何を提案するかを見てください。

このラベルが必要なのは、1つのストアにあなたの**すべての**クラスターとマネージドサービスの
メトリクスが入っているからです。フィルタがなければ、テナント全体が混ざったものが返ってきます。

`namespace` ── `lab` クラスター**内部の** namespace です。最初のラボのアプリは `default` に
デプロイされたので、ここも `default` です。テナントの namespace（`tenant-workshopXX`）と
混同しないでください ── これらは別々のクラスターにある別々のものです。テナントの namespace は
`tenant` ラベルにあります。

```promql
count by (pod) ( ... )
```

`pod` ラベルでグループ化し、各グループにいくつの系列が入ったかを数えます。私たちが
興味があるのは数値そのものではなく、結果として得られる `pod` の値のリストです。

</details>

```promql
# count by (pod) — マッチした系列を pod ラベルで分け、各グループに系列がいくつ
# あるかを数える。数値そのものは重要ではない: 欲しいのは、結果として出てくる pod 名のリスト。
count by (pod) (
  # メトリクスの名前 — コンテナ CPU 時間のカウンター
  container_cpu_usage_seconds_total{
    cluster="kubernetes-lab",   # あなたのクラスター: ここはリリース名、アプリ名 lab ではない
    namespace="default"         # rickroll がデプロイされている lab クラスター内部の namespace
  }
)
```

**何が見えるはずか:** 表示を Graph から **Table** に切り替えてください ── その方がリストが
読みやすくなります。表には `rickroll-...`、`fortio-...`、そしてラボ11をやっていれば
`propusk-build-...` が並びます。

## ステップ4. CPU の急増を見つける

前のステップのカウンターは生のままでは読めません。それを、Pod の request や `kubectl top` の
表示と比べられる量 ── 消費コア数に変えましょう。その過程で `rate()` が何をするのか、
そしてクエリに増えた2つの条件がどこから来るのかは、下の解説にあります。入力する前に開いてください。

<details>
<summary><b>クエリを部分ごとに分解する</b></summary>

```promql
rate( ... [2m])
```

`rate` はカウンターを取り、**その1秒あたりの増加速度**を、2分間の窓で平均して計算します。
CPU時間のメトリクスにとって、これはとても便利な量を与えます。「1秒あたり何秒のCPUか」、
つまり何コアが消費されていたか、です。`0.24` は1コアの24%、すなわちミリコアで `240m` を意味します。

窓 `[2m]` は折り合いです。窓が小さいと（`[30s]`）── グラフはガタつき、まばらなデータでは
途切れます。大きいと（`[5m]`）── 急増がならされ、低いピークは完全に消えることがあります。
`[2m]` から始めて、そこから調整してください。

⚠️ **窓は収集間隔の最低でも2倍でなければなりません。** 収集は30秒ごとに起きるので、`[1m]` より
小さくは設定できません ── 窓に入る点が1つだけになり、1つの点から速度は計算できず、グラフは
空になります。これは「何も描かれない」の最も多い原因です。

```promql
pod=~"rickroll-.*"
```

`=~` ── 完全一致ではなく正規表現による比較です。ここでは完全一致は使えません: Pod の名前には
ランダムな末尾が含まれ、作り直すたびに変わります。

```promql
container!=""
```

コンテナ名のない系列を捨てます。そういう系列は存在します: これは Pod 全体の集計であり、
捨てなければ各 Pod が二重に数えられ、グラフはちょうど2倍の値を示します。これもまた
古典的な罠です。

```promql
sum by (pod) ( ... )
```

残ったものすべてを Pod 単位で合計します。1つの Pod には複数のコンテナがあり得ますが、
私たちが興味があるのは Pod 全体です。

</details>

```promql
# rate(...[2m]) — カウンターの 1 秒あたりの増加速度、2 分間の窓で平均したもの。
# CPU 時間については「何コアが消費されていたか」と読める:
# 0.24 — 1 コアの 24 パーセント、つまり 240m。
sum by (pod) (     # pod のコンテナを合計: コンテナごとではなく pod ごとに 1 本の線
  rate(container_cpu_usage_seconds_total{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*",  # =~ 正規表現による比較: pod 名の末尾はランダム
    container!=""        # pod 全体の合計系列を捨てる、さもないとすべてが 2 倍になる
  }[2m])
)
```

時間範囲をラボ3をやっていたときに設定してください ── 例えば直近3時間です。

**何が見えるはずか:** ゼロのすぐそばの平らな線、それから負荷の間だけの鋭い立ち上がり、
それから下への戻り。レプリカが複数になっていた場合は線も複数になり、しかもそれらは
一度にではなく、Pod が作られるにつれて現れます。

## ステップ5. オートスケーリングの段差を見つける

急増は見つけました。今度は、それに対してクラスターがどう応えたかを見ましょう。各瞬間に
アプリのコピーをいくつ動かし続けていたか、そしていくつ動かし続けたかったか。これは2つの
異なる数値で、その差こそがこのステップで最も面白いものです。それらがどこから来るのかは
下の解説にあります。

<details>
<summary><b>これらのメトリクスはどこから来るのか、そして desired は current とどう違うのか</b></summary>

これらのメトリクスはアプリからではなく `kube-state-metrics` から来ます ── これは API を通じて
クラスターのオブジェクトを読み、そのフィールドを数値に変えます。`horizontalpodautoscaler`
ラベルは HPA オブジェクトの名前（`HorizontalPodAutoscaler`、ラボ3のあのオートスケーリング規則）、
`deployment` ラベルは Deployment の名前、つまり「アプリのコピーをこれだけ保て」という記述の
名前で、以下オブジェクトの種類ごとに同様です。

`desired` ── 負荷から計算した結果、オートスケーリングが今この瞬間に**望んでいる**コピー数。
`current` ── **実際に**動いている数です。この2つの間には常に隙間があります: Pod は瞬時には
作られません。

`desired` が `current` を長く上回り続けるなら、それはコピーが作られていないということです。
原因はほとんど常に同じ: ノードに空きが足りず、新しい Pod が `Pending` のままぶら下がっている
のです。ラボ11でぶつかったのとまったく同じ状況です。

隣に置くと役立つもの:

```promql
# rickroll のコピーが全部でいくつ作られたか
kube_deployment_status_replicas{cluster="kubernetes-lab", deployment="rickroll"}
# そのうちいくつが readiness チェックを通過し、すでにトラフィックを受けているか
kube_deployment_status_replicas_available{cluster="kubernetes-lab", deployment="rickroll"}
```

新バージョンのロールアウト中にこの2つが食い違うのは、まさに新しいコピーが readiness
チェックを通過するまでのあの一時停止です。

</details>

```promql
# ..._status_current_replicas — rickroll のコピーが今この瞬間にいくつ動いているか。
# 数値はアプリからではなく、kube-state-metrics が読んだ HPA オブジェクトから来る。
kube_horizontalpodautoscaler_status_current_replicas{
  cluster="kubernetes-lab",             # あなたの lab クラスターだけ
  horizontalpodautoscaler="rickroll"    # ラボ 3 のオートスケーリングオブジェクトの名前
}
```

そしてその隣に、2つ目のクエリとして:

```promql
# ..._status_desired_replicas — 負荷に基づいて、オートスケーリングが今いくつのコピーを
# 持ちたがっているか。current が desired に遅れているのが、まさに pod の作成時間。
kube_horizontalpodautoscaler_status_desired_replicas{
  cluster="kubernetes-lab",
  horizontalpodautoscaler="rickroll"
}
```

**何が見えるはずか:** 段状の線です。1だったのが、それから3、それから5か6、それから ──
負荷が引いた後、約1分の遅れで ── 下へ戻ります。

これを前のステップのCPU消費のグラフに重ねてください: Explore では2つ目のクエリを
`+ Add query` ボタンで追加します。段差が急増の**後ろ**を数十秒遅れて追っているのが見えます:
まずCPUが上がり、それからオートスケーリングがそれに気づいて反応した。これが「なぜユーザーは
結局のところ遅延に気づけてしまったのか」という問いへの答えです。

## ステップ6. 同じものをオートスケーリングの目で見る

オートスケーリングが見るのは絶対的な消費ではなく、**`requests` に対する割合**です。
`requests` とは Pod のリソース要求です: Pod がそのリソースを使うかどうかにかかわらず、
スケジューラがノード上でその Pod のために予約するCPUとメモリの量です。
最も近い対応物は vSphere の reservation です。

決定が下される、まさにその量を見てみましょう。クエリは割り算記号で分けられた2つの部分から
成ります: 上に実際の消費、下に要求です。

```promql
# 上の部分 — pod の実際の CPU 消費。上と同じクエリ。
sum by (pod) (
  rate(container_cpu_usage_seconds_total{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*", container!=""
  }[2m])
)
/
# 下の部分 — pod がどれだけ要求したか。割り算の結果は要求に対する割合: 1 は
# 「要求したのとちょうど同じだけ消費している」、0.5 は要求の半分を意味する。
sum by (pod) (
  kube_pod_container_resource_requests{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*",
    resource="cpu"     # このメトリクスにはメモリの系列もある — CPU だけを残す
  }
)
```

**何が見えるはずか:** ほとんどの間ずっと低いところを走り、負荷の間だけ上がる線です。
このグラフの1という値は「Pod は要求したのとちょうど同じだけ消費している」を意味します。

ラボ3の `hpa.yaml` には `averageUtilization: 50` があり、`rickroll.yaml` には
`requests.cpu: 20m` があります。つまり発動のしきい値はPodあたり10ミリコアで、グラフ上では
それが `0.5` の目盛りです。線がそれを越えた瞬間を見つけ、前のステップの段差と照らし合わせて
ください: その間にはあの数十秒があります。

⚠️ PromQL で2つの式を割ると、**すべての**ラベルの一致で対応づけられます。ここではそれが
噛み合います。両方の部分が `by (pod)` でグループ化されていて、グループ化の後には他のラベルが
残らないからです。もしラベルの集合が違っていたら、結果は空になっていたでしょう ── エラーも
警告もなく、空のグラフです。これはこの言語の最も厄介な特徴です。

## ステップ7. 毎日使う3つのクエリ

これらは保存しておく価値があります ── 日々の問いの大半をカバーします。

**クラスターで最もCPUを消費しているのは誰か、トップ10:**

```promql
# topk(10, ...) — 値が最も大きい 10 系列だけを残す。
# by (namespace, pod) でグループ化すると答えに namespace が加わる: 誰の pod か分かる。
# 窓 [5m] は前のステップより広い: 欲しいのは急増の形ではなく、平均的な水準だから。
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{cluster="kubernetes-lab", container!=""}[5m])
  )
)
```

**Pod ごとのメモリ（カウンターではないので `rate` なし）:**

```promql
# container_memory_working_set_bytes — カウンターではなく瞬時値: この瞬間にこれだけの
# バイトが占有されている。ここで rate() を使えばナンセンス — 「1 秒あたりのバイト」— になる。
sum by (pod) (
  container_memory_working_set_bytes{
    cluster="kubernetes-lab", namespace="default", container!=""
  }
)
```

⚠️ 使うのはあくまで `working_set` であり、`container_memory_usage_bytes` ではありません。後者は
ファイルキャッシュを含み、それは負荷がかかればカーネルが手放すものなので、アプリの実際の
必要とは何の関係もない数字で人をたびたび怖がらせます。メモリのために Pod を kill する判断も
`working_set` に基づいて下されます。

**どれだけリソースが予約されているか対どれだけ実際に使われているか:**

```promql
# sum by なし — すべてを 1 つの数値に合計する: クラスターの全 pod のためにどれだけの CPU が
# 予約されているか。これは消費ではなく request: 予約されて遊んでいる分も合計に入る。
sum(kube_pod_container_resource_requests{cluster="kubernetes-lab", resource="cpu"})
```

この数値を最初のクエリの合計と比べてください。「予約されている」と「使われている」の差が、
あなたが対価を払って何も得ていない分です。vSphere の reservation についてと同じ話ですが、
ここではそれをグラフで見られます。

ラボ11をやっていれば、ついでに Android のビルドを見てみてください ── はっきり見えます。

```promql
# 同じ rate だが、ビルドの pod でフィルタ。sum without by (pod) — ビルドがいくつの pod を
# 立ち上げようと、ビルド全体で 1 本の線。
sum(rate(container_cpu_usage_seconds_total{
  cluster="kubernetes-lab", pod=~"propusk-build-.*", container!=""
}[2m]))
```

1コア半から2コアの平らな台地が20分間、それからゼロへの急落。Job はグラフ上でこう見えます
── 仕事を最後までやり遂げて終わる、1回限りのタスクです。ずっと動かし続けられるアプリと違い、
その線には終わりがあります。

## ステップ8. ログを覗いてみる

データソースを **`vlogs-generic`** に切り替えます。ここでのクエリ言語は別物です: PromQL では
数値の系列を記述しましたが、LogsQL ではフィールドの値によって行を選び出します。

下のクエリはこう読めます: 「`kubernetes_namespace_name` フィールドが `default` に等しく、かつ
`kubernetes_pod_name` フィールドが `rickroll` で始まる行を見せて」。
末尾のアスタリスクは、PromQL で `=~` を書かせたのと同じ、Pod 名のランダムな末尾です。

```logsql
kubernetes_namespace_name:default AND kubernetes_pod_name:rickroll*
```

時刻を合わせてください: CPU消費のグラフで見つけた急増の分を取り、その分のログを見ます。
その分、nginx にはリクエストの記録の急増があります。

**メトリクスとログを分けたのは、まさにこのためです。** グラフを使えば、3時間の中から瞬間を
1秒で見つけられました。その分のログを使えば、正確に何が起きていたかが分かります。逆方向は
うまくいきません: ログをスクロールして「いつ調子が悪くなったか」を探すのは、非常に長く
かかることがあります。

## これが vSphere ならこうなる

vCenter はホストと仮想マシンのカウンターを表示します ── 問いが仮想マシンについてである限り、
それで十分です。問いが「サービスに何が起きたのか」になった途端、vRealize Operations が必要に
なります: 別製品、別ライセンス、別のインストール、それを動かすための別の仮想マシン、そして
それを設定できる別の人。

ここではメトリクスとログの収集は、アプリのチェックボックスで有効にするアドオンであり、Grafana
はストレージごとカタログの一項目として立ち上がります。ライセンスも、導入プロジェクトもありません。

**正直に言って、vSphere の方が便利なところ。** インストール直後に動くものに関しては、vCenter が
文句なしに勝ち、それをこのラボの中でまさに見ました。

| | vSphere | Cozystack |
|---|---|---|
| インストール直後のグラフ | どのオブジェクトにも Performance タブ | アドオンを有効にして Grafana を開く必要がある |
| 出来合いのビュー | どんな VM やホストにもある | テナントでは ── マネージドサービスについてだけ |
| 必要なカウンターを探す | マウスでリストから選ぶ | PromQL でクエリを書く |
| 参入の敷居 | 1時間 | 数日、PromQL を学ばなければならない |
| 使いこなしたときの深さ | カウンターの集合に制限される | どのメトリクスとラベルが集められているかに制限される |

PromQL は言語であり、それは本当に学ばなければなりません。最初の2週間は、あなたは他人の
クエリをコピーしては、なぜグラフが空なのか分からずにいるでしょう。その代わりに得られるのは、
vCenter にはまったくないものです: 任意の問い ── 「このアプリの Pod の消費を、その予約に対する
割合で、ノードごとにグループ化して、先週の火曜日について見せて」── を尋ねて、「そんな
カウンターはない」ではなく答えを得られる能力です。
