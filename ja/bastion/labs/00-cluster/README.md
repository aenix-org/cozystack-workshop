# ラボ 0 · 自分専用の Kubernetes クラスター

| | |
|---|---|
| **所要時間** | 15分、うち10分は待ち時間 |
| **これで分かること** | クラスターはカタログの一項目であって、四半期がかりのプロジェクトではないということ |
| **必要なもの** | テナントのダッシュボードへのアクセス。bastion 上の `kubectl`（インストール済み） |

## なぜこれが大事なのか

このあと、あなたはアプリケーションをデプロイし、壊し、直し、スケールさせていきます。そのすべてには、あなたが完全なオーナーであり、失敗しても何のコストもかからない場所が必要です。

vSphere なら、そうした場所は誰かがあなたに割り当ててくれます。ここでは、あなた自身が10分で手に入れ、終わったら同じくらい簡単に自分で削除します。

## ミニ用語集

このあとのすべてのラボに出てくる7つの言葉です。3列目には、その用語が似ている vSphere のものを挙げ、そのうえで、どこが違うのかをすぐに示しています。ここでのアナロジーは理解を助けますが、完全に一致するものは一つもありません。そして、アナロジーそのものよりも、それがどこで崩れるのかを正確に知っておくことのほうが大切です。

| 用語 | 何なのか | 似ているが… |
|---|---|---|
| **Kubernetes クラスター** | 複数のマシンと、その上にアプリケーションを配分する管理プログラムの組み合わせです。あなたはアプリケーションを渡すだけで、どのマシンで動かすかは指示しません。それはクラスターが自分で決めます | **ESXi クラスター**に似ていますが、DRS は仮想マシンを配置したうえで、ホスト間を移動させながら継続的にリバランスします。ここでの単位はコンテナで、その配置は起動時に一度だけ、加えてノードが故障したときに再度選ばれます。すでに動いているものをクラスターが自分から並べ替えることはありません |
| **コントロールプレーン** | クラスターの管理層です。あなたのコマンドを受け取り、望ましい状態を保存し、ノードに仕事を割り振ります | **vCenter**に似ていますが、Web UI を持つ独立したサーバーではなく、いくつかのプロセスの集まりです。Cozystack ではそれらはプラットフォーム側に存在し、あなたのノード上にはありません |
| **ノード** | あなたのアプリケーションが最終的に動くマシンです | **ESXi ホスト**に似ていますが、ここではハードウェアではなく VM であり、数分で作成されます |
| **ノードグループ** | 同一のノードの集まりについての記述です。何台で、どのサイズか | **ホストのクラスター**に似ていますが、このグループは負荷に応じて自分でノードを追加・削除できます |
| **Kubeconfig** | クラスターのアドレスと、それへのアクセス権を収めたファイルです。これがなければ `kubectl` はどこに接続すればよいか分かりません | **vCenter のアドレスとアカウントの組み合わせ**に似ていますが、これはクライアントの設定ではなく、あなたのディスク上にあるただのテキストファイルです |
| **テナント** | プラットフォームの中のあなたの区画です。自分専用のクォータ、自分専用の権限、自分専用のオブジェクト | **リソースプールとフォルダーへの権限の組み合わせ**に似ていますが、これはさらに可視性の境界でもあります。隣人があなたのテナントを覗き見ることはありません |
| **Namespace** | クラスターの内部にある、オブジェクトを置く区画です | **vCenter インベントリのフォルダー**に似ていますが、分離はより厳格です。異なる namespace のオブジェクトは短い名前ではお互いを見つけられません |

コンテナについては別に一言述べる価値があります。これこそ、あなたが慣れ親しんだ世界からの主な逸脱だからです。コンテナとは、動作に必要なあらゆるものと一緒に単一のイメージファイルにパッケージされた、実行中のアプリケーションです。仮想マシンとの違いは、内部に自前のオペレーティングシステムを持たないことです。コンテナは、それが動いているマシンのカーネルを利用します。だからこそ規模が違ってきます。VM は起動に1分かかりギガバイト級の重さですが、コンテナは1秒で起動し、数十メガバイトの軽さです。まさにそのため、クラスターはコンテナをまとめて再起動することを何とも思いません。このあとのラボで、あなたはそれをやることになります。

## Windows をお使いの方へ — まずこれを読んでください

ラボのコマンドは Linux と macOS のコマンドラインを前提に書かれています。素の PowerShell では、その一部は動きません。PowerShell は構文もコマンドの体系も異なるからです。

解決策は **WSL** — Windows 内部の Linux サブシステムです。管理者として実行した PowerShell で、たった1つのコマンドでインストールできます。

```powershell
# Windows 内部に Linux サブシステムをインストールします: カーネル、サービス、そして
# デフォルトの Ubuntu ディストリビューション。インストール後、Windows は再起動を求めてきます。
wsl --install
```

再起動すると Ubuntu のコンソールが手に入り、あとは他のみんなと同じようにその中で作業します。WSL の中では、クラスターに接続するためのコマンドである自前の `kubectl` が必要になります。

```bash
# snap は Ubuntu のパッケージマネージャーです。--classic は隔離なしでパッケージをインストールします:
# 隔離モードでは kubectl がホームフォルダーにあるアクセスファイルを見られません。
sudo snap install kubectl --classic
```

Windows のドライブは WSL からは `/mnt/c/...` というパスで見えるので、普通のブラウザでダウンロードしたファイルは中からも利用でき、どこかへコピーする必要はありません。これは少しあとで、クラスターのアクセスファイルを受け取るときに役立ちます。Windows 側に保存すれば、WSL からは `/mnt/c/Users/Ivan/Downloads/filename` のようなパスに置かれることになります。

⚠️ **WSL がセキュリティポリシーで禁止されている場合** — 企業の bastion ではよくあることです — それでもラボは進められます。ダッシュボードで行うことはすべてオペレーティングシステムに依存しないからです。実行できないのは、チェックスクリプトと、完全にコマンドだけで構成されたいくつかのステップだけです。そうした箇所は個別に印を付けてあります。

## ラボのフォルダーには何があるか

ファイルはすべてすでにあなたのものです。リポジトリと一緒に取得済みです。作成したり、あらためて打ち込んだりするものは何もありません。以下で `kubectl apply -f name.yaml` と書かれているところでは、ファイルはここから取られます。

```bash
# パスはリポジトリのルートから数えます — 次のステップでそれを取得します
cd labs/00-cluster
```

| ファイル | 何なのか | いつ必要になるか |
|---|---|---|
| `cluster.yaml` | ラボ用クラスターの記述: バージョン、ノード、モニタリング | 最初のステップで管理クラスターに適用します |
| `check.sh` | クラスターが立ち上がり、あなたが接続できたことのチェック | ラボの最後に実行します |

## ステップ 0. 教材はすでに bastion 上にある

📍 **場所:** bastion 上（bastion のターミナル内）。

マニフェスト — クラスターに何を作成するかを記述したファイル — とチェックスクリプトは、すでにあなたのホームフォルダーの `~/workshop` ディレクトリにあり、あなたのテナント番号もそこに差し込み済みです。クローンするものは何もありません。中に入って、何があるか見てみましょう。

```bash
cd ~/workshop
ls manifests scripts labs
```

ここから先、ラボ内のすべてのパスはこのフォルダー（`~/workshop`）から数えます。

## プラットフォームへのアクセスを手に入れる

📍 **場所:** ブラウザ、そのあと bastion 上。

プラットフォームに注文するものはすべて、あなたのテナントと同じ場所である**管理クラスター**上に存在します。それにコマンドで接続するにはアクセスファイルが必要です。この bastion では**すでに設定済み**です — `~/.kube/config`。アクセスはトークンベースなので、クラスターを扱うときにブラウザは開かず、Keycloak も何も尋ねてきません。

このパスはすべてのラボで使われます。アクセスが機能することを確認しましょう。

```bash
# 管理クラスターに、あなたの Kubernetes クラスターの一覧を尋ねます。
# --kubeconfig はアクセスファイルを明示的に指し示します（ここではこれがデフォルトファイルでもあります）。
kubectl --kubeconfig ~/.kube/config get kubernetes.apps.cozystack.io -n tenant-workshopXX
```

**表示されるはずのもの:** 空の一覧か、`No resources found` という行のどちらかです。まだクラスターを一つも作成していないからです。大事なのは別のことです。エラーメッセージではなく、クラスター自身が応答したということです。

⚠️ **あなたのテナント番号は、ダッシュボードにサインインするときのログインです:** `workshop03`、`workshop07` などです。あなたのテナントの namespace は、`tenant-` という語とこの番号からできています: `tenant-workshop03`。以下で `workshopXX` と書かれているところはすべて、あなた自身の番号に置き換えてください。

## ステップ 1. クラスターを作成する

📍 **場所:** ブラウザ、Cozystack ダッシュボード内。

テナント → **Create application** → `Kubernetes`。

入力します。

| フィールド | 値 | なぜそうするか |
|---|---|---|
| Name | `lab` | 短く — コマンドで打ち込むことになるからです |
| Version | 提示されたものを残す | 最新の安定版だからです |
| Control plane replicas | **1** | デフォルトは2つ。ラボ用のテスト環境なら1つで十分です |
| Node group: name | `md0` | この名前はノード名の一部になります — 後ほど `kubectl get nodes` の出力で目にします |
| Node group: min replicas | **1** | 1ノードから始めます |
| Node group: max replicas | **3** | グループが自分で成長できる上限です。デフォルトは10で、スケーリングのラボはこの上限を前提に組まれています |
| Node group: instance type | `u1.medium` | 1プロセッサ、4 GB |
| Node group: disk | `20Gi` | |
| Storage class | `replicated` | データは異なるノード上に3つのコピーで置かれます |
| Addons → **Monitoring agents** | **有効にする** | そうしないとメトリクスが蓄積されず、グラフのラボで見るものが何もなくなります |

作成をクリックします。

⚠️ **`Monitoring agents` は今すぐ有効にしてください。** メトリクスの収集は後付けで有効にできません。1週間後にチェックを入れても、それ以前に起きたことはすべて永久に失われます。グラフのラボは、今日から蓄積されるデータに依存しています。

⚠️ **隣で誰かが同じことをしているなら — 数分ずらしてください。** 同時に複数の作成が走ると内部のインストーラーに負荷がかかり、両方のクラスターが立ち上がるのに3倍の時間がかかります。ラボは自分のペースで進めるものです。急ぐ必要はありません。

### もう少し詳しく: cluster.yaml の中身

これはダッシュボードが落ちたときの代替手段ではありません。ダッシュボードのボタンは、まさにこれと同じファイルを組み立ててクラスターに送ります。つまり、ここではテキストが一次的なもので、マウスはその上に乗った層にすぎません。私たちが向かっているのはテキストでの作業です。ファイルに存在する記述はレビューでき、Git に入れて、ロールバックできますが、ボタンを押すことはそうはいきません。

このファイルはこのラボのフォルダーにあります: **`labs/00-cluster/cluster.yaml`**。開いたり、あらためて打ち込んだりするものは何もありません。ラボの最初でリポジトリを取得していれば、すでにあなたのものです。フィールドごとに見ていけるよう、以下に全文を示します。

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: Kubernetes
metadata:
  name: lab
  namespace: tenant-workshopXX
spec:
  version: v1.35
  storageClass: replicated
  controlPlane:
    replicas: 1
  addons:
    monitoringAgents:
      enabled: true
  nodeGroups:
    md0:
      minReplicas: 1
      maxReplicas: 3
      instanceType: u1.medium
      diskSize: 20Gi
      storageClass: replicated
```

⚠️ 以下のコマンドは**管理クラスター上で**、テナントと一緒に渡されたアクセスで実行されます。`lab` クラスターそのものへのアクセスファイルはまだ存在しません。それはクラスターが立ち上がってから初めて現れます。

```bash
# ラボのフォルダーに移動します — ここから先、すべてのファイルはここから取られます
cd labs/00-cluster
# 適用する前に、ファイル内の XX をあなた自身のテナント番号に置き換えてください。
# apply = 「クラスターをファイルに記述された状態にせよ」。このコマンド自身がクラスターを
# 立ち上げるのではありません — それはプラットフォームに注文を渡し、プラットフォームが
# 何をどの順で作成するかを決めます。
#   -f   記述をファイルから取る
kubectl apply -f cluster.yaml
# get = 「何があるか見せろ」。kubernetes.apps.cozystack.io はオブジェクト型の完全名で、
# ファイルに記述されたまさにそれ（kind: Kubernetes）、lab はあなたの注文の名前です。
#   -n   どの namespace を見るか。フラグなしだと kubectl はデフォルトの namespace を見ます
#   -w   変更を監視して出力する。抜けるには Ctrl+C、これでインストールは中断されません
# READY 列に True が現れるまで待ちます。
kubectl -n tenant-workshopXX get kubernetes.apps.cozystack.io lab -w
```

## ステップ 2. 待ちながら、何から組み上がるのかを見る

📍 **場所:** ブラウザ、ダッシュボード内。

ステータスは通常5分から10分で `Ready` に変わります。

⚠️ **20分以上経ってもステータスが変わらない場合 — 原因はあなたのクラスターにないかもしれません。** プラットフォーム上のすべてのアプリケーションのインストールは共有のキューが取り仕切っており、そこに誰かの長い操作が並んでいると、あなたのクラスターは順番を待つことになります。作業に取り掛かられたかどうかを見るには:

```bash
# 注文そのものと、プラットフォームがそれについて書いていることを見ます。
# 出力の末尾にある status.conditions セクションがその報告です: 作業に取り掛かられたか、
# 何が妨げているか、何を待っているか。
kubectl --kubeconfig ~/.kube/config -n tenant-workshopXX \
  get kubernetes.apps.cozystack.io lab -o yaml
```

そこを見ても要領を得ないなら — テナントのイベントを見てください。これはプラットフォームがあなたのオブジェクトに対して何をしたかのログです。

```bash
# events = 出来事のログ。新しいものが下に来るよう、時刻で並べ替えます。
kubectl --kubeconfig ~/.kube/config -n tenant-workshopXX \
  get events --sort-by=.lastTimestamp | tail -20
```

ここで最もよく見つかるのは `exceeded quota: tenant-quota` という行です。これは、あなたのテナントに割り当てられたリソース分をクラスターが超過していることを意味し、クラスターは自分でこの状態から抜け出せません。場所を空けるか、クォータを拡張する必要があります。

インストールが走っている間に、あなたのテナントに実際に何が現れるのか、ダッシュボードで見てください。

**コントロールプレーン**は、いくつかの普通のアプリケーションとしてデプロイされました。「このクラスターの vCenter」を担う独立したマシンはありません。管理層は、他のすべてと並んで動くプロセスです。

**ノード** — こちらは仮想マシンです。あなたが移行するものとまったく同じ、ごく普通のものです。自分のディスク、自分のメモリ、自分のアドレスを持ち、あなたのテナントの中に存在します。

ここから大事なことが導かれます: **ここでの Kubernetes は仮想化を置き換えるのではなく、その上に乗っています。**「VM を動かす」か「コンテナを動かす」かを選ぶ必要はありません。どちらも、同じハードウェア上で、同じインターフェースで動きます。

## ステップ 3. 新しいクラスターへのアクセスを手に入れる

📍 **場所:** bastion 上。ファイル自体はコマンドかダッシュボードから取得します。

**取得するもの。** `lab` クラスターの kubeconfig — その API サーバーのアドレスと、それへのあなたのアクセスデータが記録されたテキストファイルです。こうしたファイルがなければ、`kubectl` はどこに接続すればよいか、誰として名乗ればよいか分かりません。ファイルはあなた自身が bastion 上に `~/lab.kubeconfig` という名前で作成します。パス中の `~` はあなたのホームフォルダーで、macOS では `/Users/name`、Linux と WSL では `/home/name` です。

⚠️ **これは2つ目のアクセスファイルであって、1つ目の置き換えではありません。** テナントと一緒に渡されたもの（ラボでは `~/.kube/config` というパスにあります）は管理クラスターへ通じています — アプリケーションを注文する場所であり、たった今 `lab` を作成した場所です。新しいファイルは `lab` クラスターそのものの内部へ通じています。これらはアドレスの異なる2つの別々のクラスターで、ここから先は両方とも必要です。プラットフォームへの注文は1つ目のファイルで、自分のクラスター内部での作業は2つ目のファイルで行います。

**それがある場所。** プラットフォームはそれをあなたのテナント内の Secret `kubernetes-lab-admin-kubeconfig` に入れました。Secret は、パスワード、鍵、アクセスファイルを保管するクラスターオブジェクトです。Secret 内で必要な鍵は `admin.conf` です。

⚠️ **Secret には4つの鍵があり、必要なのはまさに `admin.conf` です。** その隣には `admin.svc` があります — 同じものですが、クラスターの内側からしか見えない内部アドレスが入っており、bastion からはそれで接続できません。`super-admin.*` のペアは、設定された制限を迂回する権限を与えるもので、障害後の調査のためのものであって、日常の作業のためではありません。

**主な方法 — コマンドで。** Cozystack はあなたのクラスターに、まさにこの Secret を読むことだけを許可し、それ以外は何も許可しない専用のアクセスルールを設定します。コマンドは**管理クラスター上で**、テナントと一緒に渡されたアクセスで実行され、その結果は bastion 上のファイルに入れられます。

```bash
# get secret = Secret を見せる。-o go-template — 全体を印字するのではなく、
# そこから1つのフィールドを取り出してテキストとして出力します:
#   index .data "admin.conf"   Secret から admin.conf という鍵を取る
#   base64decode               Secret の内容は base64 エンコードされて保存されているので、
#                              この関数が元のテキストを返します
#   > ~/lab.kubeconfig         出力を画面ではなくファイルに書き込む
kubectl -n tenant-workshopXX get secret kubernetes-lab-admin-kubeconfig \
  -o go-template='{{ printf "%s\n" (index .data "admin.conf" | base64decode) }}' > ~/lab.kubeconfig
```

**同じことをマウスで。** この同じ Secret は、ダッシュボードの `lab` アプリケーションのページ、その secret 一覧の中に見えます — `kubernetes-lab-admin-kubeconfig` という名前で探してください。`admin.conf` 鍵の値をコピーし、任意のテキストエディタを開いてコピーしたものを貼り付け、ホームフォルダーに `lab.kubeconfig` という名前でファイルを保存します。

## ステップ 4. 接続する

📍 **場所:** bastion 上（bastion のターミナル内）。

**これから起きること:** `kubectl` にどのアクセスファイルを使うかを伝え、クラスターにそのノードの一覧を尋ねます。

macOS と Linux:

```bash
# KUBECONFIG は、kubectl がどのアクセスファイルを取るかを知るための変数です。
# export により、このターミナルウィンドウで以降実行されるすべてのコマンドから見えるようになります。
export KUBECONFIG=~/lab.kubeconfig
# nodes はクラスターのノード、あなたのアプリケーションが動くまさにあの仮想マシンです。
# その応答は、ついでにアクセスファイルが機能していることも証明します。
kubectl get nodes
```

Windows PowerShell — WSL をインストールできなかった場合のみ:

```powershell
# PowerShell では環境変数は $env: で設定し、ウィンドウを閉じるまで存続します
$env:KUBECONFIG="$HOME\lab.kubeconfig"
kubectl get nodes
```

**表示されるはずのもの** — あなたのノードとステータス `Ready` の1行です。

```
NAME                        STATUS   ROLES    AGE   VERSION
kubernetes-lab-md0-xxxxx    Ready    <none>   3m    v1.35.6
```

⚠️ **`TLS handshake timeout` と `context deadline exceeded` は、コマンドのエラーではなく、クラスター側の拒否です。** あなたのクラスターの管理部分は1コピーで動いており、プラットフォームが負荷を受けると数十秒間応答をやめます。コマンドは失敗しますが、30秒後にもう一度実行すると通ります。これが `apply` の途中で起きたなら、繰り返してください。このコマンドはクラスターをファイルに記述された状態にするだけで、新しいものを追加するわけではないので、二重に作成されることはありません。

⚠️ **`KUBECONFIG` 変数は、新しいターミナルウィンドウごとに設定する必要があります。** これを忘れると、`kubectl` は何か別のクラスターへ行くか、接続する先がないと言います。これはすべてのラボを通じて「全部壊れた」の最も多い原因です。何かの挙動がおかしければ — 最初に確認すべきは `echo $KUBECONFIG` です。

## チェック

📍 **場所:** bastion 上、`kubectl` で作業していたのと同じターミナルウィンドウで。

```bash
# スクリプトはラボのフォルダーから実行します: ファイルを自分の隣で探すからです
cd labs/00-cluster
# 名前の前の ./ は「ファイルをまさにここから実行せよ」という意味です。これがないとシェルは
# check.sh というコマンドをシステムフォルダーの中で探し、見つけられません
./check.sh
```

⚠️ **Windows ではスクリプトは PowerShell からではなく WSL から実行します** — その入れ方はこのラボの最初に書いてあります。WSL がなくてもラボは完了できますが、成果物としてのレポートは得られません。

スクリプトは、クラスターが応答すること、ノードが正常であること、そしてその上に将来のアプリケーションのための余地があることを確認します。その隣にレポートファイルが現れます — ラボが完了した証拠として、どこにでも添付できます。

## 後片付け

クラスターはラボ 1〜5、そしてそれ以降でも必要になります。今は削除しないでください。

すべてのラボが終わったら — ダッシュボードから `lab` アプリケーションを削除します。

削除そのものには数分かかります。プラットフォームはノードの VM を停止し、管理コンポーネントを取り除き、ディスクを解放します。そのときインストールのキューが誰かの長い操作でふさがっていると、待ち時間はもっと長くなることもあります — その場合は、ラボの前の方で説明した `reconcile.fluxcd.io/requestedAt` アノテーションを使う、あの同じ手が役立ちます。

大事なのは別のことです: **解放されたものは、まるごと、ひとりでにクォータへ戻ります。** 誰かに頼んだり、なぜ確保したのかを説明したりする必要はありません。

## これで私たちができるようになったこと

- 誰かに掛け合うことなく、自分のために Kubernetes クラスターを立ち上げる
- コントロールプレーンはプロセスであり、ノードは仮想マシンだと理解する
- アクセスを取得し、bastion から接続する
- `kubectl` の挙動がおかしいとき、どこに原因を探せばよいか知っている

## そして vSphere ならこうなる

vSphere における Kubernetes は、別個の製品、別個のライセンス、そしてベンダーが関与する導入プロジェクトです。ここでは、カタログの一行と10分です。

**正直なところ、vSphere のほうが便利なところ。** 必要なのが仮想マシンだけで他に何もいらないのなら、vCenter はそれらを管理するための出来合いのツールをより多く提供します: テンプレート、クローン、ゲスト OS のカスタマイズ、単一フォルダー単位での権限。Cozystack も VM は扱えますが、その周りのエコシステムはここではまだ若いのです。得られるものが現れるのは、VM とそれ以外のすべて — データベース、キュー、クラスター、レジストリ — が同時に、一つの場所で、一つの API を通じて必要になる場面です。
