## なぜこれが大切か

社員名簿は「Propusk」のなかで最も古い部分です。2011年のアプリケーションで、書いたのはもういない請負業者。Windows Server と、一度も更新されていないバージョンの .NET の上で動いています。理由は「動いているから」。ソースコードもなく、ドキュメントもなく、あるのは4ページの復旧手順書だけ。そのなかには「セルゲイに電話する」という手順まであります。

中身は小さな Web アプリケーションです。社員とその電話番号を並べた HTTP ページを配信します。人はそれをブラウザで開き、他のサービスはデータを取りにここへアクセスします。

この名簿はコンテナへは移りません。「まだ」ではなく、決して移りません。誰も再ビルドできないアプリケーションを、物理的にコンテナ化することはできないからです。そしてそれは移行を見送る理由にはなりません。「移せないものはどうするのか?」への答えはこうです。そのまま、仮想マシンとして持ってくるのです。

けれども移すだけでは足りません。名簿は以前と同じように外部から見えなければなりません。このラボでは、コンテナの隣に仮想マシンを立ち上げ、**コンテナ化されたアプリケーションとまったく同じやり方で** 外部に公開します。プラットフォームの ingress とドメイン名を通して、です。プラットフォームにとって、仮想マシンはドメインの背後にあるもう一つのワークロードにすぎず、その背後にコンテナがあるのか OS まるごとなのかを気にする必要はありません。

## ミニ用語集

| 用語 | 何か | 似ているのは…ただし |
|---|---|---|
| **VMInstance** | クラスターのオブジェクトとしての仮想マシン | **仮想マシン**。ただしテキストで記述され、アプリケーションと同じ `kubectl` で作成されます |
| **VMDisk** | マシンとは別に存在するディスク | **vmdk**。ただし独立したオブジェクトで、マシンより長く生き残り、別のマシンに接続できます |
| **Instance type** | プラットフォームのリストにある既製のマシンサイズ。何 vCPU、何のメモリという単位 | vCPU/RAM の手動チューニングよりも、クラウドのインスタンスタイプに近い |
| **Instance profile** | ゲスト OS 向けのデバイスとドライバーのセット | **Guest OS type**。ただしゲストがどのコントローラーを見るかに影響します |
| **cloud-init** | マシンを初めて電源投入したときに一度だけ走る、初回起動時のプロビジョニングスクリプト | **Customization Specification**。ただし UI のウィザードではなく、マニフェスト内のただの YAML です |
| **Service** | クラスター内の Pod のグループに対する一つの安定したアドレス | **ロードバランサーのプール**。ただしメンバーの一覧は、ラベルをもとにプラットフォーム自身が常に最新に保ちます |
| **Ingress** | HTTPS も含めた、どのドメインをどの Service へ振り分けるかというルール | **ファームの前に立つリバースプロキシ**（nginx、HAProxy）。ただしオブジェクトとして記述され、ドメインと証明書はプラットフォームが発行します |
| **domain** | サービスが HTTP 越しに外部から見える、永続的な名前 | **企業のロードバランサーの背後にある DNS 名**。ただし DNS への申請票も証明書への申請票も要りません |
| **KubeVirt** | Kubernetes が仮想マシンを動かす仕組み | **ハイパーバイザー**。ただし二つ目のハイパーバイザーではありません。その下にあるのは、どんな Linux でも使っているのと同じ QEMU/KVM です |

## ステップ 1. 仮想マシンを立ち上げる

📍 **どこで:** ブラウザで、テナントのダッシュボードで。

仮想マシンは Cozystack のマネージドサービスで、あなたのテナント内に存在します。これは二段構えで作られます。この点はすぐに理解しておく価値があります。

### まずディスク

テナント → **アプリケーションを作成** → `VM Disk`。

| フィールド | 値 | なぜそうするか |
|---|---|---|
| Name | `spravochnik` | マシンもこの名前で呼ばれます |
| Source | `Image` → `ubuntu-22.04` | プラットフォームの既製イメージコレクションから取ります |
| Storage | `20Gi` | `ubuntu-22.04` イメージは 20Gi に展開されます。これより小さくは指定できません |
| Storage class | `replicated` | データのコピーを別々のノードに3つ |

**なぜディスクはマシン内のフィールドではなく別オブジェクトなのか。** ディスクがマシンより長く生き残るからです。マシンはまるごと削除でき、別のタイプ、別のネットワーク、別の名前で作り直して、同じディスクを接続できます。vSphere でも、ある VM から vmdk を切り離して別の VM に接続するとき、同じことをしています。ここではそれがモデルのなかで明示的に表現されています。

⚠️ **ディスクはソースイメージより小さくできません。** プラットフォームの `ubuntu-22.04` は 20Gi に展開され、10Gi のディスクを要求してもプラットフォームは拒否します。より小さなボリュームへイメージをクローンする場所がないからです。ここで小さくしすぎるのは、大きくしすぎるよりも高くつきます。ディスクは後で拡張できますが、縮小はできません。

ディスクが満たされるまで待ちます。プラットフォームがイメージをダウンロードして展開します。1〜2分かかります。

### そしてマシン

テナント → **アプリケーションを作成** → `VM Instance`。

| フィールド | 値 | なぜそうするか |
|---|---|---|
| Name | `spravochnik` | |
| Instance type | `u1.medium` | 1 CPU、4 GB。クラスターのノードが使うのと同じサイズのリスト |
| Instance profile | `ubuntu` | ゲスト OS 向けのデバイスのセット |
| Run strategy | `Always` | 動かし続ける。自分でシャットダウンしても、また起動される |
| Disks | `spravochnik` | あなたが作成したディスク |
| Cloud init | 下記参照 | ポート 8080 で名簿を立ち上げます |

cloud-init のフィールドには:

```yaml
#cloud-config
password: ubuntu
chpasswd: { expire: false }
ssh_pwauth: true
write_files:
  - path: /opt/directory/index.html
    content: |
      <!doctype html><html lang="ru"><head><meta charset="utf-8"><title>Справочник</title></head><body><h1>Справочник сотрудников</h1><ul><li>Иванов И. — 101</li><li>Петров П. — 102</li></ul></body></html>
  - path: /etc/systemd/system/directory.service
    content: |
      [Unit]
      Description=Staff directory
      After=network.target
      [Service]
      ExecStart=/usr/bin/python3 -m http.server 8080 --bind 0.0.0.0 --directory /opt/directory
      Restart=always
      [Install]
      WantedBy=multi-user.target
runcmd: [ "systemctl daemon-reload", "systemctl enable --now directory" ]
```

この cloud-init は名簿をサーバーに変えます。社員一覧を載せた HTML ページを置き、それを HTTP でポート 8080 に配信するサービスを立ち上げます。`python3` は Ubuntu イメージにすでに入っているので、インストールするものは何もなく、インターネットも要りません。ポート 8080 は適当に選んだのではありません。講師が事前に作った `Service spravochnik-http` が見ているのが、まさにこのポートです。

⚠️ **平文のパスワード — ラボ限定です。** 実際のマシンなら、ここには `sshKeys` があり、パスワードはまったくないはずです。ワークショップの時間を鍵の交換に費やさないために、近道を取っています。

**同じものをテキストで。** ディスクとマシンという二つのオブジェクトはどちらも一つのファイル `staff-directory-vm.yaml` に入っていて、一つのコマンドで作られます。まずディスク、次にマシンです。適用する前にファイルを開き、その中の `tenant-workshopXX` というプレースホルダーを自分のテナントの名前に置き換えてください。さもないとオブジェクトが違う場所に行ってしまいます。

```bash
# KUBECONFIG は kubectl がクラスターのアドレスとログイン情報を読み取る変数です。
# ここではテナントのアクセスファイルが必要です。仮想マシンは管理クラスター上のテナント内に存在します。
export KUBECONFIG=~/.kube/config
# apply = 「ファイルに書かれた状態にクラスターを合わせる」。オブジェクトが無ければ作成し、
# 有ればその記述された状態へ合わせます。
#   -f   記述をファイルから読む
kubectl apply -f staff-directory-vm.yaml
```

**見えるはずのもの:** `created` を含む2行。ディスク用に1つ、マシン用に1つです。

<details>
<summary><b>もっと詳しく:staff-directory-vm.yaml の中身</b></summary>

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: VMDisk
```

バケット、データベース、キューが属するのと同じ API グループです。ここでは仮想マシンは、独自のインターフェイスを持つ別のサブシステムではなく、Redis とまったく同じカタログのオブジェクトです。これが「一つのインターフェイスで、一つの API を通して」というフレーズの中身です。

```yaml
spec:
  source:
    image:
      name: ubuntu-22.04
  storage: 20Gi
```

URL ではなく、プラットフォームの共有コレクションにあるイメージ名です。コレクションはクラスター全体で共有され、イメージは一度だけダウンロードされます。`storage` はイメージそのものより小さくできません。`ubuntu-22.04` は 20Gi に展開されます。自分のイメージが必要なら、同じ場所にリンクを指定する `source.http` と、既存のディスクをクローンする `source.disk` があります。

```yaml
kind: VMInstance
spec:
  instanceType: u1.medium
```

マシンのサイズは vCPU と RAM のフィールドで細かく指定するのではなく、既製のリストから取ります。`u1.medium` は 1 CPU、4 GB です。Kubernetes クラスターのノードを注文するときにも同じリストが使われますが、これは偶然ではありません。クラスターのノードもまったく同じ VMInstance だからです。

```yaml
  instanceProfile: ubuntu
```

ゲスト OS のプロファイルです。ゲストが認識できるように、どのコントローラー、ドライバー、デバイスをマシンに渡すか、を決めます。最も近い類推は vSphere で VM を作るときの「Guest OS type」で、結果も同じです。プロファイルを間違えると、起動はするけれどディスクが見えないマシンになります。

```yaml
  runStrategy: Always
```

望ましい電源の状態です。`Always` — 動かし続ける。ゲストが内側からシャットダウンしても、マシンはまた起動されます。`Halted` — 電源オフ。`Manual` — そのまま、誰も介入しません。この言い回しに注目してください。Deployment の `replicas` と同じで、「電源を入れろ」ではなく「電源を入れたままにしておけ」です。

```yaml
  disks:
    - name: spravochnik
```

VMDisk オブジェクト名によるディスクのリストです。データ用の二つ目のディスクは、まさにここに2行目として追加します。

```yaml
  cloudInit: |
    #cloud-config
    write_files:
      - path: /opt/directory/index.html
      - path: /etc/systemd/system/directory.service
    runcmd: [ "systemctl daemon-reload", "systemctl enable --now directory" ]
```

cloud-init は、あらゆるクラウド向け Linux イメージが理解する、標準的な初回起動時プロビジョニングの仕組みです。初回の電源投入時に一度だけ走ります。ここでは三つのことをします。名簿の HTML ページを置き、そのページを HTTP でポート 8080 に配信する systemd サービスを立ち上げ、そのサービスを起動します。vSphere の Customization Specification に相当しますが、UI のウィザードではなくマニフェスト内のテキストです。つまり Git に置かれ、他のすべてと一緒にレビューされます。

名簿が外部から見えるようになるのは、まさにこのブロックのおかげです。講師が事前に作った `Ingress` がドメインを `Service spravochnik-http` へ振り分け、それがさらにマシン内部のポート 8080 へ振り分けます。8080 のサービスが立ち上がるとすぐ、公開のほうがそれを勝手に拾います。

### このマニフェストに無いもの、そしてこれからも無いもの

**`replicas` フィールド。** `VMInstance` にはありません。仮想マシンは一つのオブジェクトです。マシンが二台必要なら、別々の名前でオブジェクトを二つ作ります。

これは `Deployment` との根本的な違いであり、欠点ではありません。Deployment のコピーは互換で、どれでもどんなリクエストにも応じ、一つ失っても大したことはありません。仮想マシンは互換ではありません。それぞれが自分のディスクに自分の状態を持ち、「同じものをもう一台作る」は、コンテナのそれとはまったく別の意味になります。

実際上の帰結。**Pod を削除したラボで見た自己修復は、仮想マシンには存在しません。** Pod を削除すればクラスターが数秒で新しいものを作ります。VMInstance を削除するとマシンは消え、それを取り戻す唯一の方法は、生き残ったディスクを接続して手作業で戻すことです。ここでは、あなたは vSphere にいたのとまったく同じ場所にいます。それは途中で気づくのではなく、前もって知っておく価値があります。

</details>

初回の電源投入には3〜5分かかります。cloud-init がファイルシステムをディスク全体に広げ、名簿サービスを立ち上げます。手をこまねいて待つことはしません。次のステップでは、マシンがまだ起動している間に、公開のほうで何が起きているかをちょうど確認します。

## ステップ 2. マシンが起動する間にドメインを叩く

📍 **どこで:** bastion 上で（bastion のターミナルで）、別のウィンドウで。あるいは自分のラップトップのブラウザで直接。

講師が事前に名簿を公開しています。あなたのテナントにはすでに、ホスト `spravochnik.workshopXX.workshop.aenix.io` を持つ `Ingress spravochnik` と、マシン内部のポート 8080 へ振り分ける `Service spravochnik-http` があります。公開は、名簿が応答を返し始めた瞬間に受け入れる準備ができています。マシンの読み込みが終わるのを待たず、今すぐ確認しましょう。

```bash
# curl — 「アドレスへ行って応答を見せる」。XX は自分のテナント番号に置き換えます。
#   --max-time 5   長く待たずに5秒であきらめる
curl --max-time 5 http://spravochnik.workshopXX.workshop.aenix.io
```

**見えるもの:**

```
<html><head><title>503 Service Temporarily Unavailable</title></head>
<body><center><h1>503 Service Temporarily Unavailable</h1></center></body></html>
```

> **先を読む前に、立ち止まって考えてください。**
>
> ingress は講師が作り、ドメインは設定され、マシンはあなたが立ち上げました。
> なぜドメインは名簿のページではなく `503` を返すのでしょうか?

<details>
<summary><b>その答えと、このエラーより広い教訓</b></summary>

マシン内部の名簿がまだ待ち受けていないからです。

`503` は「ingress が壊れている」という意味ではありません。ingress は所定の場所にあり、トラフィックをどこへ振り分けるかを知っています。`Service spravochnik-http` へ、そしてそれがあなたのマシンの Pod を選択してリクエストをポート 8080 へ転送します。けれども cloud-init がファイルシステムを広げ、サービスを立ち上げている間は、マシン内部の 8080 でまだ誰も応答していません。サービスには準備完了のバックエンドが一つもないのです。ingress はまさにそれを報告しています。ルートはあるが、そこで応答できる者がまだいない、と。

ここでの応答コードは、それ自体が診断です。

| 見えるもの | その意味 |
|---|---|
| `503` | ingress は所定の場所にあるが、その背後に準備完了のバックエンドがない |
| `404` | ingress は存在するが、ルールが間違ったサービスへ振り分けている |
| 応答なし、timeout | このホストを持つ ingress がそもそも作られていない |

**教訓はこのエラーより広いものです。** ingress からの `503` は、ingress 自体についてではなく、バックエンドの準備状態についてのものです。ドメインの背後のアプリケーションがクラッシュしたり、その Pod がまだ readiness チェックを通っていなかったりしても、同じ `503` が返ります。外部への公開とワークロードの準備状態は、二つの別のことです。ドメインは事前に設定され、しばらくの間は空で、その背後に応答できる者が現れたちょうどそのときに中身が満たされます。仮想マシンなら「8080 のサービスが立ち上がったとき」、コンテナなら「Pod が readiness を通ったとき」です。仕組みは同じであり、それこそが「仮想マシンはコンテナ化されたアプリケーションと同じやり方で公開される」というフレーズの意味です。

</details>

## ステップ 3. マシンに入る

📍 **どこで:** ダッシュボードで、`spravochnik` マシンのカードで。

カードにはコンソールがあります。vSphere の「Open Console」と同じ画面です。それを開いてください。ログイン `ubuntu`、パスワード `ubuntu`。

⚠️ **コンソールが黒い画面と点滅するカーソルを表示していたら — 待ってください。** cloud-init がまだ終わっておらず、プロンプトはひとりでに現れます。マシンを再起動しないでください。cloud-init の途中での再起動は、マシンを半分だけ設定された状態に残します。

**ターミナルからの同じログイン。** `virtctl` は仮想マシンを扱うための別のコマンドです。コンソール、ポート転送、電源のオンとオフを行います。単一のファイルとしてインストールされます。その方法は `workshop/README.md` に書かれています。

その構文の一つの癖は、前もって取り上げておく価値があります。さもないと、いちばん最初のコマンドが拒否で返ってきます。`virtctl` のターゲットは、裸の名前ではなくタイプの接頭辞をつけて指定します。`vmi/<name>` です。`vmi` は virtual machine instance、マシンの **実行中インスタンス** です。あなたが作った `VMInstance` オブジェクトと、実行中インスタンスは、API 上の二つの別のオブジェクトです。テナントアクセスのもとでは、権限は `virtualmachineinstances` の **サブリソース**（`console` と `portforward`）に付与されており、`virtualmachines` オブジェクトまるごとには付与されていません。裸の名前は vm オブジェクトに当たり、`forbidden` で返ってきます。プラットフォームはインスタンス名を、接頭辞 `vm-instance-` にあなたのマシンの名前をつなげて組み立てます。`spravochnik` はインスタンス `vm-instance-spravochnik` です。

```bash
# テナントアクセス:マシンはテナント内に存在します
export KUBECONFIG=~/.kube/config
# console = マシンのシリアルコンソールに接続します。vSphere の「Open Console」が与えるのと
# 同じ画面ですが、テキストベースです:
#   --namespace  クラスターのどのセクションを見るか。あなたのテナントでは
#                tenant- にあなたのログインをつけた名前です。XX は自分の番号に置き換えます
#   vmi/...      ターゲット:VMInstance の記述ではなく、マシンの実行中インスタンス
virtctl console --namespace=tenant-workshopXX vmi/vm-instance-spravochnik
```

接続後に画面が空なら Enter を押してください。ログインプロンプトが現れます。コンソールから抜けるには `Ctrl+]`。あなたのテナント内のすべての実行中インスタンスの名前は `kubectl --kubeconfig ~/.kube/config get vminstance -n tenant-workshopXX` で表示されます。

内側から見れば、ふつうの Ubuntu です。名簿が立ち上がったことを確認しましょう。

```bash
uname -a                       # カーネルとアーキテクチャ:ベアメタルサーバーと同じ行
systemctl status directory     # 名簿サービス:active (running) であるべき
curl -s localhost:8080 | head  # 同じページ。ただしマシン自身の内側から要求したもの
```

`systemctl status directory` が `active (running)` を示し、`localhost:8080` への `curl` が社員一覧を含む HTML を返したなら、サーバーは準備ができていて、外側の公開はもうすぐ `503` をページに切り替えます。内側に Kubernetes の痕跡はまったくなく、あるべきでもありません。ゲストは自分がクラスターの中にいることを知りません。vSphere の仮想マシンが vCenter について知る必要がないのと、まったく同じです。

## ステップ 4. ドメインが応答する — 名簿が公開された

📍 **どこで:** bastion 上で（bastion のターミナルで）。あるいは自分のラップトップのブラウザで。

`503` を返したのと同じリクエストです。ただし今はもう 8080 のサービスが立ち上がっています。自分の番号を入れてください。

```bash
curl http://spravochnik.workshopXX.workshop.aenix.io
```

**見えるはずのもの** — 名簿ページの HTML:

```html
<h1>Справочник сотрудников</h1><ul><li>Иванов И. — 101</li><li>Петров П. — 102</li></ul>
```

このアドレスをブラウザで開けば、同じ一覧が見えます。名簿は、人にやさしいドメイン名で、プラットフォームからの HTTPS つきで、ネットワークへの申請票も証明書への申請票も一枚も出さずに、外部から見えています。

**いま何が起きたのかを解きほぐしましょう。**

Kubernetes について何も知らない Ubuntu の仮想マシンが、ふつうのポートでふつうの HTTP を待ち受けています。外部からはドメイン `spravochnik.workshopXX.workshop.aenix.io` で到達され、リクエストは、コンテナ化されたアプリケーションを公開するのと同じ ingress を通ってそこへたどり着きます。ゲスト内のエージェントもなく、ゲートウェイもなく、「統合」もありません。公開にとって、ドメインの背後にあるのが何か — nginx の Pod なのか仮想マシンまるごとなのか — は違いを生みません。`Service` が見え、`Service` の背後には準備完了のバックエンドがあり、それで十分なのです。

これこそが「レガシーはコンテナ化する必要はない」という言葉の意味です。2011年の名簿は、これまでどおりに働き続けます。そして外側から見れば、それは「Propusk」のどんな新しいサービスともまったく同じに見えます。名前、ドメイン、HTTPS です。

## 検証

📍 **どこで:** bastion 上で（bastion のターミナルで）、`kubectl` で作業したのと同じウィンドウで。

スクリプトはオブジェクトの有無ではなく、実質的な動作を確認します。ドメイン名で `200` が返り、それが名簿ページであること、マシン自身が動いていること、それを公開する `Ingress` が所定の場所にあること、です。ドメインによる確認はテナントアクセスがなくても動きます。`curl` があれば足ります。テナントアクセスがあると、マシンの状態のチェックが加わります。

```bash
# テナントアクセス:ここからスクリプトは仮想マシン自体と Ingress を取ります
export KUBECONFIG=~/.kube/config
# tenant- という語をつけないあなたのログイン:これからスクリプトはセクション名 tenant-workshopXX と
# ドメイン名 spravochnik.workshopXX.workshop.aenix.io の両方を組み立てます
export COZY_TENANT=workshopXX
# 名前の前の ./ は「現在のフォルダにあるファイル」、つまり labs/12-vm のものを意味します
./check.sh
```

⚠️ **Windows ではスクリプトは PowerShell からではなく WSL から実行します。** インストール方法はラボ 0 の最初に書かれています。WSL がなくてもラボは進められますが、成果物のレポートは出ません。

`COZY_TENANT` は必須です。これがないとスクリプトはすぐに止まります。ドメインはこれから組み立てられるからです。テナントアクセスが設定されていなければ、マシンの状態のチェックは警告つきでスキップされ、主要な確認 — ドメインでの応答 — は動きます。

## 後片付け

モニタリングのラボを予定しているなら、仮想マシンは残しておいてください。その消費はグラフにも現れ、よい実例になります。予定していないなら、ダッシュボードからマシンとディスクを削除してください。

⚠️ **正しい順序で削除してください。まずマシン、それからディスク。** 動いているマシンに接続されたディスクは削除されず、削除中の状態のまま宙ぶらりんになったオブジェクトが残ります。

名簿を公開する `Ingress` と `Service` は講師が作ったものです。これらには触れないでください。このテスト環境の次の参加者に必要になります。

後片付けのコストは、ここでは他のラボよりも正直に高いです。データの入ったディスクはデータの入ったディスクであり、瞬時には消えません。その代わり、作成にはディスク容量の申請票も承認も要りませんでした。

## いま私たちにできること

- テナント内で仮想マシンを立ち上げる — マウスでも、テキストでも
- なぜディスクとマシンが二つのオブジェクトなのか、そしてそれが何をもたらすのかを説明する
- ワークロードを ingress とドメインで外部へ公開する — コンテナと同じやり方で
- ingress からの `503` を、故障ではなく「ドメインの背後にまだ応答できる者がいない」と読む
- レガシーの移行が書き直しを必要としないことを、生きた実例で示す

## そしてこれが vSphere なら

vSphere の仮想マシンはホームグラウンドで、そこでは慣れたやり方で作られます。違いはマシン自体ではなく、それを人にやさしい名前で外部へ露出させることにあります。

このマシンを vSphere でドメインとして公開するには、別製品としてのリバースプロキシまたはロードバランサー、外部アドレスのためのネットワークへの申請票、名前のための DNS への申請票、そして証明書のためのセキュリティへの申請票が必要になります。三つか四つのコマンド、三つか四つのシステム、そして「これを全部誰が運用するのか」という一般的な問い。ここでは公開は、講師が事前に立ち上げた `Ingress` オブジェクトと、マシンが応答し始めた瞬間に中身が満たされるドメインです。

**vSphere のほうが便利なところ、正直に。** 仮想マシンそのものの管理という点では、vCenter はまだ豊かで、そうでないふりをするのは意味がありません。

| 何 | vSphere | Cozystack |
|---|---|---|
| テンプレートとクローン作成 | 成熟しており、ゲストのカスタマイズつき | ディスクのクローンはあるが、カスタマイズウィザードはない |
| スナップショット | 慣れ親しんだもの、ツリーつき | あるが、その周辺のエコシステムはより若い |
| ライブマイグレーション | vMotion、長年かけて磨かれたもの | あるが、使われる頻度は低く、実戦での検証も少ない |
| VM フォルダに対する権限 | 粒度が細かい | テナントレベルの権限、フォルダはない |
| コンソールとゲストツール | VMware Tools、テレメトリすべて | qemu-guest-agent、データはより少ない |

**もっぱら** 仮想マシンだけが必要なら — 正直な答えは、移行のための移行には意味がない、というものです。見返りが現れるのは、仮想マシンの隣に何か他のものが必要なところです。クラスター、データベース、キュー、レジストリ、オブジェクトストレージ、ドメインでの公開など。そのとき、五つの権限モデルを持つ五つの製品の代わりに、一つのカタログがあり、2011年の名簿はそのなかで他のすべての隣に並びます。
