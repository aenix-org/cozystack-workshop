## なぜこれが重要か

「Pass」サービスは、たった一種類の通行証——特定の日付のための一回限りの通行証——で展開されました。
1 か月後、クライアントが改良の要望を持って戻ってきました。どれももっともな内容です。

| 通行証の種類 | ほかに何が必要か |
|---|---|
| 一回限り | 日付、入口 |
| 週間 | 開始/終了の期間、入口のリスト、バッジが返却されたかどうかの印 |
| 車両 | ナンバープレート、車種、トレーラーの有無、重量、駐車スペースの番号 |
| 団体 | 組織、担当者、付き添い、年齢付きの参加者リスト |

列が固定されたテーブルでは、この問題には二つの解決策があり、そのどちらも良くありません。

**解決策その一：すべての列を持つ単一のテーブル。** `car_plate`、`car_model`、`trailer`、
`weight_kg`、`parking`、`valid_from`、`valid_to`、`badge_returned`、`organization`、`contact`、
`escort` を追加します——すると一回限りの通行証は 15 のうち 11 のフィールドが空になります。半年も
すれば列は 30 になり、どの列がどの種類で必須なのか誰も覚えておらず、最初の `NOT NULL` フィールドが
シナリオの半分を壊します。

**解決策その二：種類ごとにテーブル。** 一つの代わりに四つのテーブル、さらに、警備が門で統合された
リストを見せられるよう、それらを結び付ける五つ目。新しい通行証の種類が増えるたびに、スキーマの
マイグレーション、リリース、そして承認が必要になります。そして「今日のすべての通行証を見せて」という
クエリは四つの部分の `UNION` になり、五つ目を追加するときには手直しが必要になります。

**団体通行証の参加者リストはそのどちらにも収まりません。** 長さが可変なので、通行証への参照を持つ
さらにもう一つのテーブルが必要になります。

第三の道があります：すべてのレコードが同じ形を持つことを要求しないストアです。このラボでは MongoDB を
立ち上げ、四つの異なる形の通行証を四つ入れ、それらをまたいで検索します。そしてそのために何を支払うのかを
正直に見ていきます——なぜなら私たちは確かに支払っており、しかも少なからず支払っているからです。

Kubernetes と MongoDB の用語は、このラボで初めて登場したときに説明され、いくつかは下の小さな用語集に
まとめてあります。

## ミニ用語集

| 用語 | 何か | 〜に似ているが |
|---|---|---|
| **ドキュメント** | 一件のレコード。フィールド、入れ子のオブジェクト、リストの集まり | **テーブルの行** に似ているが、隣のレコードが違うフィールドの組を持っていてもよく、それはエラーではない |
| **コレクション** | ドキュメントの集まり | **テーブル** に似ているが、デフォルトではスキーマを持たない。スキーマを追加することはできるが、それは別途の判断 |
| **BSON** | ドキュメントが保存されるバイナリ形式 | JSON に似ているが、型を持つ：日付は文字列ではなく日付 |
| **レプリカセット** | 複数のコピー。一つがプライマリで、残りが引き継ぐ | **HA クラスター** に似ているが、コピー同士が投票し合うので、奇数個必要 |
| **`mongosh`** | MongoDB のコマンドシェル | **PowerCLI** に似ているが、クエリ言語ではなく完全な JavaScript |

このラボに残るほかの言葉——_id、シャーディング、ドット区切りのフィールド記法、スパースインデックス、
スキーマバリデータ、$lookup——は、進みながら、それが最初に必要になるステップで導入します。今それらを
暗記する必要はありません：動作から切り離されては頭に残りません。

<details>
<summary><b>リスト全体を一度に見たい場合</b></summary>

| 用語 | 何か | 〜に似ているが |
|---|---|---|
| **`_id`** | ドキュメントの一意なキー | **主キー** に似ているが、設定しなければ自動で作られる |
| **シャーディング** | データを複数のレプリカセットに分割すること | 信頼性ではなく容量に関わる話 |
| **ドット区切りのフィールド記法** | ドットを介して入れ子のフィールドに到達する：`car.plate` | **フォルダ内のファイルパス** に似ているが、リストの中にも到達する：`members.age` |
| **スパースインデックス** | フィールドが存在するドキュメントだけを含むインデックス | フィールドが一部のレコードにしかない場合の当然の必需品 |
| **スキーマバリデータ** | ドキュメントが満たすことを求められるルール | **保存前のフォーム検証** に似ているが、手動で、しかも後付けで有効にする——デフォルトではスキーマはない |
| **`$lookup`** | 別のコレクションからデータを引き込む方法 | **JOIN** に似ているが、一方向的で、明らかにコストが高い：結合はオプティマイザが選ぶのではなく、力任せに実行される |

</details>

## ラボのフォルダに何があるか

ファイルはすべてすでに手元にあります——リポジトリと一緒に受け取っています。新しく作ったり打ち直したり
するものはありません：以下で `kubectl apply -f ファイル名.yaml` と書かれているところでは、ファイルは
ここから取られます。

```bash
cd labs/10-mongodb
```

| ファイル | 何か | いつ必要になるか |
|---|---|---|
| `mongodb.yaml` | ドキュメントデータベースの注文——ダッシュボードのボタンと同じもの | これは `lab` クラスターではなく **テナントの中で** 適用する |
| `passes.js` | 異なる種類の通行証でデータベースを満たす：一回限り、週間、車両 | データベースの中で実行する |
| `validator.js` | ドキュメントを検証するルール——ゴミがデータベースに入らないように | 次に実行する |
| `check.sh` | 異なる形のドキュメントが並んで存在し、不適合なものが拒否されることのチェック | ラボの最後に実行する |

## ステップ 1. MongoDB を注文する

📍 **どこで:** ブラウザで、Cozystack のダッシュボードで、自分のテナントで。

テナント → **Create application** → `MongoDB`。

| 項目 | 値 | なぜ |
|---|---|---|
| Name | `passes` | 短く——あとでアドレスに打ち込むことになる |
| Version | `v8` | 現行のブランチ |
| Replicas | **1** | 学習用のテスト環境。本番でなぜ三つなのかはすぐ下に |
| Size | `5Gi` | 四つのドキュメントは数バイト、残りは余裕分 |
| Storage class | `replicated` | データは異なるノードに三つのコピーで置かれる |
| Resources preset | `s1.small` | プロセッサ 1、2 GB |
| Sharding | off | データが一台のサーバーに収まらなくなったらシャーディングする |
| Users | `passapp` ユーザー、パスワードを **明示的に** 設定する | このユーザーで作業する |
| Databases | `passes` データベース、`passapp` を admin ロールで | ロールがないとユーザーは受け入れられない |
| External | off | 外向きには公開しない |

⚠️ **必ずパスワードを手で設定し、書き留めておいてください。** 項目を空のままにすると、チャートが
自分でパスワードを生成し——それをダッシュボードに表示されない Secret に入れてしまいます。接続できない、
動いているデータベースだけが手元に残ります。

これ以降、何度も出会う二つの言葉があります。**チャート** とは、プラットフォームがサービスをデプロイ
するために使う設計図です：テンプレートの集まりに、フォームで記入した値を加えたもの。いちばん近いのは
セットアップウィザード付きの仮想マシンのテンプレートです。**Secret** とは、パスワードや鍵を保持する
クラスターのオブジェクトです。ダッシュボードではアプリケーションのカードの別タブとして表示されます。

⚠️ **ロールのないユーザーはデプロイ時の失敗を意味します。** Users セクションで `passapp` を作っても、
Databases セクションでどのデータベースにもロールを与えないと、チャートは "user is not assigned to any
database role" というエラーで止まります。これは故障ではなく、役に立たないユーザーを防ぐ安全策ですが、
メッセージはすぐには見つかりません。

⚠️ **単一のコピーは通常の形の MongoDB ではありません。その理由を理解しておく価値があります。**
MongoDB は三つのレプリカの集まりを前提に設計されています：投票でプライマリを選び、一つを失っても作業は
止まりません。投票には過半数が必要なので、コピーの数は奇数にされます。単一のコピーでは一緒に投票する
相手がいないため、これに対してチャートは特別な `unsafeFlags` モードを有効にします。ラボではこれが
テスト環境のリソースを節約します。本番では決してこのやり方をしてはいけません。

### もう少し詳しく：mongodb.yaml の中身

ラボのフォルダには `mongodb.yaml` があります：

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: MongoDB
metadata:
  name: passes
  namespace: tenant-workshopXX
spec:
  replicas: 1
  size: 5Gi
  storageClass: replicated
  resourcesPreset: s1.small
  version: v8
  external: false
  sharding: false
  users:
    passapp:
      password: YourPasswordHere
  databases:
    passes:
      roles:
        admin:
          - passapp
  backup:
    enabled: false
```

`namespace: tenant-workshopXX` — **マネージドサービスは、ラボ 0 の lab クラスターではなく、
管理クラスター上のあなたのテナントの中に存在します。** これは二つの異なるクラスターです。

`users` と `databases` は互いに結び付いた二つのマップで、両者のつながりは必須です。`users` は
アカウントを列挙し、`databases` はデータベースと、その中で誰が何をできるかを列挙します。`roles.admin` は
一つのデータベース内で読み取り・書き込み・構造変更の権利を与えます。`roles.readonly` は読み取りのみです。

⚠️ ユーザーはサービス用のデータベース `admin` で作られますが、権限はあなたのデータベースで与えられます。
だからこそ接続文字列には `authSource=admin` が必要になります——これについては次のステップで別途詳しく。

`sharding: false` — 普通のレプリカセット。シャーディングを有効にすると config サーバーとルーターが
加わります：私たちには不要なデータ分割のために、余分な Pod が三つか四つ。

このファイルは **lab クラスターではなく** テナントに適用されます——つまりアクセスファイルもテナント用の
ものである必要があります。bastion 上ではすでに設定済みです——`~/.kube/config`（どのラボでも同じパス、
トークンベースのアクセス、ブラウザは開きません）。

では、データベースをテキストとして注文します。コマンド自身は何もインストールしません：注文を
プラットフォームに手渡し、プラットフォームが自分の側で必要なものすべてを立ち上げます。

```bash
# apply = 「ファイルに書かれた状態にクラスターを合わせる」。
#   --kubeconfig ~/.kube/config  どのアクセスファイルを使うか。指定しないと kubectl は
#                                  デフォルトのアクセスを使い、別のクラスターへ迷い込んでしまう
#   -f mongodb.yaml                どのファイルを適用するか（-f = file）
kubectl --kubeconfig ~/.kube/config apply -f mongodb.yaml
```

**表示されるはず** — `mongodb.apps.cozystack.io/passes created`。`created` という語は、注文が
受理されたことを意味するのであって、データベースが準備できたことではありません。

準備には 3〜5 分かかります：サーバーが立ち上がり、レプリカセットが初期化され、ユーザーが作られます。
進み具合はこうやって見られます：

```bash
# get = 「そこに何があるか見せて」。READY 列を見れば、注文が稼働状態に達したかどうかがわかる。
#   -n tenant-workshopXX  どの namespace を見るか（namespace はクラスター内部の区画であり、
#                         あなたのテナントはまさにこうした独立した namespace）
kubectl --kubeconfig ~/.kube/config get mongodb passes -n tenant-workshopXX
```

⚠️ **ダッシュボードの `mongodb-passes-credentials` という Secret は、最初の数分間はパスワードが
空になっています。** これはサービスアカウント `databaseAdmin` の認証情報を保持しており、チャートが
それを埋めるのは、オペレーター（注文を稼働状態へ導き、その後も見張り続けるプラットフォームのプログラム）が
ユーザーを作った後——つまり、状態をリコンサイルする次の周回のときだけです。数分待ってページを更新して
ください。このアカウントは必要ありません：私たちは `passapp` で作業し、そのパスワードはあなた自身が
設定しました。

## ステップ 2. 作業用の Pod を作る

📍 **どこで:** bastion 上、lab クラスターで。

配置は、マネージドサービスに関するほかのラボと同じです。

**MongoDB は管理クラスター上のあなたのテナントの中に存在します。** テナントでのあなたのロールでは、
サービスの注文と削除はできますが、そこで自分の Pod を動かしたりポートフォワードしたりはできません。

**あなたの作業の場は、ラボ 0 の lab クラスターです。** そこから、内部アドレスを通じて向かいます：

```
mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017
```

| 部分 | 意味 |
|---|---|
| `mongodb-` | Cozystack のカタログがアプリケーション名に付けるプレフィックス |
| `passes` | ダッシュボードで設定した名前 |
| `-rs0` | レプリカセットの名前。オペレーターは最初のセットのサービスをこう名付ける |
| `tenant-workshopXX` | あなたのテナント。自分の番号に置き換える |
| `svc.cozy.local` | 管理クラスターの内部名のゾーン |
| `27017` | MongoDB の標準ポート |

**Pod** とは Kubernetes における実行の最小単位です：常に同じノード上に存在し、単一のアドレスを共有する
一つまたは複数のコンテナ。いちばん近いたとえは一つのタスクのために立ち上げる仮想マシンですが、数秒で
作られ、惜しげもなくシャットダウンされる点が違います。そうした Pod を `mongo:8.0` イメージで立ち上げます：
その中には `mongosh`——MongoDB のコマンドシェル——が入っており、bastion にインストールする必要は
ありません。

データベースのアドレスは、ユーザー名とパスワードと合わせて一行で書かれます——これを接続文字列と
呼びます。コマンドを打つ前に、これを一通り見ていきましょう。

<details>
<summary><b>接続文字列を一通り見る</b></summary>

```
mongodb://passapp:password@host:27017/passes?authSource=admin&directConnection=true
```

`mongodb://` — スキーム。続いてユーザー名、パスワード、アドレス、ポート。

ポートの後の `/passes` — **デフォルトのデータベース**。接続すればすぐにその中にいて、別途コマンドは
要りません。

`authSource=admin` — **アカウントそのものをどのデータベースで探すか。** `passapp` ユーザーはサービス用の
データベース `admin` で作られ、その権限は `passes` で与えられます。このパラメータがないと、ドライバは
`passes` でアカウントを探しに行き、見つけられず、"Authentication failed" を返します——これは
「パスワードが違う」ように見えるメッセージで、調査を誤った方向へ導きます。これはマネージド MongoDB への
最初の接続で最もよくある間違いです。

`directConnection=true` — 「このサーバーに直接つなぎ、レプリカセットの構成を割り出そうとするな」。
このパラメータがないと、ドライバはサーバーにセットの他のメンバーは誰かと尋ね、メンバーの内部名を返して
もらいますが、それは外部から常に解決できるとは限りません。単一のコピーでは割り出すものがないので、直接
そう言うほうが簡単です。三つのコピーがある本番では逆です：このパラメータは設定しません。そこで欲しいのは、
まさに古いプライマリが倒れたときの新しいプライマリへの自動切り替えだからです。

**なぜアドレスとパスワードを、コマンドに直接ではなく Pod の変数に入れるのか。** `kubectl exec` に
書いたものはすべて、シェルの履歴とノード上のプロセス一覧に残ります。Pod の変数は一度だけ設定され、以降
パスワードはコマンドに現れません。

これで問題が完全に解決するわけではないので、先に正直に言っておきます：`--env` を通じて渡された値は
Pod の spec に残ります——あなたの namespace で Pod を読む権利を持つ者なら誰にでも見え、クラスターの
データベースに置かれ、監査ログに載ります。学習用のテスト環境では許容できますが、本番では許容できません：
本番ではパスワードを Secret に入れ、`envFrom` を通じて組み込みます。まさにそれが Secret に関するラボの
主題です。

</details>

Pod を立ち上げます。`workshopXX` を自分のテナント番号に、`YourPasswordHere` を実際のパスワードに
置き換えてください：

```bash
# KUBECONFIG — kubectl がどのアクセスファイルを使うか。ここでは lab 0 の
# lab クラスター：自分の Pod を起動できるのはこの中だけで、テナントにはこれでは入れない。
export KUBECONFIG=~/lab.kubeconfig

# run = 「単一の Pod を作り、その中でこのイメージを実行する」。重要なフラグ：
#   --image=mongo:8.0        何を実行するか。イメージには mongosh シェルが含まれている
#   --restart=Never          Deployment ではなく、あくまで単一の Pod を作る。さもないと
#                            クラスターは Pod が終了するたびに再起動してしまう
#   --env=MONGO_URI=...      Pod 内部の環境変数。パスワードはこの中に留まり、
#                            以降のコマンドで毎回繰り返さずに済む
#   --command -- sleep 86400 コンテナを何で動かし続けるか。mongo イメージはデフォルトで
#                            データベースサーバーを起動してしまう——それは不要で、必要なのは
#                            中に入れる生きたコンテナ。86400 秒は 1 日
kubectl run mongo-workbench \
  --image=mongo:8.0 \
  --restart=Never \
  --env=MONGO_URI="mongodb://passapp:YourPasswordHere@mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017/passes?authSource=admin&directConnection=true" \
  --command -- sleep 86400

# wait = 「条件が満たされるまで制御を返さない」
#   --for=condition=Ready  Pod 自身が準備完了を報告するまで待つ
#   --timeout=180s         永遠にぶら下がらず、エラーを返すまでどれだけ待つか
kubectl wait --for=condition=Ready pod/mongo-workbench --timeout=180s
```

**表示されるはず** — `pod/mongo-workbench created`、続いて
`pod/mongo-workbench condition met`。

では、毎回これをすべて打たなくて済むよう短いコマンドを用意し、データベースへの接続を確認します：

```bash
# mo — ターミナルのウィンドウを閉じるまで生きているショートカット：これがシェルで
# 自分のコマンドを宣言するやり方。
#   exec        すでに動いている Pod の中で何かを実行する
#   -i          標準入力を中へ渡す：これがないとプログラムを流し込めない
#   sh -c '...' Pod 内でシェルを実行し、$MONGO_URI を Pod 自身に展開させる。
#               クォートをシングルにしているのはわざと：変数を展開すべきはあなたの
#               ターミナルではなく Pod——さもないとパスワードがコマンド履歴に残ってしまう
#   --quiet     mongosh の挨拶を出さず、答えだけを残す
mo() { kubectl exec -i mongo-workbench -- sh -c 'mongosh --quiet "$MONGO_URI"'; }

# ping — サービス用のリクエスト、「生きてる?」。何も読み書きせず、接続と
# 認証情報が受け入れられたことを確認する。| 記号はこの行を mongosh の入力へ送る
echo 'db.runCommand({ ping: 1 })' | mo
```

**表示されるはず** — `{ ok: 1 }`。

`mongosh` はプログラムを標準入力から読むので、この同じコマンドでファイルまるごとを飲み込めます：
`mo < passes.js`。

⚠️ **答えが `Authentication failed` の場合** — 接続はあるが認証情報が違います。順に確認してください：
接続文字列の `authSource=admin`；パスワードがダッシュボードで設定したものと一致するか；ユーザー名が
`passapp` か。修正した文字列で Pod を作り直すには：`kubectl delete pod mongo-workbench` を実行して
最初からやり直します。

⚠️ **答えが `getaddrinfo ENOTFOUND` の場合、または接続がぶら下がる場合** — 名前が解決されていません。
おそらく `workshopXX` を自分の番号に置き換えていないか、ダッシュボードのアプリケーションがまだ準備
できていません。

データを調べるには、一度に一コマンドずつではなく、生きたシェルの中でのほうが便利です——シェルは開いた
ままで、その中でクエリを次々に打っていけます：

```bash
# -i ではなく -it：t が加わる——「ターミナルをちょうだい」。だから入力プロンプトや、
# 上矢印でのコマンド履歴、ハイライトが使える。t がないとシェルは黙って入力を待つだけ。
kubectl exec -it mongo-workbench -- sh -c 'mongosh "$MONGO_URI"'
```

**表示されるはず** — `passes>` という形のプロンプト：あなたが降り立ったデータベースの名前です。

これ以降、本文中のコマンドは、このシェルで打つとおりの形で示されます。抜けるには——`exit`。

## ステップ 3. 四つの異なる形の通行証を四つ入れる

📍 **どこで:** bastion 上、lab クラスターで。

`passes.js` ファイルは `mongosh` 用のプログラムです：四つの通行証をデータベースに追加し、ドキュメントが
何件になったかを表示します。あらかじめテーブルを一つも作る必要はなく、その理由の説明はすぐ下にあります。

```bash
cd labs/10-mongodb
# < 記号はファイルの中身をコマンドの入力へ流し込む——mongosh シェルでファイルの全文を
# 手で打ち込んだのと同じこと。
mo < passes.js
```

**表示されるはず** — `コレクション内のドキュメント数: 4`。

<details>
<summary><b>入れたものを一通り見る</b></summary>

まず気づく価値があるのは：**`CREATE TABLE` がなかった** ことです。`passes` コレクションは最初の挿入の
瞬間に生まれました。スキーマを持ちません——つまり、デフォルトでは MongoDB は、ドキュメントがどんな
フィールドを持ってよいかについて意見を持ちません。

では、ドキュメントへ。

**一回限りの通行証** — 最も短い形：

```js
  {
    type: "一回券",
    guest: "田中 太郎",
    host: "petrov@corp.example",
    entrance: "北口",
    valid_on: ISODate("2026-09-01T09:00:00Z"),
    purpose: "面接"
  }
```

六つのフィールド、すべてスカラー。テーブルなら普通の行です。

`ISODate(...)` は文字列ではなく、まさに日付です。MongoDB はドキュメントをバイナリの BSON 形式で保存し、
そこでは値が型を持ちます：日付、整数、浮動小数点、真偽値、バイナリデータ。これはただの JSON との重要な
違いです：日付でなら比較や並べ替えができますが、文字列 `"2026-09-01"` でできるのは、書き方に恵まれた
ときだけです。

**週間の通行証** — `valid_on` の代わりに今度は `valid_from` と `valid_to` があり、単一の入口の代わりに
`entrances` は今や **リスト** です：

```js
    entrances: ["北口", "南口"],
    badge_returned: false
```

フィールドの中に直接リスト。テーブルなら、別途の「通行証 — 入口」テーブルか、あるいは後で誰もまともに
検索できないカンマ区切りの文字列が必要になったでしょう。

一回限りの通行証には `badge_returned` フィールドがそもそもありません。`NULL` でもなく、空でもなく——
**このドキュメントにはそんなフィールドが存在しない** のです。これらは別のことであり、検索の仕方も
異なります。

**車両の通行証** — **入れ子のオブジェクト** が現れました：

```js
    car: {
      plate: "品川 300 あ 12-34",
      model: "トヨタ ハイエース",
      trailer: false,
      weight_kg: 3500
    },
```

車両に関わるものすべてが単一の `car` フィールドの中に収まっています。これは中に JSON を入れた文字列では
なく、れっきとした構造です：`car.plate` で検索でき、それにインデックスを張れます。

**団体の通行証** — **オブジェクトのリスト**：

```js
    members: [
      { name: "伊藤 修", age: 16 },
      { name: "山本 真理", age: 15 },
      { name: "中村 勇", age: 17 }
    ]
```

可変長の参加者リストで、それぞれが自分のフィールドを持ちます。そして——注目してください——この
ドキュメントには **`guest` フィールドがありません**：来客の代わりに組織と担当者があります。この
ドキュメントの形は、ほかと一つのフィールドで違うのではなく、本質的に異なります。

これこそ、ドキュメントモデルが存在する理由です。空の列もなく、四つのテーブルもなく、それらを結び付ける
五つ目もありません。

</details>

## ステップ 4. 異なる形のドキュメントをまたいで検索する

📍 **どこで:** 作業用 Pod の中の `mongosh` シェルで。

警備と管理が必要とするものはすべて、普通のクエリです。どれも同じように読めます：`db` は接続している
データベース、`passes` はその中のコレクション、続いてドットの後に動作が来て、括弧の中に絞り込み条件が
入ります。条件は常にオブジェクトとして書かれます：「フィールド — どんな値であるべきか」。

**特定の日付のすべての通行証：**

```js
// find = 「条件に一致するドキュメントを見せて」
// { valid_on: ISODate(...) } — ドキュメントの valid_on フィールドがちょうどこの日付と
// 等しくなければならない。ISODate は文字列ではなく日付：比較は綴りではなく時刻で行われる
db.passes.find({ valid_on: ISODate("2026-09-02T07:30:00Z") })
```

**表示されるはず** — 一件のドキュメント、クズネツォフの車両通行証。

**車両の通行証だけ：**

```js
// 普通の文字列フィールドに対する条件：完全一致で、ここに大文字小文字の区別なしはない
db.passes.find({ type: "車両券" })
```

**ナンバープレートで検索する——ドットを介して入れ子のオブジェクトの中へ到達する：**

```js
// "car.plate" — ドキュメントへのパス：car オブジェクト内部の plate フィールド。
// パスを囲むクォートは必須。さもないと JavaScript はドットを自分流に解釈してしまう
db.passes.find({ "car.plate": "品川 300 あ 12-34" })
```

<details>
<summary><b>なぜこれが機能するのか、そして「中に JSON を入れた文字列」とどう違うのか</b></summary>

`"car.plate"` はフィールドへのパスのドット区切り記法です。MongoDB はドキュメントの構造を理解しており、
入れ子のオブジェクトをひとかたまりのテキストとして保存するのではなく、その中へ到達できます。

違いは実際的です。もし `car` がリレーショナルなテーブルに、中に JSON を入れた `TEXT` 列として置かれて
いたら、プレートでの検索は `LIKE '%品川 300 あ 12-34%'` を意味します——インデックスなしのフルスキャンで、
誤検出付き。ここではインデックスを張れる普通の条件であり、実際に張ります。

⚠️ `"car.plate"` を囲むクォートは必須です：それがないと JavaScript はドットをオブジェクトのプロパティへの
アクセスとして読み、何を求められているのか理解できません。

</details>

**複数の入口で有効な通行証：**

```js
// entrances は文字列ではなくリスト：["北口", "南口"]。条件は普通のフィールドと
// 同じように書き、MongoDB がリストの各要素に対して自分で照合してくれる
db.passes.find({ entrances: "南口" })
```

注意：条件は、あたかも `entrances` が値 `"南口"` を持つ普通のフィールドであるかのように書かれて
いますが、実際にはリストです。**フィールドがリストなら条件は各要素に対して照合されるべきだと、MongoDB は
自分で理解します。** 「含む」のための別の構文は要りません。

**未成年を含む団体の通行証：**

```js
// members.age というパスはオブジェクトのリストの内部——各参加者の age フィールドへ導く。
// $lt = より小さい。$ の付いた条件は値ではなく比較の仕方：
// 「フィールドは 16 より小さくなければならない」であって「16 と等しくなければならない」ではない
db.passes.find({ "members.age": { $lt: 16 } })
```

ドット区切りのパスはオブジェクトのリストの中へも効きます：条件は各参加者に対して照合されます。`$lt` —
「より小さい」。この種の条件は二十ほどあります：`$gt`、`$gte`、`$in`、`$ne`、`$exists`、`$regex` など。

**そもそも車両が指定されているすべての通行証：**

```js
// $exists は値についてではなく、ドキュメントにそのフィールドが存在するかどうかを問う：
// 「このドキュメントにそもそも car フィールドはあるか?」
db.passes.find({ car: { $exists: true } })
```

`$exists` こそ、「フィールドが存在しない」と「フィールドが空」の、まさにその区別です。テーブルでは
この問いは生じません：列は常にそこにあり、問題は `NULL` かどうかだけです。

**管理向けの集計——各種類の通行証が何件あるか。** ここではクエリはドキュメントを選ぶのではなく、それらに
わたって合計を計算するので、コマンドが異なります——`aggregate`。打つ前に一通り見ていきましょう。

<details>
<summary><b>集約パイプラインを一通り見る</b></summary>

MongoDB における集約は **パイプライン** です：ステージのリストで、そのそれぞれが前のステージの結果を
入力として取ります。シェルにおけるコマンドのパイプラインのようなもので、一つの出力が次の入力へ渡ります。

`$group` — グループ化。`_id: "$type"` は「グループ化のキーは `type` フィールドの値」を意味します。名前の
前のドル記号は「これは文字列ではなくフィールドへの参照だ」と告げます。`$sum: 1` — 各ドキュメントにつき
1 を加える、つまりそれらを数えます。

`$sort: { count: -1 }` — 降順に並べる。`-1` は「降順」、`1` は「昇順」。

SQL での同じ結果は — `SELECT type, count(*) FROM passes GROUP BY type ORDER BY 2 DESC`。より短く、より
馴染みがあり、ここでは正直な比較は MongoDB に不利に働きます：そのクエリ言語のほうが冗長で、習得により
時間がかかります。

</details>

```js
// aggregate = 「ドキュメントを一連のステージの連鎖に通す」。ステージは順に並び、
// それぞれ前のステージが生み出したものを受け取る：
//   $group — type フィールドの値でドキュメントをグループに分け、それぞれを数える
//   $sort  — グループを count で並べる。-1 は「降順」の意味
db.passes.aggregate([
  { $group: { _id: "$type", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
])
```

**表示されるはず** — `{ _id: '一回券', count: 1 }` という形の四行。

## ステップ 5. 大半が持たないフィールドへのインデックス

📍 **どこで:** 作業用 Pod の中の `mongosh` シェルで。

警備は毎日ナンバープレートで検索します。この検索が今どれだけのコストなのかを見てみましょう：クエリは
前と同じですが、ドキュメントの代わりに、データベースがそれらをどう探したかについてのレポートを求めます。

```js
// explain = 「ドキュメントを寄こすのではなく、どうやって探したかを教えて」
//   "executionStats"     レポートのモード：計画だけでなく、実際に何が起きたか
//   .executionStats      答えの全部を読まなくて済むよう、ちょうどこのセクションだけ取り出す
// レポートでは totalDocsExamined を見る——1 件を返すために
// データベースが何件のドキュメントを読んだか
db.passes.find({ "car.plate": "品川 300 あ 12-34" }).explain("executionStats").executionStats
```

**表示されるはず** — `totalDocsExamined` がコレクション内のドキュメント数と等しくなります。データベースは
一件を見つけるために全部に目を通しました。四件のドキュメントでは気づかれませんが、四十万件ではもう
気づかれます。

インデックスを作ります——データベースが、必要なドキュメントを全部を順に読むことなく見つけるために使う、
別途の構造です：

```js
// createIndex = 「このフィールドにインデックスを作り、これ以降は自分で保守し続けて」
//   { "car.plate": 1 }   どのフィールドに作るか。1 は「昇順」
//   name: "car_plate"    インデックスの名前。後で見分けて削除できるように
//   sparse: true         フィールドを持つドキュメントだけがインデックスに入る
db.passes.createIndex({ "car.plate": 1 }, { name: "car_plate", sparse: true })

// 同じレポートを繰り返し、前のものと比べる
db.passes.find({ "car.plate": "品川 300 あ 12-34" }).explain("executionStats").executionStats
```

**表示されるはず** — `totalDocsExamined` が 1 に等しくなり、計画では `COLLSCAN` の代わりに `IXSCAN` が
現れます。これらは検索方法の名前です：`COLLSCAN` はコレクション全体のスキャン、`IXSCAN` はインデックスに
よる参照です。

<details>
<summary><b>スパースインデックスとは何か、そしてなぜここにあるのか</b></summary>

`{ "car.plate": 1 }` — どのフィールドに作るか。`1` は「昇順」、`-1` は降順を意味します。完全一致の検索では
方向は関係ありませんが、並べ替えでは関係します。

`sparse: true` — **フィールドを持つドキュメントだけがインデックスに入ります。**

このフラグがなければ、MongoDB は車両のない三つのドキュメントにも「フィールドなし」という値でインデックスの
エントリを作っていたでしょう。インデックスはほぼ二倍の大きさになり、それらのエントリは何の役にも立ちません：
「車両が指定されていない」という基準で通行証を探す人はいません。

実際の通行証台帳では、およそ一割が車両の通行証です。スパースインデックスは普通のものより十倍小さく、保守も
十倍安上がりになります。

⚠️ **スパースインデックスには代償があり、それを知っておく必要があります。** このインデックスを通じて
このフィールドで並べ替えると、フィールドのないドキュメントが失われます——それらはインデックスに入って
いないからです。そうした場合、MongoDB は自らインデックスを捨ててスキャンに戻ります。厄介なのは、これが
黙って起こることです。

**そしてここで、このステップの要点です。** すべての通行証の種類を一つのテーブルに入れたリレーショナル
データベースでは、`car_plate` へのインデックスは、行の九割が `NULL` である列に張らなければなりません。
一部の DBMS はそうした行もインデックスに入れてしまい、肥大化します。これは部分インデックスで回避されます
——`sparse` と同じ種類の仕組みですが、どこでも使えるわけではなく、すぐには自明でもありません。

つまり問題は一つの同じものです。違いは、ここではそれが「すべての種類を一つのテーブルに入れよう」の副作用
として生じない点です：一部のレコードのために作らねばならなかった列が、私たちにはありません。

</details>

## 予見できる失敗 · リストに載らない通行証

作業を続けましょう。門の係員がもう一つ一回限りの通行証を発行しました——急いで書いたスクリプトを通じて：

```js
// insertOne = 「ドキュメントを 1 件追加する」。どんなフィールドが入っているか、データベースは尋ねない
db.passes.insertOne({
  tipe: "一回券",
  guest: "小林 誠",
  host: "petrov@corp.example",
  data: ISODate("2026-09-04T09:00:00Z")
})
```

挿入は成功しました：`acknowledged: true`（「受理」）と、新しい `_id`——データベースが自分で考え出した、
ドキュメントの一意なキー——が返ってきました。今ドキュメントが五件あることを確認しましょう：

```js
// countDocuments = 「条件に一致するドキュメントを数える」。
// 空の波括弧は制限のない条件、つまり「すべて」
db.passes.countDocuments({})
```

五件。では警備が毎朝すること——一回限りの通行証のリストを開きます：

```js
// 検索のステップと同じ type による絞り込み：type フィールドが
// "一回券" と等しい通行証を見せる
db.passes.find({ type: "一回券" })
```

> **読み進める前に、立ち止まって考えてください。**
>
> 何件の通行証が返ってきましたか? 五件目はどこ? 同じ間違いをリレーショナルデータベースでしたら何が
> 起きるか——そしてなぜそのほうが良いのか?

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

返ってきた通行証は二件ではなく一件です。来客のニコラエフが到着し、警備は彼を見つけられず、それを
解きほぐすのにしばらくかかります——なぜならドキュメントは **存在し**、**正常に挿入され**、どこにも
エラーが記録されなかったからです。

原因は二つのタイプミスです：`type` の代わりに `tipe`、`valid_on` の代わりに `data`。MongoDB はそれらに
気づきませんでした。なぜなら **コレクションにはスキーマがなく、したがってどのフィールドが正しいかに
ついての意見もない** からです。MongoDB にとって `tipe` は、ほかのどれとも同じく正当なフィールドです。

被害者を探しましょう——`type` フィールドがそもそもないドキュメントです：

```js
// $exists: false — 前のステップの逆：「フィールドがドキュメントにない」。
// こういうクエリは手元に置いておく価値がある：スキーマの外に何が溜まったかを見せてくれる
db.passes.find({ type: { $exists: false } })
```

リレーショナルデータベースでは、`tipe` 列を伴う `INSERT` は即座に失敗します：`column "tipe" does not
exist`。エラーはテストで表面化し、一週間後に門でではありません。**これがスキーマの柔軟性の主たる代償です：
かつてデータベースがしていたチェックを、今や誰かほかの者がしなければならない。**

**この間違いより広い教訓。** そしてここで、誤った結論を引き出さないことが重要です。正しい結論は
「ドキュメントデータベースは悪い」ではなく、「デフォルトでスキーマがないことは、スキーマがまったくない
ことを意味しない」です。あなたのデータには常にスキーマがあります：明示的に記述されているか、あるいは
人々の頭の中とコードの中に——誰もチェックしないところに——存在するかのどちらかです。

壊れたドキュメントを取り除き、検証を有効にしましょう。

</details>

type のないドキュメントを削除します：

```js
// deleteMany = 「条件に一致するドキュメントをすべて削除する」。条件は上の検索と
// 同じ——つまり、たった今見たものがそのまま削除される
db.passes.deleteMany({ type: { $exists: false } })
```

**表示されるはず** — `deletedCount: 1`。

では検証を有効にします——すべてのドキュメントが満たすことを求められるルールです。それは `validator.js`
ファイルにあります。適用する前に一通り見ていきましょう。

<details>
<summary><b>ルールを一通り見る</b></summary>

```js
db.runCommand({
  collMod: "passes",
  validator: { $jsonSchema: { … } },
  validationLevel: "strict",
  validationAction: "error"
});
```

`collMod` — 既存のコレクションの設定を変更する。バリデータは後付けで稼働中のコレクションに掛けられ、
何も止める必要はありません。

```js
      required: ["type", "host"],
```

必須のフィールド。**リストに何がないかに注目してください：`guest` です。** 団体の通行証には来客がなく、
その代わりに組織があります。ルールは、正当なドキュメントの形がそこを通り抜けられるくらいに広くなければ
なりません——そしてこの制約はすぐに感じられます：ドキュメントが多様であるほど、それら全部に共通して
要求できることは少なくなります。

```js
        type: {
          enum: ["一回券", "週間券", "車両券", "団体券"],
        },
```

リストの中の値だけ。五つ目の通行証の種類はルールの変更を要します——そしてそれは良いことです：変更が
意図的なものになります。

```js
        car: {
          bsonType: "object",
          required: ["plate"],
          …
        },
```

ルールは入れ子のオブジェクトにも効きます。`car` フィールドがあるなら、`plate` を持たなければなりません。
フィールドがなければ——要求はなく、ドキュメントは正当です。

```js
  validationLevel: "strict",
  validationAction: "error"
```

`strict` — すべての挿入とすべての更新を検証する。より穏やかな `moderate` もあります：新しいドキュメントと、
すでにルールを満たすものへの更新を検証し、古い不正なものはそのまま放っておきます。不整合がすでに積み
上がったコレクションで検証を有効にするのは、`moderate` を使ってです：まず悪化を止め、次に古いものを直し、
それから `strict` に切り替えます。

`error` — 拒否する。`warn` もあります：ログに記録し、それでも受け入れる。拒否を有効にする前に、一週間
どれだけ入ってくるかを観察するのに向いています。

</details>

ルールを適用します：

```bash
# passes.js と同じ手口：ファイルの中身が mongosh の入力に流し込まれる。
# ルールは稼働中のコレクションに掛けられる——データベースを止める必要はない
mo < validator.js
```

**表示されるはず** — `ルールを設定しました`。

同じタイプミスを繰り返してみます——今度はルールの監視下で：

```js
// tipe フィールドはルールにとって未知で、ドキュメントに必須の type がない。
// 以前なら、こういうドキュメントは黙ってコレクションに収まっていた
db.passes.insertOne({ tipe: "一回券", guest: "確認", host: "x@corp.example" })
```

**表示されるはず** — `MongoServerError: Document failed validation`。今度はタイプミスが通りません。

⚠️ **検証はすべてを捕まえるわけではなく、これははっきり言っておく必要があります。** ルールは `type`
フィールドが存在し、かつリストの中の値であることを求めます。**任意の** フィールドのタイプミス——`guest`
の代わりに `guestt`——は通してしまいます：ドキュメントは依然として正当で、ただ余分なフィールドが付いて
いるだけだからです。未知のフィールドをすべて禁じることもできますが（`additionalProperties: false`）、
そうすると新しいフィールドのたびにルールの編集が必要になり、避けようとしていたものにまっすぐ戻ります——
ちょっとしたことごとにスキーマのマイグレーション。どこに線を引くかはあなたが下す判断であり、それは常に
妥協です。

## ステップ 6. 正直に：ドキュメントモデルが負けるところ

📍 **どこで:** 作業用 Pod の中の `mongosh` シェルで。

スキーマの柔軟性が唯一の違いではなく、残りは MongoDB に有利ではありません。

<details>
<summary><b>通常の形の JOIN はない</b></summary>

課題：各通行証について、それを注文した従業員の電話番号と役職を引き込む。従業員は別のコレクション `staff`
にあり、email をキーとします。

SQL ならこれは一行です：`JOIN staff ON staff.email = passes.host`。

ここでは——パイプラインのステージ：

```js
db.passes.aggregate([
  // $lookup = 「各通行証について別のコレクションへ行き、そこからレコードを持ち帰る」
  { $lookup: {
      from: "staff",          // どこへ行くか——従業員のコレクション
      localField: "host",     // 通行証のどのフィールドを比較するか
      foreignField: "email",  // 従業員のどのフィールドと
      as: "host_info"         // 見つけたものをドキュメントにどんな名前で入れるか
  } },
  // 見つかったものは、一致が 1 件でも常にリストとして入る。
  // $unwind はリストを単一の値へと巻き戻す
  { $unwind: "$host_info" }
])
```

`staff` コレクションは私たちにはありません——クエリは何も返しません。これは構文の見本としてここにあるので
あって、ラボのステップとしてではありません。

機能します。ただし：

- `$lookup` は **一方向的** です：左側の各ドキュメントについて、右側で検索が走ります。これは結合方法を
  選ぶオプティマイザではなく、まさに力任せの参照です
- 結果は、一致が一件でも **リストとして** 返ってきます。だから、それを展開するための `$unwind`
- 二つより多くのコレクションを結合するのは、面倒で遅くなります
- シャーディングされた構成では、最近まで `$lookup` は制限付きで動いていました

だからこそ MongoDB の世界では、この課題は別のやり方で解かれます：**一緒に必要になるデータは、一緒に
保存する。** 依頼者の電話番号と役職は、通行証のドキュメントに直接書き込まれます。

そしてこれは、些細な不便ではなく、本物のトレードオフです：

| | `staff` への参照 | ドキュメント内のデータのコピー |
|---|---|---|
| 読み取り | `$lookup` が必要 | 一度の参照 |
| 従業員が電話番号を変えた | 一か所で直す | すべての通行証を辿らなければならない |
| 整合性 | データベースが見張る | アプリケーションが、つまりあなたが見張る |

リレーショナルデータベースには選択肢がありません——そこでは正規化と外部キーです。ここには選択肢があり、
それとともに責任があります。

</details>

<details>
<summary><b>外部キーはそもそもまったくない</b></summary>

やってみましょう：

```js
// host フィールドは意味の上では従業員を指す。そんな従業員は存在しない——
// データベースはこれを確認するだろうか? このドキュメントは前のステップのルールを満たす：type は
// あってリストの中にあり、host は文字列
db.passes.insertOne({ type: "一回券", host: "存在しない@corp.example", guest: "テスト" })
```

ドキュメントは挿入されます。そんな email の従業員はいませんが、データベースはそれを見ようとしません。

リレーショナルデータベースなら、外部キーがそうした行を拒否します。ここでは外部キーという概念がそもそも
まったく存在しません：**データの一貫性は、まるごとアプリケーションの肩にかかっています。** 前のステップの
バリデータはドキュメントの形をチェックしますが、あるフィールドの値が別のコレクションに存在することは
チェックできません。

実際には、これはこういう意味です：「そんな従業員はいるか」というチェックのひとつひとつを開発者が書き、
もし書き忘れたら——警備が依頼者に電話しようとしたときに判明します。

テスト用のドキュメントを取り除くのを忘れずに：

```js
// deleteOne = 「条件に一致するドキュメントを 1 件削除する」、一度に全部ではなく
db.passes.deleteOne({ host: "存在しない@corp.example" })
```

</details>

<details>
<summary><b>トランザクションはあるが、デフォルトではない</b></summary>

ここでは正確であることが重要です。なぜなら人々は MongoDB について、両方の方向で事実でないことをよく
言うからです。

**本当：** 複数ドキュメントのトランザクションは MongoDB に確かに存在します。レプリカセットではバージョン
4.0 からです。二つのドキュメントを、両方が適用されるか、どちらも適用されないかのどちらかになるように
変更できます。

**これも本当：** デフォルトでは存在しません。**単一のドキュメント** に対する操作はアトミックです。それ
以上が欲しいなら——セッションを開き、明示的にトランザクションを開始します：

```js
// セッションはデータベースとの独立した「会話」であり、その中でトランザクションを宣言できる
const s = db.getMongo().startSession();
s.startTransaction();          // ここから変更が積み重なるが、誰にも見えない
// … s.getDatabase("passes") を通した操作 …
s.commitTransaction();         // すべてを一度に適用する。すべてを一度に取り消すには——abortTransaction()
```

**そして三つ目の真実、最も実際的なもの：** MongoDB のトランザクションはリレーショナルデータベースより
高価で、時間制限があり、データモデル全体が、あなたはそれらをほとんど必要としないという前提の上に築かれて
います。もしあなたのシナリオがそれらを頻繁に必要とするなら、それはデータを別の形で配置すべきだった——
あるいは、ここではドキュメントデータベースが不要だという——しるしです。

通行証サービスにとってはこれは問題ではありません：通行証は単一のドキュメントであり、それに対するすべての
操作はそれ自体でアトミックです。給与計算にとっては問題であり、しかも大きな問題です。

</details>

<details>
<summary><b>スキーマの不整合はひとりでに忍び込む</b></summary>

これはタイプミスですでに見ました。しかし、もっと厄介な種類があります：エラーを通じてではなく、見落としを
通じて忍び込んだ不整合です。

一年後、コレクションの中で日付が三通りに保存されていることに気づきます：`ISODate` として、文字列
`"2026-09-01"` として、そしてタイムスタンプを持つ数値として——三つの異なるチームが別々の時期に書いた
からです。日付にわたる範囲検索はレコードの三分の一しか見つけられず、なぜなのか誰も理解できません。

コレクションに実際に何があるかは、こうやって見られます：

```js
db.passes.aggregate([
  // $$ROOT — ドキュメントの丸ごと全部。$objectToArray はそれを
  // 「フィールド名 — 値」のペアに分解し、フィールドをデータとして扱えるようにする
  { $project: { fields: { $objectToArray: "$$ROOT" } } },
  // ペアのリストを展開する：1 ペアが、次のステージの入力での 1 行になる
  { $unwind: "$fields" },
  // 2 つの属性で一度にグループ化する：フィールド名 (k) とその値の型 (t)、
  // そしてその組み合わせが何回現れたかを数える
  { $group: { _id: { k: "$fields.k", t: { $type: "$fields.v" } }, n: { $sum: 1 } } },
  { $sort: { "_id.k": 1 } }   // アルファベット順に。1 つのフィールドが自分の型の隣に並ぶように
])
```

このクエリは各ドキュメントを「フィールド — 値」のペアに分解し、値の型を判定し、各フィールドが各型で
何回現れたかを数えます。私たちの四つのドキュメントでは、揃った絵を見せます。一年経った実際のコレクション
では、誰も疑っていなかったものを見せます。これは、受け継いだデータベースを解きほぐすときに最も役立つ
クエリの一つです。

**持ち帰る価値のある要点：** スキーマバリデータは飾りでも「形だけの手続き」でもありません。ドキュメント
データベースでは、それがあなたと不整合の間に立つ唯一のものです。有効にするのは、切羽詰まってからではなく、
すぐにです。

</details>

**正直な比較の結論：**

| 課題 | リレーショナル | ドキュメント |
|---|---|---|
| 同じ形のレコード | 自然 | 可能ではあるが、なぜわざわざ |
| 異なる形のレコード | 空の列か、種類ごとのテーブル | 自然 |
| リストと入れ子 | 別々のテーブル | ドキュメント内のフィールド |
| 他のデータとの結合 | JOIN、オプティマイザ | `$lookup` かデータのコピー |
| 参照整合性 | データベースが見張る | アプリケーションが見張る |
| トランザクション | デフォルトで | 明示的、より高価、より稀 |
| タイプミスへの防御 | 常にスキーマがある | バリデータ、有効にしたなら |
| スキーマの変更 | マイグレーションとリリース | 新しいフィールドがひとりでに現れる |

## これでできるようになったこと

- ドキュメントモデルがふさわしいのはいつで、それが自分に厄介ごとを招くやり方になるのはいつかを説明する
- カタログから MongoDB を注文し、`authSource`、ロール、単一のコピーでつまずかない
- 異なる形のドキュメントを保存し、入れ子のフィールドやリストの中で検索する
- スパースインデックスを作り、その節約が何を代償にしているかを理解する
- スキーマバリデータを有効にし、それが何から守り、何から守らないかを知る
- ドキュメントデータベースに欠けているものを声に出して挙げる：外部キー、通常の JOIN、デフォルトの
  トランザクション

## そして vSphere ならこれは

レプリカセットのための三台のマシン、そしてそのうち最も手間のかかる部分はインストールではなく、コピー間の
投票の設定です：誰がプライマリか、接続が失われたときに何をするか、遅れているものをどう戻すか。加えて、
一年後にこのデータベースを誰が更新するのかについて、情報セキュリティチームとの別途の話し合い。

ここでは——カタログの一項目と五分。

**正直に、vSphere のほうが便利なところ。** MongoDB の載った仮想マシンは、歩み寄れるマシンです：SSH で
ログインし、`mongotop` を眺め、設定をいじり、危険な操作の前にスナップショットを取る。マネージド
サービスはこれを **意図的に** 与えません：テナントは Pod の中やデータベースのログの中への `exec` を
許しません。すべてが動いている限り、それは利点です——壊す手立てが少ない。データベースが奇妙な振る舞いを
するとき、管理者のいつもの一連の行動は使えず、残されるのはプラットフォームを運用する者のところへ行くこと
だけです。

そして二つ目、とりわけ MongoDB に固有のこと。マネージドサービスはバージョンとパラメータの組を固定します。
MongoDB のメジャーバージョンのアップグレードは、自分のインストール環境なら自分で計画する操作で、
アプリケーションの互換性チェックと、スナップショットへ戻す選択肢を伴います。ここではバージョンの変更は
フォームの一項目であり、内側では他人のアップグレード手順です。たいていはこれこそが望むものです。しかし
アップグレードが失敗する日には、自分の手でそれを解決することはなく、これを途中で気づくのではなく、
あらかじめ理解しておく必要があります。
