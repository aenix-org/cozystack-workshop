# ラボ6 · 自分専用のプライベートイメージレジストリ

| | |
|---|---|
| **所要時間** | 45分（うち10分は待ち時間） |
| **何を証明するか** | イメージレジストリは10分で立ち上がり、クラスターはそこからだけイメージを取得できる |
| **必要なもの** | ラボ0で作ったクラスター、ノートPC上の `kubectl`、`docker`（または `podman`）、ダッシュボードへのアクセス |

## なぜ重要か

「Passes（入館証）」サービスが情報セキュリティ部門まで到達し、そこから1通のメールが返ってきました。

> コンテナイメージがインターネット上のパブリックレジストリから取得されています。これは容認できません。
> イメージの中身は誰も検証しておらず、同じ名前のまま内容が変わりうるうえ、外部リソースが利用
> できなくなれば本番サービスは起動しません。すべてのイメージは組織の内部レジストリに保管しなければ
> なりません。

反論の余地はありません。どの指摘ももっともです。`latest` タグの付いたパブリックイメージは、今日と
明日で別物になりうる。イメージの作者はそれを削除できる。外部レジストリは、最悪のタイミングでダウン
ロード速度を制限してくることがある。これは仮定の話ではなく、大手のパブリックレジストリはどこもそう
しています。

つまり、自分専用のレジストリが必要になります。ふつうこれはそれ自体が一つのプロジェクトです。VMの
申請、インストール、証明書、ストレージ、バックアップ、誰かの四半期まるごと。今日はそれがカタログの
1項目です。

そしてレジストリが自分専用で閉じている以上、クラスターにそこへのアクセスを与える必要があります。
ここで誰もがつまずきます。私たちもわざとつまずいてみせます。

## ちょっとした用語集

| 用語 | 何か | 似ているもの…ただし |
|---|---|---|
| **イメージ（image）** | アプリケーションを、実行に必要なものすべてごと写し取ったもの | **VMテンプレート**、ただし不変：中に入って直すことはできず、新しく作り直す |
| **レイヤー（layer）** | イメージの一部。イメージはレイヤーから組み立てられ、レイヤーは再利用される | 異なるイメージの同一レイヤーは、レジストリに1回だけ保管される |
| **タグ（tag）** | イメージのバージョンラベル：`passes-api:v1` | **テンプレートのバージョン名**、ただしタグは別のイメージに付け替えられ、それがトラブルの主な原因になる |
| **レジストリ（registry）** | HTTP経由で提供されるイメージの保管場所 | **Content Library**、ただしテンプレートを丸ごとコピーするのではなく、起動のたびにレイヤーをネットワーク越しに渡す |
| **Harbor** | UI、プロジェクト、権限、脆弱性スキャナーを備えたレジストリ | **Content Library＋権限＋レポート**、ただしイメージの中身を検査し、署名することもできる |
| **Harborのプロジェクト** | レジストリ内部の、独自の権限を持つ領域 | **Content Library内のフォルダ**、ただし公開にも非公開にもでき、それによって認証情報が必要かどうかが決まる |
| **`imagePullSecret`** | レジストリのログインとパスワードを保持し、ノードが読み取る Secret | **Content Libraryを接続するためのアカウント**、ただし必要なのは**ノード**であって、あなたではない。あなたの `docker login` はクラスターの役には立たない |
| **Dockerfile** | イメージを構築するための手順書 | **テンプレートを準備するための手順書**、ただしビルドのたびに丸ごと最初から実行される |
| **Downward API** | Pod に自分自身についての情報を環境変数を通じて渡す方法 | **VMware Toolsのゲスト変数**、ただし値は起動時にクラスターが注入する。アプリケーションはそれを要求しない |

## 2つのkubeconfig：取り違えないこと

ここから先、このラボでは2つの異なるクラスターを扱います。最初のコマンドを打つ前に、この2つをはっきり
分けておく価値があります。

| kubeconfig | 何か | それで何をするか |
|---|---|---|
| `~/.kube/workshop` | Cozystackの管理クラスター、あなたのテナント | マネージドサービスを見る：Harbor、データベース、キュー |
| `~/lab.kubeconfig` | ラボ0で作った**あなたの** `lab` クラスター | アプリケーションをデプロイする |

どちらもダッシュボードから取得します。テナント用は `kubeconfig-tenant-workshopXX` Secret（Secrets
タブ）に、クラスター用はあなたの `lab` クラスターのアクセス欄にあります。

⚠️ **このラボで「何も動かない」の最もよくある原因は、コマンドが間違ったクラスターに送られたことです。**
コマンドのブロックごとに、それがどのクラスター向けかを明記してあります。自信がなければ：

```bash
# echo は変数の値を表示する：kubectl が今どのアクセスファイルを使っているか。
# 空なら、kubectl はあなたが思っているファイルではなくデフォルトの ~/.kube/config を使う。
echo $KUBECONFIG

# get nodes =「クラスターのノードを表示せよ」。ここではリトマス試験紙になる：
# その答えで、コマンドが2つのクラスターのどちらに送られたかがわかる。
kubectl get nodes
```

`lab` クラスターには `kubernetes-lab-md0-...` のような名前のノードが1つだけあります。管理クラスターでは、
このコマンドはおそらく拒否を返します。テナントにはノードを見る権限がないからです。

## ラボのフォルダに何があるか

ファイルはすべてすでにあなたのものです。リポジトリと一緒に受け取っています。作成したり打ち直したり
するものは何もありません。以下で `kubectl apply -f name.yaml` と書かれているところでは、ファイルはここ
から取られます。

```bash
# このラボのコマンドはすべてラボのフォルダから実行する — そこへ移動する
cd labs/06-harbor
```

| ファイル | 何か | いつ役立つか |
|---|---|---|
| `app/` | 「Passes」サービスのGoのソースと `Dockerfile` — これらからイメージを構築する | ローカルで構築するとき、`docker build` |
| `passes-broken.yaml` | **わざと不完全にした**ファイル：レジストリへのアクセス認証情報がない | 拒否を自分の目で見るために適用する |
| `passes.yaml` | 同じファイルだが、レジストリへのアクセスが入っている | 仕組みを理解したあとに適用する |
| `check.sh` | イメージがインターネットではなくあなたのHarborから来たことの確認 | ラボの最後に実行する |

## ステップ1. Harborを作成する

📍 **場所：** ブラウザ、Cozystackのダッシュボード内。レジストリはテナントの共有リソースであり、あなたの
ラボクラスターの一部ではありません。だから、クラスター自体が作られたのと同じ場所で作成します。

テナント → **アプリケーションを作成** → `Harbor`。

| 項目 | 値 | 理由 |
|---|---|---|
| 名前 | `harbor` | レジストリのアドレスの一部になる。どうなるかは作成後にわかる |
| Host | 空のままにする | そうすればアドレスは名前とテナントのドメインから自動で組み立てられる |
| Storage class | `replicated` | データは異なるノードにまたがって3つのコピーで保持される |
| Trivy → enabled | **オフにする** | 脆弱性スキャナーは数ギガバイトのデータベースをダウンロードする。学習用のテスト環境では、それは余計な20分の待ち時間になる |
| Database → replicas | `1` | レジストリのデータベースの耐障害性は今日はテストしない |
| Database → size | `5Gi` | |
| Redis → replicas | `1` | |
| Redis → size | `1Gi` | |
| Core / Registry preset | 提案されたままにする | |

⚠️ **このフォームのRedisはHarbor自身の内部キャッシュであり、次のラボとは関係ありません。** キャッシュに
関するラボでは、自分のアプリケーション用に別のRedisを立てます。名前は同じでも、役割は異なります。

作成をクリックして待ちます。Harborは5〜10分で立ち上がります。これは単一のアプリケーションではなく、
複数のサービスに加えてデータベース、さらにイメージのレイヤーそのものを収めるオブジェクトストレージ
からなります。

⚠️ **Harborが「準備未完了」の状態に15分以上とどまっているなら** — 何が起きているか見てみましょう：
`kubectl -n tenant-workshopXX get pods | grep harbor`。たいていはプラットフォーム全体で共有される
インストールキューです。あなたのアプリケーションはその中で他の人のものの後ろに並んで待っています。

HarborはイメージのレイヤーをS3互換ストレージに保管し、そのためのバケットは自動で作成されます。この
ためにテナントで自分のストレージを有効にする必要はありません。親のもので足ります。それでも30分以上
たってもPodが現れない場合は、このコマンドの出力を添えてワークショップのチャットに書き込んでください。

## ステップ2. 認証情報を取得してレジストリにログインする

📍 **場所：** ダッシュボード、続いてノートPC上のターミナル。

作成した `harbor` アプリケーションを開き、シークレットのタブを探します。そこにレジストリの認証情報を
持つシークレットがあり、その中に必要な3つのキーがあります：

| キー | 中身 |
|---|---|
| `url` | あなたのレジストリのアドレス。`https://harbor-....<テスト環境のドメイン>` の形式 |
| `admin-password` | 管理者のパスワード |
| `redis-password` | Harborの内部パスワード。あなたには不要 |

ログインは `admin` です。

⚠️ **レジストリのアドレスを推測せず、`url` キーから取ってください。** プラットフォームはアプリケーション名に
サービス種別のプレフィックスを付けるので、アドレスは名前から予想したものと違うことがあります。同じ
アドレスはアプリケーションの ingress の一覧でも見られます。

同じパスワードはコマンドでも取得できます。テナントは**すべての**シークレットを一律に読むことは許されて
いません。自分で確かめてみてください、`kubectl auth can-i get secrets` は `no` と答えます。しかし作成した
アプリケーションごとに、プラットフォームはまさにその認証情報だけを許可する個別のルールを設定します：

```bash
# get secret =「Secret オブジェクトを表示せよ」。シークレットの名前は、アプリケーション種別の
# プレフィックスとその名前から組み立てられる：harbor- ＋ harbor。
#   -n tenant-workshopXX  どの namespace を見るか — あなたのテナント
#   -o jsonpath='...'     オブジェクト全体を表示するのではなく、1つのフィールドだけを取り出す
#   base64 -d             デコードする：シークレット内の値は base64 で保管されている
#   ; echo                改行を足す。さもないとパスワードがプロンプトとくっつく
kubectl -n tenant-workshopXX get secret harbor-harbor-credentials \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo
```

ダッシュボードは base64 をいじらなくて済む点で便利です。コマンドはスクリプトに組み込める点で便利です。

そのアドレスをブラウザで開いてログインします。プロジェクトが1つ、`library` だけあるHarborのUIが表示
されます。

次は同じことをターミナルから。`docker login` はユーザー名とパスワードを尋ね、認証情報をあなたの
ノートPC上、`~/.docker/config.json` ファイルに保存します。その後は `docker push` と `docker pull` は何も
尋ねずにこのレジストリへ行きます。

```bash
# login =「このレジストリの認証情報を覚えておけ」。
# 引数は url キーから取ったレジストリのアドレス。ここでの harbor-harbor.workshop03.example.org は例。
# コマンドはユーザー名（admin）とパスワードを尋ねる。パスワードは入力しても表示されない。
docker login harbor-harbor.workshop03.example.org
```

以降、本文中の `harbor-harbor.workshop03.example.org` は**あなたの**アドレスです。自分のものに置き換えて
ください。

**表示されるはず：**

```
Login Succeeded
```

⚠️ **この `docker login` は、あなたのノートPCにレジストリへのログインを教えました — そして、それだけです。**
クラスターには何もしていません。これを覚えておいてください。ラボのもう少し先で必要になります。

## ステップ3. 非公開プロジェクトを用意する

📍 **場所：** ブラウザ、Harbor内。

**Projects** → **New Project**。

| 項目 | 値 | 理由 |
|---|---|---|
| Project Name | `passes` | サービスごとに1プロジェクト — そのほうが権限を配りやすい |
| Access Level | **Public にチェックを入れない** | セキュリティ部門が求めたのは閉じたレジストリであって、「自分のものだが、インターネット全体に開かれている」ものではない |
| Storage quota | `-1`（無制限） | テスト環境ではクォータは邪魔になるだけ |

最初から存在していた `library` プロジェクトは公開です。そこからは認証情報なしでイメージが取得できます。
だからこそ私たちはそれを使いません。このラボが題材にしている、まさにそのアクセスエラーが起きない
からです。

## ステップ4. イメージを構築する

📍 **場所：** ノートPC上。

このラボのフォルダには `app/` があります — 「Passes」サービスのソースとビルドの手順書です。構築する前に、
その中に何があるか見ておきましょう。

<details>
<summary><b>詳しく見る：アプリの中身</b></summary>

ファイル `app/main.go`、Goで約70行。これはちょうど2つのことをします。

**`/healthz` に対して `ok` という語で応答します。** これは準備状態チェック用のアドレスです。クラスターは
ここをノックし、応答を得るまでレプリカへトラフィックを送りません。

**`/` に対して小さなJSONで応答し**、その中で自分自身について報告します：

```json
{
  "service": "passes-api",
  "version": "v1",
  "pod": "passes-api-7d9f8c6b4-xk2mp",
  "node": "kubernetes-lab-md0-abc12",
  "namespace": "default",
  "registry": "harbor-harbor.workshop03.example.org",
  "time": "2026-08-21T09:12:33Z"
}
```

アプリケーションはどうやって自分の名前、ノード、namespace を知るのでしょうか。**調べているわけでは
ありません**。起動時にクラスターがそれらを環境変数に入れているのです：

```go
Pod:  env("POD_NAME", "不明"),
Node: env("NODE_NAME", "不明"),
```

そしてマニフェストには、そこに何を入れるかが書かれています：

```yaml
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
```

これは downward API と呼ばれます —「上から降ろされた情報」。vSphereで最も近いのは、VMware Toolsが
マシンの中へ渡すゲスト変数です。違いは、ここではアプリケーションが何も尋ねず、どこへも行かないこと
です。プロセスが起動する時点で、値はすでに環境の中にあります。クラスターのAPIへのクライアントも、
そのAPIへの権限も必要ありません。

**アプリケーションには外部ライブラリが1つもなく、Goの標準ライブラリだけです。** これは気取りでは
ありません。依存関係を伴うビルドはパッケージを求めてインターネットへ行きますが、このラボ全体は、
セキュリティ部門がインターネットへ行くことを禁じたところから始まっています。

ファイル `app/Dockerfile` はビルドの手順書です。2つのステージがあります：

```dockerfile
FROM golang:1.23-alpine AS build
...
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/passes-api .

FROM alpine:3.21
COPY --from=build /out/passes-api /usr/local/bin/passes-api
```

最初のステージはビルド用のステージです。Goコンパイラ一式、およそ350 MBが必要です。2つ目のステージが、
実際にクラスターへ送られるものです。最初のステージからは**完成したバイナリだけ**が持ち込まれ、それ以外は
すべて捨てられます。

結果は、350メガバイトではなく約10メガバイトのイメージです。サイズだけの話ではありません。中にはコン
パイラも、ソースも、パッケージマネージャーもありません。仮にコンテナに入り込んだ者がいても、使える
ものが何もないのです。

これを仮想マシンのテンプレートの仕組みと比べてみてください。テンプレートはオペレーティングシステム
全体を内側に抱え、コンパイラがかつてそこに紛れ込んでいればそれごと抱えます。後からそれを小さくするの
はほぼ不可能です。

最後の行：

```dockerfile
RUN adduser -D -u 10001 app
USER 10001
```

アプリケーションはrootでは動きません。適切に設定されたクラスターでは Pod は root での実行を許されません。
これは私たちが細かいのではなく、現代のどのクラスターでも突き当たる要件です。

</details>

`docker build` コマンドはイメージを構築します。`Dockerfile` を読み、そこに書かれた手順を実行し、結果を
あなたのノートPC上のイメージ保管領域に置きます。結果が保管される名前は `-t` フラグで指定し、3つの部分
からなります：

| 部分 | 意味 |
|---|---|
| `harbor-harbor.workshop03.example.org` | レジストリのアドレス — イメージを取りに行く先 |
| `passes/passes-api` | レジストリ内のプロジェクトと名前 |
| `v1` | バージョンタグ |

レジストリのアドレスはイメージ名の一部です。だからこそ、自分のレジストリへ移ると、すべてのマニフェスト
が変わります。イメージ名が別のものになるからです。

構築しましょう。アドレスを自分のものに置き換えてください：

```bash
cd labs/06-harbor

# build =「Dockerfile からイメージを構築せよ」。
#   --platform linux/amd64  どのプロセッサ向けに構築するか。クラスターのノードは x86 で、
#                           ノートPC は ARM のことがある — その場合、フラグなしでは間違ったものができる
#   -t <アドレス>/<プロジェクト>/<名前>:<タグ>  結果に付ける名前。名前の先頭にあるレジストリのアドレスが、
#                           後で docker push が送る先になる
#   app/                    最後の引数 — Dockerfile とソースのあるフォルダ。
#                           その中身がまるごとビルダーに渡される
docker build --platform linux/amd64 -t harbor-harbor.workshop03.example.org/passes/passes-api:v1 app/
```

⚠️ **`--platform linux/amd64` は飾りではありません。** Apple Silicon（M1〜M4）のMacやARMのノートPCを
使っているなら、このフラグがないとARMイメージが構築されます。エラーなく構築され、エラーなくpushされ、
そしてクラスターでは — そこのノードはふつうのx86です — Pod は `CrashLoopBackOff` に陥り、ログには
`exec format error` と出ます。これは診断に長い時間がかかります。まわりのどこにも、原因がプロセッサの
アーキテクチャだと示唆するものがないからです。

**表示されるはず** — ビルドの各ステップに関する行、そして最後に：

```
Successfully tagged harbor-harbor.workshop03.example.org/passes/passes-api:v1
```

## ステップ5. イメージを自分のレジストリへ送る

📍 **場所：** ノートPC上。

構築したイメージは今のところ、あなたのディスク上にしかありません。`docker push` はそれをレイヤーごとに
レジストリへ送ります。すでにレジストリにあるレイヤーは再び送られません。

```bash
# push =「イメージをレジストリへ送れ」。送り先は、docker がイメージ名から取る：
# 名前の最初の部分がレジストリのアドレスで、そこへ、docker login の認証情報を添えて送られる。
docker push harbor-harbor.workshop03.example.org/passes/passes-api:v1
```

**表示されるはず** — レイヤーが出ていく様子、そして最後に長いハッシュ、`digest` の入った行。

ブラウザでHarborを見てみましょう：**Projects** → `passes` → そこに `passes/passes-api` というリポジトリが
現れ、その中にタグ `v1` があります。サイズ、日付、そして同じ `digest` が見られます。

その `digest` はイメージの正確な中身です。タグ `v1` は明日別のイメージに付け替えられても誰も気づき
ませんが、`digest` は偽造できません。ここから、誰もが遅かれ早かれ学ぶ規則が出てきます：**本番へはタグ
ではなく digest で送り出す。**

## ステップ6. クラスターへデプロイする

📍 **場所：** ノートPC上、`lab` クラスター。


<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

**イメージをダウンロードしているのは、あなたではありません。** ダウンロードするのは `kubelet` — クラス
ターのノード上のサービスです。それは別のマシン、別のプロセス、別のユーザーです。

あなたの `docker login` は、認証情報を**あなたのノートPC上**の `~/.docker/config.json` ファイルに書き込み
ました。クラスターのノードはそのファイルについて何も知りませんし、知りようもありません。ノードとあなた
のノートPCの間には、あなたがそこへコマンドを送るという事実以外、共通するものが何一つないからです。

ラボの少し前、`docker login` の後の警告に戻ってみてください。まさにそう書いてありました。ただ、その
帰結がまだ見えていなかっただけです。

**正しいやり方。** 認証情報はクラスター自体の中に — 特別な種類の Secret オブジェクトの中に — 置く必要が
あり、そのうえでアプリケーションのマニフェストに、ダウンロード時にどのシークレットを使うかを書く必要が
あります。そのようなシークレットを `imagePullSecret` と呼びます。

**なぜクラスターにはあなたのものではなく、別個の認証情報が必要なのか。** 理由は3つあり、3つとも実務的な
ものです。

第一に、あなたがいないかもしれない。ノードは午前3時に再起動し、イメージをまた取りに行きます。もし
あなたのアカウントで行くなら、すべてが、あなたがまだこの会社で働いていて、パスワードが失効していない
ことにかかってしまいます。

第二に、権限が違う。あなたにはレジストリへ**書き込む**権限、そこへビルドを送る権限が必要です。クラス
ターに必要なのは**読む**ことだけです。クラスターにレジストリからイメージを消す権限を与えるのはよくない
考えですが、あなたのアカウントを使えば、まさにそれを与えてしまうことになります。

第三に、痕跡が違う。レジストリのログに、イメージをダウンロードしたのが `admin` ではなく
`robot$passes-puller` だと記録されていれば、インシデントの調査が可能になります。

**なぜノードを直接設定しないのか。** 認証情報をノードに直接、コンテナランタイムの設定の中に置くことも
できます — そうすれば `imagePullSecret` は不要です。そうする人もいます。しかしクラスター内のノードは
使い捨てです。アップグレードで再作成され、負荷の増加とともに追加され、障害時には停止されます。ノード上
に手作業で行った設定は、そのノードが最初に置き換えられるまでしか生きません。クラスター内のシークレット
は、どんな置き換えよりも長く生き延びます。

**教訓は、このエラーより広い。** `ImagePullBackOff` は、ほぼ必ず次の3つのどれかです：イメージ名のタイプミス、
認証情報がない、あるいはイメージはあるが正しいプロセッサのアーキテクチャ向けではない。Pod のステータス
ではなく `kubectl describe pod` を見てください — 本当の原因はそこに書かれています。

</details>

## ステップ7. クラスターにレジストリへのアクセスを与える

📍 **場所：** ノートPC上、`lab` クラスター。

レジストリの認証情報を持つシークレットを作成します。`create secret` コマンドの専用の亜種が、イメージの
ダウンロード時に `kubelet` が自分で読める種類のシークレットを作ります：

```bash
# create secret docker-registry =「レジストリの認証情報を持つシークレットを作れ」
#   harbor             クラスター内でのシークレットの名前。アプリケーションのマニフェストがこれを参照する
#   --docker-server    これらの認証情報がどのレジストリ向けか — イメージ名にあるのと同じアドレス
#   --docker-username  誰がログインするか
#   --docker-password  パスワード。$、! やスペースが含まれる場合はシングルクォートが必要
kubectl create secret docker-registry harbor \
  --docker-server=harbor-harbor.workshop03.example.org \
  --docker-username=admin \
  --docker-password='YOUR-PASSWORD'
```

⚠️ **コマンドラインに書いたパスワードはシェルの履歴に残ります。** テスト環境では問題になりませんが、
実務の環境では問題です。履歴に残さない方法：

```bash
# read はキーボードで打たれたものを HARBOR_PASS 変数に入れる：
#   -s  打った内容を画面に表示しない
#   -r  バックスラッシュを特殊文字として扱わない
# この行の後、画面には何も現れない：パスワードを貼り付けて Enter を押す。
read -rs HARBOR_PASS

# ここからはパスワードが変数から差し込まれるので、シェルの履歴には
# 変数名だけが残る。ダブルクォートは必須：それがないとスペースで値が壊れる。
kubectl create secret docker-registry harbor \
  --docker-server=harbor-harbor.workshop03.example.org \
  --docker-username=admin \
  --docker-password="$HARBOR_PASS"

# unset は変数を消し、パスワードがこのウィンドウの次のコマンドに渡らないようにする
unset HARBOR_PASS
```

<details>
<summary><b>このシークレットの中身と、なぜ専用の型を持つのか</b></summary>

どんな種類のシークレットができたか、クラスターに聞いてみましょう：

```bash
#   -o jsonpath='{.type}'  オブジェクトの1つのフィールドを表示する — シークレットの型
#   {"\n"}                 改行を足す。さもないと出力がプロンプトとくっつく
kubectl get secret harbor -o jsonpath='{.type}{"\n"}'
```

```
kubernetes.io/dockerconfigjson
```

シークレットには**型**があり、それは飾りではありません。ふつうのシークレットはキーと値の組の集まりで、
それをどう扱うかはアプリケーション次第です。`kubernetes.io/dockerconfigjson` 型のシークレットは
`kubelet` 自身が理解します。中に `~/.docker/config.json` と同じ形式のファイルが入っていることを知って
いて、イメージのダウンロード時にそれを使えるのです。

中身を見るには（そこのパスワードは base64 になっています — これは**暗号化ではなく**、バイナリデータを
テキストとして書くための方法で、誰でもデコードできます）：

```bash
# .data.\.dockerconfigjson — シークレット内のキー。キー名そのものがドットで始まるので、
# エスケープする：さもないと jsonpath がそれをパスの区切りと取ってしまう。
# base64 -d は値をテキストへデコードし戻す — あなたのノートPC上の
# ~/.docker/config.json ファイルと同じ形式が見られる。
kubectl get secret harbor -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d
```

ここから重要なことが言えます：**Kubernetesの Secret はデフォルトでは暗号化されていません**。ただアクセス
権限で囲われているだけです。namespace 内でシークレットを読める者は、パスワードを見られます。これを
まともに扱う方法は、シークレットの保管庫についての別のラボで扱います。

**実務ではどうするか。** `admin` アカウントではありません。Harborにはロボットがあります：**Projects** →
`passes` → **Robot Accounts** → `pull` 権限だけを持つロボットを作成する。ロボットの認証情報を
`imagePullSecret` に入れれば、クラスターからシークレットが漏れても、誰かがあなたのイメージをダウン
ロードできるという話にとどまります — 不快ですが、致命的ではありません。`admin` が漏れれば、誰かがそれら
を差し替えられるということになります。

ラボを長引かせないために `admin` を使います。これは簡略化だと承知しておいてください。

</details>

## ステップ8. 何ができたか見る

📍 **場所：** ノートPC上、`lab` クラスター。

アプリケーションは外部に公開されていませんが、それを見る必要があります。`port-forward` はノートPCから
クラスターの中へトンネルを掘ります。コマンドが動いている間、`localhost:8080` へのリクエストは
`passes-api` サービスへ行きます。最も近いのは、NATゲートウェイ上の一時的なポートフォワードですが、
ネットワークには手を触れない点が違います。

```bash
# port-forward svc/passes-api = 特定の Pod ではなく、サービスへのトンネル
#   8080:80 — 左の数字はあなたのノートPC上のポート、右はクラスター内のサービスのポート
# ウィンドウを閉じないこと：トンネルはコマンドが動いている間だけ生きる。
kubectl port-forward svc/passes-api 8080:80
```

別のターミナルのウィンドウで：

```bash
# curl —「アドレスへ行って答えを表示せよ」。
#   -s     進捗インジケータを表示しない
#   ; echo 改行を足す：答えは1行で来るので、これがないと
#          シェルのプロンプトとくっつく
curl -s http://localhost:8080/; echo
```

**表示されるはず** — アプリケーションが、どのレプリカが答えたか、どのノードで動いているか、どのレジストリ
から来たかを報告するJSON：

```json
{
  "service": "passes-api",
  "version": "v1",
  "pod": "passes-api-7d9f8c6b4-xk2mp",
  "node": "kubernetes-lab-md0-abc12",
  "namespace": "default",
  "registry": "harbor-harbor.workshop03.example.org",
  "time": "2026-08-21T09:12:33Z"
}
```

答えの中の `pod` フィールドは、答えたレプリカの名前です。それをレプリカの一覧と照らし合わせてください：

```bash
# 新しいターミナルのウィンドウは KUBECONFIG 変数を何も知らない — ここでも設定する。
# さもないと kubectl は間違ったクラスターへ行く
export KUBECONFIG=~/lab.kubeconfig

# 同じラベルによる絞り込み：一覧には、答えの中で見た名前があるはず
kubectl get pods -l app=passes-api
```

リクエストを何度か繰り返してみてください — 名前は**同じまま**で、これは故障ではありません。
`port-forward` は起動の瞬間に1つのレプリカを選び、`Ctrl+C` までまさにそのレプリカへのトンネルを保ち
ます。この経路には負荷分散はまったくありません。`Service` にはありますが、それはクラスターの内側からしか
見えません — 外側からは、あなたは特定の Pod と話しているのです。

負荷分散を本当に確かめるには、こうします — クラスターの中で生きる一時的な Pod から8回のリクエスト：

```bash
# run は使い捨ての Pod を立て、--rm はあとで片づける。
# -- の後はすべて Pod の中で実行される：内部名でサービスを8回叩き、
# 答えたレプリカの名前の入った行を表示する。
kubectl run probe --rm -i --restart=Never --quiet --image=curlimages/curl:8.11.1 \
  -- sh -c 'for i in $(seq 1 8); do curl -s http://passes-api/ | grep -o "passes-api-[a-z0-9-]*"; done'
```

**表示されるはず：** 2つの異なる名前が混ざり合っている — これが `Service` がリクエストをレプリカに
振り分けている姿です。

トンネルを閉じるには — 最初のウィンドウで `Ctrl+C`。

輪を閉じましょう：ブラウザでHarborに入り、`passes` プロジェクトへ。`passes/passes-api` リポジトリの
ダウンロードカウンター（**Pulls**）が非ゼロになっています。あなたのクラスターは、本当にまさにここへ
来たのです。

## vSphereでこれは

レジストリに最も近いのはContent Libraryです。似ている点はあります：どちらもイメージを保管してマシンに
配り、どちらも権限とサイト間の同期を扱えます。

そこから先は分かれていき、その違いは細部にあるのではありません。

**Content Libraryはテンプレートを丸ごとコピーします。** レジストリはレイヤーを配り、同一のレイヤーは
1回だけ保管します。同じベースのAlpine上に20個のサービスがあれば、ベースはレジストリに1つのコピーだけ
置かれ、21番目のサービスが起動するとき、ノードは自分のレイヤーだけ — ほんの数メガバイトをダウンロード
します。

**テンプレートは名前で呼ばれ、イメージはアドレスで指されます。** イメージにはdigest — 中身のハッシュが
あります。それによって、自分が構築したまさにそのコードを動かしていて、他のものではないと検証できます。
テンプレートにはそのようなものがありません：誰もそれをすり替えていないことに頼るしかないのです。

**レジストリはHTTPサービスです。** ここから、この演習の眼目すべてが導かれます：パイプライン内のビルドが
1つのコマンドでそこへイメージを置き、クラスターが別のコマンドでそれを取ってきて、誰もストレージを
マウントしたり、サイト間で手作業でファイルをコピーしたりしません。

**正直に、vSphereのほうが便利なところ。** 3つあります。

Content Libraryは、認証情報について何も理解する必要がありません。接続すれば — 動きます。ここではあなた
は、レジストリへの行き方をクラスターに別途説明する必要があり、誰もがそうであるように、そこでつまずき
ました。

vCenterでは権限が一元化されています。すべてに1つのアカウント：マシンも、ライブラリも、ネットワークも。
ここではダッシュボードの権限、クラスターの権限、Harborの権限が3つの異なる集合で、それらを同期させ続け
なければなりません。これは、レジストリがプラットフォームの一部ではなく、それ自体で独立した製品である
ことの代償です。

テンプレートは編集できます。テンプレートからマシンを展開し、さらに調整し、新しいテンプレートを取得する
