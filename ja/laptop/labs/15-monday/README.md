# ラボ 15 · 月曜日に何をするか

| | |
|---|---|
| **所要時間** | 20分、コマンドは一つも打ちません |
| **何を証明するか** | 学んだことは、小さく始めれば自分のフリートにも適用できる |
| **必要なもの** | あなた自身と、自分のシステムの一覧だけ |

ここにはコマンドも `check.sh` もありません。このラボを確認できるのは月曜日だけです。
テスト環境の電源を切り、職場のすべてが元どおりになったあと、次に何をするかについての会話です。

## できあがったもの

14個のラボを通じて、あなたは動く社内サービス「Pass」を組み上げました。従業員がこれを使ってゲスト用の入館証を申請し、警備は受付でその一覧を見て、経営陣は月に一度レポートを見ます。それぞれの部品は順番に登場したのではなく、具体的な痛みから生まれました。

| 登場したもの | なぜ |
|---|---|
| 自前のイメージレジストリ | セキュリティチームがインターネットからのイメージ取得を禁じた |
| キャッシュ | レガシーの従業員名簿は応答に800ミリ秒かかっていた |
| ドキュメントストレージ | 入館証にはさまざまなフィールドがある。1回限り、週単位、車両用、団体用 |
| シークレットストレージ | 監査でマニフェスト内にデータベースのパスワードが見つかった |
| 分析用データベース | 経営陣がゲストの数とピークの時間帯を知りたがった |
| Bucket | モバイルチームがビルドしたAPKを置く場所がなかった |
| Git上のインフラ | 3人でやっていて、誰かが手作業で変更し、すべてが落ちた |
| カタログ内の自前のエントリ | 子会社が同じサービスを自分たちにも欲しがった |

これらのサービスは一つとしてあなたがインストールもアップデートもしていません。プラットフォームが責任を持つカタログのエントリです。あなたがインストールし、修正したのは自分のアプリケーションだけです。

次は、これをテスト環境の外で繰り返す方法についてです。

## なぜこれが大切か

この種のトレーニングの最もよくある結末は「面白いが、うちではうまくいかない」です。うまくいかないからではなく、14個のラボを終えたあとでも、300台の仮想マシンがあり、その半分が何をしているのか誰も覚えていない自分のインフラで、どこから始めればいいのか分からないからです。

順番に整理しましょう。どこから始め、何に手を出さず、予算に承認する人たちにどう意義を説明するか。

## どこから始めるか: 最初の一手の候補は3つ

最も重要なアプリケーションからではありません。最も放置されたものからでもありません。始めるのは、間違えても安上がりで、結果が目に見えるものからです。

### 候補その1: どのみち入れ直すつもりだったもの

誰にでも「そろそろ新しいOSに移すべきだ」とか「バージョンを更新する時期だ」と、とうの昔に決まっているシステムがあります。それが理想的な最初の一手です。どのみち手を付けるつもりだったので、リスクはすでに計画に織り込まれており、必要な承認の数もまったく同じです。

### 候補その2: テスト環境やデモ環境

失っても惜しくない本番アプリケーションのコピーです。ここで試すのは、あなた自身が移行を再現できるかどうかであって、プラットフォームではありません。プラットフォームはワークショップですでに試しました。違いは、今回はあなたのイメージ、あなたのネットワーク、あなたのセキュリティポリシーだということです。

### 候補その3: 新しいリソースを求めているもの

新しいサービス用に仮想マシンを2、3台欲しいとやってきたチームは、最も都合のよいケースです。何も移行せず、すべてをゼロから作り、申請フォームの代わりにその場でダッシュボードを見せられます。速さの違いは双方が見て取るでしょう。

## 最初に手を出すべきでないもの

**ライセンスがハードウェアに紐づいたシステム。** 何かを移す前に契約条件を確認してください。hypervisorの物理コア数でライセンスを数える製品があり、移行が節約額を上回るコストになることがあります。

**理解していないもの。** 7年前に業者がアプリケーションをインストールし、以来誰も中を見ていないなら、移行は調査に変わります。やり遂げられる仕事ではありますが、最初の仕事ではありません。

**独自の耐障害性を持つクラスター化されたシステム。** レプリケーション付きのデータベース、アプリケーションクラスター、自分自身のコピーを見張っているものすべて。ここでは耐障害性の責任を今後どちらが持つのか——アプリケーションかプラットフォームか——を決める必要があり、それはシステムの持ち主との別の会話になります。

## うまくいく順序

1. **テスト環境を立てる。** 移行のためではなく、どんな思いつきでも申請を出さずに同じ時間内に試せる場所を持つためです。サーバー1台、インストール1回、コミットメントはゼロ。
2. **上に挙げた中から1つのシステムを移す。** データごと丸ごと、「動いていて、ユーザーがそれを見ている」状態まで。
3. **1か月そのシステムと暮らす。** ここで、どんなワークショップも与えられないことを学びます。深夜3時にどう振る舞うのか、アップデート時に何が壊れるのか、監視に何が足りないのか。
4. **ここでようやく残りの計画を立てる。** プレゼン資料からではなく、自分のハードウェアで得た数字とともに。

手順2と3のあいだで、たいてい急ぎたくなります。やめておきましょう。1つのシステムを本番で1か月運用するほうが、同じ1週間で10個移すよりも多くを教えてくれます。

## これを経営陣にどう説明するか

会話はテクノロジーについてではありません。たいていは3つのことで決まります。

**ライセンスコスト** — 最もよく使われる論拠ですが、最も滑りやすくもあります。正直に計算しましょう。節約には、消し込む1行だけでなく、移行にかかるあなたの時間のコスト、チームのトレーニング、そして両方のプラットフォームが同時に動く期間も含まれます。

**リソース払い出しの速さ。** ここではあなた自身の実体験があります。自分の手でクラスターを10分、データベースを5分で立ち上げました。同じ申請が自社でどれだけかかるかと比べてみてください。それはビジネスが翻訳なしに理解する数字です。

**単一ベンダーからの独立。** ここ数年で重みを増した論拠です。単独では効かず、1つ目と組み合わさって効きます。プラットフォームを切り替えられる能力こそが、価格交渉の立場を与えてくれるものです。

約束しないほうがよいこと: 楽になる、ということです。楽にはなりません——少なくとも最初の1年は。安く、リソースの払い出しは速く、単一ベンダーへのロックインもなくなりますが、楽にはなりません。楽さを約束することは、半年後に信頼を失う最速の方法です。

## 質問はどこへ持っていくか

- **Telegramのコミュニティ** — ワークショップが行われたのと同じチャットです。「これを正しくやるにはどうすればいいか」という質問はいつでも歓迎されます。

  何かが書かれているとおりに振る舞わないなら、たいていは推測するより chart を見るほうが速いです。自前のレジストリについてのラボで、あなたはもうこれをやりました。

## いま私たちにできること

- 移す最初のシステムを「最も重要」ではなく「間違えても安上がり」という基準で選ぶ
- 先送りにすべきケースと、今取りかかるべきケースを見分ける
- 経営陣に、実際には存在しない楽さを約束しない
- 近くの誰も答えを知らないとき、どこで尋ねればいいかを知っている

## これが vSphere だったら

会話はもっと短かったでしょう。あなたは月曜日に何をするかをすでに知っています。10年間それをやってきたからです。違いはそこにあります——テクノロジーの違いではなく、ここでは習慣をもう一度ゼロから積み上げなければならないという点です。

よい知らせは、習慣は少しずつ、一度に1つのシステムで身につけられることです。悪い知らせは、最初の数か月は慣れているよりも遅く働くことになる点です。速さは新しい習慣が積み重なるにつれて戻ってきます——ただし、その遅れをあらかじめスケジュールに織り込んでおかなければなりません。
