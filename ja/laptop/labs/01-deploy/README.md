# ラボ 1 · 最初のアプリケーション

| | |
|---|---|
| **所要時間** | 25分 |
| **何を証明するか** | アプリケーションはテキストで記述され、数秒でデプロイされ、誰の許可も要らない |
| **必要なもの** | ラボ 0 で作ったクラスター、`kubectl`、ファイル `~/lab.kubeconfig` |

## なぜこれが大切か

実際の課題に取りかかる前に、害のないもので練習しましょう。何もしない、たった一つのことだけをする
小さなアプリケーションをデプロイします。そのたった一つとは、**自分自身のコピーの名前**を表示することです。

無意味に聞こえますが、まさにその名前が次の3つのラボの主役になります。その名前を通じて、あなたは
コピーが死んでは再び生まれる様子を、それが6つに増える様子を、そして古いバージョンが新しいものに
入れ替わる様子を見ることになります。

デプロイはテキストで行います。1つのファイルと1つのコマンドです。このラボにマウスは登場しません。
それには理由があり、そこから始めましょう。

## 小さな用語集

| 用語 | 何か | 似ているもの…ただし |
|---|---|---|
| **Pod** | 実行中のアプリケーションのコピー | **仮想マシン**に似ているが、Pod は使い捨て。修理もバックアップもしない — 削除すれば新しいものが作られる |
| **イメージ (Image)** | 実行に必要なものをすべて含んだアプリケーションのスナップショット | **VM テンプレート**に似ているが、変更不可。中に入って直すことはできず、新しく作り直す |
| **Deployment** | どのイメージを、何個コピーし、どう更新するかの記述 | **vApp** に似ているが、特定の VM への参照ではなく、望ましいコピー数を保持する |
| **Service** | コピー群の背後にある恒久的なアドレス | **ロードバランサーのプール**に似ているが、背後のコピーがすべて再作成されても名前は変わらない |
| **ConfigMap** | クラスター内に置かれた設定ファイル | **VM のディスク上のファイル**に似ているが、アプリケーションとは別に存在し、起動時に中に差し込まれる |
| **マニフェスト (Manifest)** | 望ましい状態を記述したファイル | 直接の対応物はなく、まさにそこが要点 |

## ラボのフォルダに入っているもの

ファイルはすでにすべて手元にあります — リポジトリと一緒に取得済みです。新しく作ったり打ち直したりする
必要はありません。以下で `kubectl apply -f name.yaml` と書かれている箇所では、ファイルはここから取られます。

```bash
# パスはラボ 0 で取得したリポジトリのルートからの相対
cd labs/01-deploy
```

| ファイル | 何か | いつ必要になるか |
|---|---|---|
| `rickroll.yaml` | アプリケーション一式: nginx の設定、デプロイ本体、そしてそこへの入口 | 自分の `lab` クラスターに適用する |
| `check.sh` | アプリケーションが応答し Pod 名を返すことのチェック | ラボの最後に実行する |

## ステップ 1. ダッシュボードが終わり、あなたのクラスターが始まる場所

📍 **場所:** ノートPC上。

Cozystack のダッシュボードは、あなたが**プラットフォームに注文するもの**を表示します。Kubernetes クラスター、
データベース、キュー、仮想マシン — カタログの項目です。`lab` クラスターはそこに1つの項目として現れます。
注文済みで稼働中、という具合に。

ダッシュボードはその中身をのぞきませんし、のぞくこともできません。あなたのクラスターは、それ自身の
アドレスと、それ自身のアクセスファイル — あの `~/lab.kubeconfig` — を持つ別個の API サーバーです。
管理ダッシュボードはそれとは通信しません。`lab` クラスターには独自のグラフィカルコンソールもありません。
それに接続できるアドオンの中に、そのようなものは載っていないのです。

そこから責任の境界が生まれます。覚えておく価値があります。**プラットフォームはあなたが注文したものに責任を持ち、
注文したものの中身については、あなたが責任を持つ。** クラスターの中では、作業は `kubectl` を通じて行われます。
これはオブジェクトの記述をその API サーバーへ送り、今そこに何があるかを見せてくれるコマンドです。

接続しましょう:

```bash
# KUBECONFIG — kubectl がどのアクセスファイルを使うかを読み取る変数。
# ここでは lab クラスターへのアクセスであって、テナントへのものではない: ファイルが違えば、クラスターも違う。
export KUBECONFIG=~/lab.kubeconfig
# get nodes = 「ノードを表示せよ」。応答は kubectl が正しい相手と通信していることを確認してくれる。
kubectl get nodes
```

**見えるはずのもの:** あなたのノードと `Ready` ステータスが並んだ行。もし代わりに接続エラーが出たら、
`echo $KUBECONFIG` を確認してください。この変数はターミナルの新しいウィンドウごとに設定する必要があります。

## ステップ 2. アプリケーションをデプロイする

📍 **場所:** ノートPC上。

このラボのフォルダへ移動します — リポジトリはラボ 0 で取得済みです:

```bash
# パスはリポジトリをクローンしたフォルダからの相対
cd labs/01-deploy
```

まだリポジトリがない場合:

```bash
# clone = リポジトリを丸ごとダウンロードする; 隣に同じ名前のフォルダが現れる
git clone https://github.com/aenix-org/cozystack-migration-workshop.git
cd labs/01-deploy
```

フォルダには `rickroll.yaml` があります。適用する前に、中に何があるかを見ていきましょう。

<details>
<summary><b>詳しく見る: rickroll.yaml の中身</b></summary>

ファイルには `---` の行で区切られた4つのオブジェクトがあります。順番に見ていきましょう。

### 1つ目: ウェブサーバーの設定

```yaml
kind: ConfigMap
metadata:
  name: rickroll-conf
data:
  default.conf: |
    server {
      listen 8080;
      root /usr/share/nginx/html;
      location / {
        sub_filter '__POD__' '$hostname';
        sub_filter_once off;
      }
    }
```

`ConfigMap` は、設定ファイルをアプリケーションとは別にクラスターへ置くための方法です。中身は
ごく普通の nginx の設定（nginx はウェブサーバーで、私たちのページを配信するのがこれです）で、
仮想マシン上で `/etc/nginx/conf.d/` に置かれるであろうものと同じです。

肝心の行は `sub_filter '__POD__' '$hostname'` です。これは nginx にこう指示します。配信するページの中で、
テキスト `__POD__` を、自分が動いているマシンの名前に置き換えよ、と。Pod の中では、マシンの名前は
Pod 自身の名前です。こうしてページは、誰が自分を配信したかを知るのです。

なぜ設定をイメージに焼き込まず別オブジェクトにするのか。イメージを再ビルドせずに変更できるように、です。
バージョンのロールアウトについてのラボで、これを活用します。

### 2つ目: ページそのもの

```yaml
kind: ConfigMap
metadata:
  name: rickroll-page-v1
data:
  index.html: |
    ...<div class="pod">вас обслужил под<b>__POD__</b></div>...
```

nginx が置き換えることになる、あの `__POD__` です。名前の `-v1` は偶然ではありません。バージョンの
ロールアウトについてのラボで `-v2` が登場し、両者の切り替えが新しいバージョンのロールアウトになります。

### 3つ目: アプリケーション

```yaml
kind: Deployment
spec:
  replicas: 1
```

`Deployment` はアプリケーション全体の記述です。`replicas: 1` は、いくつのコピーを実行し続けるかです。
言い回しに注目してください。「1つ実行せよ」ではなく、**「1つ保ち続けよ」**です。この違いは、コピーを削除する
次のラボで表れます。

```yaml
      image: nginxinc/nginx-unprivileged:1.27-alpine
```

イメージです。非特権版の nginx を採用しました — これはポート 8080 で待ち受け、root として動きません。
通常の nginx は、正しく構成されたクラスターでは与えられない権限を要求します。これは私たちの気難しさではなく、
現代のどんなクラスターでも出くわすセキュリティ要件です。

```yaml
      resources:
        requests: {cpu: 20m, memory: 32Mi}
        limits:   {cpu: 300m, memory: 128Mi}
```

2つの別々のものであり、いつも混同されます。

`requests` は、**保証として予約する量**です。スケジューラーはこの数値を使って、Pod がどのノードに収まるかを
決めます。もっとも近い対応物は vSphere の reservation です。

`limits` は、**それより上には上がることを許されない**上限です。対応物は vSphere の limit です。

`20m` は「20ミリ CPU」、つまりコアの100分の2と読みます。少なめに要求しているのは意図的です。
アプリケーションはごく小さく、スケーリングのラボでは低いリクエストが、コピーが増えていく様子を
自分の目で見せてくれます。

```yaml
      readinessProbe:
        httpGet: {path: /healthz, port: http}
```

準備完了チェックです。クラスターはこのアドレスをノックし、応答を得るまで Pod にトラフィックを送りません。
これこそが、バージョンのロールアウトについてのラボで無停止の更新を実現するものです。新しいコピーは、
本当にリクエストを処理できる状態になって初めて、リクエストを受け取り始めます。

### 設定はどうやってコンテナの中に入るか

2つの ConfigMap は記述しましたが、それだけではクラスターの中に置かれているだけで nginx には届きません。
それらを結びつけるのが2つのブロックで、このラボの仕掛け全体がそこに懸かっています:

```yaml
          volumeMounts:
            - name: page
              mountPath: /usr/share/nginx/html
            - name: conf
              mountPath: /etc/nginx/conf.d
      volumes:
        - name: page
          configMap:
            name: rickroll-page-v1
        - name: conf
          configMap:
            name: rickroll-conf
```

下から上へ読みます。`volumes` はこう宣言します。「この ConfigMap を取って、ファイルの入ったフォルダにせよ」。
`volumeMounts` はこう言います。「そのフォルダをコンテナの中の、このパスに置け」。結果として、`index.html` は
nginx がページを探す場所に、`default.conf` は nginx が設定を探す場所に収まります。

あなたの世界からのもっとも近い例えは、共有フォルダを仮想マシンに接続することです。違いは、中身が
クラスターの中に別個のオブジェクトとして存在し、イメージにもマシン自体にも触れずに変更できる点です。

⚠️ **`volumes` の順序は重要です。** バージョンのロールアウトについてのラボは、ボリュームを**番号で**指定する
コマンド — リスト内の最初のもの — でページを切り替えます。もしブロックを入れ替えると、コマンドは黙って
ページの代わりに設定を差し込み、nginx は動かなくなります。ファイル自身の中にこれについてのコメントがあります。
安全なやり方 — 番号ではなくボリューム名によるパッチマージ — は、バージョンのロールアウトについてのラボで
扱います。

### 4つ目: 恒久的なアドレス

```yaml
kind: Service
spec:
  selector:
    app: rickroll
  ports:
    - port: 80
      targetPort: http
```

`Service` は、アプリケーションのすべてのコピーが背後に控える恒久的な名前です。`rickroll` に向けてアクセスすれば、
そのうちのどれか一つに届きます。

Service と Pod の間のつながりは、アドレスのリストではなく**条件**です。`selector: app: rickroll` は
「ラベル `app: rickroll` を持つすべての Pod」を意味します。ラベルとは、後でそのペアによって見つけられるように
オブジェクトに付ける、任意の「キー: 値」のペアです。もっとも近いのは vSphere のタグですが、ここではラベルは
目で見て探すためのものではなく、実際に機能する接続を組み立てるためのものです。このラベルを持つ新しい Pod が
現れれば — それは自動的にロードバランシングに加わります。消えれば — 外れます。誰も手でリストを編集しません。

これこそが、アドレスを書き込むロードバランサーのプールとの決定的な違いです。

</details>

さて、適用します:

```bash
# apply = 「ファイルに記述された状態にクラスターを合わせよ」。4つのオブジェクトすべてが
# 1つのコマンドで作成され、ファイル内の順序はクラスターが自分で解決する。
#   -f   記述をファイルから取る
kubectl apply -f rickroll.yaml
```

**見えるはずのもの** — オブジェクトの作成に関する4行:

```
configmap/rickroll-conf created
configmap/rickroll-page-v1 created
deployment.apps/rickroll created
service/rickroll created
```

コピーが起動するまで待ちます:

```bash
# rollout status は Deployment がやり遂げるまで待つ: 必要な数のコピーが
# 実行され、リクエストを受け付ける準備ができるまで。条件が満たされると、コマンドは自分で終了する。
kubectl rollout status deployment/rickroll
```

待ったのは数秒でした。起動したのはオペレーティングシステムではなく、すでに動いている1つの中の
たった1つのプロセスです。ノード上のカーネルはずっと前に立ち上がっていて、すべてのコンテナで共有されています。
同じ場所で仮想マシンなら、起動に1〜2分かかったでしょう — 自分自身のカーネル、サービス、ネットワークを
立ち上げる必要があるからです。

## ステップ 3. クラスターがファイルから何を作ったかを見る

📍 **場所:** ノートPC上。

クラスターはファイルそのものを保存するのではなく、そこから作成したオブジェクトを保存します。適用したものが
今どう見えるかを尋ねてみましょう:

```bash
# get deployment rickroll = 1つのオブジェクトを型と名前で表示する。
#   -o yaml   手で書けるのと同じ形で、全体を出力する
kubectl get deployment rickroll -o yaml
```

出力は長いです。大部分はクラスターが自分で埋めました — デフォルト値、内部フィールド、現在の状態です。
次の行を目で探してください:

```yaml
spec:
  replicas: 1
  template:
    spec:
      containers:
      - image: nginxinc/nginx-unprivileged:1.27-alpine
```

これがあなたがファイルに書いたものです。**クラスターの中では、すべてがテキストで記述されています** —
あなたが適用するものも、クラスターが返してくるものも。ラボ 0 で Cozystack のダッシュボードを通じて
クラスターを注文したとき、ダッシュボードはまさに同じテキストを組み立ててプラットフォームへ送りました。
ボタンはテキストの上に載った層であって、テキストの代替ではありません。

違いは、後に何が残るかにあります。ファイルは Git に入れ、適用前にレビューし、誰がいつ変更したかを調べ、
1つのコマンドでロールバックし、最初のクラスターでどのチェックボックスにチェックを入れたかを思い出そうと
しなくても、同じものを2つ目のクラスターにデプロイできます。マウスのクリックは痕跡を残しません。1か月後には
誰も、あなた自身も含めて、なぜそこにその値が設定されていたのかを覚えていないでしょう。

## ステップ 4. ブラウザで開く

📍 **場所:** ノートPC上。

**これから起こること:** アプリケーションはクラスターの中に存在し、外からは見えません。下のコマンドは、
ノートPCから内側へトンネルを張ります。

```bash
# port-forward = ノートPCからクラスターの内側へのトンネル。コマンドが動いている間だけ生きている。
#   svc/rickroll   rickroll という名前の Service へトンネルを張る。Service はそれをさらに
#                  アプリケーションの生きたコピーへとルーティングする
#   8080:80        左の番号は ノートPC上のポート、右はクラスター内の Service のポート
kubectl port-forward svc/rickroll 8080:80
```

コマンドは終了しません。あなたが止めるまでトンネルを開いたまま保持します。<http://localhost:8080> を
開いてください。

**見えるはずのもの:** きらめく見出し、曲の一節、そして一番下に — Pod 名。それをクラスターが示すものと
照らし合わせてください。

📍 **場所:** 2つ目のターミナルウィンドウ内。最初のウィンドウはトンネルで塞がっています — コマンドが
動いている間、そこには何も入力できません。新しいウィンドウを開き、そこでもう一度アクセスファイルを設定して
ください。環境変数は新しいウィンドウには引き継がれません。

```bash
export KUBECONFIG=~/lab.kubeconfig
```

```bash
# get pods = 「実行中のコピーを表示せよ」。
#   -l app=rickroll   すべての Pod ではなく、ラベル app=rickroll を持つものだけを表示する —
#                     まさに Service がそれらを見つけるのに使うラベル
kubectl get pods -l app=rickroll
```

名前が一致します。ページを配信したのは、まさにこのコピーです。

トンネルを閉じるには — `Ctrl+C`。

## チェック

📍 **場所:** ノートPC上、`kubectl` で作業していたのと同じターミナルウィンドウ内。

```bash
# ラボのフォルダから実行すること: スクリプトは自分のそばにあるファイルを探す。
# 名前の前の ./ は「ちょうどここからファイルを実行せよ」を意味し、システムフォルダで探せという意味ではない
./check.sh
```

⚠️ **Windows ではスクリプトは WSL から実行します**。PowerShell からではありません — その準備の仕方は
ラボ 0 の冒頭に書かれています。WSL がなくてもラボを終えることはできますが、成果物のレポートは残りません。

スクリプトはマニフェストが適用されたという事実ではなく、実質的な動作をチェックします。アプリケーションが
HTTP で応答すること、応答に Pod 名が含まれること、そしてその名前が実際に実行中のコピーと一致することです。

## 後片付け

このアプリケーションはラボ 2、3、4 で必要になります — 今は削除しないでください。維持するのは安上がりです。
nginx のコピー1つはコアの100分の2と32メガバイトしか要求せず、削除する段になれば — それは1つのコマンドで、
リソースはその同じ瞬間にノードの共有プールへ戻ります。

## これでできるようになったこと

- プラットフォームのダッシュボードがどこで終わり、あなた自身のクラスターがどこから始まるかを見分ける
- アプリケーションを1つのファイルと1つのコマンドでデプロイする
- マニフェストを読み、それぞれのブロックが何のためにあるかを説明する
- `requests` と `limits` を区別する
- Service がコピーを、アドレスのリストではなくラベルによって見つけることを理解する
- `port-forward` を通じて、ブラウザでクラスターの内側に届く

## そしてこれが vSphere だったら

VM の申請、アドレスを求めてネットワークへの申請、証明書を求めてセキュリティへの申請。うまくいって数日。
ここでは — 1つのファイルと1つのコマンドです。

**正直に言って、vSphere のほうが便利な点。** VM をデプロイすると、一人前のマシンが手に入ります。中に入り、
何でもインストールし、その場で直し、そのまま動かし続けられます。Pod は違う作りです — 変更不可であり、
「中に入って直す」ことには意味がありません。次の再起動でその修正は消えてしまうからです。これは規律を
もたらしますが、最初のうちは苛立たしく、そうでないふりをするのは愚かです。
