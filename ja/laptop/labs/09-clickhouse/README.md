# ラボ 9 · 100万行に対する分析

| | |
|---|---|
| **所要時間** | 45分 |
| **何が示せるか** | 100万件のレコードに対するレポートがミリ秒で計算され、そのセットアップは10分で済む |
| **必要なもの** | ラボ0で作ったクラスターと `~/lab.kubeconfig`、自分のテナントのダッシュボードへのアクセス、`workshopXX` という形式のテナント番号、SQLを読む力 |

> ⚠️ **SQLを読む必要のある濃密なラボです。ラボ8の直後にはスケジュールしないでください。**

## なぜこれが重要か

「入館証（Pass）」サービスは、稼働してもう半年になります。経営陣が、一見無害に聞こえる質問を
携えてやって来ます。

> 月にどれくらいのゲストが来るのか、それは増えているのか減っているのか、そして入口に行列ができるのは
> 何時なのか。月に一度、できれば毎日見たいのだが。

入館証そのものが入っているデータベースには、それは入っていません。そこにあるのは現在の申請であって、
何年分もの履歴ではありません。履歴は入館ログにあります。サービスが稼働してきた全期間の、改札を通った
一件一件の記録です。それはすでに100万行あり、これからも増え続けます。

そこから、おなじみの展開が始まります。誰かが本番データベースに対して `GROUP BY` クエリを書き、それが
2分間走って、その2分間、入館証サービスを停止させます。誰かがExcelへのエクスポートを提案し、行数の
上限にぶつかります。誰かが夜間に別のデータベースへエクスポートする仕組みを作り、半年後には、なぜレポートの
数字が現実と食い違うのか、誰も覚えていません。

正解は、**分析専用の、作りの異なる別のデータベース**です。「同じものを別のサーバーに」ではなく、内部の
作りが違うものです。このラボではClickHouseを立ち上げ、100万件の入館レコードを読み込み、レポートの
計算にどれだけ時間がかかるかを見てみます。

その過程で、**なぜカラム型データベースは分析に速く、ピンポイントの操作に遅いのか**を明らかにしていきます。
後半は前半と同じくらい重要で、それを知らないことこそが、ClickHouseを不要な場所に置いてしまう原因に
なるからです。

このラボの用語はすべて、初出のときに説明されます。そして次のセクションは、すでに導入した用語の
用語集です。

## 用語集

| 用語 | それは何か | 〜に似ているが |
|---|---|---|
| **OLAP** | 「クエリは少ないが、その一つ一つが数百万行を読む」種類のワークロード | **vRealizeの四半期レポート**に似ているが、集計の切り口は事前に計画されるのではなく、質問された瞬間に組み立てられる |
| **カラム型DBMS** | 各フィールドを別々のストリームとして保存する | **直接の対応物はない**が、問い合わせたフィールドだけを読む。ただし単一の値を変更するのは高くつく |
| **ClickHouse** | カラム型DBMS。ここではカタログから使うマネージドサービス | PostgreSQLの置き換えではなく、その補完 |
| **MergeTree** | ClickHouseにおけるテーブル保存の主要な方式 | データはパートに収められ、パートは定期的により大きなものへマージされる |
| **ソートキー（`ORDER BY`）** | パート内でデータが並べられる順序 | **ディスク上のファイルの並び順**に似ているが、これが唯一の本物の「インデックス」。テーブルごとに一つで、事前に選ぶ |
| **HTTPインターフェース** | 普通のHTTPリクエストでClickHouseと話す手段 | クエリはPOSTのボディにテキストとして送られ、答えはテーブルとして返ってくる |

このラボの残りの用語 — OLTP、行指向DBMS、パート、ミューテーション、シャード、レプリカ、Keeper —
は、それが初めて必要になるステップで、進みながら導入します。今それらを暗記する必要はありません。
実際の操作から切り離されていては、頭に残りません。

<details>
<summary><b>一覧をまとめて見たい場合は</b></summary>

| 用語 | それは何か | 〜に似ているが |
|---|---|---|
| **OLTP** | 「多数の小さな操作」という種類のワークロード。申請を作る、ステータスを変える | **自身のデータベースを扱うvCenter**に似ているが、各操作が触れるのはほんの数行。ただしその数が多い |
| **行指向DBMS** | レコードを丸ごと、行また行と保存する | **データストア上のファイル。それぞれが丸ごと収まっている**のに似ているが、まさにそのために行の変更は簡単で、カラムを素早く合計するのは難しい |
| **パート** | 一度のインサートで生まれる、ディスク上のデータの塊 | 手で触るものではないが、その数とサイズが挙動を説明する |
| **ミューテーション** | 遅延して行われる行の変更や削除 | その場では行われず、パートを丸ごと、バックグラウンドで書き直す |
| **シャード** | データの一部分を、別々のサーバー群に置いたもの | 容量の話であって、信頼性の話ではない |
| **レプリカ** | データの完全なコピー | **データストアのレプリカ**に似ているが、これは信頼性の話であって、容量の話ではない |
| **Keeper** | コピー同士が互いに協調するためのサービス | **クォーラムディスク**に似ているが、コピーが二つ以上あるときにだけ必要 |

</details>

## ステップ1. ClickHouseを発注する

📍 **場所:** ブラウザで、Cozystackのダッシュボードで、自分のテナントで。

テナント → **Create application** → `ClickHouse`。

| 項目 | 値 | なぜ |
|---|---|---|
| Name | `analytics` | 短く。あとでアドレスに打ち込むことになる |
| Replicas | **1** | 学習用のテスト環境。これは**サーバー**のコピーであって、データのコピーではない — 下の警告を参照 |
| Shards | **1** | 100万行は少ない。データが1台のサーバーに収まらなくなったときにシャードする |
| Size | `5Gi` | 100万行で数メガバイト。残りは余裕分 |
| Log storage size | `2Gi` | サーバー自身のテキストログ用のボリューム、`/var/log/clickhouse-server` |
| Log TTL | `15` | 15日より古いクエリログは破棄される |
| Storage class | `replicated` | データは別々のノード上に3つのコピーとして配置される |
| Resources preset | `u1.small` | プロセッサー1、4 GB。グルーピングはメモリ内で計算される |
| Users | ユーザー `analyst`、パスワードは自分で考える | これが作業に使うユーザー |
| ClickHouse Keeper → enabled | **オフにする** | Keeperはコピー同士を協調させる。コピーは一つ — 協調する相手がいない |

> ⚠️ **サーバーのコピーはデータのコピーではありません。** `Replicas` 項目は複数のClickHouseサーバーを
> 立ち上げますが、テーブルそのものはレプリケーションされません。次のステップで作る普通の `MergeTree` は、
> 作られたサーバー上にだけ存在します。このようなテーブルでレプリカを2にすると、インサートは一方の
> サーバーへ行き、クエリはあるときはそれに、あるときは空っぽの隣のサーバーに当たることになります。
>
> データが実際に複製されるようにするには、テーブルを `ReplicatedMergeTree` として作り、協調のために
> Keeperをオンにする必要があります。それは別の話題で、学習用のテスト環境では意味がありません。ただし
> 本番でレプリカを2にする前に、この違いは知っておく必要があります。

⚠️ **ちゃんとしたパスワードを考えて、書き留めておいてください。** あとでコマンドの中でも確認スクリプトの
中でも必要になります。あとからダッシュボードで確認することもできます。アプリケーション `analytics` →
**Secrets** タブ → `clickhouse-analytics-credentials`。

⚠️ **Keeperはデフォルトでオンで、それが正しいデフォルトです。** コピーが二つ以上になった途端、誰が何を
書いたかを合意する場所が必要になります。今回はコピーが一つで、3つのKeeperコピーは何の意味もなく
テスト環境のリソースを浪費します。フォームにこのチェックボックスが見当たらなければ、追加パラメーターの
セクションを展開してください。

### もう少し詳しく: clickhouse.yaml の中身

ラボフォルダーには `clickhouse.yaml` が含まれています。

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: ClickHouse
metadata:
  name: analytics
  namespace: tenant-workshopXX
spec:
  replicas: 1
  shards: 1
  size: 5Gi
  logStorageSize: 2Gi
  logTTL: 15
  storageClass: replicated
  resourcesPreset: u1.small
  users:
    analyst:
      password: YourPasswordHere
  backup:
    enabled: false
  clickhouseKeeper:
    enabled: false
```

`apiVersion: apps.cozystack.io/v1alpha1` — Cozystackのカタログを、APIのように見える側から見たもの。
ボタンを押すと、ダッシュボードはまさにこのオブジェクトを組み立てます。

`namespace: tenant-workshopXX` — **マネージドサービスは、ラボ0で使ったlabクラスターではなく、管理
クラスター上の自分のテナントに存在します。** これは二つの別々のクラスターであり、このラボの残りの間ずっと
それを意識しておく必要があります。

`shards` と `replicas` は、人が絶えず混同する二つの別物です。**シャードは容量の話。** データはサーバー群の
間で分割され、それぞれが自分の分を持ちます。**レプリカは信頼性の話。** それぞれがすべてを丸ごと持ちます。
100万行は数メガバイト — シャードするものは何もありません。

`users` — ユーザーのマップ。ClickHouseは与えられたパスワードで `analyst` を作り、ダッシュボードから
見える Secret `clickhouse-analytics-credentials` に入れます。

⚠️ あなたのユーザーと並んで、このSecretにもう一つ現れます — `backup`。チャートがバックアップの仕組みの
ために自分で作るものです。触る必要はありません。

`backup.enabled: false` — ラボではバックアップは不要です。本番では真っ先にオンにするものです。

`clickhouseKeeper.enabled: false` — 上記の、コピーが一つの件を参照。

このファイルは、**labクラスターではなく**テナントに対して適用します。

```bash
# --kubeconfig はアクセスファイルを明示的に指定し、KUBECONFIG 変数を上書きする。
# だから発注は、labクラスターではなく管理クラスター上のテナントへ向かう。
kubectl --kubeconfig ~/.kube/workshop apply -f clickhouse.yaml
```

テナントのkubeconfigはダッシュボードから取得します：**Info → Secrets タブ →
`kubeconfig-tenant-workshopXX`**。それを `~/.kube/workshop` に保存してください。

準備ができるまで待ちます。それは2〜4分です。サーバーが立ち上がり、ボリュームが作られ、ユーザーが
セットアップされます。

## ステップ2. 作業用Podをセットアップする

📍 **場所:** ノートPC上で、labクラスターで。

ここで一度立ち止まって、構成を理解しておく必要があります。

**Pod** はKubernetesにおける実行の最小単位です。常に一緒に生き死にする一つ以上のコンテナです。vSphereで
最も近い対応物は仮想マシンですが、自身のオペレーティングシステムを持たず、自身のディスクも持ちません。
この先、この語は絶えず出てきます。

**ClickHouseは、管理クラスター上の自分のテナントに存在します。** テナントでのあなたのロールは、サービスの
発注や削除は許しますが、そこで自分のPodを走らせたりポートフォワードしたりすることは許しません。これは
不具合ではなく、境界です。

**あなたの作業場所は、ラボ0で作ったlabクラスターです。** そこから、内部アドレス経由でClickHouseに
到達します。

```
chendpoint-clickhouse-analytics.tenant-workshopXX.svc.cozy.local:8123
```

この名前を部分に分解してみましょう。

| 部分 | 何を意味するか |
|---|---|
| `chendpoint-` | ClickHouseオペレーターが自身のServiceに付けるプレフィックス |
| `clickhouse-` | Cozystackカタログがアプリケーション名に付けるプレフィックス |
| `analytics` | ダッシュボードで設定した名前 |
| `tenant-workshopXX` | あなたのテナント。自分の番号に置き換える |
| `svc.cozy.local` | 管理クラスターの内部名ゾーン |
| `8123` | HTTPインターフェースのポート。9000番もある — ネイティブプロトコル用 |

作業用Podを立ち上げます。自分のテナント番号と自分のパスワードに置き換えてください。

```bash
# ここから先はすべてlabクラスターで起きるので、kubectl をそちらに切り替える。
export KUBECONFIG=~/lab.kubeconfig
# run は指定したイメージから単一のPodを作る — クラスター内の使い捨ての小さなマシン。
# このイメージには curl が入っていて、それで十分：別途 ClickHouse クライアントは要らない。
#   --restart=Never  中のコマンドが終わっても、もう一度立ち上げない
#   --env=CH_URL     ストレージのHTTPインターフェースのアドレス。末尾のスラッシュは必須
#   --env=CH_AUTH    普通のHTTP認証用の「ユーザー:パスワード」の組
#   --command --     二つのダッシュより後ろはすべて、Podが実行するコマンド
# sleep 86400 = 「1日何もしない」：Podは作業場所としてだけ必要。
kubectl run ch-workbench \
  --image=curlimages/curl:8.11.1 \
  --restart=Never \
  --env=CH_URL="http://chendpoint-clickhouse-analytics.tenant-workshopXX.svc.cozy.local:8123/" \
  --env=CH_AUTH="analyst:YourPasswordHere" \
  --command -- sleep 86400
# wait はPodが起動するまでターミナルを止めるが、2分より長くは待たない。
kubectl wait --for=condition=Ready pod/ch-workbench --timeout=120s
```

**なぜアドレスとパスワードを、コマンド内にじか書きせずPodの変数にするのか。** `kubectl exec` に打ち込む
ものはすべて、シェルの履歴と、ノード上のプロセス一覧に残ります。Podの変数は一度だけ設定され、それ以降
パスワードはコマンドに現れません。

⚠️ **これで問題が完全に解決するわけではなく、それを先に正直に言っておくほうが誠実です。** `--env`
経由で渡した値はPodの記述の中に残ります。あなたのnamespaceでPodを読む権限を持つ者からは見えますし、
クラスターのデータベースの中にあり、監査ログにも入ります。学習用のテスト環境なら許容できますが、本番用
なら許容できません。そこではパスワードは別のクラスターオブジェクト（`Secret` — 機微な値のためのオブジェクト）
に入れ、それへの参照で結び付け、オブジェクト自体はシークレットストアから満たします。それがSecretに
関するラボの内容です。

さて、毎回 `curl` を打たなくて済むように、短いコマンドを設定しましょう。まず、それが何でできているかを
分解します。

<details>
<summary><b>このコマンドを、一片ずつ分解する</b></summary>

`kubectl exec -i ch-workbench` — 作業用Podの中で何かを実行する。`-i` フラグは標準入力を中へ転送する。
これがないとクエリはClickHouseに届かない。

`sh -c '…'` シングルクォートで — 文字列はそのまま中へ渡され、`$CH_AUTH` は**Podの中で**、Podの変数から
展開される。あなたのノートPCはこれらの値を見ず、コマンド履歴にも書き込まない。

`curl -sS` — 静かに、しかしエラーは報告する。`-s` は進行インジケーターを消し、`-S` は `-s` が本来なら
呑み込んでしまうエラーメッセージを呼び戻す。

`-u "$CH_AUTH"` — ユーザー名とパスワード。ClickHouseは普通のHTTP認証を受け付ける。

`--data-binary @-` — 「リクエストボディを標準入力からそのまま取る」。まさにこうしてSQLはClickHouseに
入る。**クエリは普通のPOSTリクエストのボディ**であって、何か特別なプロトコルではない。ゆえに一つの帰結：
ClickHouseに到達するのにドライバーは要らない。`curl` で十分で、それはトラブルシューティングのときにしばしば
助けになる。

`?default_format=PrettyCompact` — 答えを返す形式。`PrettyCompact` は人間向けのテーブル。形式は30種類以上
あり、下では `JSON` が必要になる。

</details>

```bash
# ch を定義する — 長いコマンドの短い名前。ここから「ch」は次を意味する：標準入力に届いた
# SQLをClickHouseへ送り、答えをテーブルとして表示する。
# この名前は、このターミナルウィンドウを閉じるまで生きている。新しいウィンドウでは定義し直す。
ch() {
  kubectl exec -i ch-workbench -- sh -c \
    'curl -sS -u "$CH_AUTH" --data-binary @- "$CH_URL?default_format=PrettyCompact"'
}
```

接続を確認しましょう。

```bash
# echo は文字列を出力し、| でそれを ch の入力へ渡す。SELECT version() は考えうる
# 最も安いクエリ：サーバーはディスクから何も読まず、ただ自分のバージョンを名乗るだけ。
echo 'SELECT version()' | ch
```

**見えるべきもの** — 小さな枠に入ったClickHouseのバージョン番号。

⚠️ **コマンドが沈黙するか `Could not resolve host` / `Connection refused` で失敗する場合** — この先へ
進む意味はありません。ありがちな原因を、可能性の高い順に：`workshopXX` を自分の番号に置き換えていない、
ダッシュボードのアプリケーションがまだ準備できていない、Service名のタイプミス。答えが
`Authentication failed` なら、接続はできていてパスワードが間違っています。正しい `CH_AUTH` でPodを
作り直してください。

Windows PowerShellのユーザーは、あなた用のバージョンを：

```powershell
# $input — 左のパイプラインから関数に入ってきたもの。
# 行末のバッククォートは、コマンドを次の行へ続ける。
function ch {
  $input | kubectl exec -i ch-workbench -- sh -c `
    'curl -sS -u "$CH_AUTH" --data-binary @- "$CH_URL?default_format=PrettyCompact"'
}
"SELECT version()" | ch
```

## ステップ3. 入館ログのテーブルを作る

📍 **場所:** ノートPC上で、labクラスターで。

入館ログ用のテーブルを設定します。改札を通るごとに1行です。ファイル `01-schema.sql` はラボフォルダーに
あり、適用する前に読んでおく価値があります。その中の2行が、あとでどのクエリが速く出て、どれが速く
出ないかを決めます。

<details>
<summary><b>スキーマを一行ずつ見ていく</b></summary>

```sql
-- IF NOT EXISTS — テーブルが既に存在しても文句を言わない。このファイルは2回適用できる。
CREATE TABLE IF NOT EXISTS passes
(
    pass_id      UInt64,                 -- 入館証の番号
    created_at   DateTime,               -- その人が改札を通った時刻
    guest_name   String,                 -- ゲストの名前：みなそれぞれ固有
    host_dept    LowCardinality(String), -- 受け入れ先の部署：値は少ない
    entrance     LowCardinality(String), -- 入口：三つある
    pass_type    LowCardinality(String), -- 一回きり、週次、車両
    duration_min UInt16                  -- ゲストが中に滞在した分数
)
ENGINE = MergeTree               -- 保存の仕方：ディスク上のパート、バックグラウンドでのマージ
ORDER BY (created_at, entrance)  -- データをどの順序で並べるか；これがインデックスでもある
```

`UInt64`、`UInt16` — 8バイトと2バイトの符号なし整数。ClickHouseでは型のサイズを意識して選びます。
10億行×余分な4バイトで4ギガバイトです。分単位の滞在時間には、2バイトで十分すぎます。

`LowCardinality(String)` — 異なる値が少ない文字列。入口名は三つ、部署は五つです。ClickHouseはこうした
フィールドを辞書として保存します。ディスク上には、100万回繰り返される単語ではなく、数値が並びます。
節約は絶大で、それを数字で見ることになります。

⚠️ **ルールはこうです。** 異なる値が数千までなら `LowCardinality`、それを超えるなら普通の `String`。
ほぼ常に一意なゲストの名前を `LowCardinality` で包むのは、事態を悪くすることを意味します。辞書がデータ
そのものより大きくなってしまいます。

`ENGINE = MergeTree` — 保存の主要な方式。インサートのたびに新しい**パート**がディスクに置かれ、パートは
バックグラウンドでより大きなものへマージされます。ゆえに、ちなみに重要な実践的ルールが導かれます。
インサートは**多数の行のバッチで**行うべきで、一件ずつではありません。100万回の単一行インサートは
100万個のパートを作り、サーバーを落とします。

```sql
ORDER BY (created_at, entrance)
```

これがファイルの中で最も重要な行で、データを書き始める前に選びます。

`ORDER BY` は**データがディスク上に物理的にどの順序で並ぶか**を設定します。それはまた唯一の本物の
インデックスとして働きます。ClickHouseは数千行ごとにマークを保持し、それを使って、ファイルのどの部分を
まるごと読み飛ばせるかを割り出します。

「3月に何件の入館があったか」というクエリは「ファイルのこの区間を読む」に変わります。「番号424242の
入館を探す」というクエリは、何にも変わりません。`pass_id` はソートキーに入っていないので、カラム全体を
読まざるを得ません。これは別のステップで見ますが、実装の欠陥ではなく、設計の直接の帰結です。

**なじみのある世界からのアナロジー。** ソートキーは、紙の入館証を書庫にどの順序で綴じるかを決めるのに
似ています。日付順か、姓の順か。日付順に綴じれば、3月のフォルダーは瞬時に取り出せますが、特定のイワノフは
一枚ずつめくって見つけることになります。そして誰も、後から100万枚を綴じ直したりはしません。

</details>

**適用します。**

```bash
cd labs/09-clickhouse
# < はファイルを読んで ch の入力へ流し込む、つまりファイルの内容を単一のクエリとして
# ClickHouseへ送る。CREATE TABLE は空の答えを返す — それが成功。
ch < 01-schema.sql
```

## ステップ4. 100万件のレコードを生成する

📍 **場所:** ノートPC上で、labクラスターで。

入館データがまだ一件もなく、100万件が必要です。それをClickHouseの中でそのまま生成します。エクスポートも
スクリプトも中間ファイルもなしです。まず、生成器が何でできているかを見ましょう。

<details>
<summary><b>生成器を一行ずつ見ていく</b></summary>

```sql
INSERT INTO passes
SELECT …
FROM numbers(1000000)
```

`numbers(1000000)` — 組み込みの生成テーブル：0から999999までの単一カラム `number` を持つ100万行。
ディスクからは何も読まず、実体として存在せず、その場で計算されます。これは定番の手口です。ClickHouseの
テスト用データはすべてこうして作られます。

```sql
    number AS pass_id,
```

入館証の番号。`number` が一意なので、一意です。

```sql
    addDays(
        toDateTime('2026-01-01 00:00:00'),
        toUInt16(sqrt(cityHash64(number, 'day') % 57600))
    )
```

`cityHash64(number, 'day')` — 高速なハッシュ関数。行の番号から擬似ランダムな数を作り、同じ入力は常に
同じ結果を返します。第2引数の `'day'` は「ソルト」です。ソルトが違えば、同じ番号でも違う結果になります。
こうして単一の `number` から、いくらでも独立したランダム値を作れます。

`% 57600` は0から57599までの数を与え、その `sqrt` は0から239、つまり8ヶ月内のある日を与えます。ここの
平方根は飾りではありません。**データを期間の終わりのほうへ集中させます。** ゲストは時とともに増えていきます
— 現実がそうであるように。そしてまさにそれが、経営陣がレポートで見たいものです。

```sql
            [8, 9, 9, 10, 10, 10, 11, 11, 12,
             13, 14, 14, 15, 15, 15, 16, 17, 18][1 + cityHash64(number, 'hour') % 18]
```

到着時刻の「時」。均一な「8から18まで」の代わりに、時が異なる頻度で繰り返される配列から値を取ります。
10は3回、15は3回、8はたった1回現れます。これによって**はっきりした二つのピーク** — 昼前と昼後 — が
生まれます。まさにそれが、経営陣が探してほしいと言ったもので、テストデータの中に、これから探そうと
しているものが入っているのは良いことです。

⚠️ ClickHouseの配列の添字は、0ではなく1から始まります。ゆえに `1 + …`。

```sql
    ['Северная', 'Северная', 'Северная',
     'Южная', 'Южная', 'Западная'][1 + cityHash64(number, 'entrance') % 6] AS entrance
```

不均一な分布のための同じ手口。北の入口が流量の半分、南が三分の一、西が残りを受け持ちます。均一な
データはレポートの中で不自然に見え、何も示しません。

```sql
    toUInt16(30 + cityHash64(number, 'duration') % 300) AS duration_min
```

滞在時間は30から329分。`toUInt16` が必要なのは、カラムの型が明示的に宣言されているのに対し、算術の
結果がそれより幅広いためです。

**どれだけ時間がかかったか。** 100万行が、まるごとサーバーの中で、数秒で生成され書き込まれました。
データはネットワークを渡らず、あなたのノートPCを通らず、中間ファイルに置かれませんでした。テスト用データを
作る通常のやり方 — 一件ずつインサートするスクリプト — と比べてみてください。

</details>

**適用します。**

```bash
# このファイルには単一の INSERT … SELECT が入っている：ClickHouseは100万行を自分で考え出して書き込む、
# 一度もサーバーの外に出ることなく。
ch < 02-generate.sql
```

**見えるべきもの** — 空の答えと、数秒後にプロンプトが戻ってくること。`INSERT` からの空の答えが成功です。

得られたものを確認しましょう。

```bash
# 条件なしの count() は「テーブルには全部で何行あるか」という問いに答える。
echo 'SELECT count() FROM passes' | ch
```

**見えるべきもの** — `1000000`。

## ステップ5. 経営陣が求めてきたレポート

📍 **場所:** ノートPC上で、labクラスターで。

まさに経営陣が求めてきたレポート：月ごとに何人のゲストが来たか、訪問は平均どれくらい続くか、何時に
最も多く人が到着するか、どの入口がより混むか。ファイル `03-report.sql` は単一のクエリで、実行する前に
分解します。

<details>
<summary><b>レポートを一行ずつ見ていく</b></summary>

```sql
-- データに現れる月ごとに、レポートの行が1つ。
SELECT
    toStartOfMonth(created_at)          AS month,        -- どの月に割り当てるか
    count()                             AS guests,       -- そこに何件の入館があったか
    round(avg(duration_min))            AS avg_minutes,  -- 平均の訪問時間
    topK(1)(toHour(created_at))[1]      AS peak_hour,    -- 最も多い到着時刻の「時」
    topK(1)(entrance)[1]                AS busiest_entrance  -- 最も多い入口
FROM passes
GROUP BY month   -- 一つの月のすべての行を、単一の答えの行にまとめる
ORDER BY month   -- 月を昇順で出力する
```

`toStartOfMonth` は正確な時刻を、その月の初日に変えます。期間ごとにグルーピングする古典的な手口です。
「年と月でグルーピング」の代わりに、グルーピングにもソートにも使う単一の値です。

`count()` — グループに落ちた行数。それがまさに「月ごとに何人のゲストか」です。

`topK(1)(x)[1]` — グループ内で `x` の最も多い値。`topK(1)` は要素1個の配列を返し、`[1]` がそれを取り
出します。こうしてピークの時刻も最も混む入口も、単一のレポート行に収まります。

このクエリに**ない**ものを、別途書き留めておく価値があります。サブクエリも、一時テーブルも、JOINも
ありません。すべてがデータに対する単一のパスで計算されます。

</details>

**適用します。**

```bash
# テーブル全体に対する一つのグルーピング。答えの行数は、データに現れる月の数だけになる。
ch < 03-report.sql
```

**見えるべきもの** — 8行、月ごとに1行、ゲスト数が増えていくもの。

さて肝心なのは、**計算にどれだけかかったか**です。クエリ末尾の `JSON` 形式は、答えに統計ブロックを
付け加えます。

```bash
# <<'SQL' … SQL — ファイルなしで、複数行のテキストをコマンドの入力へ渡す方法。
# SQL を囲むクォートは「中身をそのままにする」の意味：さもないとシェルが、
# クエリの中の文字を自分のものとして解釈しようとしてしまう。
ch <<'SQL'
-- 同じレポートを、2カラム — 月とゲスト数 — に絞ったもの。
SELECT toStartOfMonth(created_at) AS month, count() AS guests
FROM passes
GROUP BY month
ORDER BY month
FORMAT JSON  -- 答えをテーブルではなくJSONで返す：その中に統計ブロックが入っている
SQL
```

出力を末尾までスクロールします。

```json
    "statistics": {
        "elapsed": 0.0089,
        "rows_read": 1000000,
        "bytes_read": 4000000
    }
```

**100万行、約9ミリ秒。** あなたの数字はあなた自身のものになりますが、桁は同じ — 単位ミリ秒か、数十
ミリ秒です。

<details>
<summary><b>この同じレポートを普通のデータベースでやると</b></summary>

おなじみのシナリオを取りましょう。入館ログはPostgreSQLかMS SQLの中に、入館証サービスそのもののすぐ
隣にあります。

**クエリに何が起こるか。** 行指向のデータベースはレコードを丸ごと保存します。番号、時刻、ゲストの名前、
部署、入口、種別、滞在時間 — すべてが一行に、次々と並びます。月ごとに `count()` を計算するには、
一件一件の行を通らねばならず、それは**ディスクからすべてのフィールドを読む**ことを意味します。レポートに
は登場しないゲストの名前も含めてです。100万行なら数十秒、1000万行なら数分です。

これは `created_at` へのインデックス、カバリングインデックス、マテリアライズドビュー、あるいは事前集計
テーブルで回避できます。これらの解決策はどれも機能しますが、どれもこう意味します。誰かが**どのレポートが
求められるかを事前に知っておく**必要があった、と。別の切り口を求められれば、また振り出しに戻ります。

**サービスに何が起こるか。** 重いクエリは、本番のワークロードとディスクとメモリを取り合います。レポートを
計算している間、入口の警備員はぐるぐる回るインジケーターを見ることになります。そこから「レポートは夜間
だけ」というルールが生まれ、そこから — リードレプリカ、夜間エクスポート、食い違う数字、そして「なぜ
レポートは昨日のデータを表示するのか」という問いが生まれます。

**実際に人がすること。** 隣に、分析用に作られた二つ目のデータベースを立て、そこにデータを流し込みます。
まさに今わたしたちがやったことです。ただし二つ目のデータベースは、ロールアウトのプロジェクトで四半期を
かけてではなく、カタログから10分で立ち上がりました。

| | 行指向（PostgreSQL） | カラム型（ClickHouse） |
|---|---|---|
| 番号で入館証を探す | インデックス経由でマイクロ秒 | カラム全体を読む |
| 一つの入館証のステータスを変える | マイクロ秒 | バックグラウンドでパートを書き直す |
| 月ごとにゲストを数える | 秒か分 | ミリ秒 |
| 行を追加する | 日常的 | バッチのほうが良い、一件ずつは悪い |
| トランザクション | 本格的 | 通常の意味では存在しない |

どちらのカラムも「より良い」わけではありません。これらは違う仕事のための道具で、正解はほぼ常に両方、
それぞれをあるべき場所に、です。

</details>

## ステップ6. なぜ速いのか：カラムを見る

📍 **場所:** ノートPC上で、labクラスターで。

「カラム型」という語は、数字を見るまでは抽象的に聞こえます。

```bash
ch <<'SQL'
-- テーブルの各カラムがどれだけ場所を取るかを、ClickHouse自身に尋ねる。
SELECT
    name,                                                    -- カラムの名前
    formatReadableSize(data_compressed_bytes)   AS on_disk,  -- ディスク上にどれだけ載っているか
    formatReadableSize(data_uncompressed_bytes) AS raw,      -- 圧縮なしならどれだけになるか
    round(data_uncompressed_bytes / data_compressed_bytes, 1) AS ratio  -- 何倍に圧縮されたか
FROM system.columns   -- システムテーブル：この中でClickHouseは自分自身を記述する
WHERE database = currentDatabase() AND table = 'passes'   -- わたしたちのテーブルだけ
ORDER BY data_compressed_bytes DESC   -- 重いカラムを上に
SQL
```

**見えるべきもの** — おおよそこんな絵です。

```
name          on_disk    raw       ratio
guest_name    5.20 MiB   13.4 MiB  2.6
pass_id       3.81 MiB   7.63 MiB  2.0
created_at    1.20 MiB   3.81 MiB  3.2
duration_min  1.10 MiB   1.91 MiB  1.7
entrance      35.1 KiB   1.00 MiB  29.2
pass_type     41.0 KiB   1.05 MiB  26.1
host_dept     52.3 KiB   1.10 MiB  21.4
```

あなたの数字はあなた自身のものになりますが、比率は同じです。

<details>
<summary><b>ここから何が見えて、なぜそれが速さを説明するのか</b></summary>

**第一に、各フィールドが別々に載っています。** それが「カラム型」の意味です。行指向のデータベースでは、
ディスクは「1行目まるごと、2行目まるごと、3行目まるごと」と進みます。ここでは「`created_at` を全部
ひと続きで、`entrance` を全部ひと続きで、`guest_name` を全部ひと続きで」です。

ゆえに、この全体が企てられた目的そのものである帰結が導かれます。**クエリは、自分が言及するフィールドだけ
を読む。** 月次レポートには `created_at` と行カウンターが必要です。それは1メガバイト強を読み、その5倍を
占めるゲストの名前には触れません。

行指向のデータベースは、同じクエリのためにすべてを読みます。書き方が下手だからではなく、フィールドが
混ざり合って載っているからです。50万1件目の行の時刻に辿り着くには、その時刻を他のすべてと一緒に抱えている
ブロックを読まなければなりません。

**第二に、`entrance` の `ratio` を見てください。** 29倍です。三つの選択肢から取られた100万個の値が、
ほとんど無に等しいところまで圧縮されました。

これが `LowCardinality` の働きです。ディスク上には3つの文字列の辞書と100万個の小さな数があり、それと
並んで一般的な圧縮が効きます。この圧縮にとって、並んだ同じ数は贈り物です。値がどれも異なる `guest_name`
では、圧縮はたったの2.5倍です。

**第三に、そしてこれが直感を裏切りますが、圧縮は物事を遅くするのではなく速くします。** 解凍は余分な
作業のように思えます。実際にはボトルネックはプロセッサーではなくディスクです。35キロバイトを読んで解凍
するほうが、1メガバイトを読むより速いのです。だからこそカラム型データベースは積極的に圧縮し、二重に勝ちます
— 場所でも時間でも。

</details>

クエリが本当に少ししか読まないことを確かめましょう。一つの小さなカラムに対して数えます。

```bash
ch <<'SQL'
-- 100分より長い訪問を数える。このクエリは7カラムのうち1つだけを名指す — だから
-- テーブルのほんの一部だけを読むはず。それを bytes_read で確かめる。
SELECT count() FROM passes WHERE duration_min > 100 FORMAT JSON
SQL
```

出力末尾の `bytes_read` を見て、それをテーブルのデータ量と比べます。

```bash
ch <<'SQL'
-- 全カラムの非圧縮の量を合計する。それがまさに「全部でどれだけデータがあるか」— 
-- 前の出力の bytes_read と比較すべき数字。
SELECT formatReadableSize(sum(data_uncompressed_bytes)) AS total
FROM system.columns
WHERE database = currentDatabase() AND table = 'passes'
SQL
```

⚠️ **比較すべきは非圧縮の量であって、ディスク上のサイズではありません。** クエリ統計の `bytes_read` は、
データベースが解凍して読んだもの — 非圧縮の数字です。それを `bytes_on_disk` で割ると、圧縮済みデータに
対する割合が出て、圧縮のよく効くテーブルではそのような「割合」は軽々と100パーセントを超えます。数字は
比較可能でなければなりません。さもないと、その数は見た目はきれいでも無意味です。

このクエリは100万行を通過しながら、データのほんの数パーセントしか読みませんでした。`duration_min` を
読み、`guest_name` には触れませんでした。

## ステップ7. ピークを見つける

📍 **場所:** ノートPC上で、labクラスターで。

経営陣の質問の後半は、入口の行列についてです。一日の各時刻に何件の入館が落ちたかを数え、それをターミナル
にそのままバーとして描きます。クエリは二つの部分からなります — 実行する前に分解します。

<details>
<summary><b>クエリを分解する</b></summary>

内側のクエリは普通のグルーピングです。一日の各時刻に何件の入館が落ちたか。11行が出てきます。

外側のクエリはそれに絵を付け加えます。`bar(value, from, to, width)` は擬似グラフィックのバーを描きます
— まさに、Excelを開かずにターミナルで結果を眺められるように作られた、ClickHouseの組み込み関数です。

`max(guests) OVER ()` — ウィンドウ関数：**結果全体**にわたる最大値であって、グループにわたるものでは
ありません。`OVER` の後ろの空の括弧は「ウィンドウは行の集合全体」を意味します。これは、いちばん長い
バーがちょうど50文字になり、残りがそれに比例するために必要です。

なぜ `OVER ()` なしにただ `max(guests)` と書けなかったか：それは集約関数になり、11行を1行に潰して
しまうからです。ウィンドウ関数は同じものを計算しますが、行はその場に残します。

</details>

```bash
ch <<'SQL'
SELECT
    hour,                                     -- 一日の中の時刻
    guests,                                   -- この時刻に落ちた入館の数
    bar(guests, 0, max(guests) OVER (), 50) AS chart  -- 擬似グラフィックのバー
FROM
(
    -- 内側のクエリ：時刻による普通のグルーピング
    SELECT toHour(created_at) AS hour, count() AS guests
    FROM passes
    GROUP BY hour
)
ORDER BY hour   -- 時刻を昇順に、絵が上から下へ読めるように
SQL
```

**見えるべきもの** — 二つの山：朝の10時ごろと、午後の3時ごろ。

経営陣への答えは出来上がりです。ピークは10時と15時、そして入口にもう一人配置する意味があるのは、まさに
この時間帯です。

ついでに、クエリログも見てみましょう — ClickHouseはそこにすべてのクエリを記録します。

```bash
ch <<'SQL'
-- ClickHouseは、実行されたすべてのクエリをシステムテーブル system.query_log に記録する。
SELECT
    event_time,                                       -- クエリが終わった時刻
    query_duration_ms,                                -- 何ミリ秒かかったか
    formatReadableQuantity(read_rows) AS rows_read,   -- 何行読んだか
    formatReadableSize(read_bytes)    AS bytes_read,  -- その際に何バイト引き上げたか
    -- クエリのテキスト：中の改行を潰して先頭50文字を取る、
    -- さもないと出力が画面に収まらない
    substring(replaceRegexpAll(query, '\\s+', ' '), 1, 50) AS query
FROM system.query_log
WHERE type = 'QueryFinish'  -- 終わったものだけ：開始には別のレコードがある
  AND user = 'analyst'      -- 自分のものだけ、サーバー自身のサービスクエリは除く
ORDER BY event_time DESC    -- 最近のものを上に
LIMIT 10                    -- そして10で十分
SQL
```

あなたのクエリの全履歴が、所要時間と読んだ量とともに。それは普通のテーブルで、ログ用ボリュームではなく
データ用ボリュームに置かれています。発注フォームの `Log storage size` は、このログではなくサーバーの
テキストログについてです。このログの保持期間は `Log TTL` で設定されます。本番では、まさにこのテーブルが
「なぜ昨日の夜7時にすべてが遅かったのか」という問いに答えます。

⚠️ ログは数秒に一度ディスクへ書き出されるので、ごく最新のクエリはまだそこにないかもしれません。コマンドを
繰り返してください。

## 予測できる失敗 · 番号で単一の入館証を探す

レポートは出来上がりました。警備が日常的な依頼を持ってやって来ます。**番号424242の入館を探す。**

クエリはおのずと思い浮かびます。

```bash
ch <<'SQL'
-- 入館証の番号で単一の行を探す。SELECT * は「全カラムを返す」の意味。
SELECT * FROM passes WHERE pass_id = 424242 FORMAT JSON
SQL
```

行は見つかります。でもそれではなく、出力末尾の統計を — `rows_read` を見てください。

> **読み進める前に、立ち止まって考えてください。**
>
> 一つの行を返すために、データベースは何行読んだでしょうか。`pass_id` にインデックスを張ったPostgreSQL
> なら何行読むでしょうか。そしてなぜ、その差はちょうどそれほど大きいのでしょうか。

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

`rows_read` はおよそ **1 000 000** になります。単一の行を返すために、ClickHouseは `pass_id` カラム
全体を読みました。

その理由は、このラボの少し前に取り組んだものです。**ClickHouseにおける唯一の本物のインデックスはソート
キー**であり、わたしたちのそれは `(created_at, entrance)` です。データは `pass_id` で順序付けられておらず、
パートを飛ばす手がかりが何もなく、残されているのはフルスキャンだけです。

`pass_id` にインデックスを張ったPostgreSQLなら、ツリーのページを数枚と1行を読むでしょう。5桁の差 — 
しかもClickHouseに有利なほうではありません。

さて同じことを、今度は正しくやります。警備は普通、番号だけでなく**それがいつ起きたか**も知っています。

```sql
-- 同じ検索だが、時間の枠を付ける。created_at への条件はソートキーに落ち、
-- ClickHouseはその日から外れるものをすべて捨てる。
SELECT * FROM passes
WHERE created_at >= '2026-03-01' AND created_at < '2026-03-02'
  AND pass_id = 424242
FORMAT JSON
```

今度は `rows_read` を見てください — 100万ではなく数千です。`created_at` への条件がソートキーに落ち、
ClickHouseは必要な区間を除くすべてのパートを捨てました。もし入館証が別の日のものだったら見つからない
かもしれません — 大事なのは見つかったことではなく、読まれた行の数です。

**このエラーより広い教訓。** ClickHouseは「速いデータベース」ではありません。それは一種類の仕事のために
作られたデータベースです。少数のカラムにわたって多数の行を読み、何かを計算する。その仕事では、行指向の
データベースを桁違いに引き離します。その反対 — 一つの行を探す、一つのフィールドを変える、トランザクションを
ロールバックする — では、同じだけの桁数で後れを取ります。

ゆえに、持ち帰る価値のある実践的ルールが導かれます。

| タスク | どこで |
|---|---|
| 入館証を発注する、変える、取り消す | サービスの隣にある普通のデータベース |
| 特定の入館証を番号で探す | 同じ場所 |
| 年次レポート、ファネル、ピーク、トレンド | ClickHouse |
| イベントログ、メトリクス、ログ | ClickHouse |

両方のデータベースが一つのテナントに、両方ともカタログから、両方とも数分で立ち上がります。もはや
「すべてを一つで」を選ぶ必要はありません — そしてそれこそが、新しいデータベースのたびに新しいVMと新しい
チケットを意味した世界と比べての、おそらく最大の変化です。

</details>

## ステップ8. ここでの不便な点を正直に

📍 **場所:** ノートPC上で、labクラスターで。

あるゲストが姓を変え、1件のレコードを直す必要があります。普通のデータベースなら、それは `UPDATE` で
マイクロ秒です。

構文を先に押さえておいてください。`UPDATE passes SET …` ではなく `ALTER TABLE … UPDATE` です。これは
作者の気まぐれではなく、正直な警告です。**あなたが実行するのは、行の更新ではなく、テーブルの変更です。**

```bash
ch <<'SQL'
-- 1行のゲストの名前を変える。このコマンドはすぐに制御を返すが、作業はそこで終わらない：
-- ClickHouseはそれをキューに入れ、バックグラウンドで実行する。
ALTER TABLE passes UPDATE guest_name = 'Иванов И. И.' WHERE pass_id = 424242
SQL
```

何が起きているか見てみましょう。

```bash
ch <<'SQL'
-- テーブルへの遅延した変更のキュー — もう一つのClickHouseシステムテーブル。
SELECT
    command,       -- 何をするよう命じられたか
    is_done,       -- 作業が終わっていれば1
    parts_to_do,   -- 書き直すべきパートがあといくつ残っているか
    create_time    -- タスクがキューに入れられた時刻
FROM system.mutations
WHERE table = 'passes'
ORDER BY create_time DESC
SQL
```

<details>
<summary><b>ミューテーションとは何か、なぜそれが高くつくのか</b></summary>

コマンドはすぐに制御を返し、作業のほうはキューに入りました。こうした遅延した作業は**ミューテーション**と
呼ばれ、`system.mutations` で見えます。`is_done` は終わったかどうかを、`parts_to_do` は書き直すべきパートが
あといくつ残っているかを示します。

なぜ書き直すのか。データはカラムの形で圧縮されたパートに載っています。圧縮ブロックの中の単一の値を
変えることはできません — ブロックを解凍し、変更し、圧縮し、新たに書き込まねばなりません。実際には
ClickHouseは**パート全体**を、その全カラムごと書き直します。

わたしたちの100万行なら、それはコンマ以下秒であり、`is_done` はおそらくもう `1` です。10億行のテーブル
なら、同じ操作は数時間のディスク作業であり、書き直しの間、場所の使用量は2倍になります。

ゆえに、ClickHouseの世界では当然とされているルールが導かれます。

- **データは変えない。** 追記する。入館ログはそもそも変わるべきではありません。入館は起きたか起きなかったか
  のどちらかです
- どうしてもレコードを直す必要があるなら、行の新しいバージョンを書き、読むときに新しいほうを取ります。
  これには別種のテーブルがあります（`ReplacingMergeTree`）
- 古いデータの削除は、クエリではなく保持期間（`TTL`）で行います。「3年より古い行を捨てる」。すると
  個々の行ではなく、パート全体が削除されます
- 一括の編集は、100個の小さな操作の代わりに、めったに行わない単一の操作にまとめます

**そしてここに完全に欠けているもの：通常の意味でのトランザクション。** 一つの口座から別の口座へ、両方の
操作が適用されるかどちらも適用されないかのどちらかになるようにお金を移す、ということはClickHouseでは
できません。これは実装の欠落ではありません — 読み取り速度のための意図的な放棄です。だからこそClickHouseは
入館証サービスの下ではなく、その隣に置かれるのです。

</details>

## そしてvSphereでこれをやると

分析データベース用の別のマシン — そしてほぼ即座に、一つでは足りないと判明します。レプリカ用の二つ目と、
日次エクスポートのための場所が要ります。「月に何人のゲストか」というレポートは、それ自身のハードウェア、
それ自身の監視、それ自身のオーナーを持つインフラのプロジェクトへと変わります。

ここでは — カタログのエントリと10分、100万行の生成を含めてです。

**vSphereのほうが便利なところを、正直に。** データベースの載ったVMは、歩いて近づけるマシンです。SSHで
ログインし、topを見て、設定をいじり、その隣にスクリプトを置き、危険な操作の前にスナップショットを取って、
うまくいかなかったらロールバックします。マネージドサービスはこれを**わざと**与えません。テナントでは、
Podに `exec` することもログに入ることも許されません。あなたはサービスを、その下のマシンではなく、発注
フォームを通じて管理します。

すべてが動いている限り、これは利点です — 壊す手立てが少ない。何かが奇妙な振る舞いをするとき、この制約は
痛切に感じられます。管理者の見慣れた一連の操作は使えず、残されているのはプラットフォームを運用する者に
頼ることだけです。クエリログとメトリクスはこの痛みの一部をカバーしますが、すべてではなく、すべてをカバー
するふりをするのは不誠実でしょう。

そしてもう一つ、人が後になって思い出すこと。マネージドサービスとは、誰か他人のデフォルトを意味します。
ClickHouseのバージョン、パートのマージのパラメーター、メモリの設定は、あなたのために選ばれています。
たいていは分別を持って、ときにあなたのワークロードには合わず、そしてそれらを自分のマシンでのように自由に
変えることはできません。
