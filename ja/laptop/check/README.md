# チェックスクリプト

各ラボのフォルダには `check.sh` が置かれています。これはラボが本当に完了しているか —
「ファイルを適用した」ことではなく、**実質的に動作している**ことを検証します。

実行は好きなときに自分で行います。結果はターミナルに表示されるレポートと、どこにでも添付できる
アーティファクトファイルです。コミュニティチャット、認定申請、自分のメモなど、どこにでも添付できます。

## 実行方法

```bash
cd labs/03-scale
./check.sh
```

### Windows を使っている場合

スクリプトは bash で書かれており、Windows そのものでは実行できません。**WSL** — 管理者権限の
PowerShell で1つのコマンドを実行するだけで導入できる Linux サブシステム — が必要です：

```powershell
wsl --install
```

コンピューターは再起動を求めてきます。再起動後に Ubuntu のコンソールが開きます。そこから先は
みんなと同じですが、WSL の中では `kubectl` を自分で用意する必要があります：

```bash
sudo snap install kubectl --classic
```

学習用クラスターへのアクセス情報 — ラボ0で作成したあの `lab.kubeconfig` — は、スクリプトが
`KUBECONFIG` 変数を通じて見つけます。WSL の中に保存した場合、パスはいつものものです：

```bash
export KUBECONFIG=~/lab.kubeconfig
```

Windows のドライブに保存した場合、WSL にコピーする必要はありません — ドライブは中から
`/mnt/c/...` として見えます。あなたの Windows のユーザー名と、保存したフォルダに置き換えてください：

```bash
export KUBECONFIG=/mnt/c/Users/<your-name>/lab.kubeconfig
```

⚠️ **WSL を導入できない場合** — 会社支給のノートパソコンではよくある状況です — 自動チェックを
除いて、ラボはすべて問題なく進められます。その場合はアーティファクトのレポートは得られません：
Linux か macOS を使っている同僚にあなたの kubeconfig でスクリプトを実行してもらうか、対応する
ラボの「チェック」セクションのコマンド出力を申請に添付してください。

スクリプトは `KUBECONFIG` 変数を通じて、どこを見ればよいかを自分で判断します。設定されて
いなければ、その旨を伝えて停止します。

管理クラスター上のテナントへのアクセスが必要なラボでは、さらに `COZY_TENANT` 変数 —
あなたのテナント名、例えば `workshop07` — が必要です。

```bash
export COZY_TENANT=workshop07
./check.sh
```

## 出力される内容

ターミナルには、チェックごとに1行ずつ表示されます。

```
[  OK  ] application deployed and responding
[  OK  ] Pod name is injected into the page
[ FAIL ] autoscaling is not configured
         no HorizontalPodAutoscaler found for deployment/rickroll
         hint: apply hpa.yaml from this folder
```

⚠️ **レポートはラボのフォルダに書き出され、日付と時刻が付きます。** リポジトリが共有されていたり、
チェックを何度も実行したりした場合、そこに複数のファイルが溜まっていきます — 他人の実行結果や
過去の実行結果を自分のものと取り違えないよう、名前の中の時刻を確認してください。

それと並んで `report-<lab>-<date>.md` というファイルが現れます — 同じ結果を Markdown 形式にした
もので、収集された証拠 — バージョン、コマンドの出力、オブジェクト名 — も一緒に含まれています。
これがアーティファクトです。

## スクリプト作成者への要件

**適用した事実ではなく、実質を確認すること。** 悪い例：「Deployment オブジェクトが存在する」。
良い例：「アプリケーションが HTTP で応答し、その応答に Pod の名前が含まれている」。

**どの失敗も、何をすべきかを説明すること。** ヒントのない `FAIL` 行は不良品です。読者は
行き詰まっているからこそスクリプトを実行するのです。

**スクリプトは修復も作成もしません。** 読み取るだけです。唯一の例外は、ネットワーク到達性を
確認するための一時的な Pod で、これは後始末まで自分で行います。

**macOS と Linux で動作すること。** GNU 固有の `sed -i`、`readlink -f`、`date -d` は使いません。
両方のシステムでテストします。

**最初のエラーで止まらないこと。** すべてのチェックを実行し、全体像を示します。`set -e` は
使わないでください。

**パスワードやトークンを出力しないこと。** 値が秘密であれば `<hidden>` と書きます。

**冪等であること。** 10回続けて実行してもクラスターの状態は変わりません。

## 共有ライブラリ

`check/lib.sh` — 共有関数で、各スクリプトの冒頭で読み込まれます：

- `ok "text"` / `fail "text" "hint"` / `warn "text"` — 結果を出力する
- `need_kubeconfig` — `KUBECONFIG` が設定されていてクラスターが応答することを確認する
- `need_tenant` — `COZY_TENANT` が設定されていることを確認する
- `evidence "heading" "value"` — アーティファクトに証拠を1つ追加する
- `finish` — 集計し、レポートを書き出し、終了コードを返す

終了コード：`0` — すべて通過、`1` — 失敗あり。こうすることで、スクリプトを自動化に組み込めます。
