## 17. 詳しく見る: convert.sh の中身

このスクリプトは 5 つのステップから成り、それぞれ何をしているかを表示します。

**ステップ 1 — ハードウェアアクセラレーションの確認。** `/dev/kvm` デバイスがあるかどうかを調べます。
`virt-v2v` は内部で小さな仮想マシンを起動してイメージの中に入り込みます。もしプロセッサが
私たちのマシンの中まで渡されていれば、このネストされた仮想化は高速に動きます。もし渡されて
いなければソフトウェアモードが動きます。遅いですが、動くことは動きます。
`LIBGUESTFS_BACKEND=direct` という行が、まさにそのモードへの切り替えです。

**ステップ 2 — 元イメージのダウンロード。**

```bash
wget -O source.ova "$OVA_URL"
```

上の図にあった、ワークショップの共有ストレージから `app-1.ova` を取得します。講師が事前に
そこへファイルをアップロードしておいたものです。**あなた自身のプロジェクトでは、ここが
vSphere からのエクスポートに当たります:** `Export OVF Template` あるいは `ovftool`、
そしてその後は同じ再パッケージ化です。

**ステップ 3 — 再パッケージ化そのもの。**

```bash
virt-v2v -i ova /root/source.ova -o local -os /root/out -of qcow2 -on app
```

`-i ova` — 入力は何か: OVA 形式のファイルです。`-o local -os /root/out` — 結果をどこに
置くか: ローカルフォルダ `/root/out` の中です。`-of qcow2` — **必須の**フラグです。これが
ないと `virt-v2v` はデフォルトの形式を選んでしまい、プラットフォームはそのディスクを
受け付けません。`-on app` — 結果に付ける名前で、ここからファイル名 `app.qcow2` が
生まれます。

これには数分かかります。画面には `Copying disk 1/1` のような行が流れていきます。
まさにここで、先ほど触れた、あの 2 つ目の目に見えないドライバーの作業が行われています。

**ステップ 4 — あなたのバケットへのアップロード。**

```bash
mc alias set mybucket "$S3_ENDPOINT" "$ACCESS_KEY" "$SECRET_KEY"
mc cp /root/out/app.qcow2 "mybucket/$BUCKET/app.qcow2"
```

`mc alias set` はストレージのアドレスと鍵を `mybucket` という短い名前で覚えておき、以後
すべてのコマンドでそれらを繰り返さずに済むようにします。`mc cp` はファイルをコピーします。
構文は、あえて通常の `cp` と同じにしてあります。

**ステップ 5 — プラットフォーム向けのリンク。**

```bash
mc share download --expire 168h "mybucket/$BUCKET/app.qcow2"
```

7 日間（168 時間）有効な一時的な署名付きリンクを作成します。署名付きとは、アドレスの中に
暗号署名が埋め込まれているということです。このリンクがあれば誰でもファイルをダウンロード
できますが、それはこのリンクによってのみ、そしてリンクが生きている間だけです。バケットを
世界中に公開する必要はなく、アクセス鍵をプラットフォームに渡す必要もありません。

リンクは出力の `Share:` という語の後を探してください。次のフェーズで必要になります。
