## 28. ステップ8：なぜアプリケーションはまだ失敗するのか

**データベースが空である — アプリケーションにはスキーマが必要**

📍 **場所：** あなた自身の VM の中。この VM はすでにクラスターのネットワークに参加していて、データベースを名前で参照できます。

### まず — これもまた失敗する2回目のチェック

アドレスは修正し、アプリケーションは再起動して、ヘルスチェックのエンドポイントは `200` を返します。すべて準備が整ったように見えます。注文を作成してみましょう。

```bash
curl -s -X POST localhost:8080/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"item":"test order"}' -w '\nHTTP %{http_code}\n'
```

**返ってくるのは `500` です。** つい先ほどまで health は `200` だったのに。

<details>
<summary><b>答えと、このエラーより広い教訓</b></summary>

なぜなら、このアプリケーションのヘルスチェックはデータベースへの**接続が成立したという事実**だけを見ているからです。接続が開き、サーバーが応答した — だから「生きている」。必要なテーブルが中にあるかどうかは、チェックしていません。

そして、テーブルはありません。カタログから Postgres を注文したとき、あなたが渡されたのは**空のサーバー**です。`orders` データベースと `orders` ユーザーは用意されていますが、それだけです。古いマシンではテーブルが存在していました — かつてアプリケーションが初回起動時に一度だけ作成したもので、長年のあいだ誰もがそのことを忘れていたのです。

ついでにあなたは、緑色のヘルスチェックにどれほどの価値があるのかも目の当たりにしました。それが言っているのは「データベースまでつながった」であって、「ちゃんと動いている」ではありません。実際のプロジェクトでは、こうしたチェックの上に、ユーザーが注文を1件も出せない状態でもすべてを元気よく緑色で表示するような監視を組み立ててしまうのは簡単です。

</details>

**何をするか。** 私たちはアプリケーションを移すのであって、そのデータを移すのではありません。ですからテーブルは新たに作成する必要があります。これは一度だけ、SQL コマンドの一覧を記したファイルで行います。そのようなファイルを**スキーマ**と呼びます — ストレージがどう構成されているかを記述したもので、どんなテーブルがあり、その中にどんなフィールドがあり、それがどんな型か、を表します。

<details>
<summary><b>このファイルが実際に何を作成するか — 行ごとの解説</b></summary>

ファイルはリポジトリ内の `scripts/orders-schema.sql` です。中身はわずか2つのコマンドだけです。

**1つ目は注文テーブルを作成します。**

```sql
CREATE TABLE IF NOT EXISTS orders (
    id           BIGSERIAL PRIMARY KEY,
    item         TEXT        NOT NULL,
    status       TEXT        NOT NULL DEFAULT 'NEW',
    created_by   TEXT,
    processed_by TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ
);
```

フィールドごとに見ていきます。

- `id BIGSERIAL PRIMARY KEY` — 注文番号。`BIGSERIAL` は「データベースが次の番号を順番に自分で発行する」という意味で、`PRIMARY KEY` は「一意であり、これを使って行を検索する」という意味です。
- `item` — 何を注文したか。`NOT NULL` — 品目のない注文は意味をなさないので、データベースはそのような行を受け付けません。
- `status` — 注文の状態、デフォルトは `NEW`。メッセージが Kafka を通過すると `PROCESSED` に変わります。
- `created_by` / `processed_by` — 誰が作成し、誰が処理したか。まさにここにアプリケーションが `kafka` と書き込み、このフィールドによって、ステップ9でキューが本当に動作していることが分かります。
- `created_at` / `processed_at` — いつか。`TIMESTAMPTZ` — タイムゾーン付きのタイムスタンプです。
- `IF NOT EXISTS` — 「テーブルがすでに存在するなら、何もせず文句も言わない」。これのおかげで、このファイルは何も壊さずに再度適用できます。

**2つ目は履歴を1行追加します。**

```sql
INSERT INTO orders (...) SELECT '12x rack rails', 'PROCESSED', ...
WHERE NOT EXISTS (SELECT 1 FROM orders);
```

これは見た目のためのものです。ステップ9で注文一覧が空にならないようにするためです。`WHERE NOT EXISTS` は「テーブルが空のときだけ挿入する」という意味で、再度実行しても重複は作られません。

**このファイルに意図的に含まれていないもの：** `CREATE DATABASE` も `CREATE USER` もありません。データベースもロールも、ステップ5で Postgres を注文したときに Cozystack のカタログがすでに作成しています。これこそがマネージドサービスの意義です。定型作業はサービスが引き受け、あなたに残されるのは自分のスキーマだけです。

</details>

> ⚠️ **ファイルのコメントとの食い違い。** `orders-schema.sql` のヘッダーには、まずスーパーユーザーとして `GRANT CREATE,USAGE ON SCHEMA public` が必要と書かれています。**これは古い情報なので、やらないでください** — `orders` ロールは、データベースとスキーマを所有する `orders_admin` に属しているため、すでに権限を持っています。確認済みです。ファイル内のコメントは修正します。
