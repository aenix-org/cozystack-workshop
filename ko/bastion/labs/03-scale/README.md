# 랩 3 · 부하와 오토스케일링

| | |
|---|---|
| **소요 시간** | 30분 |
| **무엇을 증명하는가** | 복제본 수는 서비스 데스크 티켓이 아니라 부하가 정할 수 있다 |
| **준비물** | 랩 0에서 만든 클러스터, 랩 1의 `rickroll`, 터미널 창 세 개, 브라우저 |

## 왜 중요한가

이 실습 전체의 이유인 "출입증" 서비스는 균일하지 않게 동작합니다. 아침 여덟 시에는 보안팀과 사무실 절반이 동시에 이것을 열고, 오후 세 시에는 아무도 건드리지 않습니다. 피크에 맞춰 용량을 잡으면 하루 아홉 시간 동안 허공을 데우는 셈이고, 평균에 맞춰 잡으면 출입구에 줄이 생깁니다.

세 번째 선택지를 한번 시험해 봅시다. 복제본 수를 사람이 아니라 부하 자체가 정하도록 하는 것입니다. 애플리케이션에 실제 트래픽을 주고, 복제본이 여섯 개까지 늘어났다가 다시 하나로 줄어드는 것을 지켜보겠습니다.

그 과정에서 사람들이 여기서 가장 자주 걸려 넘어지는 것 — "얼마나 요청하는가"와 "얼마나 허용하는가"의 차이 — 를 함께 정리하겠습니다.

## 미니 용어집

| 용어 | 무엇인가 | 무엇과 비슷하지만… |
|---|---|---|
| **HPA** | 메트릭에 따라 복제본 수를 바꾸는 오브젝트 | **DRS 더하기 VM 수동 추가**와 비슷하지만, 인스턴스를 호스트에 분산시키는 것이 아니라 인스턴스의 개수를 바꾼다 |
| **metrics-server** | Pod의 현재 소비량을 수집하는 서비스 | **vCenter 통계 수집**과 비슷하지만, 최근 몇 분만 보관하고 이력은 전혀 없다 |
| **requests** | 보장된 양으로 예약해 두는 리소스의 양 | **Reservation**과 비슷하지만, 사용률 퍼센트가 여기서 계산되고, Pod가 어디에 들어갈지도 이것이 정한다 |
| **limits** | Pod가 그 위로 올라갈 수 없는 상한 | **Limit**과 비슷하지만, 상한에서 CPU는 스로틀링되고 메모리는 Pod를 죽인다 |
| **Utilization** | `requests` 대비 퍼센트로 나타낸 소비량 | **그래프의 "CPU Usage %"**와 비슷하지만, 600%가 될 수 있고 그것은 오류가 아니다 |
| **Fortio** | 웹 인터페이스가 있는 부하 생성기 | **HCIBench**와 비슷하지만, 클러스터 안에 일반 애플리케이션으로 산다 |

## 1단계. 복제본 하나로 시작하는지 확인한다

📍 **위치:** bastion에서(bastion 터미널에서).

이 랩 전체는 복제본 수가 눈에 띄게 늘어나는 것에 달려 있습니다. 그러니 하나에서 시작해야 합니다 — 그렇지 않으면 늘어난 것을 비교할 대상이 없습니다. 지금 몇 개의 복제본이 돌고 있는지 봅시다.

```bash
# KUBECONFIG는 클러스터의 주소와 로그인 정보가 담긴 파일의 경로입니다.
# 이 변수가 설정되기 전까지 kubectl은 bastion 자체에서 클러스터를 찾고 발견하지 못합니다.
export KUBECONFIG=~/lab.kubeconfig

# READY 열은 "준비됨 / 요청됨"으로 읽습니다: 1/1은 복제본 하나가 요청되어 돌고 있다는 뜻입니다.
kubectl get deployment rickroll
```

`1/1`이라고 나와야 합니다. 그보다 많으면 하나로 되돌리세요. 그렇지 않으면 늘어나는 것이 그만큼 잘 보이지 않습니다:

```bash
# scale은 애플리케이션 레코드에서 정확히 한 필드 — 복제본 수 — 만 바꿉니다.
# 여분의 복제본은 클러스터가 몇 초 안에 스스로 정리합니다.
kubectl scale deployment rickroll --replicas=1
```

## 2단계. 애플리케이션이 무엇을 요청하는지 읽는다

오토스케일링을 설정하기 전에, 그것이 무엇을 기준으로 퍼센트를 계산할지 이해해야 합니다.

```bash
# 클러스터의 오브젝트에는 필드가 수백 개 있고, 테이블에는 보이지 않습니다. jsonpath는 응답에서
# 정확히 한 지점만 뽑아냅니다. 경로는 위에서 아래로 읽습니다: spec.template은 복제본을 만드는
# 템플릿, containers[0]은 그 안의 첫 번째 컨테이너, resources는 CPU와 메모리에 대한 요청과
# 상한입니다. 꼬리의 {"\n"}은 줄바꿈으로, 응답이 다음 명령 프롬프트와 붙지 않게 합니다.
kubectl get deployment rickroll \
  -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}'
```

```json
{"limits":{"cpu":"300m","memory":"128Mi"},"requests":{"cpu":"20m","memory":"32Mi"}}
```

숫자 두 쌍인데, 사람들이 끊임없이 헷갈립니다. CPU로 짚어 봅시다.

**`requests: cpu: 20m`** — "20밀리cpu", 즉 코어의 100분의 2입니다. 이것이 요청입니다. 클러스터가 항상 Pod 뒤에 붙여 두기로 약속하는 양입니다. 스케줄러는 이 숫자로 Pod가 노드에 들어갈지 정합니다: 노드에 있는 모든 Pod의 요청 합계는 노드의 용량을 초과할 수 없습니다. 가장 가까운 비유는 vSphere의 reservation입니다.

**`limits: cpu: 300m`** — 상한입니다. 노드가 놀고 있더라도 Pod에게는 코어의 10분의 3보다 더 주지 않습니다. 비유하자면 vSphere의 limit입니다.

둘 사이에는 열다섯 배의 간격이 있고, 이는 의도적입니다: Pod는 CPU가 한가할 때 많이 가져갈 수 있지만, 보장되는 것은 조금뿐입니다.

⚠️ **CPU와 메모리는 자신의 limit에 닿았을 때 다르게 동작하며, 그것은 보이는 것보다 더 중요합니다.** CPU limit에 닿으면 애플리케이션은 그저 더 느려집니다(스로틀링). 메모리 limit에 닿으면 커널이 컨테이너를 죽입니다: `OOMKilled` 상태가 보이고 Pod는 다시 생성됩니다. 첫 번째는 불쾌하고, 두 번째는 장애입니다. vSphere에서도 메모리를 초과할 수는 없지만, 거기서는 게스트가 스왑을 받아 죽는 대신 성능이 저하됩니다.

**그리고 이제 이 랩의 핵심입니다.** HPA는 부하를 limit에서도, 노드의 용량에서도, 애플리케이션이 자기 안에서 보는 코어 수에서도 계산하지 않습니다. **`requests`로부터** 계산합니다. `requests: 20m`에서 임계값 50%는 복제본당 10밀리cpu를 뜻합니다.

여기서 처음 설정하는 사람들에게서 오토스케일링이 가장 자주 작동하지 않는 이유가 나옵니다: **컨테이너에 `requests.cpu`가 지정되어 있지 않으면, 계산할 기준이 없어 HPA는 아예 작동하지 않습니다.** 오류를 내지도 않습니다 — 조용히 `<unknown>`만 계속 보여줍니다.

## 3단계. 오토스케일링을 켠다

`hpa.yaml` 파일이 폴더에 있습니다. 살펴본 다음 적용합시다.

<details>
<summary><b>자세히 보기: hpa.yaml 안에는 무엇이 있는가</b></summary>

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rickroll
```

`autoscaling/v2`는 장식이 아닙니다. 옛 `v1`에서는 CPU 목표만 설정할 수 있었고 증가 속도를 제어할 수 없었습니다. `metrics` 블록 아래의 모든 것은 `v1`에서 사용할 수 없습니다. 인터넷에서 `autoscaling/v1`로 된 예제를 본다면 — 치명적으로 낡은 것은 아니지만, 필요한 것의 절반은 다루지 못합니다.

```yaml
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rickroll
```

누구를 지켜보고 누구를 돌리는가. HPA는 Pod를 직접 관리하지 않습니다 — Deployment의 `replicas` 필드를 바꾸고, 거기서부터는 자가 복구 랩에서와 같은 사슬이 작동합니다: Deployment가 그 수를 ReplicaSet에 전달하고, ReplicaSet이 부족한 복제본을 만듭니다.

여기서 실용적인 규칙이 나옵니다: **HPA가 존재하는 한, `replicas`를 손으로 바꾸는 것은 의미가 없습니다.** 셋으로 설정하면 15초 뒤 HPA가 자기 값을 설정합니다. 한 필드에 두 메커니즘은 언제나 다툼이고, 그 다툼에서는 HPA가 이깁니다.

```yaml
  minReplicas: 1
  maxReplicas: 6
```

허용 구간. 하한은 "부하가 없으니 다 끄자"로부터 지켜 줍니다 — HPA는 0까지 축소할 수 없습니다. 상한은 예산과 노드를 보호합니다: 그것이 없으면 갑작스러운 급증(또는 CPU를 먹어 치우는 애플리케이션 버그)이 노드에 자리가 없어질 때까지 복제본을 불려 놓습니다.

여섯은 학습용 노드 `u1.medium`에 맞춰 골랐습니다. 각각 20m 요청의 복제본 여섯 개는 120m — 노드가 여유롭게 감당합니다.

```yaml
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
```

규칙: 모든 복제본에 걸친 **평균** 부하를 그들의 `requests`의 50%, 즉 복제본당 10m로 유지한다.

여기서 "평균"이라는 단어가 핵심이며, 모든 산수가 이것에 달려 있습니다. HPA는 이렇게 계산합니다:

```
필요한 복제본 = ceil( 현재 복제본 × 현재 부하 ÷ 목표 부하 )
```

복제본 하나가 부하 645%이고 목표가 50%면 `ceil(1 × 645 / 50) = 13`이 됩니다. 열셋은 여섯보다 크므로 HPA는 `maxReplicas`에 닿습니다.

목표가 왜 80이 아니라 50인가: 80%에서는 애플리케이션이 이미 곤란해진 뒤에야 증가가 시작됩니다. 절반은 새 복제본이 올라오는 데 걸리는 시간에 여유를 남깁니다. 실제 서비스에서는 이 숫자를 시작에 몇 초가 걸리는지에 맞춰 조정합니다.

```yaml
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 2
          periodSeconds: 15
```

증가 속도. 기본적으로 Kubernetes는 확대에 앞서 일정 기간의 메트릭 이력을 봐서 무작위 급증에 흔들리지 않게 합니다. 랩에서는 그것이 "아무 일도 일어나지 않는다"처럼 보이므로, 창을 0으로 만듭니다: 첫 측정에 곧바로 반응합니다.

`Pods: 2 / 15s` — 15초마다 복제본을 두 개 넘게는 추가하지 않는다. 그래서 올라가는 길은 계단 모양이 됩니다: 1 → 3 → 5 → 6.

⚠️ **`policies`를 지정하면 표준 정책에 더하는 것이 아니라 교체하는 것입니다.** 표준 증가 정책(15초마다 두 배)은 여기서 더 이상 적용되지 않습니다.

```yaml
    scaleDown:
      stabilizationWindowSeconds: 60
```

반대로 아래로는 지연을 두고 옵니다. HPA는 지난 1분 동안 요청된 개수의 최댓값을 보고, 그 구간 내내 부하가 낮았을 때만 복제본 수를 줄입니다. 그렇지 않으면 급증 사이의 모든 멈춤마다 복제본이 사라졌다 다시 나타나기 시작합니다.

여기서 표준값은 **300초**, 5분입니다. 랩 시간 안에 되돌아오는 것을 볼 수 있도록 우리는 1분으로 줄였습니다. 실전에서는 5분이 더 합리적입니다.

</details>

## 4단계. 통과하지 못할 확인

무엇을 얻었는지 봅시다:

```bash
# hpa는 horizontalpodautoscaler의 약자이며, kubectl은 두 표기를 모두 이해합니다.
# TARGETS 열은 "현재 부하 / 목표"로 읽고, REPLICAS는 지금
# 요청된 복제본이 몇 개인지입니다.
kubectl get hpa rickroll
```

**보게 될 것:**

```
NAME       REFERENCE             TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
rickroll   Deployment/rickroll   cpu: <unknown>/50%   1         6         1          10s
```

`TARGETS` 열에는 부하 대신 `<unknown>`이 있습니다. 오토스케일링은 애플리케이션이 CPU를 얼마나 소비하는지 모르고, 그래서 판단할 근거가 없습니다.

⚠️ **아니면 곧바로 퍼센트가 보일 수도 있습니다** — 예를 들어 `cpu: 5%/50%`. 그것이 당신에게 무언가 다르다는 뜻은 아닙니다: 당신 클러스터의 메트릭 수집기가 이미 얼마간 돌아 Pod를 폴링할 시간이 있었던 것입니다. `<unknown>`은 방금 띄운 클러스터에서 나타납니다. 곧바로 숫자가 나오더라도 아래 설명은 어쨌든 읽어 두세요. `<unknown>`의 원인은 언젠가 만나게 되고, 그것이 앞을 막는 순간보다 미리 배워 두는 편이 낫기 때문입니다.

**이것은 고장이 아니며 여기서 고칠 것은 없습니다.** Pod 부하는 별도의 서비스 `metrics-server`가 수집합니다. 그것은 노드를 대략 15초에 한 번씩 폴링하고 결과를 짧은 창으로 평균 냅니다. 연속된 두 측정값이 생기기 전까지는 넘겨줄 것이 없어, HPA는 정직하게 "모른다"고 씁니다.

메트릭이 흐르고 있는지는 직접 확인할 수 있습니다:

```bash
# top = "이 Pod들이 지금 리소스를 얼마나 먹고 있는가." 숫자는 오토스케일링을 먹이는
# 바로 그 metrics-server에서 나옵니다: top이 답한다면 데이터 원천은 살아 있고,
# 그저 시간 문제일 뿐입니다.
kubectl top pods -l app=rickroll
```

```
NAME                        CPU(cores)   MEMORY(bytes)
rickroll-6f4b9c8d57-p9wqt   1m           4Mi
```

5분이 지나도 여전히 `<unknown>`이고 `kubectl top`이 `error: Metrics API not available`이라고 답한다면 — 그때는 정말로 고장이며, 원인은 둘 중 하나입니다: `metrics-server`가 클러스터에 설치되어 있지 않거나, 컨테이너에 `requests.cpu`가 설정되어 있지 않은 것입니다(이 경우 `kubectl top`은 작동하지만 HPA는 여전히 계산하지 못합니다 — 퍼센트를 뽑을 기준이 없습니다).

`metrics-server`는 클러스터와 함께 스스로 설치됩니다 — 따로 켤 필요가 없습니다. 그것은 `cozy-monitoring` 네임스페이스에 살며, 이렇게 확인할 수 있습니다:

```bash
# -n = 어느 네임스페이스에서 볼지. 네임스페이스는 클러스터의 한 구획이며,
# kubectl은 기본적으로 default를 보므로 거기서는 시스템 Pod가 보이지 않습니다.
# deploy는 deployment의 약자입니다.
kubectl -n cozy-monitoring get deploy metrics-server
```

이것을 랩 0의 **Monitoring agents** 체크박스와 혼동하지 마세요: 그 체크박스는 메트릭을 저장소로 수집하고 그래프를 그리는 일(관측성 랩)을 담당하고, `metrics-server`는 `kubectl top`과 오토스케일링을 위한 현재 숫자를 담당합니다. 서로 다른 메커니즘이고, 독립적으로 삽니다.

정확한 원인은 다음이 알려 줍니다:

```bash
# describe = 오브젝트의 전체 카드: 모든 필드, 이벤트, 조건.
# 몇 개의 테이블 열만 출력하는 get과 다릅니다.
kubectl describe hpa rickroll
```

맨 아래 `Conditions`에 사람이 읽을 수 있는 설명이 담긴 `ScalingActive` 줄이 있습니다.

**교훈은 이 오류보다 넓습니다.** Kubernetes에서 "적용됨"과 "작동함"은 시간상 나뉘어 있습니다. `apply` 명령은 당신의 의도를 클러스터에 기록할 뿐입니다. 거기서부터 컨트롤러들이 그것을 이어받고, 각자 자기 속도가 있습니다: HPA는 15초에 한 번 재계산하고, 메트릭은 1분 늦으며, 가비지 컬렉터는 몇 분에 한 번 옵니다. vCenter에서 온 습관 — "다이얼로그가 닫혔으니 끝났다" — 은 여기서 당신을 배신합니다. 봐야 하는 것은 명령의 반환 코드가 아니라 오브젝트의 `status`입니다.

</details>

## 5단계. 부하 생성기를 띄운다

bastion에서 `port-forward`를 통해 애플리케이션에 부하를 거는 것은 의미가 없습니다: 병목이 애플리케이션이 아니라 당신의 가정용 인터넷과 터널 자체가 되기 때문입니다. 생성기는 클러스터 안, 대상 옆에 있어야 합니다.

`fortio.yaml` 파일이 폴더에 있습니다.

<details>
<summary><b>자세히 보기: fortio.yaml 안에는 무엇이 있는가</b></summary>

```yaml
kind: Deployment
metadata:
  name: fortio
```

Fortio는 클러스터의 평범한 애플리케이션이며, 다른 모든 것과 같은 Deployment로 배포됩니다. 여기에 특별한 "테스트용 인프라"는 없고, 그 자체가 시사하는 바가 있습니다.

```yaml
        - name: fortio
          image: fortio/fortio:latest
          args: ["server"]
```

Fortio 이미지는 두 가지 모드로 실행할 수 있습니다. `fortio load ...`는 명령줄에서의 일회성 실행입니다. `fortio server`는 웹 인터페이스가 있는, 계속 돌아가는 서비스로, 버튼으로 부하를 시작하고 그 결과를 바로 그 자리에서 그래프로 봅니다. 우리는 두 번째를 택합니다: 워크숍에서는 브라우저에서 지연 히스토그램을 보는 것이 터미널에서 숫자 한 열을 읽는 것보다 명확합니다.

⚠️ **매니페스트의 `latest` 태그는 실전에서는 하면 안 되는 것입니다.** 오늘은 한 이미지, 한 달 뒤에는 다른 이미지라서, 자기 테스트를 다시 재현할 수 없게 됩니다. 학습용 생성기에는 참을 만하지만, 그 밖의 무엇에도 안 됩니다.

```yaml
          ports:
            - containerPort: 8080
              name: http
```

Fortio의 웹 인터페이스는 8080에서 수신하고 `/fortio/` 경로에 삽니다. `http`라는 이름은 아래 Service에서 필요합니다.

```yaml
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: "1"
              memory: 256Mi
```

주목하세요: 생성기에는 대상보다 더 많이 할당됩니다. `rickroll`의 20m에 대비되는 100m 요청, 300m에 대비되는 코어 하나 전체의 상한.

이것은 관대함이 아니라 올바른 테스트의 필수 조건입니다. 생성기가 CPU가 모자라면 자기 상한에 부딪히고, 당신은 애플리케이션이 아니라 Fortio를 측정하게 됩니다. 이 오류의 증상은 알아보기 쉽습니다: 지연은 오르는데 대상의 부하는 제자리에 머무릅니다.

```yaml
kind: Service
metadata:
  name: fortio
spec:
  ports:
    - port: 8080
      targetPort: http
```

웹 인터페이스를 위한 안정된 주소. 클러스터 안에서는 이제 `http://fortio:8080/`로 닿을 수 있고, 밖에서는 `port-forward`를 통해서인데, 그것을 다음에 하겠습니다.

</details>

적용하고 기다립니다:

```bash
# 파일에는 오브젝트가 한꺼번에 둘 있습니다: 생성기가 든 Deployment와, 그 웹 인터페이스를 위한
# 안정된 주소인 Service.
kubectl apply -f fortio.yaml

# rollout status는 복제본이 준비될 때까지 터미널을 붙잡고 진행 상황을 출력합니다.
# 여기서 일부러 기다립니다: 생성기가 올라오기 전에는 부하를 걸 대상이 없습니다.
kubectl rollout status deployment/fortio
```

## 6단계. 브라우저에서 Fortio를 연다

📍 **창 1** — Fortio로 가는 터널. 랩 1의 `rickroll`로 가는 터널이 아직 열려 있는 경우 `8080`과 충돌하지 않도록 포트 `8081`을 골랐습니다:

```bash
export KUBECONFIG=~/lab.kubeconfig

# port-forward는 bastion에서 클러스터 안으로 터널을 놓습니다.
#   svc/fortio    연결 대상: fortio라는 이름의 Service
#   8081:8080     "이쪽 포트 : 클러스터 안 포트"로 읽습니다 — localhost:8081로의
#                 요청이 이 Service의 포트 8080으로 갑니다
kubectl port-forward svc/fortio 8081:8080
```

명령은 끝나지 않습니다 — 터널을 열어 둡니다. 그것이 도는 동안 <http://localhost:8081/fortio/> 를 여세요.

⚠️ **경로 끝의 슬래시는 필수입니다.** 슬래시 없는 `http://localhost:8081/fortio`에서는 Fortio가 404로 답하고, 마치 시작되지 않은 것처럼 보입니다.

## 7단계. 증가를 지켜볼 두 번째 창을 준비한다

랩의 요점은 Fortio 보고서의 숫자가 아니라 복제본에 일어나는 일입니다. 이것은 부하 이후가 아니라 부하와 동시에 봐야 합니다.

📍 **창 2** — 랩이 끝날 때까지 열어 두세요.

`-w`(watch) 플래그로 지켜보겠습니다. 이것은 "화면을 새로 고친다"가 아니라 "변화가 있을 때마다 새 줄을 출력한다"는 뜻입니다. 출력은 테이블이 아니라 이벤트 로그로 나옵니다. 이는 `watch kubectl get pods`와의 중요한 차이입니다. 후자에서는 "지금" 스냅샷만 보이고 중간 상태를 쉽게 놓칩니다.

```bash
export KUBECONFIG=~/lab.kubeconfig

# rickroll의 복제본을 지켜봅니다: 새 줄 하나하나가 그중 하나의 상태 변화입니다.
# 명령은 끝나지 않습니다. 나가려면 Ctrl+C — 이는 복제본 자체에는 아무 영향이 없습니다.
kubectl get pods -l app=rickroll -w
```

세 번째 창이 있으면 이것도 거기에 두세요 — 그러면 의사 결정 과정 자체를 볼 수 있습니다:

```bash
# 같은 지켜보기이되, 오토스케일링의 결정을 봅니다: TARGETS는 부하가 어떻게
# 바뀌는지, REPLICAS는 그에 응해 복제본을 몇 개 요청했는지 보여줍니다.
kubectl get hpa rickroll -w
```

## 8단계. 부하를 건다

📍 **위치:** 브라우저의 Fortio 탭에서.

폼을 채웁니다:

| 필드 | 값 | 왜 그렇게 |
|---|---|---|
| URL | `http://rickroll/` | Service 이름; Fortio는 클러스터 안에 있어 이를 직접 봅니다 |
| QPS | `1200` | 초당 천이백 요청 |
| Duration | `90s` | 1분 30초: 증가에도, 그것을 알아보기에도 충분합니다 |
| Connections | `80` | 병렬 연결 여든 개 |

**Start**를 누릅니다.

⚠️ **당신의 Fortio 버전에서 필드 이름이 다르게 되어 있으면**(예를 들어 연결 수가 `Threads`로 표기되어 있으면) 의미로 판단하세요: URL, 요청 빈도, 지속 시간, 병렬성. 같은 부하는 브라우저를 거치지 않고 명령으로도 걸 수 있습니다:

```bash
# exec는 당신의 bastion이 아니라, 이미 돌고 있는 Pod 안에서 명령을 실행합니다.
#   deploy/fortio   이 애플리케이션의 Pod 안에서; 정확히 어느 Pod인지는 kubectl이 스스로 고름
#   --              이 구분자 뒤의 모든 것은 Pod를 위한 명령
#   -qps 1200       초당 천이백 요청
#   -c 80           병렬 연결 여든 개
#   -t 90s          부하를 1분 30초 동안 유지
# 마지막 인자는 대상입니다: 우리 애플리케이션의 Service 이름.
kubectl exec deploy/fortio -- fortio load -qps 1200 -c 80 -t 90s http://rickroll/
```

## 9단계. 무슨 일이 일어나는지 지켜본다

📍 **창 2**, 시작 후 약 20초 뒤:

```
NAME                        READY   STATUS              AGE
rickroll-6f4b9c8d57-p9wqt   1/1     Running             22m
rickroll-6f4b9c8d57-mn4kd   0/1     Pending             0s
rickroll-6f4b9c8d57-mn4kd   0/1     ContainerCreating   0s
rickroll-6f4b9c8d57-t8zxc   0/1     ContainerCreating   0s
rickroll-6f4b9c8d57-mn4kd   1/1     Running             3s
rickroll-6f4b9c8d57-t8zxc   1/1     Running             3s
```

그다음 둘 더, 이어 하나 더. 1분 안에 복제본이 여섯 개가 됩니다.

📍 **HPA를 봅시다** — 그것이 무엇을 보고 무엇을 결정했는지:

```bash
# TARGETS는 목표 대비 현재 평균 부하, REPLICAS는 요청된 복제본 수입니다.
kubectl get hpa rickroll
```

```
NAME       REFERENCE             TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
rickroll   Deployment/rickroll   cpu: 645%/50%   1         6         6          8m
```

**645%.** 이 랩을 다듬어 본 테스트베드에서는 정확히 그만큼 나왔습니다. 당신 것은 자릿수가 다르겠지만, 분명히 수백 퍼센트일 것입니다.

이 숫자는 무엇으로부터 계산되는지를 떠올리기 전까지는 터무니없어 보입니다. 노드의 용량이 아니라 복제본의 **요청**으로부터인데, 우리 요청은 20m — 코어의 100분의 2입니다. 복제본은 요청한 것보다 몇 배 더 가져가고, 그것은 허용됩니다: `requests`는 보장된 최소치이지 상한이 아닙니다. 상한은 `limits`이고, 거기까지는 아직 멀었습니다.

한편 노드는 결코 한가하지 않습니다: `u1.medium`은 코어 하나이고, 이 순간 그 위에서 애플리케이션의 복제본들과 부하 생성기 자체가 함께 돌고 있습니다. 높은 퍼센트는 용량이 넘쳐서가 아니라 분모가 작아서 나옵니다.

**백을 넘는 퍼센트는 여기서 경보가 아니라 정상입니다.** 이것이 vCenter에서 가져온 직관을 깨뜨리는 핵심입니다: 거기서 "CPU Usage 645%"는 재앙을 뜻했을 것입니다. 퍼센트가 할당된 것에서 계산되었기 때문입니다. 여기서는 요청된 최소치에서 계산되고, 요청과 상한 사이에는 열다섯 배의 간격이 있습니다.

HPA의 산수를 직접 확인해 보세요:

```bash
# 각 복제본의 소비량을 따로. CPU(cores)는 밀리cpu로 출력됩니다:
# 100m은 코어의 100분의 1, 1000m은 코어 하나 전체입니다.
kubectl top pods -l app=rickroll
```

복제본들에 걸친 평균이 바로 HPA가 임계값과 비교하는 숫자입니다: 20m 요청의 50%, 즉 10m. 모든 복제본에 걸친 합계는 노드의 코어에 부딪히고 — 부하를 더 올려도 바로 거기서 증가가 멈춥니다.

📍 **한편 브라우저의 Fortio 탭에서는** 지연 히스토그램이 그려지고 있습니다. 실행을 끝까지 지켜보세요: 마지막에 `Code 200 : 108000 (100.0 %)` 같은 줄이 나타납니다. 오류 0 — 애플리케이션이 견뎌 냈습니다. 이 줄이 어디 있는지 기억해 두세요: 랩 4에서 그것이 주된 증거가 됩니다.

## 10단계. 복제본이 다시 줄어드는 것을 지켜본다

부하가 끝났습니다. 아무것도 하지 말고, 창 2를 보세요.

처음 1분 30초에서 2분 동안은 아무 일도 일어나지 않습니다. 이 멈춤은 세 가지 지연으로 이루어집니다: 메트릭이 약 1분 늦고, `stabilizationWindowSeconds: 60`은 지난 1분 내내 부하가 낮았기를 요구하며, HPA 자체는 15초에 한 번 재계산합니다.

그다음 줄들이 한꺼번에 쏟아집니다:

```
rickroll-6f4b9c8d57-t8zxc   1/1     Terminating   4m
rickroll-6f4b9c8d57-mn4kd   1/1     Terminating   4m
...
```

복제본 다섯이 떠나고, 하나가 남습니다 — `minReplicas`.

**비대칭에 주목하세요.** 올라갈 때는 복제본 둘씩 계단으로 갔지만, 내려올 때는 한 번의 움직임이었습니다. 이는 의도된 것입니다: "복제본이 너무 많다" 쪽으로 틀리면 지갑만 손해지만, "너무 적다" 쪽으로 틀리면 서비스를 무너뜨리는 것입니다. 그래서 공격적으로 늘리고 조심스럽게 줄입니다.

## 검증

📍 **위치:** bastion에서, `kubectl`로 작업하던 바로 그 터미널 창에서.

스크립트는 매니페스트가 적용되었다는 사실이 아니라 메커니즘이 정말로 살아 있는지를 확인합니다: HPA가 존재하고 올바른 Deployment를 대상으로 하는지, 컨테이너에 퍼센트가 계산되는 기준인 `requests.cpu`가 있는지, `metrics-server`가 실제로 숫자를 넘겨주는지(`TARGETS`가 `<unknown>`이 아닌지), 그리고 HPA 상태에 스케일링이 이미 작동했다는 표시가 아직 남아 있는지.

⚠️ **정리 전에 검증을 실행하세요** — HPA를 삭제하고 나면 확인할 것이 없습니다.

⚠️ **Windows에서는 스크립트를 PowerShell이 아니라 WSL에서** 실행합니다 — 그것을 어떻게 설치하는지는 랩 0 시작 부분에 적혀 있습니다. WSL이 없어도 랩은 완료할 수 있지만, 보고서 아티팩트는 없습니다.

```bash
# ./는 시스템 PATH의 명령이 아니라 "현재 폴더의 파일"을 뜻합니다.
# 스크립트는 클러스터에서 아무것도 바꾸지 않습니다: 읽고 보고서를 출력할 뿐입니다.
./check.sh
```

## 정리

**HPA를 삭제합니다.** 랩 4에서는 부하 아래에서 새 버전을 롤아웃하는데, 같은 시간에 복제본 수를 바꾸는 여분의 메커니즘은 그림을 흐릴 뿐입니다:

```bash
# delete -f = "이 파일에 기술된 것을 클러스터에서 제거하라." 애플리케이션은 남습니다:
# 파일에 기술된 것은 HPA뿐입니다. 삭제 후 복제본 수는 현재 값에서 얼어붙습니다.
kubectl delete -f hpa.yaml
```

**Fortio는 남겨 둡니다** — 랩 4에서 부하 원천으로 필요합니다. 랩 4를 계획하고 있지 않다면, 그것도 제거하세요:

```bash
# 파일의 두 오브젝트를 모두 제거합니다 — 생성기의 Deployment와 그 Service.
kubectl delete -f fortio.yaml
```

`rickroll` 애플리케이션은 건드리지 마세요.

당신이 해제한 모든 것은 컨테이너가 끝난 바로 그 순간 노드의 공용 풀로 돌아갔습니다. 여기에는 "할당됐지만 반환되지 않은" 것이 없습니다 — 요청은 Pod가 사는 만큼만 정확히 삽니다.

## 우리가 이제 할 수 있는 것

- `requests`와 `limits`의 차이를 설명하고, 각각에 부딪혔을 때 무슨 일이 일어나는지 예측하기
- HPA가 왜 `requests`로부터 퍼센트를 계산하는지, 그것들 없이는 왜 작동하지 않는지 이해하기
- HPA 공식을 읽고, 복제본을 몇 개 요청할지 미리 말하기
- "매니페스트가 적용됐다"와 "메커니즘이 작동하기 시작했다"를 구분하고, 상태를 어디서 봐야 하는지 알기
- 애플리케이션에 bastion이 아니라 클러스터 안에서 실제 부하를 걸기

## 그리고 vSphere에서라면 이것은

vSphere에서는 위로 스케일링합니다: 돌아가는 머신에 CPU와 메모리를 핫 애드합니다. 사람이 일정에 따라 혹은 알림에 따라 하고, 그게 전부입니다 — vCenter는 애플리케이션 인스턴스를 늘릴 수 없습니다. 그러려면 로드 밸런서, 머신 템플릿, 그리고 누군가의 손 작업이 필요합니다. DRS는 다른 문제를 풉니다: 기존 머신을 호스트 사이에서 옮기지만, 그 개수는 바꾸지 않습니다.

여기서 복제본 수는 부하의 결과이며, 스무 줄의 텍스트로 기술됩니다.

**솔직히, vSphere가 더 편한 지점.** 세 가지이고, 모두 중요합니다.

첫째, 핫 애드는 어떤 애플리케이션에서도 작동합니다. 2009년에 작성되어 오직 단일 인스턴스로만 존재하는 것도 포함해서요. HPA는 애플리케이션이 여러 복제본으로 동시에 돌 수 있기를 요구합니다: 공유 상태 없이, 로컬 파일에 쓰지 않고, 세션을 인스턴스에 고정하지 않고. 그렇게 하지 못한다면 오토스케일링은 당신에게 쓸 수 없고, Kubernetes는 이 문제를 풀어 주지 않습니다 — 드러낼 뿐입니다. 바로 여기에 마이그레이션의 진짜 경계가 지나가며, 매니페스트에 있지 않습니다.

둘째, 메트릭. vCenter는 통계를 몇 달씩 보관하고, "지난 화요일에 무슨 일이 있었나"라는 질문은 그래프로 답합니다. `metrics-server`는 최근 몇 분을 보관하고 그 이상은 없습니다 — 정확히 HPA를 먹이기 위해 설계되었습니다. 이력을 위해서는 Prometheus를 세워야 하고, 그것은 별도의 작업입니다(랩 14).

셋째, 비용 예측 가능성. 코어 넷짜리 머신은 얼마얼마 하고, 그것은 미리 알 수 있습니다. 오토스케일링은 나쁜 날에는 평소보다 여섯 배 많은 소비를 얻게 된다는 뜻입니다. `maxReplicas`는 성능을 미세 조정하는 손잡이가 아니라 당신의 돈 퓨즈이며, 그에 걸맞게 다뤄야 합니다.
