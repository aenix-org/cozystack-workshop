# 랩 8 · 매니페스트에 없는 시크릿

| | |
|---|---|
| **소요 시간** | 50분, 그중 일부는 저장소가 올라오고 여러분이 봉인을 해제하는 동안 기다리는 시간입니다 |
| **무엇을 증명하는가** | 비밀번호를 Git에서 영구히 제거하고, 파일 하나 건드리지 않고 바꿀 수 있다는 것 |
| **준비물** | 랩 0의 클러스터와 `~/lab.kubeconfig`; 자기 테넌트의 대시보드 접근 권한; `workshopXX` 형식의 테넌트 번호 |

> ⚠️ **`workshopXX`는 이름이 아니라 자리표시자입니다.** 자기 테넌트 번호로 바꾸세요.
> 그러지 않으면 명령이 다른 사람의 테넌트로 가서 접근 거부 오류를 받게 되고, 더 나쁘게는
> 다른 사람의 데이터를 받게 됩니다. 여러분의 번호는 비밀번호와 함께 받았습니다.

> ⚠️ **빽빽한 랩입니다: 열한 개의 단계와 낯선 접근 모델.**
> 온전히 하루 저녁을 잡아 두세요.

## 왜 중요한가

Passes 서비스는 잘 돌아갑니다: 직원이 방문객용 출입증을 요청하면 보안팀이 목록을 봅니다.
보안팀이 정기 감사를 나왔고, 여러분의 리포지터리에서 한 줄을 가져왔습니다:

```yaml
- name: DB_PASSWORD
  value: "Propusk2019!"
```

출입증 데이터베이스의 비밀번호가 매니페스트 안에 있습니다. 매니페스트는 Git 안에 있습니다. Git은
세 팀에 걸쳐 열두 명이 볼 수 있고, 또 네 명은 이미 퇴사했으며, 리포지터리의 완전한 사본이 작년에
통합 작업을 했던 외주 업체의 VM에 남아 있습니다.

감사관의 질문은 일상적으로 들립니다: **"이 비밀번호를 바꾸고, 지난 한 달 동안 누가 이걸
읽었는지 보여 주세요."** 답할 것이 없습니다. 비밀번호를 바꾼다는 건 그것이 하드코딩된 모든
곳을 찾아낸다는 뜻이고, 누가 읽었는지는 알 수 없습니다. Git에서 파일을 읽는 것은 어디에도
기록되지 않기 때문입니다.

이 랩에서는 비밀번호를 OpenBao로 옮기고, 애플리케이션이 거기서 비밀번호를 가져오도록 가르치고,
명령 하나로 비밀번호를 바꾸고, 시스템이 그에 대해 무엇을 알고 있는지 살펴봅니다.

가는 길에 거의 모두가 걸려 넘어지는 질문 하나를 짚고 넘어갑니다: **Kubernetes의 Secret이
진짜 시크릿 저장소와 어떻게 다른가.**

이 랩의 모든 용어는 처음 나올 때 풀어서 설명하고, 다음 절은 이미 소개한 용어들의 용어집입니다.

## 용어집

| 용어 | 무엇인가 | …와 비슷하지만 |
|---|---|---|
| **Secret (Kubernetes)** | base64로 기록된 데이터를 담은 클러스터 객체 | **VM 디스크의 비밀번호 파일**과 비슷하지만, 보호된 것처럼 보일 뿐 실제로는 아닙니다 — 아래에서 분해해 봅니다 |
| **base64** | 임의의 바이트를 출력 가능한 문자로 기록하는 방법 | **uuencode, MIME 첨부**와 비슷하지만, 암호화가 아닙니다. 키가 없고, 누구나 되돌릴 수 있습니다 |
| **시크릿 저장소** | 별도의 서비스: 시크릿을 암호화해 보관하고 규칙에 따라 내어 줍니다 | **직접적인 비유가 없지만**, "비밀번호로 가득 찬 네트워크 폴더"가 아닙니다 — 정책, 만료, 로그를 갖춘 서비스입니다 |
| **OpenBao** | 그런 저장소 중 하나. HashiCorp Vault의 포크이며 MPL 라이선스로 배포됩니다 | 명령과 API는 Vault와 같고, 유틸리티 이름만 `bao`입니다 |
| **Root 토큰** | 모든 것에 완전한 접근 권한을 가진 계정 | **root**와 비슷하지만, 설정 때 한 번만 쓰고 그 뒤로는 좁은 토큰을 발급합니다 |

이 랩의 나머지 어휘 — `sealed`, 봉인 해제 키, 정책, 토큰, KV v2, 로테이션, 감사 로그,
init 컨테이너 — 는 진행하면서 각각이 처음 필요해지는 단계에서 소개합니다. 지금 외울 필요는
없습니다: 동작과 떼어 놓으면 어차피 머리에 남지 않습니다.

<details>
<summary><b>전체 목록을 미리 보고 싶다면</b></summary>

| 용어 | 무엇인가 | …와 비슷하지만 |
|---|---|---|
| **봉인됨 (sealed)** | 서비스는 실행 중이지만 마스터 키가 메모리에 없습니다: 데이터는 암호화된 채로 있고 API는 요청을 거부합니다 | **"서비스는 올라왔지만 볼륨이 마운트되지 않음"**과 비슷하지만, 재시작할 때마다 손으로 다시 봉인을 해제해야 합니다 |
| **봉인 해제 키 (unseal key)** | 저장소의 봉인을 해제하는 데 쓰는 마스터 키의 조각 | **금고 열쇠**와 비슷하지만, 조각이 여러 개이고 기본적으로 하나 이상을 제시해야 합니다 |
| **정책 (policy)** | 경로들과 각 경로에서 허용되는 것들의 목록 | **폴더에 대한 ACL**과 비슷하지만, 경로는 디스크의 파일이 아니라 API 안의 주소입니다 |
| **토큰 (token)** | 저장소로 들어가는 임시 출입증 | **세션**과 비슷하지만, 토큰에는 수명이 있어 스스로 만료되고 취소할 수 있습니다 |
| **KV v2** | 버전 이력이 있는 "키-값" 엔진 | **변경 이력이 있는 파일 폴더**와 비슷하지만, 모든 버전과 각 기록 시각을 보관합니다; 예전 값은 결코 사라지지 않습니다 |
| **로테이션 (rotation)** | 예정에 따라 시크릿을 새것으로 교체하는 것 | **정해진 주기에 따른 비밀번호 변경**과 비슷하지만, 여기서는 명령 하나이고 애플리케이션은 다음 시작 때 그것을 가져갑니다 |
| **감사 로그 (audit log)** | "누가, 언제, 무엇을 요청했는가"의 기록 | **파일 공유의 접근 로그**와 비슷하지만, 실패한 요청과 거부를 포함해 모든 API 요청마다 한 줄이 기록됩니다 |
| **시크릿 제로 (secret zero)** | 애플리케이션이 나머지 모든 시크릿에 대한 권리를 증명하는 데 쓰는 단 하나의 시크릿 | 완전히 없앨 수는 없습니다. 수명이 짧고 좁고 일회용으로 만들 수는 있습니다 |
| **Init 컨테이너 (init container)** | 메인 컨테이너가 시작하기 전에 실행되고 끝나는 컨테이너 | **서비스가 올라오기 전에 실행되는 시작 스크립트**와 비슷하지만, 실패하면 메인 컨테이너가 아예 시작하지 않습니다 — 그게 바로 원하는 동작입니다 |

</details>

## 랩 폴더에 무엇이 있는가

모든 파일은 이미 여러분에게 있습니다 — 리포지터리와 함께 받았습니다. 새로 만들거나 다시
입력할 것은 없습니다: 아래 본문에서 `kubectl apply -f name.yaml`이라고 되어 있는 곳이면,
그 파일은 여기서 가져옵니다.

```bash
cd labs/08-openbao
```

| 파일 | 무엇인가 | 언제 쓰는가 |
|---|---|---|
| `openbao.yaml` | 시크릿 저장소 주문서 — 대시보드의 버튼과 같은 것 | `lab` 클러스터가 아니라 **테넌트에** 적용합니다 |
| `secrets-demo-naive.yaml` | 서비스의 오늘 모습: 비밀번호가 파일 안에 그대로. 감사가 찾아낸 게 이것입니다 | 자기 `lab` 클러스터에 적용합니다 |
| `secrets-demo-secret.yaml` | "순진한 수정": 비밀번호를 Secret으로 옮김 — 그리고 그것으로 충분하지 않은 이유 | 같은 곳에 적용합니다 |
| `secrets-demo.yaml` | 최종 버전: 비밀번호가 어디에도 없음 — 평문으로도, base64로도 | 같은 곳에 적용합니다 |
| `check.sh` | 애플리케이션이 저장소에서 비밀번호를 받아오는지 확인 | 랩 마지막에 실행합니다 |

## 1단계. 문제를 직접 눈으로 본다

📍 **위치:** bastion(공유 VM)에서, lab 클러스터에서.

감사가 찾아낸 것을 우리 영역에서 재현해 봅시다: lab 클러스터에 작은 `secrets-demo` 서비스를
올리되, 비밀번호는 자기 명세에서 곧바로 건네받도록 합니다. 먼저 파일을 살펴보고, 그다음
적용합니다.

<details>
<summary><b>자세히 보기: secrets-demo-naive.yaml 안에 무엇이 있는가</b></summary>

이것은 평범한 `Deployment`입니다 — 애플리케이션에 대한 명세: 어떤 이미지를 가져오고 몇 개의
사본을 실행 상태로 유지할지. **이미지**는 프로그램이 들어 있는 파일시스템의 완성된 스냅샷입니다;
vSphere에서 가장 가까운 비유는 VM 템플릿인데, 운영체제만 없는 것입니다. **컨테이너**는 이미지의
실행 중인 인스턴스입니다. **Pod**는 Kubernetes에서 가장 작은 실행 단위입니다: 언제나 함께 살고
함께 죽는 하나 이상의 컨테이너. Deployment는 실행 중인 Pod의 수가 주문된 수와 일치하도록
보장합니다.

```yaml
      containers:
        - name: app
          image: busybox:1.36
```

여러분이 자기 레지스트리에 관한 랩에서 Go로 만든 진짜 Passes 앱은 여기서 건드리지 않습니다:
잘 돌아가고 있고, 연습 때문에 망가뜨릴 이유가 없습니다. 그래서 그 옆에 별도의 작은
`secrets-demo` 서비스를 올립니다 — 우리가 관심 있는 건 애플리케이션이 아니라 비밀번호가
그것에 도달하는 경로입니다. 그래서 그 자리에는 단 하나의 의미 있는 일을 하는 아주 작은
컨테이너가 있습니다 — 10초에 한 번씩 어떤 비밀번호로 동작하고 있는지 로그에 씁니다.

```yaml
          env:
            - name: DB_PASSWORD
              value: "Propusk2019!"
```

이 줄이 바로 이야기의 핵심입니다. 환경 변수는 애플리케이션에 설정을 전달하는 가장 평범한
방법입니다: 매니페스트의 `env`가 컨테이너 안의 변수가 됩니다. 메커니즘은 좋습니다; 나쁜 것은
**파일 안에 그대로 들어 있는 값**입니다.

```yaml
                  "$(printf %s "$DB_PASSWORD" | sha256sum | cut -c1-12)"
```

애플리케이션은 비밀번호가 아니라 그 **지문**을 출력합니다 — sha256의 처음 열두 글자. 지문을
보면 비밀번호가 바뀌었는지는 알 수 있지만, 지문에서 비밀번호 자체를 복원할 수는 없습니다.
로그는 이렇게 써야 합니다; 랩이 끝날 때까지 이 방식을 쓸 겁니다.

`resources.requests`는 보장으로 예약해 둘 리소스의 양이고(vSphere의 reservation에 해당),
`resources.limits`는 그 위로 올라가지 못하는 상한선입니다(limit에 해당). 값은 일부러 아주 작게
잡았습니다: 애플리케이션은 아무것도 하지 않으니까요.

</details>

**적용합니다.**

```bash
# KUBECONFIG는 kubectl에게 어느 클러스터와 이야기할지 알려 줍니다. 여기서는 랩 0의
# lab 클러스터입니다; 테넌트는 나중에, 저장소를 주문하는 단계에서 필요합니다.
export KUBECONFIG=~/lab.kubeconfig
cd labs/08-openbao
# apply = "클러스터를 파일에 기술된 상태로 만들어라". -f = 명세를 파일에서 가져온다.
# 이 이름을 가진 객체가 아직 없으므로, 새로 생성됩니다.
kubectl apply -f secrets-demo-naive.yaml
```

**보게 될 것** — `created`라는 단어로 끝나는 줄.

무엇을 얻었는지 봅시다:

```bash
# logs = 애플리케이션이 자기 출력으로 무엇을 찍었는지 보여 준다. 별도의 로그 파일은 없다.
#   deploy/secrets-demo  이 명세로 올라온 Pod에서 출력을 가져온다
#   --tail=2             시작 이후 전부가 아니라, 마지막 두 줄만
kubectl logs deploy/secrets-demo --tail=2
```

**보게 될 것** — 대략 이런 것:

```
08:14:31 connecting to passes-db.internal as passes_app, password fingerprint sha256:a609df223d57
```

애플리케이션은 동작합니다. 비밀번호는 파일 안에, 파일은 Git 안에 있습니다. 이것이 바로 감사가
찾아낸 상황입니다.

## 2단계. 순진한 수정: 비밀번호를 Secret으로 옮기기

📍 **위치:** bastion에서, lab 클러스터에서.

인터넷 검색이 처음으로 제안하는 것: "Kubernetes에는 그걸 위한 Secret이 있다." 조언대로 해
봅시다 — 그리고 먼저 파일에서 무엇이 바뀌는지 봅시다.

<details>
<summary><b>매니페스트에서 무엇이 바뀌었는가</b></summary>

별도의 객체가 나타났습니다:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: passes-db
type: Opaque
data:
  password: UHJvcHVzazIwMTkh
```

`Secret`은 민감한 데이터를 위한 클러스터 객체입니다. `data` 필드의 값은 base64로 기록되므로,
파일에서는 `Propusk2019!` 자리에 이제 `UHJvcHVzazIwMTkh`가 있습니다.

그리고 Deployment에서는 값 자리에 참조가 나타났습니다:

```yaml
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: passes-db
                  key: password
```

`value` 대신 `valueFrom`은 이런 뜻입니다: "값을 여기서가 아니라, 저기 저 객체에서 가져와라."
Kubernetes는 컨테이너가 시작할 때 `passes-db` 시크릿의 `password` 키 내용을 `DB_PASSWORD`
변수에 넣어 줍니다.

이 기법 자체는 옳습니다 — 값을 직접 써넣기보다 시크릿을 참조하는 것. 문제는 그 참조의 반대편
끝에 무엇이 있느냐입니다.

</details>

**적용합니다.**

```bash
# 같은 apply. 파일에는 두 객체가 들어 있습니다 — Secret과 바뀐 Deployment; 클러스터는
# 기술된 것을 이미 가진 것과 비교해 둘을 일치시킵니다.
kubectl apply -f secrets-demo-secret.yaml
```

애플리케이션이 여전히 동작하는지 확인합시다:

```bash
# rollout status는 애플리케이션의 새 버전이 이전 버전을 완전히 대체할 때까지 기다렸다가,
# 그제서야 제어를 돌려줍니다. 이것이 없으면 이전 Pod의 로그를 읽게 될 수도 있습니다.
kubectl rollout status deploy/secrets-demo
kubectl logs deploy/secrets-demo --tail=2
```

지문은 같습니다 — `sha256:a609df223d57`. 애플리케이션은 다른 경로로 같은 비밀번호를 받았습니다.

**문제가 해결됐나요?** 비밀번호는 더 이상 Deployment에 쓰여 있지 않습니다. 파일에는 알아볼 수
없는 문자열이 있습니다. 확인해 봅시다.

## 예고된 실패 · "Secret"은 "암호화됨"을 뜻하지 않는다

이제 모든 게 괜찮은지 스스로 확인해 보세요. 시크릿 안에 무엇이 있는지 클러스터에 물어보세요:

```bash
# get … -o yaml = "객체를, 클러스터가 저장하는 그대로 통째로 보여 줘라".
# data 필드를 보세요 — 그게 시크릿의 내용입니다.
kubectl get secret passes-db -o yaml
```

같은 문자열 `UHJvcHVzazIwMTkh`가 보일 겁니다. 알아볼 수 없어 보이고, 그래서 안전해 보입니다.

이제 명령 하나:

```bash
#   -o jsonpath='{.data.password}'  객체에서 껍데기 없이 정확히 한 필드만 뽑아낸다
#   | base64 -d                     그것을 넘겨 디코딩한다: d = decode
#   ; echo                          끝에 줄바꿈을 찍는다, 그러지 않으면 결과가
#                                   다음 터미널 프롬프트에 달라붙는다
kubectl get secret passes-db -o jsonpath='{.data.password}' | base64 -d; echo
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 비밀번호를 얻기 위해 방금 정확히 무엇을 했나요? 어떤 키가 필요했나요? 이 명령을 실행할 수
> 있는 사람이 또 누가 있을까요?

출력은 `Propusk2019!`입니다. 평문으로.

**base64는 암호화가 아니라 인코딩입니다.** 텍스트를 위해 만들어진 채널로 임의의 바이트를 실어
나르려고 발명됐습니다: 이메일 첨부, JSON 안의 데이터, 설정 파일 안의 바이너리. 그 안에는 키가
없는데, 보호도 없기 때문입니다. 누구나 되돌릴 수 있습니다 — 어떤 사람이든, 어떤 브라우저든,
어떤 디코더 웹사이트든.

Kubernetes가 Secret에서 base64를 쓰는 건 바로 이 이유 때문입니다: 임의의 바이트(예를 들어
인증서나 키)를 YAML에 넣을 수는 없지만, base64로는 넣을 수 있습니다. 객체 이름의 "Secret"이라는
단어는 "여기에 민감한 것을 넣는다"는 뜻이지, "여기서 보호된다"는 뜻이 아닙니다.

이것이 실제로 의미하는 바:

| 주장 | 사실인가? |
|---|---|
| Secret은 클러스터에서 암호화되어 있다 | 아니요. 관리자가 별도로 저장 데이터 암호화를 켜지 않았다면, 클러스터의 데이터 저장소에는 거의 평문으로 놓여 있습니다 |
| Secret은 Git에 커밋해도 된다 | 아니요. 그건 거기에 비밀번호를 넣는 것과 똑같습니다 |
| 누가 Secret을 읽었는지 볼 수 있다 | 아니요. 객체를 평범하게 읽는 것은 어디에도 기록되지 않습니다 |
| Secret은 권한 없이는 읽을 수 없다 | 사실입니다, 그리고 이것이 유일한 진짜 보호입니다. 클러스터의 권한은 실제로 접근을 제한합니다 |
| Secret은 정해진 주기에 따라 스스로 바뀐다 | 아니요. 여러분이, 손으로, 모든 곳에서 한꺼번에 바꿉니다 |

**교훈은 이 오류보다 넓습니다.** 그리고 핵심. 이 모든 게 해결됐다 하더라도, 감사관의 질문은
남습니다: **지난 한 달 동안 누가 비밀번호를 읽었는지 보여 주세요.** Kubernetes는 여기에 아예
답하지 못합니다 — 잘못 만들어져서가 아니라, 그것이 그의 일이 아니기 때문입니다. 시크릿 보관은
별도의 작업이고, 그것을 위한 별도의 서비스가 있습니다.

덧붙이자면, Cozystack 테넌트에서 여러분의 역할은 `kubectl`로 시크릿을 읽게 해 주지
**않습니다** — 시도해 보면 거부당합니다. 하지만 랩 0의 lab 클러스터는 온전히 여러분 것이고,
거기서 여러분은 관리자입니다. 위 명령이 동작한 건 바로 그 때문입니다.

## 3단계. OpenBao를 주문한다

📍 **위치:** 브라우저에서, Cozystack 대시보드에서, 자기 테넌트에서.

테넌트 → **애플리케이션 생성** → `OpenBAO`.

| 필드 | 값 | 이유 |
|---|---|---|
| Name | `secrets` | 짧고, 나중에 주소에 입력해야 합니다 |
| Replicas | **1** | 학습용 테스트베드. 둘 이상이면 차트가 Raft 복제를 켜는데, 그건 이미 다른 저장 모드입니다 |
| Size | `2Gi` | 시크릿은 킬로바이트를 차지합니다; 이 공간은 내부 데이터용입니다 |
| Storage class | `replicated` | 데이터는 서로 다른 노드에 세 벌 복사본으로 놓입니다 |
| Resources preset | `t1.small` | CPU 1개, 512 MB |
| UI | 활성화 | 클러스터 내부의 웹 인터페이스 |
| External | 비활성화 | 바깥으로 노출하지 않습니다 |

⚠️ **하나의 복사본과 여러 개 사이를 전환하는 것은 체크박스가 아닙니다.** 하나의 복사본은
데이터를 파일에 저장하고, 여러 개는 Raft에 저장합니다. 모드를 바꾸려면 데이터를 마이그레이션해야
하므로, 프로덕션에서는 이 결정을 설치 후가 아니라 설치 전에 내립니다.

### 같은 것을 텍스트로 — 그리고 필드 훑어보기

랩 폴더에는 `openbao.yaml`이 있습니다:

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: OpenBAO
metadata:
  name: secrets
  namespace: tenant-workshopXX
spec:
  replicas: 1
  size: 2Gi
  storageClass: replicated
  resourcesPreset: t1.small
  ui: true
  external: false
```

`apiVersion: apps.cozystack.io/v1alpha1`은 Cozystack 카탈로그 그 자체인데, API처럼 보이는
쪽에서 본 것일 뿐입니다. 버튼을 누르면 대시보드는 정확히 이 객체를 조립해 클러스터로 보냅니다.
버튼은 텍스트 위에 얹힌 층이지, 텍스트의 대안이 아닙니다.

`kind: OpenBAO`는 카탈로그에서의 위치입니다. 대소문자에 주의하세요: `OpenBao`가 아니라
`OpenBAO`. 클러스터는 대소문자에 까다롭습니다.

`namespace: tenant-workshopXX` — **관리형 서비스는 관리 클러스터의 여러분 테넌트에 살지,
랩 0의 lab 클러스터에 있지 않습니다.** 이 둘은 서로 다른 클러스터이고, 랩의 나머지 동안 이
점을 염두에 두는 것이 중요합니다: 애플리케이션은 한쪽에, 저장소는 다른 한쪽에 있게 됩니다.

`replicas`, `size`, `storageClass`, `resourcesPreset` — 마우스로 채운 것과 같은 것들입니다.

`ui: true` — 웹 인터페이스를 올립니다. `external: false` — 서비스에 외부 주소를 주지 않습니다;
클러스터 내부에서는 어차피 닿을 수 있습니다.

이 파일은 **lab 클러스터가 아니라** 테넌트에 적용합니다:

```bash
# --kubeconfig는 접근 파일을 명시적으로 지정하고 KUBECONFIG 변수를 덮어씁니다.
# 그래서 주문은 lab 클러스터가 아니라 관리 클러스터의 테넌트로 갑니다.
kubectl --kubeconfig ~/.kube/config apply -f openbao.yaml
```

테넌트에 대한 관리 접근은 이 bastion에 이미 설정되어 있습니다 — 파일 `~/.kube/config`
(토큰 기반, 브라우저가 열리지 않음). 가져오거나 저장할 것은 없습니다.

이후 본문에서는 이 파일을 거의 쓰지 않습니다: 서비스는 마우스로 주문하고, OpenBao 자체와의
작업은 그것의 자체 API를 통합니다.

애플리케이션이 준비 상태에 도달할 때까지 기다리세요. 1~2분 걸립니다.

## 4단계. 작업용 Pod를 준비하고 연결을 확인한다

📍 **위치:** bastion에서, lab 클러스터에서.

여기서 잠시 멈춰 배치를 이해할 필요가 있습니다.

**OpenBao는 관리 클러스터의 여러분 테넌트에 삽니다.** 테넌트에서 여러분의 역할은 서비스를
주문하고 삭제하게 해 주지만, 거기서 자기 Pod를 실행하거나 포트 포워딩으로 서비스에 연결하게
해 주지는 않습니다. 이것은 결함이 아니라 경계입니다: 테넌트는 관리형 서비스를 위한 곳이지,
작업대가 아닙니다.

**여러분의 작업대는 랩 0의 lab 클러스터입니다.** 거기서 여러분은 관리자입니다. 거기서
OpenBao로 닿을 겁니다 — 모든 서비스가 가진 내부 주소를 통해:

```
openbao-secrets.tenant-workshopXX.svc.cozy.local:8200
```

이름을 부분으로 나눠 봅시다:

| 부분 | 무슨 뜻인가 |
|---|---|
| `openbao-` | 카탈로그가 이름에 붙이는 접두사. 애플리케이션을 `secrets`라고 이름 지었더니, 객체들은 `openbao-secrets…` 같은 이름을 얻었습니다 |
| `secrets` | 대시보드에서 준 이름 |
| `tenant-workshopXX` | 여러분의 테넌트. 자기 번호로 바꾸세요 |
| `svc.cozy.local` | 관리 클러스터의 내부 이름 영역 |
| `8200` | OpenBao API 포트 |

작업용 Pod를 올립시다. 그 안에는 `bao` 유틸리티가 들어 있을 겁니다 — 그것으로 저장소에 명령을
내릴 것이고, bastion에 설치할 필요는 없습니다. 자기 테넌트 번호로 바꾸세요:

```bash
# run은 주어진 이미지로 Pod 하나를 생성합니다 — 클러스터 내부의 일회용 작은 기계.
#   --image          내용을 어디서 가져올지: bao 유틸리티가 들어 있는 공식 OpenBao 이미지
#   --restart=Never  안의 명령이 끝나면 다시 올리지 않는다
#   --env            Pod의 환경 변수: 안의 어떤 명령이든 이것을 보게 된다
#   --command --     두 대시 뒤의 모든 것이 Pod가 실행할 명령이다
# sleep 86400 = "하루 동안 아무것도 하지 마라": Pod는 작업 공간으로만 필요합니다.
kubectl run bao-workbench \
  --image=openbao/openbao:2.5.1 \
  --restart=Never \
  --env=BAO_ADDR=http://openbao-secrets.tenant-workshopXX.svc.cozy.local:8200 \
  --command -- sleep 86400
# wait는 조건이 충족될 때까지 터미널을 붙잡습니다.
#   --for=condition=Ready  Pod가 시작되어 명령을 받을 준비가 됨
#   --timeout=120s         2분 뒤 포기하고 오류를 반환
kubectl wait --for=condition=Ready pod/bao-workbench --timeout=120s
```

`BAO_ADDR`은 `bao` 유틸리티가 저장소 주소를 가져오는 변수입니다. Pod를 생성할 때 한 번 설정해
두면, 매 명령마다 `-address=…`를 쓰지 않아도 됩니다.

이 Pod는 일회용 작업대라 아까울 것 없습니다: 랩 마지막에 명령 하나로 삭제합니다.

lab 클러스터에서 테넌트가 보이는지 확인합시다:

```bash
# exec = 이미 실행 중인 Pod 안에서 명령을 실행한다; 명령 자체는 -- 뒤에 온다.
# bao status는 저장소에 상태를 묻습니다: 봉인됐는지, 초기화됐는지.
# 여기서는 연결 확인도 겸합니다: 답이 오기라도 했다면 — 테넌트가 보이는 것입니다.
kubectl exec bao-workbench -- bao status
```

**보게 될 것** — 상태 표. 여기서 값 `Initialized false`와 `Sealed true`는 맞습니다:
저장소는 실행 중이지만, 아직 설정되지 않았고 닫혀 있습니다:

```
Key                Value
---                -----
Seal Type          shamir
Initialized        false
Sealed             true
Total Shares       0
Threshold          0
Version            2.5.0
Storage Type       file
```

⚠️ **명령은 0이 아닌 종료 코드를 반환합니다 — 2인데, 이것은 오류가 아닙니다.** `bao status`에서
종료 코드는 명령의 성공이 아니라 저장소의 상태를 뜻합니다: 0 — 봉인 해제됨,
2 — 봉인됨. 여러분의 셸이 0이 아닌 코드를 강조하거나 `command terminated with exit code 2`라는
문구가 보이더라도 — 놀라지 마세요, 모든 게 정상대로 진행되고 있습니다.

⚠️ **명령이 `connection refused`, `no such host`, 또는 `i/o timeout`으로 실패하면 —**
더 나아갈 이유가 없습니다; 연결이 먼저입니다. 가능성이 높은 순으로 흔한 원인:
`workshopXX`를 자기 번호로 바꾸지 않았다; 대시보드의 애플리케이션이 아직 준비되지 않았다;
이름에 오타. 이름은 `openbao-<애플리케이션 이름>` 규칙으로 만들어집니다: 애플리케이션을
`secrets`라고 이름 지었으니, 주소에는 `secrets`가 아니라 `openbao-secrets`가 들어갑니다.

## 예고된 실패 · 저장소가 서비스를 거부한다

연결이 됐으니, 비밀번호를 저장할 수 있습니다. 해 보세요:

```bash
# bao kv put = 저장소에 레코드를 넣는다.
#   secret/passes/db  그것이 놓일 경로
#   password=…        레코드의 내용: "필드 이름 = 값" 쌍
kubectl exec bao-workbench -- bao kv put secret/passes/db password=Propusk2026
```

**보게 될 것** — 기록 확인 대신 거부:

```
Error making API request.
Code: 503. Errors:
* Vault is sealed
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 서비스는 실행 중이고 포트도 응답하는데, 저장소는 동작하기를 거부합니다. 실행 중인 서비스가
> 왜 일부러 요청을 처리하지 않을 수 있을까요? 그리고 왜 그것이 십중팔구 옳은 일일까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

앞 단계의 `bao status` 출력을 더 자세히 보세요:

```
Sealed             true
Initialized        false
```

**봉인된 저장소는 방금 설치된 OpenBao의 정상 상태입니다.** 디스크의 데이터는 마스터 키로
암호화되어 있고, 마스터 키는 프로세스의 메모리에 없습니다. 거기에 놓이기 전까지 서비스는
아무것도 읽지도 쓰지도 못하며, 모든 것을 정직하게 거부합니다.

랩의 나머지 내내 "봉인을 해제한다"는 정확히 한 가지를 뜻합니다: 저장소에 마스터 키의 조각들을
제시해 저장소가 키를 자기 메모리에 넣게 하는 것. 이 말은 종이에 인쇄하는 것과는 아무 상관이
없습니다.

왜 이렇게 만들어졌는가. 마스터 키가 암호화된 데이터 옆에 놓여 있다면, 암호화는 아무 의미가
없을 겁니다: 디스크를 훔친 사람이 둘 다 얻으니까요. 그래서 키는 **오직 RAM에만** 살고, 사람이나
외부 시스템이 그것을 제시할 때 거기로 들어갑니다.

여기서 곧바로 받아들일 만한 결론이 하나 따라옵니다: **Pod를 재시작할 때마다 OpenBao는 다시
봉인됩니다.** 노드가 재부팅되고, 버전이 업그레이드되고, 클러스터가 Pod를 옮기면 — 저장소는
봉인을 해제할 때까지 다시 응답을 멈춥니다. 프로덕션에서는 이것을 외부 모듈(클라우드 KMS,
하드웨어 HSM)을 통한 자동 봉인 해제로 처리하는데, 그건 그 자체로 하나의 프로젝트입니다. 랩에서는
손으로 봉인을 해제하고 그 메커니즘을 실제로 봅니다.

**교훈은 이 오류보다 넓습니다.** **관리형 서비스는 설치, 업그레이드, 복제, 백업을 여러분의
어깨에서 덜어 줬지만, 운영상의 결정까지 덜어 주지는 않았습니다.** Cozystack은 2분 만에 여러분을
위해 OpenBao 프로세스를 올려 줬습니다. 봉인 해제 키를 어디에 보관할지, 누가 봉인을 해제해도
되는지, 노드가 재부팅된 새벽 세 시에 무엇을 할지 — 이것들은 여전히 여러분의 질문이고, 플랫폼이
이를 여러분 대신 조용히 답해 버리지 않은 것은 다행입니다.

</details>

## 5단계. 초기화하고 봉인을 해제한다

📍 **위치:** bastion에서, lab 클러스터에서.

**이제 벌어질 일:** OpenBao는 마스터 키를 생성해 조각으로 자르고, root 토큰과 함께 우리에게
건네줍니다. 이 일은 두 번 다시 일어나지 않습니다 — 키는 정확히 한 번만 보여 줍니다.

```bash
# operator init은 저장소의 일생에 한 번 실행됩니다: 마스터 키를 만들어 그 조각들을
# root 토큰과 함께 출력합니다. 이 값들을 다시 보여 줄 사람은 아무도 없습니다.
#   -key-shares=1     마스터 키를 몇 조각으로 자를지
#   -key-threshold=1  그것을 다시 합치려면 몇 조각을 제시해야 하는지
kubectl exec bao-workbench -- bao operator init -key-shares=1 -key-threshold=1
```

**보게 될 것:**

```
Unseal Key 1: 8kJq…=
Initial Root Token: s.7Yx…
```

⚠️ **지금 당장 두 값을 bastion의 파일에 복사하세요** — 예를 들어
`~/openbao-lab.txt`에, 클립보드에만이 아니라. 다시 보여 줄 사람은 아무도 없습니다. 봉인 해제
키를 잃으면 저장소의 모든 시크릿을 잃습니다 — 그것을 복구하는 것은 설계상 불가능합니다.

둘 다 여러 번 필요하고, 그 시점은 이렇습니다:

- **봉인 해제 키** — 저장소의 Pod가 재시작할 때마다. 재시작하면 다시 봉인되고, 모든 명령이
  `Code: 503 ... * Vault is sealed`라고 답하기 시작합니다.
  해법은 멈췄던 바로 그 자리에서 같은 명령으로 다시 봉인을 해제하는 것입니다;
- **root 토큰** — 랩 마지막에, 확인 스크립트를 위해. 이 두 순간 사이에 랩 거의 전체가 지나가고,
  그때쯤이면 여러분은 십중팔구 터미널을 닫아 놨을 겁니다.

<details>
<summary><b>`-key-shares`와 `-key-threshold`가 무슨 뜻인지, 그리고 프로덕션은 왜 다른지</b></summary>

마스터 키는 통째로 넘겨지지 않습니다. `key-shares`개의 조각으로 잘리고, 그것을 다시 합치려면
그중 `key-threshold`개를 제시해야 합니다. 이 방식은 샤미르의 비밀 공유(Shamir's Secret
Sharing)라고 합니다.

핵심은 **한 사람이 혼자서는 봉인을 해제할 수 없다**는 것입니다. 고전적인 프로덕션 구성은 조각
다섯 개에 임계값 셋입니다: 조각은 서로 다른 부서의 다섯 보유자에게 나눠 주고, 재부팅 후 저장소를
올리려면 아무 셋을 모아야 합니다. 퇴사하는 관리자 한 명이 접근 권한을 들고 나가지 못하고,
부정직한 관리자 한 명이 그것을 혼자 손에 넣지 못합니다.

우리는 조각 하나에 임계값 하나로 설정하는데, 랩에서는 여러분 혼자이고 우리가 원하는 것은
절차가 아니라 메커니즘이기 때문입니다. **프로덕션에서 이렇게 하면 안 됩니다**, 그리고 이건
형식적인 말이 아닙니다: 조각 하나는 모든 것이 새어 나갈 수 있는 단일 지점을 뜻합니다.

</details>

봉인을 해제하세요. 자기 봉인 해제 키로 바꾸세요:

```bash
# unseal은 저장소에 마스터 키의 조각 하나를 건넵니다. 조각이 임계값에 이르면,
# 키가 프로세스의 메모리에 들어가고 저장소가 요청 처리를 시작합니다.
kubectl exec bao-workbench -- bao operator unseal <여러분의-봉인-해제-키>
# 바뀐 상태를 보기 위해 status를 다시 실행합니다.
kubectl exec bao-workbench -- bao status
```

**보게 될 것** — `Sealed  false`와 `Initialized  true`.

이제 root 토큰으로 로그인합니다. 그것은 작업용 Pod 안에 기억되고, 이후 명령들은 토큰을 묻지
않습니다:

```bash
# login은 입력한 토큰을 Pod 안 파일의 항목으로 교환합니다 — 그때부터 유틸리티는
# 토큰을 거기서 스스로 가져오고, 매 명령마다 입력하지 않아도 됩니다.
# -it는 Pod에 터미널을 줍니다: 이것이 없으면 유틸리티는 프롬프트를 출력할 곳도, 입력을 받을 곳도 없습니다.
kubectl exec -it bao-workbench -- bao login
```

유틸리티는 토큰을 물어보고 **입력하는 동안 보여 주지 않습니다** — 의도된 것입니다.
`init` 출력의 Initial Root Token을 붙여넣으세요.

⚠️ **`bao login`이 토큰 파일을 쓸 수 없다고 불평하면**, 매 명령마다 토큰을 환경
변수로 전달하세요:
`kubectl exec bao-workbench -- env BAO_TOKEN='여러분의-토큰' bao status`.
동작은 하지만, 토큰이 명령 이력에 남습니다 — 랩에서는 참을 만하지만, 프로덕션에서는 아닙니다.

## 6단계. 엔진을 켜고 비밀번호를 저장한다

📍 **위치:** bastion에서, lab 클러스터에서.

갓 설치된 OpenBao는 비어 있습니다: 그 안에는 무언가를 넣을 곳이 하나도 없습니다. 시크릿 엔진은
명시적으로 켭니다.

```bash
# secrets enable은 엔진을 켭니다 — 한 종류의 일을 아는 저장소의 한 부분.
#   -path=secret  그것을 어느 경로에 걸지: 이제부터 모든 것이 secret/…으로 기록된다
#   kv-v2         정확히 어떤 엔진인지: 버전 이력이 있는 "키-값"
kubectl exec bao-workbench -- bao secrets enable -path=secret kv-v2
```

<details>
<summary><b>시크릿 엔진이 무엇인지, 그리고 왜 하나 이상인지</b></summary>

OpenBao는 단일 저장소가 아니라 엔진들의 집합인데, 각각은 자기 일을 알고 자기 경로에
마운트됩니다:

| 엔진 | 하는 일 |
|---|---|
| `kv-v2` | 넣은 것을 버전 이력과 함께 저장합니다. 평범한 "키-값" |
| 데이터베이스 엔진 | PostgreSQL이나 MongoDB에 두 시간짜리 임시 사용자를 **스스로** 만들고 스스로 삭제합니다 |
| PKI | 보안 부서에 1년에 한 번 요청하는 대신, 요청 시 인증서를 발급합니다 |
| transit | 데이터를 저장하지 않고 요청 시 암호화합니다: 키는 저장소를 결코 떠나지 않습니다 |

`-path=secret` — 그것을 어느 경로에 마운트할지. 이제부터 이 엔진에 대한 모든 접근은
`secret/…`을 통합니다.

우리는 `kv-v2`를 택합니다 — 가장 단순한 경우: 저장해야 할 완성된 비밀번호가 있습니다.
데이터베이스 엔진은 훨씬 더 흥미롭습니다: 영구 비밀번호라는 현상 자체를 없애고, 실행할 때마다
애플리케이션에 임시 계정을 발급합니다. 그건 다음 단계이고, 거기까지는 자라야 합니다; 여기서
시작하는 게 합리적입니다.

</details>

비밀번호를 저장합니다:

```bash
# kv put은 완전히 새로운 버전을 기록합니다: 나열된 필드가 그 내용이 됩니다.
# 필드는 몇 개든 될 수 있습니다; 여기서는 둘 — 비밀번호와 데이터베이스 사용자 이름.
kubectl exec bao-workbench -- \
  bao kv put secret/passes/db password=Propusk2026 username=passes_app
```

**보게 될 것** — `version  1`과 생성 시각이 있는 작은 표.

다시 읽히는지 확인합시다:

```bash
# kv get은 레코드를 읽어 그 필드를 표로 출력합니다. 아직은 root 토큰으로 읽고 있습니다 — 즉,
# 애플리케이션에 권한이 충분한지가 아니라, 레코드가 자리 잡았는지를 확인하는 것입니다.
kubectl exec bao-workbench -- bao kv get secret/passes/db
```

## 7단계. 애플리케이션에 접근을 부여한다 — 정확히 한 줄에만

📍 **위치:** bastion에서, lab 클러스터에서.

애플리케이션에 root 토큰을 주면 안 됩니다: 그것으로는 다른 사람의 시크릿을 읽거나 저장소를
삭제하는 것을 포함해 무엇이든 할 수 있습니다. 애플리케이션에 필요한 것은 단 하나의 경로에 대한
읽기 접근입니다.

정책을 작성합시다:

```bash
# policy write는 이름 붙은 권한 목록을 저장소에 저장합니다.
#   passes-read  정책 이름; 나중에 이 이름으로 토큰에 부여됩니다
#   -            정책 텍스트를 파일이 아니라 표준 입력에서 가져온다
#   -i           kubectl exec에서: 그 입력을 Pod 안으로 전달한다
# <<'HCL' … HCL은 파일 없이 여러 줄 텍스트를 명령에 바로 전달하는 방법입니다.
kubectl exec -i bao-workbench -- bao policy write passes-read - <<'HCL'
path "secret/data/passes/db" {
  capabilities = ["read"]
}
path "secret/metadata/passes/db" {
  capabilities = ["read"]
}
HCL
```

<details>
<summary><b>정책 읽기</b></summary>

정책은 경로들과 각 경로에서 허용되는 것들의 목록입니다. 명시적으로 허용되지 않은 것은 모두
거부됩니다; 별도의 "거부"를 쓸 필요가 없습니다.

```hcl
path "secret/data/passes/db" {
  capabilities = ["read"]
}
```

`secret/data/passes/db`는 파일시스템이 아니라 **API 안의** 경로입니다. `kv-v2` 엔진에서는
이렇게 구성됩니다: `secret` — 엔진이 마운트된 곳, `data` — 엔진 자체의 내부 접두사,
`passes/db` — `kv put` 명령에서 지정한 것.

⚠️ **이 `data` 접두사가 알 수 없는 거부의 절반의 원인입니다.** 명령줄에서는
`secret/passes/db`라고 쓰지만, 정책에서는 `secret/data/passes/db`라고 씁니다. `bao kv`
유틸리티는 `data`를 대신 넣어 주지만, 정책은 그렇지 않습니다.

`capabilities = ["read"]` — 읽기만. 쓰기도, 삭제도, 이웃 경로 나열도 아닙니다.

두 번째 블록 `secret/metadata/passes/db`는 버전 정보에 대한 접근입니다: 언제 기록됐는지,
버전이 몇 개인지, 어느 것이 현재인지. 이것도 읽기만.

`bao policy write passes-read -` — 끝의 대시는 "내용을 표준 입력에서 읽어라"를 뜻합니다.
그래서 명령을 `kubectl exec -i`로 실행합니다: `-i` 플래그가 입력을 Pod 안으로 전달합니다.

</details>

이 정책으로 토큰을 발급합니다:

```bash
# token create는 새 토큰을 발급하고 권한 집합을 그것에 묶습니다.
#   -policy=passes-read  어떤 권한을: 위에서 작성한 정책
#   -ttl=24h             수명; 하루 뒤 토큰은 스스로 동작을 멈춥니다
#   -field=token         토큰 값만 출력, 주위의 표 없이 —
#                        그래야 복사해 넘겨주기 쉽습니다
kubectl exec bao-workbench -- \
  bao token create -policy=passes-read -ttl=24h -field=token
```

**보게 될 것** — 토큰이 담긴 한 줄.

토큰을 복사하세요 — 곧 필요합니다.

여기서 수명은 형식적인 것이 아닙니다. 토큰이 로그에 흘러 들어가고, 백업에 들어가고, bastion과
함께 새어 나가도 — 모레면 쓸모없습니다. 매니페스트의 비밀번호에는 그런 성질이 없습니다.

## 8단계. 토큰을 클러스터에 넣고 매니페스트에서 비밀번호를 제거한다

📍 **위치:** bastion에서, lab 클러스터에서.

애플리케이션은 자기가 주장하는 바로 그것임을 OpenBao에 증명할 무언가가 필요합니다. 그 무언가가
바로 토큰입니다.

```bash
# create secret generic은 디스크의 파일을 거치지 않고 클러스터에 직접 Secret 객체를 생성합니다.
#   passes-bao-token      객체 이름; 애플리케이션 명세가 이 이름으로 시크릿을 참조합니다
#   --from-literal=name=…  값을 명령줄에서 문자열로 설정한다
#                          (값이 파일에 있을 때 쓰는 --from-file도 있습니다)
kubectl create secret generic passes-bao-token \
  --from-literal=token='앞-단계의-토큰을-붙여넣으세요'
```

**유의: 파일이 아니라 명령입니다.** 토큰은 클러스터에 직접 생성되어 Git에는 절대 들어가지
않습니다 — 그것이 들어갈 파일이 없으니까요.

<details>
<summary><b>시크릿 제로: 우리가 이기지 못한 것에 대한 정직한 이야기</b></summary>

합리적인 반론: 우리는 데이터베이스 비밀번호를 없앴지만 클러스터에 토큰을 넣었습니다. 그저 문제
하나를 다른 문제로 바꾼 것 아닐까요?

그렇지 않습니다, 그리고 토큰이 비밀번호와 어떻게 다른지는 이렇습니다:

| | 매니페스트의 비밀번호 | 클러스터의 토큰 |
|---|---|---|
| Git에 있는가 | 예, 영원히, 커밋 이력 전체에 | 아니요, 명령으로 생성됐습니다 |
| 수명 | 영원 | 하루, 그다음 스스로 죽음 |
| 무엇을 부여하는가 | 출입증 데이터베이스에 대한 완전한 접근 | 저장소에서 한 줄 읽기 |
| 취소 | 쓰여 있는 모든 곳에서 비밀번호 변경 | 명령 하나, 즉시 |
| 누가 썼는지 볼 수 있는가 | 아니요 | 예, 감사 로그에서 |

하지만 이것이 문제를 완전히 닫지는 못하고, 닫힌 척하는 것은 정직하지 못한 일입니다.
**애플리케이션이 나머지에 대한 권리를 증명하는 시크릿은 언제나 하나 남습니다.** 그것에는
이름까지 있습니다 — 시크릿 제로. 그것을 없애는 것은 불가능합니다: 무언가로 자신을 밝혀야
하니까요.

어른스러운 시스템이 그것으로 하는 일:

- **Kubernetes 인증.** OpenBao는 Pod의 서비스 토큰을 Kubernetes 자체에 대조해 검증하고,
  그 대가로 자기 토큰을 발급합니다. 그러면 "시크릿 제로"는 사람이 거기 넣은 문자열이 아니라,
  클러스터가 부여하는 Pod의 아이덴티티가 됩니다
- **일회용 토큰(response wrapping).** 운영자가 한 번만 쓸 수 있는 토큰을 발급합니다.
  애플리케이션이 "이미 사용됨" 거부를 받으면, 토큰이 가로채인 것입니다 — 그리고 그것은
  즉시 보입니다

두 접근법 모두 존재하고 동작하지만, 이 랩에서는 우리를 너무 멀리 데려가 버릴 겁니다. 길이
있다는 것, 그리고 목표가 "시크릿 0개"가 아니라 "영원한 시크릿 열댓 개 대신 수명이 짧고 좁고
취소 가능한 시크릿 하나"라는 것을 기억해 두세요.

</details>

이제 깨끗한 매니페스트를 적용합니다. 먼저, 자기 테넌트 번호로 바꾸세요:

```bash
# sed는 s/바꿀-것/바꿀-내용/g 패턴으로 텍스트를 편집합니다; g = 첫 번째만이 아니라
# 줄의 모든 곳에서. -i는 결과를 화면에 출력하는 대신 "파일 자체를 편집한다"는 뜻입니다.
# 예시의 workshop03 자리에, 자기 번호를 넣으세요.

# macOS: -i 뒤의 빈 따옴표는 필수입니다 — 그러지 않으면 sed가 다음 단어를
# 백업 파일 확장자로 받아들여 아무것도 바꾸지 않습니다
sed -i '' 's/tenant-workshopXX/tenant-workshop03/g' secrets-demo.yaml
# Linux
sed -i 's/tenant-workshopXX/tenant-workshop03/g' secrets-demo.yaml
```

<details>
<summary><b>자세히 보기: secrets-demo.yaml 안에 무엇이 있는가</b></summary>

핵심부터 시작합시다: **이 파일에서 비밀번호를 찾아보세요.** 거기 없습니다 — 평문으로도,
base64로도, 그것이 담겨 있을 객체에 대한 참조로도.

```yaml
      volumes:
        - name: secrets
          emptyDir:
            medium: Memory
            sizeLimit: 1Mi
```

`emptyDir`은 Pod와 같은 동안 살고 그와 함께 사라지는 임시 폴더입니다. `medium: Memory`는 그것이
디스크의 파일이 아니라 RAM의 한 영역임을 뜻합니다. 비밀번호는 노드의 디스크에도, 볼륨 스냅샷에도,
백업에도 닿지 않습니다.

```yaml
      initContainers:
        - name: fetch-secret
          image: openbao/openbao:2.5.1
```

init 컨테이너는 메인 컨테이너 **앞에** 실행되어 성공적으로 끝나야 하는 컨테이너입니다. 실패하면
메인 컨테이너는 아예 시작하지 않습니다. 시크릿을 가져오는 데는 이것이 바로 원하는 동작입니다:
애플리케이션이 빈 비밀번호로 시작했다가 데이터베이스에 첫 요청을 할 때 실패하면 안 되니까요.

```yaml
              bao kv get -field=password secret/passes/db \
                | tr -d '\n' > /secrets/db_password
              chmod 0400 /secrets/db_password
```

필드 하나를 가져와 파일에 씁니다. `tr -d '\n'`은 혹시 줄바꿈이 나타나면 그것을 제거합니다: 끝에
여분의 문자가 붙은 비밀번호는 데이터베이스에 통하지 않고, 그걸 추적하는 일은 불쾌합니다.
`chmod 0400` — 소유자만 읽을 수 있습니다.

```yaml
          env:
            - name: BAO_ADDR
              value: http://openbao-secrets.tenant-workshopXX.svc.cozy.local:8200
            - name: BAO_TOKEN
              valueFrom:
                secretKeyRef:
                  name: passes-bao-token
                  key: token
```

저장소의 주소와 토큰. 토큰은 여러분이 명령으로 생성한 객체에 대한 참조로 옵니다. 파일에는 객체
이름만 들어 있고, 이름은 시크릿이 아닙니다.

```yaml
      securityContext:
        runAsNonRoot: true
        runAsUser: 100
        runAsGroup: 1000
        fsGroup: 1000
```

모든 것이 비-root로 실행됩니다. `fsGroup`은 두 컨테이너 — 파일을 쓰는 쪽과 읽는 쪽 — 이 모두
폴더에 접근할 수 있게 하는 데 필요합니다. 이것이 없으면 init 컨테이너는 메인 컨테이너가 열 수
없는 파일을 쓰게 되고, 여러분은 어디서 틀렸는지 30분을 헤매게 됩니다.

```yaml
          volumeMounts:
            - name: secrets
              mountPath: /secrets
              readOnly: true
```

폴더는 메인 컨테이너에 읽기 전용으로 주어집니다. 애플리케이션은 비밀번호를 훼손할 수도,
바꿔치기할 수도 없습니다.

</details>

**적용합니다.** Deployment는 새 버전으로 넘어갑니다: init 컨테이너가 저장소로 가서 비밀번호를
Pod의 메모리에 넣고, 그제서야 애플리케이션 자체가 시작합니다.

```bash
kubectl apply -f secrets-demo.yaml
# 새 버전이 이전 버전을 완전히 대체할 때까지 기다립니다. init 컨테이너가 비밀번호를
# 가져오지 못하면, 기다림은 끝나지 않습니다 — 그리고 그것이 바로 우리가 원하는 동작입니다.
kubectl rollout status deploy/secrets-demo
```

## 9단계. 애플리케이션이 저장소에서 비밀번호를 받았는지 확인한다

📍 **위치:** bastion에서, lab 클러스터에서.

먼저 init 컨테이너가 뭐라고 했는지 봅시다:

```bash
# -c는 Pod 안의 컨테이너를 선택합니다. 여기엔 둘이 있어서, -c 없이는 kubectl이 어느 것을
# 뜻하는지 추측할 수 없습니다. fetch-secret은 애플리케이션이 시작하기 전에 실행된 것입니다.
kubectl logs deploy/secrets-demo -c fetch-secret
```

**보게 될 것:**

```
password fetched from OpenBao, not present in the manifest
```

이제 서비스 자체:

```bash
# 메인 컨테이너: init 컨테이너가 놓은 파일을 읽습니다.
kubectl logs deploy/secrets-demo -c app --tail=2
```

지문이 **바뀌었습니다** — 예전엔 `sha256:a609df223d57`였는데, 지금은 다릅니다. 애플리케이션은
리포지터리의 어떤 파일에도 없는 새 비밀번호로 동작하고 있습니다.

순진한 시크릿을 제거합시다; 더 이상 필요 없고 방해만 됩니다:

```bash
# delete는 클러스터에서 객체를 제거합니다. 애플리케이션은 더 이상 그것을 참조하지 않으므로,
# 삭제해도 아무것도 망가지지 않습니다.
kubectl delete secret passes-db
```

## 10단계. 로테이션: 파일 하나 건드리지 않고 비밀번호를 바꾼다

📍 **위치:** bastion에서, lab 클러스터에서.

감사관의 첫 번째 요구로 돌아갑시다: "비밀번호를 바꾸세요." 예전에 이것은 그것이 쓰여 있는
모든 곳을 찾아 고치고, 커밋하고, 롤아웃하고, 아무것도 빠뜨리지 않았기를 바라는 것을 뜻했습니다.

이제는:

```bash
# 같은 kv put. 레코드의 이전 버전은 지워지지 않습니다 — 그 옆에 두 번째 것이 나타납니다.
kubectl exec bao-workbench -- \
  bao kv put secret/passes/db password=Propusk2026-осень username=passes_app
# rollout restart는 애플리케이션 명세의 단 한 줄도 바꾸지 않고 애플리케이션의 Pod를 다시 만듭니다.
# 이 모든 것이 이걸 위한 것이었습니다: 새 비밀번호는 다음 시작 때 적용됩니다.
kubectl rollout restart deploy/secrets-demo
kubectl rollout status deploy/secrets-demo
# 로그의 지문이 비밀번호 자체는 보여 주지 않으면서 비밀번호가 바뀌었음을 보여 줍니다.
kubectl logs deploy/secrets-demo -c app --tail=2
```

**보게 될 것** — 지문이 다시 바뀌었습니다. 명령 둘, 바뀐 파일 0개, 커밋 0개.

⚠️ **애플리케이션은 새 값을 즉시가 아니라 재시작 때 가져옵니다.** 우리는 시작 시 init
컨테이너로 시크릿을 가져옵니다 — 단순하고 믿을 만한 방식이지만, 갱신하려면 재시작이 필요합니다.
서비스가 시크릿을 실시간으로 가져와야 한다면, 값을 타이머에 맞춰 다시 읽고 파일을 갱신하는
사이드카 컨테이너를 추가합니다. 그건 더 복잡하고, 여기서 시작할 것은 아닙니다.

이력을 봅시다:

```bash
# kv metadata get은 값이 아니라 레코드의 버전에 대한 정보를 보여 줍니다: 몇 개인지,
# 각각 언제 생성됐는지, 지금 어느 것이 현재인지.
kubectl exec bao-workbench -- bao kv metadata get secret/passes/db
```

**보게 될 것** — 두 버전과 각각의 생성 시각. 예전 값은 사라지지 않았습니다: 새 비밀번호가
데이터베이스에 맞지 않는 것으로 드러나면, 되돌아갈 곳이 있습니다.

이전 값을 통째로 읽을 수도 있습니다:

```bash
# -version=1은 현재 버전 대신 처음 기록된 버전을 읽습니다.
kubectl exec bao-workbench -- bao kv get -version=1 secret/passes/db
```

이것이 바로 **로테이션**입니다: 유출이 일어난 뒤가 아니라 계획에 따라 시크릿을 새것으로
교체하는 것. "서비스 계정 비밀번호는 분기에 한 번 바꾼다" 같은 규칙이 달성 불가능한 것에서
일정표의 한 줄로 바뀝니다.

## 11단계. 감사 로그: 누가 무엇을 요청했는가

📍 **위치:** bastion에서, lab 클러스터에서.

감사관의 두 번째 요구 — "누가 비밀번호를 읽었는지 보여 주세요." 로그를 켭시다:

```bash
# audit enable은 감사 장치를 켭니다.
#   file              장치 유형: 레코드를 텍스트로 기록
#   file_path=stdout  디스크의 파일 대신 — Pod의 표준 출력으로, 거기서
#                     플랫폼이 로그를 수집합니다
kubectl exec bao-workbench -- bao audit enable file file_path=stdout
# audit list는 켜진 장치를 나열합니다 — 위 명령이 통했는지 확인.
kubectl exec bao-workbench -- bao audit list
```

**보게 될 것** — `file` 유형의 장치 하나가 켜진 표.

<details>
<summary><b>감사 로그에 무엇이 들어가고, 평범한 로그와 어떻게 다른지</b></summary>

이 순간부터 OpenBao는 **모든 API 요청마다** 레코드를 씁니다: 누가 물었는지(어떤 토큰, 어떤
정책), 정확히 무엇을, 언제, 어느 주소에서, 그리고 무엇이 응답됐는지. 요청당 레코드가 둘입니다 —
요청 자체와 그에 대한 응답.

익숙한 애플리케이션 로그와의 세 가지 차이:

**거부도 기록됩니다.** 다른 사람의 경로를 읽으려는 시도는 성공한 읽기와 똑같이 흔적을 남깁니다.
보안팀의 관심을 끄는 것은 바로 거부입니다: 성공한 읽기는 업무이지만, 잇따른 거부는 정찰입니다.

**시크릿 값은 로그에 들어가지 않습니다.** 경로, 이름, 토큰은 해시되고, 시크릿 자체는 기록되지
않습니다. 로그는 그 내용까지 함께 넘기지 않고 바깥으로 넘길 수 있습니다.

**로그를 쓸 곳이 없으면, OpenBao는 동작을 멈춥니다.** 이것은 의도된 결정입니다: 요청을 기록하지
못하면서 처리하는 저장소는 멈춘 저장소보다 나쁩니다. 여기서 실용적인 따름정리가 나옵니다 —
유일한 감사 장치를 가득 찰 수 있는 디스크의 파일로 향하게 하지 마세요.

⚠️ **이 로그는 랩에서 읽을 수 없고, 이것은 분명히 말해야 합니다.** 우리는 그것을 OpenBao Pod의
표준 출력으로 보냈는데, 여러분의 역할은 테넌트에 있는 Pod의 로그를 읽을 수 없습니다 — 테넌트는
서비스의 관리를 여러분에게 넘겨주지만, 그 내부에 대한 접근은 넘겨주지 않습니다. 실제 설치에서는
플랫폼의 로그 수집기가 로그를 가져다 보안팀이 보는 곳에 두지, 여러분이 `kubectl`로 보는 것이
아닙니다.

그래도 여러분 자신이 볼 수 있는 것은 앞 단계의 버전 이력(`bao kv metadata get`)입니다: 누가,
언제 **썼는지**, 초 단위까지. 완전한 감사는 아니지만, "비밀번호를 마지막으로 언제 바꿨는가"라는
질문에는 답합니다.

</details>

옆에 보고서 파일이 나타납니다. **어떤 시크릿도 보고서에 들어가지 않습니다** — 버전, 이름,
지문만.

## 정리

```bash
# delete -f = "이 파일에 기술된 모든 것을 클러스터에서 제거하라".
kubectl delete -f secrets-demo.yaml
# 파일이 아니라 명령으로 생성된 것은 이름으로 삭제합니다.
kubectl delete secret passes-bao-token
kubectl delete pod bao-workbench
```

OpenBao 자체는 대시보드에서 삭제합니다: `secrets` 애플리케이션 → 삭제.

왜 이것이 싼가. 고전적인 설치에서 시크릿 저장소는 하나의 프로젝트입니다: 서버, 클러스터링,
인증서, 봉인 해제 절차, 모니터링 통합. 여기서 여러분은 그것을 2분 만에 얻고 10초 만에 돌려줬으며,
그것이 차지했던 공간은 해제됩니다.

⚠️ **삭제하면 안에 있는 모든 시크릿이 제거됩니다.** 삭제된 저장소의 봉인 해제 키와 root 토큰은
쓸모없는 문자열로 변합니다. 거기에 진짜 무언가를 넣었다면 — 먼저 꺼내세요.

## 이제 우리가 할 수 있는 것

- Kubernetes의 Secret이 왜 "암호화"가 아닌지 동료에게 설명하고, 명령 하나로 뒷받침하기
- 무슨 일이 벌어지는지 이해하면서 OpenBao를 주문하고, 초기화하고, 봉인을 해제하기
- 시크릿을 저장소에 넣고, 수명이 짧은 토큰으로 애플리케이션에 정확히 한 경로에 대한 접근을
  부여하기
- 리포지터리의 파일 하나 건드리지 않고 비밀번호를 바꾸고, 버전 이력을 보기
- "누가 이 비밀번호를 읽었는가"라는 질문에 분명히 답하기 — 그리고 그 답이 어디서 나오는지
  이해하기

## 그리고 vSphere에서라면

직접적인 비유가 없고, 그것이 정직한 답입니다. 고전적인 인프라에서 서비스 계정 비밀번호는 세 곳에
동시에 삽니다: VM의 설정 파일 안, 부서의 비밀번호 관리자 안, 그리고 그것을 설정한 사람의 머릿속.
로테이션은 이 셋을 모두 도는 여정을 뜻하고, 그래서 하지 않습니다. "누가 읽었는가"라는 질문에는
답이 없는데, 파일을 읽는 것을 아무도 기록하지 않기 때문입니다.

vSphere Credential Store가 있고, Windows Credential Manager가 있고, 기업용 비밀번호 관리자가
있습니다 — 이들 모두 "사람이 비밀번호를 보관하기에 편리하다"는 문제를 해결합니다.
"애플리케이션이 정책에 따라, 제한된 시간 동안, 기록에 남긴 채 비밀번호를 스스로 받아온다"는
문제는 해결하지 못합니다.

**vSphere가 더 편리한 지점, 정직하게.** 위의 어느 것도 아닙니다 — 하지만 편리함에는 대가가
따르고, 그 대가는 이렇습니다.

VM의 파일에 있는 비밀번호는 **언제나 사용 가능합니다**: 호스트가 재부팅되고, 머신이 올라오고,
서비스가 파일을 읽어 동작하기 시작합니다. 새벽 세 시에 누군가를 깨울 필요가 없습니다. 재시작
후의 OpenBao는 봉인되어 있고, 봉인을 해제하기 전까지 애플리케이션은 시작하지 않습니다. 이것은
여러분의 인프라에 새로운 장애 지점과 새로운 절차를 더합니다 — 당직자와, 키 보유자와, 문서화된
프로세스와 함께. 외부 KMS를 통한 자동 봉인 해제는 이 문제를 없애지만, 바로 그 외부 KMS에 대한
의존을 더합니다.

그리고 둘째. 디스크의 파일은 어떤 관리자든 한눈에 이해합니다. 경로, 정책, 토큰, TTL, 경로
한가운데의 `data` 접두사 — 이것은 팀이 배워야 할 별도의 모델이고, 처음 두어 달 동안은 알 수 없는
거부의 원천이 될 겁니다.

그래도 이득이 더 크지만, 공짜가 아니며, 이 비용을 염두에 두고 마이그레이션을 계획해야 합니다.
