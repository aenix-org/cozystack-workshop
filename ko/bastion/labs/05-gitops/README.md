## 왜 중요한가

연습은 끝났습니다. 지금부터는 실제 업무입니다.

비즈니스 쪽에서 **「출입증」**이라는 내부 서비스를 원합니다. 직원이 모바일 앱으로 방문자 출입증을 신청하면, 경비가 정문에서 그 목록을 보고, 경영진은 한 달에 한 번 보고서를 봅니다. 여러분은 플랫폼 팀 소속이고, 이걸 출시하는 게 여러분의 일입니다.

이 서비스 뒤에는 여러 팀이 붙게 되고, 플랫폼 팀은 여러분을 포함해 셋입니다. 그리고 바로 여기서, 이 실습이 실무 파트의 맨 앞에 오는 이유가 시작됩니다.

**관리자가 셋일 때 무슨 일이 벌어지나.** 누군가는 대시보드로 앱을 띄웠습니다. 누군가는 `kubectl edit`으로 리밋을 손봤습니다. 한밤중이었고 불이 났었으니까요. 누군가는 금요일에 복제본 수를 바꿔놓고 월요일이 되자 잊어버렸습니다. 한 달 뒤, 아무도 두 가지 질문에 답하지 못합니다. **이 설정은 왜 이렇게 되어 있는가**, 그리고 **원래 어떠해야 하는가**. 그리고 전부 무너지고 나면, 복구할 근거가 아무것도 없다는 게 드러납니다. 상태는 오직 클러스터의 머릿속에만 있었고, 클러스터와 함께 사라졌으니까요.

이 병을 고치는 건 규정도 아니고, 「손으로 건드리지 말자고 다 같이 약속하기」도 아닙니다. 고치는 방법은 손으로 건드리는 일을 **무의미하게** 만드는 것입니다. 클러스터가 알아서 원래대로 되돌려 놓습니다. 오늘 우리가 켜는 게 바로 이것입니다.

## 작은 용어집

| 용어 | 무엇인가 | 비슷한 것… 하지만 |
|---|---|---|
| **저장소** | 파일들의 집합에, 그 편집 이력 전체가 함께 담긴 것: 무엇이 바뀌었는지, 누가 바꿨는지, 왜 바꿨는지 | **공유 드라이브에 있는 템플릿 폴더**, 다만 하나를 다 같이 쓰는 게 아니라 각자 자기 전체 복사본을 가집니다 |
| **GitOps** | 하나의 접근 방식: 원하는 상태는 Git에 놓여 있고, 클러스터에서 도는 에이전트가 그것을 클러스터로 실어 나릅니다 | **blueprint을 쓰는 vRealize Automation**, 다만 일회성 적용이 아니라 끊임없는 조정(reconcile)입니다 |
| **Flux** | 바로 그 에이전트. 클러스터 안에서 돕니다 | **스케줄에 따라 도는 에이전트/스크립트**, 다만 「적용하고 잊기」가 아닙니다: 매분 확인하고 어긋난 부분을 바로잡습니다 |
| **Kustomization** | 클러스터 안의 객체: 저장소에서 정확히 무엇을 적용할지 | **배포 작업(job)**, 다만 `kustomize` 유틸리티와 혼동하지 마세요 — 이름은 같지만 뜻이 다릅니다 |

이 실습의 나머지 단어들 — Git, 커밋, 브랜치, Pull request, 조정(reconciliation), 드리프트(drift), GitRepository, Prune — 은 진행하면서, 처음 필요해지는 단계에서 소개됩니다. 지금 외울 필요는 없습니다: 행동과 떨어져서는 어차피 머리에 남지 않으니까요.

| **드리프트(drift)** | 사실과 기술 사이의 어긋남 | **템플릿을 벗어나 이뤄진 변경**, 다만 여기서 드리프트는 「규정 준수 보고서에 기록되는」 게 아니라 조용히 제거됩니다 |
| **GitRepository** | 클러스터 안의 객체: 상태를 어디서 가져올지 | **템플릿 소스 설정**, 다만 소스는 누군가 「배포」를 누르는 순간이 아니라 스케줄에 따라 스스로 조회됩니다 |
| **Prune** | 「Git에서 사라진 것을 클러스터에서 삭제하는」 모드 | 직접적인 비유는 없습니다; 이것이 없으면 저장소에서 파일을 삭제해도 클러스터에서는 아무것도 삭제되지 않습니다 |

보내기 전에 — 무엇을 넣는지 살펴봅시다.

<details>
<summary><b>자세히 보기: namespace.yaml와 passes.yaml 안에 무엇이 있나</b></summary>

### `namespace.yaml` — 나만의 namespace

```yaml
kind: Namespace
metadata:
  name: passes
```

namespace는 하나의 클러스터 안의 논리적 칸막이입니다. vSphere에서 가장 가까운 비유는 vCenter 트리의 폴더나 resource pool입니다: 같은 리소스이지만 범위가 따로, 권한이 따로, 쿼터가 따로입니다.

왜 손으로 만들지 않고 애플리케이션과 함께 Git에 넣는가: 서비스가 언젠가 저장소에서 빠지면, Flux는 namespace도 함께 제거합니다. 반년 뒤에 왜 만들어졌는지 아무도 기억 못 하는 빈 칸막이가 남지 않습니다.

### `passes.yaml` — 서비스 자체

`---` 줄로 구분된 네 개의 객체.

**첫 번째 — nginx 설정이 담긴 `ConfigMap`.** `ConfigMap`은 텍스트 파일을 애플리케이션과 분리해 클러스터에 넣고, 그 파일은 컨테이너 안에 마운트됩니다. 요점은 이미지를 다시 빌드하지 않고 설정을 바꾸는 것입니다.

안에는 평범한 nginx 설정이 있습니다. 한 줄은 눈여겨볼 만합니다:

```
sub_filter '__POD__' '$hostname';
```

이것은 nginx에게 지시합니다: 내보내는 페이지에서 `__POD__`라는 텍스트를, 실행 중인 머신의 이름으로 바꾸라고요. Pod 안에서 머신 이름은 곧 Pod 자신의 이름입니다. 페이지는 그렇게 어느 복제본이 응답했는지 알려줍니다. 나중에 그 이름으로, 복제본이 이제 둘이 됐다는 걸 보게 됩니다.

**두 번째 — 페이지가 담긴 `ConfigMap`.** 지금은 자리표시자입니다: 진짜 애플리케이션은 다음 실습에서 등장하고, 오늘 중요한 것은 서비스가 무엇을 보여주는지가 아니라 클러스터에 **어디서 왔는지**입니다.

**세 번째 — `Deployment`.** 애플리케이션의 기술: 어떤 이미지인지, 복제본이 몇 개인지, 준비 상태를 어떻게 확인하는지.

```yaml
spec:
  replicas: 1
```

복제본을 몇 개 실행 상태로 유지할지. 표현을 눈여겨보세요: 「하나 시작하라」가 아니라 「하나 유지하라」입니다. 이 숫자를 Git으로 바꿔서 무슨 일이 벌어지는지 볼 겁니다.

```yaml
          readinessProbe:
            httpGet:
              path: /healthz
              port: http
```

준비 상태 검사: 클러스터가 이 주소를 두드려 보고, 응답을 받기 전까지는 그 복제본으로 트래픽을 보내지 않습니다. Flux도 이걸 필요로 합니다 — 적용 직후 성공을 보고하는 대신 준비될 때까지 기다리도록 시킬 겁니다.

**네 번째 — `Service`.** 모든 복제본 앞에 서는 고정된 이름. `Service`와 Pod의 연결은 주소 목록이 아니라 `selector: app: passes`라는 조건, 즉 「이 레이블이 붙은 모든 Pod」입니다. 레이블이 붙은 새 복제본이 나타났다 — 그러면 자동으로 로드 밸런싱 대상에 들어갑니다.

네 객체 중 어느 것에도 비밀번호도, 키도, 토큰도 없습니다. 우연이 아닙니다: Git에 들어간 것은 영원히 거기 남습니다 — 이력은 다시 쓸 수 있지만, 미리 clone한 사람은 누구나 옛 복사본을 갖고 있습니다. 비밀 정보는 여기에 있을 자리가 없습니다; 그것을 위한 별도의 메커니즘과 별도의 실습이 있습니다.

</details>

GitHub으로 보냅니다. Git은 무엇이든 무작정 기억하는 게 아니라, 명시적으로 보여준 것만 기억합니다 — 그래서 명령이 세 개이고, 각자 자기 일을 합니다:

```bash
# add = 다음 이력 항목에 들어갈 파일을 표시합니다.
git add apps
# commit = 표시된 것을 하나의 항목으로 저장합니다: 내용, 작성자, 시각, 그리고 이유.
#   -m "..."  바로 그 이유. 이력에 영원히 남고, 사람들이 읽게 됩니다.
# 커밋은 지금은 여러분의 bastion에만 있습니다 — 아직 GitHub에는 없습니다.
git commit -m "add passes service v1"
# push = 쌓인 커밋을 GitHub으로 보냅니다. 이 명령 전까지는 거기서 아무것도 바뀌지 않습니다.
git push
```

**보게 될 것** — 브라우저에서, 저장소 페이지에, 파일 두 개가 든 `apps` 폴더. 그 사이 클러스터에서는 아직 아무것도 바뀌지 않았습니다: Git은 클러스터에 대해 아무것도 모릅니다.

## 단계 3. 클러스터에 Flux 설치하기

📍 **위치:** bastion에서 (bastion 터미널).

Flux는 클러스터 안의 여러 서비스입니다. 하나는 Git으로 들어가 내용을 내려받고, 다른 하나는 내려받은 것을 클러스터에 적용하며 어긋남을 감시합니다.

클러스터는 여러분 것이고, 여러분은 그 클러스터의 완전한 관리자입니다. 직접 설치하면 되고, 플랫폼 팀에 요청할 필요가 없습니다.

먼저 `flux` 명령줄 도구입니다. 이것은 클러스터가 아니라 여러분의 bastion에 있습니다: 이걸로 서비스를 설치하고, 그다음 서비스에게 상태를 물어봅니다.

macOS:

```bash
# Homebrew는 Flux 프로젝트의 저장소에서 formula를 가져와 실행 파일 하나를 놓습니다.
brew install fluxcd/tap/flux
```

Linux:

```bash
# Flux 사이트의 스크립트가 여러분의 아키텍처를 감지해 파일을 /usr/local/bin에 놓습니다.
#   -s          curl이 다운로드 표시 없이 조용히 동작합니다
#   | sudo bash 내려받은 텍스트가 곧바로 관리자 권한으로 실행됩니다 — 시스템 폴더에
#               쓰기 때문에 그 권한이 필요합니다
curl -s https://fluxcd.io/install.sh | sudo bash
```

Windows (PowerShell, Chocolatey가 설치돼 있다면):

```powershell
# choco — Windows용 서드파티 패키지 매니저; 똑같은 flux.exe 파일 하나를 설치합니다.
choco install flux
```

이제 서비스 자체를 클러스터에 설치합니다:

```bash
# 접근 파일을 지정합니다: 아래 명령은 클러스터에 객체를 만드는데, 어느 클러스터인지가 중요합니다.
export KUBECONFIG=~/lab.kubeconfig
# flux install은 클러스터에 `flux-system` namespace를 만들고 그 안에 서비스를 배포합니다.
#   --components=...  정확히 어느 것을 설치할지:
#     source-controller     Git으로 들어가 저장소의 최신 복사본을 유지합니다
#     kustomize-controller  내려받은 것을 클러스터에 적용하고 어긋남을 감시합니다
flux install --components=source-controller,kustomize-controller
```

⚠️ **Enter를 누르기 전에 `KUBECONFIG`가 어디를 가리키는지 확인하세요.** 우리는 Flux를, 여러분에게 클러스터를 넘겨준 그 클러스터가 아니라 여러분 자신의 `lab` 클러스터에 설치합니다. 의심스러우면 — `kubectl get nodes`가 `kubernetes-lab-md0-...` 같은 이름의 노드 하나를 보여줘야 합니다.

**보게 될 것** — 만들어지는 것들의 목록, 그리고 맨 끝에 설치 성공을 알리는 줄:

```
✔ install finished
```

우리는 네 서비스 중 둘만 설치합니다. Flux의 전체 세트는 Helm 차트를 배포하고 메신저로 알림을 보낼 수도 있지만 — 오늘은 그게 필요 없고, 노드는 하나뿐이며 메모리도 많지 않습니다.

서비스가 떴는지 확인하세요:

```bash
# -n flux-system — Flux가 자리 잡은 namespace. 이 플래그가 없으면 kubectl은
# default namespace를 보고 아무것도 보여주지 않습니다.
kubectl get pods -n flux-system
```

**보게 될 것** — `Running` 상태의 두 줄.

<details>
<summary><b><code>flux</code> CLI 설치가 안 됐다면</b></summary>

똑같은 것을 도구 없이 평범한 매니페스트로 설치할 수 있습니다:

```bash
# 같은 서비스 세트를, 다만 완성된 기술로: -f는 디스크의 경로뿐 아니라
# 링크도 받습니다. kubectl이 파일을 내려받아 그 내용을 적용합니다.
kubectl apply -f https://github.com/fluxcd/flux2/releases/latest/download/install.yaml
```

차이: 이렇게 하면 둘 대신 네 서비스가 전부 뜹니다. 메모리에 영향이 있겠지만, 실습은 그래도 진행됩니다. 이후 본문에서 `flux ...` 명령은 상태를 보기 위해서만 필요하며 — `kubectl get gitrepository`와 `kubectl get kustomization`으로 대체할 수 있습니다. 같은 것을 보여주되, 그저 덜 깔끔할 뿐입니다.

</details>

## 단계 4. Flux를 저장소로 향하게 하기

📍 **위치:** bastion에서 (bastion 터미널).

Flux는 설치됐지만, 아직 어디로 가야 할지 모릅니다. 두 개의 객체로 알려줍니다.

이 실습 폴더의 `flux/gitrepository.yaml`을 열고, `교체하세요` 자리표시자 대신 **본인** 저장소의 주소를 넣으세요:

```yaml
  url: https://github.com/교체하세요/passes-gitops
```

<details>
<summary><b>자세히 보기: gitrepository.yaml와 kustomization.yaml 안에 무엇이 있나</b></summary>

### `GitRepository` — 어디서 가져올지

```yaml
kind: GitRepository
spec:
  interval: 1m
  url: https://github.com/교체하세요/passes-gitops
  ref:
    branch: main
```

이 객체의 유일한 임무는 저장소의 최신 복사본을 유지하는 것입니다. 클러스터에 아무것도 적용하지 않고, 내려받기만 합니다.

`interval: 1m` — 얼마나 자주 업데이트를 가지러 갈지. 기다리지 않도록 실습에서는 1분으로 골랐습니다. 실무에서는 보통 1분에서 5분 사이로 두고, push에 대한 즉각적인 반응은 간격을 줄여서가 아니라 웹훅으로 만듭니다: 무언가 바뀌면 GitHub이 직접 클러스터를 두드립니다.

`ref: branch: main` — 어느 브랜치를 진실의 원천으로 삼을지. `main`에 병합된 것은 전부 클러스터로 갑니다. 다른 브랜치에 있는 것은 가지 않습니다. 여기서 리뷰가 생깁니다: 변경은 먼저 자기 브랜치에서 살고, 거기서 살펴볼 수 있으며, `main`으로 병합해야만 효력이 생깁니다.

### `Kustomization` — 무엇을 적용할지

```yaml
kind: Kustomization
spec:
  interval: 1m
  path: ./apps
  prune: true
  sourceRef:
    kind: GitRepository
    name: passes
  wait: true
```

`path: ./apps` — 저장소 안의 폴더. 그 안에 있는 것은 전부 클러스터로 갑니다. 그 옆에 있는 파일 — 예를 들어 루트의 `README.md` — 는 건드리지 않습니다.

여기서 `interval: 1m`은 `GitRepository`에서와 같은 뜻이 아닙니다. 거기서는 「얼마나 자주 내려받을지」였습니다. 여기서는 **클러스터의 실제 상태를 기술된 상태와 얼마나 자주 조정할지**입니다. Git에서 아무것도 바뀌지 않았더라도, 1분에 한 번 Flux는 클러스터가 기술과 맞는지 확인하고 일치시킵니다. 실습을 조금 더 진행하면 바로 이것에 걸리게 됩니다.

`prune: true` — Git에서 사라진 객체를 클러스터에서 삭제합니다. 이것이 없으면 Git은 완전한 기술이기를 멈춥니다: 저장소에서 파일을 삭제해도 객체는 클러스터에서 계속 돌고, 반년 뒤에는 아무도 그게 어디서 왔는지 이해하지 못합니다. `prune`이 있으면 기술과 현실이 양방향으로 일치합니다.

`wait: true` — 적용 직후에 성공을 보고하지 말고, 적용된 것이 준비될 때까지 기다립니다. 그 차이는 「신청서를 냈다」와 「신청이 처리됐다」 사이의 차이와 정확히 같습니다.

</details>

둘 다 적용합니다:

```bash
# -f는 파일이 아니라 폴더를 가리킵니다: 그 안의 모든 매니페스트가 적용됩니다 —
# GitRepository도 Kustomization도. 둘 다 flux-system namespace에 만들어집니다.
kubectl apply -f flux/
```

무엇이 됐는지 봅시다:

```bash
# Flux에게 조정 상태를 물어봅니다.
#   --watch  창을 계속 붙잡아 두고 변화가 생길 때마다 줄을 갱신합니다
# READY: True는 저장소의 내용이 클러스터에 도달해 적용됐다는 뜻입니다.
# REVISION — 브랜치와, 현재 적용된 커밋의 짧은 식별자.
flux get kustomizations --watch
```

**보게 될 것** — 수십 초 뒤, `Ready: True` 상태와 적용된 커밋의 해시:

```
NAME     REVISION            SUSPENDED  READY  MESSAGE
passes   main@sha1:a1b2c3d   False      True   Applied revision: main@sha1:a1b2c3d
```

`Ctrl+C`로 관찰을 멈추고 클러스터에 무엇이 나타났는지 보세요:

```bash
# all — 주요 객체 유형을 한 번에 가리키는 약칭: Pod, Deployment, Service 등.
# `passes` namespace는 손으로 만들지 않았습니다: 애플리케이션과 함께 저장소에서 왔습니다.
kubectl get all -n passes
```

**여러분은 손으로 아무것도 적용하지 않았습니다.** 텍스트를 GitHub에 넣었고, 클러스터가 스스로 그것을 가져왔습니다. 이것과 `kubectl apply -f`의 차이는 편리함이 아니라 — 이제 어떻게 되어야 하는지가 적힌 단 하나의 장소가 있다는 것입니다.

## 단계 5. `git push`를 통한 첫 변경

📍 **위치:** bastion에서, 저장소 폴더.

「출입증」 서비스에는 복제본 하나로는 부족합니다: 경비는 목록을 24시간 지켜보고, 애플리케이션을 업데이트한다고 정문을 멈춰 세워선 안 됩니다. 둘로 설정합시다.

예전이라면 `kubectl scale`을 실행했을 겁니다. 이제는 — 파일 편집입니다.

`apps/passes.yaml`을 열고 바꾸세요:

```yaml
spec:
  replicas: 2
```

보냅니다:

```bash
# 첫 전송 때와 같은 세 단계: 파일 표시, 이유와 함께 저장, 전송.
git add apps/passes.yaml
git commit -m "passes: two replicas so the gate does not go dark during rollout"
git push
```

이제 클러스터를 지켜보며 기다립니다:

```bash
# -w = 「지켜보며 계속 덧붙이기」: 창은 계속 붙잡혀 있고, 복제본의 상태가
# 바뀔 때마다 새 줄이 나타납니다. 나가려면 Ctrl+C.
kubectl get pods -n passes -w
```

**보게 될 것** — 1분 안에 두 번째 복제본이 나타납니다. 여러분이 만든 게 아닙니다.

1분을 기다리기 싫다면 — Flux에게 지금 바로 조정하라고 요청할 수 있습니다:

```bash
# reconcile = 「다음 1분을 기다리지 말고 지금 바로 조정하라.」
#   kustomization passes  어느 객체를 조정할지
#   --with-source         먼저 Git으로 가서 최신 커밋을 가져오고 그다음에야 적용합니다;
#                         이 플래그가 없으면 조정은 앞서 내려받은 복사본을 기준으로 진행됩니다
flux reconcile kustomization passes --with-source
```

커밋 메시지를 눈여겨보세요. `two replicas so the gate does not go dark during rollout` — 이게 이유입니다. 반년 뒤, 누군가 「왜 여기 하나가 아니라 둘이지」라고 물으면, 답을 5초 만에 찾습니다:

```bash
# log = 커밋 이력, 최신이 맨 위.
#   --oneline         커밋당 한 줄: 짧은 식별자와 이유 텍스트
#   apps/passes.yaml  바로 이 파일을 건드린 커밋만 보여줍니다
git log --oneline apps/passes.yaml
```

대시보드도 `kubectl`도 이런 흔적을 남기지 않습니다.

## 단계 6. 모든 게 통제되고 있는지 확인해 봅시다

📍 **위치:** bastion에서 (bastion 터미널).

밤, 장애, 서비스에 복제본이 모자랍니다. 여러분은 늘 하던 대로 합니다:

```bash
# Git을 건너뛰고 클러스터에서 곧바로 복제본 수를 바꿉니다 — 오늘까지 하던 대로.
#   -n passes  애플리케이션은 이 namespace에 있습니다; 플래그가 없으면 명령이 찾지 못합니다
kubectl scale deployment passes -n passes --replicas=5
```

```
deployment.apps/passes scaled
```

됐습니다. 확인해 봅시다:

```bash
# READY 열은 「준비됨/주문됨」으로 읽힙니다: 몇 개의 복제본이 응답하고, 몇 개여야 하는지.
kubectl get deployment passes -n passes
```

복제본 다섯. 1분 기다렸다가 다시 보세요:

```bash
# 같은 명령. 유일한 차이는 두 번의 실행 사이에 1분이 지났다는 것뿐입니다.
kubectl get deployment passes -n passes
```

**보게 될 것:**

```
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
passes   2/2     2            2           8m
```

다시 복제본 둘. 여러분의 명령은 실행됐다가 되돌려졌습니다.

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 누가 되돌렸을까요? 왜 여러분의 명령에 오류 하나 없이 조용히 일어났을까요?
> 그리고 무엇보다: 이것은 고쳐야 할 고장일까요, 아니면 의도대로 동작하는 것일까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

Flux가 되돌렸고, 그것이 바로 Flux를 설치한 이유입니다.

1분에 한 번 `Kustomization`은 Git에 있는 것을 가져와 클러스터에 있는 것과 비교합니다. Git은 `replicas: 2`라고 합니다. 클러스터에는 `5`가 있었습니다. 어긋남 — 이는 클러스터가 틀렸다는 뜻입니다. 진실의 원천은 클러스터가 아니니까요.

**왜 `kubectl scale`이 오류를 반환하지 않았나.** 그럴 수 없었습니다: 요청받은 것을 정직하게 정확히 해냈으니까요. Kubernetes는 변경을 받아들였고, 복제본은 실제로 떴습니다. 1분 뒤 조정이 와서 기술된 상태를 복원했습니다. 아무도 누구와 다투지 않았습니다 — 서로 다른 메커니즘이 각자 자기 규칙대로 동작했을 뿐입니다.

**왜 이것이 버그가 아니라 기능인가.** 실습을 시작할 때의 고통으로 돌아가 봅시다: 여러분은 셋이고, 누군가 손으로 무언가를 바꿨으며, 무엇이 어디에 설정됐는지 아무도 모릅니다. 이제 그런 일은 일어나지 않습니다. Git을 벗어나 이뤄진 변경은 다음 조정까지만 삽니다 — 즉, 살지 못합니다. 여기서 세 가지가 따라 나옵니다:

1. **클러스터를 조용히 잘못 설정할 수 없습니다.** 「눈총받는다」가 아니라 물리적으로 불가능합니다.
2. **Git은 언제나 현실을 기술합니다.** 「기술해야 한다」가 아니라 — 실제로 기술합니다. 어긋남이 스스로 사라지니까요.
3. **클러스터 복원이 지루한 절차가 됩니다.** Flux를 설치하고, 저장소를 주고, 기다립니다. 있던 것이 전부 돌아옵니다. 전부 적혀 있으니까요.

**교훈은 이 오류보다 넓습니다.** 여러분은 방금 「적용하고 잊기」와 「끊임없이 조정하기」의 차이를 봤습니다. 평범한 `kubectl apply`는 한 발의 발사입니다: 상태가 바뀌고 나면 스스로 살아가고, 누구든 그것을 밀어 옮길 수 있습니다. 조정은 발사가 아니라 끌어당김입니다: 기술이 끊임없이 현실을 자기 쪽으로 끌어당깁니다.

그 똑같은 메커니즘은, 덧붙이자면, 여러분의 오류가 아닌 것도 고칩니다. 노드 장애가 Pod를 삭제하거나 누군가 실수로 `Service`를 지워도 — 그것도 돌아옵니다.

**언제 방해가 되나.** 장애가 났을 때, 정말로 무언가를 즉시 바꿔야 하고 논의할 시간이 없을 때 방해가 됩니다. 그런 경우를 위해 Flux는 일시 정지할 수 있습니다:

```bash
# suspend = 이 객체에 대한 조정을 일시 정지합니다. Flux는 클러스터를 기술에
# 맞추기를 멈추고, 손으로 한 변경이 살아남기 시작합니다. 그동안 Git의 내용은 바뀌지 않습니다.
flux suspend kustomization passes
```

이 뒤로 조정은 돌지 않고, 손으로 무엇이든 할 수 있습니다. 되돌리려면:

```bash
# resume = 조정을 다시 켭니다. 바로 다음 조정이 손으로 한 것을 전부 제거합니다.
flux resume kustomization passes
```

⚠️ 일시 정지는 미뤄둔 빚입니다: `Kustomization`이 멈춰 있는 동안 Git은 다시 현실을 기술하기를 멈추고, 여러분은 출발했던 바로 그 자리로 돌아갑니다. 규칙은 하나입니다: 멈췄으면 — 다시 켜라는 알림을 스스로에게 걸어 두세요.

</details>

## 단계 7. `git revert`를 통한 롤백

📍 **위치:** bastion에서 (bastion 터미널).

이제 진짜 상황입니다. 변경을 롤아웃했는데, 그게 나쁜 것으로 드러납니다.

편집을 하나 합시다: 누군가 생각 없이 메모리를 동작 불가능한 값까지 쥐어짠다고 해봅시다. `apps/passes.yaml`에서 메모리 리밋을 바꾸세요:

```yaml
          resources:
            requests:
              cpu: 20m
              memory: 4Mi
            limits:
              cpu: 300m
              memory: 4Mi
```

보냅니다. 뻔히 나쁜 변경도 좋은 변경과 같은 길을 갑니다: 지금은 여러분의 `push`와 클러스터 사이에 아무 검사도 없습니다 — 그리고 그게 이 단계의 요점입니다.

```bash
# 같은 add, commit, push. 커밋의 이유는 정직하게 적습니다 — 5분 뒤,
# 변경을 되돌려야 할 때 쓸모가 있습니다.
git add apps/passes.yaml
git commit -m "passes: trim memory limit"
git push
```

기다리며 지켜봅니다:

```bash
# 조정이 새 기술을 가져올 때까지 복제본을 지켜봅니다.
kubectl get pods -n passes -w
```

**보게 될 것** — 새 복제본이 뜨지 않습니다. `OOMKilled` 상태는 프로세스가 메모리 리밋을 초과해 종료됐다는 뜻이고, `CrashLoopBackOff`는 클러스터가 이미 그 복제본을 연달아 여러 번 재시작했으며 이제 다음 시도까지 점점 더 오래 기다린다는 뜻입니다. Nginx는 4메가바이트에 들어가지 못하고 시작하자마자 죽습니다.

```bash
# 같은 목록이지만, 지켜보지 않고 한 번의 스냅샷으로.
kubectl get pods -n passes
```

```
NAME                      READY   STATUS             RESTARTS   AGE
passes-6c9d4f7b8-2xk4n    1/1     Running            0          12m
passes-7f8a1b2c3-qq7lp    0/1     CrashLoopBackOff   3          90s
```

옛 복제본은 아직 돌고 있습니다 — 서비스는 살아 있지만, 업데이트는 멈춰 섰습니다. 롤백할 때입니다.

**예전이라면 이렇게 롤백했을 겁니다:**

```bash
# undo는 Deployment를 이전 리비전으로 — 편집 이전의 설정으로 되돌립니다.
kubectl rollout undo deployment/passes -n passes
```

이 명령은 동작합니다. 복제본은 이전 이미지와 이전 설정으로 돌아가고, 20초 안에 모든 게 괜찮아집니다 — 정확히 Flux가 Git과 조정하는 순간까지는요. 그런데 Git에는 여전히 `memory: 4Mi`가 적혀 있습니다. 1분 안에 망가진 상태가 돌아옵니다.

**`rollout undo`를 하지 마세요. 진실이 사는 곳에서 롤백하세요** — Git에서:

```bash
# revert = 지정한 커밋의 변경을 되돌리는 새 커밋을 추가합니다.
#   HEAD       「현재 브랜치의 마지막 커밋」 — 바로 나쁜 리밋이 든 그 커밋
#   --no-edit  커밋 메시지용 편집기를 열지 않습니다; Git이 제목을 스스로 씁니다
git revert --no-edit HEAD
# 되돌리는 커밋이 GitHub으로 보내지기 전까지, Flux는 그것에 대해 아무것도 모릅니다.
git push
```

**보게 될 것** — `Revert "passes: trim memory limit"` 제목의 새 커밋, 그리고 1분 안에 클러스터에 다시 동작하는 복제본 둘.

```bash
# 복제본이 다시 뜹니다: 동작하는 메모리 리밋이 돌아왔습니다.
kubectl get pods -n passes
# 그리고 여기서 지금 어느 커밋이 적용됐는지 볼 수 있습니다 — 되돌리는 커밋과 일치해야 합니다.
flux get kustomizations
```

<details>
<summary><b><code>git revert</code>가 「원래대로 되돌리기」와 어떻게 다른가</b></summary>

`git revert`는 나쁜 커밋을 지우지 않습니다. 나쁜 커밋의 변경을 되돌리는 **새** 커밋을 추가합니다. 이력에는 전부 남습니다: 무엇이 망가졌는지, 언제 알아챘는지, 무엇을 롤백했는지.

```bash
# -4 — 가장 최근 커밋 네 개를 보여줍니다; 맨 위가 가장 최신입니다.
git log --oneline -4
```

```
9f3c1ab Revert "passes: trim memory limit"
5d2b8e0 passes: trim memory limit
c71a4f9 passes: two replicas so the gate does not go dark during rollout
0e5f2d3 add passes service v1
```

이것을 Git이 없을 때의 모습과 비교해 보세요. 한 달 뒤 「잠깐, 우리 이미 이 지뢰를 밟은 적 있지 않나?」라는 질문에는 답이 없습니다: `kubectl rollout undo`는 흔적을 남기지 않고, `Deployment`의 리비전 이력은 마지막 열 개만 보관하다가 객체와 함께 죽습니다.

여기 여러분에게는 네 줄이 있고, 거기서 볼 수 있습니다: 그래, 밟았다, 언제인지, 누구인지, 정확히 무엇을 했는지, 롤백까지 얼마나 살아 있었는지.

**두 번째 명령도 있습니다 — `git reset`, 이것은 정말로 이력을 지웁니다.** 공유 저장소에서는 쓰지 않습니다: 여러분 컴퓨터에서 지운 커밋은 동료 두 명의 컴퓨터에 여전히 있고, 그들의 다음 `push`가 그것을 되돌려 놓습니다. 공유 브랜치에서 되돌리기는 언제나 `revert`입니다.

</details>

## 단계 8. pull request를 통한 리뷰

📍 **위치:** 브라우저, GitHub.

우리가 고치는 고통의 마지막 부분입니다: 변경이 곧바로 클러스터로 갔고, 아무도 그것을 보지 않았습니다. 앞 단계의 나쁜 메모리 리밋은 리뷰에서 10초 만에 걸렸을 겁니다 — 그런데 리뷰가 없었습니다.

변경을 위한 브랜치를 만드세요:

```bash
# checkout -b = 새 브랜치를 만들고 곧바로 그리로 전환합니다. 브랜치는 변경의 별도 갈래입니다:
# 거기서 만든 커밋은 `main`에 닿지 않고, 따라서 클러스터에도 닿지 않습니다.
#   passes/version-line  브랜치 이름; 이름의 슬래시는 허용되며 그룹화에 쓰입니다
git checkout -b passes/version-line
```

`apps/passes.yaml`에서 페이지의 한 줄을 바꾸세요 — 예를 들어 텍스트의 버전을 `v1`에서 `v1.1`로. 브랜치를 보냅니다:

```bash
git add apps/passes.yaml
git commit -m "passes: bump the version shown on the page"
# origin — Git이 여러분이 저장소를 clone해 온 주소를 기억하는 이름.
#   -u origin passes/version-line  GitHub에 같은 이름의 브랜치를 만들고 그 연결을
#                                  기억해서, 이후로는 맨 `git push`만으로 충분하게 합니다
git push -u origin passes/version-line
```

이에 대한 응답으로 GitHub은 pull request를 만드는 링크를 출력합니다. 그걸 여세요.

**「Files changed」 탭을 보세요.** 이것이 바로 인프라 리뷰입니다: 「철수가 리밋을 고쳤다고 말한다」가 아니라, 구체적인 줄들 — 전과 후가 강조 표시된 채로. 동료는 클러스터로 갈 것을 정확히 보고, 특정 줄에 코멘트를 남길 수 있습니다.

그동안 클러스터는 바뀌지 않았고, 앞으로도 바뀌지 않습니다: `GitRepository`는 `main` 브랜치를 보고, 변경은 다른 브랜치에 살고 있으니까요.

**Merge pull request**를 누르세요 — 변경이 `main`에 안착하고, 다음 조정이 그것을 클러스터로 가져옵니다. 1분 뒤 터널을 열어 서비스가 무엇을 내보내는지 봅니다:

```bash
# port-forward = bastion에서 클러스터 안으로 이어지는 임시 터널.
#   -n passes     서비스가 사는 namespace
#   svc/passes    어디로 이끄는지: 특정 복제본이 아니라 Service로
#   8080:80       왼쪽은 bastion의 포트, 오른쪽은 클러스터 안 서비스의 포트
kubectl port-forward -n passes svc/passes 8080:80
```

📍 **브라우저에서** <http://localhost:8080> — 페이지에 `v1.1`. 터널은 `Ctrl+C`로 닫습니다.

이제 변경의 전체 경로는 이렇습니다: **브랜치 → pull request → 리뷰 → merge → 클러스터**. 어느 단계에서도 아무도 손으로 클러스터에 들어가지 않았습니다.

<details>
<summary><b>이 중에서 우리가 하지 않았지만 실무에서는 하는 것</b></summary>

실제 운영 저장소가 그 위에 더하는 세 가지:

**브랜치 보호.** GitHub 설정에서 `main` 브랜치는 직접 push가 막혀 있고, 들어가는 유일한 길은 승인이 붙은 pull request입니다. 그러지 않으면 규율이 선의에 기대게 되는데, 선의는 새벽 3시에 무너집니다.

**병합 전 검사.** 자동화가 매니페스트를 클러스터로 보내기 전에 문법과 정책 준수를 검사하고, 망가진 것은 병합되지 못하게 합니다.

**여러 환경.** 보통 저장소에는 폴더가 하나가 아니라 `apps/staging`와 `apps/production`가 있고, 각각 자기 클러스터에 자기 `Kustomization`을 둡니다. 변경은 먼저 staging으로 가서 자리를 잡고, 그다음 production으로 갑니다.

우리가 이걸 하지 않은 것은 각 항목이 저마다 한 시간짜리 일이고, 그것들 때문에 기본 원리가 바뀌지는 않기 때문입니다: 진실의 원천은 여전히 Git이고, Flux는 여전히 클러스터를 그쪽으로 끌어당깁니다.

</details>

## 검증

📍 **위치:** bastion에서, `kubectl`로 작업하던 바로 그 터미널 창.

```bash
# 실습 폴더로 돌아갑니다: 스크립트는 거기 있고, 여러분은 본인 저장소 폴더에서 작업하고 있었습니다.
cd labs/05-gitops
export KUBECONFIG=~/lab.kubeconfig
# 스크립트는 클러스터에서 아무것도 바꾸지 않습니다: 상태를 읽어 보고서를 출력할 뿐입니다.
./check.sh
```

⚠️ **Windows에서 스크립트는 PowerShell이 아니라 WSL에서 실행합니다** — 설치 방법은 실습 0 시작 부분에 적혀 있습니다. WSL 없이도 실습은 마칠 수 있지만, 보고서 아티팩트는 남지 않습니다.

스크립트는 Flux가 설치됐다는 사실이 아니라 메커니즘이 동작한다는 것을 확인합니다: Flux 서비스가 살아 있는지, 소스가 여러분 저장소를 가리키며 거기서 성공적으로 읽는지, 클러스터의 객체가 (손으로 적용된 게 아니라) 정말로 Flux에 속하는지, 서비스가 HTTP로 응답하는지, 그리고 조정이 일시 정지되지 않았는지.

스크립트가 여러분 저장소의 이력까지 보게 하고 싶다면 — clone이 어디 있는지 알려주세요:

```bash
# LAB_REPO — 스크립트가 여러분 저장소의 clone이 어디 있는지 알아내는 변수.
# 홈 폴더가 아닌 다른 곳에 clone했다면 본인 경로를 넣으세요.
export LAB_REPO=~/passes-gitops
./check.sh
```

그러면 클러스터에 적용된 커밋이 여러분 브랜치의 최신 커밋과 일치하는지, 그리고 롤백이 `revert`를 통해 이뤄졌는지도 추가로 확인합니다.

## 정리

우리는 아무것도 삭제하지 않습니다: 저장소와 Flux는 나중에 필요합니다 — 다음 서비스들도 같은 방식으로 클러스터에 도착합니다.

모든 실습을 끝냈다면, 이렇게 전부를 한 번에 제거할 수 있습니다:

```bash
# delete kustomization = 조정 객체를 클러스터에서 제거합니다.
#   --silent  확인을 다시 묻지 않습니다
flux delete kustomization passes --silent
```

`prune: true` 덕분에, `Kustomization`이 가져온 모든 것이 그것과 함께 떠납니다: 애플리케이션, 설정, 그리고 `passes` namespace 자체까지. 손으로 하나하나 나열할 필요도 없고 아무도 남은 것을 잊지 않습니다 — 무엇이 만들어졌는지 목록을 Flux가 스스로 보관하니까요.

이것은, 덧붙이자면, 곧바로 눈에 띄지는 않는 GitOps의 또 다른 이점입니다. 서비스를 완전히 삭제하는 것은 폴더를 `git rm`하고 `push`하는 것입니다.

## 이제 우리가 할 수 있는 것

- 클러스터의 상태를 Git에 보관하고, 그것이 `kubectl apply`와 어떻게 다른지 이해하기
- 우리 클러스터에 Flux를 설치하고 저장소로 향하게 하기
- 조정이 무엇인지, 그리고 왜 Git을 벗어난 변경은 살아남지 못하는지 설명하기
- `kubectl rollout undo`가 아니라 `git revert`를 통해 롤백하기
- 인프라 변경을 pull request와 리뷰를 거쳐 진행하기

## 그리고 vSphere에서라면 이것은

가장 가까운 비유는 vRealize Automation의 blueprint입니다: 원하는 구성을 따로 기술하고 그 기술로부터 배포합니다. 하지만 거기서부터 길이 갈립니다. blueprint는 배포하고 손을 놓습니다; 이후 누군가 vCenter에 들어가 머신의 메모리를 바꿔도, blueprint는 그것을 알지 못합니다. 준수 도구가 그 어긋남을 보고서에 보여주고 — 그게 끝, 사람이 그것을 해결하러 갑니다.

여기서는 어긋남이 스스로, 매분, 보고서도 사람도 없이 해결됩니다.

두 번째 차이는 이력에 관한 것입니다. vCenter에는 작업 로그가 있습니다: 누가 언제 무엇을 했는지. 그것은 「무슨 일이 일어났나」라는 질문에는 답하지만, 「왜」와 「어떠해야 하는가」에는 답하지 못합니다. Git에는 둘 다 있습니다: 변경의 텍스트, 작성자, 커밋 메시지 속 이유, 그리고 pull request 속 논의.

**솔직히, vSphere가 더 편한 지점.** 세 가지.

**진입 장벽.** vCenter에서 가상 머신의 메모리를 바꾸려면 vCenter를 쓸 줄 알아야 합니다. 여기서 그것을 바꾸려면 Git을 쓸 줄 알아야 합니다: 브랜치, 커밋, 병합, 충돌. Git을 모르는 사람에게 이것은 「더 편함」이 아니라 — 새로운 직업이고, 처음 2주 동안은 예전보다 더 느리게 일하게 됩니다.

**반응 속도.** 긴급 상황에서는 브랜치와 리뷰와 1분의 조정을 거쳐서가 아니라 지금 당장 상태를 바꾸고 싶습니다. 일시 정지 메커니즘이 있지만, 그것을 쓰는 걸 잊지 말아야 하고 끄는 것도 잊지 말아야 합니다.

**실패의 명확함.** vCenter에서 무언가 배포되지 않으면, 오류가 붙은 작업을 보여줍니다. 여기서 배포되지 않으면, `GitRepository`의 상태를, 그다음 `Kustomization`을, 그다음 이벤트를, 그다음 두 서비스의 로그를 봐야 합니다. 진단이 여러 계층에 흩어져 있고, 익숙해지기 전까지는 솔직히 불편합니다.
