# 랩 11 · 클러스터에서 모바일 앱 빌드하기

| | |
|---|---|
| **시간** | 40분, 그중 최대 15분은 첫 빌드를 기다리는 데 씁니다 |
| **무엇을 증명하는가** | 빌드 서버는 서버가 아니라, 빌드가 진행되는 동안 노드를 점유했다가 반납하는 작업입니다 |
| **필요한 것** | 랩 0에서 만든 클러스터, `kubectl`, `~/lab.kubeconfig`, 테넌트 대시보드 접근 권한 |

## 왜 중요한가

모바일 팀은 Propusk의 클라이언트를 개발하고 있습니다. 직원이 게스트 출입증을
신청하는 바로 그 화면입니다. 지금은 개발자 한 명의 VM에서 빌드합니다. 그가 휴가를 가면
릴리스가 나오지 않습니다.

그들에게는 전용 빌드 서버가 없고, 앞으로도 없을 것입니다. Android SDK용 전용 머신을
요청했지만 두 번이나 거절당했습니다 — "부하가 고르지 않아 머신이 놀게 된다"는 이유였습니다.
솔직히 맞는 말입니다. 빌드는 하루에 20분 돌아가는데, 그 빌드에 필요한 머신은 4코어에
16기가바이트짜리입니다.

여기서 우리는 요구받은 그대로 합니다. 그 4개의 코어를 **20분 동안** 빌려 APK를 빌드하고
반납합니다. 그리고 완성된 파일은 전화기를 든 테스터까지 포함해서 누구든 가져갈 수 있는
곳에 둡니다 — 바로 버킷입니다.

모든 랩을 통틀어 워크로드가 **끝나는** 것은 이번이 처음입니다. 지금까지 배포한 모든 것은
영원히 돌아가도록 설계된 것이었습니다.

## 미니 용어집

| 용어 | 무엇인가 | ~와 비슷하지만 |
|---|---|---|
| **Job** | 작업: 무언가를 실행하고 성공적으로 끝날 때까지 기다림 | **게스트 OS의 예약 작업**과 비슷하지만, job은 실행할 머신을 스스로 만들고 스스로 치웁니다 |
| **Deployment** | 영원히 돌아가는 애플리케이션에 대한 설명 | **vApp**과 비슷하지만 결코 "성공적으로 끝나지" 않습니다 — 사라진 복제본은 다시 생성됩니다 |
| **객체 저장소** | 파일도 디렉터리도 없는 저장소 — 키와 그 내용만 있음 | **데이터스토어**와 비슷하지만 마운트되지 않습니다. 객체를 통째로 넣고 가져오며, HTTP로 합니다 |
| **버킷** | 객체 저장소 안의 이름이 붙은 영역 | **데이터스토어의 폴더**와 비슷하지만 중첩되지 않습니다: 버킷은 최상위 레벨이고, 그 안의 "폴더"는 객체 이름의 일부입니다 |
| **S3** | HTTP로 객체 저장소에 접근하는 프로토콜 | 직접적인 비유는 없습니다; NFS보다는 REST API에 가깝습니다 |
| **액세스 키** | 로그인과 비밀번호 대신 "access key / secret key" 쌍 | **서비스 계정**과 비슷하지만, 키는 사람이 아니라 버킷 단위로 발급됩니다 |
| **Secret** | 비밀번호와 키를 넣어 두는 클러스터 객체 | **자격 증명 저장소(credential store)의 항목**과 비슷하지만, 클러스터 안에서는 암호화가 아니라 base64입니다. 눈에서 감출 뿐, 관리자로부터 감추지는 못합니다 |
| **emptyDir** | Pod가 사는 딱 그만큼만 존재하는 임시 디스크 | **임시 vmdk**와 비슷하지만, Pod와 함께 사라지며 복구할 방법이 없습니다 |

### Job 대 Deployment — 표 하나로

이것이 이 랩의 핵심 구분이며, 무언가를 적용하기 전에 확실히 짚고 넘어갈 가치가 있습니다.

아래 두 행 모두에 **Pod**라는 단어가 등장합니다. Pod는 클러스터에서 가장 작은 실행
단위입니다: 특정 노드 위에 올라온 컨테이너(또는 여러 개)입니다. 가장 가까운 비유는 단일
작업 전용의 가상 머신이지만, 몇 초 만에 생성되고 노드보다 오래 살지 못한다는 점이
다릅니다. Job도 Deployment도 스스로 무언가를 실행하지는 않습니다: 이들은 Pod를 생성하고,
Pod가 사라졌을 때 무엇을 할지 결정합니다.

| | Deployment | Job |
|---|---|---|
| 무엇이 "다 잘됨"을 의미하는가 | 복제본이 지금 이 순간 돌아가고 있음 | 프로세스가 코드 0으로 종료됨 |
| Pod가 성공적으로 끝남 | 클러스터는 이를 실패로 간주하고 새 것을 생성 | 클러스터는 일이 끝났다고 간주 |
| 얼마나 오래 사는가 | 삭제할 때까지 | 완료될 때까지 |
| 몇 번 실행되는가 | 전혀 — "실행"되는 게 아니라 그냥 돌아감 | 한 번(또는 지정한 횟수만큼) |
| 끝난 뒤 무엇이 남는가 | 돌아가는 애플리케이션 | 작업 결과와 로그 |

여기서 모두가 걸려 넘어지는 실질적인 결과가 나옵니다: **빌드를 Deployment로 실행하면,
클러스터는 그것을 계속 반복해서 실행합니다**. 빌드가 성공적으로 끝났으니 — 복제본이
사라졌고 — 그러니 새 것을 만들어야 합니다. 무한 루프이며, 클러스터 탓이 아닙니다: 그렇게
하라고 시킨 것입니다.

## 랩 폴더에 무엇이 있는가

모든 파일은 이미 여러분의 것입니다 — 저장소와 함께 받았습니다. 새로 만들거나 다시
타이핑할 것은 없습니다: 아래에서 `kubectl apply -f name.yaml`이라고 나오는 곳마다, 그
파일은 여기서 가져옵니다.

```bash
cd labs/11-android
```

| 파일 | 무엇인가 | 언제 필요한가 |
|---|---|---|
| `bucket.yaml` | 빌드된 APK를 담을 저장소 | **테넌트에서** 적용합니다 |
| `propusk-src.yaml` | Propusk 모바일 앱의 소스 코드 | 여러분의 `lab` 클러스터에서 적용합니다 |
| `android-build.yaml` | 빌드 자체. 스크립트는 job에 인라인으로 넣지 않고 ConfigMap으로 빼냈습니다 | 역시 거기서 적용합니다 |
| `check.sh` | 빌드가 성공했고 APK가 저장소에 안착했는지 확인 | 랩 마지막에 실행합니다 |

## 1단계. 버킷 만들기

📍 **위치:** 브라우저에서, 테넌트 대시보드에서.

**테넌트**는 플랫폼에서 여러분의 몫입니다: 대시보드에서 보이고 여러분이 관리하는
부분입니다. 랩 0의 `lab` 클러스터도 그 안에서 주문했고, 버킷도 거기서 주문하게 됩니다.

버킷은 **관리형 서비스**입니다 — 카탈로그에 준비된 항목이지요: 여러분이 필요한 것을
말하면, 플랫폼이 그것을 띄우고, 업데이트하고, 고칩니다. 버킷은 **`lab` 클러스터 안이
아니라** 그 옆, 테넌트에 있습니다. 그리고 그래야 마땅합니다: 빌드 아티팩트는 그것이 빌드된
클러스터보다 오래 살아남기 때문입니다.

이 bastion(공유 VM)의 테넌트 접근 파일은 이미 설정되어 있습니다 — `~/.kube/config`이며,
모든 랩과 같은 경로입니다(토큰 기반 접근이라 브라우저가 열리지 않습니다).

테넌트 → **Create application** → `Bucket`.

| 필드 | 값 | 이유 |
|---|---|---|
| Name | `builds` | 짧고 안에 무엇이 있는지 분명함 |
| Users | 사용자 `ci` 추가 | 이 키로 빌드가 씁니다 |
| Locking | 끔 | 객체 삭제 방지; 빌드에는 과함 |
| Storage pool | 비워 둠 | 기본 풀로 충분함 |

원한다면 **같은 버킷을 텍스트로**. 참고: 여기서 `namespace`(클러스터 안의 칸막이; 여러분의
테넌트는 별도의 namespace입니다)는 테넌트의 것이고, `lab` 클러스터가 아니라 테넌트 접근
파일이 필요합니다.

```bash
# KUBECONFIG — kubectl이 어떤 접근 파일을 쓰는지. 여기서는 테넌트의 것입니다: 버킷은
# lab 클러스터가 아니라 관리 클러스터에서 주문됩니다
export KUBECONFIG=~/.kube/config

# apply = "클러스터를 파일에 기술된 상태로 만들어라". 이 명령은 저장소를 직접 만들지
# 않습니다 — 주문을 플랫폼에 넘길 뿐입니다.
#   -f bucket.yaml   어떤 파일을 적용할지. 그 전에 파일 안의
#                    tenant-workshopXX를 여러분의 namespace로 바꾸세요. 안 그러면 주문이 엉뚱한 곳으로 갑니다
kubectl apply -f bucket.yaml
```

**보여야 할 결과** — `bucket.apps.cozystack.io/builds created`.

<details>
<summary><b>자세히 보기: bucket.yaml 안에 무엇이 있는가</b></summary>

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: Bucket
```

`apps.cozystack.io`는 플랫폼의 관리형 서비스가 사는 API 그룹입니다. 가상 머신,
데이터베이스, 큐도 같은 접두사를 갖게 됩니다. 이것은 "Kubernetes 위의 애드온"이 아닙니다 —
플랫폼이 기술한 평범한 Kubernetes 객체입니다.

```yaml
spec:
  users:
    ci: {}
```

사용자 맵입니다. 각 키는 별도의 S3 사용자이고, 각각에 대해 플랫폼은 **고유한** 액세스 키
쌍을 발급합니다. 빈 객체 `{}`는 전체 접근을 뜻합니다.

하나의 버킷에 여러 사용자를 두는 이유: 빌드에는 쓰기 권한이 필요하고, 모바일 팀과
테스터에게는 읽기 전용만 필요합니다. 서로 다른 키, 서로 다른 권한, 각각 따로 회수됩니다:

```yaml
  users:
    ci: {}
    mobile:
      readonly: true
```

랩 시간을 아끼려고 하나로 해결하겠지만, 알아 둘 가치가 있습니다.

</details>

버킷 프로비저닝에는 몇 초가 걸립니다. 대시보드에서 준비됨으로 표시될 때까지 기다리세요.

## 2단계. 키 가져오기

📍 **위치:** 대시보드에서, 버킷 카드의 **Secrets** 탭.

Secret `bucket-builds-ci-credentials`를 찾으세요. 네 개의 값을 담고 있습니다:

| 필드 | 무엇인가 |
|---|---|
| `endpoint` | 저장소 주소, `https://` **없이** — 접두사는 직접 붙여야 합니다 |
| `bucketName` | 실제 버킷 이름: 길고, 식별자가 붙어 있으며, `builds`가 아님 |
| `accessKey` | "로그인" |
| `secretKey` | "비밀번호" |

⚠️ **`bucketName`은 여러분이 입력한 이름이 아닙니다.** `builds`라는 이름은 Cozystack
객체의 이름입니다. 저장소에서의 실제 버킷 이름은 플랫폼이 직접 발급하며, `bucket-a9209f83-...`
처럼 생겼습니다. 바로 이것을 대입해야 하며, 그러지 않으면 존재하지 않는 버킷에 대한 접근
거부를 받고 오타를 찾느라 10분을 허비하게 됩니다.

이 네 값은 커맨드라인으로도 얻을 수 있습니다 — 플랫폼은 여러분이 만든 모든 애플리케이션의
자격 증명에 대한 접근 권한을 부여합니다. 아래 명령은 네 값 중 하나인 `accessKey`를
추출합니다; 나머지도 같은 방식으로 가져오며, 필드 이름만 바뀝니다.

```bash
# 이전 단계와 같은 테넌트 접근으로 작업합니다: 시크릿은 테넌트에 있습니다.
# get secret = "비밀번호와 키가 든 객체를 보여줘". 시크릿 안의 값은
# base64로 인코딩되어 있습니다 — 이것은 암호화가 아니라 이진 데이터를 텍스트로 쓰는 방식일 뿐입니다.
#   -n tenant-workshopXX   어떤 namespace에서 찾을지
#   -o jsonpath='...'      객체 전체가 아니라 그중 필드 하나만 반환:
#                          .data.accessKey — data 섹션 안의 accessKey 필드
#   base64 -d              읽을 수 있는 형태로 다시 디코딩(d = decode)
#   ; echo                 줄바꿈 추가: 없으면 값이
#                          다음 터미널 프롬프트에 붙어 버립니다
kubectl -n tenant-workshopXX get secret bucket-builds-ci-credentials \
  -o jsonpath='{.data.accessKey}' | base64 -d; echo
```

다만 테넌트가 모든 시크릿을 통째로 읽는 것은 허용되지 않습니다: `kubectl auth can-i get
secrets`는 `no`라고 답합니다. 권한은 특정 이름에 한정해 좁게 부여됩니다 — 랩 0에서 만든
여러분 클러스터의 kubeconfig에도 마찬가지입니다.

## 3단계. 키를 자신의 클러스터에 넣기

빌드는 `lab` 클러스터에서 돌아가지만, 키는 테넌트에 있습니다. 클러스터가 서로 다르니
자동으로 넘어가는 것은 없습니다. 직접 옮기겠습니다.

📍 **위치:** bastion에서(bastion 터미널에서).

이전 단계의 네 값으로 `lab` 클러스터에 우리만의 Secret을 만들겠습니다. 필드 이름은 바꾸지
마세요: 빌드 스크립트는 정확히 이 이름의 변수를 찾습니다.

```bash
# 여기서부터 랩 끝까지는 테넌트가 아니라 lab 클러스터로 작업합니다
export KUBECONFIG=~/lab.kubeconfig

# create secret generic = "지금 나열할 값들로 시크릿을 만들어라".
# generic은 이미지 레지스트리 비밀번호나 TLS 인증서용으로 준비된 타입이 아니라
# "임의의 이름-값 쌍의 집합"을 뜻합니다.
#   bucket-creds        시크릿의 이름. Job이 이 이름으로 참조합니다
#   --from-literal=name='value'   한 쌍. ВСТАВЬТЕ_... 자리에는
#                       대시보드의 버킷 카드에 있는 값을 대입하세요
kubectl create secret generic bucket-creds \
  --from-literal=endpoint='ВСТАВЬТЕ_endpoint' \
  --from-literal=bucketName='ВСТАВЬТЕ_bucketName' \
  --from-literal=accessKey='ВСТАВЬТЕ_accessKey' \
  --from-literal=secretKey='ВСТАВЬТЕ_secretKey'
```

**보여야 할 결과:**

```
secret/bucket-creds created
```

⚠️ **작은따옴표를 쓰세요.** 시크릿 키에는 `$`, `!`, `&`가 흔히 들어갑니다. 큰따옴표
안에서는 셸이 이들을 제멋대로 해석해서, 복사한 것과 다른 키를 얻게 됩니다.

**이 명령을 파일로 저장소에 두지 않고 손으로 입력하는 이유.** 이 랩의 나머지 모든 것은
Git에 넣을 수 있는 텍스트입니다. 시크릿은 안 됩니다. 클러스터 안의 `Secret` 객체는 값을
base64로 저장하는데, base64는 암호화가 아니라 표기 방식입니다: 파일에 접근한 사람은 누구나
키를 읽습니다. Git에 시크릿 파일을 두는 것은 전체 이력을 포함해 키를 영원히 Git에 두는
것입니다. 이것이 바로 Propusk 시나리오에 OpenBao를 끌어들이는 그런 종류의 감사 지적입니다.

## 4단계. 무엇을 빌드할지 살펴보기

폴더에는 `propusk-src.yaml`이 있습니다 — 앱의 소스 코드를 ConfigMap 형태로 담은 것입니다.
**ConfigMap**은 안에 텍스트 파일을 담는 클러스터 객체입니다: 클러스터는 이후 그 파일들을
컨테이너 안에 디스크 상의 평범한 파일로 놓습니다. 가장 가까운 비유는 설정 파일을 모아 둔
공유 폴더이지만, 클러스터 자체에 저장되고 작업 설명과 함께 도착한다는 점이 다릅니다.

소스 코드가 거기 있는 이유도 같습니다: 빌드에는 파일이 필요한데, 텍스트 파일 여섯 개를
위해 네트워크 디스크를 마련할 이유는 없습니다.

앱은 한 가지 일만 합니다: «방문객 출입증 신청하기»라는 문구를 표시합니다. 이것으로
충분합니다. 이 랩은 Android에 관한 것이 아니라 그것이 어디서 빌드되는지에 관한 것이기
때문입니다.

**APK**는 마지막에 나오는 결과물입니다. 컴파일된 애플리케이션, 이미지, 텍스트, 그리고 어떤
화면을 띄울지에 대한 설명이 담긴 아카이브입니다; 전화기가 설치하는 것이 바로 이것입니다.
역할로 보면 Windows의 `.msi`와 같습니다: 사용자에게 건네는 단일 파일입니다.

<details>
<summary><b>자세히 보기: 소스 코드 안에 무엇이 있는가</b></summary>

ConfigMap의 키들에 나뉘어 담긴 파일 여섯 개입니다.

### `settings.gradle.kts` — Gradle이 의존성을 찾는 곳

```kotlin
pluginManagement {
  repositories { google(); mavenCentral(); gradlePluginPortal() }
}
```

Android 빌드 플러그인, Kotlin 플러그인, 그리고 그들이 끌어오는 모든 것을 내려받는 세 개의
공개 저장소입니다. 첫 빌드가 느린 이유를 설명해 주는 것이 바로 이 목록입니다: 빈
컨테이너에서 모든 것을 내려받아야 하기 때문입니다.

⚠️ 보안 부서가 의존성을 인터넷에서 가져오는 것을 금지하면, 바로 이 자리가 여러분이 가장
먼저 바꿀 곳입니다. 그러면 여기에 여러분의 프록시 저장소를 적게 됩니다. Harbor가 Docker
Hub의 대체재가 된 것과 똑같습니다.

### `build.gradle.kts` — 도구 버전

```kotlin
plugins {
  id("com.android.application") version "8.5.2" apply false
  id("org.jetbrains.kotlin.android") version "1.9.24" apply false
}
```

`apply false`는 "버전을 선언하되 루트 프로젝트에서는 활성화하지 마라"를 뜻합니다 — `app`
모듈이 활성화합니다. 버전은 일부러 고정했습니다: "최신"을 끌어오는 빌드는 한 달 뒤에
오늘과 다르게 빌드되며, 그 이유를 파헤치는 사람은 바로 여러분입니다.

### `app-build.gradle.kts` — 모듈 자체

```kotlin
android {
  namespace = "io.aenix.propusk"
  compileSdk = 34
  defaultConfig { minSdk = 24; targetSdk = 34 }
}
```

`compileSdk 34`는 우리가 컴파일 기준으로 삼는 Android SDK의 버전입니다. 이것은 SDK 설치
단계에서 정확히 무엇을 내려받아야 하는지도 결정하며, 그 양은 약 1.5기가바이트입니다.

`minSdk 24`는 앱이 실행될 가장 오래된 Android입니다. 여기서는 Android 7입니다.

```kotlin
  kotlinOptions { jvmTarget = "17" }
```

Kotlin은 JVM 바이트코드로 컴파일되며, 그래서 Java 버전에 대한 요구가 생깁니다. 우리가 쓰는
이미지에는 JDK 17이 들어 있고, 이 두 숫자는 반드시 일치해야 합니다.

### `MainActivity.kt` — 애플리케이션

```kotlin
class MainActivity : Activity() {
  override fun onCreate(savedInstanceState: Bundle?) {
    ...
    view.text = getString(R.string.greeting)
```

액티비티 하나, `TextView` 하나, 리소스에서 가져온 텍스트. 호환성 라이브러리 대신 맨
`android.app.Activity`를 씁니다: 앱에는 외부 의존성이 전혀 없으며, 이것이 매 빌드마다 몇
분의 다운로드 시간을 아껴 줍니다.

`R.string.greeting`은 `strings.xml`의 문자열에 대한 참조입니다. `R` 클래스는 빌드 시점에
생성되며, 소스에는 없습니다. "unresolved reference: R" 오류를 보게 된다면, 그것은 여러분의
코드가 아니라 리소스 생성 단계가 실패했다는 뜻입니다.

### `AndroidManifest.xml`과 `strings.xml`

매니페스트는 아이콘에서 어떤 액티비티가 실행되는지 선언합니다. `strings.xml`은 텍스트를
코드와 분리해 둡니다 — 그렇게 하면 프로그래머를 거치지 않고 번역할 수 있습니다.

</details>

소스 코드를 클러스터에 넣습니다. 아직 아무것도 실행되지 않습니다: 이것들은 다음 단계에서
빌드가 필요로 할 파일일 뿐입니다.

```bash
# 안에 파일 여섯 개가 든 ConfigMap을 생성합니다. 제자리에 있는지 확인하려면:
# kubectl get configmap propusk-src
kubectl apply -f propusk-src.yaml
```

**보여야 할 결과** — `configmap/propusk-src created`.

## 5단계. Job 뜯어보기

실행하기 전에, 무엇을 실행하는지 정확히 읽어 보세요. 빌드는 노드 전체를 점유하므로, 무엇을
위해 그러는지 이해해 둘 가치가 있습니다.

<details>
<summary><b>자세히 보기: android-build.yaml 안에 무엇이 있는가</b></summary>

파일에는 객체 두 개가 있습니다: 빌드 스크립트가 든 ConfigMap과 Job 자체입니다.

### 빌드 스크립트

이것이 ConfigMap에 있는 이유는 nginx 페이지가 Deployment와 별도로 있었던 것과 같습니다:
`command` 필드 안에 든 40줄짜리 셸은 읽을 수가 없습니다.

다섯 단계이며, 다섯 개 모두 빌드 서버에서 손으로 입력할 법한 평범한 명령입니다. 컨테이너는
비어서 시작합니다: 이미지에서 온 Java와 Gradle은 있지만 Android SDK도, 키도, 소스도
없습니다 — SDK와 키는 빌드 명령이 끌어오고, 소스는 컨테이너에 마운트된 ConfigMap이 함께
가져옵니다.

| 단계 | 하는 일 | 걸리는 시간 |
|---|---|---|
| 1 | Android command-line tools를 내려받음 — SDK 자체를 설치하는 데 쓰이는 유틸리티 모음 | 1~2분 |
| 2 | 라이선스를 수락하고 SDK, 플랫폼 34, build-tools를 설치 | 5~15분 |
| 3 | `gradle :app:assembleDebug` — 소스를 APK로 컴파일 | 3~8분 |
| 4 | S3 저장소용 커맨드라인 클라이언트 `mc`를 설치 | 몇 초 |
| 5 | APK를 두 개의 이름으로 버킷에 넣음 | 몇 초 |

세 줄은 자세히 볼 가치가 있습니다.

```bash
# yes — "y"를 끝없이 출력하는 명령입니다: 이렇게 하면 "라이선스를
# 수락하시겠습니까? [y/n]" 같은 질문 묶음이 사람 없이 답해집니다.
#   >/dev/null 2>&1   일반 출력과 오류 출력을 모두 버림: 여기서는 필요 없음
#   || true           "명령이 오류를 반환하더라도 괜찮은 것으로 간주하라"
yes | sdkmanager --sdk_root="$ANDROID_SDK_ROOT" --licenses >/dev/null 2>&1 || true
```

여기서 `|| true`는 대충 넘긴 것이 아니라 필수입니다: `sdkmanager`가 입력을 닫으면 `yes`는
SIGPIPE를 받고 0이 아닌 코드를 반환합니다. `set -o pipefail` 아래에서는 이것이 아무 이유
없이 빌드를 실패시킵니다. 라이선스가 실제로 수락되지 않았다면, 바로 다음 명령이 SDK 설치를
거부하므로, 우리가 오류를 숨기는 것은 아닙니다.

```bash
# alias set = "저장소 주소와 키를 builds라는 짧은 이름으로 기억해 둬라". 그래야
# 이후 모든 복사 명령에서 그것들을 반복하지 않습니다.
#   "https://${endpoint}"   주소: https:// 접두사는 우리가 직접 붙입니다. 시크릿에는 없습니다
#   ${accessKey} ${secretKey}   S3 용어로 로그인과 비밀번호이며, 시크릿에서 옵니다
#   >/dev/null              출력을 끔
mc alias set builds "https://${endpoint}" "${accessKey}" "${secretKey}" >/dev/null
```

출력은 일부러 껐고, 스크립트에 `set -x`가 없는 이유도 같습니다: Job의 로그는 클러스터에
접근할 수 있는 모든 사람에게 보이며, 키가 거기 들어가서는 안 됩니다.

```bash
# echo는 작업 로그에 한 줄을 출력합니다. 아무 일도 하지 않습니다 — 이전 복사
# 명령이 끝까지 실행되었다는 표시입니다
echo "APK-UPLOADED ${bucketName}/propusk/propusk-${STAMP}.apk"
```

표시용 줄입니다. 이것으로 `check.sh`는 "Job이 돌았다"와 "APK가 실제로 버킷에 도착했다"를
구분합니다 — 이 둘은 서로 다른 주장이며, 두 번째가 더 강합니다.

### Job

```yaml
kind: Job
spec:
  backoffLimit: 1
```

빌드가 실패했을 때 Pod를 몇 번 다시 만들지입니다. 0이 더 정직하겠지만, 1.5기가바이트짜리
SDK를 내려받는 도중 네트워크가 이따금 끊기고, 두 번째 시도가 "왜 내 것이 실패했지"를
파헤치는 것보다 쌉니다.

```yaml
  activeDeadlineSeconds: 7200
```

작업 전체에 대한 상한, 두 시간입니다. 이것이 없으면 멈춰 버린 빌드가 저녁까지 노드를 붙들고
있고, 여러분은 배포가 안 되는 옆 사람에게서 그 얘기를 듣게 됩니다.

카운트다운은 컨테이너 시작이 아니라 Job 생성 시점부터 시작합니다: `Pending`에 머문 시간과
랩 조금 뒤에 나오는 노드 재생성이 같은 한도를 깎아 먹습니다. 여기에는 한 시간으로
부족했습니다 — 사람이 이미 기다려 낸 직후에 빌드가 `DeadlineExceeded`로 죽곤 했습니다.

```yaml
      restartPolicy: Never
```

Job에서 이 필드는 필수이며, 유효한 값은 둘뿐입니다. `Never`는 이런 뜻입니다: 실패한
프로세스를 같은 Pod 안에서 재시작하지 말고, 결정을 Job에 넘겨라 — Job이 새 것을 만듭니다.
그렇게 하면 각 시도가 자신만의 로그를 가지며, 몇 번째가 실패했는지 볼 수 있습니다.

Deployment에서 익숙한 `Always` 값은 여기서는 쓸 수 없습니다: "항상 재시작"과 "끝날 때까지
기다림"은 서로 모순되기 때문입니다.

```yaml
          envFrom:
            - secretRef:
                name: bucket-creds
```

시크릿의 네 키 모두가 같은 이름의 환경 변수가 됩니다. 대안은 각 변수를 따로 나열하는
것인데; 같은 종류의 키 네 개에 대해서는 불필요한 잡음입니다.

⚠️ 알아 둘 만한 부작용: `envFrom`은 나중에 추가된 것을 포함해 시크릿의 **모든** 키를
환경으로 끌고 들어옵니다. 여러분이 직접 만든 시크릿, 그리고 단일 작업에 대해서는
허용됩니다. 네임스페이스 전체에 걸친 공유 시크릿에 대해서는 아닙니다.

```yaml
          resources:
            requests: {cpu: "1", memory: 4Gi}
            limits:   {cpu: "2", memory: 6Gi}
```

바로 이것이 Android 빌드의 정직한 값입니다. `requests`는 예약할 양입니다: 코어 하나와
4기가바이트. 더 적게는 의미가 없습니다 — Kotlin 컴파일러가 그것을 다 먹어 치우고 더
달라고 합니다. `limits`는 상한입니다: 코어 두 개와 6기가바이트.

첫 랩의 앱과 비교해 보세요: CPU `20m`에 메모리 `32Mi`. CPU는 50배, 메모리는 130배
차이입니다. 이것은 "`requests`를 도대체 왜 지정하는가"라는 질문과 관련됩니다: 그것들이
없으면 스케줄러는 빌드를 nginx만큼 가볍다고 여겨, 들어가지도 못할 노드에 배치합니다.

```yaml
        - name: work
          emptyDir:
            sizeLimit: 12Gi
```

노드 위의 임시 디스크입니다. SDK, Gradle 캐시, 빌드 결과가 여기에 안착합니다 — 통틀어
6~8기가바이트입니다. Pod가 사는 딱 그만큼만 존재합니다: Job이 끝나면 디스크는 사라집니다.

**여기서 왜 매 빌드가 느린지 곧바로 따라 나옵니다.** 우리는 매번 SDK와 의존성을 처음부터
내려받습니다. 실제 빌드 서버라면 `emptyDir` 대신 퍼시스턴트 볼륨이 있어 작업보다 오래
살아남습니다: 첫 빌드는 더 느리고, 두 번째는 눈에 띄게 빠릅니다. 우리는 불필요한 요소를
하나 더 들이지 않으려고 랩에서 일부러 이렇게 하지 않지만, 실제로는 가장 먼저 추가할
것입니다.

```yaml
            items:
              - key: app-build.gradle.kts
                path: app/build.gradle.kts
```

ConfigMap 키는 슬래시를 담을 수 없지만, 마운트 경로는 담을 수 있습니다. 그렇게 해서 여섯
키의 평평한 맵이 Gradle이 기대하는 디렉터리 트리로 펼쳐집니다.

</details>

## 6단계. 실행하기 — 그리고 벽에 부딪히기

📍 **위치:** bastion에서, `lab` 클러스터에서.

job을 적용하고, 그것이 생성한 Pod를 바로 봅니다.

```bash
# 파일에서 객체 두 개를 생성합니다: 스크립트가 든 ConfigMap과 Job 자체.
# 이 순간부터 클러스터는 빌드를 위한 노드를 찾아 실행할 의무를 집니다
kubectl apply -f android-build.yaml

# get pods = "Pod를 보여줘". 작업의 Pod에는 자기 이름이 없습니다 — Job이
# 자기 이름 뒤에 무작위 꼬리를 붙여 스스로 지어냅니다. 그래서 이름이 아니라 레이블로 찾습니다:
#   -l job-name=propusk-build   job-name 레이블이 job의 이름과 같은 Pod를 선택.
#                               Job이 이 레이블을 자기 Pod에 스스로 붙입니다
kubectl get pods -l job-name=propusk-build
```

**아마도 보게 될 것:**

```
NAME                   READY   STATUS    RESTARTS   AGE
propusk-build-x7k2p    0/1     Pending   0          40s
```

`Pending`은 "시작하는 중"을 뜻하지 않습니다. "시작하지 못했고 앞으로도 못한다"는 뜻입니다.
클러스터는 그 이유를 Pod의 이벤트에 적습니다 — 누가 그것에 무엇을 하려 했는지에 대한
기록입니다.

```bash
# describe = "객체에 대해 알려진 모든 것을 보여줘": 설정, 상태, 이벤트.
# 출력이 길어서, 그 끝부분만 남깁니다:
#   sed -n '/Events:/,$p'   "Events:"가 나오는 줄부터
#                           출력 끝까지 출력($ — 끝)
kubectl describe pod -l job-name=propusk-build | sed -n '/Events:/,$p'
```

**보여야 할 결과** — Pod가 배치되지 못한 이유가 담긴 줄:

```
Warning  FailedScheduling  0/1 nodes are available: 1 Insufficient cpu, 1 Insufficient memory.
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 정확히 무엇이 맞지 않았을까요? 랩 0에서 어떤 노드를 주문했는지, 그리고 Job이 메모리를
> 얼마나 요청했는지 떠올려 보세요.

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

랩 0에서 우리는 `u1.medium` 노드를 골랐습니다 — 코어 하나와 4기가바이트입니다. Job은
`requests: memory 4Gi`와 `cpu 1`을 요청합니다. 노드가 가진 것과 정확히 같지만, 그중 일부는
이미 쓰이고 있습니다: kubelet이 자기 몫으로 메모리를 예약하고, 게다가 노드에서는 네트워킹과
모니터링용 시스템 Pod가 돌아가며, 거기에 첫 랩의 앱까지 있습니다.

**둘 다** 부족하다는 점에 주목하세요 — CPU도입니다. `u1.medium` 노드는 코어 하나를 주는데,
빌드는 온전한 하나를 요청하고, 코어의 일부는 이미 시스템 Pod가 차지하고 있습니다. 그래서
메시지에 이유가 하나가 아니라 둘인 것입니다: 스케줄러에게는 그중 하나만으로도 충분합니다.

스케줄러는 노드 위 모든 Pod의 `requests`를 합산해, 노드가 실제로 내줄 수 있는 것과
비교합니다. 여유 공간이 모자라서, Pod는 영원히 기다리는 상태로 남습니다.

**교훈은 이 오류보다 넓습니다.** Kubernetes 스케줄러는 실제 소비량이 아니라 **선언된** 것을
셉니다. 모든 Pod가 졸고 있고 CPU 사용률이 3퍼센트인 노드라도, `requests`의 합이 이미
용량과 같다면 스케줄러 입장에서는 완전히 점유된 것일 수 있습니다. 그 반대도 마찬가지입니다:
부하로 숨넘어가는 노드도 `requests`의 합이 상한에 닿을 때까지 새 Pod를 계속 받아들입니다.

이것은 겉보기에 텅 빈 클러스터에서 첫눈에 이상해 보이는 `Insufficient cpu, Insufficient
memory` 조합도 설명해 줍니다 — 여러분은 이것을 한 번 이상 마주치게 됩니다.

vSphere에서 여러분은 둘 다에 익숙합니다: DRS가 배치 시에 고려하는 reservation, 그리고
그것이 따로 살펴보는 실제 부하입니다. 여기서 배치는 **오직** reservation만으로 계산되며,
나머지 절반은 없습니다.

</details>

## 7단계. 노드 키우기

📍 **위치:** 대시보드에서, `lab` 애플리케이션에서.

`Kubernetes` → `lab` → edit를 여세요. node group에서 다음을 바꿉니다:

| 필드 | 이전 | 이후 | 이유 |
|---|---|---|---|
| Instance type | `u1.medium` (1코어, 4GB) | `u1.large` (2코어, 8GB) | 빌드가 들어가는 최소치 |
| Disk | `20Gi` | `40Gi` | SDK, Gradle 캐시, 이미지 레이어가 20에는 안 들어감 |

테넌트의 쿼터가 허용한다면 `u1.xlarge`(4코어, 16GB)를 고르세요. 빌드가 눈에 띄게 빨라지고,
남는 리소스는 랩 직후에 반납하게 됩니다. 허용하지 않으면 저장 시 폼이 거부하며, 그러면
`u1.large`가 남는 선택지입니다.

⚠️ **노드 타입을 바꾸면 노드의 가상 머신이 다시 생성됩니다.** 옛 노드가 떠나고 새 노드가
올라오며 Pod가 옮겨 갑니다. 몇 분이 걸리고, 노드의 로컬 디스크에 살던 모든 것이 사라집니다.
우리 랩에서는 이것이 무해합니다 — 데이터는 노드가 아니라 관리형 서비스에 있기
때문입니다 — 하지만 프로덕션 클러스터에서는 계획을 세워 진행하는 작업입니다.

새 노드를 기다리세요. `lab` 클러스터에는 그래픽 콘솔이 없어서, 명령으로 지켜봅니다:

```bash
# get nodes = "클러스터의 노드를 보여줘" — Pod가 그 위에서 돌아가는
# 바로 그 가상 머신들입니다.
#   -w   watch, "종료하지 말고 변경이 있을 때마다 줄을 덧붙여라". 옛 노드는
#        목록에서 빠지고, 새 노드가 나타나 STATUS=Ready에 도달합니다.
#        지켜보기를 벗어나려면 — Ctrl+C, 클러스터에는 아무 영향이 없습니다
kubectl get nodes -w
```

노드가 `Ready`가 되는 즉시, 멈춰 있던 빌드 Pod가 스스로 움직입니다 — 스케줄러는 `Pending`
Pod를 끊임없이 재검토하므로, 부탁할 필요가 없습니다. 움직이는지 확인합니다:

```bash
# 노드 수정 전과 같은 질의입니다. 이제 STATUS 열에는
# ContainerCreating가, 그리고 1~2분 뒤에는 Running이 보여야 합니다
kubectl get pods -l job-name=propusk-build
```

## 8단계. 빌드 기다리기

📍 **위치:** bastion에서, `lab` 클러스터에서.

빌드를 그 로그에서 지켜보겠습니다 — 즉, 스크립트가 컨테이너 안에서 화면에 출력하는
것에서 말이죠.

```bash
# logs = "작업이 출력한 것을 보여줘".
#   -f                  follow: 종료하지 말고 줄이 나타나는 대로 덧붙임.
#                       종료 — Ctrl+C, 그래도 빌드는 계속됩니다
#   job/propusk-build   Pod가 아니라 Job 자체를 가리켜도 됩니다: kubectl이 알아서 그 Pod를 찾습니다
kubectl logs -f job/propusk-build
```

**보여야 할 결과** — 스크립트의 다섯 단계가 순서대로. 시간 이정표:

| 로그 표시 | 대략 언제 |
|---|---|
| `== 1/5 Android command-line tools 설치 중 ==` | 즉시 |
| `== 2/5 라이선스에 동의하고 SDK 내려받는 중 (가장 오래 걸리는 단계) ==` | +1~2분, 가장 오래 멈춰 있음 |
| `== 3/5 APK 빌드 중 ==` | 시작으로부터 +5~15분 |
| `BUILD SUCCESSFUL in ...` | 시작으로부터 +10~25분 |
| `APK-UPLOADED bucket-.../propusk/propusk-...apk` | 바로 그 뒤 |

⚠️ **`2/5` 표시에서 20분간의 침묵은 정상이며, 멈춘 것이 아닙니다.** `sdkmanager`는 비대화형
모드에서 다운로드 진행률을 보여주지 않습니다: 조용히 있다가 `done`을 출력합니다. 프로세스가
살아 있는지는 다른 터미널 창에서 확인할 수 있습니다 — Pod가 CPU와 메모리를 먹고 있는지
보세요:

```bash
# top = "지금 얼마나 소비하고 있는지". requests 요청이 아니라 바로 이 순간의
# 실제 사용량입니다. 0이 아닌 CPU는 안에서 작업이 진행되고 있다는 뜻입니다
kubectl top pod -l job-name=propusk-build
```

Job은 Pod가 코드 0으로 종료되었을 때 완료된 것으로 간주됩니다(0이라는 반환 코드는 널리
통용되는 "오류 없이 실행됨"입니다):

```bash
# Pod가 아니라 job 자체를 봅니다: Pod에는 없는 열이 있습니다
kubectl get job propusk-build
```

```
NAME             STATUS     COMPLETIONS   DURATION   AGE
propusk-build    Complete   1/1           18m32s     19m
```

`DURATION` 열이 바로 "빌드가 얼마나 걸리는가"라는 모바일 팀의 질문에 대한 답입니다. 같은
Job을 삭제하고 다시 만들어 두 번째로 실행해도 똑같이 걸립니다: 캐시가 없으며, 그 이유를
우리는 압니다.

## 9단계. APK 가져오기

📍 **위치:** 테넌트 대시보드에서, 버킷 카드에서.

버킷에는 웹 인터페이스가 있습니다 — 버킷 카드에서 그것을 열고 같은 `accessKey`와
`secretKey`로 로그인하세요. 안에서 다음을 보게 됩니다:

```
propusk/propusk-20260821-141207.apk
propusk/propusk-latest.apk
```

파일 하나에 이름 둘은 흔한 관행입니다: 날짜가 붙은 이름은 빌드 이력을 보여주고, `latest`
로는 테스터가 오늘 날짜가 며칠인지 묻지 않고도 늘 가장 최신의 것을 집습니다.

`propusk` "폴더"는 실제로 존재하지 않는다는 점에 주목하세요. 객체 저장소에는 디렉터리가
없습니다: `propusk/propusk-latest.apk`가 객체 이름 전체이고, 그 안의 슬래시는 우리 편의를
위해 인터페이스가 트리로 그린 것입니다.

여러분에게 익숙한 **파일 공유와 무엇이 다른가**:

| | 파일 공유(NFS, SMB) | 객체 저장소(S3) |
|---|---|---|
| 어떻게 연결되는가 | 디스크로 마운트됨 | 마운트되지 않고, HTTP로 요청 |
| 부분 쓰기 | 파일 중간에 쓸 수 있음 | 불가, 객체는 통째로 넣음 |
| 디렉터리 | 진짜임 | 없음, 슬래시는 이름의 일부 |
| 잠금 | 있음 | 없음 |
| 누가 접근할 수 있는가 | 같은 네트워크에 있는 사람 | 키와 HTTPS를 가진 누구나 |
| 얼마나 담기는가 | 볼륨이 담는 만큼 | 사실상 상한 없음 |

여기서 선택의 규칙이 나옵니다: **데이터베이스나 문서 공유 폴더는 파일 공유, 아티팩트와
백업은 객체 저장소**. 데이터베이스를 S3에 올리려는 것은 인터넷 너머로 SMB를 통해 APK를
나눠 주는 것만큼 괴롭습니다.

```bash
# 스크립트는 여러분과 같은 접근 파일로 lab 클러스터에 접속합니다. 버킷
# 자격 증명은 bucket-creds 시크릿에서 가져옵니다 — 따로 입력할 것은 없습니다
export KUBECONFIG=~/lab.kubeconfig
./check.sh
```

⚠️ **Windows에서는 스크립트가 PowerShell이 아니라 WSL에서 실행됩니다** — 설치 방법은 랩 0
시작 부분에 나와 있습니다. WSL 없이도 랩을 마칠 수 있지만, 아티팩트 리포트는 나오지
않습니다.

스크립트는 여러분이 매니페스트를 적용했는지가 아니라, 빌드가 끝까지 실행되었는지를
검사합니다: Job이 성공적으로 끝났고, 로그에 `BUILD SUCCESSFUL`이 있으며, APK가 버킷에
도착했고, 시크릿의 저장소가 클러스터 안에서 실제로 응답하는지입니다.

## 정리

끝나고 나면 Job은 아무것도 소비하지 않습니다: Pod가 종료되었고, 그 코어와 기가바이트는
`Complete` 시점에 노드의 여유 용량으로 반납되었습니다 — 다른 누군가가 곧바로 가져갈 수
있습니다. 남는 것은 클러스터의 기록과 로그뿐입니다 — 몇 킬로바이트입니다.

바로 삭제할 필요는 없습니다. 로그가 아직 쓸모 있습니다. 다 마쳤다면:

```bash
# delete -f = "이 파일에 기술된 것을 클러스터에서 제거하라". Job과 함께
# 그 로그도 사라지므로, 이 명령은 순서상 처음이 아니라 마지막에 옵니다
kubectl delete -f android-build.yaml
kubectl delete -f propusk-src.yaml
# 시크릿은 따로 삭제합니다: 그에 해당하는 파일이 없으며, 여러분이 명령으로 만들었습니다
kubectl delete secret bucket-creds
```

⚠️ **더 이상 필요 없다면 노드를 `u1.medium`으로 되돌리세요** — 그러지 않으면 워크숍이 끝날
때까지 코어 네 개를 점유합니다. 버킷과 그 내용물은 그대로 두세요: 작고, 다시 빌드하고 싶을
때 쓸모가 있습니다.

바로 이 정리의 저렴함이 전용 빌드 서버에 반대하는 논거입니다. 우리는 빌드가 진행되는 동안
더 큰 노드를 빌렸고, 필드 하나를 고쳐 이전 노드를 반납했습니다.

## 이제 우리가 할 수 있는 것

- Job과 Deployment를 구별하고, 빌드를 후자로 실행해서는 안 되는 이유를 이해하기
- 그것을 위한 머신을 마련하지 않고도 무거운 일회성 작업을 클러스터에서 실행하기
- 아티팩트를 객체 저장소에 넣고, 그것이 어떻게 파일 공유가 아닌지 설명하기
- `Pending`을 "로딩 중"이 아니라 "`requests` 기준으로 안 들어갔다"로 읽기
- Android 빌드의 진짜 값을 코어, 기가바이트, 분으로 말하기

## 그리고 vSphere였다면 이랬을 것

빌드 에이전트 역할을 할 VM 요청. 하루에 20분 일하는데 왜 16기가바이트가 필요한지에 대한
정당화. 거절. 한 분기 뒤의 두 번째 시도. 그다음엔 98%의 시간을 놀고, 삭제하기가 무서워서
1년 뒤에는 SDK 세 세대가 설치되어 있는 머신.

여기서 리소스는 작업이 진행되는 동안 빌려서 스스로 반납됩니다.

**솔직히, vSphere가 더 편한 지점.** 영구적으로 사는 빌드 머신에는 부정할 수 없는 장점이
하나 있습니다: 그 위에는 이미 모든 것이 내려받아져 있다는 것입니다. 우리 빌드 시간은 대부분
SDK와 의존성을 내려받는 것이고, 영구 에이전트에는 그것이 없을 것입니다. 이것은 캐시용
퍼시스턴트 볼륨으로 해결되지만, 볼륨은 마련해야 하고, 크기를 지켜봐야 하며, 청소해야
합니다 — 즉, 우리가 벗어나려던 바로 그 일의 일부를 도로 떠안는 것입니다. 차이는, 볼륨은
푼돈이 들고 요청이 필요 없는 반면, 머신은 필요했다는 점입니다.

그리고 둘째: SSH로 접속해 빌드가 왜 이상하게 구는지 볼 수 있는 살아 있는 머신은 편합니다.
Job의 Pod로는 로그만 볼 수 있고, 완료 후에는 그마저도 더 적습니다. 클러스터에서 빌드를
디버깅하는 것은 처음에는 더 느립니다.
