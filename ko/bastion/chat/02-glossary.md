## 2. 작은 용어집: 여러분 쪽에서는 뭐라고 부르고 여기서는 뭐라고 부르는가

**다시 돌아와 참고할 수 있는 하나의 메시지**

워크숍에서 생기는 혼란의 절반은 기술이 아니라 용어 때문입니다. 아래에 그 번역을 정리했습니다. 비유가
오해를 부르는 지점에서는 어디가 정확히 그런지 솔직하게 적었습니다. 잘못된 비유는 없는 것보다 나쁘기 때문입니다.

| vSphere에서는 | Cozystack / Kubernetes에서는 | 비유가 어긋나는 지점 |
|---|---|---|
| 가상 머신 | **VM Instance** | 어긋나는 것이 없습니다 — 바로 그것입니다 |
| VM 디스크 | **VM Disk** | 별도의 객체입니다. 디스크 없는 VM은 없으므로 디스크가 항상 먼저 생성됩니다 |
| VM 템플릿 | 카탈로그의 이미지 | — |
| 애플리케이션 컨테이너 | **Pod** | Pod는 일회용입니다. 고치는 게 아니라 삭제하면 새 것이 생성됩니다 |
| vApp | **Deployment** | — |
| 리소스 풀 | 쿼터가 있는 **테넌트** | 테넌트는 접근 경계이기도 합니다. 외부인은 안을 들여다볼 수 없습니다 |
| vCenter | API 서버 | 대시보드는 그것의 얼굴일 뿐, 그 자체가 아닙니다 |
| HA | **Deployment**가 N개의 복제본을 유지 | "죽은 것을 되살린다"가 아니라 "요청한 만큼 항상 유지한다"입니다 |
| 로드 밸런서 풀 | **Service** | — |
| Datastore | **Storage Class** | `replicated` — 세 개의 노드에 복제, `local` — 복제 없음 |
| Postgres가 설치된 별도의 VM | **카탈로그의 Postgres** | 복제와 백업을 갖추고 오며, 스스로 업데이트합니다 |
| IT 부서에 내는 요청 티켓 | *비유 없음* | 여러분이 직접, 1분 만에 합니다 |

⚠️ **두 "VM"을 혼동하지 마세요.** 이 경로에서 "VM"이라는 단어는 **bastion(공유 VM)**을 뜻합니다 —
여러분이 SSH로 접속해서 클러스터를 조작하는 공유 머신입니다. 그리고 여러분이 클러스터 안에서 띄울 머신
(컨버터, 그다음 app-VM)은 **VM Instance**이고, 이것을 "여러분의 머신" 또는 "app-VM"이라고 부릅니다.
bastion은 명령을 내리는 곳이고, app-VM은 클러스터 안에서 여러분이 생성하는 것입니다. `kubectl`/`virtctl`
명령은 bastion에서 입력하고, `netfix`, 데이터베이스 스키마, `psql`은 app-VM 안에서(`virtctl console`을
통해) 실행됩니다.

**익숙해져야 할 한 가지.** vSphere에서는 객체를 **생성**합니다: 클릭하면 나타나고, 그때부터는 스스로
살아갑니다. 여기서는 **원하는 상태를 기술**하면, 클러스터가 그것을 실제 상태와 끊임없이 비교하여 그 차이를
없앱니다. 그래서 무언가를 삭제해도 다시 돌아올 수 있습니다 — 오류 때문이 아니라, 여러분이 그 바람을
취소한 적이 없기 때문입니다.
