## 16. 단계 2: 변환기 머신

**변환 작업을 수행할 VM을 띄우기**

📍 **위치:** bastion(공유 VM)에서.

**"변환"이란 무엇이고 왜 피할 수 없는가.** 가상 머신의 디스크는 파일입니다. VMware는 이를 자체 포맷인 `VMDK`로 저장합니다. Cozystack에서 VM을 실행하는 KVM은 그 포맷을 이해하지 못합니다 — `QCOW2`가 필요합니다. 내용물은 똑같습니다. 온갖 것이 딸려 있는 여러분의 CentOS 그대로지만, 포장이 다릅니다. 변환이란 파일을 한 포맷에서 다른 포맷으로 다시 포장하는 것이며, 데이터 자체는 바뀌지 않습니다.

거기에 더해, 내부에 있는 것도 손봐야 합니다. vSphere에서 자라난 시스템은 VMware의 가상 하드웨어를 찾을 것으로 기대합니다. 자체 네트워크 카드, 자체 디스크 컨트롤러, `vmxnet3`와 `pvscsi` 드라이버 말입니다. 새 보금자리에서는 하드웨어가 다릅니다 — `virtio`입니다. 알맞은 드라이버를 부팅 이미지에 미리 심어 두지 않으면, 머신이 시작해도 디스크도 네트워크도 찾지 못합니다. 이 또한 변환이 처리해 줍니다.

**왜 가상 머신 자체가 아니라 별도의 머신인가.** 도구 이름은 `virt-v2v`인데, 산더미 같은 의존성을 끌고 오고 수십 기가바이트를 잡아먹습니다. 모두가 함께 작업하는 공유 bastion에 이를 설치하는 것은 나쁜 생각입니다. bastion은 작고 여러분 모두에게 단 하나뿐이니까요. 스토리지 바로 옆 클러스터에 일회용 머신을 띄워서, 그 안에서 작업하고, 끄는 편이 더 낫습니다.

덤으로, 이것이야말로 실제 마이그레이션 프로젝트에서 변환에 쓰이는 바로 그 방식입니다. 변환기는 VPN 너머 누군가의 워크스테이션이 아니라 데이터 바로 옆에 자리합니다.

```bash
kubectl apply -f manifests/02-conversion-vm.yaml
kubectl get vminstance -n tenant-workshopXX -w
```

`Running` 상태가 될 때까지 기다립니다(감시를 멈추려면 Ctrl+C를 누르세요). **콘솔을 통해** 안으로 들어갑니다:

```bash
virtctl console --namespace=tenant-workshopXX vm-instance-convert
```

**변환기 머신 접속:**
```
login:    ubuntu
password: ubuntu
```

콘솔에서 나가려면 — `Ctrl+]`. 화면이 비어 있으면 Enter를 누르세요.

⚠️ **`virtctl ssh`로는 들어가지 마세요.** 지난 워크숍들에서 아무에게도 작동하지 않았습니다. `exit status 255`를 응답하고 연결을 끊어 버립니다. 콘솔은 클러스터 API를 거치며 언제나 작동합니다. 같은 일을 마우스로도 할 수 있습니다 — 대시보드의 머신 페이지에 있는 **VNC** 버튼입니다.

**이 명령이 정확히 무엇을 만들었는가.** 파일에는 두 개의 객체가 기술되어 있으므로, 대시보드에는 하나가 아니라 두 개의 항목이 나타납니다:

• `convert-tools`라는 이름의 **VM Disk** — 카탈로그 이미지 `ubuntu-20.04`에서 복제한 25Gi 디스크
• `convert`라는 이름의 **VM Instance** — 그 디스크를 연결하는 머신 자체

VM은 디스크 없이는 결코 존재하지 않습니다 — 그래서 디스크가 항상 먼저, 별도의 객체로 생성됩니다. 이것을 기억해 두세요. 단계 4에서 똑같은 짝을 보게 됩니다.

⚠️ 그리고 이름에 대해 바로 한마디 하겠습니다. 안 그러면 헷갈릴 겁니다. 대시보드의 객체는 `convert`라고 불리지만, 그것이 띄우는 머신은 클러스터 내부에서 접두사가 붙은 **`vm-instance-convert`**로 알려져 있습니다. 그러니 대시보드에서는 `convert`를 찾고, `virtctl` 명령에서는 `vm-instance-convert`라고 씁니다.

🖱 **대시보드를 통해:** 같은 두 객체를 손으로, 차례차례 생성합니다.
**1)** **VM Disk → Deploy new**: 이름 `convert-tools`, source = **image**, 이미지 `ubuntu-20.04`, 크기 `25Gi`, storage class `replicated`.
**2)** **VM Instance → Deploy new**: 이름 `convert`, instance type `u1.large`, profile `ubuntu`, 그리고 디스크 목록에서 한 단계 전에 생성한 `convert-tools`를 고릅니다. 바로 거기서 **VNC** 버튼으로 안에 들어갈 수 있고, 그러면 ssh도 virtctl도 필요 없이 전부 브라우저에서 됩니다.

⚠️ 디스크는 25Gi보다 작게 만들지 마세요: 이미지보다 작으면 복제가 진행되지 않고, 그러면 디스크가 Terminating 상태에 멈춰 걸리적거립니다.

⚠️ 매니페스트는 의도적으로 **ubuntu-20.04** 이미지를 지정하고 있으니, 바꾸지 마세요. 24.04에서는 머신이 부팅되지 않고, 22.04에서는 변환이 CentOS 7 내부의 오래된 패키지 데이터베이스에 걸려 넘어집니다. 여러분이 확인하지 않아도 되도록 우리가 확인해 두었습니다.
