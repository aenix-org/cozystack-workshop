## 왜 중요한가

어제 16:40에 "Propusk"가 15분 동안 응답이 느렸습니다. 불만은 늘 그렇듯 오늘 11:00에
접수되었습니다. 경영진의 질문은 이것이었습니다. 그게 무엇이었고, 또 일어날 것인가.

"지금 재현해서 한번 보자"라는 접근법은 통하지 않습니다. 어제 다른 누군가가 만든 부하를
지금 재현할 수는 없기 때문입니다. 답할 수 있는 유일한 방법은, 누가 묻기도 전에 미리 찍어 둔
**어제의 기록**을 갖고 있는 것입니다.

이번 lab에서는 lab 3에서 우리가 만든 부하의 흔적을 그래프에서 찾아냅니다. 트래픽이 시작될 때의
CPU 스파이크와, 오토스케일링이 복제본을 추가하며 생긴 계단식 상승입니다. 이를 위해 특별한 준비는
전혀 하지 않았습니다. 기록은 이미 거기 있습니다.

## 미니 용어집

| 용어 | 무엇인가 | 비슷하지만… |
|---|---|---|
| **메트릭(Metric)** | 규칙적으로 찍히는 숫자: CPU가 얼마, 메모리가 얼마, 요청이 몇 건 | **vCenter 그래프의 카운터**와 비슷하지만, 마지막 값이 아니라 이력으로 저장됩니다 |
| **레이블(Label)** | 메트릭에 붙는 "name=value" 쌍: pod, namespace, cluster | **카운터가 붙어 있는 객체**와 비슷하지만, 레이블은 여러 개이고 그중 무엇으로든 잘라 보고 묶어 볼 수 있습니다 |
| **시계열(Time series)** | 하나의 레이블 집합을 가진 단일 메트릭의 시간에 따른 변화 | **vCenter의 그래프 하나**와 비슷하지만, 레이블의 조합마다 각각의 시계열이 되고 그 수는 수천 개에 이릅니다 |
| **스크레이프(Scrape)** | 수집: 에이전트가 N초마다 소스를 폴링합니다 | **vCenter의 카운터 수집**과 비슷하지만, 애플리케이션이 데이터를 밀어 보내는 것이 아니라 에이전트가 당겨 옵니다 |
| **PromQL** | 메트릭용 쿼리 언어 | 직접적인 유사물이 없습니다. vCenter에서는 카운터를 고르지만, 여기서는 식을 씁니다 |
| **VictoriaMetrics** | 수집된 메트릭이 보관되는 저장소 | **vCenter의 통계 데이터베이스**와 비슷하지만, Prometheus 자체는 아니면서도 Prometheus 쿼리 언어를 이해합니다 |
| **Grafana** | 메트릭과 로그를 보는 인터페이스 | **Performance 탭**과 비슷하지만, 별도의 제품입니다. 대시보드는 손으로 작성하거나 기성품을 가져다 씁니다 |
| **리텐션(Retention)** | 이력을 얼마나 오래 보관하는가 | **vCenter의 통계 레벨**과 비슷하지만, 파라미터로 설정됩니다. 기본값은 두 개의 별도 저장소에 걸쳐 3일과 14일입니다 |
| **로그(Logs)** | 애플리케이션이 기록하는 줄(line) | **게스트 OS의 로그**와 비슷하지만, 중앙에서 수집되며 PromQL이 아닌 자체 쿼리 언어를 가집니다 |
| **Pod** | 실행의 최소 단위: 컨테이너 하나 또는 여럿이 항상 단일 노드 위에 함께 있습니다 | **가상 머신**과 비슷하지만, 일회용입니다. 재부팅하는 대신 새 이름으로 다시 생성됩니다 |
| **namespace** | 클러스터 내부의 구획: 서로 다른 namespace의 동일한 이름은 충돌하지 않습니다 | **vCenter 인벤토리의 폴더**와 비슷하지만, 권한·쿼터·네트워크 정책까지 나눕니다 |
| **테넌트(Tenant)** | 플랫폼에서 당신의 몫: Grafana가 여기 살고, 클러스터의 메트릭이 이곳으로 흘러듭니다 | **자체 권한을 가진 리소스 풀**과 비슷하지만, 단순한 리소스가 아니라 완성된 서비스까지 나눠 줍니다 |

### 메트릭과 로그 — 왜 서로 다른 것인가

이 둘은 늘 한데 묶여 다뤄지고, 그러다 보면 사람들은 메트릭에만 존재하는 것을 로그에서 찾아 헤매게 됩니다.

| | 메트릭 | 로그 |
|---|---|---|
| 무엇인가 | 규칙적인 간격의 숫자 | 이벤트가 일어난 순간의 줄(line) |
| 예시 | "16:41:30에 Pod가 240 millicore를 사용했다" | "16:41:31 ERROR connection refused" |
| 용량 | 적고, 양이 예측 가능하다 | 많고, 애플리케이션이 얼마나 수다스러운지에 따라 달라진다 |
| 보관 기간 | 몇 주, 몇 달 | 며칠 |
| 답하는 질문 | "얼마나, 그리고 언제" | "정확히 무슨 일이 일어났는가" |
| 쿼리 언어 | PromQL | LogsQL (Grafana에서는 별도의 데이터 소스입니다) |

이 둘은 한 쌍으로 작동합니다. **메트릭은 그 순간을 찾아 주고, 로그는 그 원인을 찾아 줍니다.** 그래프가
16:41에 스파이크를 보여 주면, 당신은 그 분(minute)의 로그로 갑니다. 반대 방향으로는 통하지 않습니다.
로그에서 "언제 상황이 나빠졌는지"를 찾는 일은 끝없이 걸릴 수 있습니다.

### 왜 메트릭은 요청이 있을 때가 아니라 끊임없이 수집되는가

이것이 모니터링과 진단을 가르는 핵심이며, 분명하게 짚고 넘어갈 가치가 있습니다.

요청이 있을 때 수집하는 것은 **물리적으로** 불가능합니다. 질문이 던져지는 시점에 이미 이벤트는 끝나
있습니다. 어젯밤에 아무도 기록하지 않았다면, 어떤 시스템도 어젯밤의 부하를 보여 주지 못합니다.

그래서 에이전트는 무차별적으로, 30초마다 모든 것을 폴링해 저장소에 넣습니다. 그렇습니다,
이 숫자들의 99%는 아무도 들여다보지 않을 것입니다. 그 99%의 대가는 디스크 몇 기가바이트입니다.
빠진 1%의 대가는 "무슨 일이 있었는지 우리는 모르고, 앞으로도 영영 모른다"입니다.

⚠️ **미리 알아 둘 만한 단점.** 끊임없는 수집은 곧 끊임없는 비용을 뜻합니다. 에이전트는 CPU와
메모리를 차지하고, 저장소는 계속 자랍니다. 큰 클러스터에서는 메트릭이 소비 항목에서 눈에 띄는
비중을 차지하게 되어, 이를 솎아내야 합니다. 리텐션을 줄이고, 불필요한 레이블을 버리고, 거의
쓰이지 않는 메트릭의 수집을 끄는 것입니다. 이것은 일상적인 운영 작업이며, 첫 달에는 나타나지
않지만 언젠가는 반드시 나타납니다.

## 1단계. 메트릭이 애초에 수집되고 있는지 확인하기

📍 **위치:** 노트북에서.

`lab` 클러스터는 메트릭을 스스로 노출하지 않고 `Monitoring agents` 애드온을 통해 노출합니다.
이 애드온이 켜져 있는지 확인합니다:

```bash
# KUBECONFIG — kubectl이 클러스터의 주소와 누구로 로그인할지를 읽어 오는 변수입니다. `lab` 클러스터를
# 만들 때 ~/lab.kubeconfig 파일을 저장해 두었습니다. 새 터미널 창을 열 때마다 다시 설정해야 합니다.
export KUBECONFIG=~/lab.kubeconfig

# get pods = "어떤 pod들이 있는지 보여 줘".
#   -n cozy-monitoring   전체 클러스터가 아니라 이 namespace 안만 봅니다: 바로 여기에
#                        애드온이 수집기를 넣습니다.
kubectl get pods -n cozy-monitoring
```

**목록에 `vmagent`와 `fluent-bit`가 보인다면** — 모두 제자리에 있는 것이니, 다음으로 넘어갑니다.

⚠️ **목록이 비어 있는지가 아니라 이름을 보세요.** `cozy-monitoring` namespace는 항상 존재합니다.
플랫폼은 여기에 `metrics-server`도 넣는데, 이것은 자체 etcd를 가진 어떤 클러스터에도 설치되며
애드온과는 무관합니다. 다시 말해, `metrics-server` 한 줄을 보고 메트릭 수집이 켜져 있다고
결론짓는 것은 전형적인 오류이며, 이 오류는 오직 Grafana에서, 모든 것이 텅 비어 있을 때에야 드러납니다.

**목록에 `metrics-server`는 있지만 `vmagent`도 `fluent-bit`도 없다면:**

```
NAME                              READY   STATUS    RESTARTS   AGE
metrics-server-7d4b8c9f5-x2klm    1/1     Running   0          3d
```

이는 애드온이 꺼져 있고, 당신에게 과거의 기록이 없다는 뜻입니다. 이것은 마침 앞 절의 정확한
예시입니다. 수집은 소급하여 켤 수 없습니다.

수집은 대시보드에서 켭니다: `Kubernetes` → `lab` → edit → Addons 섹션에서 `Monitoring agents`에
체크. 애드온은 몇 분 안에 올라오지만, **메트릭은 오직 그 순간부터 쌓이기 시작합니다** — lab 3의
스파이크는 더 이상 찾을 수 없습니다.

그러니 스파이크를 다시 만들어야 합니다. lab 3의 정리 과정에서 오토스케일링이 제거되었고, lab 4의
정리 과정에서 부하 생성기가 제거되었으니, 둘 다 되살려야 한다는 점을 유념하세요:

```bash
export KUBECONFIG=~/lab.kubeconfig          # 위와 같은 접근 파일

# apply = "클러스터를 파일에 기술된 상태로 만들어라". 두 파일 모두 이웃 lab의 폴더에 있으므로
# 경로가 `../`로 시작합니다 — 다시 타이핑할 필요가 없습니다.
kubectl apply -f ../03-scale/hpa.yaml       # rickroll의 오토스케일링 규칙
kubectl apply -f ../03-scale/fortio.yaml    # 부하 생성기

# rollout status = "터미널을 붙잡고 있다가 롤아웃이 끝나면 알려 줘".
# deployment/fortio — 객체 유형과 그 이름. 생성기가 올라오면 명령이 `successfully rolled out`
# 줄과 함께 프롬프트를 돌려줍니다.
kubectl rollout status deployment/fortio
```

`kubectl get hpa rickroll`이 `<unknown>` 대신 퍼센트를 보여 줄 때까지 기다립니다. `hpa`는
오토스케일링 객체인 `HorizontalPodAutoscaler`의 약칭입니다. 여기에는 몇 분이 걸립니다. 그다음
생성기의 포트를 포워딩하고 lab 3에서와 같은 부하를 걸어 줍니다. 그러지 않으면 오토스케일링 계단이
나타나지 않습니다:

```bash
# port-forward = 노트북에서 클러스터 안으로 터널을 뚫습니다. 명령이 실행되는 동안,
# localhost:8081로 보낸 요청이 부하 생성기에 도달합니다.
#   svc/fortio    대상: fortio라는 이름의 service(pod가 아님)
#   8081:8080     왼쪽은 당신의 노트북 위의 포트, 오른쪽은 service 내부의 포트
# 창을 닫지 마세요: 터널은 명령이 실행되는 딱 그동안만 살아 있습니다.
kubectl port-forward svc/fortio 8081:8080
```

<http://localhost:8081/fortio/>에서: **URL** `http://rickroll/`, **QPS** `1200`,
**Duration** `90s`, **Connections** `80`. 끝나고 몇 분 뒤에 이곳으로 돌아오세요 — 데이터가
거기 있을 것입니다.

⚠️ 이런 상황에 빠지지 않으려면, 클러스터를 만드는 바로 그 순간에 `Monitoring agents`를 켜세요 —
lab 0의 파라미터 표에 별도의 항목으로 있습니다.

<summary><b>거기서 정확히 무엇이 실행되고, 수집된 데이터가 어디로 가는가</b></summary>

당신 클러스터의 `cozy-monitoring` namespace에서는 다음이 실행됩니다:

| 무엇이 | 무엇을 하는가 |
|---|---|
| `vmagent` | 30초마다 메트릭 소스를 폴링하고 수집한 것을 테넌트로 보냅니다 |
| `kube-state-metrics` | 클러스터 객체의 상태를 메트릭으로 바꿉니다: 복제본이 몇 개인지, Pod가 어떤 상태인지 |
| `node-exporter` | 노드 자체의 메트릭: CPU, 메모리, 디스크, 네트워크 |
| `fluent-bit` | 컨테이너 로그를 수집해 테넌트로 보냅니다 |
| `metrics-server` | **모니터링의 일부가 아님**: 클러스터와 함께 설치되며 `kubectl top`과 오토스케일링에 현재 값을 공급합니다. 아무것도 저장하지 않고 메트릭 수집에는 관여하지 않습니다 |

주의: **여기에는 저장소가 없습니다**. 수집된 모든 것은 네트워크를 통해 즉시 테넌트로, Grafana 옆의
공유 메트릭 저장소로 보내집니다. 이는 의도적입니다. `lab` 클러스터는 일회용이라 당신이 삭제할
것이지만, 그것이 어떻게 동작했는지에 대한 기록은 그 삭제보다 오래 살아남아야 하기 때문입니다.

수집기가 데이터를 보내는 주소를 보려면:

```bash
# get vmagent = "수집기 객체를 보여 줘". 익숙한 표 대신 그 기술(description)에서 필드 하나만
# 요청합니다 — -o jsonpath 문법은 어떤 클러스터 객체에도 통합니다:
#   .items[0]                  찾은 첫 번째(그리고 여기서는 유일한) 수집기
#   .spec.remoteWrite[0].url   메트릭을 넘겨 주는 주소
#   {"\n"}                     줄바꿈, 없으면 출력이 프롬프트에 붙어 버립니다
kubectl get vmagent -n cozy-monitoring \
  -o jsonpath='{.items[0].spec.remoteWrite[0].url}{"\n"}'
```

```
http://vminsert-shortterm.tenant-workshopXX.svc.cozy.local:8480/insert/0/prometheus
```

이 주소는 당신의 테넌트를 가리킵니다. lab 12의 가상 머신이 애플리케이션과 통신할 때 썼던 것과 같은
메커니즘입니다: 평범한 주소들 사이의 평범한 네트워크입니다.

</details>

## 2단계. 테넌트의 Grafana 열기

📍 **위치:** 브라우저에서.

주소는 당신의 테넌트 호스트의 `grafana` 서브도메인입니다:

```
https://grafana.<your tenant host>
```

정확한 주소는 대시보드에 적혀 있습니다: 당신의 테넌트 → `Monitoring` 앱 → `Ingress` 탭. Ingress는
서비스를 도메인 이름 아래 외부로 공개하는 규칙으로, 가장 가까운 유사물은 로드 밸런서의 항목이며 다만
같은 클러스터 안에서 기술된다는 점이 다릅니다. 주소는 호스트 이름까지 포함해 온전히 거기 있습니다.

두 번째 장소는 바로 이 lab의 `check.sh` 출력입니다: "Grafana for your metrics"라는 줄입니다.
스크립트가 그 동일한 ingress에서 주소를 뽑아내므로, 손으로 타이핑할 필요가 없습니다.

⚠️ **당신의 테넌트에 `Monitoring` 앱이 없다면** — 당신에게는 자체 Grafana도 없다는 뜻이고,
메트릭은 상위 테넌트의 모니터링으로 갑니다. 확실한 방법은 카탈로그(`Administration` 섹션)에서
`Monitoring`을 배포하는 것입니다: 주소가 당신 자신의 앱의 `Ingress` 탭에 나타나고, 아래의 모든
쿼리가 동작할 것입니다. `check.sh`도 남의 모니터링을 찾아내어 그것이 실행되는 namespace 이름을
알려 주지만, 그 namespace에 접근 권한이 있어야만 그것을 열 수 있습니다.

**로그인 방법.** 로그인은 `admin`입니다. 비밀번호는 `grafana-admin-password` Secret에 있습니다:
대시보드 → `Monitoring` 앱 → `Secrets` 탭 → `password` 키 → `Reveal`.

테넌트로서는 `kubectl`이 이 Secret에 대한 접근을 주지 않으므로(core Secret은 당신에게 보이지 않습니다), 대시보드를 통해 가세요.

당신의 모니터링이 상위의 것이라면 이 Secret은 손이 닿지 않는 곳에 있습니다 — 그럴 때는 위에서
설명한 대로 자신의 `Monitoring` 앱을 배포하거나, 테스트베드를 운영하는 사람에게 접근을 요청하세요.

들어가고 나면 **Explore**를 엽니다 — 대시보드를 저장하지 않고 일회성 쿼리를 하는 섹션입니다.
데이터 소스 드롭다운에서 **`vm-shortterm`**을 선택합니다(기본값이기도 합니다).

⚠️ **쿼리 필드를 `Code` 모드로 전환하세요.** Grafana는 Explore를 빌더(`Builder`)로 엽니다 —
쿼리 텍스트를 입력할 곳이 없는, 드롭다운으로 된 폼입니다. `Builder | Code` 토글은 입력 필드 위,
오른쪽에 있습니다. 아래의 모든 쿼리는 `Code`에서 입력합니다.

<details>
<summary><b>목록의 데이터 소스들이 무엇인가</b></summary>

| 소스 | 내부에 무엇이 | 보관 |
|---|---|---|
| `vm-shortterm` | 고해상도 메트릭 | 3일 |
| `vm-longterm` | 동일한 메트릭을 솎아낸 것 | 14일 |
| `vlogs-generic` | 컨테이너 로그 | 1일 |

메트릭 저장소가 하나가 아니라 둘인 것은 해상도와 용량 사이의 절충입니다. 인시던트를 조사할 때는
30초마다 볼 수 있는 `shortterm`을 씁니다. "2주 전에 어떻게 동작했는가"라는 질문에는 해상도는 더
거칠지만 깊이는 더 깊은 `longterm`으로 답합니다.

20초 간격 데이터는 하루, 시간 단위 데이터는 1년을 사는 vCenter의 통계 레벨과 정확히 같은 논리입니다.

⚠️ **`vlogs-generic`은 로그이고, 거기서는 쿼리 언어가 다릅니다.** PromQL은 여기서 동작하지
않으며, 이것은 버그가 아닙니다: 로그에는 자신만의 문법이 있습니다. 소스를 바꾸고 같은 쿼리를
붙여넣느라 시간을 낭비하지 마세요.

</details>

⚠️ **테넌트 Grafana에는 기성 Pod 대시보드가 없습니다.** 목록에는 데이터베이스, ingress, 큐를 위한
대시보드가 있습니다 — 매니지드 서비스에 속하는 것들입니다. "Pod와 노드" 수준의 대시보드는 테넌트
세트의 일부가 아닙니다. 그러니 여기서부터는 Explore에서 작업하며 쿼리를 손으로 씁니다. 이것은
vCenter의 기성 Performance 탭보다 덜 편리하며, 그렇지 않은 척할 이유가 없습니다.

## 3단계. 당신의 Pod들을 찾기

📍 **위치:** Grafana의 Explore, `vm-shortterm` 소스에서.

가장 투박한 질문부터 시작합시다: 클러스터에 도대체 어떤 Pod들이 보이는가. 쿼리는 짧지만 낯선 부분이
셋 있습니다 — 입력하기 전에 분해 설명을 펼쳐 보세요.

<details>
<summary><b>쿼리를 부분별로 분해하기</b></summary>

```promql
container_cpu_usage_seconds_total
```

메트릭 이름입니다. 이것은 카운터입니다: 컨테이너가 시작된 이후 CPU 시간을 몇 초나 썼는지. 오직
올라가기만 합니다 — 컨테이너가 재시작할 때까지, 재시작 후에는 0부터 다시 시작합니다.

그 자체로는 쓸모없습니다: "Pod가 CPU를 4718초 썼다"는 아무것도 말해 주지 않습니다. 이 메트릭은
`rate()`를 거친 뒤에야 유용해지며, 그것은 다음 단계에서 다룹니다.

```promql
{cluster="kubernetes-lab", namespace="default"}
```

레이블에 의한 필터입니다. 여기 두 레이블 모두 중요합니다.

`cluster` — 플랫폼이 아는 당신 클러스터의 이름입니다. 이것은 `lab`과 **같지 않습니다**:
애플리케이션은 `lab`이라 불리지만, 그것을 배포하는 릴리스는 `kubernetes-lab`이고, 레이블에
들어가는 것은 그 릴리스 이름입니다. 이것은 누구나 걸려 넘어지는 첫 번째 함정입니다. 당신 것이 뭐라고
불리는지 확인하려면: 값을 지우고 Grafana의 자동완성이 무엇을 제안하는지 보세요.

이 레이블이 필요한 이유는, 하나의 저장소가 당신의 **모든** 클러스터와 매니지드 서비스의 메트릭을
담고 있기 때문입니다. 필터가 없으면 테넌트 안의 모든 것이 뒤섞여 나옵니다.

`namespace` — `lab` 클러스터 **내부**의 namespace입니다. 첫 lab의 앱은 `default`에 배포되었으므로,
여기서도 `default`입니다. 테넌트 namespace(`tenant-workshopXX`)와 혼동하지 마세요 — 이 둘은 서로
다른 클러스터에 있는 서로 다른 것입니다. 테넌트 namespace는 `tenant` 레이블에 있습니다.

```promql
count by (pod) ( ... )
```

`pod` 레이블로 묶고 각 그룹에 몇 개의 시계열이 들어갔는지 셉니다. 우리가 관심 있는 것은 숫자 자체가
아니라, 그 결과로 나오는 `pod` 값들의 목록입니다.

</details>

```promql
# count by (pod) — 매칭된 시계열을 pod 레이블로 쪼개고 각 그룹에 시계열이 몇 개인지 셉니다.
# 숫자 자체는 중요하지 않습니다: 우리가 원하는 것은 그 결과로 나오는 pod 이름들의 목록입니다.
count by (pod) (
  # 메트릭 이름 — 컨테이너 CPU 시간 카운터
  container_cpu_usage_seconds_total{
    cluster="kubernetes-lab",   # 당신의 클러스터: 여기는 릴리스 이름이지 앱 이름 lab이 아닙니다
    namespace="default"         # rickroll이 배포된, lab 클러스터 내부의 namespace
  }
)
```

**보여야 할 것:** 뷰를 Graph에서 **Table**로 바꾸세요 — 목록은 그렇게 볼 때 더 잘 읽힙니다. 표에는
`rickroll-...`, `fortio-...`가, 그리고 lab 11을 했다면 `propusk-build-...`가 있을 것입니다.

## 4단계. CPU 스파이크 찾기

앞 단계의 카운터는 날것 그대로는 읽을 수 없습니다. 이것을 Pod의 request와 비교하고 `kubectl top`이
보여 주는 값과도 비교할 수 있는 양으로 — 소비된 코어 수로 — 바꿔 봅시다. `rate()`가 그 과정에서 무엇을
하는지, 그리고 쿼리의 두 추가 조건이 어디서 오는지는 아래 분해 설명에 있습니다. 입력하기 전에 펼쳐 보세요.

<details>
<summary><b>쿼리를 부분별로 분해하기</b></summary>

```promql
rate( ... [2m])
```

`rate`는 카운터를 받아 2분 창(window)으로 평균을 내어 **초당 증가율**을 계산합니다. CPU 시간
메트릭에 대해 이것은 아주 편리한 양을 줍니다: "초당 CPU가 몇 초", 즉 코어가 몇 개나 소비되고
있었는가. `0.24`는 코어 한 개의 24%, 즉 millicore로 `240m`을 뜻합니다.

`[2m]` 창은 절충입니다. 더 작은 창(`[30s]`) — 그래프가 들쭉날쭉하고 데이터가 성길 때 끊어집니다.
더 큰 창(`[5m]`) — 스파이크가 뭉개지고 낮은 봉우리는 아예 사라질 수 있습니다. `[2m]`으로 시작해
거기서부터 조정하세요.

⚠️ **창은 수집 간격의 최소 두 배여야 합니다.** 수집은 30초마다 일어나므로 `[1m]` 미만은 설정할 수
없습니다 — 창 안에 점이 하나만 들어가고, 점 하나로는 rate를 계산할 수 없어 그래프가 비어 버립니다.
이것이 "아무것도 안 그려져요"의 가장 흔한 원인입니다.

```promql
pod=~"rickroll-.*"
```

`=~` — 정확한 일치가 아니라 정규식에 의한 비교입니다. 여기서는 정확한 일치가 통하지 않습니다: Pod
이름에는 무작위 꼬리가 붙고 재생성될 때마다 바뀝니다.

```promql
container!=""
```

컨테이너 이름이 없는 시계열을 버립니다. 그런 시계열이 존재합니다: 그것은 Pod 전체에 대한 집계이고,
버리지 않으면 모든 Pod가 두 번씩 세어져 그래프가 딱 두 배의 진실을 보여 줍니다. 또 하나의 전형적인
함정입니다.

```promql
sum by (pod) ( ... )
```

남은 모든 것을 Pod별로 합칩니다. Pod에는 컨테이너가 여럿 있을 수 있습니다. 우리는 Pod 전체에
관심이 있습니다.

</details>

```promql
# rate(...[2m]) — 카운터의 초당 증가율을 2분 창으로 평균 낸 것.
# CPU 시간에 대해서는 "코어가 몇 개나 소비되고 있었는가"로 읽힙니다:
# 0.24 — 코어 한 개의 24%, 즉 240m.
sum by (pod) (     # pod의 컨테이너들을 합칩니다: 컨테이너당이 아니라 pod당 한 줄
  rate(container_cpu_usage_seconds_total{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*",  # =~ 정규식에 의한 비교: pod 이름의 꼬리는 무작위입니다
    container!=""        # pod 전체 합계 시계열을 버립니다, 안 그러면 모든 게 두 배가 됩니다
  }[2m])
)
```

시간 범위를 lab 3을 하던 때로 설정하세요 — 예를 들어 최근 3시간.

**보여야 할 것:** 0 바로 위의 평평한 선, 그다음 부하가 지속되는 동안의 가파른 상승, 그다음 다시
하강. 복제본이 여럿 생겼다면 선도 여럿일 것이고, 그것들은 한꺼번에가 아니라 Pod가 생성되는 대로
나타납니다.

## 5단계. 오토스케일링 계단 찾기

스파이크는 찾았습니다. 이제 클러스터가 그것에 어떻게 반응했는지 봅시다: 각 순간에 애플리케이션의
복제본을 몇 개나 돌리고 있었고, 몇 개를 유지하려 했는지. 이 둘은 서로 다른 숫자이고, 그 둘 사이의
차이가 이 단계에서 가장 흥미로운 지점입니다. 이 숫자들이 어디서 오는지는 아래 분해 설명에 있습니다.

<details>
<summary><b>이 메트릭들이 어디서 오는지, 그리고 desired가 current와 어떻게 다른지</b></summary>

이 메트릭들은 애플리케이션이 아니라 `kube-state-metrics`에서 옵니다 — API를 통해 클러스터 객체를
읽어 그 필드들을 숫자로 바꿉니다. `horizontalpodautoscaler` 레이블은 HPA 객체(`HorizontalPodAutoscaler`,
lab 3의 바로 그 오토스케일링 규칙)의 이름이고, `deployment` 레이블은 Deployment의 이름, 즉
"애플리케이션 복제본을 이러이러하게 몇 개 유지하라"는 기술의 이름이며, 모든 객체 유형에 대해 이런
식입니다.

`desired` — 부하로부터 계산해 낸 결과, 오토스케일링이 지금 **원하는** 복제본 수. `current` —
**실제로** 실행 중인 수. 이 둘 사이에는 언제나 간극이 있습니다: Pod는 즉시 생성되지 않습니다.

`desired`가 오랫동안 `current`보다 높게 유지된다면, 복제본이 생성되지 못하고 있다는 뜻입니다. 원인은
거의 항상 같습니다: 노드에 자리가 충분치 않아 새 Pod가 `Pending`에 걸려 있는 것입니다. 바로 당신이
lab 11에서 마주쳤던 상황입니다.

함께 보면 유용한 것:

```promql
# rickroll 복제본이 총 몇 개 생성되었는지
kube_deployment_status_replicas{cluster="kubernetes-lab", deployment="rickroll"}
# 그중 몇 개가 readiness 체크를 통과해 이미 트래픽을 받고 있는지
kube_deployment_status_replicas_available{cluster="kubernetes-lab", deployment="rickroll"}
```

새 버전을 롤아웃하는 동안 이 둘이 벌어지는 것은, 바로 새 복제본이 readiness 체크를 통과하는 동안의
그 멈춤입니다.

</details>

```promql
# ..._status_current_replicas — 지금 이 순간 rickroll 복제본이 몇 개 실행 중인지.
# 이 숫자는 애플리케이션이 아니라 kube-state-metrics가 읽은 HPA 객체에서 옵니다.
kube_horizontalpodautoscaler_status_current_replicas{
  cluster="kubernetes-lab",             # 당신의 lab 클러스터만
  horizontalpodautoscaler="rickroll"    # lab 3의 오토스케일링 객체 이름
}
```

그리고 그 옆에, 두 번째 쿼리로:

```promql
# ..._status_desired_replicas — 오토스케일링이 부하를 근거로 지금 갖고자 하는 복제본 수.
# current가 desired에 뒤처지는 것이 바로 pod 생성에 걸리는 시간입니다.
kube_horizontalpodautoscaler_status_desired_replicas{
  cluster="kubernetes-lab",
  horizontalpodautoscaler="rickroll"
}
```

**보여야 할 것:** 계단 모양의 선. 하나였다가, 셋이 되고, 다섯이나 여섯이 되었다가, 부하가 잦아든 뒤
약 1분의 지연을 두고 — 다시 내려갑니다.

이것을 앞 단계의 CPU 소비 그래프 위에 겹쳐 보세요: Explore에서는 `+ Add query` 버튼으로 두 번째
쿼리를 추가합니다. 계단이 스파이크보다 수십 초 뒤처져 **뒤따라간다**는 것을 볼 수 있습니다: 먼저
CPU가 오르고, 그다음 오토스케일링이 그것을 알아채고 반응했습니다. 이것이 "왜 사용자들이 결국 느려짐을
알아챌 수 있었는가"라는 질문에 대한 답입니다.

## 6단계. 같은 것을 오토스케일링의 눈으로 보기

오토스케일링은 절대적인 소비가 아니라 **`requests`에 대한 비율**을 봅니다. `requests`는 Pod의 리소스
요청입니다: 스케줄러가 그 Pod를 위해 노드에 CPU와 메모리를 얼마나 예약하는가, Pod가 그 리소스를 쓰든
안 쓰든 상관없이. 가장 가까운 유사물은 vSphere의 예약(reservation)입니다.

결정이 내려지는 바로 그 양을 봅시다. 쿼리는 나눗셈 기호로 구분된 두 부분으로 이루어집니다: 위에는
실제 소비, 아래에는 request입니다.

```promql
# 위쪽 부분 — pod의 실제 CPU 소비. 위와 같은 쿼리입니다.
sum by (pod) (
  rate(container_cpu_usage_seconds_total{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*", container!=""
  }[2m])
)
/
# 아래 부분 — pod가 얼마나 요청했는지. 나눗셈의 결과는 request 대비 비율입니다: 1은
# "요청한 만큼 정확히 소비 중"을, 0.5는 요청한 것의 절반을 뜻합니다.
sum by (pod) (
  kube_pod_container_resource_requests{
    cluster="kubernetes-lab", namespace="default",
    pod=~"rickroll-.*",
    resource="cpu"     # 이 메트릭에는 memory 시계열도 있습니다 — CPU만 남깁니다
  }
)
```

**보여야 할 것:** 거의 항상 낮게 흐르다가 부하가 지속되는 동안 올라가는 선. 이 그래프에서 값 1은
"Pod가 요청한 만큼 정확히 소비한다"를 뜻합니다.

lab 3의 `hpa.yaml`에는 `averageUtilization: 50`이 있고, `rickroll.yaml`에는 `requests.cpu: 20m`이
있습니다. 즉 트리거 임계값은 Pod당 10 millicore이고, 그래프에서는 `0.5` 지점입니다. 선이 그것을
넘어간 순간을 찾아, 앞 단계의 계단과 대조해 보세요: 그 둘 사이에는 바로 그 수십 초가 있을 것입니다.

⚠️ PromQL에서 두 식을 나누는 것은 **모든** 레이블의 매칭으로 동작합니다. 여기서는 양쪽이 `by (pod)`로
묶여 있고 묶은 뒤에 다른 레이블이 남지 않으므로 맞아떨어집니다. 만약 레이블 집합이 달랐다면 결과는
비어 나왔을 것입니다 — 오류도 경고도 없이, 빈 그래프. 이것이 이 언어의 가장 음험한 특성입니다.

## 7단계. 일상적으로 쓰는 세 가지 쿼리

이것들은 저장해 둘 만합니다 — 매일 마주치는 대부분의 질문을 커버합니다.

**클러스터에서 누가 CPU를 가장 많이 소비하는가, 상위 10:**

```promql
# topk(10, ...) — 값이 가장 큰 시계열 열 개만 남깁니다.
# by (namespace, pod)로 묶으면 답에 namespace가 더해집니다: 누구의 pod인지 볼 수 있습니다.
# [5m] 창은 앞 단계들보다 넓습니다: 스파이크의 모양이 아니라 평균 수준을 원하기 때문입니다.
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{cluster="kubernetes-lab", container!=""}[5m])
  )
)
```

**Pod별 메모리(카운터가 아니므로 `rate` 없음):**

```promql
# container_memory_working_set_bytes — 카운터가 아니라 순간값입니다: 이 순간에 이만큼의
# 바이트가 점유되어 있다. 여기서 rate()는 "초당 바이트"라는 말도 안 되는 값을 줍니다.
sum by (pod) (
  container_memory_working_set_bytes{
    cluster="kubernetes-lab", namespace="default", container!=""
  }
)
```

⚠️ 특별히 `working_set`이지, `container_memory_usage_bytes`가 아닙니다. 후자는 파일 캐시를
포함하는데, 이 캐시는 압박이 오면 커널이 내어 주므로, 애플리케이션의 실제 필요와는 아무 상관없는
수치로 사람들을 자주 놀라게 합니다. 메모리 때문에 Pod를 죽이는 결정도 `working_set`을 근거로
내려집니다.

**리소스가 얼마나 예약되어 있는가 대 실제로 얼마나 쓰이는가:**

```promql
# sum without by — 모든 것을 하나의 숫자로 합칩니다: 클러스터의 모든 pod에 CPU가 얼마나
# 예약되어 있는가. 이것은 소비가 아니라 request입니다: 예약되어 놀고 있는 것도 합계에 들어갑니다.
sum(kube_pod_container_resource_requests{cluster="kubernetes-lab", resource="cpu"})
```

이 숫자를 첫 번째 쿼리의 합계와 비교하세요. "예약된" 것과 "쓰인" 것의 차이가, 당신이 값을 치르고도
아무것도 돌려받지 못하는 몫입니다. vSphere의 예약(reservation)에 관한 이야기와 똑같은 대화이며, 다만
여기서는 그것을 그래프로 볼 수 있습니다.

lab 11을 했다면, 하는 김에 Android 빌드도 한번 보세요 — 뚜렷하게 보입니다:

```promql
# 같은 rate이지만 build pod에 필터를 겁니다. sum without by (pod) — 빌드가 pod를 몇 개
# 올리든 빌드 전체에 한 줄.
sum(rate(container_cpu_usage_seconds_total{
  cluster="kubernetes-lab", pod=~"propusk-build-.*", container!=""
}[2m]))
```

한 개 반에서 두 개 코어 수준의 평평한 고원(plateau)이 20분, 그다음 0으로 뚝. 이것이 Job이 그래프에서
보이는 모습입니다 — 일을 끝까지 수행하고 마치는 일회성 작업입니다. 계속 돌아가도록 유지되는
애플리케이션과 달리, 그 선에는 끝이 있습니다.

## 8단계. 로그를 들여다보기

데이터 소스를 **`vlogs-generic`**으로 전환합니다. 여기서는 쿼리 언어가 다릅니다: PromQL에서는
숫자 시계열을 기술했지만, LogsQL에서는 필드 값으로 줄(line)을 선택합니다.

아래 쿼리는 이렇게 읽힙니다: "`kubernetes_namespace_name` 필드가 `default`와 같고
`kubernetes_pod_name` 필드가 `rickroll`로 시작하는 줄을 보여 줘". 끝의 별표는 Pod 이름의 바로 그
무작위 꼬리, PromQL에서 `=~`를 쓰게 만들었던 그것입니다.

```logsql
kubernetes_namespace_name:default AND kubernetes_pod_name:rickroll*
```

시간을 맞추세요: CPU 소비 그래프에서 찾아낸 스파이크의 그 분(minute)을 잡아, 그에 해당하는 로그를
보세요. 그 분에는 nginx의 요청 기록이 스파이크를 이룰 것입니다.

**이것이 우리가 메트릭과 로그를 나눈 이유입니다.** 그래프로는 세 시간 중에서 그 순간을 1초 만에
찾아냈습니다. 그 분의 로그로는 정확히 무슨 일이 일어나고 있었는지를 찾아냈습니다. 반대 방향으로는
통하지 않습니다: 로그를 스크롤하며 "언제 상황이 나빠졌는지"를 찾는 일은 아주 오래 걸릴 수 있습니다.

정리할 것은 없습니다. `Monitoring agents` 애드온은 소비가 적고 워크숍이 끝날 때까지 유용할
것입니다 — 켜 둔 채로 두세요.

메트릭은 스스로 지워집니다: 기본값으로 `shortterm`은 3일, `longterm`은 14일, 로그는 하루를

## 이제 우리가 할 수 있는 것

- 왜 메트릭이 끊임없이 수집되는지, 그리고 로그와 어떻게 다른지 설명하기
- 클러스터의 수집이 켜져 있는지, 그리고 정확히 어디로 보내는지 확인하기
- 당신의 Pod와 그 소비를 찾아내는 쿼리를 작성하고, `container!=""`에 걸려 넘어지지 않기
- 그래프에서 부하 스파이크와 그에 대한 오토스케일링의 반응 찾기
- `desired`와 `current`의 벌어짐을 자리가 부족하다는 신호로 읽기

## 그리고 vSphere에서라면 이것은

vCenter는 호스트와 가상 머신의 카운터를 보여 줍니다 — 질문이 가상 머신에 관한 것인 한 그것으로
충분합니다. 질문이 "그 서비스에 무슨 일이 있었나"가 되는 순간, vRealize Operations가 필요합니다:
별도의 제품, 별도의 라이선스, 별도의 설치, 그것을 돌릴 별도의 가상 머신들, 그리고 그것을 구성할 줄
아는 별도의 사람.

여기서는 메트릭과 로그 수집이 애플리케이션에서 체크박스 하나로 켜는 애드온이고, Grafana는 그
저장소와 함께 카탈로그 항목으로 올라옵니다. 라이선스도, 도입 프로젝트도 없습니다.

**vSphere가 더 편리한 지점, 솔직히.** 설치 직후 바로 동작하는 것에 관해서라면 vCenter가 압도적으로
이기며, 우리는 바로 이 lab에서 그것을 보았습니다:

| | vSphere | Cozystack |
|---|---|---|
| 설치 직후의 그래프 | 모든 객체의 Performance 탭 | 애드온을 켜고 Grafana를 열어야 함 |
| 기성 뷰 | 어떤 VM과 호스트에도 있음 | 테넌트에서는 — 매니지드 서비스에 대해서만 |
| 필요한 카운터 찾기 | 목록에서 마우스로 고름 | PromQL로 쿼리를 씀 |
| 진입 장벽 | 한 시간 | 며칠, PromQL을 배워야 함 |
| 숙달한 뒤의 깊이 | 카운터 집합에 의해 제한됨 | 어떤 메트릭과 레이블이 수집되는지에 의해 제한됨 |

PromQL은 언어이고, 정말로 배워야 합니다. 처음 두 주 동안은 남의 쿼리를 베끼면서도 왜 그래프가
비어 있는지 이해하지 못할 것입니다. 그 대가로 vCenter에는 아예 없는 것을 얻습니다: 임의의 질문을
던지고 — "이 애플리케이션의 Pod 소비를 그 예약 대비로, 노드별로 묶어서, 지난 화요일에 대해 보여 줘" —
"그런 카운터는 없습니다"가 아니라 답을 받는 능력입니다.
