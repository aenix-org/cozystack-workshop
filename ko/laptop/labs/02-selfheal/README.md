## 왜 중요한가

곧 여러분은 「출입증」 서비스를 책임지게 됩니다. 보안팀은 아침 7시에 방문객 명단을 확인하는데,
거기서는 「지금 재부팅 중이니 잠시 기다려 주세요」가 통하지 않습니다. 그런 약속을 떠맡기 전에,
아무것도 걸려 있지 않은 지금 — 클러스터가 스스로 무엇을 하고, 무엇을 여러분이 직접 해야 하는지 정확히 알아 두는 편이 좋습니다.

Kubernetes의 가장 요란한 약속인 자가 복구를 파헤쳐 봅시다. 실행 중인 애플리케이션 복사본을
삭제하고, 그것이 사라져 있는 시간을 시계로 재 보겠습니다. 그런 다음 다른 무언가를 삭제하면 —
복사본이 돌아오지 않는 것을 보게 됩니다. 이 두 경우의 차이가 바로 이 랩의 내용입니다.

## 1단계. 우리가 가진 것을 살펴본다

📍 **위치:** 노트북에서.

`rickroll` 애플리케이션은 이미 실행 중입니다. 무언가를 망가뜨리기 전에, 그것이 어떤 객체들로
이루어져 있는지 살펴봅시다: 명령 하나로 클러스터에 세 가지 종류의 개체를 한꺼번에 물어봅니다.

```bash
# KUBECONFIG — 클러스터의 주소와 로그인 자격 증명이 담긴 파일의 경로입니다.
# 이 변수가 설정되기 전까지 kubectl은 노트북 자체에서 클러스터를 찾다가 찾지 못합니다.
export KUBECONFIG=~/lab.kubeconfig

# get = 「무엇이 있는지 보여 줘」. 쉼표로 구분하여 세 종류의 객체를 한꺼번에 나열합니다.
#   -l app=rickroll   app=rickroll 레이블이 붙은 것만 보여 줍니다 — 즉 클러스터의
#                     전체 내용이 아니라 우리 애플리케이션만
kubectl get deployment,replicaset,pods -l app=rickroll
```

**여러분이 봐야 할 것** — 세 객체마다 한 줄씩:

```
NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/rickroll   1/1     1            1           14m

NAME                                  DESIRED   CURRENT   READY   AGE
replicaset.apps/rickroll-6f4b9c8d57   1         1         1       14m

NAME                             READY   STATUS    AGE
pod/rickroll-6f4b9c8d57-xk2mp    1/1     Running   14m
```

⚠️ **`replicaset` 줄이 하나보다 많을 수 있습니다.** 새 버전을 롤아웃할 때마다 이전 세트가
이력에 남습니다 — 열에 0이 찍힌 채로. 살아 있는 것은 1이 찍힌 줄이고, 나머지는 롤백할 곳이
있도록 남아 있습니다.

객체가 셋입니다. 랩 1의 매니페스트에서는 Deployment 하나만 기술했는데도 말이죠. 나머지 둘은
클러스터가 스스로 만들었으며, 이것은 겉치레 세부사항이 아닙니다 — 이후의 모든 것이 이 사슬에 달려 있습니다.

<details>
<summary><b>사슬 풀어 보기: 누가 누구를 만들었고, 왜</b></summary>

이름을 보세요. Pod의 이름은 ReplicaSet의 이름에 무작위 문자 다섯 개를 더한 것이고,
ReplicaSet의 이름은 Deployment의 이름에 해시를 더한 것입니다. 이렇게 사슬이 만들어집니다.

**Deployment**은 여러분의 의도를 통째로 담습니다: 어떤 이미지인지, 복사본은 몇 개인지, 어떻게
업데이트할지. 그것은 Pod를 직접 지켜보지 않습니다 — ReplicaSet을 지켜봅니다.

**ReplicaSet**은 단 하나의 생각만 담습니다: 「`app=rickroll` 레이블이 붙은 Pod가 정확히
이만큼 있어야 한다」. 그게 전부입니다. 이미지나 버전에 대해서는 아무것도 모릅니다.

**Pod**는 실행 중인 복사본입니다.

이것이 추측이 아님을 이렇게 확인할 수 있습니다:

```bash
# 기본 kubectl 표는 ownerReferences 필드를 보여 주지 않습니다 — 명시적으로 요청해야 합니다.
#   -o jsonpath=...   「서버 응답에서 이 필드들을 꺼내 이렇게 출력해」
# 표현식 안에서: range .items[*] — 찾은 모든 Pod를 순회, .metadata.name —
# Pod의 이름, ownerReferences[0].kind와 .name — 그것을 만든 대상의 종류와 이름.
kubectl get pods -l app=rickroll -o jsonpath='{range .items[*]}{.metadata.name}{"  <- "}{.metadata.ownerReferences[0].kind}{"/"}{.metadata.ownerReferences[0].name}{"\n"}{end}'
```

출력:

```
rickroll-6f4b9c8d57-xk2mp  <- ReplicaSet/rickroll-6f4b9c8d57
```

`ownerReferences` 필드는 「이 객체가 나를 만들었다」는 기록입니다. ReplicaSet에도 같은 기록이
있는데, 거기서는 Deployment을 가리킵니다.

객체 하나가 아니라 세 층인 이유: 각 층이 서로 다른 것을 책임지기 때문입니다. 랩 4에서 새 버전을
롤아웃할 때 Deployment은 새 버전을 위한 **두 번째** ReplicaSet을 만들고, 옛 세트에서 새 세트로
복사본을 하나씩 옮기기 시작합니다. 그동안 옛 ReplicaSet은 어디로도 사라지지 않습니다 — 바로
그것이 명령 하나로 롤백할 수 있게 해 줍니다.

기억해 둘 만한 부수적 사실: 부모를 삭제하면 그 자식들이 함께 딸려 갑니다. ReplicaSet을 손으로
삭제하면 — Deployment이 1초 안에 새것을 만듭니다. Deployment을 삭제하면 — 모든 것이 사라집니다.
두 번째 경우는 랩 마지막에 시험해 보겠습니다.

## 2단계. 복사본을 죽이고 시간을 잰다

이제 Pod를 삭제하겠습니다. 전원을 끄는 것도, 재부팅하는 것도 아닙니다 — 마치 누군가 가상 머신에서
Delete from Disk를 클릭한 것처럼 완전히 삭제합니다.

**이제 일어날 일:** 아래 명령은 현재 복사본의 이름을 기억한 뒤 그것을 삭제하고, 그다음 1초에
한 번씩 클러스터에 **다른** 이름의 복사본이 Running 상태로 나타났는지 물어봅니다. 나타나는 즉시,
그것이 얼마나 걸렸는지 출력합니다.

```bash
# items[0].metadata.name — 목록의 첫 번째 Pod 이름입니다. 이것을 POD 변수에 저장합니다:
# 그러지 않으면 나중에 옛 복사본과 새 복사본을 구별할 수 없습니다.
POD=$(kubectl get pods -l app=rickroll -o jsonpath='{.items[0].metadata.name}')
echo "killing: $POD"

# date +%s — 현재 시각을 초 단위로. 이것이 우리의 스톱워치입니다: 삭제 전에 기록해 두고,
# 맨 마지막에 새로 잰 값에서 뺍니다.
START=$(date +%s)

# delete pod — 복사본을 완전히 삭제합니다.
#   --wait=false   Pod가 완전히 사라질 때까지 기다리지 않고 즉시 제어권을 돌려줍니다:
#                  초를 세기 시작해야 하는 것은 이후가 아니라 바로 이 순간부터이기 때문입니다
kubectl delete pod "$POD" --wait=false

# 1초에 한 번씩 Pod 목록을 다시 읽어, 다음이 동시에 성립하는 줄을 찾습니다:
#   $1!=old        이름이 옛것과 일치하지 않음 — 즉 이것은 다른 복사본
#   $2=="1/1"      컨테이너 하나 중 하나가 준비됨
#   $3=="Running"  Pod가 실행 중
#   --no-headers   표 머리글을 출력하지 않아 awk가 데이터만 보게 함
#   2>/dev/null    Pod가 아예 없는 몇 초 동안 오류 메시지를 숨김
while true; do
  NEW=$(kubectl get pods -l app=rickroll --no-headers 2>/dev/null \
        | awk -v old="$POD" '$1!=old && $2=="1/1" && $3=="Running" {print $1; exit}')
  [ -n "$NEW" ] && break
  sleep 1
done
echo "new copy $NEW ready in $(( $(date +%s) - START ))s"
```

**여러분이 봐야 할 것:**

```
killing: rickroll-6f4b9c8d57-xk2mp
pod "rickroll-6f4b9c8d57-xk2mp" deleted
new copy rickroll-6f4b9c8d57-p9wqt ready in 4s
```

4초. 테스트베드에서는 노드가 얼마나 바쁜지에 따라 편차가 2에서 15까지 납니다. 이미지는 이미
노드에 있어 내려받을 것이 없으므로, 모든 것은 프로세스를 시작하고 준비 상태를 확인하는 데 달려 있습니다.

**이름을 눈여겨보세요.** 꼬리가 바뀌었습니다: `xk2mp`가 `p9wqt`가 되었습니다. 이것은 같은
Pod가 재시작된 것이 아니라 — 다른 Pod입니다. 옛것은 이제 어디에도 없습니다. 그것을 고칠 수도,
휴지통에서 되살릴 수도, 그 디스크에 무엇이 있었는지 들여다볼 수도 없습니다.

아무도 무언가를 「복원」하지 않았습니다. ReplicaSet은 초당 여러 번 「주문됨: 1」과 「있음: 0」을
대조하고, 불일치가 있으면 빠진 것을 만듭니다. 복사본이 사라졌고 — 불일치가 생겼고 — 복사본이
만들어졌습니다. 같은 메커니즘은 Pod가 더 중요한 워크로드를 위해 노드에서 축출되었을 때에도,
노드 자체가 다운되었을 때에도, Pod 안의 애플리케이션이 메모리 부족으로 죽었을 때에도 똑같이 작동했을 것입니다.

## 3단계. 결함 내성이 있었는지 확인한다

복사본은 4초 만에 돌아왔습니다. 그렇다면 서비스가 중단되지 않았다는 뜻일까요?

확인해 봅시다. **터미널 창 두 개**가 필요합니다.

📍 **창 1** — 클러스터 안에서, 1초에 한 번씩 Service를 통해 우리 애플리케이션을 찔러 보고
성공 시 점, 오류 시 `X`를 그리는 작은 Pod를 실행합니다:

```bash
export KUBECONFIG=~/lab.kubeconfig

# run = 매니페스트 없이 명령줄에서 곧바로 Pod 하나를 만듭니다.
#   --rm             명령을 중단하는 즉시 Pod를 삭제합니다
#   -it              Pod의 출력이 여러분 화면으로 오고, Ctrl+C로 멈춥니다
#   --restart=Never  복사본은 하나이고 다시 만들 필요가 없습니다: 이것은 서비스가 아니라 도구입니다
#   --image          busybox — wget이 들어 있는 몇 메가바이트짜리 이미지
# -- 뒤의 모든 것은 Pod 안에서 실행됩니다. 주소 http://rickroll은 Service의 이름이며,
# 클러스터 안에서 스스로 애플리케이션의 주소로 바뀝니다.
#   -q               다운로드 통계를 출력하지 않습니다
#   -T 2             응답을 2초 넘게 기다리지 않고, 그러지 않으면 실패로 간주합니다
#   -O /dev/null     응답 본문은 버립니다, 우리에게 중요한 것은 응답이 왔다는 사실뿐입니다
kubectl run pinger --rm -it --restart=Never --image=busybox:1.36 -- \
  sh -c 'while true; do wget -q -T 2 -O /dev/null http://rickroll/healthz \
         && echo "$(date +%T) ." || echo "$(date +%T) X"; sleep 1; done'
```

각 줄에는 타임스탬프가 붙습니다: 이렇게 하면 장애 그 자체뿐 아니라 그것이 **몇 초** 동안
지속됐는지도 보게 됩니다 — 그리고 그것이 바로 이 랩 전체가 노리는 숫자입니다.

⚠️ **백그라운드 실행이 아니라 두 번째 터미널이 필요합니다.** 이 연습의 핵심은 다른 창에서
복사본을 삭제하는 **바로 그 순간** 장애를 보는 것입니다: 십자 표시가 있는 줄이 여러분 눈앞에
나타나야 합니다. 나중에 `kubectl logs`에서 읽을 수도 있지만, 그러면 가장 중요한 것 — 여러분의
행동과 그 결과 사이의 연결이 사라집니다.

노트북이 아니라 클러스터 안에서 하는 이유: `port-forward`는 특정 Pod에 달라붙어 그것과 함께
죽으므로, 어느 쪽이든 장애를 보여 줄 것입니다 — 장애가 없는 곳에서도. 반면 이웃 Pod에서 보내는
`wget`은 Service를 통과합니다, 즉 실제 클라이언트가 하는 것과 정확히 같은 방식으로.

점이 흐르기 시작할 때까지 기다리세요.


<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

앞서 여러분은 **복사본**을 — 즉 사실을 삭제하고 있었습니다. 「복사본이 셋 있어야 한다」는
기록은 그대로 남아 있었고, 현실이 그것과 어긋났으며, 컨트롤러가 그 어긋남을 없앴습니다.

이번에 여러분은 **기록 자체**를 삭제했습니다. 어긋날 대상이 남아 있지 않습니다: 원하는 상태는
「이 애플리케이션은 존재하지 않는다」이고, 실제 상태도 「이 애플리케이션은 존재하지 않는다」입니다.
둘은 일치하고, 컨트롤러는 할 일이 없습니다. 그러는 김에 `ownerReferences` 사슬을 따라,
ReplicaSet과 세 Pod 모두가 Deployment과 함께 떠났습니다.

**교훈은 이 오류보다 넓습니다.** 이 랩에서 통째로 가져갈 만한 규칙:

> Kubernetes는 **사실**의 상실로부터는 여러분을 보호하지만, **의도**의 상실로부터는 전혀 보호해 주지 않습니다.

자가 복구 전체는 어떻게 되어야 하는지에 대한 기록이 온전한 동안에만 정확히 작동합니다. 기록이
바뀌거나 삭제되면, 클러스터는 그것이 무엇이든 새로운 원하는 상태에 현실을 성실하게 그리고 아주
빠르게 맞춥니다. 「정말인가요?」라고 묻지도 않고, 휴지통을 남기지도 않습니다.

실질적 결과는 두 가지이고, 둘 다 딱 한 번 불쾌합니다.

**첫째: 여기서 삭제는 vSphere보다 조용합니다.** Deployment을 없애는 것은 한 줄입니다 —
확인도, 빨간 아이콘이 붙은 「Delete from Disk?」도 없습니다. 클러스터에서 그것을 복원할 수
없습니다: 삭제된 객체는 어디에도 저장되지 않습니다.

**둘째: 유일하게 진짜인 보호책은 의도를 클러스터 바깥에 두는 것입니다.** 매니페스트가 Git에
있고 자동화가 그것을 클러스터로 가져온다면, 우발적 삭제는 자동화가 1분 뒤 저장소에서 객체를
되돌려 놓는 것으로 치유됩니다. 그것이 바로 GitOps이며, 랩 5에서 켜 보겠습니다. 지금으로서는
여러분의 `rickroll.yaml`이 의도의 유일한 복사본입니다. 그것이 파일에 들어 있는 것은 다행입니다:
검토하고, Git에 넣고, 다시 적용할 수 있습니다.

덧붙이자면, 가운데 고리는 따로 시험해 볼 만하고 다르게 동작합니다. 애플리케이션을 복원한 뒤
(다음 단계), Deployment이 아니라 ReplicaSet을 삭제해 보세요:

```bash
# rs — replicaset의 약자; kubectl은 두 표기를 모두 이해합니다.
# Deployment은 그대로 두고 가운데 고리를 삭제합니다.
kubectl delete rs -l app=rickroll

# 그리고 곧바로 무엇이 남았는지 봅니다: 세트의 이름을 삭제 전과 비교하세요.
kubectl get rs -l app=rickroll
```

세트는 1초 안에 다시 나타납니다 — 그것도 **같은 이름으로**. 이름의 해시는 Pod 템플릿으로부터
계산되는데, 우리는 템플릿을 건드리지 않았습니다: 같은 이름이라는 것은 클러스터가 새로운 무언가를
만든 게 아니라 정확히 같은 것을 복원했다는 뜻입니다. 「이 애플리케이션이 있어야 한다」는 기록은
온전히 남아 있었습니다 — 그것을 책임지는 것은 Deployment이고, 그것은 세트의 삭제를 견뎌 냈습니다.

## 그리고 vSphere에서라면 이렇게 될 것이다

vSphere HA는 호스트 장애 후 VM을 재시작합니다: 먼저 클러스터가 호스트가 정말로 사라졌는지
확인해야 하고(그것이 수십 초), 그다음 머신이 처음부터 부팅합니다 — 커널, 서비스, 애플리케이션.
몇 분. 하트비트 상실에 기반한 VM Monitoring도 같은 방식으로, 같은 시간 규모로 작동합니다.

여기서는 몇 초이고, 호스트 장애 때만이 아닙니다: 같은 메커니즘이 복사본이 축출될 때, OOM이
그것을 죽일 때, 여러분이 직접 삭제할 때 작동합니다.

**vSphere가 더 편리한 지점, 정직하게.** 세 가지입니다.

첫째, vSphere HA는 디스크에 있던 모든 것과 함께 **바로 그 똑같은 머신**을 되돌립니다. Pod는
비어서 돌아옵니다: 영구 볼륨에 있지 않았던 것은 모두 영영 사라집니다. 상태가 없는 애플리케이션에는
이것이 장점이지만, 몇 년 동안 자기 `/var`에 무언가를 써 온 레거시 서비스에는 아주 고약한 뜻밖의 일들의 원천입니다.

둘째, vSphere에는 Fault Tolerance가 있습니다: 두 머신이 lock-step으로 움직이며 호스트 장애 시
다운타임이 0이고, 애플리케이션을 전혀 손보지 않아도 됩니다. Kubernetes에는 직접적인 대응물이
없고, 있을 수도 없습니다 — 여기서 다운타임 0은 복사본을 여럿 두는 것으로 달성되며, 이는
애플리케이션이 여러 복사본으로 실행될 수 있어야 함을 뜻합니다. 그럴 수 없다면 Kubernetes는 그
문제를 대신 풀어 주지 않고 — 드러냅니다.

셋째, 사후 분석. vCenter에서는 머신이 재시작된 이유가 클러스터 이벤트에 단 하나의 항목으로
보이고, 거기에 그대로 남습니다. Kubernetes에서는 이벤트가 약 한 시간 살아 있다가 사라지므로,
여러 컴포넌트의 로그로부터 그림을 재구성해야 합니다. 로그와 이벤트 수집을 설정하기 전까지는
(랩 14), 「밤새 왜 재시작됐는가」는 답이 없는 질문입니다.
