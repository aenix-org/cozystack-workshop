## 왜 중요한가

「출입증」 서비스는 작동하고, 정보보안팀도 만족하며, 레지스트리는 여러분 소유입니다. 그런데 경비팀이 찾아옵니다.

> 출입구에서 방문자 목록이 열리는 데 10초가 걸립니다. 사람들은 줄을 서 있고, 우리는
> 화면을 보며 기다립니다. 예전엔 괜찮았는데요.

무슨 일인지 봅시다. 목록의 각 행은 방문자 한 명이고, 방문자마다 초대한 직원이 있으며,
직원 정보는 여러분 쪽에 있지 않습니다. 그 정보는 2011년에 설치된 인사(HR) 시스템에 있고,
요청 하나에 **800밀리초**가 걸려 응답합니다. 화면에 열두 행이면 거의 10초입니다.

인사 시스템은 다시 작성할 수 없습니다: 여러분 것이 아니고 다른 사람 소유이며, 변경 대기열은
내년까지 꽉 차 있습니다. 같은 이유로 속도를 높일 수도 없습니다.

할 수 있는 것은 그것에게 그렇게 자주 묻지 않는 것입니다. 직원의 성과 부서는 대략 몇 년에
한 번 바뀝니다. 목록을 열 **때마다** 느린 시스템에 그것을 묻는 것은 낭비입니다: 한 번 묻고
답을 기억해 두면 충분합니다.

답을 기억해 두는 곳을 캐시라고 합니다. 오늘 우리는 캐시를 하나 넣고 — 더 중요하게는
**전후의 차이를 측정**할 것입니다. 「빨라졌다」가 아니라 구체적인 숫자로요.

## 미니 용어집

| 용어 | 무엇인가 | ~와 비슷하지만 |
|---|---|---|
| **캐시** | 반복되는 질문에 대한 준비된 답을 담는 빠른 저장소 | **스토리지 어레이의 읽기 캐시**와 비슷하지만, 여기서는 무엇을 캐시할지 장치가 아니라 애플리케이션이 결정합니다 |
| **Redis** | 전부 메모리(RAM)에 담기는 키-값 저장소 | 직접적인 대응물은 없습니다; 접해 본 적 있다면 memcached가 가장 가깝습니다 |
| **키** | 캐시에서 값을 찾는 기준이 되는 문자열 | **파일 이름**과 비슷하지만, 여러분이 직접 지어내며, 어떻게 짓느냐에 모든 것이 달려 있습니다 |
| **TTL (time to live)** | 항목이 스스로 사라지기까지 살아 있는 시간 | **스냅샷 보관 기간**과 비슷하지만, 삭제는 아무도 관여하지 않고 예약된 작업도 없이 일어납니다 |
| **미스 (cache miss)** | 답이 캐시에 없어 느린 원본까지 가야 함 | **스토리지 어레이의 읽기 캐시 미스**와 비슷하지만, 여기서 미스는 밀리초가 아니라 다른 사람의 시스템까지 다녀오는 비용이 듭니다 |
| **히트 (cache hit)** | 답이 캐시에서 발견됨 | **읽기 캐시 히트**와 비슷하지만, 히트를 세는 것은 애플리케이션이고, 그것 또한 응답의 `cached` 필드에서 볼 수 있습니다 |
| **Sentinel** | Redis를 감시하다가 장애 시 리더 역할을 재지정하는 서비스 | **HA 에이전트**와 비슷하지만, Redis 자체 안에서 실행되어 별도의 클러스터가 필요 없습니다 |
| **관리형 서비스** | 플랫폼이 여러분 대신 설치·업데이트·백업해 주는 서비스 | 그것이 실행되는 머신의 root 권한은 주어지지 않습니다 — 그리고 바로 그것이 핵심입니다 |
| **Fortio** | 웹 인터페이스와 지연 히스토그램을 갖춘 부하 생성기 | vSphere에는 대응물이 없습니다: 인프라를 측정하는 도구가 아니라 서비스를 측정하는 도구입니다 |
| **p50 / p99** | 중앙값과 「최악의 백분위」: 요청의 99%는 지연이 이 값보다 높지 않습니다 | 평균 지연은 오해를 부르지만, 이 두 숫자는 그렇지 않습니다 |

## 1단계. v2 버전을 빌드하여 자신의 레지스트리에 푸시

📍 **위치:** 노트북에서.

`app/` 폴더에 소스가 있습니다. 이전 랩의 버전과 두 가지가 다릅니다:
「느린 명부」 모드와 캐시 처리입니다.

<details>
<summary><b>자세히 보기: app/ 안에는 무엇이 있나</b></summary>

**하나의 이미지, 두 가지 역할.** `MODE` 변수가 프로세스가 무엇으로 시작될지 결정합니다:

| `MODE` | 무엇인가 | 무엇을 하나 |
|---|---|---|
| `hr` | 레거시 명부의 스텁 | `HR_DELAY`(기본 800ms)만큼 대기한 뒤 직원 데이터를 반환합니다 |
| `api` | 「출입증」 서비스 자체 | 명부로 가고, `REDIS_ADDR`이 설정돼 있으면 — 먼저 캐시로 갑니다 |

하나 대신 두 개의 이미지를 두면, 버전 업데이트를 잊을 수 있는 곳이 두 군데가 됩니다.

**데이터를 가지러 가는 과정.** 캐시 로직 전체는 약 스무 줄입니다:

```go
if cache != nil {
    raw, found, err := cache.Get(key)
    switch {
    case err != nil:
        log.Printf("кеш недоступен (%v), иду в справочник", err)
    case found:
        if json.Unmarshal([]byte(raw), &emp) == nil {
            fromCache = true
        }
    }
}

if !fromCache {
    emp, err = fetchEmployee(hrClient, hrURL, id)
    ...
    cache.SetTTL(key, string(b), ttl)
}
```

첫 번째 분기를 눈여겨보세요: **캐시를 사용할 수 없어도 애플리케이션은 죽지 않습니다.** 로그에
기록하고 명부로 갑니다 — 느리지만 올바르게요. 이것은 장식이 아니라 모든 캐시의 필수
속성입니다: 캐시는 속도를 높이지만 작동의 조건이 될 수는 없습니다. 서비스가 캐시와 함께
쓰러진다면, 여러분이 만든 것은 캐시가 아니라 또 하나의 장애 지점입니다.

덧붙이자면, 이 속성으로부터 랩 뒷부분에서 예측 가능한 실패가 자라나게 됩니다.
조용히 계속 작동하는 애플리케이션은 운영 환경에서는 반갑지만 디버깅할 때는 음험합니다.

**키.** `employee:42` — 엔티티 이름, 콜론, 식별자. 여기서 콜론은 Redis 문법이 아니라 널리
채택된 관습입니다: 나중에 `employee:*` 패턴으로 검색할 수 있게 해 주고, 하나의 Redis에 두
애플리케이션이 살 때 자신의 키를 남의 것과 혼동하지 않게 해 줍니다.

**수명은 쓰기와 같은 명령으로 설정됩니다:**

```go
r.do("SET", key, val, "EX", strconv.Itoa(ttlSeconds))
```

`SET` 다음에 `EXPIRE`를 두 명령으로 하는 게 아닙니다. 두 명령 사이에 연결이 끊길 수 있고 —
그러면 키는 캐시에 영원히 남습니다. 그런 키는 나중에 몇 달씩 찾아 헤매게 됩니다.

**여기서 Redis 클라이언트는 직접 만든, 쉰 줄짜리입니다.** Redis 프로토콜은 텍스트 기반이라
`GET`과 `SET`은 함수 하나에 들어갑니다. 실제 프로젝트라면 기성 라이브러리를 씁니다 —
연결 풀링, 재시도, sentinel을 처리해 주니까요. 여기서 직접 만든 것이 필요한 이유는 바로
빌드에 외부 의존성이 없도록 하기 위해서입니다: 이전 랩이 어떻게 시작했는지 떠올려 보세요.

**연결 풀을 키운 별도의 HTTP 클라이언트:**

```go
tr := http.DefaultTransport.(*http.Transport).Clone()
tr.MaxIdleConnsPerHost = 64
```

이 줄이 없으면 부하 상황에서 절반의 시간이 명부로 향하는 TCP 연결을 맺는 데 쓰이고, 측정은
명부의 지연이 아니라 우리 자신의 부주의를 보여 주게 됩니다. 측정의 첫 번째 규칙: 자신이
측정한다고 생각하는 것을 실제로 측정하고 있는지 확인하세요.

</details>

빌드해서 자신의 Harbor에 푸시합니다. `build`는 `Dockerfile`로부터 이미지를 빌드해 노트북에
남기고, `push`는 그것을 레지스트리로 보냅니다. 이미지 이름은 이전 랩과 같지만 태그는
다릅니다 — `v2`: 이제 레지스트리에는 두 버전이 모두 있게 되고, 예전 것은 사라지지 않습니다.

자신의 주소로 바꾸세요:

```bash
cd labs/07-redis

# build = 「Dockerfile로부터 이미지를 빌드하라」.
#   --platform linux/amd64  어떤 프로세서용으로 빌드할지; 클러스터 노드는 x86입니다
#   -t <호스트>/<프로젝트>/<이름>:<태그>  결과에 붙일 이름; 이름 맨 앞의 레지스트리
#                           호스트가 나중에 push가 보낼 곳입니다
#   app/                    Dockerfile과 빌드할 소스가 있는 폴더
docker build --platform linux/amd64 -t harbor.workshop03.example.org/passes/passes-api:v2 app/

# push = 「이미지를 레지스트리로 보내라」. 주소는 이미지 이름의 첫 부분에서,
# 자격 증명은 이전 랩에서 한 docker login에서 가져옵니다.
docker push harbor.workshop03.example.org/passes/passes-api:v2
```

⚠️ **Apple Silicon Mac이나 ARM 기반 노트북을 쓴다면 `--platform linux/amd64`는 필수입니다.**
없으면 이미지가 ARM용으로 빌드되어 오류 없이 푸시되지만, 클러스터에서는 로그에
`exec format error`와 함께 `CrashLoopBackOff`를 냅니다.

## 2단계. 명부와 서비스 배포

📍 **위치:** 노트북에서, `lab` 클러스터.

두 매니페스트 모두 레지스트리 주소 대신 자리표시자 `HARBOR-HOST`가 있습니다: `sed`가 파일을
제자리에서 편집하며 그것을 바꿉니다. 그다음 `apply`가 파일에 기술된 것을 클러스터에 넘기고,
`rollout status`가 복제본이 뜰 때까지 기다립니다.

```bash
# KUBECONFIG는 kubectl에게 어떤 접근 파일을 쓸지 알려 줍니다. 여러분의 `lab`
# 클러스터로 전환합니다; 터미널 창을 닫을 때까지 유지됩니다.
export KUBECONFIG=~/lab.kubeconfig

# sed -i = 「파일을 제자리에서 편집하라」.
#   's|old|new|g'  모든 출현을 치환; 주소에 슬래시가 있어서 구분자로 / 대신 |를
#                  사용합니다
#   macOS 버전 sed는 -i 뒤에 인자를 반드시 요구합니다; 빈 따옴표는
#   「백업을 만들지 말라」는 뜻입니다. Linux에서는 그 인자가 있으면 안 됩니다.
#   줄 끝에 파일이 두 개 있습니다: sed는 여러 개를 한꺼번에 받아 한 번에 편집합니다.

# Linux
sed -i    's|HARBOR-HOST|harbor.workshop03.example.org|g' hr-legacy.yaml passes-api.yaml
# macOS
sed -i '' 's|HARBOR-HOST|harbor.workshop03.example.org|g' hr-legacy.yaml passes-api.yaml

# apply = 「클러스터를 파일에 기술된 상태로 만들라」. -f 플래그는 파일마다 반복합니다.
kubectl apply -f hr-legacy.yaml -f passes-api.yaml

# rollout status는 복제본이 준비될 때까지 기다렸다가 스스로 종료합니다; 준비되지 않으면 오류를 반환합니다
kubectl rollout status deployment/hr-legacy
kubectl rollout status deployment/passes-api
```

⚠️ 두 매니페스트 모두 `harbor` Secret을 참조합니다 — 이전 랩에서 만든 바로 그
`imagePullSecret`입니다. 그것을 만들지 않았다면 Pod들이 `ImagePullBackOff`에 빠집니다.
Secret을 만들려면:

```bash
# create secret docker-registry = 「레지스트리 자격 증명을 담은 Secret을 만들라」;
# 그런 Secret은 kubelet이 노드로 이미지를 내려받을 때 직접 읽을 수 있습니다.
#   harbor             클러스터 내 Secret 이름 — 두 매니페스트가 이것을 참조합니다
#   --docker-server    이 자격 증명이 어느 레지스트리를 위한 것인지
#   --docker-username  누가 로그인하는지; --docker-password — Harbor 관리자 비밀번호
kubectl create secret docker-registry harbor \
  --docker-server=harbor.workshop03.example.org \
  --docker-username=admin --docker-password='여러분의-비밀번호'
```

체인이 작동하는지 확인합시다. 서비스는 클러스터 안에서만 보이므로 요청도 거기서 합니다:
`curl`이 담긴 일회용 Pod를 띄우면, 그것이 `passes-api` 서비스에 물어보고, 답을 출력한 뒤
사라집니다.

```bash
# run probe = 「probe라는 이름의 Pod를 실행하라」.
#   --rm              작업이 끝나는 즉시 Pod를 삭제
#   -i                그 출력을 우리에게 보여 줌
#   --restart=Never   재시작하지 않음: 이것은 상시 서비스가 아니라 일회성 명령입니다
#   --image=...       어떤 이미지를 쓸지; 새것이 딸려오지 않도록 버전을 고정했습니다
#   --quiet           서비스 라인은 출력하지 않고 답만
#   --                이 두 대시 뒤의 모든 것은 Pod 내부의 명령입니다
# <service>.<namespace>.svc.cluster.local 형태의 주소는 서비스의 내부 이름입니다;
# 이 이름으로 Pod들은 주소를 몰라도 서로를 찾습니다.
kubectl run probe --rm -i --restart=Never --image=curlimages/curl:8.11.1 --quiet -- \
  curl -s "http://passes-api.default.svc.cluster.local/employee?id=42"
```

**여러분이 봐야 할 것:**

```json
{"cache":"off","cached":false,"dept":"Логистика","id":"42","name":"Попова Е. К.",
 "pod":"passes-api-6f8b9c7d5-x2ktm","took_ms":803,"ttl_s":60}
```

핵심 필드: `cache: off` — 캐시 없음, `took_ms: 803` — 바로 이것, 여러분의 800밀리초입니다.
우리가 줄일 대상이 바로 이 숫자입니다.

## 3단계. 지금 얼마나 나쁜지 측정

📍 **위치:** 노트북에서, `lab` 클러스터.

요청 하나는 측정이 아닙니다. 실제와 비슷한 부하와 지연의 분포가 필요합니다.

생성기를 배포합니다. 그것은 평범한 애플리케이션처럼 떠서 서비스 옆 클러스터 안에 삽니다 —
그래야 측정이 여러분의 인터넷이나 터널에 좌우되지 않습니다:

```bash
# 파일에는 객체가 둘 있습니다: 생성기 자체와 그것을 위한 서비스
kubectl apply -f fortio.yaml
kubectl rollout status deployment/fortio
```

이제 부하를 시작합니다. `kubectl exec` 명령은 이미 실행 중인 Pod 안에서 무언가를 실행합니다 —
여기서는 생성기 안에서 생성기 자체가 포격 모드로 실행됩니다:

```bash
# exec deploy/fortio = 이 애플리케이션의 Pod 안에서 명령을 실행
#   --            경계: 왼쪽은 kubectl, 오른쪽은 Pod 안으로 들어가는 명령
#   fortio load   포격 모드: 요청을 보내고 응답 시간을 측정
#   -qps 20       초당 20개 요청 — 「있는 힘껏 밀어붙이기」가 아니라 페이스를 정합니다
#   -t 20s        측정이 얼마나 지속되는지
#   -c 16         병렬 연결 16개. 이 수는 임의가 아닙니다:
#                 명부는 800ms에 응답하므로, 연결 하나는 초당 요청 한 개보다
#                 조금 넘게 처리합니다. 정해진 초당 20개를 유지하려면 연결이
#                 최소 열여섯 개는 필요합니다 — 그러지 않으면 Fortio가 지연의
#                 벽에 부딪혀 요청한 페이스를 내지 못합니다.
#   마지막 인자는 우리가 포격하는 주소입니다
kubectl exec deploy/fortio -- fortio load -qps 20 -t 20s -c 16 \
  "http://passes-api.default.svc.cluster.local/employee?id=42"
```

**여러분이 봐야 할 것** — 출력 끝에 히스토그램과 백분위 줄들:

```
# target 50% 0.801
# target 90% 0.806
# target 99% 0.812
Code 200 : 400 (100.0 %)
```

**이 숫자들을 적어 두세요.** 10분 뒤 비교를 위해 필요한데, 기억이란 「음, 대충 팔백쯤이었지」가
「음, 대충 반 초쯤이었지」로 바뀌도록 만들어져 있습니다.

### 마우스로 같은 것을

마우스로 — 이건 Cozystack 대시보드가 아닙니다: 대시보드는 관리 클러스터를 다루며 테넌트의
카탈로그 항목을 보여 주지만, 여러분의 `lab` 클러스터 안은 들여다보지 못합니다. 생성기 자체에
자체 웹 인터페이스가 있고, 거기엔 터널로 닿아야 합니다.

```bash
# port-forward svc/fortio = 노트북에서 클러스터 내 생성기 서비스로 가는 터널
#   8081:8080 — 왼쪽 숫자는 노트북의 포트, 오른쪽은 클러스터 내 서비스 포트
# 8081 포트를 쓰는 이유는 8080이 여러분 머신의 다른 무언가에 점유돼 있을 수 있어서입니다.
# 창을 닫지 마세요: 터널은 명령이 실행되는 동안만 삽니다. 멈추려면 — Ctrl+C.
kubectl port-forward svc/fortio 8081:8080
```

<http://localhost:8081/fortio> 를 여세요. 다음을 채워 넣으세요:

| 필드 | 값 |
|---|---|
| URL | `http://passes-api.default.svc.cluster.local/employee?id=42` |
| QPS | `20` |
| Duration | `20s` |
| Connections | `16` |

**Start**를 누르세요. 아래쪽에 지연 히스토그램이 그려집니다. 숫자보다 명확합니다: 모든 요청이
800ms 부근의 좁은 띠 하나에 모인 것을 볼 수 있습니다 — 즉 「가끔」이 아니라 항상, 그리고
똑같은 정도로 느리다는 뜻입니다.


<details>
<summary><b>왜 평균 지연이 아니라 p50과 p99인가</b></summary>

평균 지연은 운영에서 가장 기만적인 지표입니다.

상상해 보세요: 10ms짜리 요청 아흔 개와 2000ms짜리 요청 열 개. 평균은 209ms이고, 보고서상으로는
모든 게 그럴듯해 보입니다. 하지만 실제로는 열 명 중 한 명이 2초를 기다리다 떠났습니다.

**p50 (중앙값)** — 요청의 절반은 이 숫자보다 빠르고, 절반은 느립니다. 「보통 사용자는 얼마나
기다리나」라는 질문에 답합니다.

**p99** — 요청의 99%가 이 숫자보다 빠릅니다. 「얼마나 나빠질 수 있나」라는 질문에 답합니다.
출입구의 경비가 불평할지 말지를 결정하는 것은 바로 p99입니다: 사람들은 평균이 아니라
기다려야 했던 그 한 번에 대해 불평합니다.

우리 측정에서 p50과 p99는 거의 일치했습니다 — 801ms와 812ms. 이는 느림이 무작위가 아니라
체계적임을 보여 주는 신호입니다: 정확히 항상 느립니다. 이런 것은 캐시로 고칩니다. 만약 p50이
10ms이고 p99가 2000ms였다면 원인은 다른 것이고, 캐시는 도움이 되지 않았을 것입니다.

</details>

## 4단계. Redis 생성

📍 **위치:** 브라우저에서, Cozystack 대시보드. Redis는 Harbor처럼 공유 테넌트 리소스입니다.

테넌트 → **Create application** → `Redis`.

| 필드 | 값 | 왜 그런가 |
|---|---|---|
| Name | `cache` | 서비스 이름에 들어가므로 짧을수록 편합니다 |
| Replicas | `2` | 리더 복제본 하나와 팔로워 하나: 그것이 무엇을 주는지 보게 됩니다 |
| Size | `1Gi` | 직원 명부는 메모리에 넉넉히 여유를 두고 들어갑니다 |
| Storage class | `replicated` | |
| Resources preset | 제안된 것을 그대로 둡니다 | |
| Version | `v8` | |
| Auth enabled | **켬** (기본값) | 플랫폼이 비밀번호를 직접 생성합니다 |
| External | **끔** | 이 캐시를 외부에 노출할 이유가 없습니다 |

준비되기까지 3~5분 기다릴 것으로 예상하세요.

⚠️ **이 Redis는 Harbor 생성 폼에서 봤을 수 있는 Redis와 아무 관련이 없습니다.** 거기 있는 것은
레지스트리 자체의 내부 캐시입니다. 이것은 여러분의 애플리케이션을 위한, 여러분 자신의
것입니다.

<details>
<summary><b>관리형 Redis가 VM에 설치한 Redis와 어떻게 다른가</b></summary>

가상 머신에 Redis를 설치하는 것은 30분짜리 일입니다: `apt install redis`, `bind`와
`requirepass`를 손보고, 부팅 시 켜지도록 설정. 관리형 서비스가 과해 보이는 이유가 바로
이것입니다. 차이는 설치가 아니라 그다음에 일어나는 일에 있습니다.

**복제.** `replicas: 2`를 설정하면 — 서로 다른 노드에 데이터 복제본 두 개와, 그것들을 지켜보는
sentinel 세 개를 얻습니다. 리더 복제본이 있는 노드가 죽으면 sentinel들이 선출을 치러 두 번째
복제본을 리더로 만듭니다. 애플리케이션은 몇 초의 멈춤과 함께 이를 견뎌 냅니다. 같은 것을
손으로 조립하는 것은 하루짜리 일이고, 그것이 설정된 것처럼 보이기만 하는 게 아니라 실제로
페일오버되는지 검증하는 데 또 하루가 듭니다.

**업데이트.** Redis의 취약점은 드물지 않습니다. VM에서 업데이트는 `apt upgrade`, 재시작,
그리고 설정이 메이저 버전 변경에서 살아남기를 바라는 것을 뜻합니다. 여기서는 이미지
업데이트가 플랫폼 업데이트와 함께 도착하고, 복제본이 재시작되는 순서는 서비스가 사라지지
않도록 배치돼 있습니다.

**관측 가능성.** 지표는 이미 수집되고 있습니다: 익스포터가 각 복제본 옆에서 실행되고,
그래프는 여러분의 수고 없이 마련돼 있습니다. VM에서는 그것이 또 하나의 패키지, 또 하나의
설정, 그리고 잊어버린 또 하나의 항목입니다.

**포기하는 것.** 솔직히 말하면: Redis가 있는 머신의 root입니다. SSH로 들어갈 수 없고, 설정을
손으로 편집할 수 없으며, 옆에 자신의 스크립트를 놓을 수도 없습니다. 애플리케이션 파라미터로
드러나지 않은 것은 여러분의 손이 닿지 않습니다 — 그리고 드러난 것은 전부와는 거리가 멉니다.
비표준 `maxmemory-policy`나 Redis 모듈이 필요하다면 관리형 서비스는 그것을 주지 않고,
여러분은 VM에 직접 설치해야 합니다. 이것은 사소한 게 아니라 실제 한계입니다.

</details>

## 5단계. Redis 주소 찾기와 연결성 확인

📍 **위치:** 노트북에서, **관리** 클러스터.

Redis는 관리 클러스터의 여러분 테넌트에 살고, 애플리케이션은 여러분의 `lab` 클러스터에
삽니다. 이것은 서로 다른 두 클러스터이고, 가장 먼저 할 일은 두 번째가 첫 번째에 닿을 수
있는지 확인하는 것입니다.

어떤 서비스가 생겼는지 봅시다:

```bash
# --kubeconfig는 접근 파일을 명령 안에서 바로 지정합니다 — KUBECONFIG를 건드리지 않고 딱 한 번만.
# 이렇게 하면 연달아 실행하는 두 명령을 헷갈리지 않고 서로 다른 클러스터로 보낼 수 있습니다.
#   -n tenant-workshopXX  여러분 테넌트의 namespace
#   get svc               「서비스를 보여 줘」 — Pod가 뒷받침하는 영구 주소
#   | grep redis          출력에서 redis라는 단어가 있는 줄만 남김
kubectl --kubeconfig ~/.kube/workshop -n tenant-workshopXX get svc | grep redis
```

**여러분이 봐야 할 것** — 뜻이 드러나는 접두사를 가진 여러 서비스:

| 이름 | 그 뒤에 무엇이 있나 |
|---|---|
| `rfrm-redis-cache` | 리더 복제본(master) — 여기에 쓰고 읽습니다 |
| `rfrs-redis-cache` | 팔로워 복제본(replicas) — 읽기 전용 |
| `rfs-redis-cache` | sentinel — 감시하고 역할을 전환하는 서비스 |

⚠️ **이름에 붙은 여분의 `redis-`는 어디서 왔나.** 플랫폼은 애플리케이션 이름에 서비스 유형을
담은 접두사를 붙입니다: Redis 유형의 `cache` 애플리케이션은 내부적으로 `redis-cache`라고
불립니다. 그래서 `rfrm-cache`가 아니라 `rfrm-redis-cache`입니다. 이름을 추측하지 마세요 —
위 명령의 출력을 보세요, 그것이 진실의 근원입니다.

우리에게 필요한 것은 `rfrm-redis-cache`입니다: 캐시는 쓰기도 하고 읽기도 하는데, 쓰기는 리더
복제본에만 할 수 있습니다.

여러분의 클러스터에서 보이는 전체 이름은 이렇게 조립됩니다:

```
rfrm-redis-cache.tenant-workshopXX.svc.cozy.local
```

비밀번호를 가져옵니다. 📍 **위치:** 대시보드, `cache` 애플리케이션, secrets 탭.
`redis-cache-auth` Secret의 `password` 키가 필요합니다.

이제 — 연결성 확인. 📍 **위치:** 노트북에서, **`lab`** 클러스터.

여러분의 클러스터에서 Redis 클라이언트가 담긴 일회용 Pod를 띄우고, 그것에게 Redis에 `ping`
이라는 단어를 말하라고 시킵니다. 답이 돌아오면 테넌트의 캐시가 `lab` 클러스터에서 보인다는
뜻이고 — 지금 우리가 확인하는 것은 오직 그것 하나뿐입니다.

⚠️ **비밀번호는 `-a` 플래그가 아니라 `REDISCLI_AUTH` 변수로 전달합니다.** 명령의 인자로 들어가는
것은 무엇이든 노드의 프로세스 목록에서 보이고 Pod의 명세에 남습니다 — 그리고 그것은 여러분의
namespace에 접근할 수 있는 누구나 읽을 수 있습니다. `redis-cli` 자체가 이에 대해 경고하는데,
원인을 없애는 대신 경고를 잠재우는 것은 나쁜 습관입니다.

```bash
export KUBECONFIG=~/lab.kubeconfig

# run redis-probe = redis-cli 클라이언트가 담긴 일회용 Pod:
#   --rm --restart=Never  제 할 일을 하고 스스로 삭제됨, 재시작 필요 없음
#   -i --quiet            출력을 우리에게 보여 주고 서비스 라인은 출력하지 않음
#   --env=REDISCLI_AUTH   비밀번호는 인자가 아니라 환경 변수로 Pod에 들어갑니다
#   --                    이 대시 오른쪽은 Pod 안으로 들어가는 명령입니다
#   redis-cli -h <이름>   어느 서버에 접속할지; 이름은 그 전체 이름 그대로입니다
#   ping                  짧은 「살아 있니」; 그에 대한 답은 PONG입니다
kubectl run redis-probe --rm -i --restart=Never --image=redis:7-alpine --quiet \
  --env=REDISCLI_AUTH='여러분의-비밀번호' -- \
  redis-cli -h rfrm-redis-cache.tenant-workshopXX.svc.cozy.local ping
```

**여러분이 봐야 할 것:**

```
PONG
```

⚠️ **`PONG` 대신 이름 확인 오류가 났다면** — 관리 클러스터의 내부 이름이 여러분의 클러스터에서
보이지 않는 것입니다. 이것은 IP로 주소를 지정해 해결합니다:

```bash
# -o jsonpath='{.spec.clusterIP}' — 객체의 한 필드를 출력: 플랫폼이 이 서비스에
# 할당한 내부 주소. {"\n"}은 줄바꿈을 추가합니다.
kubectl --kubeconfig ~/.kube/workshop -n tenant-workshopXX get svc rfrm-redis-cache \
  -o jsonpath='{.spec.clusterIP}{"\n"}'
```

이후로는 어디서든 이름 대신 얻은 주소를 넣으세요. 똑같이 작동합니다; 유일한 단점은 Redis가
재생성되면 주소는 바뀌지만 이름은 바뀌지 않는다는 것입니다. 주소로도 응답하지 않으면 —
워크숍 채팅에 글을 남기세요, 이것은 여러분의 오류가 아니라 테스트베드 구성 문제입니다.

## 6단계. 캐시 켜기

📍 **위치:** 노트북에서, `lab` 클러스터.

애플리케이션을 통째 매니페스트가 아니라 패치로 바꿉니다 — 그래야 무엇이 바뀌는지 정확히
보입니다. 먼저 여러분의 Redis 주소를 패치에 넣고, 그다음 패치를 클러스터에 넘깁니다:
`kubectl patch`는 이미 존재하는 객체를 통째로 교체하는 게 아니라 변경을 덧붙입니다.

```bash
# 앞서와 같은 주소 치환, 다만 자리표시자가 다릅니다 — REDIS-ADDR

# Linux
sed -i    's|REDIS-ADDR|rfrm-redis-cache.tenant-workshopXX.svc.cozy.local|g' cache-patch-broken.yaml
# macOS
sed -i '' 's|REDIS-ADDR|rfrm-redis-cache.tenant-workshopXX.svc.cozy.local|g' cache-patch-broken.yaml

# patch deployment passes-api = 「이 객체를 파일에 있는 것으로 고쳐라」
#   --patch-file  변경을 어디서 가져올지
# 환경 변수를 바꾼다는 것은 새 Pod를 뜻합니다: 기존 것들은 교체됩니다.
kubectl patch deployment passes-api --patch-file cache-patch-broken.yaml

# 새 복제본이 준비될 때까지 기다립니다 — 그러지 않으면 아직 옛것을 측정하게 됩니다
kubectl rollout status deployment/passes-api
```

다시 측정합니다 — 캐시를 켜기 전에 측정했던 것과 같은 명령으로요. 포격 조건은 마지막
플래그까지 일치해야 합니다, 그러지 않으면 비교할 것이 없습니다:

```bash
# 같은 초당 20개 요청, 같은 20초, 같은 16개 연결
kubectl exec deploy/fortio -- fortio load -qps 20 -t 20s -c 16 \
  "http://passes-api.default.svc.cluster.local/employee?id=42"
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 숫자는 바뀌지 않았습니다: 같은 800밀리초. 그런데도 Pod는 하나도 죽지 않았고, 응답에 오류도
> 없으며, 모든 요청이 `200`을 반환했습니다. Redis는 생성됐고 주소도 맞습니다 — 방금 그것으로부터
> `PONG`을 받았으니까요.
>
> 어디를 봐야 할까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

먼저 애플리케이션 자체가 무엇을 답하는지 보세요: 응답에는 캐시가 켜져 있는지, 그리고 답이
캐시에서 왔는지 보여 주는 필드가 있습니다.

```bash
# 앞서와 같은 curl이 담긴 일회용 Pod: 클러스터 안에서 서비스에 물어봅니다
kubectl run probe --rm -i --restart=Never --image=curlimages/curl:8.11.1 --quiet -- \
  curl -s "http://passes-api.default.svc.cluster.local/employee?id=42"
```

```json
{"cache":"redis","cached":false,"took_ms":802, ...}
```

`cache: redis` — 캐시가 켜져 있습니다. `cached: false` — 그런데도 답은 캐시에서 오지
않았습니다. 게다가 몇 번을 반복해도 **항상** false입니다.

이제 로그입니다. 애플리케이션은 자신이 하지 못한 것을 거기에 씁니다 — 그리고 지금 진실이
보이는 유일한 곳이 바로 거기입니다:

```bash
# logs = 「애플리케이션이 자기 출력에 쓴 것을 보여 줘」.
#   -l app=passes-api  이름을 지정한 한 복제본이 아니라, 이 레이블을 가진 모든 복제본을 한꺼번에
#   --tail=20          전체 로그가 아니라 각 복제본의 마지막 스무 줄
kubectl logs -l app=passes-api --tail=20
```

여기 답이 있습니다. 우리는 Redis 주소는 지정했지만 비밀번호는 지정하지 않았습니다. Redis는
인증을 요구합니다 — 여러분이 생성 시 직접 `Auth enabled`를 켰고, 그것은 옳은 설정입니다.
애플리케이션은 정직하게 시도했다가 거절당했고, 그것을 로그에 쓴 뒤 명부로 갔습니다.

**왜 이것이 고장처럼 보이지 않았나.** 고장이 없었기 때문입니다. 애플리케이션은 캐시를 사용할
수 없는 상황을 견디도록 설계돼 있습니다: 캐시는 속도를 높이지만 작동의 조건이 될 수는
없습니다. 운영 환경에서는 이것이 여러분을 구합니다 — Redis가 쓰러져도 서비스를 쓰러뜨리지
않습니다. 디버깅할 때는 바로 그 속성이 문제를 숨깁니다: 모든 게 초록색이고 오류도 없는데,
빨라지지도 않습니다.

**교훈은 이 오류보다 넓습니다.** 작동을 방해하지 않는 실패는 가장 값비싼 종류의 실패입니다. 경보를
울리지 않고 운영 환경에서 몇 달씩 삽니다. 그래서 실용적인 규칙이 나옵니다: **모든 가속
장치에는 그것이 작동하고 있다는 관측 가능한 신호가 있어야 합니다.** 우리에게 그것은 응답의
`cached` 필드입니다. 만약 그것이 없었다면 여러분은 지금 추측하고 있었을 것입니다.

실제 시스템이라면 이 자리에 「캐시 히트 비율」 지표와, 그것이 0으로 떨어질 경우를 대비한
알림이 있습니다.

## 7단계. 비밀번호를 넣고 다시 측정

📍 **위치:** 노트북에서, `lab` 클러스터.

Redis 비밀번호는 관리 클러스터에 있고, 애플리케이션은 그것을 여러분의 클러스터에서
필요로 합니다. 우리는 그것을 옮깁니다 — 셸 변수를 통해서요, 비밀번호가 명령 히스토리에 남지
않도록요:

```bash
# read는 키보드로 입력한 것을 REDIS_PASS 변수에 넣습니다:
#   -s  입력한 것을 화면에 표시하지 않음
#   -r  백슬래시를 특수 문자로 취급하지 않음
# 이 줄 다음에는 화면에 아무것도 나타나지 않습니다: 대시보드의 비밀번호를 붙여넣고 Enter.
read -rs REDIS_PASS

# create secret generic = 평범한 Secret, 키-값 쌍의 모음.
#   redis-password              클러스터 내 Secret 이름
#   --from-literal=password=... 그 안에 이 값을 가진 password 키를 만듭니다;
#                               패치가 참조하는 것은 「Secret 이름 + 키」 쌍입니다
kubectl create secret generic redis-password --from-literal=password="$REDIS_PASS"

# unset은 비밀번호가 이 창의 다음 명령들에 닿지 않도록 변수를 지웁니다
unset REDIS_PASS
```

전체 패치를 적용합니다. 거기에는 같은 Redis 주소에 더해, 방금 만든 Secret에 대한 참조와 캐시
항목의 수명이 들어 있습니다; 설명은 명령 바로 다음 스포일러에 있습니다.

```bash
# 같은 주소 치환, 이번엔 작동하는 패치 파일에서

# Linux
sed -i    's|REDIS-ADDR|rfrm-redis-cache.tenant-workshopXX.svc.cozy.local|g' cache-patch.yaml
# macOS
sed -i '' 's|REDIS-ADDR|rfrm-redis-cache.tenant-workshopXX.svc.cozy.local|g' cache-patch.yaml

# 기존 Deployment를 파일 내용으로 고치고 새 복제본을 기다립니다
kubectl patch deployment passes-api --patch-file cache-patch.yaml
kubectl rollout status deployment/passes-api
```

<details>
<summary><b>자세히 보기: cache-patch.yaml 안에는 무엇이 있나</b></summary>

```yaml
spec:
  template:
    spec:
      containers:
        - name: api
          env:
            - name: REDIS_ADDR
              value: "rfrm-redis-cache.tenant-workshopXX.svc.cozy.local:6379"
            - name: REDIS_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: redis-password
                  key: password
            - name: CACHE_TTL
              value: "60"
```

**왜 전체 매니페스트가 아니라 패치인가.** 패치는 「상태가 이래야 한다」가 아니라 「이것을
바꿔라」입니다. 파일에서는 무엇이 바뀌는지 정확히 보입니다, 눈으로 새 세 줄을 찾아 헤매야
하는 이백 줄이 아니라요.

**왜 이것이 나머지 변수를 지우지 않나.** Kubernetes의 리스트는 키로 병합될 수 있습니다. `env`의
경우 키는 `name` 필드입니다: 패치의 세 항목은 이미 있는 것들에 더해지고, `REDIS_ADDR` 항목은
망가진 패치에서 남은 동명의 것을 교체합니다. 컨테이너 리스트도 같은 방식으로, 이름으로
병합됩니다 — 그래서 `- name: api`가 필수입니다; 그것이 없으면 Kubernetes는 여러분이 어느
컨테이너를 편집하는지 이해하지 못합니다.

**왜 비밀번호를 텍스트가 아니라 `secretKeyRef`를 통해 넣나.** 값은 Pod가 시작되는 순간
`redis-password` Secret에서 도착합니다. 매니페스트 자체에는 비밀번호가 없습니다 — 그리고
그것이 중요한데, 매니페스트는 Git으로 들어가 거기 영원히 남을 것이기 때문입니다. Secret은
Git에 들어가지 않습니다.

솔직히 말하면: 클러스터 안의 Secret은 여전히 평문으로, 그저 다른 곳에 놓여 있을 뿐입니다. 이
namespace에서 Secret을 읽을 수 있는 사람은 누구나 비밀번호를 보게 됩니다. 진짜 해결책은 외부
시크릿 저장소이고, 그것은 별도의 랩입니다.

**`CACHE_TTL: 60`.** 60초는 타협입니다. 아래 — 다음 스포일러를 읽으세요.

</details>

부하를 주기 전에 하나씩 확인합시다. 아직 물어본 적 없는 식별자로 같은 요청을 연달아 두 번:
첫 번째는 반드시 느리고, 두 번째는 — 빠릅니다.

```bash
# 같은 curl이 담긴 일회용 Pod, 다만 그 안에서 sh 셸이 실행됩니다:
#   sh -c '...'  하나의 문자열로 전달된 여러 명령을 실행
#   ; echo       답들이 붙어 버리지 않도록 사이에 줄바꿈을 삽입
# id=777을 쓴 이유는 이 직원을 아직 물어본 적이 없어서입니다: 캐시에 확실히 없습니다.
kubectl run probe --rm -i --restart=Never --image=curlimages/curl:8.11.1 --quiet -- \
  sh -c 'curl -s "http://passes-api.default.svc.cluster.local/employee?id=777"; echo;
         curl -s "http://passes-api.default.svc.cluster.local/employee?id=777"'
```

**여러분이 봐야 할 것** — 두 개의 답, 그리고 서로 다릅니다:

```json
{"cached":false,"took_ms":804, ...}
{"cached":true,"took_ms":1, ...}
```

첫 번째 요청은 미스입니다: 캐시가 비어 있어 명부로 가야 했고, 804ms. 두 번째는 히트입니다:
답이 이미 있었고, 1ms.

이제 부하를 준 측정, 같은 플래그의 같은 명령으로, 세 번째:

```bash
# 포격 조건은 아무것도 바꾸지 않습니다: 바뀌는 것은 서비스 내부뿐입니다
kubectl exec deploy/fortio -- fortio load -qps 20 -t 20s -c 16 \
  "http://passes-api.default.svc.cluster.local/employee?id=42"
```

**여러분이 봐야 할 것:**

```
# target 50% 0.0012
# target 90% 0.0021
# target 99% 0.0043
Code 200 : 400 (100.0 %)
```

## 8단계. 이득 집계

📍 **위치:** 종잇조각에.

세 숫자를 표에 모으세요. 여러분의 것은 다를 것입니다 — 테스트베드, 네트워크, 노드의 이웃
때문에:

| | p50 | p99 | 경비에게 이것이 뜻하는 바 |
|---|---|---|---|
| 캐시 없음 | 801ms | 812ms | 12행 목록이 ~9.6초에 열림 |
| 캐시 켬, 비밀번호 없음 | 802ms | 815ms | 아무것도 바뀌지 않음 |
| 캐시 작동 | 1.2ms | 4.3ms | 같은 목록 — ~0.05초 |

차이는 **수백 배**이고, 이것은 수사가 아니라 측정된 두 숫자의 몫입니다.

우리가 하지 **않은** 것을 눈여겨보세요. 인사 시스템을 다시 쓰지 않았습니다. 노드를 추가하지
않았습니다. 「출입증」 서비스의 로직에서 단 한 줄도 바꾸지 않았습니다 — 그저 같은 것을 두 번
묻지 않도록 가르쳤을 뿐입니다. 변경은 환경 변수 세 개에 들어갔습니다.

<details>
<summary><b>캐시가 도움이 되지 않을 때와, 그것을 미리 알아보는 법</b></summary>

캐시는 만능 가속이 아닙니다. 한 가지 조건에서 도움이 됩니다: **같은 질문이 여러 번 던져질
때.** 세 가지 경우로 스스로를 시험해 보세요.

**모든 요청이 고유하다.** 방문자 목록이 매번 새로운 직원의 정보를 요청한다면 히트는 전혀
없을 것이고, 모든 요청에 Redis로 다녀오는 왕복이 더해질 것입니다. 더 느려집니다. 이렇게
확인할 수 있습니다 — 서로 다른 식별자로 짧은 시리즈를 두 번 돌리고 각각의 첫 요청을 보세요:

```bash
# 서로 다른 직원으로 연달아 두 번의 포격, 각각 10초.
# 각 시리즈 시작 시 그 키에 대해 캐시는 비어 있고 — 첫 요청은 명부로 갑니다.
kubectl exec deploy/fortio -- fortio load -qps 20 -t 10s -c 16 \
  "http://passes-api.default.svc.cluster.local/employee?id=1"
kubectl exec deploy/fortio -- fortio load -qps 20 -t 10s -c 16 \
  "http://passes-api.default.svc.cluster.local/employee?id=2"
```

각 시리즈의 첫 요청은 미스입니다. 드물게 반복되는 키의 큰 집합에서 캐시는 오버헤드로
전락합니다.

**데이터가 TTL보다 자주 바뀐다.** 직원 정보가 10초마다 바뀌는데 TTL은 60으로 설정돼 있다면,
경비는 최대 1분 동안 오래된 데이터를 보게 됩니다. 캐시는 언제나 신선도를 속도와 맞바꾸며,
신선도를 얼마나 내줄 수 있는지 정하는 것은 기술적 결정이 아니라 고객에게 물을 문제입니다.

**항상이 아니라 가끔 느리다.** 첫 측정에서 p50과 p99의 차이를 기억하나요? p50이 작고 p99가
거대하다면 느린 것은 데이터 원본이 아니라 뭔가 간헐적인 것입니다: 가비지 컬렉션, 노드의 이웃,
데이터베이스의 락. 캐시는 이것을 가릴 뿐 고치지는 못하고, 언젠가 여러분은 똑같은 것을, 다만
1년 늦게 그리고 캐시까지 얹은 채로 풀어 헤치고 있을 것입니다.

</details>

<details>
<summary><b>TTL은 어떻게 고르나</b></summary>

TTL은 캐시의 유일한 진짜 파라미터이고, 기술적 근거로 고르는 것이 아닙니다.

질문은 이렇습니다: **얼마나 오래 오래된 데이터를 보여 줄 용의가 있나요?**

직원 명부의 경우: 성은 몇 년에 한 번, 부서는 1년에 한 번 바뀝니다. 출입구에서 어제의 부서는
누구도 성가시게 하지 않습니다. TTL은 한 시간이든 하루든 상관없을 것입니다.

우리가 60초로 설정한 것은 랩이 관측 가능하도록 하기 위해서입니다: 1분을 기다리고 요청을
반복하면 — `cached: false`를 다시 보게 됩니다, 항목이 만료되어 명부로 다녀왔기 때문입니다.
하루짜리 TTL이라면 그것을 믿음으로 받아들여야 했을 것입니다.

극단적인 경우:

| TTL | 무엇을 얻나 |
|---|---|
| 너무 작음 | 히트가 적고, 캐시가 거의 작동하지 않으며, 원본의 부하가 그대로 남습니다 |
| 너무 큼 | 빠르지만, 사용자가 어제의 데이터를 보고 다른 것에 대해 불평합니다 |
| 아예 설정 안 함 | 키가 쌓이고, 메모리가 바닥나며, Redis가 아무거나 축출하기 시작합니다 |

마지막 행이 가장 음험합니다. TTL 없는 캐시는 시간이 지나면 아무도 백업하지 않는 데이터베이스로
변합니다.

</details>

## 검증

📍 **위치:** 노트북에서, `kubectl`로 작업하던 바로 그 터미널 창.

스크립트는 두 클러스터에 동시에 가며 그것들을 환경 변수에서 가져옵니다. 앞의 둘은 필수이고,
세 번째는 테넌트 kubeconfig의 경로입니다.

```bash
cd labs/07-redis

# 애플리케이션을 어느 클러스터에서 확인할지 — 여러분의 `lab`
export KUBECONFIG=~/lab.kubeconfig
# 여러분의 테넌트 번호: 이것으로 스크립트는 namespace 이름 tenant-workshop03을 조립합니다
export COZY_TENANT=workshop03
# 관리 클러스터에 대한 접근이 어디 있는지 — 거기서 스크립트는 Redis 자체를 봅니다.
# 설정하지 않아도 됩니다: 그러면 스크립트는 ~/.kube/workshop을 찾고, 찾지 못하면 —
# 관리 클러스터에 대한 검사를 건너뛰고 그렇다고 말합니다.
export COZY_KUBECONFIG=~/.kube/workshop

./check.sh
```

⚠️ **Windows에서는 스크립트를 PowerShell이 아니라 WSL에서 실행합니다** — 설치 방법은 랩 0 시작
부분에 적혀 있습니다. WSL이 없어도 랩은 완료할 수 있지만, 산출물 보고서는 없습니다.

스크립트는 어떤 매니페스트의 말도 곧이곧대로 믿지 않습니다. 무작위 식별자로 직접 요청을
연달아 두 번 하고 지켜봅니다: 첫 번째는 미스여서 수백 밀리초가 걸려야 하고, 두 번째는
히트여서 한 자릿수가 걸려야 합니다. 그 차이를 보고서에 숫자로 기록합니다. 그 과정에서 느린
명부가 실제로 느린지 확인합니다: 그것 없이는 비교가 아무 의미도 없을 것입니다.

## 정리

모든 것이 다음 랩들에서 필요합니다 — 지금은 아무것도 삭제하지 않습니다.

모든 랩을 끝냈을 때:

```bash
# delete -f = 파일에 기술된 바로 그 객체들을 클러스터에서 제거
kubectl delete -f passes-api.yaml -f hr-legacy.yaml -f fortio.yaml
# Secret은 파일이 아니라 명령으로 만들었으므로 — 이름으로 삭제합니다
kubectl delete secret redis-password
```

Redis 자체는 평범한 애플리케이션처럼 대시보드를 통해 삭제합니다.

캐시를 삭제하는 것은 값싸고 거의 안전한 작업이며, 그것이 캐시의 별도 속성입니다: **캐시에는
다른 어디에도 존재하지 않는 데이터가 없습니다.** 그 안의 모든 것은 원본으로 다녀오면 복구할
수 있습니다. Redis를 잃는다는 것은 그것이 다시 채워지는 몇 분 동안 속도를 잃는다는 뜻이지 —
정보를 잃는다는 뜻이 아닙니다. 데이터베이스라면 그렇게 되지 않고, 데이터베이스에 관한 랩에서
여러분은 이 이야기로 돌아오게 됩니다.

## 이제 우리가 할 수 있는 것

- 관리형 Redis를 프로비저닝하고, 여러분이 설정하지 않은 복제가 무엇을 주는지 설명하기
- 변경 전후의 지연을 이야기하는 대신 측정하기
- p50과 p99를 읽고 왜 평균 지연이 속이는지 이해하기
- 고객이 얼마나 많은 낡음을 견디는지에 근거해 TTL 고르기
- 작동을 방해하지 않는 실패 — 가장 값비싼 종류의 실패를 찾아내기

## 그리고 vSphere에서라면 이것은

vSphere에는 이 작업에 대응하는 것이 없고, 그것은 분명히 말할 가치가 있습니다. 캐시는 인프라
객체가 아니라 애플리케이션 아키텍처의 일부입니다. 하이퍼바이저는 인사 시스템의 답을 캐시할
수 없고, 그럴 수 있어서도 안 됩니다.

가상 머신의 세계에서 여러분이 할 일: Redis용 VM 요청, 설치, `requirepass` 구성, 자동 시작
구성, 그다음 — 여유가 되면 — 복제본용 두 번째 VM, sentinel, 페일오버 검증. 며칠의 작업, 그중
캐시 본체는 30분이 걸리고 나머지는 발판입니다. 어느 관리자에게나 익숙한 습관이 여기서
나옵니다: 「일단 복제본 없이 가고, 나중에 추가하죠.」 나중에, 추가하지 않습니다.

차이는 여기서 Redis가 더 빨리 설치된다는 것이 아닙니다. 차이는 복제본, 페일오버, 지표,
업데이트가 기본으로 도착하고, 「일단 복제본 없이」가 애초에 선택지로 떠오르지 않는다는
것입니다.

**vSphere가 더 편한 지점, 솔직히.** 세 가지입니다.

**완전한 제어.** 자신의 VM이라면 어떤 버전의 Redis든, 어떤 모듈이든, 어떤 `maxmemory-policy`든,
그리고 자신의 모니터링 스크립트를 옆에 설치할 수 있습니다. 여기서는 애플리케이션 파라미터로
드러난 것에만 접근할 수 있습니다 — 그리고 드러난 것은 전부와는 거리가 멉니다.

**진단.** VM의 Redis가 이상하게 동작하면 SSH로 들어가 `redis-cli INFO`, `SLOWLOG`, 시스템
카운터를 봅니다. 여기엔 SSH가 없고, 같은 정보에 이르려면 `kubectl exec`와 지표를 거쳐야
합니다 — 더 느리고 더 낮은 해상도로요.

**이웃의 예측 가능성.** Redis가 있는 VM은 vCenter에서 보이는, 보장된 코어와 메모리를 뜻합니다.
관리형 서비스는 다른 사람의 워크로드 옆 공유 노드에 삽니다; 리밋이 그것을 보호하지만,
「왜 오늘 2밀리초 더 느린가」는 전용 머신에서보다 알아내는 데 더 오래 걸릴 것입니다.
