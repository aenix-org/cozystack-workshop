# Lab 12 · 컨테이너 옆의 VM

| | |
|---|---|
| **소요 시간** | 30분, 그중 5~10분은 머신이 부팅되기를 기다리는 데 씁니다 |
| **무엇을 증명하나** | 옮기기 위해 레거시를 컨테이너화할 필요는 없습니다. 마이그레이션한 VM은 컨테이너 애플리케이션과 똑같은 ingress와 도메인으로 외부에 게시됩니다 |
| **필요한 것** | 테넌트 대시보드 접근 권한, 테넌트 `~/.kube/workshop`, `kubectl`, `virtctl` |

## 왜 중요한가

직원 명부는 "Propusk"에서 가장 오래된 부분입니다. 2011년에 만들어진 애플리케이션으로, 지금은 없는 외주 업체가 작성했습니다. Windows Server와, 한 번도 업데이트되지 않은 버전의 .NET에서 돌아갑니다. "잘 돌아가니까"라는 이유로요. 소스도 없고, 문서도 없습니다. 딱 네 페이지짜리 복구 안내서가 있을 뿐이고, 그 안에는 "세르게이에게 전화할 것"이라는 단계가 적혀 있습니다.

내부를 보면 작은 웹 애플리케이션입니다. 직원과 전화번호 목록이 담긴 HTTP 페이지를 제공합니다. 사람들은 브라우저로 열어 보고, 다른 서비스들은 이 애플리케이션에서 데이터를 조회합니다.

이 명부는 컨테이너로 옮겨 가지 않습니다. "아직은"이 아니라 영영 그렇습니다. 아무도 다시 빌드할 수 없는 애플리케이션은 물리적으로 컨테이너화할 수 없습니다. 그렇다고 이전을 포기할 이유는 되지 않습니다. "옮겨지지 않는 것들은 어떻게 할까?"라는 질문의 답은 이렇습니다. 있는 그대로, 가상 머신으로 가져오는 것입니다.

하지만 옮기는 것만으로는 부족합니다. 명부는 예전과 똑같이 외부에서 보여야 합니다. 이번 lab에서는 컨테이너 옆에 가상 머신을 세우고, **컨테이너 애플리케이션과 똑같은 방식으로** 외부에 게시하겠습니다. 플랫폼의 ingress와 도메인 이름을 통해서요. 플랫폼 입장에서 VM은 도메인 뒤에 있는 또 하나의 워크로드일 뿐이고, 그 뒤에 컨테이너가 있는지 아니면 OS 하나가 통째로 있는지 신경 쓸 필요가 없습니다.

## 미니 용어집

| 용어 | 무엇인가 | 무엇과 비슷하지만… |
|---|---|---|
| **VMInstance** | 클러스터 객체로서의 가상 머신 | **가상 머신**이지만, 텍스트로 기술되고 애플리케이션과 동일한 `kubectl`로 생성됩니다 |
| **VMDisk** | 머신과 별개로 존재하는 디스크 | **vmdk**이지만, 별개의 객체입니다. 머신보다 오래 남고 다른 머신에 붙일 수 있습니다 |
| **Instance type** | 플랫폼 목록에서 고르는 기성 머신 크기: vCPU 몇 개, 메모리 얼마 | vCPU/RAM을 손수 조정하는 것보다는 클라우드의 인스턴스 타입에 가깝습니다 |
| **Instance profile** | 게스트 OS를 위한 장치와 드라이버 세트 | **Guest OS type**이지만, 게스트가 보게 될 컨트롤러에 영향을 줍니다 |
| **cloud-init** | 머신이 처음 켜질 때 한 번 실행되는 최초 부팅 프로비저닝 스크립트 | **Customization Specification**이지만, UI의 마법사가 아니라 매니페스트 안의 평범한 YAML입니다 |
| **Service** | 클러스터 내부의 Pod 그룹을 위한 하나의 안정적인 주소 | **로드 밸런서 풀**이지만, 멤버 목록은 플랫폼이 레이블로 스스로 최신 상태로 유지합니다 |
| **Ingress** | 어떤 도메인을 어떤 Service로 보낼지에 대한 규칙, HTTPS와 함께 | **팜 앞단의 리버스 프록시**(nginx, HAProxy)이지만, 객체로 기술되고 도메인과 인증서는 플랫폼이 발급합니다 |
| **도메인** | 서비스가 HTTP로 외부에서 보이는 영구적인 이름 | **회사 로드 밸런서 뒤의 DNS 이름**이지만, DNS나 인증서를 위해 티켓을 넣을 필요가 없습니다 |
| **KubeVirt** | Kubernetes가 VM을 실행하는 메커니즘 | **하이퍼바이저**이지만, 두 번째 하이퍼바이저는 아닙니다. 그 밑은 어떤 Linux나 쓰는 것과 같은 QEMU/KVM입니다 |

## 1단계. VM 띄우기

📍 **위치:** 브라우저에서, 테넌트 대시보드에서.

VM은 Cozystack 매니지드 서비스이며, 여러분의 테넌트 안에 존재합니다. 두 단계로 생성되는데, 이 점은 바로 이해해 두는 것이 좋습니다.

### 먼저 디스크

테넌트 → **Create application** → `VM Disk`.

| 필드 | 값 | 왜 이렇게 |
|---|---|---|
| Name | `spravochnik` | 머신도 이 이름으로 불리게 됩니다 |
| Source | `Image` → `ubuntu-22.04` | 플랫폼의 기성 이미지 컬렉션에서 가져옵니다 |
| Storage | `20Gi` | `ubuntu-22.04` 이미지는 20Gi로 풀리므로 그보다 작게 지정할 수 없습니다 |
| Storage class | `replicated` | 데이터를 서로 다른 노드에 3부 복제 |

**왜 디스크는 머신 안의 필드가 아니라 별개의 객체인가.** 디스크가 머신보다 오래 남기 때문입니다. 머신을 통째로 삭제하고, 다른 타입, 다른 네트워크, 다른 이름으로 다시 만들어도 같은 디스크를 붙일 수 있습니다. vSphere에서 vmdk를 한 VM에서 떼어 다른 VM에 붙일 때 하는 것과 같은 일이며, 여기서는 이것이 모델에 명시적으로 표현되어 있습니다.

⚠️ **디스크는 원본 이미지보다 작을 수 없습니다.** 플랫폼의 `ubuntu-22.04`는 20Gi로 풀리므로, 플랫폼은 10Gi 디스크 요청을 거절합니다. 이미지를 더 작은 볼륨으로 복제해 넣을 방법이 없기 때문입니다. 여기서 작게 잡는 것이 크게 잡는 것보다 비쌉니다. 디스크는 나중에 키울 수는 있어도 줄일 수는 없습니다.

디스크가 채워질 때까지 기다리세요. 플랫폼이 이미지를 다운로드하고 풀며, 1~2분 걸립니다.

### 그다음 머신

테넌트 → **Create application** → `VM Instance`.

| 필드 | 값 | 왜 이렇게 |
|---|---|---|
| Name | `spravochnik` | |
| Instance type | `u1.medium` | 1 CPU, 4 GB — 클러스터 노드가 쓰는 것과 같은 크기 목록 |
| Instance profile | `ubuntu` | 게스트 OS를 위한 장치 세트 |
| Run strategy | `Always` | 계속 실행 상태로 유지. 스스로 꺼지면 다시 시작됩니다 |
| Disks | `spravochnik` | 여러분이 만든 디스크 |
| Cloud init | 아래 참조 | 포트 8080에 명부를 띄웁니다 |

cloud-init 필드에는:

```yaml
#cloud-config
password: ubuntu
chpasswd: { expire: false }
ssh_pwauth: true
write_files:
  - path: /opt/directory/index.html
    content: |
      <!doctype html><html lang="ru"><head><meta charset="utf-8"><title>Справочник</title></head><body><h1>Справочник сотрудников</h1><ul><li>Иванов И. — 101</li><li>Петров П. — 102</li></ul></body></html>
  - path: /etc/systemd/system/directory.service
    content: |
      [Unit]
      Description=Staff directory
      After=network.target
      [Service]
      ExecStart=/usr/bin/python3 -m http.server 8080 --bind 0.0.0.0 --directory /opt/directory
      Restart=always
      [Install]
      WantedBy=multi-user.target
runcmd: [ "systemctl daemon-reload", "systemctl enable --now directory" ]
```

이 cloud-init은 명부를 서버로 만듭니다. 직원 목록이 담긴 HTML 페이지를 넣고, 그것을 포트 8080에서 HTTP로 제공하는 서비스를 설정합니다. `python3`는 이미 Ubuntu 이미지에 있으므로 설치할 것도 없고 인터넷도 필요 없습니다. 포트 8080은 무작위로 고른 것이 아닙니다. 강사가 미리 만들어 둔 `Service spravochnik-http`가 바라보는 바로 그 포트입니다.

⚠️ **평문 비밀번호 — lab 전용입니다.** 실제 머신이라면 여기에 `sshKeys`가 있고 비밀번호는 아예 없을 것입니다. 워크숍 시간을 키 교환에 쓰지 않으려고 지름길을 택했습니다.

**같은 것을 텍스트로.** 디스크와 머신, 두 객체 모두 하나의 파일 `staff-directory-vm.yaml`에 들어 있고 하나의 명령으로 생성됩니다. 먼저 디스크, 그다음 머신 순입니다. 적용하기 전에 파일을 열어 그 안의 `tenant-workshopXX` 플레이스홀더를 여러분 자신의 테넌트 이름으로 바꾸세요. 그러지 않으면 객체가 엉뚱한 곳으로 갑니다.

```bash
# KUBECONFIG는 kubectl이 클러스터 주소와 로그인 데이터를 읽어 오는 변수입니다.
# 여기서는 테넌트 접근 파일이 필요합니다: VM은 관리 클러스터 위의 테넌트에 존재합니다.
export KUBECONFIG=~/.kube/workshop
# apply = "클러스터를 파일에 적힌 대로 만들어라". 객체가 없으면 생성하고,
# 객체가 있으면 기술된 상태로 맞춥니다.
#   -f   파일에서 기술 내용을 읽습니다
kubectl apply -f staff-directory-vm.yaml
```

**보게 될 것:** `created`가 붙은 두 줄 — 하나는 디스크, 하나는 머신.

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: VMDisk
```

버킷, 데이터베이스, 큐가 사는 것과 동일한 API 그룹입니다. 여기서 가상 머신은 자체 인터페이스를 가진 별도 서브시스템이 아니라, Redis와 똑같은 카탈로그 객체입니다. "하나의 인터페이스와 하나의 API로"라는 표현의 실체가 바로 이것입니다.

```yaml
spec:
  source:
    image:
      name: ubuntu-22.04
  storage: 20Gi
```

URL이 아니라 플랫폼의 공유 컬렉션에 있는 이미지 이름입니다. 컬렉션은 클러스터 전체에서 공유되며, 이미지는 한 번만 다운로드됩니다. `storage`는 이미지 자체보다 작을 수 없습니다 — `ubuntu-22.04`는 20Gi로 풀립니다. 자체 이미지가 필요하다면, 같은 자리에 링크를 넣는 `source.http`와 기존 디스크를 복제하는 `source.disk`가 있습니다.

```yaml
kind: VMInstance
spec:
  instanceType: u1.medium
```

머신 크기는 vCPU와 RAM 필드로 맞추는 것이 아니라 기성 목록에서 가져옵니다. `u1.medium`은 1 CPU에 4 GB입니다. Kubernetes 클러스터용 노드를 주문할 때도 같은 목록을 씁니다. 우연이 아닙니다. 클러스터 노드도 똑같이 VMInstance이기 때문입니다.

```yaml
  instanceProfile: ubuntu
```

게스트 OS 프로파일: 게스트가 인식할 수 있도록 어떤 컨트롤러, 드라이버, 장치를 머신에 넘길지 정합니다. 가장 가까운 유사물은 vSphere에서 VM을 만들 때의 "Guest OS type"이며, 결과도 같습니다. 프로파일을 잘못 고르면 부팅은 되지만 디스크를 보지 못하는 머신이 됩니다.

```yaml
  runStrategy: Always
```

원하는 전원 상태입니다. `Always` — 계속 실행: 게스트가 내부에서 꺼지면 머신은 다시 시작됩니다. `Halted` — 전원 꺼짐. `Manual` — 있는 그대로 두고 아무도 개입하지 않습니다. 표현에 주목하세요. Deployment의 `replicas`와 똑같습니다. "켜라"가 아니라 "켜진 상태로 유지하라"입니다.

```yaml
  disks:
    - name: spravochnik
```

VMDisk 객체 이름으로 된 디스크 목록입니다. 데이터용 두 번째 디스크는 바로 여기에 두 번째 줄로 추가합니다.

```yaml
  cloudInit: |
    #cloud-config
    write_files:
      - path: /opt/directory/index.html
      - path: /etc/systemd/system/directory.service
    runcmd: [ "systemctl daemon-reload", "systemctl enable --now directory" ]
```

cloud-init은 모든 클라우드 Linux 이미지가 이해하는 표준 최초 부팅 프로비저닝 메커니즘입니다. 처음 켤 때 한 번 실행됩니다. 여기서는 세 가지 일을 합니다: 명부의 HTML 페이지를 넣고, 그 페이지를 포트 8080에서 HTTP로 제공하는 systemd 서비스를 설정하고, 그 서비스를 시작합니다. vSphere의 Customization Specification에 해당하지만, UI의 마법사가 아니라 매니페스트 안의 텍스트입니다. 즉 Git에 담기고 다른 모든 것과 함께 리뷰됩니다.

바로 이 블록 덕분에 명부가 외부에서 보이게 됩니다. 강사가 미리 만든 `Ingress`가 도메인을 `Service spravochnik-http`로 보내고, 그것이 다시 머신 내부의 포트 8080으로 보냅니다. 8080의 서비스가 뜨는 즉시 게시는 알아서 이를 잡아냅니다.

### 이 매니페스트에 없는 것, 그리고 앞으로도 없을 것

**`replicas` 필드.** `VMInstance`에는 없습니다. 가상 머신은 단일 객체입니다. 머신이 두 대 필요하면 서로 다른 이름의 객체를 두 개 만듭니다.

이것은 `Deployment`와의 근본적인 차이이며, 결함이 아닙니다. Deployment의 복제본은 서로 교체 가능합니다. 어느 것이든 어떤 요청이라도 처리하고, 하나를 잃어도 큰일이 아닙니다. 가상 머신은 교체 가능하지 않습니다. 각자 자기 디스크에 자기 상태를 가지며, "똑같은 것을 하나 더 만들어라"는 컨테이너에서와는 전혀 다른 의미입니다.

실질적인 결과: **Pod 삭제 lab에서 본 자가 복구는 VM에는 존재하지 않습니다.** Pod를 삭제하면 클러스터는 몇 초 만에 새것을 만듭니다. VMInstance를 삭제하면 머신은 사라지며, 되살리는 유일한 방법은 살아남은 디스크를 붙여 손으로 하는 것뿐입니다. 여기서는 vSphere에서 있던 것과 정확히 같은 자리에 있으며, 이것은 진행하다가 발견하기보다 미리 알아 두는 편이 좋습니다.

</details>

첫 부팅은 3~5분 걸립니다. cloud-init이 파일시스템을 디스크 전체로 확장하고 명부 서비스를 띄웁니다. 마냥 손 놓고 기다리지는 않겠습니다. 다음 단계에서는 머신이 아직 부팅되는 동안 게시에 정확히 무슨 일이 일어나고 있는지 확인하겠습니다.

## 2단계. 머신이 부팅되는 동안 도메인을 두드려 보기

📍 **위치:** 여러분의 랩톱에서, 별도의 터미널 창에서. 또는 브라우저에서 바로.

강사가 명부를 미리 게시해 두었습니다. 여러분의 테넌트에는 이미 호스트가 `spravochnik.workshopXX.workshop.aenix.io`인 `Ingress spravochnik`와, 머신 내부의 포트 8080으로 보내는 `Service spravochnik-http`가 있습니다. 게시는 명부가 응답하기 시작하는 순간 그것을 받아들일 준비가 되어 있습니다. 머신이 다 로드되기를 기다리지 말고 지금 바로 확인해 봅시다.

```bash
# curl — "주소로 가서 응답을 보여줘". XX를 여러분 자신의 테넌트 번호로 바꾸세요.
#   --max-time 5   오래 기다리지 않고 5초 후에 포기합니다
curl --max-time 5 http://spravochnik.workshopXX.workshop.aenix.io
```

**보게 될 것:**

```
<html><head><title>503 Service Temporarily Unavailable</title></head>
<body><center><h1>503 Service Temporarily Unavailable</h1></center></body></html>
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 강사가 ingress를 만들었고, 도메인은 구성되어 있으며, 여러분은 머신을 띄웠습니다.
> 그런데 왜 도메인은 명부 페이지가 아니라 `503`으로 응답할까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

머신 내부의 명부가 아직 수신 대기하고 있지 않기 때문입니다.

`503`은 "ingress가 고장 났다"는 뜻이 아닙니다. ingress는 제자리에 있고 트래픽을 어디로 보낼지도 압니다. 여러분 머신의 Pod를 선택해 요청을 포트 8080으로 전달하는 `Service spravochnik-http`로요. 하지만 cloud-init이 파일시스템을 확장하고 서비스를 설정하는 동안에는 머신 내부의 8080에서 아무도 응답하지 않습니다. 서비스에는 준비된 백엔드가 하나도 없습니다. 그리고 ingress가 알려 주는 것이 바로 그것입니다. 경로는 있지만, 아직 응답할 이가 없다는 것.

여기서 응답 코드 자체가 진단입니다:

| 보이는 것 | 무슨 뜻인가 |
|---|---|
| `503` | ingress는 제자리에 있지만, 그 뒤에 준비된 백엔드가 없다 |
| `404` | ingress는 존재하지만, 규칙이 엉뚱한 서비스로 보낸다 |
| 무응답, 타임아웃 | 이 호스트를 가진 ingress가 애초에 만들어지지 않았다 |

**교훈은 이 오류보다 넓습니다.** ingress의 `503`은 ingress 자체가 아니라 백엔드 준비 상태에 관한 것입니다. 도메인 뒤의 애플리케이션이 죽거나 그 Pod가 아직 준비 검사를 통과하지 못했을 때도 똑같은 `503`을 받게 됩니다. 외부 게시와 워크로드 준비는 서로 다른 두 가지입니다. 도메인은 미리 설정되어 한동안 비어 있다가, 그 뒤에 응답할 준비가 된 누군가가 나타나는 바로 그때 채워집니다. VM에서는 "8080의 서비스가 떴을 때"이고, 컨테이너에서는 "Pod가 준비 검사를 통과했을 때"입니다. 메커니즘은 같으며, 이것이 "VM은 컨테이너 애플리케이션과 똑같은 방식으로 게시된다"는 표현의 의미입니다.

</details>

## 3단계. 머신에 접속하기

📍 **위치:** 대시보드에서, `spravochnik` 머신의 카드에서.

카드에는 콘솔이 있습니다. vSphere의 "Open Console"과 같은 화면입니다. 그것을 여세요. 로그인 `ubuntu`, 비밀번호 `ubuntu`.

⚠️ **콘솔에 검은 화면과 깜빡이는 커서만 보인다면 — 기다리세요.** cloud-init이 아직 끝나지 않았고, 프롬프트는 알아서 나타납니다. 머신을 재부팅하지 마세요. cloud-init 도중의 재부팅은 머신을 반쯤 구성된 상태로 남깁니다.

**터미널에서 하는 똑같은 로그인.** `virtctl`은 가상 머신을 다루는 별도 명령입니다: 콘솔, 포트 포워딩, 전원 켜고 끄기. 단일 파일로 설치되며, 정확한 방법은 `workshop/README.md`에 적혀 있습니다.

문법의 한 가지 특이점은 미리 짚고 넘어갈 만합니다. 안 그러면 첫 명령부터 거부당해 되돌아옵니다. `virtctl`의 대상은 벌거벗은 이름이 아니라 타입 접두사를 붙여 지정합니다: `vmi/<name>`. `vmi`는 virtual machine instance, 머신의 **실행 중인 인스턴스**입니다. 여러분이 만든 `VMInstance` 객체와 실행 중인 인스턴스는 API에서 서로 다른 두 객체입니다. 테넌트 접근 권한에서는 `virtualmachineinstances` **서브리소스**(`console`과 `portforward`)에 대해 권한이 부여되며, `virtualmachines` 객체 전체에 대해서가 아닙니다 — 벌거벗은 이름은 vm 객체에 닿아 `forbidden`으로 되돌아옵니다. 플랫폼은 인스턴스 이름을 접두사 `vm-instance-`에 여러분 머신 이름을 붙여 만듭니다: `spravochnik`는 인스턴스 `vm-instance-spravochnik`입니다.

```bash
# 테넌트 접근: 머신은 테넌트에 존재합니다
export KUBECONFIG=~/.kube/workshop
# console = 머신의 시리얼 콘솔에 접속. vSphere에서 "Open Console"이 주는 것과
# 같은 화면이며, 텍스트 기반일 뿐입니다:
#   --namespace  클러스터의 어느 구획을 볼지; 여러분 테넌트의 이름은
#                tenant- 뒤에 여러분 로그인을 붙인 것입니다. XX를 여러분 번호로 바꾸세요
#   vmi/...      대상: VMInstance 기술이 아니라 머신의 실행 중인 인스턴스
virtctl console --namespace=tenant-workshopXX vmi/vm-instance-spravochnik
```

접속 후 화면이 비어 있으면 — Enter를 누르세요. 그러면 로그인 프롬프트가 나타납니다. 콘솔에서 나가려면 — `Ctrl+]`. 여러분 테넌트에서 실행 중인 모든 인스턴스의 이름은 `kubectl --kubeconfig ~/.kube/workshop get vminstance -n tenant-workshopXX`로 확인합니다.

내부에서 보면 평범한 Ubuntu입니다. 명부가 떴는지 확인하세요:

```bash
uname -a                       # 커널과 아키텍처: 베어메탈 서버에서와 똑같은 줄
systemctl status directory     # 명부 서비스: active (running)이어야 합니다
curl -s localhost:8080 | head  # 같은 페이지, 다만 머신 내부에서 요청한 것
```

`systemctl status directory`가 `active (running)`을 보여 주고 `localhost:8080`로의 `curl`이 직원 목록이 담긴 HTML을 반환했다면 — 서버는 준비되었고, 외부의 게시는 곧 `503`을 페이지로 바꿀 참입니다. 내부에는 Kubernetes의 흔적이 없으며, 없는 것이 맞습니다. 게스트는 자신이 클러스터 안에 있다는 것을 모릅니다. vSphere의 VM이 vCenter에 대해 알 필요가 없는 것과 똑같습니다.

## 4단계. 도메인이 응답한다 — 명부가 게시되었다

📍 **위치:** 여러분의 랩톱에서. 또는 브라우저에서.

`503`을 반환했던 그 요청이지만, 이제 8080의 서비스가 떴습니다. 여러분 자신의 번호를 넣으세요.

```bash
curl http://spravochnik.workshopXX.workshop.aenix.io
```

**보게 될 것** — 명부 페이지의 HTML:

```html
<h1>Справочник сотрудников</h1><ul><li>Иванов И. — 101</li><li>Петров П. — 102</li></ul>
```

이 주소를 브라우저에서 열면 똑같은 목록을 보게 됩니다. 명부는 사람이 읽기 좋은 도메인 이름으로 외부에서 보이며, 플랫폼이 제공하는 HTTPS와 함께, 네트워크나 인증서 티켓 하나 없이 그렇습니다.

**방금 무슨 일이 일어났는지 풀어 봅시다.**

Kubernetes에 대해 아무것도 모르는 Ubuntu 가상 머신이 평범한 포트에서 평범한 HTTP로 수신 대기하고 있습니다. 외부에서는 도메인 `spravochnik.workshopXX.workshop.aenix.io`로 도달하며, 요청은 컨테이너 애플리케이션을 게시하는 것과 똑같은 ingress를 통해 그 머신까지 전달됩니다. 게스트 내부에 에이전트도 없고, 게이트웨이도 없고, "통합"도 없습니다. 게시 입장에서는 도메인 뒤에 무엇이 있든 — nginx Pod든 가상 머신 하나가 통째로든 — 차이가 없습니다. `Service`가 보이고, `Service` 뒤에 준비된 백엔드가 있으며, 그것으로 충분합니다.

이것이 바로 "옮기기 위해 레거시를 컨테이너화할 필요는 없다"는 말의 의미입니다. 2011년의 명부는 늘 하던 대로 계속 돌아가며 — 외부에서 보면 여느 새로운 "Propusk" 서비스와 똑같아 보입니다: 이름, 도메인, HTTPS.

## 검증

📍 **위치:** 여러분의 랩톱에서, `kubectl`로 작업하던 바로 그 창에서.

스크립트는 객체의 존재가 아니라 실질적인 동작을 확인합니다: 도메인 이름이 `200`을 반환하고 그것이 명부 페이지인지, 머신 자체가 실행 중인지, 그것을 게시하는 `Ingress`가 제자리에 있는지. 도메인 검사는 테넌트 접근 없이도 동작합니다 — `curl`만 있으면 됩니다. 테넌트 접근은 머신 상태 검사를 추가합니다.

```bash
# 테넌트 접근: 여기서 스크립트는 VM 자체와 Ingress를 가져옵니다
export KUBECONFIG=~/.kube/workshop
# tenant- 라는 단어를 뺀 여러분의 로그인: 여기서 스크립트는 구획 이름 tenant-workshopXX와
# 도메인 이름 spravochnik.workshopXX.workshop.aenix.io를 모두 만듭니다
export COZY_TENANT=workshopXX
# 이름 앞의 ./는 "현재 폴더의 파일", 즉 labs/12-vm의 파일을 뜻합니다
./check.sh
```

⚠️ **Windows에서는 스크립트를 PowerShell이 아니라 WSL에서 실행합니다** — 설치 방법은 lab 0 초반에 적혀 있습니다. WSL이 없어도 lab은 완료할 수 있지만, 아티팩트 리포트는 없습니다.

`COZY_TENANT`는 필수입니다 — 없으면 스크립트는 바로 멈춥니다: 도메인이 그것으로부터 만들어지기 때문입니다. 테넌트 접근이 설정되어 있지 않으면 머신 상태 검사는 경고와 함께 건너뛰며, 핵심 검사인 도메인 응답은 그래도 실행됩니다.

## 정리

모니터링 lab을 계획하고 있다면 가상 머신을 남겨 두세요. 그 소비량도 그래프에 나타나며, 좋은 예시가 됩니다. 그렇지 않다면 — 대시보드로 머신과 디스크를 삭제하세요.

⚠️ **올바른 순서로 삭제하세요: 머신 먼저, 그다음 디스크.** 실행 중인 머신에 붙어 있는 디스크는 삭제되지 않으며, 삭제 상태에 걸려 버린 객체가 남게 됩니다.

명부를 게시하는 `Ingress`와 `Service`는 강사가 만든 것입니다 — 건드리지 마세요. 이 테스트베드의 다음 참가자에게 필요합니다.

여기서 정리의 비용은 다른 lab보다 솔직히 더 높습니다. 데이터가 담긴 디스크는 데이터가 담긴 디스크이며, 즉시 사라지지 않습니다. 다른 한편으로, 그것을 만드는 데는 디스크 공간 티켓도, 승인도 필요하지 않았습니다.

## 이제 우리가 할 수 있는 것

- 테넌트에서 가상 머신을 띄우기 — 마우스로도, 텍스트로도
- 왜 디스크와 머신이 두 개의 객체인지, 그리고 그것이 무엇을 가져다주는지 설명하기
- 워크로드를 ingress와 도메인으로 외부에 게시하기 — 컨테이너와 똑같은 방식으로
- ingress의 `503`을 고장이 아니라 "아직 도메인 뒤에 응답할 이가 없다"로 읽기
- 레거시를 마이그레이션하는 데 다시 쓰기가 필요하지 않다는 것을 실제 예제로 보여 주기

## vSphere라면 이것은

vSphere의 VM은 익숙한 홈그라운드이며, 거기서는 익숙한 방식으로 만듭니다. 차이는 머신 자체가 아니라, 그것을 사람이 읽기 좋은 이름으로 외부에 노출하는 데 있습니다.

vSphere에서 이 머신을 도메인으로 게시하려면 별도 제품으로서의 리버스 프록시나 로드 밸런서, 외부 주소를 위한 네트워크 티켓, 이름을 위한 DNS 티켓, 인증서를 위한 보안 티켓이 필요합니다. 서너 개의 명령, 서너 개의 시스템, 그리고 "이걸 다 누가 운영하나"라는 일반적인 물음. 여기서 게시는 강사가 미리 설정해 둔 `Ingress` 객체 하나이고, 도메인은 머신이 응답하기 시작하는 바로 그 순간 채워집니다.

**솔직히 vSphere가 더 편한 지점.** 가상 머신 자체를 관리하는 일이라면 vCenter가 여전히 더 풍부하며, 아닌 척할 이유가 없습니다:

| 무엇 | vSphere | Cozystack |
|---|---|---|
| 템플릿과 클로닝 | 성숙하고, 게스트 커스터마이징 포함 | 디스크 클로닝은 있지만, 커스터마이징 마법사는 없음 |
