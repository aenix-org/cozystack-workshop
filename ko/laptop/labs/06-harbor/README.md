# 랩 6 · 자신만의 프라이빗 이미지 레지스트리

| | |
|---|---|
| **소요 시간** | 45분, 그중 10분은 대기 |
| **무엇을 증명하나** | 이미지 레지스트리는 10분 만에 뜨고, 클러스터는 오직 그곳에서만 이미지를 가져올 수 있습니다 |
| **필요한 것** | 랩 0에서 만든 클러스터, `kubectl`, 노트북의 `docker`(또는 `podman`), 대시보드 접근 |

## 왜 중요한가

"Passes" 서비스가 정보 보안 부서까지 올라갔고, 답장 이메일이 돌아왔습니다.

> 컨테이너 이미지를 인터넷의 퍼블릭 레지스트리에서 가져오고 있습니다. 이는 용납할 수 없습니다:
> 이미지 안에 무엇이 들었는지 아무도 검증하지 않았고, 같은 이름 아래에서 내용이 바뀔 수 있으며,
> 외부 리소스를 사용할 수 없게 되면 프로덕션 서비스가 시작되지 않습니다. 모든 이미지는
> 조직의 내부 레지스트리에 저장되어야 합니다.

반박할 것이 없습니다 — 모든 지적이 타당합니다. `latest` 태그가 붙은 퍼블릭 이미지는 오늘과
내일이 다를 수 있습니다. 이미지 작성자가 그것을 삭제할 수도 있습니다. 외부 레지스트리는 가장
곤란한 순간에 다운로드 속도를 제한할 수 있습니다 — 이것은 가정이 아니라, 큰 퍼블릭 레지스트리는
모두 그렇게 합니다.

그래서 자신만의 레지스트리가 필요합니다. 보통 이것은 그 자체로 하나의 프로젝트입니다: VM 요청,
설치, 인증서, 스토리지, 백업, 누군가의 한 분기. 오늘은 카탈로그의 한 항목일 뿐입니다.

그리고 레지스트리가 여러분의 것이고 비공개이므로, 클러스터에 그에 대한 접근 권한을 주어야 합니다.
여기서 모두가 걸려 넘어지고, 우리도 일부러 걸려 넘어질 것입니다.

## 간단한 용어집

| 용어 | 무엇인가 | 비슷한 것… 하지만 |
|---|---|---|
| **이미지(image)** | 실행에 필요한 모든 것을 담은 애플리케이션의 스냅샷 | **VM 템플릿**과 비슷하지만 불변입니다: 안으로 들어가 고칠 수 없고, 새로 빌드합니다 |
| **레이어(layer)** | 이미지의 한 부분. 이미지는 레이어로 만들어지고, 레이어는 재사용됩니다 | 서로 다른 이미지의 동일한 레이어는 레지스트리에 한 번만 저장됩니다 |
| **태그(tag)** | 이미지의 버전 레이블: `passes-api:v1` | **템플릿 버전 이름**과 비슷하지만, 태그는 다른 이미지로 다시 지정될 수 있고, 그것이 문제의 주된 원인입니다 |
| **레지스트리(registry)** | HTTP로 제공되는 이미지 저장소 | **Content Library**와 비슷하지만, 템플릿 전체를 복사하는 대신 실행할 때마다 네트워크로 레이어를 나눠줍니다 |
| **Harbor** | UI, 프로젝트, 권한, 취약점 스캐너를 갖춘 레지스트리 | **Content Library + 권한 + 리포트**와 비슷하지만, 이미지 내용을 검사하고 서명할 수 있습니다 |
| **Harbor의 프로젝트** | 자체 권한을 가진 레지스트리 내부의 영역 | **Content Library의 폴더**와 비슷하지만, 공개일 수도 비공개일 수도 있고, 그에 따라 자격 증명이 필요한지가 정해집니다 |
| **`imagePullSecret`** | 레지스트리의 로그인과 비밀번호를 담고 노드가 읽는 Secret | **Content Library 연결용 계정**과 비슷하지만, 여러분이 아니라 **노드**에게 필요합니다; 여러분의 `docker login`은 클러스터에 아무 도움이 되지 않습니다 |
| **Dockerfile** | 이미지를 빌드하는 방법을 담은 지침 | **템플릿을 준비하는 지침**과 비슷하지만, 빌드할 때마다 전체가 처음부터 실행됩니다 |
| **Downward API** | 환경 변수를 통해 Pod에게 자기 자신에 대한 정보를 주는 방법 | **VMware Tools의 게스트 변수**와 비슷하지만, 값은 실행 시 클러스터가 주입합니다; 애플리케이션이 요청하지 않습니다 |

## 두 개의 kubeconfig: 헷갈리지 마세요

이제부터 이 랩은 두 개의 서로 다른 클러스터를 다루므로, 첫 명령 전에 이들을 구분해 두는 것이
좋습니다.

| Kubeconfig | 무엇인가 | 무엇을 하는가 |
|---|---|---|
| `~/.kube/workshop` | Cozystack 관리 클러스터, 여러분의 테넌트 | 매니지드 서비스를 봅니다: Harbor, 데이터베이스, 큐 |
| `~/lab.kubeconfig` | 랩 0에서 만든 **여러분의** `lab` 클러스터 | 애플리케이션을 배포합니다 |

둘 다 대시보드에서 가져옵니다. 테넌트용은 `kubeconfig-tenant-workshopXX` Secret에 있고
(Secrets 탭), 클러스터용은 여러분의 `lab` 클러스터 접근 섹션에 있습니다.

⚠️ **이 랩에서 "나는 아무것도 안 돼요"의 가장 흔한 원인은 명령이 엉뚱한 클러스터로 간
것입니다.** 모든 명령 블록 앞에 그것이 어느 클러스터를 향하는지 적혀 있습니다. 확신이 서지
않으면:

```bash
# echo는 변수 값을 출력합니다: 지금 kubectl이 어떤 접근 파일을 쓰고 있는지 보여줍니다.
# 비어 있으면 kubectl은 여러분이 생각하는 파일이 아니라 기본 파일 ~/.kube/config를 사용합니다.
echo $KUBECONFIG

# get nodes = "클러스터의 노드를 보여줘". 여기서는 리트머스 시험지입니다:
# 그 답으로 명령이 두 클러스터 중 어디로 갔는지 알 수 있습니다.
kubectl get nodes
```

`lab` 클러스터에는 `kubernetes-lab-md0-...` 같은 이름의 노드가 하나 있습니다. 관리 클러스터에서는
이 명령이 대부분 거부를 반환합니다 — 테넌트는 노드를 볼 권한이 없습니다.

```bash
# 이 lab의 모든 명령은 lab 폴더에서 실행합니다 — 그 폴더로 이동하세요

```

| `passes-broken.yaml` | **일부러 불완전하게** 만든 파일: 레지스트리 접근 자격 증명 없음 | 거부를 직접 눈으로 보려고 적용합니다 |
| `passes.yaml` | 같은 파일이지만 레지스트리 접근이 있는 것 | 파악한 뒤에 적용합니다 |
| `check.sh` | 이미지가 인터넷이 아니라 여러분의 Harbor에서 왔는지 확인 | 랩 마지막에 실행합니다 |

## 1단계. Harbor 생성

📍 **위치:** 브라우저에서, Cozystack 대시보드. 레지스트리는 여러분의 lab 클러스터의 일부가
아니라 공유 테넌트 리소스이므로, 클러스터 자체를 만들었던 바로 그 곳에서 생성합니다.

테넌트 → **Create application** → `Harbor`.

| 필드 | 값 | 이유 |
|---|---|---|
| Name | `harbor` | 레지스트리 주소의 일부가 됩니다; 어떤 것이 나오는지는 생성 후 보게 됩니다 |
| Host | 비워 둡니다 | 그러면 주소가 이름과 테넌트 도메인으로부터 스스로 조합됩니다 |
| Storage class | `replicated` | 데이터가 서로 다른 노드에 세 벌로 보관됩니다 |
| Trivy → enabled | **끄기** | 취약점 스캐너가 수 기가바이트 크기의 데이터베이스를 내려받습니다; 학습용 테스트베드에서는 이십 분의 추가 대기입니다 |
| Database → replicas | `1` | 오늘은 레지스트리 데이터베이스의 내결함성을 시험하지 않습니다 |
| Database → size | `5Gi` | |
| Redis → replicas | `1` | |
| Redis → size | `1Gi` | |
| Core / Registry preset | 제안된 대로 둡니다 | |

⚠️ **이 폼의 Redis는 Harbor 자체의 내부 캐시이며, 다음 랩과는 아무 관련이 없습니다.** 캐싱에
관한 랩에서는 여러분의 애플리케이션을 위한 별도의 Redis를 세웁니다. 이름은 같지만 역할은
다릅니다.

생성을 누르고 기다립니다. Harbor는 5~10분 만에 뜹니다: 이것은 하나의 애플리케이션이 아니라 여러
서비스에 데이터베이스, 그리고 이미지 레이어 자체를 위한 오브젝트 스토리지까지 더해진 것입니다.

⚠️ **Harbor가 "not ready" 상태로 십오 분 넘게 머무른다면** — 무슨 일이 벌어지는지 보세요:
`kubectl -n tenant-workshopXX get pods | grep harbor`. 대개는 플랫폼 전체가 공유하는 설치 큐
때문입니다: 여러분의 애플리케이션이 그 안에서 다른 사람들 것 뒤에 서서 기다리고 있는 것입니다.

Harbor는 이미지 레이어를 S3 호환 스토리지에 저장하고, 그것을 위한 Bucket은 스스로 생성됩니다 —
이를 위해 테넌트에 자신의 스토리지를 켤 필요는 없고, 상위의 것으로 충분합니다. 그래도 삼십 분
넘게 Pod가 나타나지 않으면, 이 명령의 출력과 함께 워크숍 채팅에 글을 남기세요.

## 2단계. 자격 증명을 가져와 레지스트리에 로그인

📍 **위치:** 대시보드에서, 그다음 노트북의 터미널에서.

여러분이 만든 `harbor` 애플리케이션을 열고 secret이 있는 탭을 찾으세요. 거기에 레지스트리 자격
증명이 담긴 secret이 있고, 그 안에 필요한 키가 세 개 있습니다:

| 키 | 무엇이 들어 있나 |
|---|---|
| `url` | 여러분 레지스트리의 주소, `https://harbor-....<테스트베드 도메인>` 형태 |
| `admin-password` | 관리자 비밀번호 |
| `redis-password` | Harbor의 내부 비밀번호, 여러분에게는 필요 없음 |

로그인은 `admin`입니다.

⚠️ **레지스트리 주소를 추측하지 말고, `url` 키에서 가져오세요.** 플랫폼은 애플리케이션 이름 앞에
서비스 유형을 접두사로 붙이므로, 주소가 이름으로 기대한 것과 다르게 나올 수 있습니다. 같은
주소가 애플리케이션의 ingress 목록에도 보입니다.

같은 비밀번호를 명령으로도 얻을 수 있습니다. 테넌트는 **모든** secret을 통째로 읽을 수는
없습니다 — 직접 확인해 보세요, `kubectl auth can-i get secrets`는 `no`라고 답합니다. 하지만
여러분이 만드는 각 애플리케이션마다 플랫폼은 바로 그 자격 증명만 허용하는 별도의 규칙을 만들어
둡니다:

```bash
# get secret = "Secret 객체를 보여줘". secret 이름은 애플리케이션 유형의 접두사와
# 그 이름으로 조합됩니다: harbor- + harbor.
#   -n tenant-workshopXX  어느 namespace에서 찾을지 — 여러분의 테넌트
#   -o jsonpath='...'     객체 전체를 출력하지 않고 필드 하나만 꺼냅니다
#   base64 -d             디코딩: secret 안의 값은 base64로 저장됩니다
#   ; echo                줄바꿈을 덧붙입니다, 그렇지 않으면 비밀번호가 프롬프트와 붙습니다
kubectl -n tenant-workshopXX get secret harbor-harbor-credentials \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo
```

대시보드는 base64를 만질 필요가 없다는 점에서 더 편리합니다. 명령은 스크립트에 넣을 수 있다는
점에서 더 편리합니다.

브라우저에서 주소를 열고 로그인하세요. 프로젝트가 하나뿐인 Harbor UI가 보입니다, `library`.

이제 터미널에서 같은 것을 합니다. `docker login`은 사용자 이름과 비밀번호를 묻고 자격 증명을
여러분의 노트북에, 파일 `~/.docker/config.json`에 저장합니다. 그 뒤로 `docker push`와
`docker pull`은 아무것도 묻지 않고 이 레지스트리로 갑니다.

```bash
# login = "이 레지스트리의 자격 증명을 기억해줘".
# 인자는 url 키에서 가져온 레지스트리 주소입니다; 여기서 harbor-harbor.workshop03.example.org는 예시입니다.
# 명령은 사용자 이름(admin)과 비밀번호를 묻습니다; 비밀번호는 입력해도 화면에 표시되지 않습니다.
docker login harbor-harbor.workshop03.example.org
```

이제부터 본문에서 `harbor-harbor.workshop03.example.org`는 **여러분의** 주소입니다 — 자기 것으로 바꾸세요.

**여러분이 보게 될 것:**

```
Login Succeeded
```

⚠️ **이 `docker login`은 여러분의 노트북이 레지스트리에 로그인하는 법을 가르쳤을 뿐입니다 —
오직 그것만.** 클러스터에는 아무것도 해 주지 않았습니다. 이것을 기억하세요; 랩 조금 뒤에서
필요합니다.

## 3단계. 비공개 프로젝트 만들기

📍 **위치:** 브라우저에서, Harbor 안에서.

**Projects** → **New Project**.

| 필드 | 값 | 이유 |
|---|---|---|
| Project Name | `passes` | 서비스당 하나의 프로젝트 — 그래야 권한 부여가 더 쉽습니다 |
| Access Level | **Public을 체크하지 않기** | 보안팀은 비공개 레지스트리를 요구했지, "여러분 것이지만 인터넷 전체에 열린" 것을 요구하지 않았습니다 |
| Storage quota | `-1` (제한 없음) | 테스트베드에서는 쿼터가 방해만 됩니다 |

처음부터 있던 `library` 프로젝트는 공개입니다. 거기서는 아무런 자격 증명 없이 이미지를 가져옵니다.
우리가 그것을 쓰지 않는 이유가 바로 그것입니다: 이 랩이 그것을 중심으로 만들어진 바로 그 접근
오류를 보여주지 않기 때문입니다.

## 4단계. 이미지 빌드

📍 **위치:** 노트북에서.

안에 무엇이 있는지 살펴봅시다.

파일 `app/main.go`, Go로 약 일흔 줄. 정확히 두 가지 일을 합니다.

**`/healthz`에 `ok`라는 단어로 응답합니다.** 이것은 준비 상태 확인 주소입니다: 클러스터가 여기를
두드리고, 응답을 받기 전까지는 복제본으로 트래픽을 보내지 않습니다.

**`/`에는 작은 JSON으로 응답하며**, 그 안에서 자기 자신에 대해 알립니다:

```json
{
  "service": "passes-api",
  "version": "v1",
  "pod": "passes-api-7d9f8c6b4-xk2mp",
  "node": "kubernetes-lab-md0-abc12",
  "namespace": "default",
  "registry": "harbor-harbor.workshop03.example.org",
  "time": "2026-08-21T09:12:33Z"
}
```

애플리케이션은 자신의 이름, 노드, namespace를 어떻게 알까요? **알아내지 않습니다.**
클러스터가 실행 시 그것들을 환경 변수에 넣어 줍니다:

```go
Pod:  env("POD_NAME", "неизвестно"),
Node: env("NODE_NAME", "неизвестно"),
```

그리고 매니페스트에는 거기에 무엇을 넣을지 적혀 있습니다:

```yaml
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
```

이것을 downward API라고 부릅니다 — "위에서 아래로 내려준 정보". vSphere에서 가장 가까운 유사물은
VMware Tools가 머신 안으로 건네주는 게스트 변수입니다. 차이는 여기서 애플리케이션이 아무것도 묻지
않고 어디에도 가지 않는다는 점입니다: 프로세스가 시작될 무렵이면 값은 이미 환경에 들어 있습니다.
클러스터 API로 향하는 클라이언트도, 그 API에 대한 권한도 필요 없습니다.

**애플리케이션에는 외부 라이브러리가 하나도 없고, Go 표준 라이브러리만 있습니다.** 이것은 멋
부림이 아닙니다: 의존성이 있는 빌드는 패키지를 받으러 인터넷으로 갈 것이고, 이 랩 전체가 보안팀이
인터넷 접속을 금지한 데서 시작했습니다.

파일 `app/Dockerfile`은 빌드 지침입니다. 두 개의 단계가 있습니다:

```dockerfile
FROM golang:1.23-alpine AS build
...
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/passes-api .

FROM alpine:3.21
COPY --from=build /out/passes-api /usr/local/bin/passes-api
```

첫 번째 단계는 빌드 단계입니다. 여기에는 Go 컴파일러 전체, 대략 350 MB가 필요합니다. 두 번째
단계는 실제로 클러스터로 나가는 것입니다: 첫 번째 단계에서 **완성된 바이너리만** 옮겨오고,
나머지는 전부 버립니다.

결과는 삼백오십이 아니라 약 십 메가바이트의 이미지입니다. 크기만의 문제가 아닙니다: 안에는
컴파일러도, 소스도, 패키지 관리자도 없습니다. 컨테이너에 어떻게든 들어온 자에게도 쓸 만한 것이
없습니다.

이것을 가상 머신 템플릿에서 어떻게 되는지와 비교해 보세요. 템플릿은 운영체제 전체를, 그리고
언젠가 거기 들어간 적이 있다면 컴파일러까지 함께 안에 담고 있습니다. 사후에 그것을 줄이는 것은
거의 불가능합니다.

마지막 줄들:

```dockerfile
RUN adduser -D -u 10001 app
USER 10001
```

애플리케이션은 root로 실행되지 않습니다. 제대로 구성된 클러스터에서는 Pod가 root로 실행되도록
허용되지 않으며, 이는 우리가 까다롭게 구는 것이 아니라 요즘의 어떤 클러스터에서든 마주치게 될
요구 사항입니다.

</details>

`docker build` 명령이 이미지를 빌드합니다: `Dockerfile`을 읽고, 거기 기술된 단계를 실행하며,
결과를 여러분의 노트북에 있는 이미지 저장소에 넣습니다. 결과가 저장되는 이름은 `-t` 플래그로
지정하며 세 부분으로 이루어집니다:

| 부분 | 무슨 뜻인가 |
|---|---|
| `harbor-harbor.workshop03.example.org` | 레지스트리 주소 — 이미지를 가지러 갈 곳 |
| `passes/passes-api` | 레지스트리 안의 프로젝트와 이름 |
| `v1` | 버전 태그 |

레지스트리 주소는 이미지 이름의 일부입니다. 자신의 레지스트리로 옮기는 것이 모든 매니페스트를
바꾸는 이유가 바로 이것입니다: 이미지 이름이 다른 것이 되기 때문입니다.

빌드합시다. 주소를 자기 것으로 바꾸세요:

```bash
cd labs/06-harbor

# build = "Dockerfile로 이미지를 빌드해줘".
#   --platform linux/amd64  어느 프로세서용으로 빌드할지; 클러스터 노드는 x86이고,
#                           노트북은 ARM일 수 있습니다 — 그러면 플래그 없이는 엉뚱한 것이 나옵니다
#   -t <주소>/<프로젝트>/<이름>:<태그>  결과에 붙일 이름. 이름 앞부분의 레지스트리 주소가
#                           나중에 docker push가 보낼 곳입니다
#   app/                    마지막 인자 — Dockerfile과 소스가 있는 폴더;
#                           그 내용 전체가 빌더에게 전달됩니다
docker build --platform linux/amd64 -t harbor-harbor.workshop03.example.org/passes/passes-api:v1 app/
```

⚠️ **`--platform linux/amd64`은 장식이 아닙니다.** Apple Silicon(M1–M4) Mac이나 ARM 노트북을
쓴다면, 이 플래그 없이는 ARM 이미지가 빌드됩니다. 오류 없이 빌드되고, 오류 없이 push되지만,
클러스터에서 — 거기 노드는 평범한 x86입니다 — Pod가 `CrashLoopBackOff`에 빠지고, 로그에는
`exec format error`가 찍힙니다. 이것은 진단에 오래 걸립니다, 왜냐하면 주변의 무엇도 문제가
프로세서 아키텍처라는 것을 암시하지 않기 때문입니다.

**여러분이 보게 될 것** — 빌드 단계에 관한 줄들과, 마지막에:

```
Successfully tagged harbor-harbor.workshop03.example.org/passes/passes-api:v1
```

## 5단계. 이미지를 여러분의 레지스트리로 보내기

📍 **위치:** 노트북에서.

빌드된 이미지는 아직 여러분의 디스크에만 있습니다. `docker push`는 그것을 레이어 단위로
레지스트리에 보냅니다; 레지스트리에 이미 있는 레이어는 다시 보내지 않습니다.

```bash
# push = "이미지를 레지스트리로 보내줘". 어디로 보낼지는 docker가 이미지 이름에서 가져옵니다:
# 이름의 첫 부분이 레지스트리 주소이고, docker login에서 받은 자격 증명과 함께 그리로 갑니다.
docker push harbor-harbor.workshop03.example.org/passes/passes-api:v1
```

**여러분이 보게 될 것** — 레이어들이 나가는 모습과, 마지막에 긴 해시가 담긴 줄, 곧 `digest`.

브라우저에서 Harbor를 들여다보세요: **Projects** → `passes` → 거기에 `passes/passes-api`
리포지토리가 나타났고, 그 안에 태그 `v1`이 있습니다. 크기, 날짜, 그리고 그 동일한 `digest`를 볼
수 있습니다.

그 `digest`는 이미지의 정확한 내용입니다. 태그 `v1`은 내일 다른 이미지로 다시 지정될 수 있고
아무도 알아채지 못합니다; `digest`는 위조할 수 없습니다. 여기서 누구나 조만간 배우는 규칙이
나옵니다: **프로덕션에는 태그가 아니라 digest로 배포한다.**

## 6단계. 클러스터에 배포

📍 **위치:** 노트북에서, `lab` 클러스터.

```bash
# KUBECONFIG는 kubectl에게 어떤 접근 파일을 쓸지 알려줍니다. 여러분의 `lab` 클러스터로 전환합니다:

# 터미널 창을 닫을 때까지 유효합니다.
```

랩 폴더에 `passes-broken.yaml`이 있습니다. 레지스트리 주소 대신 자리표시자 `HARBOR-HOST`가 들어

```bash
sed -i '' 's|HARBOR-HOST|harbor-harbor.workshop03.example.org|g' passes-broken.yaml
```

> **더 읽기 전에 멈추고 생각해 보십시오.**

> 여러분은 방금 `docker login`으로 레지스트리에 성공적으로 로그인했고 이미지를 성공적으로 그리로
> 보냈습니다. 레지스트리는 여러분을 압니다. 그런데 왜 클러스터는 거부당할까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

**이미지를 내려받는 것은 여러분이 아닙니다.** `kubelet`이 내려받습니다 — 클러스터 노드의
서비스입니다. 그것은 다른 머신, 다른 프로세스, 다른 사용자입니다.

여러분의 `docker login`은 자격 증명을 **여러분의 노트북**에 있는 파일 `~/.docker/config.json`에
기록했습니다. 클러스터 노드는 그 파일에 대해 아무것도 모르고, 알 수도 없습니다: 그것과 여러분의
노트북 사이에는, 여러분이 그리로 명령을 보낸다는 사실 말고는 공통된 것이 전혀 없습니다.

랩 조금 앞의 `docker login` 뒤에 있던 경고로 돌아가 보세요. 거기 적혀 있던 것이 바로 이것이지만,
그때는 결과가 아직 보이지 않았습니다.

**올바르게 하는 법.** 자격 증명을 클러스터 자체에 — 특별한 종류의 Secret 객체에 — 넣어야 하고,
그다음 애플리케이션의 매니페스트에서 내려받을 때 어떤 secret을 쓸지 지정해야 합니다. 그런 secret을
`imagePullSecret`이라고 부릅니다.

**왜 클러스터에는 여러분 것이 아니라 별도의 자격 증명이 필요한가.** 세 가지 이유가 있고, 세 가지
모두 실용적입니다.

첫째: 여러분이 자리에 없을 수 있습니다. 노드는 새벽 세 시에 재시작해 이미지를 다시 내려받으러
갑니다. 만약 그것이 여러분의 계정으로 갔다면, 모든 것이 여러분이 아직 이 회사에서 일하고 있고
비밀번호가 만료되지 않았다는 데 달려 있게 됩니다.

둘째: 권한이 다릅니다. 여러분에게는 레지스트리에 빌드를 보내기 위해 **쓰기** 권한이 필요합니다.
클러스터에는 **읽기**만 필요합니다. 클러스터에 레지스트리에서 이미지를 지울 권한을 주는 것은 나쁜
생각이고, 여러분의 계정으로는 바로 그것을 준 셈이 됩니다.

셋째: 흔적이 다릅니다. 레지스트리 로그에 이미지를 `admin`이 아니라 `robot$passes-puller`가
내려받았다고 나오면, 인시던트 조사가 가능해집니다.

**왜 노드를 직접 구성하지 않는가.** 자격 증명을 노드에 바로, 컨테이너 런타임 설정에 넣을 수
있습니다 — 그러면 `imagePullSecret`이 필요 없습니다. 사람들이 가끔 그렇게 합니다. 하지만
클러스터의 노드는 일회용입니다: 업그레이드 시 다시 만들어지고, 부하가 늘면 추가되고, 장애 시
제거됩니다. 노드에서 손으로 만든 설정은 노드가 처음 교체될 때까지만 살아 있습니다. 클러스터 안의
secret은 어떤 교체보다도 오래 살아남습니다.

**교훈은 이 오류보다 넓습니다.** `ImagePullBackOff`은 거의 언제나 셋 중 하나입니다: 이미지 이름의 오타,
자격 증명 없음, 또는 이미지는 있지만 맞는 프로세서 아키텍처용이 아님. Pod의 상태가 아니라
`kubectl describe pod`을 보세요 — 진짜 원인이 적혀 있는 곳은 거기입니다.

</details>

## 7단계. 클러스터에 레지스트리 접근 권한 부여

📍 **위치:** 노트북에서, `lab` 클러스터.

레지스트리 자격 증명이 담긴 secret을 만듭니다. `create secret` 명령의 별도 변형은 `kubelet`이
이미지를 내려받을 때 스스로 읽을 수 있는 종류의 secret을 만듭니다:

```bash
# create secret docker-registry = "레지스트리 자격 증명이 담긴 secret을 만들어줘"
#   harbor             클러스터 안의 secret 이름; 애플리케이션 매니페스트가 이것을 참조합니다
#   --docker-server    이 자격 증명이 어느 레지스트리용인지 — 이미지 이름에 있는 것과 같은 주소
#   --docker-username  누가 로그인하는지
#   --docker-password  비밀번호; $, ! 또는 공백이 있으면 작은따옴표가 필요합니다
kubectl create secret docker-registry harbor \
  --docker-server=harbor-harbor.workshop03.example.org \
  --docker-username=admin \
  --docker-password='YOUR-PASSWORD'
```

⚠️ **명령줄의 비밀번호는 셸 히스토리에 남습니다.** 테스트베드에서는 중요하지 않지만, 실제
환경에서는 중요합니다. 히스토리에 남기지 않는 방법:

```bash
# read는 키보드로 입력한 것을 HARBOR_PASS 변수에 넣습니다:
#   -s  입력한 것을 화면에 표시하지 않음
#   -r  백슬래시를 특수 문자로 취급하지 않음
# 이 줄 뒤로 화면에는 아무것도 나타나지 않습니다: 비밀번호를 붙여 넣고 Enter를 누르세요.
read -rs HARBOR_PASS

# 여기서부터 비밀번호는 변수에서 치환되므로, 셸 히스토리에는 변수 이름만
# 들어갑니다. 큰따옴표는 필수입니다: 없으면 공백이 값을 끊어 놓습니다.
kubectl create secret docker-registry harbor \
```

secret에는 **유형**이 있고, 그것은 장식이 아닙니다. 보통의 secret은 키-값 쌍의 모음이고,
그것으로 무엇을 할지는 애플리케이션에 달려 있습니다. `kubernetes.io/dockerconfigjson` 유형의
secret은 `kubelet` 자신이 이해합니다: 안에 `~/.docker/config.json`과 같은 형식의 파일이 있다는
것을 알고, 이미지를 내려받을 때 그것을 사용할 수 있습니다.

내용을 보려면(거기 비밀번호는 base64로 되어 있습니다 — 그것은 **암호화가 아니라** 바이너리
데이터를 텍스트로 적는 방법이고, 누구나 디코딩할 수 있습니다):

```bash
# .data.\.dockerconfigjson — secret 안의 키. 키 이름 자체가 점으로 시작하므로,
# 그것을 이스케이프합니다: 그렇지 않으면 jsonpath가 그것을 경로 구분자로 여깁니다.
# base64 -d는 값을 다시 텍스트로 디코딩합니다 — 여러분의 노트북에 있는
# 파일 ~/.docker/config.json과 같은 형식이 보입니다.
kubectl get secret harbor -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d
```

여기서 중요한 점이 나옵니다: **Kubernetes의 Secret은 기본적으로 암호화되지 않고**, 단지 접근
권한으로 가로막혀 있을 뿐입니다. namespace에서 secret을 읽을 수 있는 사람은 누구나 비밀번호를
봅니다. 이것을 사람답게 다루는 법은 secret 저장소에 관한 별도의 랩에서 다룹니다.

**실무에서는 어떻게 하는가.** `admin` 계정으로는 하지 않습니다. Harbor에는 로봇이 있습니다:
**Projects** → `passes` → **Robot Accounts** → `pull` 권한만 있는 로봇을 만듭니다. 로봇의 자격
증명을 `imagePullSecret`에 넣으면, 클러스터에서 secret이 유출되어도 누군가 여러분의 이미지를
내려받을 수 있다는 뜻일 뿐입니다 — 불쾌하지만 치명적이지는 않습니다. `admin`이 유출되면 누군가
그것들을 바꿔치기할 수 있다는 뜻입니다.

우리는 랩을 길게 끌지 않으려고 `admin`을 씁니다. 이것이 단순화라는 점을 알아 두세요.

## 8단계. 결과 확인하기

📍 **위치:** 노트북에서, `lab` 클러스터.

애플리케이션은 외부에 노출되지 않았지만, 그것을 들여다봐야 합니다. `port-forward`는 노트북에서
클러스터 안으로 터널을 팝니다: 명령이 실행되는 동안 `localhost:8080`으로 가는 요청이 `passes-api`
서비스로 갑니다. 가장 가까운 유사물은 NAT 게이트웨이에서의 임시 포트 포워딩이지만, 네트워크를
건드리지 않는다는 점만 다릅니다.

```bash
# port-forward svc/passes-api = 특정 Pod가 아니라 서비스로 향하는 터널
#   8080:80 — 왼쪽 숫자는 여러분 노트북의 포트, 오른쪽은 클러스터의 서비스 포트
# 창을 닫지 마세요: 터널은 명령이 실행되는 동안 살아 있습니다.
kubectl port-forward svc/passes-api 8080:80
```

다른 터미널 창에서:

```bash
# curl — "주소로 가서 응답을 보여줘".
#   -s     진행 표시기를 보여주지 않음
#   ; echo 줄바꿈을 추가: 응답이 한 줄로 오는데, 없으면
#          셸 프롬프트와 붙습니다
curl -s http://localhost:8080/; echo
```

**여러분이 보게 될 것** — 애플리케이션이 어느 복제본이 응답했는지, 어느 노드에서 실행되는지, 어느
레지스트리에서 왔는지 알리는 JSON:

```json
{
  "service": "passes-api",
  "version": "v1",
  "pod": "passes-api-7d9f8c6b4-xk2mp",
  "node": "kubernetes-lab-md0-abc12",
  "namespace": "default",
  "registry": "harbor-harbor.workshop03.example.org",
  "time": "2026-08-21T09:12:33Z"
}
```

응답의 `pod` 필드는 응답한 복제본의 이름입니다. 그것을 복제본 목록과 대조해 보세요:

```bash
# 새 터미널 창은 KUBECONFIG 변수에 대해 아무것도 모릅니다 — 여기서도 설정하세요,
# 그렇지 않으면 kubectl이 엉뚱한 클러스터로 갑니다
export KUBECONFIG=~/lab.kubeconfig

# 같은 레이블 선택: 목록에 여러분이 응답에서 본 이름이 있어야 합니다
kubectl get pods -l app=passes-api
```

요청을 여러 번 반복해 보세요 — 이름은 **같은 하나**로 유지되며, 그것은 고장이 아닙니다.
`port-forward`는 시작하는 순간 복제본 하나를 고르고 `Ctrl+C`까지 바로 그 하나로 향하는 터널을
유지합니다; 이 경로에는 로드 밸런싱이 전혀 없습니다. 그것은 `Service`에 있지만, 클러스터
안에서만 볼 수 있습니다 — 밖에서 여러분은 특정 Pod와 이야기하고 있습니다.

로드 밸런싱을 실제로 확인하려면 이렇게 할 수 있습니다 — 클러스터 안에 사는 임시 Pod에서 보내는
여덟 번의 요청:

```bash
# run은 일회용 Pod를 띄우고, --rm은 그것을 뒤에서 정리합니다.
# -- 뒤의 모든 것은 Pod 안에서 실행됩니다: 여덟 번 서비스를 내부 이름으로 호출하고
# 응답한 복제본의 이름이 담긴 줄을 출력합니다.
kubectl run probe --rm -i --restart=Never --quiet --image=curlimages/curl:8.11.1 \
  -- sh -c 'for i in $(seq 1 8); do curl -s http://passes-api/ | grep -o "passes-api-[a-z0-9-]*"; done'
```

**여러분이 보게 될 것:** 서로 다른 두 이름이 섞여 있음 — 이것이 요청을 복제본들에 나눠 뿌리는
`Service`입니다.

터널을 닫으려면 — 첫 번째 창에서 `Ctrl+C`.

고리를 닫읍시다: 브라우저에서 Harbor로, `passes` 프로젝트로 들어가세요. `passes/passes-api`
리포지토리의 다운로드 카운터(**Pulls**)가 0이 아니게 되었습니다. 여러분의 클러스터가 정말로 바로
여기로 왔던 것입니다.

## 정리

애플리케이션과 Harbor는 다음 랩에서 필요합니다 — 지금은 삭제하지 마세요.

모든 랩을 마쳤을 때:

```bash
# 파일에 기술된 객체들을 삭제합니다: Deployment도 Service도
kubectl delete -f passes.yaml
# secret은 파일이 아니라 명령으로 만들었으므로 — 이름으로 삭제합니다
kubectl delete secret harbor
```

Harbor 자체는 여느 보통 애플리케이션처럼 대시보드를 통해 삭제합니다. 그와 함께 레이어 저장소도
사라집니다 — 그것은 십여 초이지, VM 폐기 요청이 아닙니다.

정확히 무엇을 삭제하는지 이해할 필요가 있습니다. 레지스트리는 이미지가 놓여 있는 장소일 뿐 아니라,
"지난 한 해 동안 우리가 실제로 프로덕션에 무엇을 배포했는가"라는 질문에 대한 유일한 답이기도
합니다. 실제 환경에서 그것을 여기서처럼 손쉽게 삭제하는 일은 여러분이 바라지 않을 것입니다.

## 이제 우리가 할 수 있는 것

- 이미지 레지스트리를 스스로 갖추고, 그것이 Content Library와 어떻게 다른지 설명하기
- 2단계 빌드로 이미지를 빌드하고, 결과가 왜 서른 배 작게 나오는지 이해하기
- 노트북에서의 `docker login`을 클러스터에 필요한 접근과 구분하기
- `ImagePullBackOff`을 읽고 `describe pod`에서 진짜 원인 찾기
- 클러스터 API에 대한 권한을 주지 않고, downward API를 통해 Pod에게 자기 자신에 대한 정보 주기

## vSphere였다면 이렇게 됩니다

레지스트리에 가장 가까운 유사물은 Content Library입니다. 유사점이 있습니다: 둘 다 이미지를 저장하고
머신에 나눠주며, 둘 다 권한과 사이트 간 동기화를 할 수 있습니다.

그 너머로는 갈라지고, 그 차이는 사소한 데 있지 않습니다.

**Content Library는 템플릿 전체를 복사합니다.** 레지스트리는 레이어를 나눠주고 동일한 레이어는 한
번만 저장합니다. 같은 기반 Alpine 위의 서비스가 스무 개라면, 그 기반은 레지스트리에 단 한 벌 놓여
있고, 스물한 번째 서비스가 실행될 때 노드는 자신만의 레이어만 — 몇 메가바이트를 — 내려받습니다.

**템플릿은 이름으로 부르고, 이미지는 주소로 가리킵니다.** 이미지에는 digest가 있습니다 — 내용의
해시입니다. 그것으로 여러분이 빌드한 바로 그 코드를, 다른 어떤 것도 아니게 실행하고 있음을 검증할
수 있습니다. 템플릿에는 그런 것이 없습니다: 아무도 그것을 바꿔치기하지 않았으리라는 데 의존합니다.

**레지스트리는 HTTP 서비스입니다.** 여기서 이 실습의 요점 전체가 따라 나옵니다: 파이프라인의
빌드가 명령 하나로 거기에 이미지를 넣고, 클러스터가 다른 명령으로 그것을 가져오며, 아무도
스토리지를 마운트하거나 사이트 간에 파일을 손으로 복사하지 않습니다.

**솔직히 vSphere가 더 편리한 지점.** 세 가지입니다.

Content Library는 자격 증명에 대해 아무것도 이해할 것을 요구하지 않습니다. 연결하면 — 작동합니다.
여기서는 클러스터에게 레지스트리에 어떻게 접근하는지를 따로 설명해야 했고, 모두가 그러듯 여러분도
거기서 걸려 넘어졌습니다.

vCenter의 권한은 통합되어 있습니다. 모든 것에 하나의 계정: 머신, 라이브러리, 네트워크. 여기서는
대시보드의 권한, 클러스터의 권한, Harbor의 권한이 서로 동기화되어야 하는 세 개의 다른 집합입니다.
그것은 레지스트리가 플랫폼의 일부가 아니라 그 자체로 독립된 제품이라는 데서 오는 대가입니다.

템플릿은 편집할 수 있습니다. 템플릿에서 머신을 배포하고, 더 손보고, 새 템플릿을 뜹니다 — 그리고
정확한 단계의 순서가 어디에도 적혀 있지 않다는 사실이 아무것도 방해하지 않습니다. 이미지는 그렇게
빌드하지 않습니다: 빌드가 `Dockerfile`로부터 재현되지 않으면, 여러분은 곤경에 빠진 것입니다. 그
규율은 유용하지만, 거기에 익숙해지기는 어렵고, 그렇지 않은 척하는 것은 어리석습니다.
