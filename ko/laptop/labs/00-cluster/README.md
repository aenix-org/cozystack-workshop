# 랩 0 · 나만의 Kubernetes 클러스터

| | |
|---|---|
| **소요 시간** | 15분, 그중 10분은 대기 |
| **무엇을 증명하는가** | 클러스터는 분기 단위 프로젝트가 아니라 카탈로그의 한 항목이라는 것 |
| **필요한 것** | 테넌트 대시보드 접근 권한; 노트북의 `kubectl`, `kubelogin`, `git` |

## 왜 중요한가

앞으로 여러분은 애플리케이션을 배포하고, 망가뜨리고, 고치고, 확장하게 됩니다. 이 모든 것을 하려면 여러분이 온전한 주인이고 실수해도 아무 대가가 없는 공간이 필요합니다.

vSphere라면 그런 공간은 누군가가 여러분에게 배정해 주었을 것입니다. 여기서는 여러분이 직접, 10분 만에 확보하고, 끝나면 마찬가지로 손쉽게 직접 삭제합니다.

## 미니 용어집

앞으로 모든 랩에서 등장할 일곱 단어입니다. 세 번째 열은 각 용어가 닮은 vSphere의 대상을 짚고, 곧바로 그것과 어떻게 다른지도 함께 밝힙니다. 여기서 비유는 이해를 돕지만 어느 하나도 완전히 들어맞지는 않으며, 비유가 정확히 어디서 어긋나는지를 아는 것이 비유 자체보다 더 중요합니다.

| 용어 | 무엇인가 | 닮은 점… 그러나 |
|---|---|---|
| **Kubernetes 클러스터** | 여러 대의 머신에 관리 프로그램을 더한 것으로, 그 위에 애플리케이션을 분산 배치합니다. 애플리케이션을 넘겨주기만 하면 어느 머신에서 실행할지는 지정하지 않아도 스스로 결정합니다 | **ESXi 클러스터**와 닮았지만, DRS는 가상 머신을 배치할 뿐 아니라 이후에도 계속 재조정하며 호스트 사이로 옮깁니다. 여기서 단위는 컨테이너이고, 그 배치 위치는 시작 시점에 한 번, 그리고 노드가 장애를 일으킬 때 다시 선택됩니다. 클러스터가 이미 실행 중인 것을 스스로 재배치하지는 않습니다 |
| **Control plane** | 클러스터의 관리 계층입니다. 여러분의 명령을 받아 원하는 상태를 저장하고 노드에 작업을 분배합니다 | **vCenter**와 닮았지만, 웹 UI를 갖춘 별도 서버가 아니라 몇 개의 프로세스입니다. Cozystack에서는 여러분의 노드가 아니라 플랫폼 안에 존재합니다 |
| **Node** | 결국 여러분의 애플리케이션이 실행되는 머신입니다 | **ESXi 호스트**와 닮았지만, 여기서는 하드웨어가 아니라 VM이며 몇 분 만에 생성됩니다 |
| **Node group** | 동일한 노드 묶음에 대한 설명입니다. 몇 개인지, 어떤 크기인지 | **호스트 클러스터**와 닮았지만, 이 그룹은 부하에 따라 스스로 노드를 추가하고 제거할 수 있습니다 |
| **Kubeconfig** | 클러스터의 주소와 그 접근 정보를 담은 파일입니다. 이 파일이 없으면 `kubectl`은 어디로 접속해야 할지 알지 못합니다 | **계정과 함께인 vCenter 주소**와 닮았지만, 이것은 클라이언트의 설정이 아니라 여러분 디스크에 있는 평범한 텍스트 파일입니다 |
| **Tenant** | 플랫폼에서 여러분에게 할당된 몫입니다. 자신만의 쿼터, 자신만의 권한, 자신만의 객체를 가집니다 | **리소스 풀에 폴더 권한을 더한 것**과 닮았지만, 동시에 가시성의 경계이기도 합니다. 옆 사람은 여러분의 테넌트를 들여다볼 수 없습니다 |
| **Namespace** | 객체가 놓이는, 클러스터 내부의 구획입니다 | **vCenter 인벤토리의 폴더**와 닮았지만, 구분이 더 엄격합니다. 서로 다른 namespace의 객체는 짧은 이름으로는 서로를 찾지 못합니다 |

컨테이너는 따로 언급할 가치가 있습니다. 여러분에게 익숙한 세계와 가장 크게 갈라지는 지점이기 때문입니다. 컨테이너는 실행 중인 애플리케이션을 그 동작에 필요한 모든 것과 함께 하나의 이미지 파일로 묶은 것입니다. 가상 머신과 다른 점은 내부에 자체 운영체제가 없다는 것입니다. 컨테이너는 자신이 실행되는 머신의 커널을 사용합니다. 여기서 규모의 차이가 생깁니다. VM은 시작에 1분이 걸리고 수 기가바이트를 차지하지만, 컨테이너는 1초 만에 시작하고 수십 메가바이트에 불과합니다. 바로 그렇기 때문에 클러스터는 컨테이너를 무더기로 재시작하는 것을 아무렇지 않게 여기며, 앞으로의 랩에서 여러분이 하게 될 일이 바로 그것입니다.

## Windows를 쓴다면 — 이것부터 읽으세요

랩의 명령들은 Linux와 macOS 명령줄을 기준으로 작성되어 있습니다. 순수 PowerShell에서는 그중 일부가 동작하지 않습니다. PowerShell은 문법도 다르고 명령 집합도 다르기 때문입니다.

해결책은 **WSL**입니다. Windows 안의 Linux 서브시스템이지요. 관리자 권한으로 실행한 PowerShell에서 명령 하나로 설치됩니다:

```powershell
# Windows 안에 Linux 서브시스템을 설치합니다: 커널, 서비스, 그리고 기본 Ubuntu
# 배포판. 설치가 끝나면 Windows가 재부팅을 요청합니다.
wsl --install
```

재부팅 후에는 Ubuntu 콘솔이 생기고, 이후에는 다른 모든 사람과 똑같이 그 안에서 작업합니다. WSL 안에는 여러분만의 `kubectl`이 필요합니다. 클러스터에 접속할 때 쓰는 명령이지요:

```bash
# snap은 Ubuntu의 패키지 관리자입니다. --classic은 격리 없이 패키지를 설치합니다:
# 격리 모드에서는 kubectl이 홈 폴더의 접근 파일을 보지 못합니다.
sudo snap install kubectl --classic
```

Windows 드라이브는 WSL에서 `/mnt/c/...` 경로로 보이므로, 일반 브라우저로 내려받은 파일도 그 안에서 그대로 접근할 수 있습니다. 어디로도 복사할 필요가 없습니다. 이 점은 조금 뒤 클러스터의 접근 파일을 받을 때 유용합니다. Windows에 저장하면 WSL에서는 `/mnt/c/Users/Ivan/Downloads/filename` 같은 경로에 놓입니다.

⚠️ **WSL이 보안 정책으로 차단되어 있다면** — 회사 노트북에서는 흔한 일입니다 — 그래도 랩은 진행할 수 있습니다. 대시보드에서 하는 일은 모두 운영체제와 무관하기 때문입니다. 실행하지 못하는 것은 점검 스크립트와, 전적으로 명령으로만 이루어진 몇몇 단계뿐입니다. 그런 지점은 따로 표시해 두었습니다.

## 랩 폴더에 무엇이 있는가

모든 파일은 이미 여러분의 것입니다. 리포지터리와 함께 가져왔으니까요. 새로 만들거나 다시 입력할 것은 없습니다. 아래에서 `kubectl apply -f name.yaml`이라고 적힌 곳이면 어디든 그 파일은 여기서 가져옵니다.

```bash
# 경로는 리포지터리 루트를 기준으로 셉니다 — 그것은 다음 단계에서 가져옵니다
cd labs/00-cluster
```

| 파일 | 무엇인가 | 언제 필요한가 |
|---|---|---|
| `cluster.yaml` | 학습용 클러스터의 설명: 버전, 노드, 모니터링 | 첫 단계에서 관리 클러스터에 적용합니다 |
| `check.sh` | 클러스터가 떴는지, 그리고 여러분이 접속했는지 확인하는 점검 | 랩 마지막에 실행합니다 |

## 0단계. 자료 가져오기

📍 **위치:** 노트북에서.

리포지터리에는 매니페스트 — 클러스터에 무엇을 만들지 기술한 파일 — 와 점검 스크립트가 들어 있습니다. 이 랩부터 필요합니다:

```bash
# clone = 리포지터리를 변경 이력과 함께 통째로 내려받습니다.
# 옆에 cozystack-migration-workshop 폴더가 생기고, 그 안으로 들어갑니다.
git clone https://github.com/aenix-org/cozystack-migration-workshop.git
cd cozystack-migration-workshop
```

이후 랩의 모든 경로는 이 폴더를 기준으로 셉니다.

## 플랫폼 접근 권한 확보하기

📍 **위치:** 브라우저에서, 그다음 노트북에서.

여러분이 플랫폼에 주문하는 모든 것은 **관리 클러스터**에 존재합니다. 여러분의 테넌트와 같은 곳이지요. 명령으로 여기에 접속하려면 접근 파일이 필요합니다. 대시보드에서 가져오세요: `Info` 애플리케이션 → `Secrets` 탭 → `kubeconfig-tenant-workshopXX` Secret → `Reveal`. 내용을 복사하여 노트북에 `~/.kube/workshop`라는 이름으로 저장합니다.

이 경로는 모든 랩에서 사용됩니다 — 파일을 다른 곳에 저장하면, 이후 매번 여러분 자신의 경로를 대입해야 합니다.

```bash
# 파일이 읽히는지, 그리고 클러스터가 응답하는지 확인합니다.
# --kubeconfig는 이 명령에서 kubectl이 어떤 접근 파일을 쓸지 알려줍니다.
kubectl --kubeconfig ~/.kube/workshop get kubernetes.apps.cozystack.io -n tenant-workshopXX
```

**여러분이 보게 될 것:** 빈 목록이거나 `No resources found` 한 줄입니다. 아직 클러스터를 하나도 만들지 않았으니까요. 중요한 것은 다른 데 있습니다. 오류 메시지가 아니라 클러스터 자체가 응답했다는 점입니다.

⚠️ **첫 호출 시 브라우저가 열립니다.** 접근 권한은 인증서가 아니라 Keycloak을 통해 부여됩니다 — 내부 서비스의 "회사 계정으로 로그인"과 같은 로그인 서버지요. `kubectl`이 `kubelogin`을 호출하면 브라우저 창이 열리고, 여러분은 `workshopXX`로 로그인하며, 이후에는 통행증이 만료될 때까지 명령이 조용히 실행됩니다. 브라우저 대신 플러그인이 없다는 오류가 보였다면 — `kubelogin`이 설치되지 않았거나 그 파일 이름이 `kubectl-oidc_login`이 아닌 것입니다. 설치 방법은 워크숍 시작 부분에 적혀 있습니다.

⚠️ **여러분의 테넌트 번호는 대시보드에 로그인할 때 쓰는 로그인 이름입니다:** `workshop03`, `workshop07` 등이지요. 여러분 테넌트의 namespace는 `tenant-`라는 단어와 이 번호로 이루어집니다: `tenant-workshop03`. 아래에서 `workshopXX`라고 적힌 곳에는 모두 여러분 자신의 번호를 대입하세요.

## 1단계. 클러스터 만들기

📍 **위치:** 브라우저에서, Cozystack 대시보드에서.

테넌트 → **Create application** → `Kubernetes`.

다음을 입력합니다:

| 필드 | 값 | 이유 |
|---|---|---|
| Name | `lab` | 짧습니다 — 명령에 입력해야 하니까요 |
| Version | 제안된 것을 그대로 둡니다 | 최신 안정 버전입니다 |
| Control plane replicas | **1** | 기본값은 둘이지만, 학습용 테스트베드에는 하나로 충분합니다 |
| Node group: name | `md0` | 이 이름이 노드 이름에 들어갑니다 — 나중에 `kubectl get nodes`의 출력에서 보게 됩니다 |
| Node group: min replicas | **1** | 노드 하나로 시작합니다 |
| Node group: max replicas | **3** | 그룹이 스스로 늘어날 수 있는 상한입니다. 기본값은 10이고, 확장 랩이 바로 이 상한 위에 세워져 있습니다 |
| Node group: instance type | `u1.medium` | 프로세서 1개, 4 GB |
| Node group: disk | `20Gi` | |
| Storage class | `replicated` | 데이터가 서로 다른 노드에 세 벌 복사본으로 놓입니다 |
| Addons → **Monitoring agents** | **활성화** | 그러지 않으면 메트릭이 쌓이지 않아, 그래프 랩에서 볼 것이 없게 됩니다 |

생성 버튼을 누릅니다.

⚠️ **`Monitoring agents`는 지금 바로 활성화하세요.** 메트릭 수집은 나중에 소급해서 켤 수 없습니다. 일주일 뒤에 체크박스를 켠다면, 그 전에 일어난 모든 것은 영영 사라집니다. 그래프 랩은 오늘부터 쌓이는 데이터에 의존합니다.

⚠️ **옆 사람이 같은 작업을 하고 있다면 — 몇 분 간격을 두고 시차를 두세요.** 동시에 여러 개를 생성하면 내부 설치기에 부하가 걸려, 두 클러스터 모두 뜨는 데 세 배 더 걸립니다. 랩은 각자의 속도로 진행하면 되니, 서두를 필요가 없습니다.

### 명령줄에서 같은 것을 — 그리고 그 뒤에 있는 파일

이것은 대시보드가 죽었을 때를 위한 대비책이 아닙니다. 대시보드의 버튼은 바로 이와 똑같은 파일을 조립해서 클러스터로 보냅니다. 즉 여기서는 텍스트가 우선이고, 마우스는 그 위에 얹힌 한 겹입니다. 우리가 향하는 곳이 바로 텍스트로 작업하는 방식입니다. 파일에 담긴 설명은 리뷰하고, Git에 넣고, 되돌릴 수 있지만, 버튼 클릭은 그럴 수 없습니다.

파일은 이 랩의 폴더에 있습니다: **`labs/00-cluster/cluster.yaml`**. 열거나 다시 입력할 것은 없습니다. 랩 시작 때 리포지터리를 가져왔다면 이미 여러분의 것입니다. 필드 하나하나 살펴볼 수 있도록 아래에 전체를 실었습니다.

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: Kubernetes
metadata:
  name: lab
  namespace: tenant-workshopXX
spec:
  version: v1.35
  storageClass: replicated
  controlPlane:
    replicas: 1
  addons:
    monitoringAgents:
      enabled: true
  nodeGroups:
    md0:
      minReplicas: 1
      maxReplicas: 3
      instanceType: u1.medium
      diskSize: 20Gi
      storageClass: replicated
```

⚠️ 아래 명령들은 **관리 클러스터에서** 실행됩니다. 테넌트와 함께 받은 접근 권한으로요. `lab` 클러스터 자체의 접근 파일은 아직 없습니다. 그것은 클러스터가 뜬 뒤에야 생깁니다.

```bash
# 랩 폴더로 이동합니다 — 이후 모든 파일은 여기서 가져옵니다
cd labs/00-cluster
# 적용하기 전에, 파일에서 XX 자리에 여러분 자신의 테넌트 번호를 대입하세요.
# apply = "파일에 기술된 상태로 클러스터를 맞춰라". 이 명령이 클러스터를 직접 띄우는
# 것은 아닙니다 — 주문을 플랫폼에 넘기면, 플랫폼이 무엇을 어떤 순서로 만들지
# 결정합니다.
#   -f   파일에서 설명을 가져옵니다
kubectl apply -f cluster.yaml
# get = "무엇이 있는지 보여줘". kubernetes.apps.cozystack.io는 객체 타입의 전체
# 이름으로, 파일에 기술된 바로 그것이며(kind: Kubernetes), lab은 여러분 주문의 이름입니다.
#   -n   어느 namespace에서 찾을지; 이 플래그가 없으면 kubectl은 기본 namespace를 봅니다
#   -w   변화를 지켜보며 출력합니다. 나가려면 — Ctrl+C, 그래도 설치는 중단되지 않습니다
# READY 열에 True가 나타날 때까지 기다립니다.
kubectl -n tenant-workshopXX get kubernetes.apps.cozystack.io lab -w
```

## 2단계. 기다리며, 무엇으로 조립되는지 지켜보기

📍 **위치:** 브라우저에서, 대시보드에서.

상태는 보통 5~10분 안에 `Ready`로 바뀝니다.

⚠️ **20분이 넘었는데도 상태가 바뀌지 않는다면 — 원인이 여러분의 클러스터가 아닐 수 있습니다.** 플랫폼의 모든 애플리케이션 설치는 공용 큐로 진행되며, 그 안에 누군가의 긴 작업이 서 있으면 여러분의 클러스터는 차례를 기다립니다. 작업에 착수되었는지 확인하려면:

```bash
# 주문 자체와, 플랫폼이 그것에 대해 적는 내용을 봅니다.
# 출력 끝의 status.conditions 섹션이 그 보고서입니다: 작업에 착수되었는지,
# 무엇이 막고 있는지, 무엇을 기다리는지.
kubectl --kubeconfig ~/.kube/workshop -n tenant-workshopXX \
  get kubernetes.apps.cozystack.io lab -o yaml
```

거기서도 뚜렷한 것이 없다면 — 테넌트의 이벤트를 보세요. 이것은 플랫폼이 여러분의 객체에 대해 한 일의 기록입니다:

```bash
# events = 사건 기록. 가장 최신이 아래로 오도록 시간순으로 정렬합니다.
kubectl --kubeconfig ~/.kube/workshop -n tenant-workshopXX \
  get events --sort-by=.lastTimestamp | tail -20
```

여기서 가장 흔히 발견되는 것은 `exceeded quota: tenant-quota` 한 줄입니다. 이는 클러스터가 여러분 테넌트에 할당된 리소스 몫이 모자란다는 뜻이며, 스스로는 이 상태에서 빠져나오지 못합니다. 공간을 비우거나 쿼터를 늘려야 합니다.

설치가 진행되는 동안, 대시보드에서 여러분의 테넌트에 정확히 무엇이 나타나는지 살펴보세요.

**control plane**은 몇 개의 평범한 애플리케이션으로 배포되었습니다. "이 클러스터의 vCenter" 역할을 하는 별도 머신은 없습니다. 관리 계층은 다른 모든 것과 나란히 실행되는 프로세스입니다.

**노드** — 이건 가상 머신입니다. 여러분이 마이그레이션하는 것들과 똑같은, 지극히 평범한 것입니다. 자체 디스크, 자체 메모리, 자체 주소를 갖고, 여러분의 테넌트 안에 존재합니다.

여기서 중요한 사실이 따라 나옵니다: **여기서 Kubernetes는 가상화를 대체하지 않고, 그 위에서 살아갑니다.** "우리는 VM을 돌린다"와 "우리는 컨테이너를 돌린다" 사이에서 고를 필요가 없습니다. 같은 하드웨어, 같은 인터페이스에서 둘 다 동작합니다.

## 3단계. 새 클러스터 접근 권한 확보하기

📍 **위치:** 노트북에서; 파일 자체는 명령으로 또는 대시보드에서 가져옵니다.

**우리가 가져오는 것.** `lab` 클러스터의 kubeconfig입니다. 그 API 서버의 주소와 그에 대한 여러분의 접근 데이터를 기록한 텍스트 파일이지요. 이런 파일이 없으면 `kubectl`은 어디로 접속해야 할지, 누구로 자신을 내세워야 할지 알지 못합니다. 이 파일은 여러분이 노트북에서 직접, `~/lab.kubeconfig`라는 이름으로 만듭니다. 경로의 `~`는 여러분의 홈 폴더입니다: macOS에서는 `/Users/name`, Linux와 WSL에서는 `/home/name`.

⚠️ **이것은 두 번째 접근 파일이지, 첫 번째를 대체하는 것이 아닙니다.** 테넌트와 함께 받은 파일(랩에서는 `~/.kube/workshop` 경로에 있습니다)은 관리 클러스터로 이어집니다. 여러분이 애플리케이션을 주문하고 방금 `lab`을 만든 그곳이지요. 새 파일은 `lab` 클러스터 자체의 내부로 이어집니다. 이 둘은 주소가 다른 서로 다른 클러스터이며, 이제부터는 둘 다 필요합니다. 플랫폼으로의 주문은 첫 번째 파일로, 여러분 자신의 클러스터 내부 작업은 두 번째 파일로 합니다.

**어디에 있는가.** 플랫폼은 그것을 여러분 테넌트의 Secret `kubernetes-lab-admin-kubeconfig`에 넣어 두었습니다. Secret은 비밀번호, 키, 접근 파일을 보관하는 클러스터 객체입니다. Secret 안에서 여러분에게 필요한 키는 `admin.conf`입니다.

⚠️ **Secret에는 키가 네 개 있고, 여러분에게 필요한 것은 정확히 `admin.conf`입니다.** 그 옆에는 `admin.svc`가 있는데 — 같은 것이지만 클러스터 내부에서만 보이는 내부 주소를 씁니다. 노트북에서는 그것으로 접속할 수 없습니다. `super-admin.*` 쌍은 설정된 제한을 우회하는 권한을 부여하며, 일상적인 사용이 아니라 장애 사후 분석용입니다.

**주된 방법 — 명령으로.** Cozystack은 여러분의 클러스터에 바로 이 Secret만 읽을 수 있고 그 이상은 안 되는 별도의 접근 규칙을 설정합니다. 명령은 테넌트와 함께 받은 접근 권한으로 **관리 클러스터에서** 실행되며, 결과는 노트북의 파일에 담깁니다:

```bash
# get secret = Secret를 보여줍니다; -o go-template — 전체를 출력하지 말고,
# 그중 한 필드만 뽑아 텍스트로 내보냅니다:
#   index .data "admin.conf"   Secret에서 admin.conf 키를 가져옵니다
#   base64decode               Secret의 내용은 base64로 인코딩되어 저장되며,
#                              이 함수가 원래 텍스트를 돌려줍니다
#   > ~/lab.kubeconfig         출력을 화면 대신 파일에 씁니다
kubectl -n tenant-workshopXX get secret kubernetes-lab-admin-kubeconfig \
  -o go-template='{{ printf "%s\n" (index .data "admin.conf" | base64decode) }}' > ~/lab.kubeconfig
```

**같은 일을 마우스로.** 이 동일한 Secret은 대시보드의 `lab` 애플리케이션 페이지, 그 secret 목록에서 볼 수 있습니다 — `kubernetes-lab-admin-kubeconfig`라는 이름으로 찾으세요. `admin.conf` 키의 값을 복사하고, 아무 텍스트 편집기나 열어 복사한 것을 붙여 넣은 뒤, 홈 폴더에 `lab.kubeconfig`라는 이름으로 파일을 저장합니다.

## 4단계. 접속하기

📍 **위치:** 노트북에서.

**이제 일어날 일:** `kubectl`에게 어떤 접근 파일을 쓸지 알려주고, 클러스터에 그 노드 목록을 요청합니다.

macOS와 Linux:

```bash
# KUBECONFIG는 kubectl이 어떤 접근 파일을 가져올지 알아내는 변수입니다.
# export는 이 터미널 창에서 이후 실행되는 모든 명령에 그것을 보이게 합니다.
export KUBECONFIG=~/lab.kubeconfig
# nodes는 클러스터의 노드, 바로 여러분의 애플리케이션이 실행될 가상 머신들입니다.
# 이 응답은 접근 파일이 작동한다는 것도 함께 증명합니다.
kubectl get nodes
```

Windows PowerShell — WSL을 설치하지 못한 경우에만:

```powershell
# PowerShell에서 환경 변수는 $env:로 설정하며 창이 닫힐 때까지 유지됩니다
$env:KUBECONFIG="$HOME\lab.kubeconfig"
kubectl get nodes
```

**여러분이 보게 될 것** — 여러분의 노드 한 줄과 `Ready` 상태:

```
NAME                        STATUS   ROLES    AGE   VERSION
kubernetes-lab-md0-xxxxx    Ready    <none>   3m    v1.35.6
```

⚠️ **`TLS handshake timeout`과 `context deadline exceeded`는 명령의 오류가 아니라 클러스터 쪽의 거절입니다.** 여러분 클러스터의 관리 부분은 한 벌로만 실행되어, 플랫폼이 부하를 받으면 수십 초 동안 응답을 멈춥니다. 명령이 실패하면 30초쯤 뒤에 다시 실행하세요 — 그러면 통과됩니다. 이것이 `apply` 도중에 일어났다면, 그대로 다시 실행하세요. 이 명령은 새로운 것을 더하는 것이 아니라 파일에 기술된 상태로 클러스터를 맞추므로, 무엇도 두 번 만들어지지 않습니다.

⚠️ **`KUBECONFIG` 변수는 새 터미널 창마다 설정해야 합니다.** 잊어버리면 `kubectl`은 어딘가 다른 클러스터로 가거나, 접속할 곳이 없다고 말합니다. 이것이 모든 랩을 통틀어 "제가 다 망가졌어요"의 가장 흔한 원인 하나입니다. 뭔가 이상하게 동작한다면 — 가장 먼저 확인할 것은 `echo $KUBECONFIG`입니다.

## 점검

📍 **위치:** 노트북에서, `kubectl`로 작업하던 바로 그 터미널 창에서.

```bash
# 스크립트는 랩 폴더에서 실행됩니다: 파일을 자신의 옆에서 찾기 때문입니다
cd labs/00-cluster
# 이름 앞의 ./는 "바로 여기서 파일을 실행하라"는 뜻입니다; 이것이 없으면 셸은
# check.sh 명령을 시스템 폴더에서 찾다가 찾지 못합니다
./check.sh
```

⚠️ **Windows에서는 스크립트를 PowerShell이 아니라 WSL에서 실행합니다** — 설치 방법은 이 랩 시작 부분에 적혀 있습니다. WSL 없이도 랩은 완료할 수 있지만, 보고서 아티팩트는 생기지 않습니다.

스크립트는 클러스터가 응답하는지, 노드가 정상인지, 그리고 그 위에 앞으로의 애플리케이션이 들어설 공간이 있는지 확인합니다. 그 옆에 보고서 파일이 생기며 — 랩을 마쳤다는 증거로 어디에든 첨부할 수 있습니다.

## 정리

이 클러스터는 랩 1~5과 그 이후에도 필요합니다. 지금 삭제하지 마세요.

모든 랩을 마쳤을 때 — 대시보드를 통해 `lab` 애플리케이션을 삭제하세요.

삭제 자체는 몇 분 걸립니다. 플랫폼이 노드 VM을 끄고, 관리 컴포넌트를 제거하고, 디스크를 반환합니다. 그 순간 설치 큐가 누군가의 긴 작업으로 붐빈다면 대기가 더 길어질 수 있습니다 — 그럴 때는 이 랩 앞부분에서 설명한, `reconcile.fluxcd.io/requestedAt` 애너테이션을 쓰는 바로 그 방법이 도움이 됩니다.

중요한 것은 다른 데 있습니다: **비워진 것은 온전히, 저절로 쿼터로 돌아옵니다.** 누구에게 부탁하거나, 왜 그것을 가져갔는지 설명할 필요가 없습니다.

## 이제 우리가 할 수 있는 것

- 누구에게도 가지 않고 우리 스스로 Kubernetes 클러스터를 띄우기
- control plane은 프로세스이고 노드는 가상 머신임을 이해하기
- 접근 권한을 가져와 노트북에서 접속하기
- `kubectl`이 이상하게 동작할 때 원인을 어디서 찾을지 알기

## 그리고 vSphere에서라면 이것은

vSphere에서 Kubernetes는 별도의 제품, 별도의 라이선스, 그리고 벤더가 참여하는 도입 프로젝트입니다. 여기서는 카탈로그의 한 항목과 10분입니다.

**솔직히, vSphere가 더 편한 지점.** 필요한 것이 오직 가상 머신뿐이고 그 밖에는 없다면, vCenter가 그것을 관리하는 데 더 많은 기성 도구를 제공합니다: 템플릿, 클론, 게스트 OS 커스터마이징, 폴더 하나 단위의 권한. Cozystack도 VM을 다룰 수 있지만, 그 주변 생태계는 여기서 더 젊습니다. 이득은 VM과 나머지 모든 것 — 데이터베이스, 큐, 클러스터, 레지스트리 — 이 한꺼번에, 한곳에서, 하나의 API로 필요한 곳에서 나타납니다.
