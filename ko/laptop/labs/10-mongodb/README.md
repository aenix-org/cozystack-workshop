## 이것이 왜 중요한가

"출입증" 서비스는 단 하나의 출입증 유형 — 특정 날짜의 일회용 출입증 — 만으로 출시되었습니다.
한 달 뒤 고객이 보완 요청을 들고 돌아왔는데, 하나같이 합리적이었습니다:

| 출입증 유형 | 추가로 필요한 것 |
|---|---|
| 일회용 | 날짜, 출입구 |
| 주간 | 시작/종료 기간, 출입구 목록, 배지 반납 여부 표시 |
| 차량 | 번호판, 모델, 트레일러 유무, 중량, 주차 구역 번호 |
| 단체 | 조직, 담당자, 인솔자, 나이가 포함된 참가자 목록 |

고정된 컬럼을 가진 테이블에서 이 문제에는 두 가지 해결책이 있는데, 둘 다 나쁩니다.

**해결책 하나: 모든 컬럼을 담은 단일 테이블.** `car_plate`, `car_model`, `trailer`,
`weight_kg`, `parking`, `valid_from`, `valid_to`, `badge_returned`, `organization`,
`contact`, `escort`를 추가하면 — 일회용 출입증은 열다섯 개 필드 중 열한 개가 비어 있습니다.
반년이 지나면 컬럼은 서른 개가 되고, 어떤 것이 어떤 유형에 필수인지 아무도 기억하지 못하며,
첫 번째 `NOT NULL` 필드 하나가 시나리오의 절반을 망가뜨립니다.

**해결책 둘: 유형마다 테이블.** 하나 대신 네 개의 테이블, 그리고 경비가 정문에서 통합 목록을
보여줄 수 있도록 이들을 묶는 다섯 번째 테이블. 새로운 출입증 유형이 생길 때마다 스키마
마이그레이션, 릴리스, 승인이 필요합니다. 그리고 "오늘의 모든 출입증을 보여줘"라는 쿼리는
네 조각의 `UNION`이 되고, 다섯 번째를 추가할 때마다 고쳐야 합니다.

**단체 출입증의 참가자 목록은 어느 쪽에도 들어맞지 않습니다.** 길이가 가변적이어서, 출입증을
다시 참조하는 또 하나의 테이블이 필요합니다.

세 번째 길이 있습니다: 모든 레코드가 같은 형태를 갖도록 요구하지 않는 저장소입니다. 이
랩에서는 MongoDB를 세우고, 네 가지 서로 다른 형태의 출입증 네 개를 넣은 다음, 그것들을
가로질러 검색합니다. 그리고 우리가 그 대가로 무엇을 치르는지 정직하게 들여다봅니다 —
왜냐하면 우리는 대가를 치르며, 그것도 적지 않게 치르기 때문입니다.

Kubernetes와 MongoDB 용어는 이 랩에서 처음 나올 때 설명하며, 일부는 아래 간단한 용어집에
모아 두었습니다.

## 미니 용어집

| 용어 | 무엇인가 | …와 비슷하지만 |
|---|---|---|
| **문서(Document)** | 하나의 레코드. 필드, 중첩 객체, 목록의 집합 | **테이블의 행**과 비슷하지만, 이웃 레코드는 필드 구성이 다를 수 있고 그것이 오류가 아닙니다 |
| **컬렉션(Collection)** | 문서의 집합 | **테이블**과 비슷하지만, 기본적으로 스키마가 없습니다. 스키마를 추가할 수는 있지만 그것은 별도의 결정입니다 |
| **BSON** | 문서가 저장되는 이진 형식 | JSON과 비슷하지만 타입이 있습니다: 날짜는 문자열이 아니라 날짜입니다 |
| **레플리카 세트(replica set)** | 여러 개의 복사본, 하나는 주(primary), 나머지는 넘겨받습니다 | **HA 클러스터**와 비슷하지만, 복사본들이 서로 투표하므로 홀수 개가 필요합니다 |
| **`mongosh`** | MongoDB 명령 셸 | **PowerCLI**와 비슷하지만, 쿼리 언어가 아니라 완전한 JavaScript입니다 |

이 랩의 나머지 단어들 — _id, 샤딩(Sharding), 점 표기법(Dotted field notation),
희소 인덱스(Sparse index), 스키마 검증기(Schema validator), $lookup — 은 진행하면서, 그것이
처음 필요해지는 단계에서 소개합니다. 지금 외울 필요는 없습니다: 동작과 떨어져서는 머리에 남지
않습니다.

| 용어 | 무엇인가 | …와 비슷하지만 |
|---|---|---|
| **`_id`** | 문서의 고유 키 | **기본 키(primary key)**와 비슷하지만, 지정하지 않으면 대신 만들어 줍니다 |
| **샤딩(Sharding)** | 레플리카 세트들에 데이터를 나누는 것 | 신뢰성이 아니라 용량에 관한 것 |
| **점 표기법(Dotted field notation)** | 점을 통해 중첩 필드에 접근: `car.plate` | **폴더 안 파일 경로**와 비슷하지만, 목록 안으로도 접근합니다: `members.age` |
| **희소 인덱스(Sparse index)** | 필드가 존재하는 문서만 포함하는 인덱스 | 필드가 소수의 레코드에만 있는 경우의 순전한 필수품 |
| **스키마 검증기(Schema validator)** | 문서가 반드시 충족해야 하는 규칙 | **저장 전 폼 검증**과 비슷하지만, 수동으로 그리고 나중에 켭니다 — 기본적으로 스키마가 없습니다 |
| **`$lookup`** | 다른 컬렉션에서 데이터를 끌어오는 방법 | **JOIN**과 비슷하지만 단방향이고 눈에 띄게 비쌉니다: 조인이 옵티마이저에 의해 선택되는 게 아니라 완전 탐색으로 수행됩니다 |

</details>

것은 없습니다: 아래에서 `kubectl apply -f 이름.yaml`이라고 쓰인 곳마다, 파일은 여기서
가져옵니다.

```bash
cd labs/10-mongodb
```

| 파일 | 무엇인가 | 언제 필요한가 |
|---|---|---|
| `mongodb.yaml` | 문서 데이터베이스 주문서 — 대시보드의 버튼과 같은 것 | `lab` 클러스터가 아니라 **테넌트에서** 적용합니다 |
| `passes.js` | 여러 유형의 출입증으로 데이터베이스 채우기: 일회용, 주간, 차량 | 데이터베이스에서 실행합니다 |
| `validator.js` | 문서 검증 규칙 — 쓰레기가 데이터베이스에 들어가지 않도록 | 그다음에 실행합니다 |
| `check.sh` | 서로 다른 형태의 문서가 나란히 놓이고 부적합한 것은 거부되는지 확인 | 랩 마지막에 실행합니다 |

## 단계 1. MongoDB 주문하기

📍 **위치:** 브라우저에서, Cozystack 대시보드에서, 여러분의 테넌트 안에서.

테넌트 → **Create application** → `MongoDB`.

| 필드 | 값 | 이유 |
|---|---|---|
| Name | `passes` | 짧게 — 나중에 주소에 입력해야 합니다 |
| Version | `v8` | 현재 브랜치 |
| Replicas | **1** | 학습용 테스트베드. 프로덕션에서 왜 셋인지는 바로 아래에 |
| Size | `5Gi` | 문서 네 개는 바이트 단위를 차지하고, 나머지는 여유분 |
| Storage class | `replicated` | 데이터가 서로 다른 노드에 세 벌로 놓입니다 |
| Resources preset | `s1.small` | 프로세서 1개, 2 GB |
| Sharding | 끔 | 데이터가 서버 하나에 들어가지 않을 때 샤딩합니다 |
| Users | `passapp` 사용자, 비밀번호는 **명시적으로** 설정 | 이 사용자로 작업합니다 |
| Databases | `passes` 데이터베이스, admin 역할에 `passapp` | 역할이 없으면 사용자가 받아들여지지 않습니다 |
| External | 끔 | 바깥으로 노출하지 않습니다 |

⚠️ **비밀번호는 반드시 직접 설정하고 적어 두세요.** 필드를 비워 두면 차트가 비밀번호를
스스로 생성해서 — 대시보드에서 보이지 않는 Secret에 넣습니다. 그러면 접속할 수 없는, 동작하는
데이터베이스만 남게 됩니다.

앞으로 여러 번 만나게 될 두 단어. **차트(chart)** 는 플랫폼이 서비스를 배포하는 데 쓰는
청사진입니다: 템플릿 묶음에 여러분이 폼에 채운 값을 더한 것. 가장 가까운 것은 설정 마법사가
딸린 가상 머신 템플릿입니다. **Secret** 은 비밀번호와 키를 담는 클러스터 객체입니다;
대시보드에서는 애플리케이션 카드의 별도 탭으로 표시됩니다.

⚠️ **역할 없는 사용자는 배포 실패로 이어집니다.** Users 섹션에서 `passapp`을 만들었지만
Databases 섹션에서 어떤 데이터베이스에도 역할을 부여하지 않으면, 차트는 "user is not assigned
to any database role" 오류로 멈춥니다. 이것은 고장이 아니라 쓸모없는 사용자를 막는
안전장치이지만, 그 메시지는 금방 찾아지지 않습니다.

⚠️ **복사본 하나는 정상적인 형태의 MongoDB가 아니며, 그 이유를 이해할 가치가 있습니다.**
MongoDB는 세 개의 레플리카 세트를 위해 설계되었습니다: 투표로 주(primary)를 선출하고, 하나를
잃어도 작업이 멈추지 않습니다. 투표에는 과반수가 필요하므로 복사본 수는 홀수로 만듭니다.
복사본이 하나면 함께 투표할 상대가 없고, 이를 위해 차트는 특별한 `unsafeFlags` 모드를 켭니다.
랩에서는 이것이 테스트베드 자원을 아껴 주지만, 프로덕션에서는 이렇게 하면 안 됩니다.

### 더 자세히: mongodb.yaml 안에 무엇이 있는가

랩 폴더에 `mongodb.yaml`이 있습니다:

```yaml
apiVersion: apps.cozystack.io/v1alpha1
kind: MongoDB
metadata:
  name: passes
  namespace: tenant-workshopXX
spec:
  replicas: 1
  size: 5Gi
  storageClass: replicated
  resourcesPreset: s1.small
  version: v8
  external: false
  sharding: false
  users:
    passapp:
      password: 여기에비밀번호입력
  databases:
    passes:
      roles:
        admin:
          - passapp
  backup:
    enabled: false
```

`namespace: tenant-workshopXX` — **관리형 서비스는 관리 클러스터의 여러분 테넌트 안에 살며,
랩 0의 lab 클러스터가 아닙니다.** 이 둘은 서로 다른 클러스터입니다.

`users`와 `databases`는 서로 연결된 두 개의 맵이고, 그 사이의 연결은 필수입니다.
`users`는 계정을 나열하고, `databases`는 데이터베이스와 그 안에서 누가 무엇을 할 수 있는지를
나열합니다. `roles.admin`은 하나의 데이터베이스 안에서 읽고, 쓰고, 구조를 바꿀 권한을
부여합니다; `roles.readonly` — 읽기만.

⚠️ 사용자는 서비스 데이터베이스 `admin`에서 만들어지지만, 권한은 여러분의 데이터베이스에서
부여됩니다. 그래서 연결 문자열에는 `authSource=admin`이 필요합니다 — 이에 대해서는 다음
단계에서 따로 다룹니다.

`sharding: false` — 평범한 레플리카 세트입니다. 샤딩을 켜면 설정 서버와 라우터가 추가됩니다:
우리에게 필요 없는 데이터 분할을 위해 서너 개의 여분 Pod입니다.

이 파일은 **lab 클러스터가 아니라** 테넌트에 적용됩니다 — 즉 접근 파일도 테넌트용이어야
합니다. kubeconfig(클러스터의 주소와 로그인 데이터가 담긴 파일)는 대시보드에서 가져옵니다:
**Info → Secrets 탭 → `kubeconfig-tenant-workshopXX`**. 그것을 `~/.kube/workshop`에
저장하세요 — 이 경로는 모든 랩에서 쓰입니다.

이제 데이터베이스를 텍스트로 주문합니다. 이 명령은 스스로 아무것도 설치하지 않습니다: 주문을
플랫폼에 넘기고, 플랫폼이 자기 쪽에서 필요한 모든 것을 세웁니다.

```bash
# apply = "클러스터를 파일에 기술된 상태로 만들어라".
#   --kubeconfig ~/.kube/workshop  어떤 접근 파일을 쓸지. 없으면 kubectl은
#                                  기본 접근을 가져다 엉뚱한 클러스터로 가 버립니다
#   -f mongodb.yaml                어떤 파일을 적용할지 (-f = file)
kubectl --kubeconfig ~/.kube/workshop apply -f mongodb.yaml
```

**여러분이 보게 될 것** — `mongodb.apps.cozystack.io/passes created`. `created`라는 단어는
주문이 받아들여졌다는 뜻이지, 데이터베이스가 준비되었다는 뜻이 아닙니다.

준비되기까지 3~5분이 걸립니다: 서버가 올라오고, 레플리카 세트가 초기화되고, 사용자가
만들어집니다. 일이 어떻게 되어 가는지는 이렇게 지켜볼 수 있습니다:

```bash
# get = "거기 무엇이 있는지 보여줘". READY 컬럼이 주문이 동작 상태에 도달했는지 알려 줍니다.
#   -n tenant-workshopXX  어떤 namespace에서 찾을지 (namespace는 클러스터 안의
#                         칸막이입니다; 여러분의 테넌트가 바로 그런 별도의 namespace입니다)
kubectl --kubeconfig ~/.kube/workshop get mongodb passes -n tenant-workshopXX
```

⚠️ **대시보드의 `mongodb-passes-credentials` Secret은 처음 몇 분 동안 비밀번호가 비어
있습니다.** 여기에는 서비스 계정 `databaseAdmin`의 자격 증명이 들어 있고, 차트는
오퍼레이터(주문을 동작 상태로 몰아가고 그다음 계속 지켜보는 플랫폼의 프로그램)가 사용자를 만든
뒤에야 — 즉 상태를 조정(reconcile)하는 다음 회차에 — 이를 채웁니다. 몇 분 기다렸다가 페이지를
새로고침하세요. 이 계정은 필요 없습니다: 우리는 여러분이 직접 비밀번호를 설정한 `passapp`으로
작업합니다.

## 단계 2. 작업용 Pod 만들기

📍 **위치:** 노트북에서, lab 클러스터에서.

구성은 관리형 서비스를 다루는 다른 랩들과 같습니다.

**MongoDB는 관리 클러스터의 여러분 테넌트 안에 삽니다.** 테넌트에서의 여러분 역할은 서비스를
주문하고 삭제할 수 있게 하지만, 거기서 자기 Pod를 실행하거나 포트를 포워딩하는 것은 허용하지
않습니다.

**여러분의 작업 터전은 랩 0의 lab 클러스터입니다.** 바로 거기서, 내부 주소를 통해 출발합니다:

```
mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017
```

| 부분 | 무엇을 뜻하는가 |
|---|---|
| `mongodb-` | Cozystack 카탈로그가 애플리케이션 이름에 붙이는 접두사 |
| `passes` | 대시보드에서 여러분이 설정한 이름 |
| `-rs0` | 레플리카 세트 이름. 오퍼레이터는 첫 번째 세트의 서비스를 이렇게 이름 짓습니다 |
| `tenant-workshopXX` | 여러분의 테넌트. 자기 번호로 바꾸세요 |
| `svc.cozy.local` | 관리 클러스터의 내부 이름 영역 |
| `27017` | MongoDB의 표준 포트 |

**Pod**는 Kubernetes에서 실행의 가장 작은 단위입니다: 항상 같은 노드에 살며 하나의 주소를
공유하는 하나 또는 여러 개의 컨테이너입니다. 가장 가까운 비유는 단 하나의 작업을 위해 세운
가상 머신이지만, 몇 초 만에 만들어지고 미련 없이 꺼진다는 점이 다릅니다. 우리는 이런 Pod를
`mongo:8.0` 이미지로 세웁니다: 그 안에 `mongosh` — MongoDB 명령 셸 — 이 들어 있어서,
노트북에 그것을 설치할 필요가 없습니다.

데이터베이스 주소는 사용자 이름 및 비밀번호와 함께 한 줄로 적히는데 — 이를 연결 문자열이라고
합니다. 명령을 입력하기 전에 그것을 짚어 봅시다.

<details>
<summary><b>연결 문자열 짚어 보기</b></summary>

```
mongodb://passapp:비밀번호@호스트:27017/passes?authSource=admin&directConnection=true
```

`mongodb://` — 스킴. 그다음 사용자 이름, 비밀번호, 주소, 포트.

`/passes` (포트 뒤) — **기본 데이터베이스**. 접속하면 별도의 명령 없이 바로 그 안에 들어가
있습니다.

`authSource=admin` — **계정 자체를 어느 데이터베이스에서 찾을지.** `passapp` 사용자는 서비스
데이터베이스 `admin`에서 만들어지지만, 권한은 `passes`에서 부여됩니다. 이 매개변수가 없으면
드라이버는 `passes`에서 계정을 찾으러 가서, 찾지 못하고, "Authentication failed"를
반환합니다 — "비밀번호가 틀림"처럼 보여서 탐색을 엉뚱한 방향으로 이끄는 메시지입니다. 이것이
관리형 MongoDB에 처음 접속할 때 가장 흔한 오류입니다.

`directConnection=true` — "이 서버로 곧장 접속하고, 레플리카 세트의 구성을 알아내려 하지
마라". 이 매개변수가 없으면 드라이버는 세트에 또 누가 있는지 서버에 묻고, 구성원들의 내부
이름을 돌려받는데, 이것이 바깥에서 항상 해석되는 것은 아닙니다. 복사본이 하나면 알아낼 것이
없으므로, 직접 그렇게 말하는 편이 간단합니다. 복사본이 셋인 프로덕션에서는 반대입니다: 이
매개변수를 설정하지 않는데, 거기서 원하는 것이 바로 예전 주(primary)가 고장 났을 때 새 주로
자동 전환하는 것이기 때문입니다.

**주소와 비밀번호가 명령에 곧장 들어가지 않고 Pod 변수에 들어가는 이유.** `kubectl exec`에
쓰는 모든 것은 여러분 셸의 히스토리와 노드의 프로세스 목록에 남습니다. Pod 변수는 한 번
설정되고, 그 뒤로는 비밀번호가 명령에 나타나지 않습니다.

이것이 문제를 완전히 해결하지는 않으며, 미리 정직하게 말하는 편이 낫습니다: `--env`를 통해
전달된 값은 Pod의 스펙에 남습니다 — 여러분 namespace의 Pod를 읽을 권한이 있는 누구에게나
보이고, 클러스터 데이터베이스에 저장되며, 감사 로그에 남습니다. 학습용 테스트베드에서는 이것이
받아들일 만하지만, 프로덕션에서는 아닙니다: 거기서는 비밀번호를 Secret에 넣고 `envFrom`을
통해 연결합니다. 시크릿에 관한 랩이 바로 이것을 다룹니다.

</details>

Pod를 세웁니다. `workshopXX`를 여러분의 테넌트 번호로, `여기에비밀번호입력`을 여러분의
비밀번호로 바꾸세요:

```bash
# KUBECONFIG — kubectl이 어떤 접근 파일을 쓸지. 여기서는 랩 0의
# lab 클러스터입니다: 자기 Pod는 오직 그 안에서만 띄우며, 이것으로는 테넌트에 들어갈 수 없습니다.
export KUBECONFIG=~/lab.kubeconfig

# run = "Pod 하나를 만들고 그 안에서 이 이미지를 실행해라". 중요한 플래그:
#   --image=mongo:8.0        무엇을 실행할지. 이미지에는 mongosh 셸이 들어 있습니다
#   --restart=Never          Deployment가 아니라 딱 하나의 Pod를 만들기. 그러지 않으면
#                            Pod가 끝날 때마다 클러스터가 다시 띄웁니다
#   --env=MONGO_URI=...      Pod 안의 환경 변수. 비밀번호가 이 안에 머물러,
#                            뒤따르는 모든 명령에서 반복되지 않습니다
#   --command -- sleep 86400 컨테이너를 무엇으로 바쁘게 둘지. mongo 이미지는 기본적으로
#                            데이터베이스 서버를 시작하는데 — 그것은 필요 없고, 들어갈 수 있는
#                            살아 있는 컨테이너가 필요합니다. 86400초는 하루입니다
kubectl run mongo-workbench \
  --image=mongo:8.0 \
  --restart=Never \
  --env=MONGO_URI="mongodb://passapp:여기에비밀번호입력@mongodb-passes-rs0.tenant-workshopXX.svc.cozy.local:27017/passes?authSource=admin&directConnection=true" \
  --command -- sleep 86400

# wait = "조건이 충족될 때까지 제어를 돌려주지 마라"
#   --for=condition=Ready  Pod가 스스로 준비 완료를 보고할 때까지 기다립니다
#   --timeout=180s         영원히 매달리는 대신 오류를 반환하기까지 얼마나 기다릴지
kubectl wait --for=condition=Ready pod/mongo-workbench --timeout=180s
```

**여러분이 보게 될 것** — `pod/mongo-workbench created`, 이어서
`pod/mongo-workbench condition met`.

이제 매번 이 모든 것을 입력하지 않도록 짧은 명령을 하나 만들고, 데이터베이스 연결을
확인합니다:

```bash
# mo — 터미널 창을 닫을 때까지 사는 단축 명령: 셸에서
# 자기만의 명령을 선언하는 방법입니다.
#   exec        이미 실행 중인 Pod 안에서 무언가를 실행
#   -i          표준 입력을 안으로 전달: 없으면 프로그램을 넣어 줄 수 없습니다
#   sh -c '...' Pod 안에서 셸을 실행해 그 셸이 스스로 $MONGO_URI를 치환하게 합니다.
#               따옴표가 작은따옴표인 것은 의도적입니다: 변수를 치환하는 것은
#               여러분의 터미널이 아니라 Pod여야 합니다 — 그러지 않으면 비밀번호가 명령 히스토리에 남습니다
#   --quiet     mongosh 인사말을 출력하지 않고, 답만 남깁니다
mo() { kubectl exec -i mongo-workbench -- sh -c 'mongosh --quiet "$MONGO_URI"'; }

# ping — 서비스 요청, "살아 있니?". 아무것도 읽거나 쓰지 않고, 연결과
# 자격 증명이 받아들여졌는지를 확인합니다. | 기호가 이 줄을 mongosh의 입력으로 보냅니다
echo 'db.runCommand({ ping: 1 })' | mo
```

**여러분이 보게 될 것** — `{ ok: 1 }`.

`mongosh`는 프로그램을 표준 입력에서 읽으므로, 이 같은 명령이 파일 전체를 삼킬 수 있습니다:
`mo < passes.js`.

⚠️ **답이 `Authentication failed`라면** — 연결은 되어 있지만 자격 증명이 틀립니다. 순서대로
확인하세요: 연결 문자열의 `authSource=admin`; 비밀번호가 대시보드에서 설정한 것과 일치하는지;
사용자 이름이 `passapp`인지. 고친 문자열로 Pod를 다시 만들려면:
`kubectl delete pod mongo-workbench` 후 처음부터.

⚠️ **답이 `getaddrinfo ENOTFOUND`거나 연결이 멈춰 있다면** — 이름이 해석되지 않는 것입니다.
십중팔구 `workshopXX`를 자기 번호로 바꾸지 않았거나, 대시보드의 애플리케이션이 아직 준비되지
않았습니다.

데이터를 살펴보기에는 명령을 하나씩 치는 것보다 살아 있는 셸이 더 편합니다 — 셸이 열린 채로
있고, 그 안에서 쿼리를 잇달아 입력합니다:

```bash
# -i 대신 -it: t가 추가됩니다 — "터미널을 달라". 그래서 입력 프롬프트,
# 위 화살표로 명령 히스토리, 그리고 강조 표시가 생깁니다. t가 없으면 셸은 말없이 입력을 기다립니다.
kubectl exec -it mongo-workbench -- sh -c 'mongosh "$MONGO_URI"'
```

**여러분이 보게 될 것** — `passes>` 형태의 프롬프트: 여러분이 들어와 있는 데이터베이스의 이름.

이제부터 본문의 명령은 이 셸에서 입력하는 방식으로 보여 줍니다. 나가려면 — `exit`.

## 단계 3. 서로 다른 형태의 출입증 네 개를 넣기

📍 **위치:** 노트북에서, lab 클러스터에서.

`passes.js` 파일은 `mongosh`용 프로그램입니다: 데이터베이스에 출입증 네 개를 추가하고 문서가
몇 개가 되었는지 출력합니다. 미리 테이블을 하나도 만들 필요가 없으며, 바로 아래에 그 이유가
설명되어 있습니다.

```bash
cd labs/10-mongodb
# < 기호는 파일의 내용을 명령의 입력으로 넣어 줍니다 — mongosh 셸에서 파일 전체
# 텍스트를 손으로 입력하는 것과 같은 일입니다.
mo < passes.js
```

**여러분이 보게 될 것** — `документов в коллекции: 4`.

<details>
<summary><b>우리가 넣은 것 짚어 보기</b></summary>

먼저 눈여겨볼 것: **`CREATE TABLE`이 없었습니다.** `passes` 컬렉션은 첫 삽입의 순간에
생겨났습니다. 스키마가 없습니다 — 즉 기본적으로 MongoDB는 문서에 어떤 필드가 있을 수 있는지에
대해 아무 의견이 없습니다.

이제 문서들로.

**일회용 출입증** — 가장 짧은 형태:

```js
  {
    type: "разовый",
    guest: "Иванов Иван Иванович",
    host: "petrov@corp.ru",
    entrance: "Северная",
    valid_on: ISODate("2026-09-01T09:00:00Z"),
    purpose: "собеседование"
  }
```

여섯 개 필드, 모두 스칼라. 테이블이라면 평범한 행이 되었을 것입니다.

`ISODate(...)`는 문자열이 아니라 바로 날짜입니다. MongoDB는 문서를 이진 BSON 형식으로
저장하는데, 거기서는 값에 타입이 있습니다: 날짜, 정수, 부동소수점, 불리언, 이진 데이터. 이것이
평범한 JSON과의 중요한 차이입니다: 날짜로는 비교하고 정렬할 수 있지만, 문자열 `"2026-09-01"`
로는 그것이 쓰인 방식이 운 좋을 때만 됩니다.

**주간 출입증** — 이제 `valid_on` 대신 `valid_from`과 `valid_to`가 있고, 하나의 출입구 대신
`entrances`가 이제 **목록**입니다:

```js
    entrances: ["Северная", "Южная"],
    badge_returned: false
```

필드 안에 바로 목록. 테이블이라면 별도의 "출입증 — 출입구" 테이블이나, 나중에 아무도 제대로
검색할 수 없는 쉼표로 구분된 문자열이 필요했을 것입니다.

일회용 출입증에는 `badge_returned` 필드가 아예 없습니다. `NULL`도 아니고 비어 있는 것도
아니라 — **이 문서에는 그런 필드가 없습니다.** 이것들은 서로 다른 것이며, 검색 방법도
다릅니다.

**차량 출입증** — **중첩 객체**가 나타났습니다:

```js
    car: {
      plate: "А123ВС174",
      model: "ГАЗель Next",
      trailer: false,
      weight_kg: 3500
    },
```

차량에 관한 모든 것이 하나의 `car` 필드 안에 있습니다. 이것은 JSON을 담은 문자열이 아니라
온전한 구조입니다: `car.plate`로 검색하고 그 위에 인덱스를 만들 수 있습니다.

**단체 출입증** — **객체의 목록**:

```js
    members: [
      { name: "Орлов Пётр", age: 16 },
      { name: "Волкова Мария", age: 15 },
      { name: "Зайцев Илья", age: 17 }
    ]
```

가변 길이의 참가자 목록, 각자 자기 필드를 가집니다. 그리고 — 주목하세요 — 이 문서에는
**`guest` 필드가 없습니다**: 손님 자리에 조직과 담당자가 있습니다. 이 문서의 형태는 다른
것들과 필드 하나로 다른 것이 아니라 본질적으로 다릅니다.

바로 이것을 위해 문서 모델이 존재합니다. 빈 컬럼도, 네 개의 테이블도, 그것들을 묶는 다섯 번째
테이블도 없습니다.

</details>

## 단계 4. 서로 다른 형태의 문서를 가로질러 검색하기

📍 **위치:** 작업용 Pod 안의 `mongosh` 셸에서.

경비와 경영진에게 필요한 모든 것은 평범한 쿼리입니다. 모두 같은 방식으로 읽힙니다: `db`는
여러분이 접속한 데이터베이스, `passes`는 그 안의 컬렉션, 그다음 점 뒤에 동작이 오고, 괄호 안에
선택 조건이 있습니다. 조건은 항상 객체로 적힙니다: "필드 — 그것이 가져야 할 값".

**특정 날짜의 모든 출입증:**

```js
// find = "조건에 맞는 문서를 보여줘"
// { valid_on: ISODate(...) } — 문서의 valid_on 필드가 정확히 이
// 날짜와 같아야 합니다. ISODate는 문자열이 아니라 날짜입니다: 비교는 표기가 아니라 시간으로 이뤄집니다
db.passes.find({ valid_on: ISODate("2026-09-02T07:30:00Z") })
```

**여러분이 보게 될 것** — 문서 하나, 쿠즈네초프의 차량 출입증.

**차량 출입증만:**

```js
// 평범한 문자열 필드에 대한 조건: 통째로 일치, 여기에 대소문자 무시는 없습니다
db.passes.find({ type: "автомобильный" })
```

**번호판으로 검색 — 점을 통해 중첩 객체 안으로 접근:**

```js
// "car.plate" — 문서 안으로의 경로: car 객체 안의 plate 필드.
// 경로를 감싸는 따옴표는 필수입니다, 그러지 않으면 JavaScript가 점을 제멋대로 읽습니다
db.passes.find({ "car.plate": "А123ВС174" })
```

<details>
<summary><b>이것이 왜 되는지, 그리고 "JSON을 담은 문자열"과 어떻게 다른지</b></summary>

`"car.plate"`는 필드로 가는 경로의 점 표기법입니다. MongoDB는 문서의 구조를 이해하고 안으로
접근할 수 있으며, 중첩 객체를 텍스트 덩어리로 저장하지 않습니다.

차이는 실질적입니다. 만약 `car`가 관계형 테이블에서 JSON을 담은 `TEXT` 컬럼으로 있었다면,
번호판으로 검색하는 것은 `LIKE '%А123ВС174%'`를 뜻했을 것입니다 — 인덱스 없는 전체 스캔,
게다가 거짓 양성까지. 여기서는 인덱스를 만들 수 있는 평범한 조건이고, 실제로 만들 것입니다.

⚠️ `"car.plate"`를 감싸는 따옴표는 필수입니다: 그것이 없으면 JavaScript는 점을 객체 속성에
접근하는 것으로 읽고, 무엇을 요구하는지 이해하지 못합니다.

</details>

**여러 출입구에서 유효한 출입증:**

```js
// entrances는 문자열이 아니라 목록입니다: ["Северная", "Южная"]. 조건은 여전히 평범한 필드처럼
// 적히고, MongoDB가 스스로 목록의 각 원소에 대해 그것을 검사합니다
db.passes.find({ entrances: "Южная" })
```

주목하세요: 조건은 마치 `entrances`가 값 `"Южная"`를 가진 평범한 필드인 것처럼 적혔지만,
실제로는 목록입니다. **MongoDB는 필드가 목록이면 조건을 각 원소에 대해 검사해야 한다는 것을
스스로 이해합니다.** "포함한다"를 위한 별도의 구문은 필요 없습니다.

**미성년자가 포함된 단체 출입증:**

```js
// members.age 경로는 객체 목록 안으로 이어집니다 — 각 참가자의 age 필드로.
// $lt = less than. $가 붙은 조건은 값이 아니라 비교 방법입니다:
// "필드는 16보다 작아야 한다", "필드는 16과 같아야 한다"가 아니라
db.passes.find({ "members.age": { $lt: 16 } })
```

점 경로는 객체 목록 안으로도 동작합니다: 조건이 각 참가자에 대해 검사됩니다. `$lt` — "보다
작음". 이런 종류의 조건이 스무 개쯤 있습니다: `$gt`, `$gte`, `$in`, `$ne`, `$exists`,
`$regex` 등등.

**차량이 조금이라도 지정된 모든 출입증:**

```js
// $exists는 값이 아니라 문서에 그 필드가 있느냐 자체를 묻습니다:
// "이 문서에 car 필드가 조금이라도 있는가?"
db.passes.find({ car: { $exists: true } })
```

`$exists`가 바로 "필드가 없음"과 "필드가 비어 있음" 사이의 구별입니다. 테이블에서는 이 물음이
생기지 않습니다: 컬럼은 항상 있고, 유일한 물음은 `NULL`입니다.

**경영진을 위한 요약 — 각 유형의 출입증이 몇 개인지.** 여기서 쿼리는 문서를 선택하는 것이
아니라 그것들에 대한 합계를 계산하므로, 명령이 다릅니다 — `aggregate`. 입력하기 전에 짚어
봅시다.

<details>
<summary><b>집계 파이프라인 짚어 보기</b></summary>

MongoDB의 집계는 **파이프라인**입니다: 각각이 이전 것의 결과를 입력으로 받는 단계들의 목록. 한
명령의 출력이 다음 명령의 입력으로 가는 셸의 명령 파이프라인과 비슷합니다.

`$group` — 그룹으로 묶기. `_id: "$type"`는 "그룹화 키는 `type` 필드의 값"이라는 뜻입니다;
이름 앞의 달러 기호는 "이것은 문자열이 아니라 필드에 대한 참조"라고 말합니다. `$sum: 1` —
문서마다 1을 더하기, 즉 세기.

`$sort: { count: -1 }` — 내림차순으로 정렬; `-1`은 "내림차순", `1`은 "오름차순".

SQL에서 같은 결과 — `SELECT type, count(*) FROM passes GROUP BY type ORDER BY 2 DESC`. 더
짧고, 더 익숙하며, 여기서 정직한 비교는 MongoDB에 불리합니다: 그 쿼리 언어는 더 장황하고 익히는
데 더 오래 걸립니다.

</details>

```js
// aggregate = "문서를 단계의 사슬에 통과시켜라". 단계는 순서대로 가며,
// 각자 이전 단계가 내놓은 것을 받습니다:
//   $group — 문서를 type 필드의 값에 따라 그룹으로 나누고, 각각을 셉니다
//   $sort  — 그룹을 개수로 정렬, -1은 "내림차순"을 뜻합니다
db.passes.aggregate([
  { $group: { _id: "$type", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
])
```

**여러분이 보게 될 것** — `{ _id: 'разовый', count: 1 }` 형태의 네 줄.

## 단계 5. 대부분이 갖고 있지 않은 필드에 대한 인덱스

📍 **위치:** 작업용 Pod 안의 `mongosh` 셸에서.

경비는 매일 번호판으로 검색합니다. 지금 이 검색이 어떤 비용이 드는지 봅시다: 쿼리는 이전과
같지만, 문서 대신 데이터베이스가 그것들을 어떻게 찾았는지에 대한 보고서를 요청합니다.

```js
// explain = "문서를 주지 말고, 그것들을 어떻게 찾았는지 말해 줘"
//   "executionStats"     보고서 모드: 계획뿐 아니라 실제로 일어난 일까지
//   .executionStats      답에서 전부 읽지 않도록 바로 이 부분만 가져옵니다
// 보고서에서 totalDocsExamined를 봅니다 — 하나를 돌려주려고
// 데이터베이스가 문서를 몇 개 읽었는지
db.passes.find({ "car.plate": "А123ВС174" }).explain("executionStats").executionStats
```

**여러분이 보게 될 것** — `totalDocsExamined`가 컬렉션의 문서 수와 같습니다. 데이터베이스는
하나를 찾으려고 전부를 훑었습니다. 문서 네 개에서는 눈에 띄지 않지만, 사십만 개에서는 더 이상
그렇지 않습니다.

인덱스를 만듭니다 — 데이터베이스가 필요한 문서를 전부 차례로 읽지 않고 찾는 데 쓰는 별도의
구조입니다:

```js
// createIndex = "이 필드에 인덱스를 만들고 이제부터 스스로 계속 유지해라"
//   { "car.plate": 1 }   어떤 필드에. 1은 "오름차순" 순서
//   name: "car_plate"    인덱스를 뭐라 부를지, 나중에 알아보고 삭제할 수 있도록
//   sparse: true         필드를 가진 문서만 인덱스에 들어갑니다
db.passes.createIndex({ "car.plate": 1 }, { name: "car_plate", sparse: true })

// 같은 보고서를 되풀이하고 이전 것과 비교합니다
db.passes.find({ "car.plate": "А123ВС174" }).explain("executionStats").executionStats
```

**여러분이 보게 될 것** — `totalDocsExamined`가 1과 같고, 계획에는 `COLLSCAN` 대신 `IXSCAN`
이 나타났습니다. 이것들은 검색 방법의 이름입니다: `COLLSCAN`은 컬렉션 전체의 스캔, `IXSCAN`은
인덱스를 통한 조회.

<details>
<summary><b>희소 인덱스란 무엇이고 왜 여기 있는가</b></summary>

`{ "car.plate": 1 }` — 어떤 필드에 만들지; `1`은 "오름차순", `-1`은 내림차순을 뜻합니다.
정확히 일치하는 검색에는 방향이 중요하지 않지만, 정렬에는 중요합니다.

`sparse: true` — **필드를 가진 문서만 인덱스에 들어갑니다.**

이 플래그가 없으면 MongoDB는 차량이 없는 세 문서에 대해서도 "필드 없음" 값으로 인덱스 항목을
만들었을 것입니다. 인덱스는 거의 두 배로 커지고, 그 항목들은 아무짝에도 쓸모가 없습니다:
"차량이 지정되지 않음"이라는 기준으로 출입증을 검색하는 사람은 없습니다.

실제 출입증 대장에서는 차량 출입증이 십 퍼센트쯤 됩니다. 희소 인덱스는 평범한 인덱스보다 열 배
작고 유지 비용도 열 배 쌉니다.

⚠️ **희소 인덱스에는 대가가 있으며, 그것을 알아야 합니다.** 그런 인덱스를 통해 이 필드로
정렬하면 필드가 없는 문서를 잃게 됩니다 — 그것들이 인덱스 안에 없기 때문입니다. 그런 경우
MongoDB는 스스로 인덱스를 버리고 스캔으로 돌아가는데; 불쾌한 점은 이것이 조용히 일어난다는
것입니다.

**이제 이 단계의 요점입니다.** 모든 출입증 유형을 위한 단일 테이블을 가진 관계형
데이터베이스에서는 `car_plate`에 대한 인덱스를 아흔 퍼센트의 행이 `NULL`인 컬럼에 만들어야
했을 것입니다. 일부 DBMS는 그런 행도 어쨌든 인덱스에 넣고, 그러면 부풀어 오릅니다. 이는 부분
인덱스로 우회합니다 — `sparse`와 같은 종류의 메커니즘이지만, 어디서나 쓸 수 있는 것은 아니고
금방 눈에 띄지도 않습니다.

그러니 문제는 하나이며 같습니다. 차이는, 여기서는 그것이 "모든 유형을 한 테이블에 넣자"의
부작용으로 생기지 않는다는 점입니다: 우리에게는 소수의 레코드를 위해 만들어야 했던 컬럼이
없습니다.

</details>

## 예견된 실패 · 목록에 없는 출입증

계속 작업합시다. 정문의 근무자가 일회용 출입증을 하나 더 발급했습니다 — 급하게 작성된 스크립트를
통해:

```js
// insertOne = "문서 하나를 추가해라". 그 안에 어떤 필드가 있는지 데이터베이스는 묻지 않습니다
db.passes.insertOne({
  tipe: "разовый",
  guest: "Николаев Сергей Игоревич",
  host: "petrov@corp.ru",
  data: ISODate("2026-09-04T09:00:00Z")
})
```

삽입이 성공했습니다: `acknowledged: true`("받아들임")와 새로운 `_id` — 데이터베이스가 스스로
만들어 낸 문서의 고유 키 — 가 돌아왔습니다. 이제 문서가 다섯 개인지 확인합시다:

```js
// countDocuments = "조건에 맞는 문서를 세라".
// 빈 중괄호는 제약이 없는 조건, 즉 "전부"입니다
db.passes.countDocuments({})
```

다섯. 이제 경비가 매일 아침 하는 일 — 일회용 출입증 목록을 엽니다:

```js
// 검색 단계와 같은 type 기준 선택: type 필드가 "разовый"와
// 같은 출입증을 보여 주기
db.passes.find({ type: "разовый" })
```

> **더 읽기 전에 멈추고 생각해 보십시오.**
>
> 출입증이 몇 개 돌아왔나요? 다섯 번째는 어디 있나요? 관계형 데이터베이스에서 같은 오류가
> 일어나면 어떻게 될까요 — 그리고 왜 그것이 더 나을까요?

<details>
<summary><b>답과, 이 오류보다 더 넓은 교훈</b></summary>

출입증이 둘이 아니라 하나 돌아왔습니다. 손님 니콜라예프가 도착하면 경비는 그를 찾지 못하고,
그것을 해결하는 데 시간이 걸릴 것입니다 — 왜냐하면 문서는 **존재하고**, **성공적으로
삽입되었으며**, 어디에도 오류가 기록되지 않았기 때문입니다.

원인은 두 개의 오타입니다: `type` 대신 `tipe`, `valid_on` 대신 `data`. MongoDB는 그것들을
알아차리지 못했습니다, 왜냐하면 **컬렉션에는 스키마가 없고, 따라서 어떤 필드가 옳은지에 대한
의견도 없기 때문입니다.** 그것에게 `tipe`는 다른 어떤 필드와도 똑같이 정당한 필드입니다.

피해자를 찾아봅시다 — `type` 필드가 아예 없는 문서:

```js
// $exists: false — 이전 단계의 반대: "필드가 문서에 없다".
// 이런 쿼리는 손 닿는 곳에 둘 가치가 있습니다: 스키마를 벗어나 쌓인 것을 보여 줍니다
db.passes.find({ type: { $exists: false } })
```

관계형 데이터베이스에서 `tipe` 컬럼을 가진 `INSERT`는 즉시 실패했을 것입니다:
`column "tipe" does not exist`. 오류는 일주일 뒤 정문이 아니라 테스트에서 드러났을 것입니다.
**이것이 스키마 유연성의 주된 대가입니다: 예전에 데이터베이스가 하던 검사를 이제 다른 누군가가
해야 합니다.**

**교훈은 이 오류보다 넓습니다.** 그리고 여기서 잘못된 결론을 내리지 않는 것이 중요합니다. 옳은 결론은
"문서 데이터베이스는 나쁘다"가 아니라 "기본적으로 스키마가 없다는 것이 스키마가 아예 없다는
뜻은 아니다"입니다. 여러분의 데이터에는 언제나 스키마가 있습니다: 명시적으로 기술되어 있거나,
아니면 아무도 검사하지 않는 사람들의 머릿속과 코드 안에 살고 있습니다.

손상된 문서를 지우고 검증을 켭시다.

</details>

type이 없는 문서를 삭제합니다:

```js
// deleteMany = "조건에 맞는 모든 문서를 삭제해라". 조건은 위의 검색과
// 같습니다 — 즉 방금 본 바로 그것이 삭제됩니다
db.passes.deleteMany({ type: { $exists: false } })
```

**여러분이 보게 될 것** — `deletedCount: 1`.

이제 검증을 켭시다 — 모든 문서가 반드시 충족해야 하는 규칙입니다. 그것은 `validator.js`
파일에 있습니다; 적용하기 전에 짚어 봅시다.

<details>
<summary><b>규칙 짚어 보기</b></summary>

```js
db.runCommand({
  collMod: "passes",
  validator: { $jsonSchema: { … } },
  validationLevel: "strict",
  validationAction: "error"
});
```

`collMod` — 기존 컬렉션의 설정을 변경. 검증기는 살아 있는 컬렉션에 나중에 걸리며, 아무것도
멈출 필요가 없습니다.

```js
      required: ["type", "host"],
```

필수 필드. **목록에 무엇이 없는지 주목하세요: `guest`.** 단체 출입증에는 손님이 없고, 그 자리에
조직이 있습니다. 규칙은 정당한 문서 형태가 그것을 통과할 만큼 넓어야 합니다 — 그리고 이 제약은
곧바로 느껴집니다: 여러분의 문서가 다양할수록, 그것들 모두에게 함께 요구할 수 있는 것은
적어집니다.

```js
        type: {
          enum: ["разовый", "недельный", "автомобильный", "групповой"],
        },
```

목록에 있는 값만. 다섯 번째 출입증 유형은 규칙 변경을 요구할 것입니다 — 그리고 그것은 좋은
일입니다: 변경이 의도적인 것이 됩니다.

```js
        car: {
          bsonType: "object",
          required: ["plate"],
          …
        },
```

규칙은 중첩 객체에도 작동합니다. `car` 필드가 있으면, 반드시 `plate`가 있어야 합니다. 필드가
없으면 — 아무 요구도 없고, 문서는 정당합니다.

```js
  validationLevel: "strict",
  validationAction: "error"
```

`strict` — 모든 삽입과 모든 갱신을 검증. 더 부드러운 `moderate`가 있습니다: 새 문서와, 이미
규칙을 충족하는 문서에 대한 갱신을 검증하되, 오래된 부적합한 것들은 그대로 둡니다. 이미 불일치가
쌓인 컬렉션에는 바로 이 `moderate`로 검증을 켭니다: 먼저 더 나빠지는 것을 멈추고, 그다음 오래된
것을 고치고, 그다음 `strict`로 전환합니다.

`error` — 거부. `warn`이 있습니다: 로그에 기록하고 어쨌든 받아들이기. 거부를 켜기 전에 얼마나
많이 들어오는지 일주일 지켜보기에 좋습니다.

</details>

규칙을 적용합니다:

```bash
# passes.js와 같은 방식: 파일의 내용이 mongosh의 입력으로 들어갑니다.
# 규칙은 살아 있는 컬렉션에 걸립니다 — 데이터베이스를 멈출 필요가 없습니다
mo < validator.js
```

**여러분이 보게 될 것** — `правило установлено`.

같은 오타를 되풀이해 봅니다 — 이제 규칙의 감시 아래에서:

```js
// tipe 필드는 규칙에게 알려지지 않았고, 문서에는 필수인 type이 없습니다.
// 전에는 이런 문서가 조용히 컬렉션에 자리 잡았습니다
db.passes.insertOne({ tipe: "разовый", guest: "Проверка", host: "x@corp.ru" })
```

**여러분이 보게 될 것** — `MongoServerError: Document failed validation`. 이제 오타는
통과하지 못합니다.

⚠️ **검증이 모든 것을 잡아내지는 않으며, 이것은 분명히 말해야 합니다.** 규칙은 `type` 필드가
있고 목록에 있는 값일 것을 요구합니다. **선택적** 필드의 오타는 — `guest` 대신 `guestt` —
통과시킵니다: 문서는 여전히 정당하고, 그저 여분의 필드가 있을 뿐입니다. 알려지지 않은 필드를
모두 금지할 수는 있지만(`additionalProperties: false`), 그러면 새 필드가 생길 때마다 규칙을
고쳐야 하고, 여러분은 벗어나려던 바로 그것으로 되돌아갑니다 — 사소한 일마다 스키마
마이그레이션. 어디에 선을 그을지는 여러분이 내리는 결정이며, 그것은 언제나 타협입니다.

## 단계 6. 정직하게: 문서 모델이 지는 곳

📍 **위치:** 작업용 Pod 안의 `mongosh` 셸에서.

스키마 유연성이 유일한 차이는 아니며, 나머지는 MongoDB에 유리하지 않습니다.

<details>
<summary><b>익숙한 형태의 조인이 없다</b></summary>

과제: 각 출입증에, 그것을 주문한 직원의 전화번호와 직책을 끌어오기. 직원은 별도의 컬렉션
`staff`에 있고, 키는 이메일입니다.

SQL에서 이것은 한 줄입니다: `JOIN staff ON staff.email = passes.host`.

여기서는 — 파이프라인 단계:

```js
db.passes.aggregate([
  // $lookup = "각 출입증마다 다른 컬렉션으로 가서 거기서 레코드를 가져와라"
  { $lookup: {
      from: "staff",          // 어디로 갈지 — 직원 컬렉션
      localField: "host",     // 어떤 출입증 필드를 비교할지
      foreignField: "email",  // 어떤 직원 필드와
      as: "host_info"         // 찾은 것을 어떤 이름으로 문서에 넣을지
  } },
  // 찾은 것은 일치가 하나뿐이어도 항상 목록으로 들어갑니다.
  // $unwind는 목록을 다시 하나의 값으로 풀어 냅니다
  { $unwind: "$host_info" }
])
```

우리에게는 `staff` 컬렉션이 없습니다 — 쿼리는 아무것도 반환하지 않습니다. 이것은 랩 단계가
아니라 구문의 예시로 여기 있습니다.

동작합니다. 그러나:

- `$lookup`은 **단방향**입니다: 왼쪽의 각 문서마다 오른쪽에서 검색이 실행됩니다. 이것은 조인
  방법을 선택할 옵티마이저가 아니라, 바로 완전 탐색 조회입니다
- 결과는 일치가 하나뿐이어도 **목록으로** 돌아옵니다. 그래서 그것을 풀기 위한 `$unwind`
- 두 개보다 많은 컬렉션을 조인하는 것은 번거롭고 느립니다
- 샤딩된 배포에서는 최근까지 `$lookup`이 제약을 안고 작동했습니다

그래서 MongoDB 세계에서는 과제를 다르게 풉니다: **함께 필요한 데이터는 함께 저장합니다.**
주문자의 전화번호와 직책을 출입증 문서에 곧장 씁니다.

그리고 이것은 사소한 불편이 아니라 진짜 맞바꿈입니다:

| | `staff`에 대한 참조 | 문서 안의 데이터 사본 |
|---|---|---|
| 읽기 | `$lookup` 필요 | 한 번의 조회 |
| 직원이 전화번호를 바꿈 | 한 곳에서 고침 | 모든 출입증을 돌아다녀야 함 |
| 무결성 | 데이터베이스가 지킴 | 애플리케이션이, 즉 여러분이 지킴 |

관계형 데이터베이스에는 선택이 없습니다 — 거기서는 정규화와 외래 키입니다. 여기에는 선택이
있고, 그와 함께 책임이 있습니다.

</details>

<details>
<summary><b>외래 키가 아예 없다</b></summary>

해 보세요:

```js
// host 필드는 의미상 직원을 참조합니다. 그런 직원은 존재하지 않습니다 —
// 데이터베이스가 이것을 검사할까요? 문서는 지난 단계의 규칙을 충족합니다: type이
// 제자리에 있고 목록에서 왔으며, host는 문자열입니다
db.passes.insertOne({ type: "разовый", host: "не-существует@corp.ru", guest: "Тест" })
```

문서는 삽입됩니다. 그런 이메일을 가진 직원은 없지만, 데이터베이스는 그것을 보지 않습니다.

관계형 데이터베이스에서는 외래 키가 그런 행을 거부했을 것입니다. 여기에는 외래 키라는 개념이
아예 존재하지 않습니다: **데이터의 정합성은 전적으로 애플리케이션에 달려 있습니다.** 지난
단계의 검증기는 문서의 형태를 검사하지만, 필드의 값이 다른 컬렉션에 존재하는지는 검사할 수
없습니다.

실제로 이것은: "그런 직원이 있는가"라는 검사 하나하나를 개발자가 작성하고, 그가 그것을 잊었다면
— 경비가 주문자에게 전화하려 할 때 알게 된다는 뜻입니다.

테스트 문서를 지우는 것을 잊지 마세요:

```js
// deleteOne = "조건에 맞는 문서 하나를 삭제해라", 전부를 한꺼번에가 아니라
db.passes.deleteOne({ host: "не-существует@corp.ru" })
```

</details>

<details>
<summary><b>트랜잭션은 있지만 기본은 아니다</b></summary>

여기서는 정확한 것이 중요합니다, 왜냐하면 사람들이 MongoDB에 대해 양쪽 방향으로 사실이 아닌
말을 자주 하기 때문입니다.

**사실:** 다중 문서 트랜잭션은 MongoDB에 있으며, 레플리카 세트의 경우 버전 4.0부터입니다. 두
문서를 둘 다 적용되거나 둘 다 안 되도록 바꿀 수 있습니다.

**역시 사실:** 기본적으로는 없습니다. **단일 문서**에 대한 연산은 원자적입니다. 더 원한다면 —
세션을 열고 명시적으로 트랜잭션을 시작하세요:

```js
// 세션은 데이터베이스와의 별도의 "대화"이며, 그 안에서 트랜잭션을 선언할 수 있습니다
const s = db.getMongo().startSession();
s.startTransaction();          // 이 지점부터 변경이 쌓이지만, 누구에게도 보이지 않습니다
// … s.getDatabase("passes")를 통한 연산 …
s.commitTransaction();         // 전부 한꺼번에 적용. 전부 한꺼번에 취소하려면 — abortTransaction()
```

**그리고 세 번째 진실, 가장 실용적인 것:** MongoDB의 트랜잭션은 관계형 데이터베이스보다 비싸고,
시간 제한이 있으며, 데이터 모델 전체가 여러분이 그것을 거의 필요로 하지 않는다는 가정 위에
세워져 있습니다. 여러분의 시나리오가 그것을 자주 요구한다면, 그것은 데이터를 다르게 배치했어야
한다는 — 또는 여기에 문서 데이터베이스가 필요 없다는 — 신호입니다.

출입증 서비스에는 이것이 문제가 아닙니다: 출입증은 단일 문서이고, 그에 대한 모든 연산은 그
자체로 원자적입니다. 급여 계산에는 문제이며, 그것도 큰 문제입니다.

</details>

<details>
<summary><b>스키마 불일치는 저절로 스며든다</b></summary>

우리는 이미 오타에서 이것을 보았습니다. 그러나 더 음험한 종류가 있습니다: 오류가 아니라
부주의로 스며든 불일치입니다.

일 년 뒤 여러분은 컬렉션에서 날짜가 세 가지 방식으로 저장되어 있음을 발견합니다: `ISODate`로,
문자열 `"2026-09-01"`로, 그리고 타임스탬프가 붙은 숫자로 — 세 팀이 서로 다른 시기에 그것들을
썼기 때문입니다. 날짜에 대한 범위 검색은 레코드의 삼분의 일을 찾아내고, 아무도 이유를 이해하지
못합니다.

컬렉션에 실제로 무엇이 있는지는 이렇게 볼 수 있습니다:

```js
db.passes.aggregate([
  // $$ROOT — 문서 전체 그대로. $objectToArray는 그것을
  // "필드 이름 — 값" 쌍으로 쪼개서, 그다음 필드를 데이터로 다룰 수 있게 합니다
  { $project: { fields: { $objectToArray: "$$ROOT" } } },
  // 쌍의 목록을 풀어 냅니다: 한 쌍 — 다음 단계의 입력에서 한 줄
  { $unwind: "$fields" },
  // 두 속성으로 한꺼번에 그룹화합니다: 필드 이름(k)과 그 값의 타입(t),
  // 그리고 그런 조합이 몇 번 나왔는지 셉니다
  { $group: { _id: { k: "$fields.k", t: { $type: "$fields.v" } }, n: { $sum: 1 } } },
  { $sort: { "_id.k": 1 } }   // 알파벳순으로, 한 필드가 자기 타입들과 나란히 있도록
])
```

쿼리는 각 문서를 "필드 — 값" 쌍으로 쪼개고, 값의 타입을 판별하고, 각 필드가 각 타입으로 몇 번
나왔는지 셉니다. 우리의 문서 네 개에서는 고른 그림을 보여 줍니다. 실제 컬렉션에서는 일 년 뒤에
아무도 의심하지 않던 것을 보여 주며, 물려받은 데이터베이스를 풀어헤칠 때 가장 유용한 쿼리 중
하나입니다.

**가져갈 만한 결론:** 스키마 검증기는 장식도 아니고 "형식적 체크"도 아닙니다. 문서
데이터베이스에서 그것은 여러분과 불일치 사이에 서 있는 유일한 것입니다. 그것은 다급해졌을 때가
아니라 곧바로 켜야 합니다.

</details>

**정직한 비교의 결론:**

| 과제 | 관계형 | 문서 |
|---|---|---|
| 같은 형태의 레코드 | 자연스러움 | 가능하기는 하지만 왜 |
| 다른 형태의 레코드 | 빈 컬럼 또는 유형마다 테이블 | 자연스러움 |
| 목록과 중첩 | 별도의 테이블 | 문서 안의 필드 |
| 다른 데이터와의 조인 | JOIN, 옵티마이저 | `$lookup` 또는 데이터 사본 |
| 참조 무결성 | 데이터베이스가 지킴 | 애플리케이션이 지킴 |
| 트랜잭션 | 기본으로 | 명시적, 더 비쌈, 더 드묾 |
| 오타 방어 | 언제나 스키마가 있음 | 검증기, 켰다면 |
| 스키마 변경 | 마이그레이션과 릴리스 | 새 필드가 저절로 나타남 |

## 정리

작업용 Pod는 더 이상 필요 없습니다 — 그동안 내내 `sleep` 명령으로 컨테이너를 바쁘게 붙들고
있었습니다:

```bash
# delete = "클러스터에서 제거해라". Pod는 자신의 MONGO_URI 변수와 함께 사라지므로,
# 비밀번호가 클러스터에 남지 않습니다
kubectl delete pod mongo-workbench
```

MongoDB 자체는 대시보드에서 삭제합니다: `passes` 애플리케이션 → 삭제.

왜 이것이 싼가. 고전적 인프라에서 MongoDB 레플리카 세트는 세 대의 가상 머신, 설치, 투표 설정,
복제 지연 모니터링, 그리고 그 모든 것을 고칠 줄 아는 사람입니다. 여기서 여러분은 서비스를 한
시간 빌렸다가 십 초 만에 반납했고, 그것이 차지하던 공간은 클러스터의 여유 용량으로
되돌아갔습니다 — 다른 누군가가 곧바로 차지할 수 있습니다.

⚠️ **삭제와 함께 데이터도 사라집니다.** 출입증 네 개는 명령 하나로 복원되므로, 랩에서는
손실이 아닙니다. 그 안에 진짜 무언가를 넣었다면 — 먼저 백업을 켜세요; 그것은 주문 양식의 별도
섹션입니다.

## 이제 우리가 할 수 있는 것

- 문서 모델이 언제 적절하고 언제 스스로 문제를 만드는 길인지 설명하기
- 카탈로그에서 MongoDB를 주문하고 `authSource`, 역할, 복사본 하나에 걸려 넘어지지 않기
- 서로 다른 형태의 문서를 저장하고 중첩 필드와 목록 안으로 검색하기
- 희소 인덱스를 만들고 그것이 절약의 대가로 무엇을 치르는지 이해하기
- 스키마 검증기를 켜고 그것이 무엇을 막고 무엇을 막지 못하는지 보기
- 문서 데이터베이스에 없는 것을 소리 내어 말하기: 외래 키, 익숙한 조인, 기본 트랜잭션

## 그리고 vSphere였다면 이것은

레플리카 세트를 위한 세 대의 머신, 그리고 그중 가장 손이 많이 가는 부분은 설치가 아니라
복사본들 사이의 투표를 설정하는 것입니다: 누가 주(primary)인지, 연결이 끊겼을 때 무엇을 할지,
뒤처진 것을 어떻게 되돌릴지. 게다가 일 년 뒤 누가 이 데이터베이스를 업데이트할지에 대해 정보
보안 팀과의 별도의 대화까지.

여기서는 — 카탈로그의 항목 하나와 오 분.

**vSphere가 더 편리한 곳, 정직하게.** MongoDB가 있는 가상 머신은 여러분이 걸어가 다가갈 수
있는 머신입니다: SSH로 로그인하고, `mongotop`을 들여다보고, 설정을 손보고, 위험한 작업 전에
스냅샷을 뜨기. 관리형 서비스는 이것을 **의도적으로** 주지 않습니다: 테넌트는 여러분이 Pod
안으로도, 데이터베이스의 로그 안으로도 `exec`하도록 허용하지 않습니다. 모든 것이 잘 돌아가는
한, 그것은 장점입니다 — 망가뜨릴 방법이 더 적으니까. 데이터베이스가 이상하게 굴 때, 관리자의
익숙한 동작 모음은 쓸 수 없고, 남은 것은 플랫폼을 운영하는 누군가에게 가는 것뿐입니다.

그리고 두 번째, 특히 MongoDB에 고유한 것. 관리형 서비스는 버전과 매개변수 묶음을 고정합니다.
MongoDB의 메이저 버전 업그레이드는 자기 설치 환경에서라면 여러분이 직접 계획하는 작업으로,
애플리케이션 호환성 검사와 스냅샷으로 롤백할 선택지가 딸립니다. 여기서 버전 변경은 양식의 필드
하나이고 그 아래에서 돌아가는 남의 업그레이드 절차입니다. 보통은 이것이 바로 여러분이 원하는
것입니다. 하지만 업그레이드가 잘못되는 날, 여러분은 자기 손으로 그것을 해결하지 않을 것이고,
이것을 도중에 발견하는 게 아니라 미리 이해해 둬야 합니다.
