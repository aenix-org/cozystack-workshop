# 랩 1 · 첫 번째 애플리케이션

| | |
|---|---|
| **소요 시간** | 25분 |
| **무엇을 증명하나** | 애플리케이션은 텍스트로 기술되고, 몇 초 만에 배포되며, 누구에게도 허락을 구하지 않는다 |
| **필요한 것** | 랩 0에서 만든 클러스터, `kubectl`, 파일 `~/lab.kubeconfig` |

## 왜 중요한가

실제 과제에 뛰어들기 전에, 해가 되지 않는 것으로 연습해 봅시다. 딱 하나의 일만 하는 아주 작은
애플리케이션을 배포합니다. 바로 **자기 자신의 복제본 이름을 보여주는** 것입니다.

무의미하게 들리지만, 바로 그 이름이 다음 세 개 랩의 주인공입니다. 그 이름을 통해 복제본이
죽었다가 다시 태어나는 것을 보고, 그것이 여섯 개로 불어나는 것을 보며, 옛 버전이 새 버전에
자리를 내주는 것을 보게 됩니다.

배포는 텍스트로 합니다. 파일 하나와 명령 하나로요. 이 랩에는 마우스가 없고, 거기에는 이유가
있습니다. 바로 그 이야기부터 시작합니다.

## 작은 용어집

| 용어 | 무엇인가 | ...와 비슷하지만 |
|---|---|---|
| **Pod** | 실행 중인 애플리케이션 복제본 | **가상 머신**과 비슷하지만, Pod는 일회용입니다. 수리하거나 백업하지 않습니다. 삭제하면 새것이 생성됩니다 |
| **Image** | 실행에 필요한 모든 것을 담은 애플리케이션의 스냅샷 | **VM 템플릿**과 비슷하지만, 불변입니다. 안으로 들어가 고칠 수 없고, 새것을 빌드합니다 |
| **Deployment** | 어떤 이미지를, 몇 개의 복제본을, 어떻게 업데이트할지에 대한 기술 | **vApp**과 비슷하지만, 특정 VM에 대한 참조가 아니라 원하는 복제본 수를 담습니다 |
| **Service** | 복제본들이 그 뒤에 자리하는 영구 주소 | **로드밸런서 풀**과 비슷하지만, 뒤에 있는 모든 복제본이 재생성되어도 이름은 바뀌지 않습니다 |
| **ConfigMap** | 클러스터 안에 사는 설정 파일 | **VM 디스크의 파일**과 비슷하지만, 애플리케이션과 떨어져 살면서 시작 시점에 안으로 밀어 넣어집니다 |
| **Manifest** | 원하는 상태를 기술하는 파일 | 직접적인 대응물이 없으며, 바로 그것이 핵심입니다 |

## 랩 폴더에 무엇이 있나

파일은 이미 모두 가지고 있습니다. 리포지터리와 함께 받아 왔으니까요. 새로 만들거나 다시 입력할
것은 없습니다. 아래에서 `kubectl apply -f name.yaml`이라고 쓰인 곳의 파일은 모두 여기서 가져옵니다.

```bash
# 이 경로는 랩 0에서 받아 온 리포지터리의 루트를 기준으로 합니다
cd labs/01-deploy
```

| 파일 | 무엇인가 | 언제 필요한가 |
|---|---|---|
| `rickroll.yaml` | 애플리케이션 전체: nginx 설정, 배포 자체, 그리고 그것으로 들어가는 진입점 | 자신의 `lab` 클러스터에 적용합니다 |
| `check.sh` | 애플리케이션이 응답하고 Pod 이름을 돌려주는지 확인하는 검사 | 랩 마지막에 실행합니다 |

## 1단계. 대시보드가 끝나고 당신의 클러스터가 시작되는 곳

📍 **어디서:** 노트북에서.

Cozystack 대시보드는 당신이 **플랫폼에 주문하는 것**을 보여줍니다. Kubernetes 클러스터, 데이터베이스,
큐, 가상 머신 같은 카탈로그 항목들이죠. `lab` 클러스터는 거기에 하나의 항목으로 보입니다. 주문되어
실행 중인 것으로요.

대시보드는 그 안을 들여다보지 않고, 볼 수도 없습니다. 당신의 클러스터는 자체 주소와 자체 접근 파일을
가진 별도의 API 서버입니다. 바로 그 `~/lab.kubeconfig`이죠. 관리 대시보드는 그것과 통신하지 않습니다.
`lab` 클러스터에는 자체 그래픽 콘솔도 없습니다. 거기에 붙일 수 있는 애드온 중에 그런 것은 없습니다.

여기서 책임의 경계가 생기고, 기억해 둘 만합니다. **플랫폼은 당신이 주문한 것을 책임지고, 주문한 것
안에 있는 것은 당신이 책임집니다.** 클러스터 안에서의 작업은 `kubectl`을 통해 이루어집니다. 객체
기술을 그 API 서버로 보내고 지금 거기에 무엇이 있는지 보여주는 명령이죠.

연결해 봅시다:

```bash
# KUBECONFIG — kubectl이 어떤 접근 파일을 쓸지 알아내기 위해 읽는 변수입니다.
# 여기서는 테넌트가 아니라 lab 클러스터에 대한 접근입니다: 파일이 다르고, 클러스터가 다릅니다.
export KUBECONFIG=~/lab.kubeconfig
# get nodes = "노드를 보여줘". 그 응답은 kubectl이 올바른 곳과 통신하고 있음을 확인해 줍니다.
kubectl get nodes
```

**보여야 할 것:** 당신의 노드와 `Ready` 상태가 적힌 한 줄. 대신 연결 오류가 나온다면
`echo $KUBECONFIG`를 확인하세요. 이 변수는 새 터미널 창을 열 때마다 설정해야 합니다.

## 2단계. 애플리케이션 배포하기

📍 **어디서:** 노트북에서.

이 랩의 폴더로 이동하세요. 리포지터리는 랩 0에서 받아 왔습니다:


폴더에 `rickroll.yaml`이 있습니다. 적용하기 전에, 그 안에 무엇이 있는지 살펴봅시다.

<details>
<summary><b>자세히 보기: rickroll.yaml 안에 무엇이 있나</b></summary>

파일에는 `---` 줄로 구분된 네 개의 객체가 있습니다. 순서대로 살펴봅시다.

### 첫 번째: 웹 서버 설정

```yaml
kind: ConfigMap
metadata:
  name: rickroll-conf
data:
  default.conf: |
    server {
      listen 8080;
      root /usr/share/nginx/html;
      location / {
        sub_filter '__POD__' '$hostname';
        sub_filter_once off;
      }
    }
```

`ConfigMap`은 설정 파일을 애플리케이션과 분리해 클러스터에 넣는 방법입니다. 안에는 평범한 nginx
설정이 있습니다(nginx는 웹 서버이며, 우리 페이지를 서빙하는 바로 그것입니다). 가상 머신의
`/etc/nginx/conf.d/`에 놓였을 법한 것과 같습니다.

핵심 줄은 `sub_filter '__POD__' '$hostname'`입니다. nginx에게 이렇게 말합니다: 서빙하는 페이지에서
`__POD__`이라는 텍스트를 네가 실행되고 있는 머신의 이름으로 바꿔라. Pod 안에서 머신 이름은 Pod
자신의 이름입니다. 그렇게 해서 페이지는 누가 자신을 서빙했는지 알게 됩니다.

왜 설정을 이미지 안에 굽지 않고 별도 객체로 두느냐면, 이미지를 다시 빌드하지 않고도 바꿀 수 있게
하기 위해서입니다. 버전 롤아웃에 관한 랩에서 이것을 활용합니다.

### 두 번째: 페이지 자체

```yaml
kind: ConfigMap
metadata:
  name: rickroll-page-v1
data:
  index.html: |
    ...<div class="pod">요청을 처리한 Pod<b>__POD__</b></div>...
```

nginx가 치환할 바로 그 `__POD__`입니다. 이름의 `-v1`은 우연이 아닙니다. 버전 롤아웃에 관한 랩에서
`-v2`가 나타나고, 그 둘 사이를 전환하는 것이 새 버전의 롤아웃이 됩니다.

### 세 번째: 애플리케이션

```yaml
kind: Deployment
spec:
  replicas: 1
```

`Deployment`는 애플리케이션 전체에 대한 기술입니다. `replicas: 1`은 몇 개의 복제본을 계속
실행해 둘지입니다. 표현에 주목하세요. "하나를 실행하라"가 아니라 **"하나를 유지하라"**입니다. 그
차이는 다음 랩에서, 우리가 복제본을 삭제할 때 드러납니다.

```yaml
      image: nginxinc/nginx-unprivileged:1.27-alpine
```

이미지입니다. nginx의 비특권(unprivileged) 변형을 골랐습니다. 8080 포트에서 리스닝하고 root로
실행되지 않습니다. 일반 nginx는 제대로 구성된 클러스터에서는 허용되지 않는 권한을 요구합니다. 이건
우리가 까탈스러운 게 아니라, 어떤 현대적 클러스터에서든 마주치게 될 보안 요구 사항입니다.

```yaml
      resources:
        requests: {cpu: 20m, memory: 32Mi}
        limits:   {cpu: 300m, memory: 128Mi}
```

두 가지 다른 것이고, 끊임없이 혼동됩니다.

`requests`는 **보장으로서 얼마나 예약할지**입니다. 스케줄러는 이 숫자로 Pod가 어느 노드에 들어갈지
결정합니다. 가장 가까운 대응물은 vSphere의 reservation입니다.

`limits`는 그 위로 **올라가지 못하게 할** 천장입니다. 대응물은 vSphere의 limit입니다.

`20m`은 "20 밀리-CPU", 즉 코어의 100분의 2로 읽힙니다. 우리는 일부러 적게 요청합니다. 애플리케이션이
아주 작기 때문이고, 스케일링 랩에서 낮은 request가 복제본이 늘어나는 것을 눈으로 직접 보게 해주기
때문입니다.

```yaml
      readinessProbe:
        httpGet: {path: /healthz, port: http}
```

준비성 검사입니다. 클러스터는 이 주소를 두드려 보고, 응답을 받기 전까지는 Pod로 트래픽을 보내지
않습니다. 바로 이것이 버전 롤아웃에 관한 랩에서 무중단 업데이트를 제공합니다. 새 복제본은 요청을
정말로 처리할 준비가 되었을 때에만 요청을 받기 시작합니다.

### 설정은 어떻게 컨테이너 안으로 들어가나

두 개의 ConfigMap을 기술했지만, 그것들만으로는 그저 클러스터 안에 놓여 있을 뿐 nginx까지 도달하지
않습니다. 두 개의 블록이 그것들을 이어 줍니다. 그리고 이 랩의 모든 묘미가 거기에 달려 있습니다:

```yaml
          volumeMounts:
            - name: page
              mountPath: /usr/share/nginx/html
            - name: conf
              mountPath: /etc/nginx/conf.d
      volumes:
        - name: page
          configMap:
            name: rickroll-page-v1
        - name: conf
          configMap:
            name: rickroll-conf
```

아래에서 위로 읽습니다. `volumes`는 선언합니다: "이 ConfigMap을 가져다 파일들의 폴더로 만들어라".
`volumeMounts`는 말합니다: "그 폴더를 컨테이너 안 이 경로에 놓아라". 그 결과 `index.html`은 nginx가
페이지를 찾는 곳에, `default.conf`는 설정을 찾는 곳에 놓입니다.

당신의 세계에서 가장 가까운 비유는 공유 폴더를 가상 머신에 붙이는 것입니다. 차이는 그 내용물이
클러스터 안에 별도 객체로 살아 있고, 이미지도 머신 자체도 건드리지 않고 바꿀 수 있다는 점입니다.

⚠️ **`volumes`의 순서가 중요합니다.** 버전 롤아웃에 관한 랩은 볼륨을 **번호로** 지정하는 명령으로
페이지를 전환합니다. 목록의 첫 번째를요. 블록을 서로 바꿔 놓으면, 그 명령은 조용히 페이지 대신 설정을
치환해 버리고, nginx는 동작을 멈춥니다. 파일 자체에 이에 관한 주석이 있습니다. 안전한 방법 — 번호
대신 볼륨 이름으로 하는 patch-merge — 은 버전 롤아웃에 관한 랩에서 다룹니다.

### 네 번째: 영구 주소

```yaml
kind: Service
spec:
  selector:
    app: rickroll
  ports:
    - port: 80
      targetPort: http
```

`Service`는 애플리케이션의 모든 복제본이 그 뒤에 자리하는 영구 이름입니다. `rickroll`로 요청하면,
그중 어느 하나에 도달합니다.

Service와 Pod 사이의 연결은 주소 목록이 아니라 **조건**입니다. `selector: app: rickroll`은 "레이블이
`app: rickroll`인 모든 Pod"를 뜻합니다. 레이블(label)은 나중에 그 쌍으로 객체를 찾을 수 있도록 객체에
붙이는 임의의 "키: 값" 쌍입니다. 가장 가까운 것은 vSphere의 태그이지만, 여기서 레이블은 눈으로 훑어
보기 위한 것이 아니라 실제로 동작하는 연결을 짓기 위한 것입니다. 이 레이블을 가진 새 Pod가 나타나면,
그것은 자동으로 로드 밸런싱에 합류합니다. 사라지면 빠집니다. 아무도 목록을 손으로 고치지 않습니다.

바로 이것이 주소를 적어 넣는 로드밸런서 풀과의 핵심적인 차이입니다.

</details>

이제 적용해 봅시다:

```bash
# apply = "파일에 기술된 상태로 클러스터를 만들어라". 네 개의 객체가 모두 하나의 명령으로 생성됩니다;
# 파일 안의 순서는 클러스터가 스스로 알아냅니다.
#   -f   파일에서 기술을 가져온다
kubectl apply -f rickroll.yaml
```

**보여야 할 것** — 객체가 생성되었다는 네 줄:

```
configmap/rickroll-conf created
configmap/rickroll-page-v1 created
deployment.apps/rickroll created
service/rickroll created
```

복제본이 기동될 때까지 기다리세요:

```bash
# rollout status는 Deployment가 일을 끝까지 마칠 때까지 기다립니다: 필요한 수의 복제본이
# 실행 중이고 요청을 받을 준비가 될 때까지요. 그렇게 되면 명령은 스스로 종료됩니다.
kubectl rollout status deployment/rickroll
```

기다린 시간은 몇 초에 불과했습니다. 기동된 것은 운영체제가 아니라 이미 실행 중인 것 안의 하나의
프로세스였습니다. 노드의 커널은 오래전에 올라와 모든 컨테이너가 공유합니다. 같은 자리의 가상
머신이라면 부팅에 1~2분이 걸렸을 것입니다. 자신의 커널, 서비스, 네트워크를 올려야 하니까요.

## 3단계. 클러스터가 파일로부터 무엇을 만들었는지 보기

📍 **어디서:** 노트북에서.

클러스터는 파일 자체가 아니라 그것으로부터 생성한 객체들을 저장합니다. 우리가 적용한 것이 지금은
어떤 모습인지 물어봅시다:

```bash
# get deployment rickroll = 타입과 이름으로 하나의 객체를 보여준다.
#   -o yaml   손으로 쓸 수 있었을 바로 그 형태로, 전체를 출력한다
kubectl get deployment rickroll -o yaml
```

출력은 깁니다. 대부분은 클러스터가 스스로 채워 넣었습니다. 기본값, 내부 필드, 현재 상태 등이죠.
다음 줄들을 눈으로 찾아보세요:

```yaml
spec:
  replicas: 1
  template:
    spec:
      containers:
      - image: nginxinc/nginx-unprivileged:1.27-alpine
```

이것이 당신이 파일에 쓴 것입니다. **클러스터 안에서는 모든 것이 텍스트로 기술됩니다** — 당신이
적용하는 것도, 클러스터가 돌려주는 것도요. 랩 0에서 Cozystack 대시보드로 클러스터를 주문했을 때,
대시보드는 바로 이런 텍스트를 조립해 플랫폼으로 보냈습니다. 버튼은 텍스트 위의 한 겹이지, 그것의
대안이 아닙니다.

차이는 그 뒤에 남는 것에 있습니다. 파일은 Git에 넣고, 적용하기 전에 리뷰하고, 누가 언제 바꿨는지
찾아보고, 한 번의 명령으로 롤백하고, 첫 번째 클러스터에서 어떤 체크박스를 켰는지 떠올리려 애쓰지
않고도 같은 것을 두 번째 클러스터에 배포할 수 있습니다. 마우스 클릭은 흔적을 남기지 않습니다. 한 달
뒤에는 당신을 포함해 아무도 왜 하필 그 값이 설정되었는지 기억하지 못합니다.

## 4단계. 브라우저에서 열기

📍 **어디서:** 노트북에서.

**곧 무슨 일이 일어나나:** 애플리케이션은 클러스터 안에 살고 있어 밖에서는 보이지 않습니다. 아래
명령은 당신의 노트북에서 안쪽으로 터널을 놓습니다.

```bash
# port-forward = 노트북에서 클러스터 안으로 놓는 터널로, 명령이 실행되는 동안 살아 있습니다.
#   svc/rickroll   rickroll이라는 이름의 Service로 터널을 놓으면, 그것이 다시
#                  요청을 살아 있는 애플리케이션 복제본으로 라우팅합니다
#   8080:80        왼쪽 숫자는 노트북의 포트, 오른쪽은 클러스터 안 Service의 포트입니다
kubectl port-forward svc/rickroll 8080:80
```

이 명령은 끝나지 않습니다. 당신이 멈출 때까지 터널을 열어 둡니다. <http://localhost:8080>을 여세요.

**보여야 할 것:** 아른거리는 제목, 노래의 한 소절, 그리고 맨 아래에 — Pod 이름. 그것을 클러스터가
보여주는 것과 대조해 보세요.

📍 **어디서:** 두 번째 터미널 창에서. 첫 번째 창은 터널로 바쁩니다. 명령이 실행되는 동안에는 거기에
아무것도 입력할 수 없습니다. 새 창을 열고 거기서 접근 파일을 다시 설정하세요. 환경 변수는 새 창으로
넘어오지 않습니다.

```bash
export KUBECONFIG=~/lab.kubeconfig
```

```bash
# get pods = "실행 중인 복제본을 보여줘".
#   -l app=rickroll   모든 Pod가 아니라 레이블 app=rickroll이 붙은 것만 보여준다 —
#                     Service가 Pod를 찾는 데 쓰는 바로 그 레이블입니다
kubectl get pods -l app=rickroll
```

이름이 일치합니다. 페이지를 서빙한 것은 바로 이 복제본입니다.

터널을 닫으려면 — `Ctrl+C`.

## 검사

📍 **어디서:** 노트북에서, `kubectl`로 작업하던 바로 그 터미널 창에서.

```bash
# 랩 폴더에서 실행하세요: 스크립트는 자기 옆에서 파일을 찾습니다.
# 이름 앞의 ./ 는 "바로 여기서 파일을 실행하라"는 뜻이며, 시스템 폴더에서 찾으라는 게 아닙니다
./check.sh
```

⚠️ **Windows에서는 스크립트를 PowerShell이 아니라 WSL에서 실행합니다** — 설정 방법은 랩 0의 시작
부분에 적혀 있습니다. WSL 없이도 랩을 완료할 수는 있지만, 아티팩트 리포트는 나오지 않습니다.

스크립트는 매니페스트가 적용되었다는 사실이 아니라 실질적인 동작을 검사합니다. 애플리케이션이 HTTP로
응답하고, 응답에 Pod 이름이 들어 있으며, 그 이름이 실제로 실행 중인 복제본과 일치하는지를요.

## 정리

애플리케이션은 랩 2, 3, 4에서 필요하니 지금은 삭제하지 마세요. 유지 비용은 쌉니다. nginx 복제본
하나는 코어의 100분의 2와 32메가바이트를 요청하고, 삭제할 때가 되면 — 그것은 한 번의 명령이며,
자원은 바로 그 순간 노드의 공유 풀로 돌아옵니다.

## 이제 우리가 할 수 있는 것

- 플랫폼 대시보드가 끝나고 당신 자신의 클러스터가 시작되는 곳을 구분한다
- 파일 하나와 명령 하나로 애플리케이션을 배포한다
- 매니페스트를 읽고 각 블록이 무엇을 위한 것인지 설명한다
- `requests`와 `limits`를 구별한다
- Service가 복제본을 주소 목록이 아니라 레이블로 찾는다는 것을 이해한다
- `port-forward`로 브라우저를 클러스터 안까지 도달시킨다

## vSphere에서라면 이것은

VM 요청, 주소를 받기 위한 네트워크 팀 요청, 인증서를 받기 위한 보안 팀 요청. 잘해야 며칠. 여기서는
— 파일 하나와 명령 하나입니다.

**솔직히, vSphere가 더 편한 지점.** VM을 배포하면 당신은 온전한 머신을 얻습니다. 안으로 들어가
무엇이든 설치하고, 제자리에서 고치고, 그대로 계속 실행되게 둘 수 있습니다. Pod는 다르게 만들어져
있습니다 — 불변이고, "안으로 들어가 고치기"는 거기서 말이 되지 않습니다. 다음 재시작 때 수정이
사라지기 때문이죠. 이것은 규율을 잡아 주지만, 처음에는 짜증스럽고, 그렇지 않은 척하는 것은
어리석은 일입니다.
