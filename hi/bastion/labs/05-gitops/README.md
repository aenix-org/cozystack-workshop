## यह क्यों ज़रूरी है

अभ्यास खत्म हुआ। यहाँ से आगे यह एक असल काम है।

बिज़नेस को एक आंतरिक सेवा चाहिए, नाम **"Passes"**: कर्मचारी मोबाइल ऐप के ज़रिए मेहमान के लिए पास ऑर्डर करता है, सुरक्षाकर्मी प्रवेश-द्वार पर सूची देखते हैं, और प्रबंधन महीने में एक बार रिपोर्ट देखता है। आप प्लेटफ़ॉर्म टीम में हैं, और इसे शिप करना आपका काम है।

सेवा के पीछे कई टीमें होंगी, और प्लेटफ़ॉर्म टीम में आप तीन लोग हैं। और यहीं से वह वजह शुरू होती है जिसके चलते यह लैब कामकाजी हिस्से में सबसे पहले आती है।

**जब तीन एडमिन होते हैं तो क्या होता है।** किसी ने डैशबोर्ड के ज़रिए ऐप खड़ा किया। किसी ने `kubectl edit` से लिमिट बदल दी, क्योंकि आधी रात थी और आग लगी हुई थी। किसी ने शुक्रवार को कॉपियों की संख्या बदली और सोमवार तक भूल गया। एक महीने बाद कोई भी दो सवालों का जवाब नहीं दे सकता: **यह सेटिंग ऐसी क्यों है** और **इसे कैसा होना चाहिए**। और जब सब कुछ गिर पड़ता है, तो पता चलता है कि बहाल करने के लिए कुछ है ही नहीं — अवस्था सिर्फ़ क्लस्टर के दिमाग में रहती थी, और क्लस्टर के साथ ही गायब हो गई।

इसका इलाज कोई नियम-कायदा नहीं है, और न ही «चलो सब तय कर लें कि हाथ से नहीं छुएँगे»। इलाज यह है कि हाथ से छूना **बेमानी** बना दिया जाए: क्लस्टर खुद उसे वैसा ही लौटा देगा जैसा था। ठीक यही हम आज चालू करेंगे।

| **Kustomization** | क्लस्टर में एक ऑब्जेक्ट: रिपॉज़िटरी से ठीक-ठीक क्या लागू करना है | **एक डिप्लॉयमेंट जॉब**, लेकिन इसे `kustomize` यूटिलिटी के साथ न उलझाएँ — नाम एक जैसा है, मतलब अलग |

इस लैब के बाकी शब्द — Git, Commit, Branch, Pull request, Reconciliation, Drift, GitRepository, Prune — आगे बढ़ते हुए उसी स्टेप पर पेश किए जाते हैं जहाँ वे पहली बार ज़रूरी होते हैं। इन्हें अभी रटने की ज़रूरत नहीं: क्रिया से अलग होकर ये याद नहीं रहेंगे।

## लैब फ़ोल्डर में क्या है

सारी फ़ाइलें पहले से ही आपकी हैं — आपने उन्हें रिपॉज़िटरी के साथ ले लिया था। कुछ भी नए सिरे से बनाने या टाइप करने की ज़रूरत नहीं: नीचे जहाँ भी `kubectl apply -f नाम.yaml` लिखा है, फ़ाइल यहीं से आती है।

```bash
# यहाँ से आगे सभी कमांड इसी फ़ोल्डर से चलती हैं: `kubectl apply -f` में दिए पथ इसी से गिने जाते हैं।
cd labs/05-gitops
```

| फ़ाइल | यह क्या है | कब काम आती है |
|---|---|---|
| `app/` | जो क्लस्टर में पहुँचना चाहिए: namespace और खुद "Passes" सेवा | इसे अपने Git रिपॉज़िटरी में डालते हैं |
| `flux/` | Flux के लिए दो वर्णन: रिपॉज़िटरी कहाँ से लेनी है और उसमें से क्या लागू करना है | इसे अपने `lab` क्लस्टर पर लागू करते हैं |
| `check.sh` | एक जाँच कि क्लस्टर ने बदलाव खुद Git से खींचा | इसे लैब के अंत में चलाते हैं |

## स्टेप 1. रिपॉज़िटरी बनाना

📍 **कहाँ:** ब्राउज़र में, GitHub पर।

एक नई रिपॉज़िटरी बनाएँ:

| फ़ील्ड | मान | ऐसा क्यों |
|---|---|---|
| नाम | `passes-gitops` | इससे साफ़ रहता है कि यह सेवा की अवस्था है, न कि उसका सोर्स कोड |
| दृश्यता | **Public** | ताकि Flux बिना कुंजियों के इस तक पहुँच सके और आप एक्सेस पर समय न लगाएँ |
| Add a README file | बॉक्स पर टिक लगाएँ | वरना रिपॉज़िटरी खाली रहेगी, बिना किसी branch के, और Flux को पढ़ने के लिए कुछ नहीं मिलेगा |

⚠️ **यहाँ सार्वजनिक रिपॉज़िटरी परीक्षण मंच का जान-बूझकर किया गया सरलीकरण है।** प्रोडक्शन में रिपॉज़िटरी निजी होती है, और Flux उस तक deploy-कुंजी के ज़रिए पहुँचता है। यह SSH कुंजियों के साथ बीस मिनट की और माथापच्ची है, और आज हमारा मक़सद कुछ और है। उसमें क्या रहेगा — बिना एक भी पासवर्ड के मैनिफ़ेस्ट — यह आप खुद देखेंगे: पासवर्ड Git में नहीं रखे जाते, उनके लिए अलग लैब है।

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

रिपॉज़िटरी को अपनी मशीन पर खींचें:

```bash
# clone = रिपॉज़िटरी को पूरी तरह डाउनलोड करना, उसके संपूर्ण संपादन-इतिहास सहित। आपको
# किसी साझा फ़ोल्डर का एक्सेस नहीं, बल्कि डिस्क पर अपनी पूरी कॉपी मिलती है: इसके साथ ऑफ़लाइन भी काम कर सकते हैं।
# `आपका-लॉगिन` की जगह अपना GitHub लॉगिन डालें, वरना कमांड किसी और की रिपॉज़िटरी में चली जाएगी।
git clone https://github.com/आपका-लॉगिन/passes-gitops.git
# clone रिपॉज़िटरी के नाम वाला एक फ़ोल्डर बनाता है। यहाँ से आगे हम उसी के भीतर काम करते हैं।
cd passes-gitops
```

## स्टेप 2. "Passes" सेवा को रिपॉज़िटरी में डालना

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

इस लैब के फ़ोल्डर में दो फ़ाइलें हैं: `app/namespace.yaml` और `app/passes.yaml`। इन्हें अपनी रिपॉज़िटरी में, `apps` फ़ोल्डर में कॉपी करें:

```bash
# apps — वह फ़ोल्डर जहाँ से Flux वर्णन खींचेगा। नाम हमने चुना है, और ठीक यही नाम
# Flux की कॉन्फ़िगरेशन में दर्ज है, इसलिए इसे बेवजह बदलने की कोई वजह नहीं।
#   -p  अगर फ़ोल्डर पहले से मौजूद है तो इसे त्रुटि न मानें
mkdir -p apps
# वर्कशॉप सामग्री से दोनों फ़ाइलें (वे ~/workshop में हैं) अपनी
# रिपॉज़िटरी में कॉपी करें; `*.yaml` दोनों फ़ाइलें एक साथ ले लेगा।
cp ~/workshop/labs/05-gitops/app/*.yaml apps/
```

इन्हें भेजने से पहले, आइए देख लें कि आप क्या डाल रहे हैं।

<details>
<summary><b>करीब से देखें: namespace.yaml और passes.yaml में क्या है</b></summary>

### `namespace.yaml` — अपना एक namespace

```yaml
kind: Namespace
metadata:
  name: passes
```

namespace एक ही क्लस्टर के भीतर एक तार्किक विभाजन है। vSphere में इसका सबसे नज़दीकी उदाहरण vCenter के पेड़ में एक फ़ोल्डर या resource pool है: वही संसाधन, लेकिन अलग दायरा, अलग अधिकार और अलग कोटा।

इसे हाथ से बनाने के बजाय एप्लिकेशन के साथ Git में क्यों रखें: जब सेवा किसी दिन रिपॉज़िटरी से हटेगी, तो Flux namespace भी हटा देगा। ऐसा कोई खाली विभाजन पीछे नहीं छूटेगा जिसके बारे में छह महीने बाद किसी को याद न हो कि इसे क्यों बनाया गया था।

### `passes.yaml` — खुद सेवा

चार ऑब्जेक्ट, `---` पंक्ति से अलग किए गए।

**पहला — nginx कॉन्फ़िगरेशन वाला एक `ConfigMap`।** `ConfigMap` एक टेक्स्ट फ़ाइल को एप्लिकेशन से अलग क्लस्टर में रखता है, और फिर वह फ़ाइल कंटेनर के भीतर माउंट कर दी जाती है। मक़सद यह है कि इमेज को दोबारा बनाए बिना कॉन्फ़िगरेशन बदली जा सके।

अंदर एक साधारण nginx कॉन्फ़िग है। एक पंक्ति ध्यान देने लायक है:

```
sub_filter '__POD__' '$hostname';
```

यह nginx को बताता है: जो पेज वह परोसता है, उसमें `__POD__` टेक्स्ट की जगह उस मशीन का नाम रख दे जहाँ वह चल रहा है। Pod के भीतर मशीन का नाम खुद उस Pod का नाम होता है। इसी तरह पेज बताता है कि उसे किस कॉपी ने परोसा। आगे इसी नाम से आप देखेंगे कि अब दो कॉपियाँ हो गई हैं।

**दूसरा — पेज वाला एक `ConfigMap`।** फ़िलहाल यह एक प्लेसहोल्डर है: असली एप्लिकेशन अगली लैब में आता है, और आज मायने यह नहीं रखता कि सेवा क्या दिखाती है, बल्कि यह कि वह क्लस्टर में **कहाँ से आई**।

**तीसरा — एक `Deployment`।** एप्लिकेशन का वर्णन: कौन-सी इमेज, कितनी कॉपियाँ, तैयारी कैसे जाँचें।

```yaml
spec:
  replicas: 1
```

कितनी कॉपियाँ चलती रखनी हैं। शब्दों पर ध्यान दें: «एक शुरू करो» नहीं, बल्कि «एक बनाए रखो»। यही वह संख्या है जिसे हम Git के ज़रिए बदलेंगे और देखेंगे कि क्या होता है।

```yaml
          readinessProbe:
            httpGet:
              path: /healthz
              port: http
```

तैयारी की जाँच: क्लस्टर इस पते पर दस्तक देता है और जब तक जवाब नहीं मिलता, किसी कॉपी पर ट्रैफ़िक नहीं भेजता। यह Flux को भी चाहिए — हम उससे कहेंगे कि लागू करने के तुरंत बाद सफलता की सूचना देने के बजाय तैयारी का इंतज़ार करे।

**चौथा — एक `Service`।** एक स्थायी नाम जो सभी कॉपियों के आगे खड़ा रहता है। `Service` और Pods के बीच की कड़ी पतों की सूची नहीं, बल्कि शर्त `selector: app: passes` है, यानी «इस लेबल वाले सभी Pods»। इस लेबल वाली एक नई कॉपी आई — वह अपने-आप लोड बैलेंसिंग के दायरे में आ जाती है।

चारों ऑब्जेक्ट में से किसी में भी न पासवर्ड है, न कुंजी, न टोकन। यह कोई संयोग नहीं: जो कुछ Git में पहुँचता है, हमेशा के लिए पहुँच जाता है — इतिहास दोबारा लिखा जा सकता है, लेकिन जिन सबने उसे क्लोन कर लिया, उनके पास पुरानी कॉपी रह जाती है। सीक्रेट्स की यहाँ कोई जगह नहीं; उनके लिए अलग तंत्र और अलग लैब है।

</details>

इसे GitHub भेजें। Git सब कुछ अंधाधुंध याद नहीं रखता, बल्कि वही जो उसे साफ़-साफ़ दिखाया गया — इसीलिए तीन कमांड हैं, हर एक अपना काम करती है:

```bash
# add = उन फ़ाइलों को चिह्नित करना जो इतिहास की अगली प्रविष्टि में जाएँगी।
git add apps
# commit = चिह्नित को एक प्रविष्टि के रूप में सहेजना: सामग्री, लेखक, समय और कारण।
#   -m "..."  वही कारण। यह हमेशा के लिए इतिहास में रहता है, और लोग इसे पढ़ेंगे।
# कमिट फ़िलहाल सिर्फ़ आपके bastion पर है — GitHub में यह अभी नहीं है।
git commit -m "add passes service v1"
# push = जमा हुए कमिट GitHub भेजना। इस कमांड तक वहाँ कुछ नहीं बदलता।
git push
```

**आपको क्या दिखना चाहिए** — ब्राउज़र में, रिपॉज़िटरी के पेज पर, दो फ़ाइलों वाला `apps` फ़ोल्डर। इस बीच क्लस्टर में अभी कुछ नहीं बदला: Git को क्लस्टर के बारे में कुछ पता नहीं।

## स्टेप 3. Flux को अपने क्लस्टर में इंस्टॉल करना

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

Flux आपके क्लस्टर के भीतर कई सेवाएँ हैं। एक Git में जाकर सामग्री डाउनलोड करती है, दूसरी डाउनलोड की गई चीज़ को क्लस्टर में लागू करती है और विचलनों पर नज़र रखती है।

क्लस्टर आपका है, और आप उसके पूर्ण प्रशासक हैं। आप इसे खुद इंस्टॉल करते हैं; प्लेटफ़ॉर्म टीम से पूछने की ज़रूरत नहीं।

सबसे पहले, `flux` कमांड-लाइन टूल। यह आपके bastion पर रहता है, क्लस्टर में नहीं: इससे आप सेवाएँ इंस्टॉल करेंगे और फिर उनसे उनकी अवस्था पूछेंगे।

macOS:

```bash
# Homebrew, Flux प्रोजेक्ट की रिपॉज़िटरी से फ़ॉर्मूला लेकर एक निष्पादन-योग्य फ़ाइल रख देता है।
brew install fluxcd/tap/flux
```

Linux:

```bash
# Flux साइट से आया स्क्रिप्ट आपकी आर्किटेक्चर पहचानता है और फ़ाइल को /usr/local/bin में रख देता है।
#   -s          curl चुपचाप काम करता है, बिना डाउनलोड सूचक के
#   | sudo bash डाउनलोड किया गया टेक्स्ट तुरंत प्रशासक अधिकारों के साथ चलाया जाता है — सिस्टम
#               फ़ोल्डर में लिखने की वजह से वे अधिकार ज़रूरी हैं
curl -s https://fluxcd.io/install.sh | sudo bash
```

Windows (PowerShell, अगर Chocolatey इंस्टॉल है):

```powershell
# choco — Windows के लिए एक तीसरे-पक्ष का पैकेज मैनेजर; यह वही एकल flux.exe फ़ाइल इंस्टॉल करता है।
choco install flux
```

अब हम सेवाओं को खुद क्लस्टर में इंस्टॉल करते हैं:

```bash
# एक्सेस फ़ाइल सेट करें: नीचे की कमांड क्लस्टर में ऑब्जेक्ट बनाती है, और यह मायने रखता है कि किसमें।
export KUBECONFIG=~/lab.kubeconfig
# flux install क्लस्टर में एक `flux-system` namespace बनाता है और सेवाओं को उसमें तैनात करता है।
#   --components=...  ठीक-ठीक कौन-सी इंस्टॉल करनी हैं:
#     source-controller     Git में जाता है और रिपॉज़िटरी की ताज़ा कॉपी रखता है
#     kustomize-controller  डाउनलोड की गई चीज़ को क्लस्टर में लागू करता है और विचलनों पर नज़र रखता है
flux install --components=source-controller,kustomize-controller
```

⚠️ **Enter दबाने से पहले जाँचें कि `KUBECONFIG` कहाँ इशारा कर रहा है।** हम Flux को आपके अपने `lab` क्लस्टर में इंस्टॉल कर रहे हैं, उसमें नहीं जहाँ से वह आपको दिया गया था। शक हो तो — `kubectl get nodes` को `kubernetes-lab-md0-...` जैसे नाम वाला एक नोड दिखाना चाहिए।

**आपको क्या दिखना चाहिए** — जो बन रहा है उसकी सूची, और अंत में सफल इंस्टॉलेशन के बारे में एक पंक्ति:

```
✔ install finished
```

हम चार में से केवल दो सेवाएँ इंस्टॉल करते हैं। पूरा Flux सेट Helm चार्ट भी तैनात कर सकता है और मैसेंजरों में सूचनाएँ भेज सकता है — आज इसकी ज़रूरत नहीं, और हमारे पास बस एक नोड है जिस पर ज़्यादा मेमोरी नहीं है।

पक्का करें कि सेवाएँ चालू हो गईं:

```bash
# -n flux-system — वह namespace जिसमें Flux ने डेरा जमाया। इस फ़्लैग के बिना kubectl
# default namespace में देखता है और कुछ नहीं दिखाता।
kubectl get pods -n flux-system
```

**आपको क्या दिखना चाहिए** — `Running` अवस्था में दो पंक्तियाँ।

<details>
<summary><b>अगर <code>flux</code> CLI इंस्टॉल नहीं हो पाया</b></summary>

बिल्कुल यही चीज़ एक साधारण मैनिफ़ेस्ट से, बिना टूल के, इंस्टॉल हो जाती है:

```bash
# सेवाओं का वही सेट, लेकिन बने-बनाए वर्णन के रूप में: -f डिस्क पर पथ ही नहीं
# बल्कि एक लिंक भी स्वीकार करता है। kubectl फ़ाइल डाउनलोड करेगा और उसकी सामग्री लागू करेगा।
kubectl apply -f https://github.com/fluxcd/flux2/releases/latest/download/install.yaml
```

फ़र्क: इस तरह दो के बजाय चारों सेवाएँ चालू होती हैं। यह मेमोरी पर असर डालेगा, लेकिन लैब फिर भी पूरी हो जाएगी। आगे के टेक्स्ट में `flux ...` कमांड सिर्फ़ अवस्था देखने के लिए चाहिए — इन्हें `kubectl get gitrepository` और `kubectl get kustomization` से बदला जा सकता है, जो वही चीज़ दिखाती हैं, बस थोड़ा कम सलीके से।

</details>

## स्टेप 4. Flux को रिपॉज़िटरी की ओर इशारा करना

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

Flux इंस्टॉल हो गया, लेकिन उसे अभी नहीं पता कि कहाँ जाना है। हम उसे यह दो ऑब्जेक्ट से बताएँगे।

इस लैब के फ़ोल्डर से `flux/gitrepository.yaml` खोलें और `मुझे-बदलें` प्लेसहोल्डर की जगह **अपनी** रिपॉज़िटरी का पता डालें:

```yaml
  url: https://github.com/मुझे-बदलें/passes-gitops
```

<details>
<summary><b>करीब से देखें: gitrepository.yaml और kustomization.yaml में क्या है</b></summary>

### `GitRepository` — कहाँ से लेना है

```yaml
kind: GitRepository
spec:
  interval: 1m
  url: https://github.com/मुझे-बदलें/passes-gitops
  ref:
    branch: main
```

इस ऑब्जेक्ट का एकमात्र काम रिपॉज़िटरी की ताज़ा कॉपी रखना है। यह क्लस्टर में कुछ लागू नहीं करता, यह सिर्फ़ डाउनलोड करता है।

`interval: 1m` — अपडेट के लिए कितनी बार जाना है। एक मिनट लैब के लिए चुना गया है, ताकि आपको इंतज़ार न करना पड़े। प्रोडक्शन में इसे आमतौर पर एक से पाँच मिनट के बीच रखा जाता है, और push पर तुरंत प्रतिक्रिया अंतराल घटाकर नहीं, बल्कि webhook से की जाती है: कुछ बदलते ही GitHub खुद क्लस्टर पर दस्तक देता है।

`ref: branch: main` — किस branch को सत्य का स्रोत मानना है। `main` में मर्ज हुआ सब कुछ क्लस्टर तक जाएगा। दूसरी branch में जो कुछ है, वह नहीं जाएगा। समीक्षा यहीं से आती है: बदलाव पहले अपनी branch में रहता है, जहाँ उसे देखा जा सकता है, और केवल `main` में मर्ज होना ही उसे प्रभावी बनाता है।

### `Kustomization` — क्या लागू करना है

```yaml
kind: Kustomization
spec:
  interval: 1m
  path: ./apps
  prune: true
  sourceRef:
    kind: GitRepository
    name: passes
  wait: true
```

`path: ./apps` — रिपॉज़िटरी के भीतर का फ़ोल्डर। इसमें जो कुछ है, वह क्लस्टर तक जाएगा। इसके बगल की फ़ाइलें — मसलन जड़ में पड़ा `README.md` — नहीं छुई जाएँगी।

यहाँ `interval: 1m` का वही मतलब नहीं जो `GitRepository` में था। वहाँ यह «कितनी बार डाउनलोड करना है» था। यहाँ यह **कितनी बार क्लस्टर की वास्तविक अवस्था को वर्णित अवस्था से रिकॉन्साइल करना है**। अगर Git में कुछ न भी बदला हो, तब भी हर मिनट Flux जाँचता है कि क्लस्टर वर्णन से मेल खाता है या नहीं, और उसे मिला देता है। ठीक इसी पर हम लैब में थोड़ा आगे जाकर फँसेंगे।

`prune: true` — उन ऑब्जेक्ट को क्लस्टर से हटाना जो Git से गायब हो गए। इसके बिना Git पूरा वर्णन नहीं रह जाता: आप रिपॉज़िटरी से फ़ाइल हटाते हैं, लेकिन ऑब्जेक्ट क्लस्टर में चलता रहता है, और छह महीने बाद किसी को समझ नहीं आता कि वह कहाँ से आया। `prune` के साथ वर्णन और हक़ीक़त दोनों दिशाओं में मेल खाते हैं।

`wait: true` — लागू करने के तुरंत बाद सफलता की सूचना न देना, बल्कि जब तक लागू की गई चीज़ तैयार न हो जाए तब तक इंतज़ार करना। फ़र्क ठीक वही है जो «अनुरोध जमा किया» और «अनुरोध पूरा हुआ» के बीच है।

</details>

दोनों लागू करें:

```bash
# -f किसी फ़ाइल की नहीं, फ़ोल्डर की ओर इशारा करता है: उसमें पड़े सभी मैनिफ़ेस्ट लागू होंगे —
# GitRepository भी और Kustomization भी। दोनों flux-system namespace में बनते हैं।
kubectl apply -f flux/
```

देखते हैं इससे क्या निकला:

```bash
# हम Flux से रिकॉन्साइल की अवस्था पूछते हैं।
#   --watch  खिड़की को व्यस्त रखो और बदलाव होते ही पंक्ति ताज़ा करो
# READY: True का मतलब रिपॉज़िटरी की सामग्री क्लस्टर तक पहुँची और लागू हो गई।
# REVISION — branch और अभी लागू कमिट का छोटा पहचानकर्ता।
flux get kustomizations --watch
```

**आपको क्या दिखना चाहिए** — कुछ दर्जन सेकंड बाद, `Ready: True` अवस्था और लागू कमिट का हैश:

```
NAME     REVISION            SUSPENDED  READY  MESSAGE
passes   main@sha1:a1b2c3d   False      True   Applied revision: main@sha1:a1b2c3d
```

`Ctrl+C` से देखना बंद करें और देखें कि क्लस्टर में क्या आया:

```bash
# all — मुख्य ऑब्जेक्ट प्रकारों के लिए एक साथ शॉर्टहैंड: Pods, Deployment, Service और बाकी।
# `passes` namespace आपने हाथ से नहीं बनाया: वह एप्लिकेशन के साथ रिपॉज़िटरी से आया।
kubectl get all -n passes
```

**आपने हाथ से कुछ लागू नहीं किया।** आपने GitHub में टेक्स्ट डाला, और क्लस्टर ने उसे खुद खींच लिया। इसके और `kubectl apply -f` के बीच का फ़र्क सुविधा का नहीं — बल्कि यह है कि अब एक ही जगह है जहाँ लिखा है कि चीज़ें कैसी होनी चाहिए।

## स्टेप 5. `git push` के ज़रिए पहला बदलाव

📍 **कहाँ:** bastion पर, रिपॉज़िटरी फ़ोल्डर में।

"Passes" सेवा के लिए एक कॉपी काफ़ी नहीं: सुरक्षाकर्मी सूची चौबीसों घंटे देखते हैं, और एप्लिकेशन के अपडेट से प्रवेश-द्वार ठप नहीं होना चाहिए। दो लगाते हैं।

पहले आप `kubectl scale` चलाते। अब — फ़ाइल में एक संपादन।

`apps/passes.yaml` खोलें और बदलें:

```yaml
spec:
  replicas: 2
```

इसे भेजें:

```bash
# पहली बार भेजने जैसे ही तीन कदम: फ़ाइल चिह्नित करो, कारण के साथ सहेजो, भेजो।
git add apps/passes.yaml
git commit -m "passes: two replicas so the gate does not go dark during rollout"
git push
```

अब क्लस्टर देखें और इंतज़ार करें:

```bash
# -w = «देखो और जोड़ते रहो»: खिड़की व्यस्त रहती है, हर बार जब कॉपियों की अवस्था
# बदलती है तब एक नई पंक्ति आती है। बाहर निकलने के लिए Ctrl+C।
kubectl get pods -n passes -w
```

**आपको क्या दिखना चाहिए** — एक मिनट के भीतर दूसरी कॉपी आ जाती है। इसे आपने नहीं बनाया।

एक मिनट इंतज़ार नहीं करना चाहते — तो आप Flux से अभी रिकॉन्साइल करने को कह सकते हैं:

```bash
# reconcile = «अभी रिकॉन्साइल करो, अगले मिनट का इंतज़ार किए बिना»।
#   kustomization passes  किस ऑब्जेक्ट को रिकॉन्साइल करना है
#   --with-source         पहले Git में ताज़ा कमिट के लिए जाओ और तभी लागू करो;
#                         इस फ़्लैग के बिना रिकॉन्साइल पहले डाउनलोड की गई कॉपी के आधार पर चलेगा
flux reconcile kustomization passes --with-source
```

कमिट संदेश पर ध्यान दें। `two replicas so the gate does not go dark during rollout` — यही कारण है। छह महीने बाद, जब कोई पूछेगा «यहाँ दो क्यों हैं, एक क्यों नहीं», तो जवाब पाँच सेकंड में मिल जाएगा:

```bash
# log = कमिट का इतिहास, सबसे ताज़ा ऊपर।
#   --oneline         प्रति कमिट एक पंक्ति: एक छोटा पहचानकर्ता और कारण का टेक्स्ट
#   apps/passes.yaml  केवल वही कमिट दिखाओ जिन्होंने ठीक इसी फ़ाइल को छुआ
git log --oneline apps/passes.yaml
```

न डैशबोर्ड, न `kubectl` ऐसा निशान छोड़ते हैं।

## स्टेप 6. जाँचते हैं कि सब कुछ नियंत्रण में है

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

रात, एक घटना, सेवा के पास कॉपियाँ कम हैं। आप वही करते हैं जो हमेशा करते थे:

```bash
# कॉपियों की संख्या सीधे क्लस्टर में बदलें, Git को दरकिनार करते हुए — जैसे आज तक करते आए।
#   -n passes  एप्लिकेशन इसी namespace में रहता है; फ़्लैग के बिना कमांड उसे नहीं ढूँढ पाएगी
kubectl scale deployment passes -n passes --replicas=5
```

```
deployment.apps/passes scaled
```

काम कर गया। जाँचते हैं:

```bash
# READY कॉलम «तैयार/आदेशित» की तरह पढ़ा जाता है: कितनी कॉपियाँ जवाब देती हैं और कितनी होनी चाहिए।
kubectl get deployment passes -n passes
```

पाँच कॉपियाँ। एक मिनट रुकें और फिर देखें:

```bash
# वही कमांड। फ़र्क सिर्फ़ इतना कि दोनों बार चलाने के बीच एक मिनट बीत गया।
kubectl get deployment passes -n passes
```

**आप क्या देखेंगे:**

```
NAME     READY   UP-TO-DATE   AVAILABLE   AGE
passes   2/2     2            2           8m
```

फिर से दो कॉपियाँ। आपकी कमांड चली और फिर रद्द कर दी गई।

> **आगे पढ़ने से पहले रुकें और सोचें।**
>
> इसे किसने रद्द किया? यह चुपचाप क्यों हुआ, आपकी कमांड के जवाब में एक भी त्रुटि के बिना? और सबसे अहम: क्या यह कोई खराबी है जिसे ठीक करना है, या यह वैसा ही है जैसा सोचा गया था?

<details>
<summary><b>उत्तर, और इस त्रुटि से कहीं व्यापक एक सबक</b></summary>

इसे Flux ने रद्द किया, और ठीक इसी के लिए उसे इंस्टॉल किया गया था।

हर मिनट में एक बार `Kustomization` Git में जो है उसे लेकर क्लस्टर में जो है उससे तुलना करता है। Git कहता है `replicas: 2`। क्लस्टर में निकलीं `5`। एक विचलन — यानी क्लस्टर ग़लत है, क्योंकि सत्य का स्रोत वह नहीं है।

**`kubectl scale` ने त्रुटि क्यों नहीं लौटाई।** वह लौटा भी नहीं सकती थी: उसने ईमानदारी से ठीक वही किया जो उससे कहा गया। Kubernetes ने बदलाव स्वीकार किया, कॉपियाँ सचमुच चालू हुईं। एक मिनट बाद रिकॉन्साइल आया और वर्णित अवस्था बहाल कर दी। किसी ने किसी से बहस नहीं की — अलग-अलग तंत्रों में से हर एक अपने नियमों से चला।

**यह फ़ीचर क्यों है, बग नहीं।** उस तकलीफ़ पर लौटें जिससे लैब शुरू हुई थी: आप तीन हैं, किसी ने हाथ से कुछ बदला, और किसी को नहीं पता कि क्या कहाँ सेट है। अब ऐसा नहीं होता। Git के बाहर किया गया बदलाव अगले रिकॉन्साइल तक जीता है — यानी जीता ही नहीं। इससे तीन बातें निकलती हैं:

1. **क्लस्टर को चुपके से ग़लत कॉन्फ़िगर नहीं किया जा सकता।** «अच्छा नहीं माना जाता» नहीं, बल्कि भौतिक रूप से असंभव।
2. **Git हमेशा हक़ीक़त का वर्णन करता है।** «वर्णन करना चाहिए» नहीं — वह वर्णन करता है, क्योंकि विचलन खुद-ब-खुद मिट जाता है।
3. **क्लस्टर को बहाल करना एक उबाऊ प्रक्रिया बन जाता है।** Flux इंस्टॉल करो, उसे रिपॉज़िटरी दो, इंतज़ार करो। जो कुछ वहाँ था सब लौट आता है, क्योंकि वह सब लिखा हुआ है।

**सबक इस त्रुटि से व्यापक है।** आपने अभी-अभी «लगाया और भूल गए» और «लगातार रिकॉन्साइल करता है» के बीच का फ़र्क देखा। साधारण `kubectl apply` एक गोली है: अवस्था बदली और फिर अपने-आप जीती रहती है, कोई भी उसे खिसका सकता है। रिकॉन्साइल गोली नहीं, बल्कि खिंचाव है: वर्णन लगातार हक़ीक़त को अपनी ओर खींचता रहता है।

वैसे यही तंत्र उन ग़लतियों को भी ठीक करता है जो आपकी नहीं हैं। अगर किसी नोड की खराबी कोई Pod मिटा दे या कोई ग़लती से `Service` हटा दे — वह भी वापस आ जाता है।

**कब यह आड़े आता है।** यह किसी घटना के दौरान आड़े आता है, जब आपको सचमुच कुछ फ़ौरन बदलना होता है और चर्चा का समय नहीं होता। ऐसे मामलों के लिए Flux रुक सकता है:

```bash
# suspend = इस ऑब्जेक्ट के लिए रिकॉन्साइल रोक देना। Flux क्लस्टर को वर्णन तक लाना बंद
# कर देता है, और हाथ से किए बदलाव जीने लगते हैं। इस बीच Git की सामग्री नहीं बदलती।
flux suspend kustomization passes
```

इसके बाद रिकॉन्साइल नहीं चलता, और हाथ से आप कुछ भी कर सकते हैं। इसे उलटने के लिए:

```bash
# resume = रिकॉन्साइल फिर से चालू करना। अगला ही रिकॉन्साइल हाथ से किया सब कुछ हटा देता है।
flux resume kustomization passes
```

⚠️ रुकना एक टाला गया कर्ज़ है: जब तक `Kustomization` रुका हुआ है, Git फिर से हक़ीक़त का वर्णन करना बंद कर देता है, और आप ठीक वहीं लौट आते हैं जहाँ से चले थे। एक ही नियम है: रोका — तो इसे फिर चालू करने का ख़ुद को रिमाइंडर लगा लें।

</details>

## स्टेप 7. `git revert` के ज़रिए रोलबैक

📍 **कहाँ:** bastion पर (bastion टर्मिनल में)।

अब एक असल स्थिति। आप एक बदलाव रोलआउट करते हैं, और वह खराब निकलता है।

एक संपादन करें: मान लें किसी ने, बिना सोचे, मेमोरी को एक ऐसे मान तक निचोड़ दिया जो काम ही नहीं करता। `apps/passes.yaml` में मेमोरी लिमिट बदलें:

```yaml
          resources:
            requests:
              cpu: 20m
              memory: 4Mi
            limits:
              cpu: 300m
              memory: 4Mi
```

इसे भेजें। एक जान-बूझकर किया गया खराब बदलाव उसी रास्ते जाता है जिस रास्ते अच्छा: अभी आपके `push` और क्लस्टर के बीच कोई जाँच नहीं है — और यही इस स्टेप की बात है।

```bash
# वही add, commit, push। कमिट में कारण ईमानदारी से लिखा है — यह पाँच मिनट में काम
# आएगा, जब बदलाव को रद्द करना पड़ेगा।
git add apps/passes.yaml
git commit -m "passes: trim memory limit"
git push
```

हम इंतज़ार करते और देखते हैं:

```bash
# कॉपियों को तब तक देखें जब तक रिकॉन्साइल नया वर्णन न ले आए।
kubectl get pods -n passes -w
```

**आपको क्या दिखना चाहिए** — नई कॉपियाँ चालू नहीं होतीं। `OOMKilled` अवस्था का मतलब है कि प्रक्रिया को मेमोरी लिमिट पार करने के लिए मार दिया गया; `CrashLoopBackOff` का मतलब है कि क्लस्टर पहले ही कॉपी को लगातार कई बार पुनः चालू कर चुका है और अब अगली कोशिश से पहले उत्तरोत्तर ज़्यादा इंतज़ार करता है। Nginx चार मेगाबाइट में नहीं समाता और शुरू होते ही मर जाता है।

```bash
# वही सूची, लेकिन एक ही स्नैपशॉट के रूप में, बिना देखे रहे।
kubectl get pods -n passes
```

```
NAME                      READY   STATUS             RESTARTS   AGE
passes-6c9d4f7b8-2xk4n    1/1     Running            0          12m
passes-7f8a1b2c3-qq7lp    0/1     CrashLoopBackOff   3          90s
```

पुरानी कॉपी अब भी चल रही है — सेवा ज़िंदा है, लेकिन अपडेट अटक गया। रोलबैक का वक़्त है।

**पहले आप कैसे रोलबैक करते:**

```bash
# undo, Deployment को पिछली रिवीज़न पर लौटा देता — संपादन से पहले की सेटिंग्स पर।
kubectl rollout undo deployment/passes -n passes
```

यह कमांड काम करेगी। कॉपियाँ पिछली इमेज और पिछली सेटिंग्स पर लौट आएँगी, और बीस सेकंड में सब ठीक होगा — ठीक उस पल तक जब Flux Git से रिकॉन्साइल करता है। और Git में अब भी `memory: 4Mi` लिखा है। एक मिनट के भीतर टूटी अवस्था वापस आ जाती है।

**`rollout undo` न करें। वहाँ रोलबैक करें जहाँ सत्य रहता है** — Git में:

```bash
# revert = एक नया कमिट जोड़ना जो बताए गए कमिट के बदलावों को रद्द करता है।
#   HEAD       «वर्तमान branch का आख़िरी कमिट» — वही, खराब लिमिट वाला
#   --no-edit  कमिट संदेश के लिए एडिटर न खोलें; Git ख़ुद शीर्षक लिख देता है
git revert --no-edit HEAD
# जब तक रद्द करने वाला कमिट GitHub नहीं भेजा जाता, Flux को उसके बारे में कुछ नहीं पता।
git push
```

**आपको क्या दिखना चाहिए** — `Revert "passes: trim memory limit"` शीर्षक वाला एक नया कमिट, और एक मिनट के भीतर क्लस्टर में फिर से दो काम करती कॉपियाँ।

```bash
# कॉपियाँ फिर चालू होती हैं: काम करने वाली मेमोरी लिमिट वापस आ गई।
kubectl get pods -n passes
# और यहाँ दिखता है कि अभी कौन-सा कमिट लागू है — यह रद्द करने वाले से मेल खाना चाहिए।
flux get kustomizations
```

<details>
<summary><b><code>git revert</code> «वैसा ही लौटा दो जैसा था» से कैसे अलग है</b></summary>

`git revert` खराब कमिट को नहीं मिटाता। यह एक **नया** कमिट जोड़ता है जो खराब कमिट के बदलावों को रद्द करता है। इतिहास में सब कुछ बना रहता है: क्या टूटा, कब देखा गया, और क्या रोलबैक किया गया।

```bash
# -4 — चार सबसे हाल के कमिट दिखाओ; सबसे ऊपर वाला सबसे ताज़ा है।
git log --oneline -4
```

```
9f3c1ab Revert "passes: trim memory limit"
5d2b8e0 passes: trim memory limit
c71a4f9 passes: two replicas so the gate does not go dark during rollout
0e5f2d3 add passes service v1
```

इसकी तुलना उससे करें जैसा यह Git के बिना दिखता है। एक महीने बाद «रुको, क्या हम पहले भी इसी पर ठोकर खा चुके हैं?» सवाल का कोई जवाब नहीं होता: `kubectl rollout undo` कोई निशान नहीं छोड़ता, और `Deployment` का रिवीज़न इतिहास आख़िरी दस रखता है और ऑब्जेक्ट के साथ ही मर जाता है।

यहाँ आपके पास चार पंक्तियाँ हैं जिनसे दिखता है: हाँ, खाई थी, यह रहा कब, यह रहा किसने, यह रहा ठीक-ठीक क्या किया, यह रहा रोलबैक से पहले यह कितनी देर जीवित रहा।

**एक दूसरी कमांड भी है — `git reset`, जो सचमुच इतिहास मिटा देती है।** साझा रिपॉज़िटरी में इसका इस्तेमाल नहीं होता: जो कमिट आपने अपनी मशीन पर मिटाया, वह दो सहकर्मियों की मशीनों पर बना रहता है, और उनका अगला `push` उसे वापस ले आता है। साझा branch में रद्द करना हमेशा `revert` होता है।

</details>

## स्टेप 8. pull request के ज़रिए समीक्षा

📍 **कहाँ:** ब्राउज़र में, GitHub पर।

जिस तकलीफ़ का हम इलाज कर रहे हैं उसका आख़िरी हिस्सा: बदलाव फ़ौरन क्लस्टर तक चला जाता था, और उसे कोई देखता नहीं था। पिछले स्टेप की खराब मेमोरी लिमिट दस सेकंड में समीक्षा में फ़ेल हो जाती — लेकिन समीक्षा थी ही नहीं।

बदलाव के लिए एक branch शुरू करें:

```bash
# checkout -b = एक नई branch शुरू करो और तुरंत उसमें चले जाओ। branch बदलावों की एक अलग
# धारा है: इसमें किए गए कमिट `main` तक नहीं पहुँचते, और इसलिए क्लस्टर तक भी नहीं।
#   passes/version-line  branch का नाम; नाम में तिरछी लकीर की अनुमति है और वह समूहीकरण के काम आती है
git checkout -b passes/version-line
```

`apps/passes.yaml` में पेज की पंक्ति बदलें — मसलन, टेक्स्ट में संस्करण `v1` से `v1.1`। branch भेजें:

```bash
git add apps/passes.yaml
git commit -m "passes: bump the version shown on the page"
# origin — वह नाम जिसके तहत Git उस पते को याद रखता है जहाँ से आपने रिपॉज़िटरी क्लोन की थी।
#   -u origin passes/version-line  GitHub में इसी नाम की branch बनाओ और उसके साथ की
#                                  कड़ी याद रखो, ताकि आगे सिर्फ़ `git push` काफ़ी हो
git push -u origin passes/version-line
```

जवाब में GitHub एक pull request बनाने का लिंक छापता है। उसे खोलें।

**«Files changed» टैब देखें।** इंफ्रास्ट्रक्चर की समीक्षा यही होती है: «पीटर कहता है कि उसने लिमिट ठीक कर दी» नहीं, बल्कि ठोस पंक्तियाँ — पहले और बाद में, उभारी हुई। आपका सहकर्मी ठीक वही देखता है जो क्लस्टर तक जाएगा, और किसी ख़ास पंक्ति पर टिप्पणी छोड़ सकता है।

इस बीच क्लस्टर नहीं बदला, और नहीं बदलेगा: `GitRepository` `main` branch को देखता है, और बदलाव किसी दूसरी branch में रहता है।

**Merge pull request** पर क्लिक करें — बदलाव `main` में उतरता है, और अगला रिकॉन्साइल उसे क्लस्टर तक ले आता है। एक मिनट में हम एक सुरंग खोलते हैं और देखते हैं कि सेवा क्या परोसती है:

```bash
# port-forward = bastion से क्लस्टर के भीतर एक अस्थायी सुरंग।
#   -n passes     वह namespace जिसमें सेवा रहती है
#   svc/passes    कहाँ ले जाते हैं: Service तक, किसी ख़ास कॉपी तक नहीं
#   8080:80       बाईं ओर bastion का पोर्ट, दाईं ओर क्लस्टर के भीतर सेवा का पोर्ट
kubectl port-forward -n passes svc/passes 8080:80
```

📍 **ब्राउज़र में** <http://localhost:8080> — पेज पर `v1.1`। सुरंग `Ctrl+C` से बंद करें।

बदलाव का पूरा मार्ग अब यह है: **branch → pull request → समीक्षा → merge → क्लस्टर**। किसी भी स्टेप पर कोई क्लस्टर में हाथ से नहीं घुसा।

<details>
<summary><b>इसमें से प्रोडक्शन में क्या किया जाता है जो हमने नहीं किया</b></summary>

तीन चीज़ें जो एक कामकाजी रिपॉज़िटरी ऊपर से जोड़ती है:

**Branch सुरक्षा।** GitHub की सेटिंग्स में `main` branch को सीधे push से बंद कर दिया जाता है, और अंदर आने का एकमात्र रास्ता मंज़ूरी वाला pull request है। वरना अनुशासन नेकनीयती पर टिका रहता है, और नेकनीयती रात के तीन बजे टूट जाती है।

**मर्ज से पहले जाँचें।** क्लस्टर तक पहुँचने से पहले ऑटोमेशन मैनिफ़ेस्ट को सिंटैक्स और नीति-अनुपालन के लिए जाँचता है, और टूटे हुए को मर्ज नहीं होने देता।

**कई वातावरण।** आमतौर पर रिपॉज़िटरी में एक नहीं, बल्कि `apps/staging` और `apps/production` फ़ोल्डर होते हैं, हर एक के अपने क्लस्टर में अपना `Kustomization`। बदलाव पहले staging तक जाता है, जमता है, फिर production तक।

हमने यह नहीं किया क्योंकि हर चीज़ अलग एक घंटा है, और इनसे कार्यप्रणाली नहीं बदलती: सत्य का स्रोत अब भी Git है, और Flux अब भी क्लस्टर को उसकी ओर खींचता है।

## जाँच

📍 **कहाँ:** bastion पर, उसी टर्मिनल विंडो में जहाँ आपने `kubectl` के साथ काम किया।

```bash
# लैब फ़ोल्डर में लौटें: स्क्रिप्ट वहाँ रहता है, और आप अपनी रिपॉज़िटरी के फ़ोल्डर में काम कर रहे थे।
cd labs/05-gitops
export KUBECONFIG=~/lab.kubeconfig
# स्क्रिप्ट क्लस्टर में कुछ नहीं बदलता: यह सिर्फ़ अवस्था पढ़ता है और एक रिपोर्ट छापता है।
./check.sh
```

⚠️ **Windows पर स्क्रिप्ट WSL से चलता है**, PowerShell से नहीं — इसे कैसे इंस्टॉल करें, यह लैब 0 की शुरुआत में लिखा है। WSL के बिना भी आप लैब पूरी कर सकते हैं, लेकिन कोई रिपोर्ट-आर्टिफ़ैक्ट नहीं बनेगा।

स्क्रिप्ट यह नहीं जाँचता कि Flux इंस्टॉल है या नहीं, बल्कि यह कि तंत्र काम करता है: Flux की सेवाएँ ज़िंदा हैं, स्रोत आपकी रिपॉज़िटरी की ओर इशारा करता है और उससे सफलतापूर्वक पढ़ता है, क्लस्टर के ऑब्जेक्ट सचमुच Flux के हैं (न कि हाथ से लागू किए गए), सेवा HTTP पर जवाब देती है, और रिकॉन्साइल रुका हुआ नहीं है।

अगर आप चाहें कि स्क्रिप्ट आपकी रिपॉज़िटरी के इतिहास पर भी नज़र डाले — तो उसे बताएँ कि क्लोन कहाँ है:

```bash
# LAB_REPO — वह वेरिएबल जिससे स्क्रिप्ट को पता चलता है कि आपकी रिपॉज़िटरी का क्लोन कहाँ है।
# अगर आपने इसे होम फ़ोल्डर के अलावा कहीं और क्लोन किया है तो अपना पथ डालें।
export LAB_REPO=~/passes-gitops
./check.sh
```

तब यह अतिरिक्त रूप से सत्यापित करेगा कि क्लस्टर में लागू कमिट आपकी branch के आख़िरी कमिट से मेल खाता है, और रोलबैक `revert` के ज़रिए किया गया था।

## सफ़ाई

हम कुछ नहीं हटाते: रिपॉज़िटरी और Flux आगे काम आएँगे — अगली सेवाएँ इसी तरह क्लस्टर में पहुँचेंगी।

जब आप सभी लैब पूरी कर लें, तो सब कुछ एक साथ इस तरह हटा सकते हैं:

```bash
# delete kustomization = रिकॉन्साइल ऑब्जेक्ट को क्लस्टर से हटाना।
#   --silent  दोबारा पुष्टि न माँगें
flux delete kustomization passes --silent
```

`prune: true` की वजह से `Kustomization` जो कुछ लाया था वह सब उसके साथ चला जाएगा: एप्लिकेशन, सेटिंग्स, और खुद `passes` namespace। कुछ भी हाथ से गिनाना नहीं पड़ता और कोई बचा-खुचा नहीं भूलता — क्योंकि जो बनाया गया था उसकी सूची Flux अपने पास रखता है।

वैसे यह GitOps का एक अलग फ़ायदा है जो तुरंत नज़र नहीं आता। किसी सेवा को पूरी तरह हटाना यानी फ़ोल्डर का `git rm` और एक `push`।

## अब हम क्या कर सकते हैं

- क्लस्टर की अवस्था Git में रखना और समझना कि यह `kubectl apply` से कैसे अलग है
- Flux को अपने क्लस्टर में इंस्टॉल करना और उसे किसी रिपॉज़िटरी की ओर इशारा करना
- समझाना कि रिकॉन्साइल क्या है और Git के बाहर किया गया बदलाव क्यों नहीं बचता
- `kubectl rollout undo` के बजाय `git revert` के ज़रिए रोलबैक करना
- इंफ्रास्ट्रक्चर के बदलाव को pull request और समीक्षा के ज़रिए ले जाना

## और vSphere में यह ऐसा होता

सबसे नज़दीकी उदाहरण vRealize Automation में एक blueprint है: वांछित कॉन्फ़िगरेशन अलग से वर्णित होती है और उसी वर्णन से तैनात होती है। लेकिन वहाँ से रास्ते अलग हो जाते हैं। blueprint तैनात करके छोड़ देता है; अगर कोई फिर vCenter में जाकर किसी मशीन की मेमोरी बदल दे, तो blueprint को इसकी ख़बर नहीं होगी। अनुपालन टूल विचलन को एक रिपोर्ट में दिखा देंगे — और बस, उसे सुलझाने कोई इंसान जाता है।

यहाँ विचलन खुद-ब-खुद सुलझ जाता है, हर मिनट, बिना किसी रिपोर्ट और बिना किसी इंसान के।

दूसरा फ़र्क इतिहास के बारे में है। vCenter में एक टास्क लॉग होता है: किसने क्या और कब किया। यह «क्या हुआ» सवाल का जवाब देता है, लेकिन «क्यों» और «कैसा होना चाहिए» का जवाब नहीं देता। Git के पास दोनों हैं: बदलाव का टेक्स्ट, लेखक, कमिट संदेश में कारण, और pull request में चर्चा।

**कहाँ vSphere ज़्यादा सुविधाजनक है, ईमानदारी से।** तीन चीज़ें।

**प्रवेश की बाधा।** vCenter में किसी वर्चुअल मशीन की मेमोरी बदलने के लिए आपको vCenter चलाना आना चाहिए। इसे यहाँ बदलने के लिए आपको Git चलाना आना चाहिए: branch, commit, merge, conflict। जो Git नहीं जानता, उसके लिए यह «ज़्यादा सुविधाजनक» नहीं — यह एक नया पेशा है, और पहले दो हफ़्ते वह पहले से धीमे काम करेगा।

**प्रतिक्रिया की गति।** आपात स्थिति में आप अवस्था अभी बदलना चाहते हैं, न कि किसी branch, समीक्षा और एक मिनट के रिकॉन्साइल के ज़रिए। रुकने का तंत्र मौजूद है, लेकिन उसे इस्तेमाल करना याद रखना पड़ता है और बंद करना भी याद रखना पड़ता है।

**विफलता की स्पष्टता।** जब vCenter में कुछ तैनात नहीं होता, तो आपको त्रुटि वाला एक टास्क दिखाया जाता है। जब यहाँ तैनात नहीं होता, तो आपको `GitRepository` की अवस्था देखनी पड़ती है, फिर `Kustomization`, फिर घटनाएँ, फिर दो सेवाओं के लॉग। निदान परतों में बँटा है, और जब तक आदत न पड़े तब तक यह ईमानदारी से असुविधाजनक है।
