# जाँच स्क्रिप्ट्स

हर लैब फ़ोल्डर में एक `check.sh` होता है। यह जाँचता है कि लैब वाकई पूरी हुई है —
यह नहीं कि "कोई फ़ाइल लागू कर दी गई", बल्कि यह कि वह **सार रूप में काम करती है**।

आप इसे खुद चलाते हैं, जब चाहें। नतीजा — टर्मिनल में एक रिपोर्ट और एक आर्टिफ़ैक्ट फ़ाइल,
जिसे आप कहीं भी संलग्न कर सकते हैं: कम्युनिटी चैट में, सर्टिफिकेशन आवेदन में, अपने
नोट्स में।

## इसे कैसे चलाएँ

```bash
cd labs/03-scale
./check.sh
```

आप bastion (साझा VM, Linux) पर हैं — `bash`, `kubectl` और बाकी सब कुछ जो आपको चाहिए,
पहले से मौजूद है; कुछ भी इंस्टॉल करने की ज़रूरत नहीं। lab cluster तक पहुँच के
क्रेडेंशियल — वही `lab.kubeconfig` जो आपने लैब 0 में बनाया था — स्क्रिप्ट `KUBECONFIG`
वेरिएबल के ज़रिए ढूँढ लेता है:

```bash
export KUBECONFIG=~/lab.kubeconfig
```

> अगर आप लैब्स bastion पर नहीं, बल्कि अपनी खुद की Windows मशीन से कर रहे हैं — WSL कैसे
> इंस्टॉल करें और `lab.kubeconfig` कहाँ से लें, यह laptop किट में बताया गया है:
> [`../../laptop/check/README.md`](../../laptop/check/README.md)।

स्क्रिप्ट `KUBECONFIG` वेरिएबल के ज़रिए खुद तय कर लेता है कि कहाँ देखना है। अगर यह सेट
नहीं है — तो वह आपको यह बता देता है और रुक जाता है।

जिन लैब्स के लिए प्रबंधन क्लस्टर पर किसी टेनेंट तक पहुँच चाहिए, उनके लिए अतिरिक्त रूप से
`COZY_TENANT` वेरिएबल चाहिए — आपके टेनेंट का नाम, उदाहरण के लिए `workshop07`:

```bash
export COZY_TENANT=workshop07
./check.sh
```

## इससे आपको क्या मिलता है

टर्मिनल में — हर जाँच पर एक पंक्ति:

```
[  OK  ] application deployed and responding
[  OK  ] Pod name is injected into the page
[ FAIL ] autoscaling is not configured
         no HorizontalPodAutoscaler found for deployment/rickroll
         hint: apply hpa.yaml from this folder
```

⚠️ **रिपोर्ट लैब फ़ोल्डर में लिखी जाती है और उसमें तारीख़ के साथ समय भी होता है।** अगर
रिपॉज़िटरी साझा है या आपने जाँच कई बार चलाई है, तो वहाँ कई फ़ाइलें जमा हो जाएँगी — नाम में
दिए समय पर ध्यान दें, ताकि किसी और के या किसी पिछले प्रॉग को अपना न समझ बैठें।

इसके साथ एक फ़ाइल `report-<lab>-<date>.md` बनती है — वही नतीजा Markdown में, इकट्ठा किए
गए साक्ष्य के साथ: वर्शन, कमांड का आउटपुट, ऑब्जेक्ट के नाम। यही आर्टिफ़ैक्ट है।

## स्क्रिप्ट के लेखक के लिए आवश्यकताएँ

**सार जाँचें, लागू होने के तथ्य को नहीं।** ख़राब: "कोई Deployment ऑब्जेक्ट मौजूद है"।
अच्छा: "एप्लिकेशन HTTP पर जवाब देता है और जवाब में Pod का नाम मौजूद है"।

**हर विफलता बताती है कि क्या करना है।** बिना संकेत वाली `FAIL` पंक्ति एक दोष है। पाठक
स्क्रिप्ट ठीक इसीलिए चलाता है क्योंकि वह अटक गया है।

**स्क्रिप्ट न कुछ ठीक करता है, न बनाता है।** वह सिर्फ़ पढ़ता है। एकमात्र अपवाद है नेटवर्क
पहुँच जाँचने के लिए एक अस्थायी Pod, जो अपने पीछे खुद साफ़ हो जाता है।

**macOS और Linux पर काम करता है।** कोई GNU-विशिष्ट `sed -i`, `readlink -f`, `date -d`
नहीं। दोनों सिस्टम पर परखें।

**पहली त्रुटि पर नहीं रुकता।** वह हर जाँच चलाता है और पूरी तस्वीर दिखाता है। `set -e` का
इस्तेमाल न करें।

**पासवर्ड या टोकन नहीं छापता।** अगर कोई मान गोपनीय है — `<hidden>` लिखें।

**इडेम्पोटेंट।** लगातार दस बार चलाने से क्लस्टर की स्थिति नहीं बदलती।

## साझा लाइब्रेरी

`check/lib.sh` — साझा फ़ंक्शन, हर स्क्रिप्ट की शुरुआत में सोर्स किए जाते हैं:

- `ok "टेक्स्ट"` / `fail "टेक्स्ट" "संकेत"` / `warn "टेक्स्ट"` — नतीजा छापें
- `need_kubeconfig` — जाँचें कि `KUBECONFIG` सेट है और क्लस्टर जवाब देता है
- `need_tenant` — जाँचें कि `COZY_TENANT` सेट है
- `evidence "शीर्षक" "मान"` — आर्टिफ़ैक्ट में एक साक्ष्य जोड़ें
- `finish` — नतीजा समेटें, रिपोर्ट लिखें, एग्ज़िट कोड लौटाएँ

एग्ज़िट कोड: `0` — सब कुछ पास हो गया, `1` — विफलताएँ हैं। इस तरह स्क्रिप्ट को ऑटोमेशन में
इस्तेमाल किया जा सकता है।
