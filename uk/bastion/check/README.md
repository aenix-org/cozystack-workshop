# Скрипти перевірки

У кожній папці лаби лежить `check.sh`. Він перевіряє, що лабу справді виконано —
не «файл застосовано», а що вона **працює по суті**.

Учасник запускає його сам, коли захоче. Результат — звіт у терміналі та файл-артефакт,
який можна долучити куди завгодно: у чат спільноти, у заявку на сертифікацію, собі в
нотатки.

## Як запустити

```bash
cd labs/03-scale
./check.sh
```

Ви на бастіоні (Linux) — `bash`, `kubectl` і все потрібне вже є, встановлювати нічого не
треба. Файл доступу до навчального кластера — той самий `lab.kubeconfig`, який ви створили
в лабі 0, — скрипт знаходить через змінну `KUBECONFIG`:

```bash
export KUBECONFIG=~/lab.kubeconfig
```

> Якщо ви проходите лаби не на бастіоні, а зі свого комп'ютера на Windows — як
> встановити WSL і де взяти `lab.kubeconfig`, описано в ноутбучному наборі:
> [`../../laptop/check/README.md`](../../laptop/check/README.md).

Скрипт сам зрозуміє, куди дивитися, за змінною `KUBECONFIG`. Якщо її немає — скаже про це
й зупиниться.

Для лаб, де потрібен доступ до тенанта на кластері керування, додатково потрібна
змінна `COZY_TENANT` — ім'я вашого тенанта, наприклад `workshop07`:

```bash
export COZY_TENANT=workshop07
./check.sh
```

## Що отримуєте на виході

У терміналі — по рядку на перевірку:

```
[  OK  ] application deployed and responding
[  OK  ] Pod name is injected into the page
[ FAIL ] autoscaling is not configured
         no HorizontalPodAutoscaler found for deployment/rickroll
         hint: apply hpa.yaml from this folder
```

⚠️ **Звіт кладеться в папку лаби й містить дату з часом.** Якщо репозиторій спільний або
ви проганяли перевірку кілька разів, там назбирається кілька файлів — дивіться на час в
імені, щоб не прийняти чужий чи минулий прогін за свій.

Поряд з'являється файл `report-<лаба>-<дата>.md` — той самий результат у розмітці, разом зі
зібраними свідченнями: версії, вивід команд, імена об'єктів. Це і є артефакт.

## Вимоги до автора скрипта

**Перевіряємо суть, а не факт застосування.** Погано: «існує об'єкт Deployment». Добре:
«застосунок відповідає по HTTP і у відповіді є ім'я Pod».

**Кожен провал пояснює, що робити.** Рядок `FAIL` без підказки — брак. Читач
запускає скрипт саме тому, що застряг.

**Скрипт не лагодить і не створює.** Тільки читає. Єдиний виняток — тимчасовий Pod
для перевірки мережевої доступності, який видаляється за собою.

**Працює на macOS і Linux.** Жодного GNU-специфічного `sed -i`, `readlink -f`,
`date -d`. Перевіряти на обох системах.

**Не падає на першій помилці.** Проганяє всі перевірки й показує повну картину.
`set -e` не використовувати.

**Не друкує паролі й токени.** Якщо значення секретне — писати `<приховано>`.

**Ідемпотентний.** Запуск десять разів поспіль не змінює стан кластера.

## Спільна бібліотека

`check/lib.sh` — спільні функції, підключається на початку кожного скрипта:

- `ok "текст"` / `fail "текст" "підказка"` / `warn "текст"` — вивід результату
- `need_kubeconfig` — перевірити, що `KUBECONFIG` заданий і кластер відповідає
- `need_tenant` — перевірити, що заданий `COZY_TENANT`
- `evidence "заголовок" "значення"` — додати свідчення в артефакт
- `finish` — підбити підсумок, записати звіт, повернути код повернення

Код повернення: `0` — усе пройшло, `1` — є провали. Так скрипт можна використовувати
в автоматиці.
