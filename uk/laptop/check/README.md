# Скрипти перевірки

У кожній папці лаби лежить `check.sh`. Він перевіряє, що лаба справді виконана —
не «файл застосовано», а **працює по суті**.

Ви запускаєте його самі, коли захочете. Результат — звіт у терміналі та файл-артефакт,
який можна прикласти будь-куди: у чат спільноти, у заявку на сертифікацію, собі в
нотатки.

## Як запустити

```bash
cd labs/03-scale
./check.sh
```

### Якщо у вас Windows

Скрипти написані на bash і в самому Windows не запустяться. Потрібен **WSL** — підсистема
Linux, яка встановлюється однією командою в PowerShell від імені адміністратора:

```powershell
wsl --install
```

Комп'ютер попросить перезавантаження, після нього відкриється консоль Ubuntu. Далі все як у
всіх, тільки `kubectl` усередині WSL потрібен свій:

```bash
sudo snap install kubectl --classic
```

Файл доступу до навчального кластера — той самий `lab.kubeconfig`, який ви створили в
лабі 0, — скрипт знаходить через змінну `KUBECONFIG`. Якщо ви зберегли його всередині
WSL, шлях звичайний:

```bash
export KUBECONFIG=~/lab.kubeconfig
```

Якщо зберегли на диск Windows — копіювати його в WSL не потрібно, диски видно зсередини
за шляхом `/mnt/c/...`. Підставте своє ім'я користувача Windows і папку, куди зберегли:

```bash
export KUBECONFIG=/mnt/c/Users/<ваше-ім'я>/lab.kubeconfig
```

⚠️ **Якщо WSL встановити не можна** — на корпоративному ноутбуці це часта ситуація — лаби
все одно проходяться повністю, крім автоперевірки. Звіт-артефакт у цьому разі не
вийде: попросіть колегу з Linux чи macOS прогнати скрипт по вашому kubeconfig або
прикладіть до заявки вивід команд із розділу «Перевірка» відповідної лаби.

Скрипт сам зрозуміє, куди дивитися, за змінною `KUBECONFIG`. Якщо її немає — скаже про це
й зупиниться.

Для лаб, де потрібен доступ до тенанта на кластері керування, додатково потрібна
змінна `COZY_TENANT` — ім'я вашого тенанта, наприклад `workshop07`:

```bash
export COZY_TENANT=workshop07
./check.sh
```

## Що отримуєте на виході

У терміналі — по рядку на перевірку:

```
[  OK  ] application deployed and responding
[  OK  ] Pod name is injected into the page
[ FAIL ] autoscaling is not configured
         no HorizontalPodAutoscaler found for deployment/rickroll
         hint: apply hpa.yaml from this folder
```

⚠️ **Звіт кладеться в папку лаби й містить дату з часом.** Якщо репозиторій спільний або
ви прогонили перевірку кілька разів, там накопичиться кілька файлів — дивіться на час в
імені, щоб не прийняти чужий чи минулий прогін за свій.

Поряд з'являється файл `report-<лаба>-<дата>.md` — той самий результат у розмітці, разом зі
зібраними свідченнями: версії, вивід команд, імена об'єктів. Це і є артефакт.

## Вимоги до автора скрипта

**Перевіряємо суть, а не факт застосування.** Погано: «існує об'єкт Deployment». Добре:
«застосунок відповідає по HTTP і у відповіді є ім'я Pod'а».

**Кожен провал пояснює, що робити.** Рядок `FAIL` без підказки — брак. Читач
запускає скрипт саме тому, що застряг.

**Скрипт не лагодить і не створює.** Лише читає. Єдиний виняток — тимчасовий Pod
для перевірки мережевої доступності, який видаляється за собою.

**Працює на macOS і Linux.** Жодного GNU-специфічного `sed -i`, `readlink -f`,
`date -d`. Перевіряти на обох системах.

**Не падає на першій помилці.** Прогонить усі перевірки й показує повну картину.
`set -e` не використовувати.

**Не друкує паролі й токени.** Якщо значення секретне — писати `<приховано>`.

**Ідемпотентний.** Запуск десять разів поспіль не змінює стан кластера.

## Спільна бібліотека

`check/lib.sh` — спільні функції, підключається на початку кожного скрипта:

- `ok "текст"` / `fail "текст" "підказка"` / `warn "текст"` — вивід результату
- `need_kubeconfig` — перевірити, що `KUBECONFIG` заданий і кластер відповідає
- `need_tenant` — перевірити, що заданий `COZY_TENANT`
- `evidence "заголовок" "значення"` — додати свідчення в артефакт
- `finish` — підвести підсумок, записати звіт, повернути код виходу

Код виходу: `0` — все пройшло, `1` — є провали. Так скрипт можна використовувати
в автоматиці.
